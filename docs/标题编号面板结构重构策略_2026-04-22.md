# 标题编号面板结构重构策略（2026-04-22）

## 1. 背景

当前标题编号面板的问题，不是单纯“视觉不够美”，而是**信息架构与任务路径失衡**。

现状有三个同时存在的结构性矛盾：

1. 规格层原本存在 `简单 / 组合 / 专家` 三模式心智，但实现层已经被固定成“所有编辑器始终可见”的模式。
2. 右侧编辑区按照 schema 平铺字段，而不是按照用户任务组织编辑单元。
3. 左侧列表与右侧详情都在重复表达“当前级别长什么样”，造成高密度重复信息。

因此，这个面板反复重构但仍然“重、满、累”，不是因为卡片不够多，也不是因为折叠不够强，而是因为**编辑对象、默认暴露层级、结果反馈位置**没有被稳定定义。

---

## 2. 当前状态审阅

### 2.1 当前实现的关键事实

- 标题编号面板当前是固定三段结构：
  - 概览卡
  - 编号方案卡
  - 按级编辑区
  - 非编号标题折叠区
- 右侧详情区直接平铺：
  - `编号规则`
  - `标题格式`
  - `底部预览`

对应代码：

- `src/ui/panels/heading_numbering_panel.py:421`
- `src/ui/panels/heading_numbering_panel.py:465`
- `src/ui/panels/heading_numbering_panel.py:586`

### 2.2 当前测试已经锁定的决策

现有测试已经把下面两条行为锁死：

1. **固定三段布局，不再允许旧的 mode switch / stacked widget 路线**
   - `tests/test_heading_numbering_logic.py:153`

2. **所有编辑器始终可见，不再允许旧的 source/action override UI**
   - `tests/test_heading_numbering_logic.py:175`

这意味着：

- 问题不是“暂时还没折叠”，而是当前产品决策明确倾向“可发现性优先”。
- 但这种“全量暴露”已经把阅读负担推高到不可接受。

### 2.3 为什么当前界面阅读负担大

主要不是风格，而是结构：

1. **字段平权**
   - `启用编号`、`编号样式`、`前缀`、`后缀`、`生成 TOC`、`引用显示`、`段前/段后` 等控件在视觉上几乎同权。
   - 用户难以快速判断“哪几个是核心决策，哪几个只是次级参数”。

2. **重复摘要**
   - 左侧列表已经展示当前级别的编号结果与标题样式摘要。
   - 右侧又把完整参数全量展开。
   - 用户必须在两套粒度之间来回对照。

3. **结果反馈位置滞后**
   - 当前预览放在详情底部。
   - 用户先读大量字段，再看到结果。
   - 操作体验更像“填表”，而不是“调规则”。

4. **分组形式仍然服务字段，不服务任务**
   - `编号规则` 与 `标题格式` 是字段域分组，不是任务分组。
   - 用户真实任务其实是：
     - 这个级别要不要编号
     - 编号长什么样
     - 是否进入目录/引用
     - 标题长什么样

## 3. 可借鉴的方法论

这次不建议继续凭“观感”做结构决策，而应借鉴成熟方法论。

### 3.1 Carbon Forms：按任务分组，不按数据结构平铺

Carbon 的表单模式强调：

- 相关任务应放在同一节标题下，方便扫描；
- 标签要简洁；
- 只在真正相关时才渐进暴露额外输入；
- 若用户大概率会读完整内容，不应为了省空间而强行用 accordion。

参考：

- Carbon Forms Pattern  
  https://carbondesignsystem.com/patterns/forms-pattern/
- Carbon Accordion Usage  
  https://v10.carbondesignsystem.com/components/accordion/usage/

对本面板的启发：

- 不能再按 `enabled / chain / title_separator / include_in_toc` 这种字段顺序排。
- 必须按“编号构造 / 输出行为 / 标题样式”这类任务组排。
- 不应该把高频核心字段折进 accordion。

### 3.2 Microsoft Progressive Disclosure：只有“有时需要”的内容才应该折叠

Microsoft 的 progressive disclosure 指南强调：

- 只有当信息“仅在部分场景、部分时间才需要”时，才适合做渐进展开；
- 如果信息默认显示且用户几乎不会主动隐藏，就不该用 progressive disclosure；
- 若附加信息已经构成独立子任务或让其他内容更难读，应考虑单独表面，而不是简单折叠。

参考：

- Progressive Disclosure Controls  
  https://learn.microsoft.com/en-us/windows/win32/uxguide/ctrl-progressive-disclosure-controls

对本面板的启发：

- `前缀 / 样式 / 后缀` 不是低频信息，不能折。
- `直接编辑原始模板`、条件分隔符、次级引用样式这类内容才适合折。
- 如果“标题样式细项”本身已经构成独立子任务，就不该继续混在一整块字段墙里。

### 3.3 内部可借鉴的方法：先定边界，再谈视觉

仓库中的 `docs/页码策略重构方案_2026-04-11.md` 给了一个更适合本项目的做法：

- 先明确问题不是“能力缺失”，而是“边界不清 / 语义不一致 / 层间不一致”
- 先写非目标
- 先定单一真相来源与边界
- 再落地 UI 和测试

这比“直接改样式”更适合标题编号面板。

## 4. 本次重构的核心结论

### 4.1 卡片不是主决策

“再拆几张卡片”只能改善表面层次，不能解决核心问题。

只有在卡片承载**任务单元**时，卡片才有价值。

正确：

- `编号长什么样`
- `是否参与目录/引用`
- `标题样式`

错误：

- 把当前已经平铺的 12 个字段分摊进 3 张容器卡片

### 4.2 折叠不是主决策

只有下列内容适合折叠：

- 低频
- 条件性
- 专家项
- 独立子任务

因此：

- `前缀 / 编号样式 / 后缀 / 是否进目录` 这类核心字段不应折叠
- `原始模板`、`chain_separator`、次级引用表现等专家项可折叠

### 4.3 顶层三模式切换也不应该回归

虽然早期 spec 中有 `简单 / 组合 / 专家` 三模式，但顶层 mode switch 会带来：

- 隐藏状态
- 记忆成本
- 测试分叉
- 可发现性与稳定性波动

因此不建议恢复成“整个面板切模式”。

更好的方式是：

- **统一单屏 inspector**
- **默认摘要**
- **局部进入细编辑**

### 4.4 正确的产品类型不是“设置页”，而是“Inspector”

当前交互天然是：

- 左边选一个对象（级别）
- 右边编辑该对象属性

这更像设计工具或 IDE 的 inspector，而不是传统设置页。

因此本面板的结构应围绕：

- 对象选择
- 当前对象结果
- 当前对象属性编辑

来组织，而不是围绕配置 schema 组织。

## 5. 目标结构蓝图

## 5.1 总体模型

标题编号面板应重构为：

**左侧导航 + 右侧 Inspector**

不是：

**左侧摘要列表 + 右侧完整字段表单**

### 目标结构

```text
标题编号
├─ 概览区
│  ├─ 当前方案摘要
│  ├─ 最大级数
│  └─ 级别预览
├─ 左侧：级别导航
│  ├─ 级别 1
│  ├─ 级别 2
│  ├─ 级别 3
│  └─ 级别 4
└─ 右侧：当前级别 Inspector
   ├─ 顶部结果条
   │  ├─ 当前级别名
   │  ├─ 实时编号预览
   │  └─ 来源/状态标记
   ├─ 编号构造
   │  ├─ 启用编号
   │  ├─ 前缀 / 样式 / 后缀（复合编辑器）
   │  └─ 包含上级 / 分隔符
   ├─ 输出行为
   │  ├─ 生成 TOC
   │  ├─ 起始编号
   │  ├─ 引用显示
   │  └─ 标题分隔
   ├─ 标题样式摘要
   │  └─ 一句话摘要 + “调整样式”
   └─ 专家项
      └─ 原始模板编辑
```

---

## 5.2 左侧：只做导航，不做完整摘要

左侧项应保留：

- 级别名称
- 当前编号结果预览
- 轻量状态标记

左侧项不应再保留：

- 完整字体/字号/字形/对齐的整句摘要

原因：

- 左侧的职责是“选对象”
- 不是“阅读对象全部属性”

这能显著降低列表密度，并减少与右侧重复。

---

## 5.3 右侧第一优先级：结果先于参数

当前预览放在详情底部，属于结果反馈过晚。

目标改法：

- 右侧顶部始终先看到：
  - 当前预览编号
  - 是否进目录
  - 当前级别标题效果

推荐形式：

- `级别 1`
- `实时效果：第一章  示例标题 1`
- `目录：包含`

这会把用户操作从“填表”转成“调结果”。

---

## 5.4 编号规则应变成复合编辑器

当前 `编号规则` 最大的问题，不是样式，而是字段拆得太碎。

建议合并为一个复合编辑单元：

### 目标交互

```text
启用编号  [开关]

编号长相
[前缀输入] [编号样式下拉] [后缀输入]
结果：第一章

层级关系
[仅当前级 / 包含上一级 / 包含所有上级]
若需要，再显示 [分隔符]
```

这样用户是在编辑“编号长相”，而不是在读三行互相依赖的字段。

---

## 5.5 标题样式应变成“摘要优先，细项后入”

不建议默认把字体、字号、字形、对齐、行距、段前、段后全部摊开。

建议默认显示：

- `宋体 / 小四 / 加粗 / 左对齐 / 固定值 20pt / 段前 0 / 段后 0`

提供一个明确入口：

- `调整标题样式`

点击后才展开完整细项。

这不是传统 accordion，而是：

- 先给用户一行可判断的摘要
- 确认需要时再进入细编辑

这是“摘要优先”而不是“隐藏优先”。

---

## 5.6 专家项只保留一个明确出口

建议把以下内容统一放进专家区：

- 直接编辑原始模板
- 仅在复杂层级链路下才需要的分隔符
- 未来可能扩展的高级规则

原则：

- 专家项有且只有一个入口
- 入口文案要明确，例如 `高级模板编辑`
- 专家区展开后不影响基础区布局稳定性

---

## 6. 不建议采用的方案

### 6.1 不建议：全量卡片化

如果只是把现有字段重新装进几张卡：

- 主次仍不清
- 阅读路径仍长
- 只是“更整齐”，不是“更易用”

### 6.2 不建议：恢复顶层三模式

原因：

- 会重新引入隐藏状态和切换心智
- 与当前测试和实现方向冲突
- 容易再次演化成“来回定义”

### 6.3 不建议：把 `标题格式` 整块改成普通折叠区

如果样式是当前对象的重要一部分，整个折叠会降低可见性。

正确做法是：

- 保留摘要始终可见
- 仅把细项编辑展开/收起

### 6.4 不建议：继续让左侧显示完整样式摘要

这会让导航区继续承担阅读工作，削弱右侧 inspector 的价值。

## 7. 可执行修改策略

### Phase 1：结构降噪，不改能力

目标：

- 降低阅读负担
- 不改配置语义
- 不改保存结构

动作：

1. 左侧导航降噪，只保留级别、编号预览、轻量状态。
2. 右侧顶部加入固定结果条，把实时预览上移。
3. `编号规则` 改成复合编辑器。
4. `输出行为` 独立成单组。
5. `标题样式` 改成“摘要 + 进入细编辑”。

### Phase 2：专家项边界收紧

目标：

- 把真正低频项隔离出去

动作：

1. 原始模板进入专家区。
2. 条件字段只在相关条件满足时出现。
3. 非编号标题区继续保留折叠，但文案和入口语义要清楚。

### Phase 3：视觉层统一

目标：

- 去掉“参数墙”感

动作：

1. 减少虚线使用，更多依赖留白与弱分隔。
2. 降低输入框边框存在感。
3. 强化顶部结果条和当前级别标题。
4. 让左侧选中态更像导航，而不是表格高亮。

---

## 8. 测试与实现边界

当前已有测试会阻止回到旧路线，因此实施时要遵守：

1. 不恢复 `QStackedWidget` 模式切换。
2. 不恢复旧的 override/action/source UI。
3. 允许右侧采用摘要优先，但不能让核心编辑路径消失。

建议新增测试方向：

1. 左侧列表项不再包含完整样式句子。
2. 当前级别预览位于详情区顶部。
3. `编号长相` 复合编辑器存在，且 `前缀 / 样式 / 后缀` 在同一任务组。
4. 标题样式默认显示摘要，细项通过明确入口展开。

---

## 9. 最终决策

本次重构应采用以下主决策：

1. **不把“卡片化”作为主策略**
2. **不把“折叠化”作为主策略**
3. **不恢复顶层三模式**
4. **把标题编号面板重新定义为 Inspector**
5. **把字段编辑改成任务编辑**
6. **把预览放到高优先级位置**
7. **把专家项与高频项彻底分层**

一句话总结：

> 这次要改的不是“界面皮肤”，而是“编辑模型”。
