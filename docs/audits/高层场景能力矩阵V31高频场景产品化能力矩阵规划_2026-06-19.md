# 高层场景能力矩阵 V31 高频场景产品化能力矩阵规划（2026-06-19）

本文件继续回应“更高层的场景能力矩阵仍不完善，不能出现高频适用场景遗漏或者边界不清晰”的问题。

V30 已经把高层矩阵定义为十个准入槽位，并形成 12 个 pack、15 个 planned family、29 个高频任务族、51 个 request-cell、15 个 Word/OOXML 风险面、13 个控件契约、3 个插件/人工门和 11 个 dashboard source 的自动化基线。但这些只能说明“静态审计链路没有明显断裂”，不能说明用户面向高频任务时已经得到完整产品能力。

V31 的重点是把矩阵从“审计资产齐全”推进到“产品化能力齐全”：每一个高频场景都必须能解释用户入口、事实源、模板/控件、处理范围、规则 profile、对象安全、版本交付、失败回退、报告证据和边界状态。

## 1. 当前结论

当前场景矩阵的核心问题不是顶层 pack 数量不够，而是许多高频任务仍停在下列状态：

| 状态 | 表现 | 风险 |
| --- | --- | --- |
| 静态闭合 | 有 pack/family/request-cell/fixture，但 UI、执行、报告和修复未完全闭环 | 用户看得到概念，却不能稳定完成任务 |
| 边界闭合 | 专业、AI/OCR/LaTeX、复杂图形等已进入插件/人工门 | 边界清楚，但不能冒充核心自动化能力 |
| 证据闭合 | release gate 能证明链路存在 | 证据不等于交互完整，也不等于真实业务深度 |
| 控件闭合 | 场景控件契约与模板管理一致 | 还需要保证同一控件链路被执行模块消费 |
| fixture 闭合 | P1 family 有独立 fixture | fixture 代表性还需扩展到真实业务组合和失败路径 |

因此，V31 不继续盲目新增顶层入口。下一阶段应按“高频任务域 -> 能力槽位 -> 产品成熟度”的方式补强。

## 2. 完整场景能力的三层模型

完善的场景能力不应等同于一个下拉框或一个开关。它至少由三层组成：

| 层级 | 负责什么 | 示例 | 不应负责什么 |
| --- | --- | --- | --- |
| Coverage Pack | 用户心智中的大类入口 | 中文论文、英文期刊、试卷、标书、公文、合同、批量表单 | 每个细分行业都变成顶层入口 |
| Family/Profile/Preset | pack 内的可复用业务组合 | `thesis_cn`、`journal_en`、`exam_teaching`、学生版/教师版、投稿包 | 模板外观细节、一次性会话路径 |
| Capability Contract | 横向能力的稳定契约 | MaterialSchema、CountProfile、DeliveryPreset、ObjectPreflight、PluginGate | UI 文案级临时开关 |

判定一个需求是否进入“完整能力”时，应先确定它属于哪一层：

```text
用户自然说法
-> pack / family / profile / preset / plugin / negative
-> 输入事实源
-> 模板与控件契约
-> 处理范围与执行策略
-> Word/OOXML 风险与对象预检
-> 输出版本与报告
-> fixture、release gate、Workbench drilldown
```

## 4. 能力域矩阵

每个高频场景至少要被下面 12 个能力域扫描。不是每个场景都要启用每一项，但每个场景都要明确“启用、禁用、可选、人工门、负例”的状态。

| 能力域 | 解决的问题 | 高频触发场景 | 完整产品形态 |
| --- | --- | --- | --- |
| InputSourceProfile | 输入来自 DOCX、Markdown、JSON、Excel、LaTeX、PDF/OCR 还是人工资料 | 论文、投稿、试卷、批量、导入 | 输入类型、可信级别、预览、保留中间产物、失败策略 |
| TemplateBaseline | 文档长什么样 | 全部 Word 场景 | 兼容模板、少量场景覆盖、模板管理控件复用 |
| FormatScope | 处理哪些 Word story 和章节 | 论文、长文档、公文、合同、导入 | 正文/摘要/目录/脚注/页眉页脚/文本框/批注/修订的范围声明 |
| MaterialSchema | 字段、图片、签章、附件、人员、项目事实 | 标书、公文、合同、HR、申报、售前 | schema、缺失值策略、字段映射、资料包报告 |
| CountProfile | 字数、词数、字符数、参考文献、图表、display items | 中文论文、英文期刊、申报、标书、披露 | profile-driven multi-metric count，不输出单一不可解释数字 |
| ContentVisibility | 同一源生成不同版本 | 试卷、合同、投稿、披露、批量 | 学生版/教师版、审阅/签署、公开/内部、正式/归档 |
| FormulaPolicy | 公式转换、编号、低置信度处理 | 论文、投稿、技术、试卷、LaTeX 导入 | OMML 优先、图片 fallback、保留原文/标记、人工门 |
| AssetAndImagePolicy | 图片、签章、图表、题注、替换 | 标书、试卷、售前、技术、公文 | 图片角色、尺寸、居中、题注、预览、缺失策略 |
| ObjectPreflight | 保护字段、批注、修订、文本框、OLE、rels、宏 | 合同、投稿、长文档、PDF/OCR、固定表单 | 预检、阻断/降级/跳过、报告、修复入口 |
| DeliveryPreset | 输出哪些版本和文件结构 | 全部高频交付场景 | 命名、目录、DOCX/PDF/ZIP/report、中间产物、失败隔离 |
| BatchPreset | 多记录和批量输出 | HR、证书、标书、Excel 到 Word | 单记录隔离、批量报告、失败续跑、目录规则 |
| PluginManualGate | 专业判断、AI/OCR/LaTeX、复杂图形 | 专业披露、导入、试卷 AI、医疗/法律/IP | 确认状态、报告字段、人工证据、handoff |

## 5. 对外部技术记录的吸纳判断

两份外部记录不作为当前项目实现事实，但 V31 明确吸收其中两类产品原则。

### 5.1 Count Engine 记录

需要吸纳：

- 不做单一“字数统计器”，而做 profile-driven multi-metric count；
- 同时保留 Word-like、中文字符、英文词数、含/不含空格字符、参考文献、图、表、公式、章节等指标；
- 场景只保存 profile、范围和规则来源，执行结果进入报告；
- 报告必须说明采用口径、计入范围、排除范围和不确定项。

落点：

- `CountProfile` 应成为横向能力域，不只属于中文论文；
- 中文论文、英文期刊、申报、标书、披露、试卷都应能挂不同 profile；
- 后续 N2.170 应补“CountProfile 场景覆盖审计”，避免只有 profile 文件而没有场景归属和报告链。

不吸纳：

- 不承诺与 Word、学校系统、投稿系统完全一致；
- 不在场景配置里保存本次统计结果；
- 不把完整 CountEngine 作为场景页第一阶段 UI 的阻塞项。

### 5.2 试卷生成记录

需要吸纳：

- AI 或外部系统只能提供结构化源，程序负责校验、预览、渲染和导出；
- JSON 是机器源，Markdown 是人工预览，Word 是正式交付；
- 学生版/教师版/答案版来自同一结构化源的 DeliveryPreset，不应重复生成不同内容；
- 通用图片能力优先于复杂几何图自动生成；
- 复杂几何、电路、化学结构等应插件化。

落点：

- `exam_education` 是验证 ContentVisibility、DeliveryPreset、FormulaPolicy、AssetAndImagePolicy 的高价值样板；
- 这套模式也应泛化到合同审阅/签署、披露公开/归档、投稿初投/修回、批量个性化文档；
- 后续 N2.167 DeliveryPreset 审计应把试卷多版本作为核心验收样例。

不吸纳：

- 不直接改用 docxtpl 或 Pydantic 作为当前项目必选技术；
- 不把 AI 出题质量和复杂几何图生成纳入核心承诺；
- 不让 Markdown 直接决定最终 Word 版式。

## 6. 边界裁决树

新增高频需求必须按以下顺序判断，避免入口扩散和边界模糊：

1. 是否需要 Word 原生交付。不需要时进入 negative 或外部插件。
2. 是否只是模板外观。是则归 TemplateConfig 和模板管理控件。
3. 是否是资料事实、图片、签章、附件。是则归 MaterialSchema/资料包。
4. 是否是输出版本、命名、目录、PDF/ZIP/报告。是则归 DeliveryPreset/OutputConfig。
5. 是否是多记录、多人员、多公司、多项目。是则归 BatchPreset。
6. 是否是规则、字数、图表、声明、提交要求。是则归 CountProfile/RuleSource。
7. 是否是固定版位、证书、答题卡、套打。是则归 fixed-layout profile 和 Word risk。
8. 是否触达字段、批注、修订、内容控件、文本框、OLE、rels、宏。是则先走 ObjectPreflight。
9. 是否涉及法律、财务、审计、专利、医学、翻译质量、AI 内容质量、OCR/LaTeX 无损转换。是则进入 PluginManualGate。
10. 是否能从导入边界 handoff 到目标 pack。能则必须有 handoff 报告和回退策略。

只有同时满足“独立用户心智、独立事实源、独立交付方式、独立 Word 风险或独立插件边界、独立证据链”时，才考虑新增顶层 coverage pack。

## 7. 高频遗漏风险清单

下列不是 release gate blocker，但它们会让矩阵在用户视角下显得“不完整”。后续路线必须优先处理。

| 风险 | 影响场景 | 需要补的能力 |
| --- | --- | --- |
| 前台 drilldown 不足 | 全部 | 用户无法从 pack 看 request-cell、fixture、Word risk、plugin boundary、handoff |
| MaterialSchema 横向缺口 | 标书、公文、合同、HR、申报、售前、专业披露 | schema 归属、字段映射、缺失策略、资料包报告 |
| DeliveryPreset 仍偏薄 | 试卷、投稿、合同、披露、批量、标书 | 多版本输出、命名、目录、PDF/ZIP、报告等级、失败隔离 |
| CountProfile UI 和报告链不足 | 中文论文、英文期刊、申报、标书、披露 | profile 选择、范围确认、多口径报告 |
| 公式/输出/水印归属易回流模板 | 论文、投稿、公文、标书、技术、导入 | FormulaPolicy、DeliveryPreset、WatermarkPolicy 的场景归属审计 |
| fixed-layout profile 浏览器薄 | 证书、登记表、答题卡、套打 | `w:trHeight`、文本框、内容控件、占位符残留的可视化说明 |
| ObjectPreflight 修复入口不够 | 合同、投稿、长文档、导入 | 预检结果到模块跳过、降级、修复按钮的闭环 |
| 专业/导入插件生态未成形 | professional_disclosure、import_ai_boundary | plugin/manual gate 只是边界，不是自动化产品能力 |
| ambiguous 解决 UI 不足 | 产品手册、报价方案、证书材料、双语文档、通知/申请表 | 澄清问题、候选 pack 对比、决策记录 |
| 真实业务 fixture 深度不足 | 全部 P1/P1_CANDIDATE | 不只是独立 fixture，还要覆盖成功、降级、失败、人工门 |

## 8. 产品成熟度分级

V31 建议继续使用静态闭合与产品成熟度双轨，不允许静态闭合冒充 L5。

| 等级 | 定义 | 可对用户承诺 |
| --- | --- | --- |
| L1 Gray | 文档或规划存在 | 仅规划，不承诺可用 |
| L2 Blue Boundary | 明确边界、人工门或负例 | 能解释为什么不能自动完成 |
| L3 Yellow | 有 route、profile、schema 或 first-slice 执行证据 | 可试用，但需要明显提示限制 |
| L4 Orange | UI/执行/报告/fixture/release gate 基本闭环 | 可作为主流程能力，但保留特定缺口 |
| L5 Green | 高频成功/降级/失败路径均产品化，真实业务 fixture 足够 | 可稳定推荐给普通用户 |

当前矩阵里大多数 pack 是 orange/yellow/blue，而不是 green。后续所有“完善”都应以 L5 缺口为单位推进。

## 9. N2.165 之后的路线

V31 将 V30 的后续路线细化如下：

## 10. V31 判定

高层场景能力矩阵要“完善”，不能只靠 pack ready、request-cell 足量或 release gate 通过。真正的完善标准是：

- 高频用户说法都能落到明确承载层；
- 每个承载层都有事实源、模板/控件、范围、规则、对象安全、交付和边界解释；
- 专业判断、AI/OCR/LaTeX、复杂图形、非 Word 交付不被核心能力过度承诺；
- 用户能在前台 drilldown 看到为什么属于这个场景、触碰哪些风险、需要哪些资料、输出哪些版本、失败如何处理；
- 每个 P1 场景都有成功、降级、失败/人工门的真实业务证据；
- 静态闭合与产品成熟度分开记录，Green/L5 只能给到真正产品闭环的能力。

因此，V31 的结论是：当前 12 个顶层 pack 不宜继续盲目扩张；更应该补齐 MaterialSchema、DeliveryPreset、CountProfile、InputSourceProfile、FormulaPolicy、ObjectPreflight、PluginManualGate 和前台 drilldown。只有这些横向能力补齐后，高频场景才不会在真实使用时出现遗漏、断链或边界含混。
