# 高层场景能力矩阵 V10 高频覆盖与边界治理规划（2026-06-16）

## 1. 文档定位

本文继续深化“高层场景能力矩阵怎样才算完善”。V7/V8/V9 已经把场景从 6 个可执行入口扩展到 planning family、资料 schema、CountProfile、ObjectPreflight 和 DeliveryPreset。V10 不再继续扩名单，而是建立一套治理规则：

```text
任何高频文档需求，先判断归属层，再判断成熟度，再决定是否进入 UI、执行和报告。
```

本文用于约束后续 `ScenePanel`、`scene_family_registry`、`material_schema_registry`、CountEngine、ObjectPreflight、DeliveryPreset、Workbench、报告和测试。它重点解决两个风险：

1. 高频适用场景被遗漏；
2. 高频需求虽然有名字，但边界不清，最后变成散乱功能点。

## 2. V10 一句话结论

完善的场景能力矩阵不是“有很多场景名”，而是：

```text
高频任务族有归属；
横切工作流有承载；
模板参数不越界；
资料、计数、对象风险和交付 preset 能同源；
专业判断有边界或插件；
Workbench、报告和测试能证明链路闭合。
```

因此，后续不能再按“缺什么控件补什么控件”推进，而要按下面的裁决链推进：

```text
用户需求
-> 高频任务族？
-> 横切工作流？
-> 承载层？
-> 模型字段？
-> UI/执行/报告/测试证据？
-> 不承诺边界？
```

只要其中一环说不清，这个需求就不能算完整场景能力。

## 3. 当前事实基线

### 3.1 P0 可执行入口

当前顶层可执行入口仍应保持 6 个：

| 入口 | 角色 | V10 收口要求 |
| --- | --- | --- |
| `custom` | 手动组合 | 只做自由组合和临时任务，不暗含专业规则 |
| `thesis` | 中文学术论文方向 | 应继续收窄为 `thesis_cn`，不吞英文投稿 |
| `bidding` | 标书/商务投标 | 强化资料包、附件 inventory、正副本、签章和报告 |
| `official` | 公文/行政文书 | 强化文号、编号保留、状态水印、正式/内部稿 |
| `technical` | 技术/工程文档 | 强化 OLE/Visio/嵌入 Excel/域/题注保护 |
| `report` | 通用报告 | 保持轻量，不吞所有专业 profile |

P0 的含义是“可直接执行的主入口”，不是“能力已经 L4 完整”。每个 P0 仍要继续补 profile、报告和测试证据。

## 4. 防遗漏的五轴检查法

任何新需求先过五轴，不直接加按钮。

| 轴 | 要问的问题 | 如果说不清的后果 |
| --- | --- | --- |
| 任务族轴 | 用户自然会怎么描述这件文档工作 | 场景名会失真，入口会膨胀 |
| 工作流轴 | 它主要是在规范化、填充、计数、批量、审阅、打包还是导入 | 会把横切能力误做成碎片场景 |
| 承载层轴 | 它归模板、场景、资料、合规、交付、Workbench 还是插件 | 参数会互相覆盖，UI 语义混乱 |
| Word 风险轴 | 它会触碰哪些 OOXML 对象和高风险 package part | 执行可能破坏 OLE、修订、批注、域、内容控件 |
| 证据轴 | 用户在哪里看到结果、风险、跳过和产物 | 功能不可验收，测试无法锁定 |

V10 要求：只要一个高频需求无法同时回答这五轴，就不能宣布“场景能力已完善”。

## 5. 承载层裁决规则

| 需求表现 | 归属层 | 例子 |
| --- | --- | --- |
| 用户反复用一个业务名描述它 | scene family / profile | 英文投稿、合同交付、HR 批量、表单套打 |
| 只是同一任务的不同输出 | `DeliveryPreset` | 学生版、教师版、审阅稿、签署稿、正式稿、归档包 |
| 只是字段、图片、签章、附件、多实体 | `MaterialSchema` / Assets | 甲乙方、公司名、签章、证照、人员清单 |
| 只是统计规则 | `ComplianceProfile` / CountProfile | 学校字数、期刊 word count、附件 inventory |
| 只是稳定外观默认值 | 模板管理 | 样式、页边距、表格默认边框、页眉页脚外观 |
| 只是本次运行状态 | Workbench / Session | 当前文件、输出目录、确认并继续、执行日志 |
| 触碰高风险 Word 对象 | ObjectPreflight | OLE、Visio、宏、修订、批注、文本框、域、内容控件 |
| 需要外部识别或专业判断 | Plugin / 人工确认 | OCR、完整 LaTeX、AI 内容、法律、财务、IP、审计 |

硬边界：

- 场景不是第二套模板编辑器；
- 模板不是业务策略；
- 输出不是模板参数；
- 水印外观归模板，水印状态和交付版本归场景；
- 公式不是单一模板小项，而是学术、技术、试卷、投稿等场景的专业对象域；
- 行高不是普通段落样式问题，在固定版式套打中它是版位保护策略；
- Workbench 不是配置模型，它负责本次执行证据和用户确认。

## 8. CountEngine 吸纳规则

`count_engine_tech_record.md` 的核心结论必须被吸收进场景矩阵：

```text
不要做单一字数统计器，要做 profile-driven multi-metric CountEngine。
```

V10 对 CountEngine 的规划规则：

- `thesis_cn` 不能只显示一个“字数”，要并列展示中文字符、总字符、不含空格字符、参考文献、图表、公式等指标；
- `journal_en` 要区分 title、abstract、main text、references、display items、figure legends、table captions 等范围；
- `project_application` 和 `regulated_disclosure_documents` 要把章节、附件、表格、图片 inventory 纳入 profile；
- CountProfile 必须有来源、版本、适用范围和不等同于外部系统最终口径的声明；
- Workbench 和报告必须能解释“纳入了哪些范围、排除了哪些范围”。

CountEngine 的成熟度不是“跑出数字”，而是：

```text
profile 来源可见
范围解释可见
多指标结果可见
报告证据可见
测试锁定可见
```

## 9. 试卷/教学场景吸纳规则

`exam_generator_tech_stack_record.md` 的核心结论也必须进入场景矩阵：

```text
JSON 是机器事实源，Markdown 是预览层，Word 是正式输出。
```

V10 对 `exam_teaching` 的规划规则：

- AI 内容生成如果存在，只能是输入助手或插件，不是核心场景能力；
- 核心必须接收结构化题源，例如 `Paper -> sections -> questions -> answer/analysis/score`；
- 答案、解析、知识点必须始终保留在结构化数据中；
- 学生版、教师版、答案版、解析版必须由 `ContentVisibilityRule` 和 `DeliveryPreset` 从同一事实源生成；
- Markdown 只能作为人工预览和编辑层，不能成为最终排版事实源；
- 复杂几何图、电路图、化学结构式等不进入核心自动生成承诺，应走图片资产或专用插件。

这条规则可以横向复用到合同、HR、表单和项目申报：凡是多版本或批量输出，都不能让不同版本从不同内容源生成。

## 10. Word/OOXML 风险前置

每个 L2 以上 family 都必须声明 `ooxml_touchpoints`，并尽量映射到 ObjectPreflight target。否则它只是业务标签，不是 Word 场景能力。

| 风险面 | 高频来源 | V10 要求 |
| --- | --- | --- |
| `field` | 目录、页码、交叉引用、合同编号、披露字段 | 保留、更新策略、报告解释 |
| `comment` | 合同、投稿修回、双语审校、技术审阅 | 保留、摘要、禁止静默删除 |
| `revision` | 合同、技术审阅、公文内审、披露 | 默认保护、跳过高风险模块 |
| `textbox` | 表单、套打、双语说明、复杂模板 | 预检、版位保护、不要粗暴重排 |
| `content_control` | 表单、合同、公文、HR | 字段映射、残留检查、保护策略 |
| `drawing` / Visio | 技术、标书、论文、披露 | 高风险预检、必要时跳过重排模块 |
| `embedded_workbook` | 财务报价、披露、技术表格 | 预检、避免破坏嵌入对象 |
| `macro` / package part | 外来模板、复杂表单、历史合同 | 报告、阻断或人工确认 |
| `relationship` | 附件、OLE、图片、外部链接 | inventory、缺项、阻断或降级 |

当前 ObjectPreflight 已有扫描、报告、Workbench 摘要/明细和运行前确认第一版。仍未完整闭合的是：详情页、可筛选 finding、可编辑 `skip_modules_by_finding` 矩阵、按 family 差异化策略。

## 11. 场景配置控件一致性

场景配置必须继承模板管理的控件语言。它不是视觉偏好，而是用户理解参数归属的前提。

| 参数类别 | 模板管理与场景配置的共同规则 |
| --- | --- |
| 数值 + 单位 | 使用同一套 spin/spacing input，不允许同一单位在不同页换名字 |
| 左缩进/右缩进 | 同行排布，名称保持一致 |
| 段前/段后 | 同行排布，单位和模板一致 |
| 特殊缩进 | 必须可交互切换：无、首行、悬挂 |
| 行距类型 | 固定值、倍数、最小值等必须可切换 |
| 表格行高 | 在模板为默认版式，在表单/套打场景为版位保护策略 |
| 水印 | 模板定义外观，场景定义状态、版本和交付策略 |
| 输出 | 不属于模板；归 Workbench session 和 DeliveryPreset |
| 风险策略 | combo + 状态 badge + 报告话术，不混入普通表单 |
| 高风险确认 | 独立确认区，不能藏在普通开关中 |

对你前面指出的缩进控件问题，V10 给出统一原则：同一组参数在模板页和场景页出现时，控件形态、命名、单位和交互模式必须一致；差别只在语义标签上注明“模板默认”还是“场景覆盖”。

## 12. 成熟度模型

V10 建议所有 family 使用 L0-L5 成熟度：

| 等级 | 含义 | 可对用户承诺吗 |
| --- | --- | --- |
| L0 | 只有口头需求或文档想法 | 否 |
| L1 | registry 有 planning contract | 否，只能展示规划 |
| L2 | schema/profile/preset 至少一层落地 | 有条件，不进主承诺 |
| L3 | first slice 具备 UI、执行、报告、测试证据 | 可以作为受限能力 |
| L4 | 多工作流闭合，失败和边界可解释 | 可以作为稳定场景能力 |
| L5 | profile 治理、插件边界、批量/归档长期稳定 | 可以产品化推广 |

防止边界不清的关键是：不能把 L1 family 包装成 L4 场景入口。

## 13. 近期推进优先级

优先级不按“谁新鲜”排，而按“能提升最多高频任务成熟度”排。

| 顺序 | 主题 | 为什么优先 |
| --- | --- | --- |
| 1 | `contract_delivery` L3/L4 | 复用字段一致性、对象保护、审阅/签署、多版本交付 |
| 2 | ObjectPreflight 详情和可编辑策略 | 覆盖技术、合同、标书、长文档、披露等多场景安全底座 |
| 3 | CountProfile 治理 | 支撑论文、投稿、申报、披露、附件 inventory |
| 4 | `form_batch_documents` | 固定版式、内容控件、行高/版位保护是高频痛点 |
| 5 | `exam_teaching` | 结构化事实源 + 同源多版本能建立重要范式 |
| 6 | `hr_batch_documents` | xlsx/json 批量和失败隔离是高频办公能力 |
| 7 | DeliveryPreset artifact browser | 让多版本输出真正可验收 |
| 8 | plugin boundary UI | 防止 OCR、AI、法律、财务、IP 被误认为核心承诺 |

## 14. 场景需求准入清单

任何后续新增需求都按下面清单审阅：

```text
1. 这是高频任务族、横切工作流、模板参数、资料字段、交付 preset，还是插件能力？
2. 已有 P0/P1/P2 family 能否承载？
3. 是否需要新增 registry，而不是新增顶层入口？
4. 是否有 MaterialSchema / CountProfile / DeliveryPreset / ObjectPreflight 落点？
5. 是否会触碰 OOXML 风险对象？
6. 是否涉及法律、财务、IP、审计、AI 内容质量、OCR 或完整 LaTeX 等不承诺边界？
7. 用户在哪里看到缺失、风险、降级、跳过和产物？
8. 哪些 pytest 能证明它不只是文档规划？
```

只有清单通过，才允许从“需求想法”进入“场景能力矩阵”。

## 15. V10 最终验收句

后续判断一个高层场景能力是否完善，用这句话：

```text
一个高频任务族，必须有明确承载层；
一个承载层，必须有明确横切工作流；
一个工作流，必须有模型字段、UI 控件、执行消费、报告证据和测试；
一个 Word 风险，必须有 ObjectPreflight 或不触碰声明；
一个专业风险，必须有插件边界或人工确认；
一个输出承诺，必须能在 Workbench、产物和报告中被用户验收。
```

缺任何一项，都不应算完整场景能力。
