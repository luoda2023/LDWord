# 高层场景能力矩阵 V23 完备定义与高频边界准入规划（2026-06-18）

## 1. 本轮定位

本轮继续回答用户提出的核心问题：

```text
当前功能点过于不完善，不能出现高频适用场景遗漏，也不能让边界不清晰。
```

V23 不再继续扩充顶层场景入口。当前工程已经有 12 个 coverage pack、15 个 planned family、21 个 material schema，以及 CountProfile、DeliveryPreset、PluginManualGate、NaturalRequestRouter 等分层骨架。继续单纯新增“场景名”只会让导航变重，仍然无法证明高频请求已经被覆盖。

本轮结论是：

```text
完善的高层场景能力矩阵 = 高频请求清单 + 归属裁决 + 能力槽位 + Word 风险面 + UI/执行/报告/测试闭环。
```

一个场景能力如果只具备名称、开关或说明文案，不能算完整。它必须能落到具体的：

```text
pack / family / profile / material schema / count profile / delivery preset / plugin gate / repair target / report evidence / test evidence
```

否则就是“看起来有规划，实际链路断裂”。

## 4. 完整能力的定义

### 4.1 五级成熟度

| 等级 | 定义 | 不足 |
| --- | --- | --- |
| L0 请求词 | 只有用户说法或场景名字 | 无归属、无边界 |
| L1 规划族 | 有 planned family 或 coverage pack 归属 | 未必能应用默认配置 |
| L2 配置契约 | 有 profile/schema/preset/plugin gate/ownership | UI 和执行可能未打通 |
| L3 可见配置 | ScenePanel/Workbench 能展示、解释、禁用或提示 | 报告和 repair 可能缺链 |
| L4 可执行闭环 | resolver/pipeline/report/issue queue/artifact/test 有证据 | 规则来源、真实样本、插件生态仍可深化 |
| L5 产品化能力 | 有规则来源治理、真实样本回归、人工确认或插件边界、跨版本迁移策略 | 可以作为稳定业务能力承诺 |

不得把 L1/L2 宣称为 L5。文档可以规划，产品界面必须按成熟度展示能力边界。

### 4.2 十个必备能力槽位

每个高频场景能力至少要回答十个槽位：

| 槽位 | 需要回答 | 典型落点 |
| --- | --- | --- |
| `request_alias` | 用户会怎么说？有哪些歧义说法？ | `scene_natural_request_router.py` |
| `pack_family` | 属于哪个 pack/family/profile？ | `scene_coverage_manifest.py`、`scene_family_registry.py` |
| `ownership` | 参数归 template、scene、material、output、session 还是 plugin？ | `scene_parameter_ownership.py`、`control_contract_registry.py` |
| `fact_source` | 机器可信事实来自哪里？ | docx、JSON、XLSX、BibTeX/CSL、MaterialSchema |
| `word_surface` | 会触碰哪些 OOXML/package 面？ | ObjectPreflight、WordRiskSurface |
| `ui_contract` | 用户能否看到配置、禁用原因和边界？ | ScenePanel、Workbench、TemplatePanel 控件契约 |
| `execution_path` | 是否进入 resolver、scheduler、pipeline、runtime？ | resolver、runner、module runtime |
| `report_artifact` | 是否有报告、产物、manifest、issue？ | JSON/Markdown report、artifact browser |
| `repair_route` | 出问题能否回到正确面板？ | template/material/output/object_preflight/plugin_manual_gate |
| `test_evidence` | 是否有 registry/UI/runtime/report 回归？ | pytest first slice、fixture、静态审计 |

缺任一槽位，都应被标为“规划未闭环”，而不是默认为可用。

## 5. 高频需求总表

高频需求不只按“文档类型”分，还要按“任务类型”分。否则容易漏掉导入、交付、批量、审阅、规则检查这些真实使用场景。

| 高频任务类型 | 用户说法 | 应落点 | 边界 |
| --- | --- | --- | --- |
| 套模板/清洗 | 套格式、清目录、页码不对、清空样式 | `quick_formatting` | 不承诺专业合规 |
| 规则检查 | 字数、词数、图表数、参考文献条数、学校规则 | CountProfile + report | 不把一个 profile 当全局真理 |
| 结构化生成 | 试卷、批量证明、证书、offer、表单 | JSON/XLSX + MaterialSchema + DeliveryPreset | AI 只给事实源，Word 输出由程序生成 |
| 多版本交付 | 学生版、教师版、审阅稿、签署稿、客户版、归档包 | `DeliveryPreset` + `ContentVisibilityRule` | 不从多个不一致源分别生成 |
| 资料包填充 | 标书资质、项目附件、产品图片、签章 | MaterialSchema + AssetsPanel | 不验证资料真实性 |
| 专业披露 | 报价、预算、年报、ESG、专利、双语审阅 | professional pack + plugin/manual gate | 不做法律、审计、财务、专利、翻译质量结论 |
| 导入转换 | PDF 转 Word、OCR、LaTeX、AI 草稿、复杂图形 | `import_ai_boundary` | 不承诺无损转换 |
| Word 风险保护 | 修订、批注、字段、内容控件、文本框、OLE/VBA | ObjectPreflight + issue queue | 不能静默破坏文档对象 |
| 固定版位 | 套打、证书、登记表、答题卡 | fixed-layout profile | `w:trHeight` 不回普通表格样式 |
| 交付归档 | manifest、附件包、对比稿、报告、失败项 | OutputConfig + DeliveryPreset | 产物必须可追踪 |

## 6. 12 个 pack 的子场景完备清单

### 6.1 `quick_formatting`

必须覆盖：

- 普通 Word 清洗、套模板、标题编号重建或保留；
- 目录、页码、题注、页眉页脚基础修复；
- 对象预检：字段、修订、批注、OLE/VBA、文本框、外链；
- final docx、compare docx、Markdown/JSON report。

边界：

- 不做学校、期刊、法律、财务、翻译、专利结论；
- 用户只说“排版”时默认落这里，除非出现专业或导入风险词。

完善缺口：

- Workbench issue queue 应能把“模板问题”路由回模板管理；
- 普通排版与专业合规的 router 提示还可以继续前置。

### 6.2 `chinese_academic`

必须覆盖：

- 毕业论文、课程论文、开题报告、文献综述；
- 学校字数、摘要字数、正文字数、参考文献条数、图表公式数；
- 参考文献置信度、公式置信度、目录和页码；
- 学校 profile 来源、版本、人工确认。

边界：

- 不吸收英文期刊投稿；
- 不把 Word 的 `Words` 直接当中文学校字数；
- 完整 LaTeX 工程先走 import/plugin boundary。

完善缺口：

- 学校规则来源治理需要继续产品化；
- 公式处理要明确低置信度、fallback 和报告措辞。

### 6.3 `english_journal`

必须覆盖：

- manuscript、cover letter、declaration、revision、response letter；
- title/abstract/main text/methods/references/display items；
- BibTeX/CSL、图表数量、supplementary、投稿包 manifest；
- 修订和批注保护。

边界：

- 不承诺出版社终版；
- 不自动抓取未审规则；
- 不承诺完整 LaTeX 工程无损转换。

完善缺口：

- 真实期刊 profile 更新流程；
- 期刊规则来源审阅、过期、人工确认提示。

### 6.4 `exam_education`

必须覆盖：

- 试卷、题库、讲义、答题卡；
- 学生版、教师版、答案版、解析版；
- 题源 JSON、题型、分值、答案、解析、知识点；
- 公式、图片、题图、答题区、内容显隐。

边界：

- AI 质量不归核心承诺；
- 复杂几何图、学科专业图形进入 plugin/manual gate；
- 所有版本必须来自同一结构化题源。

完善缺口：

- 答题卡 fixed-layout profile；
- 学科插件边界和题图资产替换入口。

### 6.5 `bidding_materials`

必须覆盖：

- 标书、投标文件、资质证照、营业执照、附件包；
- 多主体、联合体、正本/副本、盖章、签字、目录；
- 缺项隔离、附件 manifest、失败项报告。

边界：

- 不验证证照真实性；
- 不判断投标策略或法律有效性；
- 资质证书作为附件与“批量生成证书”分开裁决。

完善缺口：

- 联合体主体 schema；
- 正副本/盖章定位与签章残留检查。

### 6.6 `official_policy`

必须覆盖：

- 通知、函、请示、批复、会议纪要、制度汇编；
- 文号、签发人、主送/抄送、版记、归档；
- 内部传阅、征求意见、正式稿、归档稿水印状态。

边界：

- 页面外观基线归模板；
- 水印颜色、角度、字号归模板外观或控件契约，状态归场景/交付；
- 不判断行政决定实质。

完善缺口：

- 公文文种 profile；

### 6.7 `technical_long_docs`

必须覆盖：

- chapter inventory、跨章节引用、字段、图表、附件；
- review/proof/final/archive 多版本交付。

边界：

- 技术事实正确性不由核心判断；
- 产品手册如果是客户/售前资料，转 `application_reports`；
- 复杂嵌入对象先预检。

完善缺口：

- 深 `doc_tree`；
- 索引、附注、多文件合并边界。

### 6.8 `application_reports`

必须覆盖：

- 项目申报、评审材料、立项书、附件包；
- 白皮书、产品手册、售前方案、客户方案；
- 限字、附件、项目/产品资料、客户版/内部版/资产报告。

边界：

- 不替代申报系统；
- 不承诺营销文案质量；
- 报价金额表和预算附件转 professional disclosure。

完善缺口：

- 产品 profile 继续细化；
- 项目附件和产品资产 schema 的 UI 化入口。

### 6.9 `contract_delivery`

必须覆盖：

- 合同、协议、审阅稿、对比稿、签署稿；
- 甲乙方、金额、日期、联系方式、签章字段一致性；
- 修订、批注、隐藏文字、字段、签章位置风险。

边界：

- 不提供法律意见；
- 不判断条款效力；
- 不验证签章真实性。

完善缺口：

- 内容控件合同模板；
- 签章定位和签署包 manifest。

### 6.10 `batch_forms`

必须覆盖：

- HR offer、证明、邀请函、证书、奖状、登记表、套打；
- one-record-one-output；
- fixed-layout 表格、内容控件、文本框、占位符残留；
- 成功/失败隔离和批量摘要。

边界：

- 不验证人员、业务、申报数据真实性；
- `w:trHeight` 是固定版位能力，不回普通 `TableConfig.row_height_pt`；
- 不把失败记录混进成功产物。

完善缺口：

- 更细 profile UI；
- 固定版位残留、行高、文本框和内容控件的统一 repair target。

### 6.11 `professional_disclosure`

必须覆盖：

- 报价、预算、财务附件、年报、ESG、专利、双语审阅；
- spreadsheet-to-document table mapping；
- 附件一致性、披露归档、术语一致性、平行文本；
- plugin/manual gate 和专业边界报告。

边界：

- 不做审计、财务、法律、专利、翻译质量结论；
- 专利说明书可处理格式/图号/术语清单，权利要求有效性必须 plugin/manual-only；
- 双语排版与翻译审阅必须分开裁决。

完善缺口：

- 专业边界 UI 提示要更早出现；
- 报价方案、产品报价方案、预算附件的裁决文案要统一。

### 6.12 `import_ai_boundary`

必须覆盖：

- OCR、PDF 转 Word、完整 LaTeX、AI 草稿、复杂图形；
- 置信度、人工确认、导入产物、降级路径；
- 二阶段路由：先确认导入风险，再进入目标业务 pack。

边界：

- 不承诺无损转换；
- 不把 AI 输出直接当机器事实源；
- 不将导入能力伪装成业务场景。

完善缺口：

- 真实插件实现；
- PDF/OCR/LaTeX/AI 的置信度报告模板和用户确认流。

## 7. 边界裁决原则

### 7.1 优先级

```text
专业判断 > 导入转换风险 > 事实源可信度 > 业务版本交付 > 模板外观
```

解释：

- 涉及法律、审计、财务、专利、翻译质量，先进入 plugin/manual gate；
- 涉及 PDF/OCR/完整 LaTeX/AI/复杂图形，先进入 import boundary；
- 有 JSON/XLSX/BibTeX/CSL/资料包，则先绑定事实源和 schema；
- final/review/student/customer/internal/archive 是 DeliveryPreset；
- 字体、字号、缩进、段距、页边距、题注外观回模板管理。

### 7.2 高频歧义

| 用户说法 | 裁决规则 |
| --- | --- |
| 产品手册 | 技术操作/接口/SOP -> `technical_long_docs`；客户/售前/白皮书 -> `application_reports` |
| 报价方案 | 方案正文 -> `application_reports/product_sales_documents`；金额表、预算、财务附件 -> `professional_disclosure/finance_quote_documents` |
| 证书材料 | 投标资质附件 -> `bidding_materials`；批量生成证书/奖状/证明 -> `batch_forms` |
| 双语文档 | 只排版 -> `quick_formatting`；术语一致性/对照审阅 -> `professional_disclosure/bilingual_translation_documents`；翻译质量 -> plugin/manual gate |
| 会议材料 | 行政会议纪要/制度 -> `official_policy`；普通总结/汇报 -> `quick_formatting` 或 `application_reports` |
| PDF 论文 | 先 `import_ai_boundary`，再进入 `chinese_academic` |
| LaTeX 公式 | 片段公式可进入目标场景；完整工程先 import/plugin boundary |
| 专利说明书 | 格式、图号、术语清单可登记；法律质量和权利要求有效性 plugin/manual-only |
| 水印 | 状态和版本语义归 scene/delivery；视觉样式归 template/control contract |

## 8. Word/OOXML 反推

完整场景矩阵必须从 Word 本体反推，否则会漏掉用户肉眼最在意的破坏。

| Word 面 | 高频 pack | 必须策略 |
| --- | --- | --- |
| `w:p` / `w:r` | 全部 | 是否保留内联格式、是否重写 run |
| `styles.xml` | 模板、论文、公文、报告 | 外观基线归模板；场景覆盖必须有原因 |
| `numbering.xml` | 论文、公文、标书、合同 | rebuild/preserve/repair 明确选择 |
| `w:tbl` / `w:tr` / `w:tc` | 试卷、报价、表单、披露 | 表格网格、合并、分页、重复表头单独处理 |
| `w:trHeight` | 答题卡、证书、套打表单 | fixed-layout policy，不回普通表格样式 |
| `w:sdt` | 表单、合同、HR、套打 | 内容控件映射、填充、残留检查 |
| `w:txbxContent` / shape | 证书、旧模板、表单 | 文本框和 shape 预检，不按普通段落处理 |
| field / TOC / PAGE / REF | 论文、公文、技术长文档 | preserve/update/skip 策略 |
| comments / revisions | 合同、期刊、披露、双语 | preserve/block/compare/report |
| hidden text | 披露、合同、审阅稿 | 显隐、计数、交付影响必须报告 |
| headers/footers/sectPr | 论文、公文、水印、签署包 | 外观归模板，状态和版本归场景 |
| footnotes/endnotes | 学术、期刊、长文档 | 是否计数、格式化、报告 |
| OLE/embedded/VBA | 财务、技术、标书 | block/warn/isolate，不能静默改写 |
| rels/package parts | 附件、图片、外链、归档 | manifest、外链风险、artifact 引用 |

## 9. 控件契约一致性

场景配置不能拥有一套和模板管理不同的控件语言。否则用户会以为同名参数在不同页面有不同含义。

### 9.1 同名参数同控件

| 参数类型 | 控件要求 |
| --- | --- |
| 字体、字号 | 复用模板管理字体/字号控件 |
| 缩进、特殊缩进、段前段后、行距 | 复用模板管理段落控件、单位、禁用态 |
| 表格固定行高 | 只在 fixed-layout 场景控件出现，不在普通 TableConfig 中冒出 |
| 公式视觉基线 | 若是字体/字号/段距，复用模板控件；若是处理策略，归 scene |
| 水印视觉 | 颜色、字号、角度归模板或视觉控件契约；启停、状态、版本归 scene/delivery |
| 输出版本 | 用 DeliveryPreset 控件，不用散落开关 |
| 内容显隐 | 用 ContentVisibilityRule 编辑器，不用自由文本伪配置 |
| plugin/manual gate | 用统一警告/确认/报告控件，不做场景私有弹窗 |

### 9.2 场景控件的最低标准

- 复用 `StyledComboBox`、`StyledSpinBox`、`ToggleSwitch`、`SpacingInput`、`SummaryGrid` 等既有控件；
- 同一行能表达清楚的标签和值不要拆成纵向堆叠；
- disabled 状态必须说明原因；
- 单位选择、数字范围、默认值、空值语义要和模板管理一致；
- 场景私有业务控件也必须遵守同一尺寸、边框、圆角、焦点和下拉样式；
- 高频能力不得藏进“高级设置”文本区。

## 10. 资料、计数、输出三条事实链

### 10.1 资料链

```text
用户资料 / JSON / XLSX
-> MaterialSchema
-> MaterialExecutionContext
-> 预检缺字段/缺资产
-> 运行填充
-> residue / manifest / report
-> repair target 回 AssetsPanel 或 ScenePanel
```

适用：

- 标书资质；
- 项目申报附件；
- 产品资产；
- 合同甲乙方/签章；
- HR/表单批量；
- 财务报价字段；
- 双语术语表。

### 10.2 计数链

```text
docx 结构识别
-> CountProfile
-> 多指标统计
-> 范围解释
-> 规则来源/版本
-> report
-> repair target 回 profile/scene
```

必须支持：

- 中文字符数、汉字数、英文词数、含空格/不含空格字符数；
- Word-like words；
- 参考文献、图、表、公式、段落、章节；
- 学校/期刊/申报/披露 profile 的范围差异。

### 10.3 输出链

```text
DeliveryPreset
-> ContentVisibilityRule
-> OutputConfig
-> artifact manifest
-> report / issue queue
```

适用：

- final/review/compare；
- student/teacher/answer/analysis；
- customer/internal；
- signing/archive/submission；
- per-record batch；
- missing-items/failed-items report。

## 13. 完备验收问卷

任何新增或升级的场景能力，合入前必须回答：

1. 用户自然会怎么说？
2. 是否存在高频歧义？
3. 落在哪个 pack？
4. 是否需要 planned family？
5. 是否需要 profile？
6. 是否需要 MaterialSchema？
7. 是否需要 CountProfile？
8. 是否需要 DeliveryPreset？
9. 是否需要 ContentVisibilityRule？
10. 是否需要 PluginManualGate？
11. 事实源是 docx、JSON、XLSX、BibTeX/CSL、资料包还是外部插件？
12. 会触碰哪些 OOXML/package 面？
13. 是否会影响修订、批注、字段、内容控件、文本框、OLE/VBA、外链？
14. 场景控件是否复用模板管理控件语言？
15. 参数 ownership 是否明确？
16. 执行链是否真实存在？
17. 报告是否能解释结果、跳过、缺项和边界？
18. issue queue 是否能路由到正确修复入口？
19. artifact 是否可定位？
20. 是否有 registry/UI/runtime/report 测试？
21. 是否有边界措辞，避免专业能力过度承诺？
22. 是否有规则来源、版本或人工确认？

任一项回答“不知道”，就是边界不清；回答“以后再接”，就是链路未闭环；回答“UI 有但执行/报告/测试没有”，就是假闭环。

## 14. 结论

高层场景能力矩阵的完善方向不是继续堆顶层入口，而是建立可审计的能力槽位：

```text
自然请求 -> 裁决 -> profile/schema/preset/plugin gate -> Word 风险 -> UI 控件 -> 执行 -> 报告 -> repair -> 测试
```

当前 12 个 pack 仍可作为稳定顶层；15 个 planned family 能覆盖主要高频业务族；21 个 material schema 已经提供资料事实源基础。但产品要达到“不遗漏高频场景、边界清晰、链路不断”，下一步必须把控件契约、repair routing、规则来源治理和 pack 槽位审计继续落到代码与测试。

V23 因此作为后续执行的高层验收基线：以后新增任何场景能力，不再问“有没有这个名字”，而是问“十个能力槽位是否都有证据”。
