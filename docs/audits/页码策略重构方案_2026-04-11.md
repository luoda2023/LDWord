# 页码策略重构方案（2026-04-11）

## 1. 背景

这次重构只聚焦“页码策略”本身，不顺手扩写成整套页眉页脚大一统改造。

当前代码已经具备“按分区识别 section type”“按 section break 控制页码格式/起始值”的基础能力，因此它并不是完全不支持：

- 全文连续阿拉伯页码
- 前置部分罗马页码 + 正文阿拉伯页码
- 正文起始页重置

但现状仍有 4 类关键问题：

1. **状态分叉**
   场景加载后，`header_footer/toc` 的值会被折叠进 `template_overrides`，而场景面板仍直接读写 `scene.header_footer`，导致“编辑态看到的是一套值，执行态实际用的是另一套值”。
2. **输出层语义不完整**
   `lowerRoman` 与 `upperRoman` 在字段指令层没有真正区分，配置层和输出层语义不一致。
3. **模型表达力不足**
   现在的 `front_matter_* + body_* + restart_body_page_number` 只能表达非常有限的二段式场景，无法稳定承载不同文档类型的分页规则。
4. **退化路径不可见**
   `doc_tree` 缺失时会直接退化为“全部当 body 处理”，但当前没有明确告警或显式兜底策略。

这意味着当前问题不是“没有能力”，而是“已有能力的边界不清、语义不完整、层间实现不一致”。

---

## 2. 重构目标

本次页码策略重构的目标是：

1. 支持以下常见模式，并且模型表达清晰：
   - 全文连续阿拉伯页码
   - 前置部分罗马页码，正文阿拉伯页码从 1 重起
   - 前置部分罗马页码，正文延续前文页码
   - 正文连续编号，附录或特定分区单独起号
2. 保证页码策略只有一个真实来源，不能再出现顶层值与 override 隐式打架。
3. 让“配置模型”“持久化/迁移”“执行规划”“Word 输出”四层语义一致。
4. 保留对旧配置的兼容读取，但新模型写回时不再继续扩散旧字段。
5. 给后续 UI 改造和预设升级留下明确承载点，而不是继续在旧字段上打补丁。

---

## 3. 非目标

本轮明确不做的事情：

1. 不解决任意“逐页手工编排”的可视化编辑问题。
2. 不同时重构所有页眉内容策略，例如 `fixed/styleref/none` 的更大范围语义统一。
3. 不把“附录用 A-1、B-1”这类扩展格式一次性做完，但模型需要给它留扩展口。
4. 不把整个 scene/template 体系一次性推倒重来，本轮只处理与页码策略直接相关的边界。

---

## 4. 核心决策

### 4.1 单一事实来源

**目标态：页码策略归模板侧所有，场景不再拥有独立的页码格式定义。**

原因：

- 页码格式、起始页、前置部分/正文如何切换，本质上是文档版式定义，不是“这个场景要不要启用某个功能”的行为定义。
- 当前 `scene.header_footer` 与 `scene.template_overrides` 同时能表达页码策略，是这轮状态分叉的根源。
- 模板侧本来已经承载 `header_footer`，模板编辑面板也已经承载了更完整的页码策略 UI。

因此建议：

1. `TemplateConfig.header_footer` 成为页码策略唯一真实来源。
2. `SceneWorkspace` 只保留：
   - `header_footer` 模块是否启用
   - 格式化范围 `format_scope`
   - 如果未来确实需要“场景级覆盖模板页码策略”，也必须使用**同一套结构化模型**，而不是退回通用 `template_overrides` 的散装 dotted-key。
3. 场景面板不再提供页码格式/起始值编辑入口，最多只显示只读摘要或模块开关。

### 4.2 用“阶段（phase）”替代“front/body 二段式”

推荐新增显式的页码阶段模型：

```python
@dataclass
class PageNumberPhaseConfig:
    phase_id: str = ""
    selectors: list[str] = field(default_factory=list)
    visible: bool = True
    number_format: str = "decimal"
    start_mode: str = "continue"   # "continue" | "restart"
    start_value: int = 1


@dataclass
class PageNumberPlanConfig:
    enabled: bool = True
    phases: list[PageNumberPhaseConfig] = field(default_factory=list)
    on_missing_doc_tree: str = "warn_and_fallback"
```

然后在 `HeaderFooterConfig` 下挂载：

```python
@dataclass
class HeaderFooterConfig:
    ...
    hide_cover_header_footer: bool = True
    page_number_plan: PageNumberPlanConfig = field(default_factory=PageNumberPlanConfig)
```

说明：

- `visible` 表示该阶段是否显示页码字段。
- `number_format` 第一阶段只要求覆盖现有格式：
  - `decimal`
  - `upperRoman`
  - `lowerRoman`
- `start_mode`
  - `continue` 表示沿用前一阶段页码
  - `restart` 表示该阶段从 `start_value` 开始
- `phase_id` 用于 UI、测试、迁移和诊断，不参与实际排版逻辑。

### 4.3 selector 采用语义分组，而不是直接绑死底层字段

推荐内置一组稳定 selector：

- `cover`
- `front_matter`
- `abstracts`
- `toc`
- `body`
- `back_matter`
- `references`
- `errata`
- `appendix`
- `acknowledgment`
- `resume`
- `all_numbered_content`

其中：

- `front_matter` 默认展开为 `abstract_cn + abstract_en + toc`
- `back_matter` 默认展开为 `references + errata + appendix + acknowledgment + resume`
- `all_numbered_content` 默认展开为除 `cover` 外所有可编号内容区

这样可以同时兼顾：

1. 模板预设层的简洁表达
2. UI 的可理解性
3. 运行期对真实 section type 的稳定映射

### 4.4 阶段必须显式、无重叠、可验证

为了避免再出现“看起来像能配，实际上靠隐式默认凑出来”的状态，阶段规则建议采用以下约束：

1. `phases` 有顺序，但**不允许重叠 selector 扩展结果**。
2. 当 `page_number_plan.enabled=True` 时，除 `cover` 外的可编号 section 应该被**恰好一个 phase** 匹配。
3. 如果某个 section 未被匹配：
   - 严格模式：报错或阻止保存
   - 非严格模式：告警并退化为 `decimal + continue`
4. 如果两个 phase 命中同一 section：
   - 一律视为配置错误，不采用“后写覆盖前写”的隐式优先级。

这能最大限度减少“配置可写、语义不可预测”的风险。

## 5. 推荐预设表达

### 5.1 全文连续阿拉伯页码

```yaml
page_number_plan:
  enabled: true
  phases:
    - phase_id: main
      selectors: [all_numbered_content]
      visible: true
      number_format: decimal
      start_mode: restart
      start_value: 1
```

### 5.2 前置部分罗马页码 + 正文阿拉伯页码

```yaml
page_number_plan:
  enabled: true
  phases:
    - phase_id: front
      selectors: [front_matter]
      visible: true
      number_format: upperRoman
      start_mode: restart
      start_value: 1
    - phase_id: body
      selectors: [body, back_matter]
      visible: true
      number_format: decimal
      start_mode: restart
      start_value: 1
```

### 5.3 前置部分小写罗马 + 正文延续编号

```yaml
page_number_plan:
  enabled: true
  phases:
    - phase_id: front
      selectors: [front_matter]
      visible: true
      number_format: lowerRoman
      start_mode: restart
      start_value: 1
    - phase_id: body
      selectors: [body, back_matter]
      visible: true
      number_format: decimal
      start_mode: continue
      start_value: 1
```

注：

- 当 `start_mode=continue` 时，`start_value` 仅作为兼容占位，不参与实际输出。
- 迁移时如果发现旧配置中 `restart_body_page_number=false` 且 `body_page_number_start != 1`，应给出“起始值被忽略”的迁移告警。

## 6. 与现有旧字段的映射关系

建议保留旧字段读取兼容，但新模型写回时只写 `page_number_plan`。

### 6.1 旧字段到新模型的映射

| 旧字段 | 新模型映射 |
|------|-----------|
| `page_number_enabled=False` | `page_number_plan.enabled=False`，`phases=[]` |
| `front_matter_page_number_format` | `phase(front_matter).number_format` |
| `front_matter_page_number_start` | `phase(front_matter).start_value` |
| `body_page_number_format` | `phase(body+back_matter).number_format` |
| `restart_body_page_number=True` | `phase(body+back_matter).start_mode=restart` |
| `restart_body_page_number=False` | `phase(body+back_matter).start_mode=continue` |
| `body_page_number_start` | `phase(body+back_matter).start_value`，仅在 `restart` 时生效 |
| `hide_cover_header_footer` | 暂时仍作为 `HeaderFooterConfig` 的兼容字段保留，不并入 `page_number_plan` |

### 6.2 写回策略

建议采用：

1. **读取兼容旧字段**
2. **内存态统一成新模型**
3. **保存时默认只写新模型**

原因：

- 如果保存时继续同时写新旧两套字段，后面又会出现“哪套才是真”的歧义。
- 兼容读取已经足够照顾旧文件，不需要把技术债继续写回磁盘。

## 7. Scene / Template 边界调整

这是这轮重构里最容易引入新问题的地方，所以必须先定边界，再改代码。

### 7.1 目标边界

| 层 | 职责 |
|----|------|
| `TemplateConfig.header_footer.page_number_plan` | 定义页码策略 |
| `SceneWorkspace.module_switches["header_footer"]` | 决定是否启用页眉页脚模块 |
| `SceneWorkspace.format_scope` | 决定哪些 section 参与处理 |
| `ResolvedConfig.header_footer` | 模板基线 + 合法覆盖后的最终页码策略 |

### 7.2 明确禁止的状态

重构后不应再允许以下状态继续存在：

1. `scene.header_footer.page_number_*` 与 `scene.template_overrides["header_footer.xxx"]` 同时表达同一语义。
2. UI 编辑的是 `scene.header_footer`，运行时实际读的是 `template_overrides`。
3. 模板保存写一套字段，场景保存再写另一套同义字段。

### 7.3 对 scene 旧数据的处理建议

不建议继续把 `scene.header_footer/toc` 悄悄折叠进通用 `template_overrides`，因为这正是隐藏状态分叉的来源。

推荐策略：

1. 对内置场景预设：
   - 清理掉页码格式相关字段
   - 让模板预设显式定义页码策略
2. 对用户旧场景文件：
   - loader 仍可识别旧字段
   - 但应走“显式迁移”路径，而不是普通 `load_scene()` 后继续把旧值藏进 `template_overrides`
3. 普通运行态：
   - `normalize_scene_payload()` 不再承担页码策略迁移承载
   - 页码策略统一在模板侧完成规范化

如果考虑兼容窗口，可以额外提供：

- 一个导入/升级工具
- 或一个“检测到旧场景页码策略，请迁移到模板”的显式提示

但不建议把“隐式提升为 override”继续保留为长期机制。

## 8. 执行链路重构建议

为了避免新的逻辑再次散落在多个模块里，页码策略执行建议拆成“规划”和“渲染”两步。

### 8.1 新增共享规划函数

建议新增一个纯函数规划器，例如：

```python
build_page_number_execution_plan(doc, doc_tree, header_footer_config) -> PageNumberExecutionPlan
```

输出至少包含：

- 每个 Word section 对应的 `section_type`
- 命中的 `phase_id`
- 是否显示页码
- 使用的 `number_format`
- `start_mode`
- `start_value`
- 是否需要 section break 才能正确生效
- 诊断信息

### 8.2 `section_format` 与 `header_footer` 共享同一执行计划

这是重构里非常关键的一条：

**不要让 `section_format` 和 `header_footer` 分别自己推导 phase 边界。**

推荐方式：

1. `heading_recognition` 先产出 `doc_tree`
2. 页码规划器基于 `doc_tree + page_number_plan` 产出统一执行计划
3. `section_format` 用这份计划决定哪里必须插入 section break
4. `header_footer` 用同一份计划决定每个 section 如何设置字段和 `w:pgNumType`

这样能避免：

- 一个模块认为这里是 front matter
- 另一个模块认为这里已经进入 body
- 二者边界不一致导致页码表现异常

### 8.3 `section_format` 的责任调整

`section_format` 继续负责插入分节，但触发条件应更明确：

1. 逻辑分区边界
2. 页码 phase 切换点
3. 必须保留的正文 H1 边界

其中第 2 条必须来自统一执行计划，而不是再复制一遍 front/body 的推断逻辑。

### 8.4 `header_footer` 的责任调整

`header_footer` 只做三件事：

1. 根据执行计划决定 section 的 header/footer 是否显示
2. 根据执行计划设置页码字段
3. 根据执行计划设置 `w:pgNumType`

它不应再自己推断：

- front matter 是什么
- body 从哪开始
- 是否应该重起页码

这些决策都应该在规划阶段完成。

## 9. Word 输出层的统一映射

当前 `lowerRoman` 与 `upperRoman` 混同，本质上是因为“字段指令格式”和“OOXML `w:pgNumType` 格式”没有使用同一张映射表。

建议统一做成单表驱动：

```python
PAGE_NUMBER_FORMAT_MAP = {
    "decimal": {
        "field_switch": None,
        "w_fmt": "decimal",
    },
    "upperRoman": {
        "field_switch": "ROMAN",
        "w_fmt": "upperRoman",
    },
    "lowerRoman": {
        "field_switch": "roman",
        "w_fmt": "lowerRoman",
    },
}
```

规则：

1. 页码字段指令和 `w:pgNumType/@w:fmt` 必须来自同一个 format map。
2. 任何新增格式都必须同时补：
   - field switch
   - `w:pgNumType`
   - round-trip 测试
3. 不允许出现“配置支持、OOXML 支持、字段不支持”的半支持状态。

## 10. UI 重构建议

### 10.1 模板面板

模板面板应成为页码策略唯一编辑入口。

推荐 UI 形态：

1. **快捷预设**
   - 连续阿拉伯页码
   - 前置罗马 / 正文阿拉伯
   - 自定义
2. **高级编辑**
   - phase 列表
   - 每个 phase 可编辑：
     - 适用 selector
     - 格式
     - 是否显示页码
     - 起号方式
     - 起始值
3. **即时摘要**
   - 例如：`封面隐藏 / 前置 upperRoman / 正文 decimal(1)`

### 10.2 场景面板

场景面板不再编辑页码格式本身。

推荐改成：

1. 只控制“页面元素”能力组是否启用
2. 只读展示当前模板页码策略摘要
3. 如果未来确实需要场景级覆盖，应单独设计“模板外观覆盖”表面，而不是让 scene 面板继续直接改 `scene.header_footer`

### 10.3 预设数据

内置模板应显式带上 `page_number_plan`。

内置场景应不再承担页码策略定义，只保留：

- 模块开关
- 处理范围
- 场景专属行为

## 11. 测试护栏

这轮重构如果不先立测试护栏，非常容易再引入新问题。

建议至少覆盖以下测试：

### 11.1 模型与迁移

1. 旧模板字段可正确迁移为 `page_number_plan`
2. 保存后默认只写新字段
3. 旧字段组合中的无效状态会产生告警
4. `page_number_plan` round-trip 不丢失

### 11.2 Scene / Template 边界

1. 加载场景后，不再出现“顶层值默认化但 override 仍生效”的分叉状态
2. UI 编辑后的值与 `resolve_config()` 实际消费值一致
3. legacy scene 不会再被静默折叠成隐藏 override

### 11.3 规划器

1. `front_matter -> body` phase 切换正确
2. `body -> appendix` phase 切换正确
3. phase selector 重叠时报错
4. 某 section 未匹配时给出诊断
5. `doc_tree` 缺失时按预期告警/退化

### 11.4 Word 输出

1. `decimal` 生成 `PAGE`
2. `upperRoman` 生成 `PAGE \\* ROMAN`
3. `lowerRoman` 生成 `PAGE \\* roman`
4. 对应 section 的 `w:pgNumType/@w:fmt` 正确
5. `restart` 时 `w:start` 正确
6. `continue` 时不错误写入 `w:start`

### 11.5 端到端回归

至少准备 3 组 e2e 用例：

1. 论文类：封面隐藏、前置罗马、正文阿拉伯重起
2. 报告类：全文连续阿拉伯
3. 自定义类：正文连续、附录单独起号

## 12. 建议实施顺序

为了不把这次重构做成“边改边冒烟”的高风险改造，建议按以下顺序推进。

### 阶段 A：先立模型和测试，不接 UI

目标：

- 新增 `page_number_plan`
- 新增纯函数规划器
- 补全迁移测试、输出测试、状态分叉回归测试

退出条件：

- 新模型已可在单元测试中完整表达旧能力
- `lowerRoman` 语义已经可被测试准确覆盖

### 阶段 B：打通 loader / resolver / persistence

目标：

- 模板侧统一读写 `page_number_plan`
- 清理 scene 对页码策略的隐式 override 承载
- 更新内置模板/场景预设边界

退出条件：

- save/load/resolve 行为一致
- 不再存在“编辑态与执行态分叉”

### 阶段 C：替换执行路径

目标：

- `section_format` 与 `header_footer` 共用执行计划
- 输出层改为单表驱动格式映射

退出条件：

- front/body/appendix 等 phase 切换能稳定工作
- 旧 front/body 逻辑不再是运行主路径

### 阶段 D：切 UI

目标：

- 模板面板升级为 phase 编辑器
- 场景面板去掉页码策略编辑
- 模板摘要展示新模型

退出条件：

- 用户只能从一个地方改页码策略
- 不再需要靠旧字段维持 UI

### 阶段 E：兼容收口

目标：

- 保留 loader 读取旧配置
- 停止写回旧字段
- 在文档和预设层全面切换到新模型

## 13. 风险点与约束

### 13.1 最大风险

最大的风险不是 Word 输出本身，而是**边界漂移**：

- loader 迁移一套语义
- resolver 合并另一套语义
- UI 再编辑第三套语义

所以这轮必须先解决“谁拥有页码策略”。

### 13.2 不要做的事情

以下做法应明确避免：

1. 在旧字段上再多加几个布尔值补洞
2. 把 phase 模型做出来，但保存时继续双写 front/body 旧字段
3. 保留 scene 顶层值和 `template_overrides` 双通道写入
4. 让 `section_format` 和 `header_footer` 各自维护一份 phase 推导逻辑

### 13.3 兼容约束

为了降低实施风险，兼容期内可以接受：

1. 读取旧配置
2. 自动映射为新模型
3. 对不合理旧组合给出告警

但不应继续接受：

1. 新配置写回旧结构
2. 旧隐式 override 成为长期主路径

---

## 14. 建议结论

这次不建议做“front/body 旧逻辑的补丁升级”，而应直接切到：

1. **模板侧唯一拥有的结构化页码阶段模型**
2. **统一的页码执行规划器**
3. **共享的 section break / 输出映射链路**
4. **清晰的 scene/template 边界**

这样做的代价比补丁大，但收益也明确：

- 不再继续堆历史兼容债
- 不会再出现 UI、持久化、执行三套状态不一致
- 后续要支持更多文档类型时，不需要再推翻一次

这份文档作为后续实现的基线，建议先按它拆成 4 个实际改造任务：

1. 模型与迁移
2. 执行规划器与输出修正
3. 预设与持久化清理
4. UI 收口
