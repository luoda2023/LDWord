# 高层场景能力矩阵 V20 子场景无遗漏与边界闭环规划（2026-06-18）

## 1. 本轮定位

V19 已经建立了 12 个 coverage pack、15 个能力原子、10 个准入门槛、Word/OOXML 风险面和控件契约。但用户继续指出：当前功能点仍然显得不完善，不能只是围绕已有模块补缺口；必须确认高频适用场景没有遗漏，且边界不能含混。

V20 不再把问题理解为“再列一些功能”。本轮要回答的是：

```text
哪些高频文档任务必须被覆盖？
这些任务应该落在哪个 coverage pack、scene family、profile、material schema、delivery preset 或 plugin boundary？
哪些看似相似的任务必须分开？
哪些看似不同的任务其实共享同一套能力？
什么时候不能承诺核心能力，必须转入插件、人工确认或边界报告？
```

本轮结论：

```text
顶层 coverage pack 仍保持 12 个，不建议继续膨胀；
真正缺的是 pack 内部的子场景、能力槽位、事实源、边界裁决和验收证据；
后续所有实现都应围绕“子场景无遗漏 + 边界不漂移 + 执行闭环可证明”推进。
```

## 3. V20 的核心判断

### 3.1 问题不是 pack 少，而是 pack 内子场景不够明

现在已有的 12 个 coverage pack 方向基本完整：

```text
quick_formatting
chinese_academic
english_journal
exam_education
bidding_materials
official_policy
technical_long_docs
application_reports
contract_delivery
batch_forms
professional_disclosure
import_ai_boundary
```

继续新增大量顶层入口会带来三个风险：

- 导航膨胀，用户不知道该进哪个；
- 场景和模板、资料包、输出包边界再次混乱；
- 没有执行链的场景名会变成空壳。

所以 V20 的策略是：

```text
顶层 pack 稳定；
子场景和 profile 细化；
高频自然请求通过 alias/router 落点覆盖；
执行闭环通过 closure task 和 report evidence 验收。
```

### 3.2 场景能力不是功能点，是一条产品链

一个功能点只有满足下面这条链，才算场景能力：

```text
自然请求
-> coverage pack
-> 子场景 / planned family / profile
-> 事实源
-> 模板基线
-> 场景策略
-> Word/OOXML 风险策略
-> UI 控件契约
-> resolver / scheduler / pipeline / runner
-> report / issue queue / artifact
-> 测试证据
-> 边界承诺
```

缺任何一环，都只能算：

- 模板参数；
- 资料字段；
- 输出开关；
- 一次性会话配置；
- 插件能力；
- 或未闭合规划。

## 4. 高频适用场景全景扫描

V20 把高频用户请求分成 9 条需求带。每条需求带都必须能落到 12 个 pack 之一，不能出现“用户常问但系统没有稳定归属”的情况。

| 需求带 | 高频用户说法 | 推荐落点 | 是否需要新增顶层 pack |
| --- | --- | --- | --- |
| 通用格式整理 | 统一 Word 格式、清洗格式、套模板、修目录页码 | `quick_formatting` | 否 |
| 学术写作与投稿 | 中文论文、课程论文、文献综述、英文期刊、cover letter、revision | `chinese_academic` / `english_journal` | 否 |
| 教学与考试 | 试卷、题库、讲义、学生版、教师版、答案版、答题卡 | `exam_education` | 否 |
| 商务投标与资质 | 标书、资质包、盖章材料、多公司投标 | `bidding_materials` | 否 |
| 公文与制度 | 通知、函、纪要、制度汇编、编号保留、归档 | `official_policy` | 否 |
| 技术与长文档 | SOP、技术手册、接口文档、验收报告、书稿、审阅定稿 | `technical_long_docs` | 否 |
| 项目与应用材料 | 申报书、白皮书、售前方案、产品手册、附件包 | `application_reports` | 否 |
| 合同、表单和批量 | 合同审阅、签署包、证书、证明、offer、登记表、套打 | `contract_delivery` / `batch_forms` | 否 |
| 专业披露和导入边界 | 年报、ESG、报价预算、专利、双语、OCR、PDF、LaTeX、AI 写作 | `professional_disclosure` / `import_ai_boundary` | 否 |

关键判断：

```text
“高频”不等于“顶层入口”。
高频任务如果共享事实源、Word 风险和交付流程，应落为同一个 pack 下的 profile 或 delivery preset。
高风险任务即使高频，也不能直接进入核心能力，必须进入 plugin/manual gate。
```

## 6. 12 个 pack 之间的边界冲突裁决

### 6.1 学术中文 vs 英文期刊

| 冲突点 | 归属 |
| --- | --- |
| 中文学位论文、课程论文、文献综述 | `chinese_academic` |
| 英文 journal manuscript、cover letter、declaration | `english_journal` |
| BibTeX/CSL 基础检查 | 优先 `english_journal`；中文论文可复用引用能力但不继承投稿包 |
| 学校字数规则 | `chinese_academic` |
| 期刊 section/display item 规则 | `english_journal` |

裁决规则：

```text
学校/学院规则 -> chinese_academic；
出版社/期刊投稿规则 -> english_journal；
引用技术能力可共享，但场景承诺不能混用。
```

### 6.2 技术长文档 vs 应用报告

| 冲突点 | 归属 |
| --- | --- |
| SOP、API、技术手册、验收报告 | `technical_long_docs` |
| 项目申报、白皮书、售前方案、附件包 | `application_reports` |
| 产品手册 | 内容偏技术使用说明时归 `technical_long_docs`；偏客户方案/售前包时归 `application_reports` |
| 附件 inventory | 两者可共享 inventory workflow，但 profile 不同 |

裁决规则：

```text
核心是“技术结构长文档”还是“应用/评审/客户交付包”。
前者重章节、交叉引用和审阅定稿；
后者重附件、限字、客户/内部版本和申报清单。
```

### 6.3 标书 vs 项目申报

| 冲突点 | 归属 |
| --- | --- |
| 投标文件、资质证照、盖章投标包 | `bidding_materials` |
| 科研/项目申报、评审附件、立项材料 | `application_reports` |
| 附件目录和证照清单 | workflow 可共享，材料 schema 和边界不同 |
| 多主体批量 | 标书优先 `bidding_materials`；普通项目材料可归 `application_reports` |

裁决规则：

```text
有招投标主体、资质证照、投标归档目录 -> bidding_materials；
有申报系统、分节限字、评审附件包 -> application_reports。
```

### 6.4 公文 vs 合同

| 冲突点 | 归属 |
| --- | --- |
| 通知、函、纪要、制度 | `official_policy` |
| 合同、协议、签署包、条款审阅 | `contract_delivery` |
| 编号保留 | 两者都需要，但 official 强依赖公文编号证据 |
| 盖章/签署 | 合同归签署包，公文归 official material/status |

裁决规则：

```text
行政发文、制度归档 -> official_policy；
双方/多方权利义务、签署包 -> contract_delivery。
```

### 6.5 表格样式 vs 固定版位

| 冲突点 | 归属 |
| --- | --- |
| 普通表格边框、表头重复、宽度 | Template `TableConfig` |
| 固定行高、套打、证书、表单定位 | `batch_forms` fixed-layout profile |
| `w:trHeight` | fixed-layout 能力 |
| 内容控件、文本框、VML shape | fixed-layout / object preflight |

裁决规则：

```text
普通排版表格 -> 模板；
固定版位、套打、证书和表单 -> 场景 profile；
`TableConfig.row_height_pt` 这类残留字段不能回流成通用模板参数。
```

### 6.6 专业披露 vs 核心文档处理

| 冲突点 | 归属 |
| --- | --- |
| 年报、ESG、财务附件、专利、双语 | `professional_disclosure` |
| 版式整理、附件归档、报告 | 核心可做 |
| 审计、法律、专利、财务、翻译结论 | plugin/manual gate |

裁决规则：

```text
核心只处理格式、结构、字段、风险和产物；
专业判断一律进入插件、人工确认和边界报告。
```

### 6.7 AI/导入能力 vs 目标场景

| 冲突点 | 归属 |
| --- | --- |
| PDF/OCR/LaTeX/AI 生成 | `import_ai_boundary` |
| 导入后形成的结构化题源 | `exam_education` |
| 导入后形成的合同字段 | `contract_delivery` |
| 导入后形成的投稿材料 | `english_journal` |

裁决规则：

```text
AI/导入是入口，不是最终场景。
只有经过置信度报告、结构化映射和人工确认后的结果，才进入目标 pack。
```

## 8. 控件一致性和模板管理边界

用户已明确要求：场景配置中的控件样式控制必须与模板管理中规定的样式一致。V20 将其定义为 `S17 控件契约` 的硬门槛。

### 8.1 样式参数归属

| 参数类型 | 归属 | 场景页处理 |
| --- | --- | --- |
| 字体、字号、段落、标题、目录、题注、页眉页脚、参考文献样式 | Template | 场景只能选择模板或带业务理由覆盖 |
| 处理范围、编号重建/保留、公式转换、引用检查、清理策略 | Scene | 场景直接管理 |
| 字段、图片、签章、附件、题源、合同主体 | Material | 场景声明需要，资料包提供事实 |
| final/review/student/teacher/archive/report/package | Output | DeliveryPreset 管理 |
| 本次路径、本次临时覆盖 | Session | 不写回可复用场景 |
| AI/OCR/PDF/专业判断 | Plugin / Manual Gate | 不进入核心排版承诺 |

### 8.2 同名控件硬规则

| 参数 | 场景页必须如何做 |
| --- | --- |
| 中文字体 / 英文字体 / 字号 | 复用模板管理控件和选项 |
| 左缩进 / 右缩进 | 同行呈现可接受，但单位、步进、写入字段必须一致 |
| 特殊缩进 | 必须可切换无/首行/悬挂；无时禁用数值并写出 0 |
| 行距类型 / 行距值 | 类型和值必须联动；固定类型禁用值 |
| 段前 / 段后 | 同行呈现可接受，复用 `SpacingInput` 语义 |
| 表格行高 | 普通表格不暴露；固定版位 profile 才暴露 `w:trHeight` |
| 水印 | 业务状态归场景/输出；颜色字号等视觉细节需有模板/控件契约 |
| 公式 | 转换策略归场景；公式外观基线归模板或场景有理由覆盖 |

验收口径：

```text
场景页如果新增样式控件，必须能在 control_contract_registry.py 中找到 canonical contract；
如果没有 contract，先补 contract 和测试，再开放 UI。
```

## 9. Word/OOXML 风险闭环

V20 要求每个 L2 以上 pack 至少声明会碰哪些 Word surface，并给出 preserve、repair、replace、block、warn、skip 或 plugin gate。

| Surface | 高频场景 | 默认策略 |
| --- | --- | --- |
| `w:p` / `w:r` / `w:pPr` / `w:rPr` | 全部 | preserve inline structure，避免无证据全量重建 |
| `styles.xml` | 模板、论文、公文、长文档 | 模板所有，场景覆盖需 provenance |
| `numbering.xml` | 论文、公文、技术、合同 | 先声明 rebuild/preserve/repair |
| `w:tbl` / `w:tr` / `w:tc` | 标书、表单、试卷、报价 | grid、merge、header、pagination、height 分开治理 |
| `w:trHeight` | 表单、证书、答题卡、套打 | fixed-layout profile，不属于普通表格 |
| `w:sdt` | 合同、表单、HR、公文 | tag/alias 映射、填充、残留报告 |
| `w:txbxContent` / `v:shape` / `wps:txbx` | 证书、表单、公文、双语 | 预检和 fixed-layout 策略 |
| `w:drawing` / media / rels | 题图、签章、资质、图表 | asset role、manifest、关系复制 |
| `w:fldSimple` / `w:instrText` | TOC、PAGE、REF、交叉引用 | preserve/update/skip 可见 |
| header/footer/sectPr | 论文、公文、合同、水印 | 外观和状态分离 |
| comments/revisions | 合同、修回稿、审阅稿 | 默认保留或要求确认 |
| footnotes/endnotes | 学术、法律、书稿 | CountProfile 声明是否计入 |
| hidden text | 合同、披露、双语 | 预检、显隐和计数说明 |
| OLE/VBA/embedded | 财务、技术、标书 | block/warn/skip |
| package relationships | 附件、图片、外链 | inventory 和外链风险报告 |

## 12. 新需求裁决流程

任何新需求先按下面流程判定：

```text
1. 用户自然会怎么说？
2. 是否落在 9 条需求带之一？
3. 是否能落到已有 12 个 coverage pack？
4. 是否只是模板外观参数？
5. 是否只是资料字段、图片或附件？
6. 是否只是输出版本或归档产物？
7. 是否只是本次会话路径或临时覆盖？
8. 是否涉及 AI/OCR/PDF/LaTeX 或专业判断？
9. 是否有 Word/OOXML 风险面？
10. 是否能进入 report/issue/artifact/test？
```

裁决结果：

| 情况 | 处理方式 |
| --- | --- |
| 已有 pack 能承接 | 补子场景/profile/workflow/closure task |
| 是外观基线 | 回模板管理 |
| 是字段/素材 | 回 MaterialSchema/资料包 |
| 是版本/产物 | 回 DeliveryPreset/OutputConfig |
| 是本次路径 | 回 Session |
| 是 AI/导入/专业判断 | 回 Plugin/Manual Gate |
| 真正新高频任务族 | 先建 planned family，不直接上导航 |

如果某个词找不到 pack、profile、delivery、material schema 或 plugin boundary，就是遗漏。

## 14. V20 结论

当前功能点确实还不完善，但完善方向不能是“继续堆控件”。正确方向是：

```text
保持 12 个 coverage pack；
补齐每个 pack 的高频子场景；
把公式、输出、水印、固定行高、AI/OCR/PDF、专业判断等边界固定下来；
用能力槽位检查每个 pack 是否断链；
用 Word/OOXML 风险面约束执行策略；
用 control contract 保证场景样式控件与模板管理一致；
用 report、issue queue、artifact 和 tests 证明闭环。
```

V20 的下一步建议不是新增场景入口，而是按下面顺序推进剩余高层工程闭环：

```text
N2.130 control contract expansion for formula/output/watermark
N2.131 issue queue repair routing
N2.132 rule source governance expansion
```

这样才能做到：高频场景不漏，边界不飘，链路不断，后续实现不会把模板、场景、资料包、输出和插件再次揉成一团。
