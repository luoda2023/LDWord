# 高层场景能力矩阵深度规划（2026-06-16）

## 1. 文档目标

本文专门回答一个更高层的问题：

> Alavette Form 的“场景”到底应该覆盖哪些高频文档任务，能力域怎样划分才不会遗漏，边界怎样定义才不会把模板、资料包、交付物和插件混在一起？

本文不是单纯的功能清单，也不是 `module_switches` 表。它用于指导后续 `ScenePanel`、内置场景、profile、资料包 schema、交付 preset、合规引擎和执行链路的长期设计。

参考输入：

- `docs/audits/场景定义横向审阅与分场景规划_2026-06-15.md`
- `docs/audits/场景与模板体系规划.md`
- `F:/01 DownLoad/02 EdgeBrows/count_engine_tech_record.md`
- `F:/01 DownLoad/02 EdgeBrows/exam_generator_tech_stack_record.md`
- `https://chatgpt.com/share/6a302438-f26c-83ee-805c-6d92fbcacb9e`

外部记录只吸收产品边界、能力分层和流程判断；不直接照搬未经验证的依赖选型，也不把“某个垂直方案”硬塞进核心场景。

## 2. 总判断

现有 6 个场景入口是合理起点，但还不是完整的场景能力矩阵。当前主要缺口不是少几个开关，而是缺少一套能解释高频任务差异的上层结构：

```text
场景族
→ 场景 profile
→ 输入源契约
→ 资料包 schema
→ 处理范围
→ 能力域
→ 合规 profile
→ 对象保护策略
→ 交付 preset
→ 批量/多版本策略
```

因此后续不应继续把“论文、标书、公文、试卷、投稿、项目申报、合同、简历”等需求压缩成同一种“排版场景”。它们共享 Word 处理底座，但任务目标、输入来源、合规口径和交付物完全不同。

## 3. 参考材料吸收结论

### 3.1 多口径计数记录

`count_engine_tech_record.md` 的核心价值是：字数/词数/数量检查不是单一函数，而是 profile-driven multi-metric count engine。

应吸收为：

- `compliance_profile.count_profile_id` 的正式能力方向；
- `校验与合规` 能力域中的独立子能力；
- 中文学位论文、英文期刊、项目申报、试卷、报告等场景共享的底层引擎；
- UI 报告必须解释“采用什么口径、计入哪些部分、排除哪些部分”，不能只显示一个数字。

不应吸收为：

- 单独的“字数统计场景”；
- 写死在论文场景里的特殊逻辑；
- 承诺与 Word、学校系统、投稿系统 100% 一致。

### 3.2 试卷生成记录

`exam_generator_tech_stack_record.md` 的核心价值是“一份结构化数据，多版本输出”。这不只属于试卷，也适用于标书正副本、投稿材料包、合同审阅稿、批量函件。

应吸收为：

- `input_source_profile.structured_formats`；
- 结构化 JSON / Markdown 预览 / Word 模板渲染的输入链；
- `delivery_presets` 的多版本语义；
- “答案/解析/知识点是否显示”这类版本差异必须是渲染配置，不是重新生成内容。

不应吸收为：

- 让核心系统直接承诺 AI 生成内容；
- 让 Markdown 成为最终排版依据；
- 过早实现复杂几何图自动生成。

### 3.3 分享对话

分享对话标题为“Word文档自动生成技术栈”。可抓取内容与两份本地记录相互印证，并额外强化了三点：

- 英文期刊投稿应是 `Journal Profile Engine + 投稿包生成`，不是固定 Word 模板；
- LaTeX 应定位为公式级/片段级兼容，完整 LaTeX 工程无损转 Word 不应成为核心承诺；
- 可编辑 Visio / OLE / 嵌入 Excel 等对象必须进入对象保护策略，不能在排版链路里被无意识破坏。

这些内容已经与当前 `input_source_profile`、`compliance_profile`、`delivery_presets`、`ObjectPreflightPolicy` 的模型方向一致，但 UI 和执行消费仍未完全闭合。

## 4. 基本概念边界

| 概念 | 负责什么 | 不负责什么 | 示例 |
| --- | --- | --- | --- |
| 场景族 | 一类高频任务心智 | 具体学校/公司/期刊细则 | 中文论文、英文期刊、标书、试卷 |
| 场景 profile | 场景族下的规则组合 | 外观细节全集 | 硕士论文、Nature Article、政府采购标书 |
| 模板 | 文档外观基线 | 是否执行、输出什么 | GB/T 7713、工程投标模板 |
| 输入源契约 | 接受哪些格式和导入风险 | 本次具体文件值 | docx、Markdown、JSON、LaTeX 片段 |
| 资料包 schema | 需要哪些字段/图片/签章 | 场景策略本身 | 公司名、Logo、公章、作者信息 |
| 合规 profile | 检查哪些规则和口径 | 版式外观基线 | 字数、图表数量、声明材料、附件齐套 |
| 交付 preset | 输出哪些版本/文件 | 输入数据真实性 | final、review、student、teacher、cover letter |
| 会话 | 本次运行状态 | 可复用规则 | 当前文档、输出目录、本次临时覆盖 |
| 插件 | 高风险/窄领域扩展 | 核心场景常规能力 | 完整 LaTeX 工程、复杂几何图、法律审查 |

判断顺序：

1. 只影响外观默认值，归模板。
2. 决定任务类型、处理范围、能力开关、失败策略，归场景。
3. 决定字段、图片、资产、实体，归资料包。
4. 决定规则口径、计数、检查清单，归合规 profile。
5. 决定输出版本和文件包，归交付 preset。
6. 只对本次有效，归会话。
7. 高风险、窄领域、依赖外部服务或难以稳定承诺，归插件。

## 5. 能力域 V2

场景能力域不应直接等同现有 6 个 UI 能力组。建议长期稳定为 12 个能力域：

| 能力域 | 核心问题 | 当前承载 | 主要缺口 |
| --- | --- | --- | --- |
| 输入与结构化来源 | 接受什么输入，怎样导入 | `InputSourceProfile` | UI 未展示；Markdown/LaTeX 策略未执行闭环 |
| 资料包与资产 | 需要哪些字段、图片、签章 | `material_schema_id`、资料包规划 | schema 未产品化；缺失策略未统一 |
| 范围与结构识别 | 处理哪些区域，哪些只读 | `FormatScopeConfig` | UI 只露出分区，页码/关键词/正文起点薄弱 |
| 模板版式基线 | 文档长什么样 | `TemplateConfig` | 场景覆盖理由需可解释 |
| 结构排版执行 | 标题、段落、页面、分节 | 核心模块 | 对象保护命中时的安全降级仍需细化 |
| 表格图表题注 | 表格、图片、题注、居中 | `table_format/caption/figure_table_center` | 图像质量、图表清单、题注引用顺序未合规化 |
| 公式与专业符号 | 公式、LaTeX、化学式、专业符号 | `formula_convert`、`equation_table_format`、`chem_typography` | `formula_convert` 未进入 UI/执行模块 |
| 参考文献与引用 | 文献格式、引用链接、Bib/CSL | `reference_format/citation_link` | BibTeX/CSL/期刊 profile 未落地 |
| 校验与合规 | 规则检查、字数、附件、声明 | `ComplianceProfile`、`validation`、`CountEngine` | CountEngine 已有 profile registry 与 Word XML 范围第一版；真实规则仍需扩展 |
| 对象保护与安全 | OLE、Visio、宏、修订、域 | `ObjectPreflightPolicy` | UI 未展示；跳过映射需按真实风险继续扩展 |
| 输出交付 | 生成哪些文件、如何命名 | `OutputConfig`、`DeliveryPreset` | preset 已驱动多版本 DOCX/报告、目标模板交付、结构化中间产物、文本对比稿第一版；内容显隐与格式级对比仍未闭合 |
| 批量与协同审阅 | 多实体、多版本、对比、修订 | `BatchPreset`、compare output | 批量目录、失败隔离、审阅链路未闭合 |

现有 UI 可以继续分组为“处理范围、功能开关、输入与资料、校验与合规、输出设置”等，但摘要和详情必须能投影上述 12 个域，否则用户会不知道某个高频能力到底在哪配置。

## 6. 高频场景族覆盖矩阵

下面矩阵用于避免高频场景遗漏。它不是要求一次性实现所有行，而是要求每一类需求都有明确落点。

| 场景族 | 高频子场景 | 等级 | 应落点 | 必备能力域 | 清晰边界 |
| --- | --- | --- | --- | --- | --- |
| 自定义/手动 | 未知文档、一次性修复、调试 | P0 | 内置场景 | 范围、能力开关、输出、安全 | 不预设专业合规 |
| 中文学术论文 | 本科/硕士/博士、课程论文、开题、综述 | P0 | 内置场景 + `thesis_cn` profile | 结构、模板、公式、参考文献、计数、合规 | 不等同英文期刊投稿 |
| 英文期刊投稿 | 初投稿、修回、改投、投稿包 | P1 | 独立场景族 `journal_en` | Journal profile、参考文献、计数、声明、投稿包、安全 | 不承诺出版社最终版式 |
| 试卷/教学材料 | 学生版、教师版、答案版、解析版、答题卡、教案 | P1 | 独立场景族或教育 profile | 结构化输入、公式、图片、多版本输出 | 不让 AI 分别生成多个版本 |
| 标书/商务投标 | 工程投标、政府采购、商务方案、陪标批量 | P0 | 内置场景 | 资料包、签章图片、表格、目录、批量、合规 | 不做法律/商务实质判断 |
| 项目申报/评审 | 基金、课题、项目建议书、验收、成果材料 | P1 | 独立 profile，可共享学术/标书能力 | 字数、附件清单、团队/预算资料、材料包 | 不替代申报系统校验 |
| 公文/行政文书 | 通知、函、请示、批复、纪要、制度 | P0 | 内置场景 + 子 profile | 公文模板、字段、保留编号、水印、输出 | 不把版记/页眉样式放场景里 |
| 会议与制度材料 | 会议纪要、议程、制度汇编、流程文件 | P1 | 行政文书 profile | 模板、资料字段、编号保留、批量汇编 | 不新建过多小场景 |
| 技术/工程文档 | 技术规范、SOP、接口文档、操作手册、验收报告 | P0 | 内置场景 | 表格图表、公式、版本字段、对象保护、变更报告 | 高风险对象默认保护 |
| 通用报告/计划 | 调研报告、总结、周报、可研、商业计划 | P0 | 内置场景 | 快速排版、目录、表格、输出报告 | 少参数，不强推资料包 |
| 合同/协议/法务文书 | 合同、协议、授权书、承诺函、保密协议 | P2 | 格式/资料一致性 profile | 字段、签章、版本对比、修订保护 | 不做法律条款审查结论 |
| HR/档案/批量函件 | 简历、证明、邀请函、录取通知、人员档案 | P2 | 资料包批量 profile | Excel/JSON、字段、批量输出、汇总报告 | 不作为顶层内置场景抢入口 |
| 产品/售前材料 | 产品手册、白皮书、售前方案、报价说明 | P2 | 技术/报告/标书 profile | 图片、表格、版本、资料字段、输出包 | 不等同营销内容生成 |
| 财务/审计/报价材料 | 报价单、预算说明、审计底稿封面、结算材料 | P2 | 资料/表格 profile | 表格、字段一致性、附件清单、输出 | 不做财务审计判断 |
| 专利/知识产权材料 | 专利交底书、说明书、权利要求书 | P2 | 专业插件或技术 profile | 结构模板、图号、术语、版本 | 不承诺专利法律质量 |
| 书稿/长文档出版 | 书稿、手册汇编、章节合集 | P2 | 长文档 profile | 章节、目录、交叉引用、索引、输出 | 不做出版社排版系统替代 |

等级含义：

- P0：当前已有入口或应立即补齐闭环。
- P1：高频且与现有能力高度相邻，应进入近期模型和 UI 规划。
- P2：高频但专业风险、差异或入口竞争较高，先用 profile/插件承接，不急于放入顶层内置场景。

## 7. P0 场景必须补齐的内容

### 7.1 自定义/手动

必须表达：

- 所有分区可选，能力默认保守关闭；
- 输入支持 docx/markdown/json，但 LaTeX 默认禁用；
- 合规只做基础手动检查；
- 输出默认 final；
- UI 要突出“手动组合”，适合保存为自定义场景或会话预设。

不能做：

- 默认开启专业能力；
- 暗中套用论文/标书规则。

### 7.2 中文学术论文

必须表达：

- `thesis_cn` 与未来 `journal_en` 分离；
- 学校/学院/学位类型进入 `compliance_profile`；
- 字数、摘要、参考文献、图表、公式数量进入 CountEngine；
- 参考文献、目录、题注、页眉页脚仍由模板提供外观基线；
- 场景决定是否处理、如何失败、报告如何解释。

必须补的链路：

- CountEngine；
- 论文合规报告；
- 公式转换 UI/执行；
- 参考文献引用顺序/链接检查；
- 对象保护命中后的用户可见解释。

### 7.3 标书/商务投标

必须表达：

- 资料包必需；
- 关键字段和图片角色可阻断；
- 支持正本/副本/汇总报告；
- 支持多公司/多项目 profile 的批量输出；
- 缺公章、Logo、资质附件等要进入合规报告。

必须补的链路：

- 资料包 schema 管理；
- 图片角色预检；
- delivery presets 驱动真实多版本输出；
- 批量失败隔离和汇总报告。

### 7.4 公文/行政文书

必须表达：

- 默认保留原编号；
- 字段资料包用于单位、文号、日期、签发人；
- 状态水印属于场景/会话；
- 公文模板只负责版心、字体、页码、版记等外观。

必须补的链路：

- 公文字段 schema；
- 征求意见稿/内部稿/正式稿 delivery preset；
- 修订、批注、域的保护提示。

### 7.5 技术/工程文档

必须表达：

- 表格图表、公式、图片、版本字段是高频能力；
- Visio/OLE/嵌入 Excel 是常见对象，必须默认保护；
- 变更报告和审阅稿是自然交付物；
- Markdown 可以作为输入，但不能替代 Word 模板最终排版。

必须补的链路：

- 对象预检 UI；
- 图片/图表质量与编号检查；
- 技术术语/版本字段资料包；
- change report delivery preset。

### 7.6 通用报告/计划

必须表达：

- 少参数、快速规范化；
- 默认不开复杂公式、参考文献、资料包；
- 保留最终稿/对比稿/报告；
- 可作为普通用户默认推荐。

必须补的链路：

- 能力摘要要简洁；
- 可从报告场景升级为技术/标书/项目申报 profile；
- 默认安全策略不能破坏复杂对象。

## 8. P1 场景设计要点

### 8.1 英文期刊投稿 `journal_en`

这应是独立场景族，不应塞进“论文排版”。

核心能力：

- Journal Profile YAML；
- Manuscript Model；
- title / abstract / main text / methods / references / display items 计数；
- figure/table checker；
- BibTeX / CSL / citeproc；
- cover letter、declaration、highlights、SI 清单；
- 投稿包生成；
- LaTeX 公式级/片段级兼容；
- 高风险对象预检。

边界：

- 不承诺一键排成出版社最终出版版式；
- 不承诺完整 LaTeX 工程无损转 Word；
- 不自动抓取期刊官网作为可信规则源，除非后续做 profile 更新器。

### 8.2 试卷/教学材料 `exam_teaching`

核心能力：

- AI 或题库输出结构化 JSON；
- Markdown 只做预览/人工检查；
- Pydantic-like schema 校验题型、分值、答案、解析；
- 学生版、教师版、答案版、解析版、答题卡；
- 公式、图片、图表、简单学科图形；
- 多版本共享同一份数据源。

边界：

- 核心场景不负责 AI 内容质量；
- 复杂几何图自动生成放插件；
- 学生版和教师版不能由两次生成得到。

### 8.3 项目申报/评审材料

核心能力：

- 申报指南 profile；
- 字数/附件/成果/预算/团队信息检查；
- 多附件清单和缺项报告；
- 申报书、附件包、审查报告；
- 项目/团队/单位资料包。

边界：

- 不替代申报系统；
- 不做实质评审分数预测；
- 附件内容真实性由用户负责。

### 8.4 合同/协议格式化 profile

核心能力：

- 甲乙方、金额、日期、签章字段一致性；
- 修订/批注保护；
- 对比稿、审阅稿、签署稿；
- 空白字段和占位符残留检查。

边界：

- 不提供法律意见；
- 不判断条款是否有效；
- 只做格式、字段、版本和交付链路。

### 8.5 HR/批量函件 profile

核心能力：

- Excel/JSON 批量数据；
- 人员字段 schema；
- 单人一份输出、汇总报告、失败隔离；
- 简历/证明/邀请/通知模板。

边界：

- 不需要作为顶层内置场景；
- 更适合成为 `输入与资料 + delivery preset + batch_preset` 的组合 profile。

## 9. 不应进入核心场景的能力

| 能力 | 原因 | 建议落点 |
| --- | --- | --- |
| 完整 LaTeX 工程无损转 Word | 宏包、class、浮动体、TikZ 差异过大 | 高级导入插件 |
| 复杂几何图自动生成 | 领域窄，实现风险高 | 教育/数学插件 |
| AI 内容生成 | 质量责任和外部模型依赖复杂 | 输入助手插件 |
| 法律条款审查 | 高风险专业判断 | 外部专业插件，只保留格式/字段检查 |
| 财务/审计判断 | 高风险专业判断 | 仅做格式、附件、字段一致性 |
| 期刊官网自动抓取规则 | 外部网站变化大 | profile 更新器，带人工确认 |
| 全量 docx 重建 | 容易破坏关系、域、OLE、Visio、修订 | 用户确认的高风险模式 |

核心判断标准：

```text
高频、可解释、可测试、低破坏、可本地闭环 → 核心能力
窄领域、高风险、依赖外部、难承诺稳定结果 → 插件或 profile
```

## 10. 场景配置 UI 与模板管理样式一致性

用户已经明确要求：场景配置中的控件样式控制必须与模板管理保持一致。这里应作为硬性设计约束。

### 10.1 控件体系

场景配置页应继续复用模板管理已经稳定的控件：

- `Card`：详情页容器；
- `SummaryGrid`：profile、合规、交付摘要；
- `TemplateFormStack` + `template_form_row`：表单行；
- `StyledComboBox`：策略/类型选择；
- `ToggleSwitch`：布尔开关；
- `FeatureToggleRow`：能力域开关；
- `OptionToggleChip` / 分段控件：少量互斥模式；
- `StyledSpinBox` / 已统一的输入控件：数值类参数。

不应新增另一套场景专用 combo、switch、form row 或卡片样式。

### 10.2 布局规则

场景配置详情页应遵循模板管理的密度和行布局：

- 同类短字段可放同一行，例如输入格式/Markdown 策略、合规 profile/报告级别、默认交付/交付数量；
- 强关联开关与策略应相邻，例如对象预检开关、保护模式、命中后跳过高风险模块；
- 摘要在上，关键控件在中，高级细项在下；
- 不嵌套卡片；
- 不用大段说明文字替代控件；
- 能用图标、combo、toggle 表达的，不用大按钮式文字块表达；
- UI 文案要说明“当前场景会做什么”，不展示底层模块名作为主要语言。

### 10.3 必须进入 ScenePanel 的 projection

`input_source_profile`、`compliance_profile`、`delivery_presets` 应在 `ScenePanel` 中形成可见摘要：

```text
场景概览
  输入：docx / markdown，LaTeX 公式片段
  合规：thesis_cn，详细报告
  对象保护：warn / strict，命中后跳过高风险模块
  交付：final / review / compliance_report

输入与资料
  接受格式、结构化格式、资料包是否必需、必填字段、图片角色、失败策略

校验与合规
  合规 profile、计数 profile、检查范围、对象预检、报告级别

输出设置
  默认 preset、全部 presets、产物类型、命名模板、是否输出结构化中间件
```

这些摘要必须和 loader/resolver/pipeline 使用的是同一份 `SceneWorkspace` 数据，不能再出现 UI 摘要与执行事实不一致。

## 11. 一个场景算完善的验收标准

每个 P0/P1 场景或 profile 必须回答以下问题：

1. 用户任务目标是什么？
2. 默认输入格式是什么？
3. 哪些输入是高风险导入？
4. 是否需要资料包，资料包 schema 是什么？
5. 默认处理范围是什么？
6. 默认模板和兼容模板是什么？
7. 场景覆盖了哪些模板参数，业务理由是什么？
8. 默认启用哪些能力域？
9. 专业能力如公式、引用、图片、表格如何处理？
10. 合规 profile 是什么，计数口径是什么？
11. 检测到 OLE、Visio、宏、修订、批注、文本框、域时怎么办？
12. 输出哪些 preset？
13. 批量/多版本是否来自同一份结构化数据？
14. UI 摘要、resolver、scheduler、pipeline 和报告是否说同一套事实？
15. 哪些事情明确不承诺？

答不上这些问题的，只能算“能力组合草稿”，不能算完整场景。

## 13. 近期直接修正建议

优先级最高的不是马上增加一堆场景入口，而是让当前矩阵有真实闭环：

1. `ScenePanel` 必须显示并编辑三类新增 profile：输入、合规、交付。
2. `校验与合规` 详情必须包含对象预检和报告级别。

6. `journal_en`、`exam_teaching`、`project_application` 已先进入规划级 registry，后续才能按成熟度进入场景工厂或 profile。

## 14. 最终结论

完善的场景能力矩阵不是“多加几个场景名”，而是让每个高频任务都有明确归属：

```text
是场景族，还是 profile？
是模板问题，还是执行策略？
是资料包字段，还是交付 preset？
是合规规则，还是专业插件？
```

只要这个归属清楚，后续功能扩展就不会反复出现“场景里缺一块、模板里塞一块、执行链又读不到”的断链问题。当前已补齐第一版 UI projection、合规/计数执行、CountEngine profile registry、delivery presets 执行、目标模板级交付、结构化中间产物、文本对比稿和 P1 场景族规划级 registry；下一步最应推进的是 CountEngine 范围抽象深化、delivery preset 内容显隐/格式级对比、P1 profile 可执行化和公式转换闭环。

## 21. Phase C3.3 对比 DOCX 交付补记（2026-06-16）

- Workbench payload 新增 `compare_paths`；
- 单个非默认 delivery preset 现在也会按 preset 输出，避免主输出与 compare/intermediate artifact 路径脱节；
