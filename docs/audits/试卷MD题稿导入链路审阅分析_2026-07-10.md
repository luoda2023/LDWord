# 试卷 MD 题稿导入链路审阅分析

日期：2026-07-10

## 1. 结论

试卷场景不应新增一个前台可感知的“题源包”或“资料包”概念。

从当前项目结构看，试卷题源的对应抽象已经存在：

- `MaterialExecutionContext` 是运行时资料上下文。
- `entity_data` 是执行时注入资料字段和结构化资料的承载层。
- `exam_items_v1` 是已经注册的试卷题源资料规则。
- `exam_question_schema` 已经能从 `entity_data["exam_items"]` 校验结构化题源，并渲染学生卷、答案速查等试卷产物。
- `EXAM_MARKDOWN_AUTHORING_PROMPT` 已经定义了“适合导入 Alavette Form 试卷场景的 Markdown 试卷内容”。

因此，正确方向不是“新增资料包板块”，而是补齐：

```text
用户上传单个 .md 题稿
  -> Markdown 题稿导入器
  -> exam_items_v1 结构化 payload
  -> MaterialExecutionContext.entity_data["exam_items"]
  -> 既有结构校验与试卷渲染链路
  -> 学生卷 / 答案速查 / Markdown 预览 / 报告证据
```

用户侧只需要理解“上传 Markdown 题稿”。资料上下文和 `exam_items_v1` 是内部模型，不应被包装成新的前台资料包。

## 2. 讨论纠偏记录

前序讨论中出现过两个容易走偏的方向。

第一，把试卷场景类比公文场景，认为也需要一个“资料包”板块。这个判断不够准确。公文、合同、批量表单等场景通常需要多个资料字段、素材、签章、附件或结构化资料并行输入；试卷默认链路更像“一个题稿源 + 一个母版 + 一组输出规则”。用户主入口应保持单文件上传。

第二，把兼容理解为“让上传框支持 `.md`”。这只是表层补丁。当前 `Pipeline.execute()` 第一阶段会直接用 `python-docx` 打开输入文件，`.md` 即使能被上传，也不能进入正确运行路径。真正缺的是 Markdown 到 `exam_items_v1` 的导入转换。

本轮审阅后的准确表述是：

```text
试卷版需要的是“MD 题稿导入 + 结构预览”，不是“资料包上传”。
```

## 3. 当前代码证据

### 3.1 已有资料上下文

`src/config/material_context.py` 中已有 `MaterialExecutionContext`：

```text
archive_id
profile_id
profile_name
entity_data
field_aliases
entity_assets_dir
images
replacements
asset_items
image_rules
```

它的 `to_resolve_kwargs()` 会把 `entity_data` 注入 `resolve_config()`，最终进入 `ResolvedConfig.entity_data`。这已经是运行时资料的承载层。

### 3.2 已有试卷题源资料规则

`src/config/material_schema_registry.py` 中已有：

```text
schema_id = "exam_items_v1"
family = "exam_teaching"
description = "Structured paper and question metadata for exam rendering."
fields = paper_title / subject / grade / duration / total_score
asset_roles = question_figure
batch_mode = "structured_source"
```

这说明项目已经把试卷题源定义成结构化资料源，而不是普通 Word 文档。

### 3.3 已有结构化试卷运行时

`src/shared/engine/exam_question_schema.py` 已经包含：

- `inspect_exam_question_schema(config)`
- `build_exam_delivery_runtime(config, output_dir, source_stem, validation)`
- `render_exam_markdown_preview(payload)`

该链路从 `entity_data` 里寻找：

```text
exam_items
exam_paper
paper
paper_json
question_schema
questions_json
questions
sections
```

并已经能把结构化 payload 渲染为学生卷、答案速查等 Word 产物。

### 3.4 已有 Markdown 题稿规范

`src/shared/engine/exam_paper_style.py` 中的 `EXAM_MARKDOWN_AUTHORING_PROMPT` 明确要求：

- 只输出 Markdown 正文。
- 不写页眉、页脚、页码、密封线、字体、页边距等版式信息。
- 使用 `#` 表示试卷标题。
- 使用引用行记录科目、年级、考试时间、满分。
- 使用 `##` 表示大题。
- 使用 `1.` 表示小题。
- 使用 `A. B. C. D.` 表示选项。
- 每题标明分值。
- 文末单独输出 `## 答案速查`。
- 需要答题区时写入 `answer_area_kind` 和 `answer_lines`。

这已经是可导入 Markdown 的产品契约雏形。

### 3.5 当前缺口

当前缺口不是结构化运行时，而是导入端：

```text
缺少 Markdown 文件 -> exam_items_v1 payload 的解析器。
```

同时，当前快捷上传和执行链路仍有不一致：

- `QuickExecutionDropArea` 仍硬编码只接受 `.docx`。
- 上传框文案仍是 “支持格式：.docx”。
- 文件选择器仍是 `Word Documents (*.docx)`。
- `Pipeline.execute()` 文档和实现仍按 `.docx` 输入处理。
- 默认试卷方案声明接受 Markdown，但 `material_schema_id` 仍为空。

这导致 UI、配置和运行时三者没有闭环。

## 4. 正确产品模型

试卷场景的前台模型应是：

```text
上传题稿
选择母版
查看题源与装配预览
生成学生卷 / 答案速查
```

而不是：

```text
上传资料包
填写资料包
再把资料包同步到试卷
```

用户主路径只需要上传 `.md`。JSON 可以作为高级调试或内部导入格式，Word 题稿解析可以作为后续能力，不应混在当前默认主入口里。

## 5. 正确技术模型

### 5.1 不新增平行题源包

不建议新增 `ExamSourcePackage` 这种与 `MaterialExecutionContext` 平行的运行时概念。

如果需要内部对象，可以命名为导入结果，而不是资料包，例如：

```text
ExamMarkdownImportResult
```

它只负责描述一次 Markdown 导入的结果：

- `payload`
- `summary`
- `issues`
- `source_path`
- `source_excerpt`

导入完成后，仍然落到：

```text
material_context.entity_data["exam_items"] = json.dumps(payload, ensure_ascii=False)
```

### 5.2 `exam_items_v1` 是落点

Markdown 解析后的 payload 应符合现有结构：

```json
{
  "paper_title": "七年级数学期中模拟试卷",
  "subject": "数学",
  "grade": "七年级",
  "duration": "90 分钟",
  "total_score": "100",
  "sections": [
    {
      "title": "一、选择题",
      "questions": [
        {
          "stem": "下列各数中，最小的是（　　）。",
          "options": ["A. -3", "B. 0", "C. 2", "D. -1"],
          "answer": "A",
          "analysis": "负数小于非负数，-3 小于 -1。",
          "score": 5
        }
      ]
    }
  ]
}
```

这样可以复用现有校验、预览、输出、报告，不需要另起一条试卷生成逻辑。

### 5.3 默认试卷方案应绑定 schema

默认试卷场景应设置：

```text
input_source_profile.material_schema_id = "exam_items_v1"
input_source_profile.require_material_package = false
```

`require_material_package = false` 很关键。它表示用户不需要上传资料包；只是这个场景内部使用 `exam_items_v1` 作为题稿结构契约。

## 6. UI 审阅结论

### 6.1 顶部上传框

试卷版顶部上传框应场景化，不应复用当前固定 `.docx` 文案。

建议主文案：

```text
上传 Markdown 题稿
支持格式：.md / .markdown
```

JSON 可作为高级入口或调试入口，不建议展示在默认主文案中。Word 题稿若未实现解析，也不应继续展示为可上传题源，否则用户会以为所有 Word 试卷都能被识别成大题、小题、答案。

### 6.2 题源与装配卡片

“题源与装配”卡片是正确方向，但当前只能显示静态说明。等 Markdown 导入器接入后，它应显示真实解析结果：

```text
题源：已加载 Markdown 题稿
结构：3 大题 / 15 小题
答案：15/15
解析：15/15
分值：声明 100 / 计算 100
输出：学生卷 + 答案速查
状态：可生成
```

如果解析失败或有不确定项，应显示：

```text
状态：需确认
问题：第 8 题未识别答案；第 12 题分值缺失
```

### 6.3 不应提前展示虚假题量

在 Markdown 尚未解析前，只能显示：

```text
等待题稿
```

或：

```text
题量待结构化校验
```

不能静态写死“多少大题多少小题”。这与之前讨论中“现在试卷链路真能预览到多少大题多少小题吗”的纠偏一致。

## 7. 执行链路建议

### 7.1 当前不可做的事

不要把 `.md` 直接传给当前 `Pipeline.execute()`。

当前 Pipeline 的基本假设仍是：

```text
输入是一个 .docx 文件
```

第一步会打开：

```python
Document(str(path))
```

因此 `.md` 文件必须在进入 Word pipeline 前被转换为结构化题源。

### 7.2 推荐分流

Workbench 运行前按场景和后缀分流：

```text
if scene is exam_paper and suffix in {".md", ".markdown"}:
    parse markdown
    inject payload into MaterialExecutionContext.entity_data["exam_items"]
    resolve_config()
    inspect_exam_question_schema()
    build_exam_delivery_runtime()
    build workbench payload
else:
    keep existing docx pipeline
```

这条分流不应绕开既有试卷运行时，而是调用既有 `exam_question_schema` 能力。

## 8. Markdown 解析器最小范围

第一版解析器只需要覆盖项目提示词已经约定的格式。

### 8.1 标题与元数据

- `# 试卷标题`
- `> 科目：数学　年级：七年级　考试时间：90 分钟　满分：100 分`

解析成：

```text
paper_title
subject
grade
duration
total_score
```

### 8.2 大题

普通 `##` 标题作为大题：

```text
## 一、选择题（本大题共 6 小题，每小题 5 分，共 30 分）
```

解析成 section title，同时可尝试提取声明题量和声明分值，用于校验。

### 8.3 小题

识别：

```text
1. 题干……（5 分）
```

解析：

- 小题序号
- 题干
- 分值

每个大题内小题可重新从 1 编号，不强行要求全卷连续编号。

### 8.4 选项

识别缩进或非缩进的：

```text
A. 选项
B. 选项
C. 选项
D. 选项
```

解析为 `options`。

### 8.5 答案速查

`## 答案速查` 之后进入答案区。支持：

```text
1. A
2. 6.3
3. A。解析：……
```

把答案按题号回填到前面的题目。若大题内题号重复，第一版可以按全卷顺序回填，后续再支持“一、选择题 1. A”这种分组答案。

### 8.6 答题区

支持在题目附近识别：

```text
answer_area_kind: lines
answer_lines: 3
```

或：

```text
answer_area_kind: free
answer_lines: 5
```

写入对应 question payload。

## 9. 验收标准

### 9.1 功能验收

- 试卷版上传框可选择 `.md`。
- 上传后不调用 `Document(str(md_path))`。
- 上传后能解析并显示真实大题数、小题数、答案覆盖数、解析覆盖数、分值一致性。
- 点击生成后输出学生卷和答案速查。
- 输出路径进入 Workbench 结果面板。
- 报告中能看到试卷题源结构校验和试卷多版本运行时渲染证据。

### 9.2 产品验收

- 默认试卷主入口不出现“资料包”表述。
- 默认试卷主入口不把未实现的 Word 题稿解析宣传为可用能力。
- “题源与装配”卡片只展示解析后的真实计数。
- 解析不完整时明确提示“需确认”，而不是静默生成。

### 9.3 回归验收

- 现有 `.docx` 普通格式化链路不受影响。
- 现有结构化 `entity_data["exam_items"]` 测试继续通过。
- `build_exam_delivery_runtime()` 输出学生卷、答案速查的行为不变。
- 公文、合同、批量表单等资料包场景不受试卷 MD 导入影响。

## 10. 建议实施顺序

1. 绑定默认试卷方案的 `material_schema_id = "exam_items_v1"`，保持 `require_material_package = false`。
2. 新增 Markdown 题稿解析器和单元测试。
3. 新增 Workbench 试卷 MD 分流执行路径，避免 `.md` 进入 `Document()`。
4. 将上传框改为可按场景配置 accepted suffixes 和文案。
5. 将“题源与装配”卡片接入解析摘要，不再只展示静态说明。
6. 补充报告字段：源文件路径、解析摘要、解析问题、结构化 payload 预览路径。

## 11. 最终判断

目前项目已经具备“试卷结构化题源运行时”，缺的是“Markdown 题稿导入到结构化题源”的前置桥。

所以，这件事不是大拆架构，也不是新增资料包系统，而是把已有设计真正闭环：

```text
Markdown 题稿
  -> exam_items_v1
  -> MaterialExecutionContext
  -> exam_question_schema
  -> 学生卷 / 答案速查
```

这条路线既符合当前项目已有模型，也符合用户实际心智：试卷场景只上传 MD 题稿，系统负责识别、预览、装配和生成。
