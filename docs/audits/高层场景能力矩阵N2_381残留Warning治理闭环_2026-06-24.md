# 高层场景能力矩阵 N2.381 残留 Warning 治理闭环

## 目标

N2.381 将 release gate 中仍然出现的 warning 从“灰区提示”升级为可审计的治理对象。原则是：能通过真实功能和样例补齐的 warning 必须补齐；确实属于外部插件、人工判断、专业责任或参考 Profile 的 warning，则必须登记为 `managed_warning`，并能追到边界证据、来源证据、dashboard 投影和 release gate 计数。

这轮不再把残留 warning 当成模板管理的散点参数处理，而是放回高层场景能力矩阵。公式、输出、水印、导入、专业披露、AI 生成、OCR/PDF/LaTeX、外部插件回执等能力都要先按场景边界建账，再决定 UI 控件、执行链路和测试口径。

## 已关闭的真实缺口

`visio_drawings` 不再是 ObjectPreflight 的残留 warning。它已经进入真实 DOCX fixture 和执行前风险识别链路：

- `scene_sample_fixture_registry` 将 `technical_long_docs_skip_objects` 覆盖到 `visio_drawings`。
- `scene_sample_docx_builder` 写入 `word/embeddings/diagram.vsdx` 作为可检测的样例对象。
- ObjectPreflight action audit 将目标数推进到 `11/11 ready`，warning 数降为 `0`。
- 样例回归测试验证 `embedded_workbooks`、`ole_objects`、`visio_drawings` 都会触发高风险模块跳过报告。

这说明“能真实补齐的 Word 对象风险”不能留在 managed warning 里；它应该进入 fixture、preflight、dashboard、drilldown 和 release gate 的正常完成度计数。

## 仍保留但必须治理的 Warning

N2.381 管理 10 个 warning，并要求它们全部为 `managed_warning`：

| 来源 | 数量 | 治理方式 | 说明 |
| --- | ---: | --- | --- |
| InputSourceProfile | 5 | boundary/manual/plugin input | 专业判断、导入转换、复杂 AI/图形生成不承诺为核心格式化能力 |
| CountProfile | 2 | reference count profile | `basic` 与 `word_xml_full` 作为 fallback/诊断 Profile 保留，不代表某个场景族默认承诺 |
| Dashboard projection | 3 | dashboard warning projection | dashboard 只镜像 InputSource 的边界 warning，不产生新的产品缺口 |
| ObjectPreflight | 0 | real fixture closure | `visio_drawings` 已关闭，后续对象风险必须优先真实补齐 |

发布门禁目标值：

- `warning_count = 10`
- `managed_warning_count = 10`
- `unmanaged_warning_count = 0`
- `object_preflight_warning_count = 0`
- `visio_fixture_closed_count = 1`

## 场景边界解释

`exam_education` 的输入 warning 属于插件/人工输入边界：复杂图形生成、AI 内容生成、题型语义质量不应被核心 Word 格式化能力过度承诺。它应连接到 `exam_ai_complex_diagram_gate` 等 plugin/manual gate，并在 UI 上呈现为场景能力边界，而不是模板参数缺失。

`professional_disclosure` 的输入 warning 属于专业责任边界：系统可以接收结构化材料、生成披露文档格式、输出报告，但不替代审计、法务、财务等专业判断。它需要 external handoff contract、boundary capability、release report 共同证明边界清晰。

`import_ai_boundary` 的输入 warning 属于导入转换边界：OCR、PDF、LaTeX、AI 导入等能力是高频场景入口，但不能直接宣称核心格式化引擎内置完整识别质量。它应通过 plugin/manual confirmation、失败报告、回退策略和导入 handoff 进入场景矩阵。

`ip_patent_documents` 的输入 warning 属于专业审查边界：专利/IP 文档可做结构、编号、格式和材料组织，但权利要求解释、审查意见判断等仍必须保留为专业人工边界。

`basic` 与 `word_xml_full` CountProfile 是参考 Profile：前者提供 fallback，后者提供诊断/全量 XML 视角。它们应继续被 runtime consumer 和 report surface 引用，但不能被 dashboard 误读成某个业务场景的默认完成度缺口。

## 控件样式一致性要求

场景配置中的控件样式控制必须继续复用模板管理中已经确立的控件契约：

- 同类参数使用同一套 label、单位、禁用态、空值清理和成对布局规则。
- 左缩进/右缩进、段前/段后、行距类型/行距值、特殊缩进类型/值等应保持一行内的成组交互语义。
- 特殊缩进必须能在 `无`、`首行`、`悬挂` 间交互切换，并同步控制数值输入的启用态。
- 行高、固定版式、公式、输出、水印等不应回流到通用模板样式里硬塞控件，而应先判定归属场景、能力边界和执行链路。

因此，N2.381 的 `managed_warning` 不代表 UI 可以忽略，而是要求 UI 使用同一套控件契约表达“这是场景边界/外部插件/参考 Profile”，并在 dashboard 与 drilldown 中给出来源。

## 闭环要求

N2.381 的闭环验收包括：

- 独立审计模块 `scene_residual_warning_governance_audit` 返回 passed。
- 导出脚本支持 JSON 与 Markdown。
- dashboard 新增 residual warning governance 计数和卡片。
- drilldown 新增 Residual warning governance 条目，10 条 warning 可按来源筛选。
- release gate 输出 `scene_residual_warning_governance_managed_count` 与 `scene_residual_warning_governance_unmanaged_warning_count`。
- CI workflow 纳入对应测试。

后续如果 warning 来源变化，不能静默漂移：新增 warning 必须先进入治理表；已消失 warning 必须从 allowlist 移除；能通过真实功能补齐的 warning 不能长期保留为 `managed_warning`。
