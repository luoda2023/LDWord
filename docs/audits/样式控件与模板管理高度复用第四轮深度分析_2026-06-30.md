# 样式控件与模板管理高度复用第四轮深度分析

日期：2026-06-30

## 1. 本轮判断

这轮再看，问题已经不能再归结为“场景页文案不友好”。更准确的判断是：

```text
模板管理已经形成了基线对象。
场景样式已经形成了覆盖对象。
执行前后已经开始形成复核对象和回执对象。

但这些对象还没有完全使用同一套样式对象语法、控件规划和阅读顺序。
```

当前项目已经有不少可复用资产：

- `StyleManagementBlock`：统一承载摘要、来源、规则、差异、预览、编辑区、回执区。
- `StyleObjectProjection`：统一描述一个样式对象需要呈现的事实。
- `style_object_projection_builders.py`：开始把模板、场景、执行的投影组装从页面层下沉。
- `StyleSourceCompactRow`：统一说明模板基线和分区样式来源。
- `StyleRuleControlDeck`：承载场景分区样式的开关、差异和批量恢复。
- `StylePresentationEnvelope`：统一预览和回执的语义外壳。
- `StyleControlSurface` / `ParagraphStyleEditor`：统一字体、字号、缩进、行距、段距等字段控件。

所以“不够好”的根因不是没有复用，而是复用层级还不一致：

```text
字段控件层已经复用。
样式管理外壳已经复用。
来源和回执投影正在复用。
但策略控件、预览外壳、页面板块顺序、冗余文案分层还没有完成同构。
```

## 2. 和模板管理比对后的真实差距

### 2.1 模板管理是基线中心

模板管理最清晰的一点是：用户知道自己正在编辑“标准格式”。它的天然对象是：

```text
模板基线
-> 影响全文
-> 编辑字段
-> 预览效果
```

当前已经打通：

- `StyleDetail` 使用 `StyleManagementBlock(mode="template_baseline_edit")`。
- 正文排版通过 `build_template_body_style_projection(...)` 进入统一投影。
- 字段编辑通过 `StyleControlSurface -> ParagraphStyleEditor` 复用。

仍然不足：

- `template_baseline_edit` 的 content plan 声明有 `source/scope`，但页面没有放入真实的 `source_slot`；主要仍靠 `owner_state` 展示来源和影响。
- 正文详情页没有同块内轻量预览，用户改行距、缩进后仍缺少“就地看效果”的反馈。
- `StyleDetail` 仍保留 `_font_cn`、`_line_value` 等内部字段别名，后续重排字段区时页面层仍可能被具体控件拖住。

### 2.2 场景分区样式是覆盖中心

场景分区样式不应该照抄模板管理，因为它不是基线，而是“在模板之上的局部覆盖”。它的对象应该是：

```text
分区样式
-> 跟随哪个模板
-> 是否启用独立样式
-> 和模板差在哪里
-> 当前有效样式长什么样
```

当前已经打通：

- `_StyleRulesDetail` 通过 `build_scene_section_style_projection(...)` 把当前分区交给 `StyleManagementBlock`。
- `SceneStyleRulesBlock -> SceneStyleOverrideSection -> StyleManagementBlock` 已经形成对象边界。
- 独立样式关闭时，编辑区可以折叠，避免用户误以为能编辑模板跟随态。

仍然不足：

- `StyleRuleControlDeck` 名义上是共享控件，但语义仍强绑定场景：`独立样式`、`全部跟随模板`、`撤销恢复` 等文字写在 deck 内部。
- `SceneStyleRulesBlock` 和 `SceneStyleOverrideSection` 仍暴露大量内部控件属性，例如 `toggles`、`rows`、`comparison_strip`、`editor`、`unit_labels`。
- 页面仍能绕过样式对象，直接摸到内部控件。这会削弱后续“和模板管理高度复用”的边界。

### 2.3 执行前复核正在接近同一对象语法

本轮已经把执行前复核接入了统一样式对象：

```text
QuickExecutionDetail
-> build_execution_prereview_style_projection(...)
-> StyleObjectProjection(source + difference)
-> StyleManagementBlock.apply_style_object_projection(...)
```

这是正确方向，因为执行前不应该自己调用：

- `build_style_source_projection(...)`
- `build_style_difference_summary_projection(...)`
- `_style_source_row.apply_projection(...)`
- `_style_difference_slot.apply_projection(...)`

现在页面层只知道“我要展示执行前复核样式对象”，不再知道 source row 和 difference slot 的拼装细节。

仍然不足：

- `StyleObjectProjection.source` 目前通过 `StyleManagementBlock._apply_slot_projection(...)` 投递到 source slot；如果 source slot 是容器，就递归找第一个 `apply_projection` 子控件。这是兼容过渡，不是最终理想契约。
- 执行前复核仍没有预览，只能说明“会使用什么”和“哪些分区不同”，不能让用户就地确认视觉效果。
- 执行前复核的入口仍夹在运行设置里，信息架构上还需要明确它是“样式复核”，不是“场景参数说明”。

### 2.4 执行后回执已经有形，但还没有成为同一张结果卡

当前执行后通过：

```text
build_execution_style_projection(...)
-> StyleObjectProjection(receipt + difference)
-> StyleManagementBlock(mode="execution_receipt_review")
```

这说明执行结果已经能回答“本次实际用了什么样式”。但它还缺两个闭环：

1. 执行前看到的 source/difference 与执行后回执之间，应使用同一套字段名和摘要顺序。
2. 回执不应只是一行结果，还应该能对齐执行前的差异摘要，让用户知道“预期和实际有没有偏离”。

## 3. 应收束成一套对象语法

后续不要再以页面为中心设计控件，而应该以样式对象为中心。

统一对象结构建议如下：

| 字段 | 含义 | 模板管理 | 场景分区 | 执行前 | 执行后 |
| --- | --- | --- | --- | --- | --- |
| `object` | 当前样式对象是谁 | 正文排版 | 某个分区 | 执行前复核 | 样式回执 |
| `source` | 来源是谁 | 模板基线 | 模板 + 分区覆盖 | 本次使用来源 | 实际使用来源 |
| `scope` | 影响哪里 | 全文正文 | 当前分区 | 本次执行 | 本次结果 |
| `policy` | 能否修改、如何生效 | 可编辑 | 跟随/独立 | 只读 | 只读 |
| `summary` | 用户先看懂的摘要 | 字体/缩进/行距 | 当前有效样式 | 使用策略 | 执行事实 |
| `difference` | 与基线差异 | 无或可选 | 有 | 有 | 有 |
| `fields` | 可编辑字段 | 有 | 条件有 | 无 | 无 |
| `preview` | 效果预览 | 应有 | 有 | 可选但建议有 | 可选 |
| `receipt` | 运行事实 | 无 | 无 | 无 | 有 |

这意味着模板管理、场景样式、执行前后不应该各自定义控件顺序，而是选择同一个 `StyleManagementBlock` mode 下的板块组合。

## 4. 建议的统一阅读顺序

所有样式对象都应遵守同一阅读顺序：

```text
1. 对象标题和动作
2. 来源与影响范围
3. 当前状态摘要
4. 策略控件
5. 差异摘要
6. 字段编辑
7. 样式预览
8. 执行回执
```

不同 mode 只决定哪些板块显示：

| mode | 来源 | 摘要 | 策略 | 差异 | 编辑 | 预览 | 回执 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `template_baseline_edit` | 有 | 有 | 无 | 无 | 有 | 应补 | 无 |
| `scene_section_rules` | 有 | 有 | 有 | 有 | 条件显示 | 有 | 无 |
| `template_overview_preview` | 可选 | 简短 | 无 | 无 | 无 | 有 | 无 |
| `execution_prereview` | 有 | 有 | 无 | 有 | 无 | 应补轻量 | 无 |
| `execution_receipt_review` | 有或回执内含 | 有 | 无 | 有 | 无 | 可选 | 有 |
| `readonly_review` | 有 | 有 | 无 | 可选 | 无 | 有 | 可选 |

这套顺序能保证用户每次都按同一条逻辑读：

```text
我在看谁 -> 它从哪里来 -> 影响哪里 -> 能不能改 -> 和基线差什么 -> 改什么 -> 长什么样 -> 实际用了什么
```

## 5. 内容板块重新规划

### 5.1 模板管理

模板管理只保留三类主板块：

```text
当前模板
样式基线
参数详情
```

其中“样式基线”应统一为：

```text
StyleManagementBlock(template_baseline_edit)
-> source slot: 模板基线
-> summary: 字体 / 缩进 / 行距
-> editor: 字段编辑
-> preview: 正文轻量预览
```

页面级 `TemplateStylePreview` 仍可保留在概览，但它应成为同一 preview envelope 的页面级 renderer，而不是另一套解释系统。

### 5.2 场景规划

场景规划不应继续把所有工程事实堆在首屏。建议分成：

```text
运行设定：场景预设、关联模板、编号策略
处理范围：处理哪些分区、启用哪些能力
样式复核：模板来源、分区独立样式、差异摘要、轻量预览
输出设置：交付格式、输出路径、命名策略
诊断详情：工程状态、计数、样本覆盖、Schema、插件信息
```

首屏最多展示前四类。诊断详情默认不进入主阅读层。

截图中的这类内容不应作为主卡片正文出现：

- `custom_basic`
- `quick_formatting`
- `Green/L5`
- `template 13 / scene 37 / material 6 / output 17`
- `preserve_layout`
- `Schema`
- `plugin`

这些可以保留为诊断属性、hover 详情、报告字段或开发者检查项，但不应该抢占用户理解路径。

### 5.3 执行前复核

执行前复核应成为工作台里的独立样式对象，而不是隐藏在运行配置中：

```text
样式复核
-> 本次按哪个模板
-> 哪些分区单独调整
-> 和模板差在哪里
-> 是否需要去模板/场景里调整
```

它不需要暴露字段编辑，不需要解释所有工程判断，也不应该把样式来源写成长段说明。

建议文案形态：

```text
样式来源  分区已调整
模板：默认格式，可在模板管理调整
分区：1 个分区独立设置
```

下方只显示差异摘要和跳转动作。

### 5.4 执行后回执

执行后回执只回答：

```text
本次实际用了什么。
是否与执行前复核一致。
输出里哪些分区用了独立样式。
```

不要在回执中重新解释模板管理功能，也不要重复展示执行前已经确认过的长说明。

## 6. 必要的新抽象

### 6.1 `StylePolicyControlDeck`

`StyleRuleControlDeck` 应继续下沉为通用策略控制区：

```text
StylePolicyControlDeck
-> policy_state: template_baseline / follow_template / independent / readonly / receipt
-> actions: restore_current / restore_all / undo_restore_all / navigate
-> difference_slot
```

场景分区只是它的一个配置：

```text
policy_state = independent_toggle_by_section
actions = restore_current + restore_all + undo_restore_all
```

这样模板管理、场景规划、执行复核可以共享同一个“策略区”外壳，而不是场景侧独占。

### 6.2 `StylePreviewSurface`

现在有 `TemplateStylePreview` 和 `StylePreview`。它们不必合并为一个 renderer，但需要统一外壳：

```text
StylePreviewSurface
-> envelope
-> renderer_kind: template_page / paragraph / execution_preview
-> renderer_widget
```

目标不是让所有预览长得完全一样，而是让它们拥有相同的标题、来源、状态、空态和尺寸规则。

### 6.3 `StyleSourceSlot`

当前 `StyleObjectProjection.source` 能投递到 source slot，但 block 需要扫描子控件寻找 `apply_projection`。这说明 source slot 还不是强契约。

建议新增一个明确外壳：

```text
StyleSourceSlot
-> apply_projection(...)
-> 内部承载 StyleSourceCompactRow 或其他来源 renderer
```

这样 `StyleManagementBlock` 不需要知道 source slot 内部结构，也不需要递归找子控件。

## 7. 删除冗余文本的规则

后续删文案不要只按“字数少”来删，应按信息层级删。

主阅读层只保留：

- 当前对象。
- 当前状态。
- 用户能做什么。
- 会影响哪里。
- 是否需要处理。

移出主阅读层：

- registry 数量。
- schema 名称。
- plugin 标记。
- internal key。
- L5 / Green 这类成熟度工程标记。
- `template 13 / scene 37 / material 6 / output 17` 这类总账计数。
- 风险策略的长解释。

保留位置：

| 信息 | 推荐位置 |
| --- | --- |
| 工程 key | tooltip 或调试属性 |
| 计数总账 | 诊断详情 / 报告 |
| 风险依据 | 折叠详情 |
| 插件/Schema | 高级诊断 |
| 原始字段路径 | 问题详情或开发者模式 |

## 8. 后续落地优先级

### P0：让所有样式入口只消费 `StyleObjectProjection`

必须继续守住：

```text
页面层只选对象和调用 builder。
builder 组装 source / summary / difference / preview / receipt。
StyleManagementBlock 统一应用投影。
具体 slot 只负责渲染自己的 projection。
```

新增守门建议：

- 模板正文、场景分区、执行前、执行后都必须从 `style_object_projection_builders.py` 取 projection。
- 页面层不得直接调用 `StyleSourceCompactRow.apply_projection(...)`。
- 页面层不得直接调用 `StyleDifferenceSummarySlot.apply_projection(...)`。
- 页面层不得直接拼 `StyleObjectProjection(...)`，除非它就是 builder。

### P0：补齐模板正文和执行前的轻量预览

这一步会直接改善用户感受：

- 模板正文详情中，字段编辑下方看到正文段落预览。
- 执行前复核中，看到本次有效样式的轻量预览。
- 场景分区继续显示同规格段落预览。

### P0：抽象 `StylePolicyControlDeck`

把 `StyleRuleControlDeck` 的场景文案下沉到 projection/spec：

- 按钮文字由 policy projection 提供。
- 是否允许恢复由 policy projection 提供。
- 差异 slot 继续复用，但不绑定“分区样式”语义。

### P1：收紧内部控件暴露

逐步减少这些外部访问：

- `SceneStyleRulesBlock.toggles`
- `SceneStyleRulesBlock.rows`
- `SceneStyleRulesBlock.comparison_strip`
- `SceneStyleRulesBlock.editor`
- `StyleDetail._font_cn`
- `StyleDetail._line_value`

替代入口：

- `apply_style_object_projection(...)`
- `set_current_variant(...)`
- `navigation_widget_for_field(...)`
- `editor_widget_for_field(...)`
- `focus_navigation_field(...)`

### P1：把工程信息移出首屏

场景概览和执行前复核应新增“诊断详情”承载工程事实。主层只保留用户判断所需文字。

## 10. 下一步建议

下一轮最值得做的不是继续改一句句说明文字，而是先补两个抽象：

```text
StyleSourceSlot
StylePreviewSurface
```

然后再抽象：

```text
StylePolicyControlDeck
```

只要这三层落地，模板管理、场景分区、执行前复核、执行后回执就能真正形成同一套对象语言。届时再删冗余文本，效果会明显得多，因为页面结构本身已经开始说人话。
