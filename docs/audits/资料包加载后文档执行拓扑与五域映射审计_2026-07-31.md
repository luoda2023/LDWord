# 资料包加载后文档执行拓扑与五域映射审计

> 日期：2026-07-31
> 状态：分析完成，尚未修改业务代码
> 范围：资料包加载、内置包编辑生命周期、字段增删改、文档执行拓扑、单条/多条资料记录、五域 Token 总览、图片映射、工作台布局

## 1. 结论

当前截图中的异常不是单一的样式问题，而是三层状态被错误地连在了一起：

1. Assets 载入一个只有一条记录的资料包后，会向 `PanelBridge` 发布包含一个 `profile_id` 的 `MaterialBatchSelection`。
2. 文档执行拓扑把“存在任意资料记录”直接解释为 `records`，因此一条普通资料记录也会切换到“按资料生成”的批次详情。
3. 批次详情嵌入统一文档执行页时只保留来源摘要卡，但仍保留内部弹性占位；外层公共方案、输出和执行控件因此被推到很远的位置，形成大面积无意义空白。

与此同时，资料包页面的“资料 Token”仍是字段专用表，图片页面又存在 Token 定义、图片规则和真实图片资源身份不一致的问题。工作台当前看到的“已准备 1 份批次资料”既没有正确表达一条资料记录的语义，也没有给用户展示这条记录内部真实的字段、时间、文件、图片和附件映射。

当前合理的产品定义应为：

- **资料包**是资料容器，不等于批次。
- **资料记录**是一次生成可以使用的数据单元。
- 一条资料记录应被视为“当前资料”，不应仅因为被装在资料包中就触发批次界面。
- 是否属于单份、多文档、按资料批次或需要映射，应由“输入文档数量 × 资料记录数量 × 源文档要求”共同推导。
- 页面只静默识别无歧义关系；遇到多文档与多记录时，不猜测配对关系。

## 2. 当前实现事实

### 2.1 单条资料记录被强制解释为批次

`resolve_document_execution_topology()` 当前先判断：

```text
文档数 > 1 且资料记录数 > 0
    -> mapping_required

否则只要资料记录数 > 0
    -> records
```

这导致以下两个本来无歧义的组合也被错误分类：

- 1 份文档 × 1 条资料记录，被分类为 `records`，而不是单份执行。
- 多份文档 × 1 条资料记录，被分类为 `mapping_required`，而不是多文档共享同一条资料。

现有测试 `test_single_record_is_still_a_record_execution_with_or_without_source` 还明确固化了“单条记录也是批次执行”的旧假设。这说明当前截图不是偶发渲染错误，而是代码和测试共同维护的一次产品基线偏移。

### 2.2 截图中的卡片来自批次详情

“已准备 1 份批次资料 / 默认测试记录”由 `BatchGenerationSourceArea` 生成。

它对所有大于零的记录数量都使用“批次资料”文案，没有区分：

- 当前资料：1 条；
- 批次资料：多条。

因此即便拓扑计算仍暂时进入 `records`，该文案也无法正确解释当前状态。

### 2.3 大面积空白来自嵌套布局

统一文档执行页将以下三种详情放进一个 `QStackedWidget`：

- 单份详情；
- 多文件详情；
- 按资料记录详情。

按资料记录详情以 `include_shared_chrome=False` 嵌入，因此只创建资料来源摘要，不创建自己的方案、输出和执行卡；这些公共卡片由外层统一页面提供。

但是 `BatchGenerationDetail.ensure_context_built()` 无论是否嵌入，都会执行：

```python
self._layout.addStretch(1)
```

多文件详情和单份详情也存在同类弹性占位。`QStackedWidget` 又容易按照较高页面的尺寸提示保留高度，所以当前按资料记录页只有顶部一张摘要卡，剩余高度全部成为空白，外层输出卡和执行区被推到页面下方。

这不是通过调整边距或给卡片设置固定高度可以根治的问题。正确边界应是：

- 独立页面可以在末尾吸收剩余空间；
- 嵌入统一执行页的子详情只报告真实内容高度；
- 堆叠容器根据当前页更新尺寸提示，而不是长期保留最高历史页面的高度。

## 3. 合理的文档执行拓扑

### 3.1 基本数量矩阵

在没有显式一对一映射表时，推荐采用以下规则：

| 文档数 D | 资料记录数 R | 合理拓扑 | 输出语义 |
|---:|---:|---|---|
| 0 | 0 | 空状态 | 等待输入 |
| 1 | 0 | 单份执行 | 1 份文档使用当前非批次资料 |
| N > 1 | 0 | 多文档执行 | N 份文档共享当前资料 |
| 0 | 1 | 单份资料执行 | 是否可执行由方案是否需要底稿决定 |
| 0 | N > 1 | 按资料生成 | 每条资料生成一份，是否需要底稿由方案决定 |
| 1 | 1 | 单份执行 | 1 份文档 × 当前资料 |
| 1 | N > 1 | 按资料生成 | 1 份共用底稿 × N 条资料 |
| N > 1 | 1 | 多文档执行 | N 份文档共享 1 条资料 |
| N > 1 | M > 1 | 需要映射 | 除非已有显式映射，否则禁止静默猜测 |

### 3.2 “单份”和“批次”的产品边界

是否属于批次不能只看 `MaterialBatchSelection` 是否非空。

推荐定义：

```text
record_count == 1
    -> current material record

record_count > 1
    -> material record batch
```

`MaterialBatchSelection` 可以继续作为跨页面传输结构，但界面和拓扑不能把结构名称当成产品语义。否则任何资料包即使只有一条记录，也会污染为“批量生成”。

### 3.3 静默识别的边界

允许静默识别：

- 1 文档 × 1 记录；
- N 文档 × 1 记录；
- 1 文档 × N 记录；
- 无底稿方案 × N 记录。

必须停止并要求建立映射：

- N 文档 × M 记录，且 N、M 均大于 1；
- 已存在显式映射，但有重复目标、孤立输入或未覆盖记录；
- 资料记录声明了不同模板或不同执行路线，不能共享当前绑定。

## 4. 合理的统一页面结构

加载资料包后，文档执行页不应替换成一张孤立的“批次资料”卡。建议保持稳定结构：

```text
文档输入
  -> 当前资料 / 资料记录摘要
  -> 处理方案与模板
  -> 输出目录
  -> 执行与状态
```

资料摘要根据记录数量改变语义：

- 0 条：未选择资料；
- 1 条：当前资料 · 默认测试记录；
- 多条：已选择 N 条资料记录。

单条资料摘要中应继续提供紧凑的五域映射预览，而不是只显示记录名称。多条资料时展示：

- 资料包名称；
- 已选择记录数；
- 完整/缺失/冲突数量；
- 展开后查看各记录映射状态。

公共方案、输出和执行卡必须紧邻当前模式的真实内容。不得使用大面积空白维持截图等高。

## 5. 五域映射总览问题

### 5.1 当前“资料 Token”仍是字段专用投影

Assets 的 `_refresh_overview_material_preview()` 当前只遍历固定字段和自由字段，并限制为前 8 行。传入的综合预览行没有参与构建，文件、图片、附件没有进入表格。

时间也不完整：只有恰好进入字段清单的时间字段可能显示，由时间流生成但未声明为普通字段的输出可能被遗漏。

### 5.2 统一映射总览的来源

总览不能只取已经成功绑定的交集，应使用以下并集：

```text
Token 定义 ∪ 领域规则 ∪ 资源绑定 ∪ 实际资源
```

每一行应包含：

```text
namespace
exact_token
resource_id
label
preview
status
diagnostics
owner_section
```

五个领域的权威来源如下：

| 领域 | Token 示例 | 权威声明 | 预览 |
|---|---|---|---|
| 字段 | `{{@text:project_name}}` | 字段清单、作用域、字段函数 | 当前解析值 |
| 时间 | `{{@time:issue_date}}` | 时间计划输入与输出 | 解析日期、计划异常 |
| 文件 | `{{@file:project_brief}}` | 内容插入规则 | 源文件名、编译状态 |
| 图片 | `{{@img:product_image}}` | 图片 Token 与插入规则 | 缩略图、文件名、数量 |
| 附件 | `{{@attach:validation_notes}}` | 附件角色定义 | 文件名、数量、处理方式 |

总览必须保留并显示异常行：

- 已声明 Token，但未绑定资源；
- 有资源，但没有 Token；
- Token 与规则角色不一致；
- 绑定存在，但源文件缺失；
- 同一角色有多个来源；
- 时间输出无法计算。

总览保持只读，点击行只负责定位到对应的领域编辑页。字段、时间、文件、图片、附件页面继续作为各自唯一编辑入口。

## 6. 默认图片映射断裂

默认测试资料包当前包含：

```text
asset_token_specs = []
asset_items.role = product_image
image_material_rules.source_role = product_image
image_material_rules.anchor_token = {{@img:product_image}}
```

图片页面发现 `asset_token_specs` 为空后，回退到公共场景槽位：

```text
role = logo
token = {{@img:LOGO1}}
```

图片路径查找按角色精确匹配，因此 `product_image` 不能显示在 `logo` 行中，界面表现为“未选”。

合理修复：

1. 默认测试资料包补充显式 `AssetTokenSpec`：
   - `token_id = product_image`
   - `token = {{@img:product_image}}`
   - `label = 默认产品图片`
   - `cardinality = single`
2. 保留 `asset_items` 为该角色的唯一资源来源。
3. 不再为同一角色额外添加 `asset_bindings`，否则会触发双来源冲突。
4. 当资料包已有图片规则或图片资源时，图片编辑器不得无条件回退到场景公共 `LOGO1`。
5. 对历史包只做纯推导和冲突报告；身份不明确时不静默改名、不自动保存。

## 7. 分阶段执行方案

### 阶段 A：先建立失败基线

在修改实现前增加或调整测试，明确当前错误：

1. 一文档 × 一记录应为单份执行。
2. 多文档 × 一记录应为多文档共享资料。
3. 一文档 × 多记录应为按资料生成。
4. 多文档 × 多记录且无映射时才进入 `mapping_required`。
5. 单条资料记录不得显示“批次资料”。
6. 嵌入详情的真实高度不得被内部 stretch 扩大。
7. 默认测试资料包图片页应显示 `{{@img:product_image}}` 及缩略图。
8. 五域总览应包含 `text/time/file/img/attach`。

现有 `test_single_record_is_still_a_record_execution_with_or_without_source` 需要废弃或改写，因为它维护的是本次确认要纠正的旧产品定义。

### 阶段 B：重构拓扑解析

将 `resolve_document_execution_topology()` 改为显式数量矩阵。

保持：

- 拓扑继续由状态推导，不恢复手动“单份/多文件/按资料”模式切换器；
- 多对多关系继续失败关闭；
- `source_requirement` 继续决定无底稿时是否阻断。

改变：

- 一条资料记录不再自动进入 `records`；
- 多文档与一条记录不再要求映射；
- 输出数量由选定拓扑统一计算。

### 阶段 C：修复嵌入布局

1. `include_shared_chrome=False` 时不添加详情内部末尾 stretch。
2. 复查单份、多文件、按资料三个嵌入详情的尺寸策略。
3. 让堆叠容器根据当前页刷新 `sizeHint`，或使用只按当前页计算高度的自适应堆叠容器。
4. 删除为了等高而产生的空白，不采用固定高度补丁。
5. 增加真实窗口尺寸与 DPI 下的几何测试。

### 阶段 D：修复图片身份

1. 为默认包补充显式图片 Token。
2. 新增图片 Token、规则、资源的纯校验/归并投影。
3. 优先级：
   - 显式 `asset_token_specs`；
   - 图片规则；
   - 已绑定图片角色；
   - 仅在前三者均不存在时使用场景默认槽位。
4. 冲突只报告，不自动猜测。
5. 打开资料包不得仅因投影归并而产生脏状态。

### 阶段 E：建设五域统一投影

新增纯 `MaterialMappingProjection`，不读取 Qt 控件、不写回资料包。

Assets 完整总览和工作台紧凑预览都从该投影派生，避免两套逻辑继续漂移：

- Assets：显示完整映射、异常和定位入口；
- Workbench：显示当前执行相关的紧凑映射和数量；
- 执行冻结：继续使用 `MaterialExecutionContext` / 冻结快照，不把 UI 预览态当作执行输入。

## 8. 验收标准

### 8.1 加载默认测试资料包

- 工作台显示“当前资料：默认测试记录”，不显示“已准备 1 份批次资料”。
- 页面不因一条记录切换成批次语义。
- 方案、输出、执行区紧随资料摘要，不出现大面积空白。
- 若尚未选择且方案要求 DOCX，执行区明确提示缺少源文档。

### 8.2 五域预览

至少能够看到：

- `{{@text:entity_name}}`
- `{{@time:issue_date}}`
- `{{@file:project_brief}}`
- `{{@img:product_image}}`
- `{{@attach:validation_notes}}`

图片行显示内置缩略图；文件和附件显示真实文件状态；未绑定项仍保留并显示明确状态。

### 8.3 拓扑

- 1 文档 × 1 记录：预计生成 1 份；
- N 文档 × 1 记录：预计生成 N 份；
- 1 文档 × N 记录：预计生成 N 份；
- N 文档 × M 记录：无显式映射时阻断；
- 无底稿方案 × N 记录：按资料生成 N 份；
- 要求底稿的方案 × N 记录但无文档：明确阻断。

### 8.4 稳定性

- 打开资料包不产生脏状态；
- 保存、关闭、重开后 Token、角色和文件身份一致；
- 切换资料包不残留上一包的图片或记录；
- 资料包完整总览与工作台紧凑预览对同一 Token 给出一致状态；
- 批次执行、失败隔离、取消和重试能力不因单记录拓扑修正而回退。

## 10. 内置资料包编辑生命周期审计

### 10.1 当前不是“只读”，而是半只读

资料包库层对内置包的约束是清楚的：

- `source_type == "builtin"`；
- 禁止覆盖保存；
- 禁止删除；
- 可以创建用户副本。

但编辑器层采用了另一套语义：

- 内置包的字段、时间、文件、图片和附件控件仍然可编辑；
- 编辑结果会进入当前内存中的资料包草稿；
- 分区“恢复”可以启用；
- 分区“保存”因为来源不可写而禁用；
- 直接调用保存会提示“内置资料包不能直接保存，请先创建副本”并返回失败。

所以它既不是严格只读，也不是完整的“编辑后保存副本”。用户可以做出修改，却没有与这次修改直接相连的完成动作。这会自然表现为“删除、修改、保存不正常”。

### 10.2 内置草稿会形成切换死路

当前资料包下拉切换流程是：

```text
发现当前包有未保存修改
  -> 自动调用 save_current_package()
  -> 内置包拒绝保存
  -> 下拉恢复到原位置
```

新建资料包前也采用同类门禁。因此，一旦内置包产生脏草稿，用户不能直接切换或新建；只能先手工恢复所有修改，或主动找到“创建副本”。界面没有把这一规则预先说明，也没有在切换时提供“保存为副本 / 放弃 / 取消”三选一。

关闭程序虽然存在“保存 / 放弃 / 取消”对话框，但选择“保存”仍会被内置包只读策略拒绝。这个对话框对内置包给出了实际上无法完成的动作。

### 10.3 已有“创建副本”能力，但没有接入保存生命周期

`_duplicate_archive()` 会取得当前编辑器快照并创建用户资料包，因此它事实上能够保存一份包含当前草稿的副本。

问题不在于缺少底层能力，而在于能力彼此割裂：

- 分区保存只会尝试原位保存；
- 内置包原位保存必然失败；
- 创建副本是资料包顶层的另一枚按钮；
- 切换与关闭流程不知道“保存副本”是一种合法提交；
- 成功创建副本后才会转成可写用户身份。

合理修订不是放开内置目录写权限，而是把“内置草稿保存”正式定义为一次 `fork-and-adopt` 事务：

```text
内置来源 + 当前草稿
  -> 选择副本名称
  -> 在用户资料包目录原子创建
  -> 校验创建结果
  -> 当前编辑会话切换到用户副本身份
  -> 更新持久化基线
  -> 清除脏状态
  -> 原内置文件保持不变
```

这与模板编辑页已经采用的“内置模板保存时创建用户副本”模式一致，不需要为资料包发明第二套相反的产品规则。

## 11. 字段增删改链路中的深层问题

### 11.1 “读取当前资料包”会反向修改模型

`current_archive()` 不是纯读取。它首先调用 `_persist_current_profile_editor()`，把 Qt 控件中的值采集、规范化并写回 `_profiles`，然后才构建快照。

下列看似只读的动作都会间接调用它：

- 判断是否有未保存修改；
- 刷新保存/恢复按钮；
- 生成批次选择；
- 计算输出预览；
- 构建执行上下文；
- 捕获持久化基线。

结果是“查询状态”本身可能改变状态。刷新按钮状态、切换页面或更新预览，都可能成为隐式提交点。后续很难判断某个字段修改究竟停留在控件、已经进入草稿模型、已经发布给工作台，还是已经写入文件。

顶层约束应改为：

```text
Query 不得写状态
Command 才能写草稿
Save 才能写资料包文件
Apply/Freeze 才能写执行快照
```

### 11.2 新增字段存在“不可见丢失”窗口

手工新增字段时，界面先创建 `__material_field_draft__...` 临时键并显示输入行。持久化采集会主动过滤这种临时键。

这意味着用户只点击“新增字段”但尚未提交合法 Token 时：

- 界面已经出现新行；
- 资料包脏状态可能仍为否；
- 切换资料包可能不提示；
- 临时行会直接消失。

未完成的编辑不能假装不存在。合理策略有两种：

1. 临时字段属于编辑会话状态，切换时提示“有未完成字段”；或
2. 离开输入行时，空草稿自动取消，并明确不计入资料包修改。

不能继续由持久化投影静默过滤，然后让用户自己推断为什么丢失。

### 11.3 “名称”和“Token 代码”语义混用

目前存在两类不同修改：

- 正式字段名称编辑主要写入 `field_aliases`，Token 身份不变；
- 手工字段代码编辑会调用 `rename_material_field()`，改变稳定字段键。

两者在界面上都容易被理解为“改字段名”，但风险完全不同：

- 修改显示名称是低风险展示变更；
- 修改 Token 代码是一次 Schema 迁移，会影响文档占位符、函数依赖、时间流和输出规则。

界面与领域模型必须明确分成：

```text
显示名称：可直接编辑
Token 代码：高级操作，需校验引用并确认影响
```

### 11.4 删除与撤销只覆盖局部

正式字段删除会清理字段清单中的值、作用域、声明、来源、函数和别名，并保存一个“最后删除字段”的内存快照；但仍有以下限制：

- 只有最后一次正式字段删除可撤销；
- 手工字段删除没有同等级撤销；
- 切换记录后撤销信息会丢弃；
- 时间计划引用只做阻断，没有统一依赖报告；
- Token 代码可能还被模板、输出命名或其他扩展规则引用，当前字段清理器并不拥有全局依赖图；
- 删除并未统一经过现有的 `publish_or_rollback_material_mutation()` 边界。

字段删除应是领域命令，不应是若干字典 `pop()` 加一个 UI 专用的最后删除缓存。建议统一为：

```text
DeleteFieldCommand
  -> 查询 MaterialDependencyIndex
  -> 无引用：进入草稿删除
  -> 可安全迁移：展示影响并原子重定向
  -> 不可安全迁移：阻断并定位引用
  -> 写入会话级 Undo Stack
```

### 11.5 分区“保存”的动作范围与按钮位置不一致

每个分区卡片都放有“恢复 / 保存”：

- “恢复”只恢复当前分区；
- “保存”实际保存整个资料包文件，包括其他分区的未保存修改。

因此用户在“字段资料”中点击保存，可能同时保存尚未确认的时间、图片或附件修改。按钮看起来是分区动作，实际却是全局提交。

最终产品基线采用既有卡片级交互：

- 每个资料编辑卡片右上角保留“恢复 / 保存”；
- “恢复”只恢复当前分区；
- “保存”通过统一事务提交资料包；用户包原位保存，内置包创建用户副本；
- 只有当前分区为脏且不存在冲突/未完成字段时，该分区的两个按钮才启用；
- 资料包顶层操作区只负责新建、创建副本、重命名、打开文件夹和删除，不混入保存或放弃修改。

这里以既有页面的一致性为优先。资料包原子提交的技术事实由保存事务和提示承担，不再通过改变按钮位置建立新的交互体系。

### 11.6 记录结构变化无法由现有分区恢复完整撤销

新增、复制或删除资料记录会改变 `profiles` 列表长度。当前分区投影会因此把多个分区都判定为脏，但 `restore_section()` 只遍历当前仍存在的记录并复制该分区字段：

- 新增的记录不会因恢复某个分区而被移除；
- 已删除的记录不会被恢复；
- 多个分区可能持续显示脏；
- 用户无法从分区按钮理解应该恢复哪一项。

记录新增、复制、删除属于资料包结构命令，必须由全局撤销/放弃处理，不应伪装成五个分区各自的内容修改。

## 12. 当前存在的四套状态及其漂移

目前实际同时存在：

| 状态层 | 当前载体 | 主要更新方式 | 风险 |
|---|---|---|---|
| 控件缓冲 | Qt 输入控件及若干 presenter 字典 | 输入信号 | 不是完整资料包 |
| 编辑模型 | `_profiles` 与当前 presenter 状态 | 显式修改 + `current_archive()` 隐式采集 | 查询会写入 |
| 预览状态 | `MaterialPreviewSnapshot` | 每次摘要刷新发布 | 会展示未保存草稿 |
| 执行状态 | `MaterialBatchSelection` + `MaterialExecutionContext` | 部分动作立即发布、部分模式 300ms 延迟发布、进入执行页时再次发布 | 与预览的更新时机不一致 |
| 磁盘基线 | `package.json` + `_persisted_snapshot` | 保存 | 内置包不可写 |

严格来说是“五层状态”，但前三层在当前实现中经常被当成同一层使用。

最危险的漂移路径是：

```text
字段输入
  -> 预览立刻显示新值
  -> 刷新保存状态时采集进 _profiles
  -> 公文模式下 300ms 后可能发布执行上下文
  -> 其他模式要到进入执行页才发布
  -> 内置包仍无法保存
```

所以同一份未保存修改可能：

- 已经出现在资料包总览；
- 已经出现在工作台紧凑预览；
- 在公文模式已经影响执行上下文；
- 在其他模式尚未影响执行上下文；
- 永远没有写入内置包磁盘。

这也解释了为什么加载资料包后，工作台卡片、记录数量和实际可执行内容容易互相对不上。

## 13. 顶层目标状态模型

### 13.1 三个权威对象

重构后只保留三个有明确边界的权威对象：

```text
LibrarySnapshot
  不可变来源；builtin 或 user 的已保存版本

MaterialEditSession
  baseline + draft + identity + dirty sections + diagnostics + undo stack

MaterialExecutionSnapshot
  用户显式应用或开始执行时冻结；运行期间不可被编辑页刷新覆盖
```

预览不是第四个权威状态。预览只是 `MaterialEditSession.draft` 的纯投影。

### 13.2 建议的编辑会话结构

```text
MaterialPackageEditSession
  source_entry
  source_policy            builtin_readonly | user_writable | unsaved_new
  baseline_archive
  draft_archive
  active_profile_id
  incomplete_edits
  dirty_sections
  validation_diagnostics
  undo_stack
  revision
```

核心不变量：

1. `baseline_archive` 和 `draft_archive` 永远不是同一个可变对象。
2. UI 查询、预览构建和脏状态计算不得修改 `draft_archive`。
3. 所有增删改都通过命令修改 `draft_archive`。
4. 执行页只接收冻结快照，不读取正在变化的 Qt 控件。
5. 内置来源永不原位写入。
6. 用户副本保存成功后才替换 `source_entry` 与 `baseline_archive`。

### 13.3 保存策略矩阵

| 来源策略 | 卡片入口 | 提交结果 |
|---|---|---|
| `builtin_readonly` | 保存 | 弹出副本命名，新建用户包、切换到副本、清除脏状态 |
| `user_writable` | 保存 | 原子覆盖当前用户包、刷新基线 |
| `unsaved_new` | 保存 | 创建用户包、采用新身份、刷新基线 |

切换资料包、切换工作模式和关闭程序统一使用同一决策服务：

| 状态 | 可选动作 |
|---|---|
| 无修改 | 直接继续 |
| 用户包有修改 | 保存 / 放弃 / 取消 |
| 内置包有修改 | 保存为副本 / 放弃 / 取消 |
| 有无效或未完成字段 | 返回修正 / 放弃未完成编辑 / 取消 |

## 14. 字段领域的重构定义

### 14.1 统一字段实体

字段不应继续由多个松散容器共同暗示。建议编辑会话内部使用统一投影：

```text
MaterialFieldDefinition
  key                 稳定 Token 标识
  display_name        用户显示名称
  namespace           text | time
  scope               fixed | floating
  value
  source
  function_spec
  aliases
  origin
```

保存时再与现有 `EntityProfile` 兼容结构互转。这样可以先重构编辑行为，不必在第一阶段立即破坏磁盘格式。

### 14.2 字段命令

至少需要：

- `AddField`
- `CommitFieldDraft`
- `ChangeFieldValue`
- `ChangeFieldDisplayName`
- `RenameFieldToken`
- `DeleteField`
- `RestoreDeletedField`
- `ChangeFieldScope`
- `ChangeFieldFunction`

每个命令返回：

```text
changed
dirty_sections
diagnostics
dependency_impact
undo_record
```

Qt presenter 只负责发命令和渲染结果，不再直接操作 `_manual_field_keys`、`_declared_field_keys`、`profile.fields` 等多份容器。

### 14.3 依赖索引

`MaterialDependencyIndex` 应覆盖：

- 字段函数输入；
- 时间计划输入与输出；
- 字段别名；
- 文档已扫描 Token；
- 输出目录命名变量；
- 批次映射键；
- 后续扩展的条件规则。

Token 改名和删除必须查询同一份索引。能安全重定向时一次完成；不能时给出明确引用位置，不做静默清理。

## 15. 顶层重构与修订方案

以下顺序替代“先补某个按钮”的局部修复顺序。

### Phase 0：冻结产品规则并建立失败测试

先补测试，不改 UI：

1. 内置包编辑后，“保存”必须创建用户副本且原文件字节不变。
2. 内置包有修改时可以切换：保存为副本 / 放弃 / 取消均有确定结果。
3. 关闭流程不再提供必然失败的“保存”动作。
4. 空字段草稿不会静默丢失。
5. 查询当前包、刷新预览、刷新按钮状态不改变编辑模型。
6. 字段删除、改 Token 在依赖存在时给出稳定结果。
7. 记录新增/删除可由全局放弃完整恢复。
8. 预览草稿不自动替换已冻结执行快照。

### Phase 1：引入 `MaterialPackageEditSession`

先包住现有 `EntityArchive`，不立即更改磁盘 Schema：

- 加载资料包时建立 baseline 与 draft；
- 当前包身份、当前路径、持久化基线统一收归 session；
- `has_unsaved_changes()` 只比较 session；
- 禁止 `current_archive()` 和其他 query 从控件采集；
- 把旧 `_persist_current_profile_editor()` 收敛为显式的表单提交命令，随后逐步删除。

这是最关键的架构切口。没有这一层，后续保存副本、五域预览和工作台执行仍会继续互相污染。

### Phase 2：统一保存、切换、关闭事务

- 实现 `SaveMaterialPackageCommand`；
- 根据 source policy 自动选择原位保存或保存副本；
- 成功发布后原子采用新身份和新基线；
- 切换、关闭、换模式全部复用同一 pending-change 决策服务；
- 保留现有 CAS、文件快照和失败恢复机制，不降低并发写入安全性。

当前 `MaterialChangeTransactionCoordinator` 中对内置来源的直接拒绝，需要改为能够准备并记录“创建用户副本”的发布目标，而不是绕过事务另调复制按钮。

### Phase 3：重构字段命令与撤销

- 建立统一字段投影和字段命令；
- 区分显示名称与 Token 代码；
- 增加依赖索引；
- 所有字段增删改进入 session undo stack；
- 移除仅支持一次的 `_last_removed_official_field`；
- 手工字段与正式字段使用同一删除/恢复语义；
- 未完成字段成为明确会话状态。

### Phase 4：分离草稿预览与执行冻结

- `MaterialPreviewSnapshot` 继续允许实时更新，但明确标记 `draft_revision`；
- 工作台预览显示“未保存修改”状态；
- `MaterialExecutionSnapshot` 只在“应用到执行 / 进入文档执行 / 开始生成”时冻结；
- `MaterialBatchSelection` 与 `MaterialExecutionContext` 从同一个冻结动作成对发布；
- 删除按不同模式决定是否 300ms 自动发布执行上下文的分叉逻辑。

### Phase 5：接回拓扑与五域统一投影

在编辑会话和执行快照稳定后，再实施本文件第 3～7 章：

- 修复单记录/多记录拓扑；
- 修复嵌入页面空白；
- 补全默认图片 Token；
- 建立五域 `MaterialMappingProjection`；
- Assets 总览和工作台紧凑预览共用同一纯投影。

如果先改工作台卡片而不先稳定资料包会话，工作台仍会不断接收到来源不明、提交程度不一的状态。

### Phase 6：迁移与清理

- 保持现有 `package.json` 可读；
- 对旧包只在内存中规范化，保存用户副本时升级；
- 删除 presenter 中重复的字段容器和隐式 harvest；
- 清理旧测试中“单记录必然是批次”“内置包只能保存失败”等错误契约；
- 增加端到端的打开、编辑、保存副本、重开、执行一致性测试。

## 16. 风险分级

### P0：必须先修

- 内置包可编辑但无法完成保存；
- 脏内置包阻断切换和新建；
- query 隐式写入编辑模型；
- 预览与执行发布时机不一致；
- 单条记录被错误解释为批次。

### P1：紧随其后

- 字段删除/改名缺少统一依赖图和事务；
- 分区保存实际提交整个资料包；
- 资料记录结构无法由分区恢复；
- 五域总览不完整；
- 默认图片 Token/角色/资源身份断裂。

### P2：体验完善

- 多级撤销历史；
- 未完成字段离开策略；
- 影响分析与定位交互；
- 工作台显示草稿版本、已应用版本和已保存版本差异。

## 17. 新增验收标准

### 17.1 内置包

- 打开默认测试资料包后初始为干净状态。
- 修改任意领域后，该领域卡片的“恢复 / 保存”启用；资料包管理行不增加保存或放弃按钮。
- 保存成功后当前来源变成用户包，原内置文件完全不变。
- 切换资料包和关闭程序都不会进入无法保存、也无法继续的死路。

### 17.2 字段

- 新增未完成字段不会无提示消失。
- 修改显示名称不改变 Token。
- 修改 Token 前能看到依赖影响。
- 删除字段能撤销，保存并重开后不会复活。
- 手工字段与正式字段遵守同一持久化和撤销规则。

### 17.3 状态一致性

- 刷新总览、切换分区、计算 dirty 不改变 draft。
- 草稿预览、已保存基线和已应用执行版本可明确区分。
- 一次显式应用同时发布匹配的 batch selection 与 execution context。
- 生成过程中继续编辑资料包不会改变已冻结任务输入。

## 19. 实施结果

本轮已经按 Phase 0～6 的顺序落地 P0 和主要 P1 修复。实现没有破坏现有 `package.json` 格式，也没有把工作台预览重新作为执行输入。

| Phase 0：失败基线 | 完成 | 已覆盖内置包保存副本、切换/关闭决策、查询纯度、全局放弃、草稿预览、单记录拓扑和五域 Token。 |
| Phase 1：编辑会话 | 完成核心边界 | 新增 `MaterialPackageEditSession`，统一保存身份、文件基线、草稿修订和来源策略；查询改用纯投影，不再通过 `current_archive()` 隐式写模型。 |

| Phase 4：预览与执行冻结 | 完成 | `MaterialPreviewSnapshot` 增加 `draft_revision`、`dirty` 和五域映射；取消字段输入后 300 ms 自动覆盖执行上下文；执行仍读取显式冻结的 Bridge 上下文。 |
| Phase 5：拓扑与五域 | 完成 | 单记录归为单份、多文档共享一条记录归为多文件、多文档 × 多记录才要求映射；字段、时间、文件、图片、附件共用统一预览投影。 |
| Phase 6：迁移与清理 | 完成兼容迁移，保留后续清理 | 旧资料包继续可读，默认测试包覆盖五域；旧 presenter 容器暂作为兼容层保留，未做高风险的一次性删除。 |

### 19.1 内置包和保存生命周期

- 通用模式默认稳定选择 `builtin/default_test_package`，不再依赖目录扫描顺序。
- 内置包允许形成可见草稿；当前分区的“保存”按钮通过命名对话框创建用户副本，不会尝试覆盖产品内置文件。
- 副本创建成功后，当前编辑会话原子切换到新的用户包身份和新基线；创建副本失败时清理半成品并恢复原状态。
- 切换、新建和关闭时提供“保存 / 放弃 / 取消”，全量放弃能力不作为资料包管理按钮常驻。
- 字段、文件、时间、图片和附件卡片统一显示“恢复 / 保存”；干净状态可见但禁用，修改对应分区后启用。
- 资料包管理行恢复为五个既有动作：新建、创建副本、重命名、打开文件夹和删除。

### 19.2 五域预览和默认测试包

默认测试资料包现在同时包含：

- 字段：`{{@text:project_no}}` 等示例字段；
- 时间：`{{@time:issue_date}}`，由默认时间流计算；
- 文件：`{{@file:project_brief}}`，带内置 Markdown 内容及编译产物；
- 图片：`{{@img:product_image}}`，Token 规格、图片规则和实际 PNG 使用同一角色；
- 附件：`{{@attach:validation_notes}}`，带内置文本附件。

Assets 和工作台预览都显示完整 Token（包含 `{{ }}` 和命名空间）、当前内容、缺失状态和领域类型。工作台最多展示 10 项时会优先保留缺失项，并保证已经存在的每个领域至少有一个代表项，避免字段数量较多时把图片、文件或附件全部挤掉。

### 19.3 文档执行数量拓扑

实施后的静默识别矩阵为：

| 文档数 | 资料记录数 | 用户可见形态 | 预计产物 |
|---:|---:|---|---:|
| 0 | 0 | 等待输入 | 0 |
| 1 | 0 | 单份 | 1 |
| N > 1 | 0 | 多文档 | N |
| 0 或 1 | 1 | 单份 | 1 |
| N > 1 | 1 | 多文档，共享当前资料 | N |
| 0 或 1 | M > 1 | 按资料 | M |
| N > 1 | M > 1 | 要求建立映射 | 0，确认前阻断 |

“单条资料”只影响单份文档的当前资料上下文，不再在 UI 上表现为批次。运行层仍复用逐记录适配器处理这一个记录，因此无底稿生成、失败隔离和现有记录执行契约不会退化。

## 20. 状态权威与数据流

本轮形成的实际边界是：

```text
资料包磁盘基线
  -> MaterialPackageEditSession
  -> Qt 编辑草稿
      -> MaterialPreviewSnapshot（实时、可标记未保存）
      -> 显式应用/开始执行
          -> MaterialBatchSelection + MaterialExecutionContext（成对冻结）
          -> DocumentExecutionSnapshot
          -> 执行器
```

关键约束：

1. 查询、刷新摘要、计算 dirty 和构建预览只做纯投影。
2. 保存、切换、新建、关闭和放弃均经过显式事务。
3. 草稿可以实时预览，但不能在输入过程中替换已经冻结的执行上下文。
4. 映射导入的新字段默认进入固定字段范围；已有明确自由字段设置不被覆盖。
5. 图片行从资料包恢复时同时还原 Token 规格、规则和实际资源，避免只显示规则却没有图片身份。

## 22. 修改评估与进一步优化

### 22.1 已关闭的高风险问题

- 内置包可编辑但无法完成保存；
- 脏内置包阻断切换、新建或关闭；
- 查询隐式修改模型；
- 字段输入过程自动污染执行上下文；
- 单记录在 UI 中被错误展示为批次；
- 多文档与一条共享资料被错误阻断为映射问题；
- 预览只显示字段，无法核对文件、时间、图片和附件；
- 默认图片只有规则或 Token，没有一致的实际资源；
- 嵌入执行详情的弹性占位制造大面积空白。

### 22.2 有意保留的后续边界

以下内容不影响本轮 P0/P1 验收，但仍值得在发布前继续收敛：

1. `MaterialPackageEditSession` 已拥有身份、基线和版本，但部分草稿字段仍由现有 presenter 容器承载；后续可以逐域迁入统一 draft 对象。
2. 字段依赖目前覆盖当前文档 Token 和时间计划；字段函数、输出命名变量、批量映射键和未来条件规则仍应接入统一 `MaterialDependencyIndex`。
3. 当前支持完整全局放弃和既有单步字段恢复，但尚未实现跨五域的多级命令撤销栈。
4. 工作台已经区分“未保存草稿”和已冻结执行上下文，后续可增加版本号对比面板；这属于可解释性增强，不应重新引入自动发布。
5. 兼容 presenter 和旧字段容器应在端到端迁移测试覆盖后逐步删除，不建议在发布前最后阶段一次性重写。

### 22.3 发布前建议

- 保留本轮数量矩阵、查询纯度、内置保存副本和五域默认包测试为发布门禁。
- 在 Windows 开发机启用 Developer Mode 或 CI 管理员权限后补跑两项符号链接测试。
- 用真实 DOCX 模板分别放置五类 Token，完成一次人工可视化验收；自动测试已经验证映射身份和状态，但人工验收仍应确认 Word 中的最终排版。

## 23. 资料包预览名称边界

2026-07-31 的后续检查发现，工作台预览曾通过场景摘要的全局中文字典，把 `company_name`、`project_no` 等字段代码临时显示成“公司名称”“项目编号”。这些名称既不属于资料包，也不是用户输入，容易被误认为已保存的字段元数据。

本轮进一步收紧为以下规则：

| 领域 | 可显示名称的唯一来源 | 无明确名称时 |
|---|---|---|
| 字段 | 后续正式的资料包字段标签契约 | 不显示名称，只显示完整 Token |
| 时间 | 后续正式的时间输出标签契约 | 不显示名称，只显示完整 Token |
| 文件 | `ContentMaterialBinding.label` | 不显示名称 |
| 图片 | `AssetItem.label` / 草稿中的 `AssetTokenSpec.label` | 不显示名称 |
| 附件 | `AttachmentBinding.label` | 不显示名称 |

附加约束：

1. `field_aliases` 只用于“替代 Token → 规范字段”的解析，不得解释为显示名称。
2. 场景摘要的 `MATERIAL_FIELD_DISPLAY_LABELS` 只服务场景/契约说明，不得被资料包预览导入。
3. 字段 key、角色 role 和内容 id 都是稳定标识符，不得自动美化为看似由用户维护的名称。
4. 没有明确标签时，UI 隐藏名称行，但始终保留可复制的完整 `{{@namespace:key}}` Token 和当前值。
5. 默认测试包中字段和时间不再显示临时中文字典名称；文件、图片、附件继续显示其在资料包中明确保存的标签。

本次边界由行为测试覆盖：已知 key（包括 `company_name`、`project_no`）以及 `field_aliases` 均不能让工作台生成字段标题；只有持久化在对应领域对象上的标签可以进入预览。
