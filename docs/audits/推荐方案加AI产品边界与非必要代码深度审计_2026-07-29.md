> 审计日期：2026-07-29  
> 审计对象：Lark Formatter V1.0 当前工作区  
> 审计性质：静态依赖、打包边界、产品职责和代码规模审阅  
> 决策目标：保留“推荐方案 + AI”，在不破坏核心闭环的前提下，识别仍可移除、迁出、延后或收敛的代码，并给出不重复计算的最终行数目标。

> 2026-07-29 实施后复核：完整发布包已降至 **184,664 第一方有效行（TOC 唯一源文件口径）**，进入 182,000～185,000 长期推荐区间。本文前半部分的 269,306 行仍保留为审计基线；最新结论见第 16 节。

## 1. 结论先行

当前产品仍然明显偏重，但问题并不是存在大量完全无人引用的“垃圾代码”。更主要的原因是：

1. 客户端产品、内部验收平台、发布治理、样本审计和源码自证被放进了同一个运行时源码树。
2. PyInstaller 使用了过宽的子模块收集规则，把入口不可达的通用 UI 控件也打进了产品。
3. `src/config` 中包含大量以 Python 表达的注册表和矩阵数据，形成了“数据行数看起来像业务代码”的膨胀。
4. 场景矩阵、批处理、精确预览、素材工作台和高级题图修复等能力同时进入主产品，没有形成核心版与可选能力包的边界。
5. AI 本身不是应整体删除的臃肿项，但其界面编排、兼容路径和能力表仍有约 2,000～3,000 行的收敛空间。

按当前快照，第一方运行时打包代码约为 **269,306 有效行**。推荐方案保留 AI 后：

- 推荐工程目标：**约 182,000 有效行**
- 合理验收区间：**175,000～185,000 有效行**
- 第一阶段硬上限：**190,000 有效行**
- 若批处理、精确 Office/PDF 预览、通用素材导入工作台都继续内置，较现实的结果会回到 **205,000～215,000 行**
- 若要求低于 **165,000 行**，通常必须再放弃 AI 内容生成路径、一个主要业务模式或一组核心领域能力，不建议为了行数强行执行

因此，当前代码相对推荐产品边界约有 **8 万～9 万行**的可优化空间。这里的“优化”包含四种不同动作，不能混为一谈：

- 从产品包中取消收集；
- 从 `src` 迁到 `tests`、`scripts` 或离线审计工具；
- 将非核心能力拆为可选模块；
- 对仍保留的代码做结构收敛和数据外置。

最终目标不是单纯删除最多代码，而是让客户运行时只包含客户功能，让工程验证只存在于工程环境。

## 3. “推荐方案 + AI”的正式边界

### 3.1 一句话产品定义

产品应是一个本地优先的文档生产工具：用户提供文档、模板、素材或自然语言目标，系统通过确定性规则和可确认的 AI 计划完成格式化或受约束的内容生成，并交付可验证的 DOCX 结果。

### 3.2 正式保留的产品能力

| 能力层 | 保留边界 |
|---|---|
| 文档入口 | 打开 DOCX、基础预检、识别模板与素材角色 |
| 规则格式化 | 标题、正文、段落、页眉页脚、表格、图片和必要版式规则 |
| 模板 | 模板选择、必要配置、模板驱动的生产；不要求完整模板工程工作台 |
| 素材 | 作为字段、附件或 AI 内容生成输入；保留最小编译和渲染内核 |
| AI 交互 | 一级 AI 页面、会话、附件角色、自然语言理解、必要澄清、计划解释 |
| AI 执行 | 生成类型化计划，预检后显式确认，再调用现有生产链 |
| AI 内容生成 | 保留受约束的考试、投标/叙事类草稿生成与校验 |
| 交付 | 输出 DOCX、验证文件存在和基本完整性、提供打开或定位动作 |
| 状态安全 | 取消、任务日志、租约、恢复、会话持久化、敏感配置隔离 |
| 本地优先 | 文档生产在本地完成；云模型只是可配置的理解/生成提供方 |

### 3.3 AI 只保留三条闭环

#### 路径 A：已有 DOCX 的格式化

用户附加 DOCX 或选择已有文档，AI 识别目标、补齐必要参数，生成类型化计划，执行预检，等待用户确认，再调用确定性格式化与交付链。

#### 路径 B：受约束的内容生成

用户提供主题、约束、模板和必要素材。AI 生成符合既定模式的 Markdown/结构化内容，经模式校验、最小素材编译和 DOCX 渲染后形成草稿，再进入确认和交付。

#### 路径 C：无法直接执行时的可信终止

当输入不充分、能力未实现、提供方不可用或风险超出允许范围时，AI 必须说明缺口并给出下一步，而不是伪造成功或绕过确认。

### 3.4 明确不进入核心产品的能力

以下项目不属于本轮“推荐方案 + AI”：

- 23 条场景路线全部达到真实可执行；
- AI 批处理；
- PDF、OCR、LaTeX 的通用内容导入；
- AI 自动生成或修改模板母版；
- 专业插件、外部交接和多代理编排；
- 项目中心、计划中心、长期记忆中心、Skills 中心；
- Web 搜索和任意工具调用运行时；
- 无确认的自动文档写入；
- 全功能素材管理工作台；
- 内置的研发成熟度、样本库、发布证书和源码自证面板；
- 对所有云模型提供方作可用性承诺。

已有 AI 审计也给出了相同方向，参见：

- `docs/audits/AI全场景闭环用例POC与最短路径审计_2026-07-29.md`

1. 将消息类型、动作类型和结果呈现改为数据驱动映射；

### 6.4 AI 依赖的素材内核不能整体删除

`assistant/adapters/content_generation_adapter.py` 实际调用 `services/material_content` 的编译、组合和渲染能力；考试模式也依赖 Markdown 结构解析。因此此前若把整个素材内容模块视为可删除项，会破坏 AI 路径 B。

正确边界是拆成两层：

#### 必须保留的最小内核

- AI 生成 Markdown 的受控解析；
- `DocumentFragment` 或等价结构化中间模型；
- 内容模式校验；
- 组合器；
- DOCX 渲染；
- 生成产物仓库；
- 必要资源物化。

#### 可选或延后的通用素材工作台

- 任意用户 DOCX 的复杂素材导入；
- 大规模规范化和迁移；
- 元文件转换；

## 9. 兼容层与迁移代码的边界

当前仍存在多处旧字段、旧母版、旧 UI 别名和 `plan_candidate` 状态兼容。兼容不是天然无用，但无限期兼容会把每次重构成本永久化。

推荐制定以下政策：

1. 正式运行时只支持“当前数据版本 + 前一个主要版本”；
2. 更老数据通过离线迁移工具处理；
3. 兼容逻辑集中在一个入口层，不散落到 UI、领域模型和渲染器；
4. 每个兼容分支必须标注删除版本和固定回归样例；
5. 没有真实用户数据样本支持的兼容分支不得永久保留；
6. 迁移完成后，内部模型统一使用当前字段名。

在该政策签署、迁移夹具补全后，预计还有 **2,000～4,000 行**兼容和别名代码可删除或迁出。由于当前缺少发布数据分布和迁移承诺，本报告不把这部分计入第一阶段的高置信度收益。

- 文档生产管线与确定性规则引擎；
- DOCX 读取、写入、结构校验和必要的损坏保护；
- AI 请求策略、附件披露授权和敏感信息隔离；
- 类型化计划和生产契约；
- 显式确认、取消、日志、租约和恢复；
- Provider 配置与失败降级；
- 路径 B 所需的最小 Markdown/内容编译内核；
- 考试、投标/叙事模式的结构校验；
- 基础图片和素材资源物化；

- 用户可见错误、预检告警和交付验证。

特别禁止以缩短代码为由：

- 将类型化契约改回自由字典；
- 将生产规则塞进 UI；
- 绕过确认直接执行；
- 用大范围 `except Exception: pass` 隐藏失败；
- 删除恢复/租约后依赖“应用不崩溃”的假设；
- 把 AI 生成文本直接写入 DOCX 而跳过结构校验。

## 13. 建议建立的长期边界门禁

### 13.1 目录依赖规则

```text
ui -> application -> domain/contracts
                   -> production ports
adapters/services -> production ports
tests/scripts ----> product modules
product modules -X-> tests/scripts/source evidence
```

产品代码禁止导入：

- `tests.*`
- `scripts.*`
- `*_audit` 工程审计模块
- 发布证书、成熟度台账和样本覆盖注册表

### 13.2 打包规则

- 禁止对大型 UI/配置命名空间使用无条件 `collect_submodules`；
- 动态导入必须有人工维护的白名单和测试；
- CI 输出“入口可达但未打包”“已打包但入口不可达”两张差异表；
- 开发 Provider、审计样本、测试夹具不得出现在正式包。

### 13.3 规模预算

建议 CI 同时跟踪：

| 指标 | 目标 |
|---|---:|
| 核心产品打包第一方有效行 | ≤ 185,000 |

行数只是门禁之一；还要同时跟踪依赖方向、圈复杂度、启动时间、安装包体积和核心路径回归。

## 14. 风险与尚未完成的验证

本报告是深度静态审计，不等同于已经完成删除。执行前仍需补齐：

1. 工作区非常脏，必须先得到可重复的干净基线；
2. Python 动态导入、字符串反射和 Qt 信号连接可能让静态可达性出现漏报；
3. 当前 269,306 行是依据打包规则的第一方代码估算，不是对最终二进制反编译后的精确计数；
4. 素材内容、题图和预览模块存在跨模式共享，需要用真实样例验证最小闭包；
5. 兼容层能否删除取决于实际用户数据版本；
6. 本轮尚未实施功能删除，也没有在删改后的分支执行完整构建和回归；
7. 外置 JSON/YAML 会降低 Python 行数，但资源体积仍然存在，应单独统计。

## 15. 最终建议

采用“核心产品 + AI 三路径 + 可选能力包”的架构边界：

1. 立即从产品中移除场景矩阵、发布治理、源码自证和宽泛强制打包；
2. 保留 AI，但只承诺路径 A、B、C，并把 AI 包收敛到 14,000～15,000 行；
3. 保留 AI 内容生成所需的最小素材编译内核，不再把整个素材模块误判为可删除；
4. 把完整批处理、精确预览、通用素材导入、高级资产治理和主题编辑拆成可选能力；
5. 将测试/审计代码迁出 `src`，将产品注册表从 Python 外置为带 schema 的版本化数据；
6. 以 **182,000 行**为最终工程目标，以 **190,000 行**为核心产品硬上限。

这套方案保留了产品最有价值的“确定性文档生产 + 可确认 AI 协作”，同时把内部治理、后续路线和高级工作台从核心运行时中剥离。它比直接删除 AI 或整个素材系统更符合真实依赖，也比仅清理孤儿文件能获得更显著、可持续的减量。
