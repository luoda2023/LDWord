## 2. 总结论

当前 6 个可执行内置场景是可用起点，但不是完整场景能力矩阵。真正完善的矩阵需要同时覆盖两条轴：

```text
文档类型轴：
自定义、论文、投稿、试卷、标书、公文、技术文档、报告、项目申报、合同、HR函件、会议制度、财务报价、产品售前、专利、书稿等

工作流轴：
导入、清理、结构识别、资料填充、排版、对象保护、计数合规、审阅对比、多版本交付、批量生成、归档复用
```

如果只按文档类型建入口，会造成顶层导航膨胀。

如果只按功能开关建入口，用户不知道“我现在做投标/投稿/合同/试卷”应该怎么配。

因此建议采用三层结构：

```text
顶层可执行场景：
只放 P0 高频、低歧义、可本地闭环的任务入口。

规划级场景族 / profile：
承接高频但尚未闭环，或不适合抢顶层入口的任务。

插件 / 专业扩展：
承接高风险、窄领域、依赖外部规则、难以稳定承诺的能力。
```

当前最主要的缺口不是“缺少几个控件”，而是缺少“场景族覆盖网 + profile 落点 + 链路验收标准”。本文后续围绕这三件事展开。

## 3. 完整性判断框架

一个场景能力是否完整，不能只看有没有 UI 开关。应按下面 10 条链路审阅：

| 链路 | 必须回答的问题 | 当前主要承载 |
| --- | --- | --- |
| 任务心智 | 用户到底在完成什么文档工作 | 场景族、场景 profile |
| 输入契约 | 接受 docx、markdown、json、xlsx、bibtex、LaTeX 片段中的哪些 | `InputSourceProfile` |
| 资料契约 | 是否需要字段、图片、签章、附件、多实体资料 | 资料包 schema、`material_schema_id` |
| 处理范围 | 处理正文、目录、摘要、参考文献、附录、附件中的哪些 | `FormatScopeConfig` |
| 模板基线 | 采用什么外观基线和兼容模板 | `TemplateConfig`、`compatible_template_ids` |
| 能力域 | 启用哪些结构、表格、公式、引用、清理、填充、输出能力 | `module_switches`、UI capability groups |
| 合规口径 | 检查哪些规则、计数哪些范围、失败如何处理 | `ComplianceProfile`、CountEngine |
| 对象安全 | 遇到 OLE、Visio、宏、修订、批注、文本框、域如何处理 | `ObjectPreflightPolicy` |
| 交付物 | 生成哪些版本、报告、中间产物、对比稿、包结构 | `DeliveryPreset`、`OutputConfig` |
| 可见闭环 | UI 摘要、resolver、scheduler、pipeline、报告、测试是否说同一套事实 | ScenePanel、Workbench、执行报告、测试 |

只要其中任意一项没有落点，这个场景就只能算“场景草稿”，不能算完整能力。

## 4. 能力域 V3

现有文档提出 12 个能力域，方向正确。本轮建议调整为 14 个长期稳定能力域，以覆盖更高频的边界场景。

| 能力域 | 核心问题 | 典型场景 | 当前状态 | 完整化要求 |
| --- | --- | --- | --- | --- |
| 输入来源与结构化 | 输入从哪里来，是否可结构化 | 试卷、投稿、项目申报、批量函件 | 已有 `InputSourceProfile` | 需要 UI 编辑、导入校验和报告解释 |
| 资料包与资产 | 字段、图片、签章、附件如何绑定 | 标书、公文、合同、HR | 有资料包规划和部分 UI | schema、必填字段、图片角色、缺失策略需场景化 |
| 处理范围与定位 | 哪些分区处理，哪些只读 | 论文、标书、公文、书稿 | `sections` 已可见 | 页码范围、正文起点、关键词、附件范围需产品化 |
| 模板版式基线 | 文档外观长什么样 | 全场景 | 模板管理已较完整 | 场景只能覆盖有业务理由的模板参数 |
| 结构排版执行 | 标题、段落、页面、分节如何改 | 全场景 | P0 已接入 | 遇对象风险时要能降级并解释 |
| 表格图表与题注 | 表格、图片、题注、图表目录 | 论文、标书、技术、报告 | 部分已接入 | 图像质量、题注顺序、图表清单需纳入合规 |
| 公式与专业符号 | OMML、LaTeX 片段、化学式、公式编号 | 论文、技术、试卷、投稿 | `formula_convert` 有模型但链路未闭合 | UI、执行模块、低置信度策略和报告需闭环 |
| 引用与参考文献 | 引用链接、参考文献、BibTeX、CSL | 论文、投稿、技术 | 参考文献页规划已存在 | 投稿 profile、Bib/CSL、引用顺序检查需单独落点 |
| 计数与规则合规 | 字数、词数、图表数、附件齐套 | 论文、投稿、项目申报、试卷 | CountEngine 第一版已接入 | profile 来源、范围分类、差异解释需要继续细化 |
| 对象保护与安全 | OLE、Visio、宏、修订、批注、文本框、域 | 技术、合同、标书、投稿 | `ObjectPreflightPolicy` 已有 | 预检结果、跳过映射、用户确认链路需闭合 |
| 内容填充与变体 | 占位符、资料字段、图片、水印、答案显隐 | 标书、公文、试卷、合同 | 模块存在但产品化不足 | 同源数据、多版本显隐规则需归交付 preset |
| 审阅与版本对比 | 对比稿、修订稿、审阅稿、变更报告 | 技术、合同、投稿修回 | 文本对比稿第一版已接入 | 格式级对比、修订保留策略、审阅包需扩展 |
| 多版本与批量交付 | 多模板、多 preset、多实体输出 | 标书、试卷、HR、项目申报 | `DeliveryPreset` 已推进 | 批量汇总、profile+preset artifact 汇总需继续闭合 |
| 导出与归档互操作 | PDF、ZIP 包、目录结构、外部系统提交 | 投稿、申报、标书、书稿 | 规划为主 | PDF/包结构/归档元数据要明确是否核心或插件 |

这 14 个能力域应成为后续场景 UI、规划 registry、测试覆盖和执行报告的共同语言。

## 5. 顶层入口与 profile 的判定规则

### 5.1 可以进入顶层可执行场景的条件

同时满足以下条件，才应该出现在主导航或场景预设下拉的第一层：

1. 高频用户心智明确，用户会自然说“我要做某类文档”。
2. 默认模板和处理范围相对稳定。
3. 输入格式和资料契约能本地校验。
4. 不依赖高风险专业判断。
5. 核心输出物能在当前 pipeline 中生成。
6. UI 摘要、执行报告和测试能证明链路闭合。

当前符合或接近符合的顶层场景：

| 顶层场景 | 状态 | 必须继续收敛的边界 |
| --- | --- | --- |
| 自定义 | 保留 | 不暗含专业合规，只做手动组合 |
| 中文学术论文 | 保留，但应改名或描述收窄 | 不再同时暗含英文期刊投稿 |
| 标书/商务投标 | 保留 | 不做商务实质判断，只做资料、格式、交付 |
| 公文/行政文书 | 保留 | 页眉页脚版式归模板，状态水印/编号保留归场景 |
| 技术/工程文档 | 保留 | 高风险对象默认保护，变更报告是核心交付 |
| 通用报告 | 保留 | 少参数、低风险、可升级到其他 profile |

### 5.2 应落为规划级场景族的条件

满足高频但尚未闭环，或与现有顶层场景共享大量能力但边界独立的任务，应先进入规划级 registry。

| 场景族 | 建议等级 | 落点 |
| --- | --- | --- |
| 英文期刊投稿 | P1 | 独立场景族 `journal_en` |
| 试卷/教学材料 | P1 | 独立场景族或教育 profile |
| 项目申报/评审 | P1 | 独立 profile，共享学术和标书能力 |
| 合同/协议/法务格式交付 | P1 | 格式与审阅交付 profile，不做法律判断 |
| HR/档案/批量函件 | P1 | 资料包批量 profile |
| 会议纪要/制度汇编 | P1 | 公文/行政下的 profile |
| 产品售前/白皮书/方案书 | P1 | 技术、报告、标书之间的 profile |
| 书稿/长文档出版 | P1 候选 | 长文档 profile，顶层待观察 |

### 5.3 应进入插件或专业扩展的条件

以下能力不应作为核心场景直接承诺：

| 能力 | 原因 | 落点 |
| --- | --- | --- |
| 完整 LaTeX 工程无损转 Word | 宏包、class、浮动体和 TikZ 差异过大 | 高级导入插件 |
| 复杂几何图自动生成 | 领域窄，工程复杂，容易拖慢主线 | 教育图形插件 |
| AI 内容生成 | 质量责任和外部模型依赖复杂 | 输入助手插件 |
| 法律条款审查 | 专业高风险 | 法务插件，核心只做格式和字段 |
| 财务/审计判断 | 专业高风险 | 财务插件，核心只做表格和附件一致性 |
| 专利权利要求质量判断 | 专业高风险 | 知识产权插件 |
| 期刊官网自动抓规则 | 外部变化大，可信源需审阅 | profile 更新器 |
| 全量 docx 重建 | 容易破坏关系、域、修订、OLE、Visio | 用户确认的高风险模式 |

### 5.4 优先级口径

| 等级 | 含义 | 导航暴露 |
| --- | --- | --- |
| P0 | 已有或应立即闭合的可执行顶层场景 | 可以暴露 |
| P1 | 高频且应进入近期模型、profile、UI 或执行闭环的规划族 | 默认不暴露，闭合后再评估 |
| P1 候选 | 高频但长文档、专业协同或交付复杂度较高，先以规划契约观察 | 不暴露 |
| P2 | 高频但专业风险、差异过大或依赖插件化能力 | 不暴露 |

| 专利/知识产权材料 | 交底书、说明书、权利要求书 | P2 插件或技术 profile | 图号、术语、章节、版本 | 文档已有 P2 判断 | 专利结构 profile | 不承诺专利法律质量 |
| 书稿/长文档出版 | 书稿、手册汇编、章节合集 | P1 候选，P2 起步的长文档 profile | 章节、目录、交叉引用、索引、导出 | 文档已有 P2 判断 | 长文档结构和归档策略 | 不替代出版社排版系统 |
| 培训/课程资料 | 讲义、练习册、培训手册、教师手册 | P1 教育 profile | 教学结构、题目、图片、答案显隐 | 可归试卷/教学材料 | 教育资料 schema | 不作为单独 AI 内容生成入口 |
| 资质/证照材料包 | 企业资质汇编、证书附件、扫描件清单 | P1 标书/项目资料 profile | 附件清单、图片/PDF、缺项报告 | 可归标书/项目申报 | 附件 inventory schema | 不识别证书真实性 |

本轮新增判断：

- 合同、HR、会议制度、产品售前、书稿不应继续只停留在“P2 以后再说”。它们是高频需求，但不一定要进入顶层导航，应进入 planning registry 或 profile 体系。
- 财务、专利、复杂法律判断要保留专业边界，核心只做格式、字段、版本和附件检查。
- 培训/课程资料与试卷不是完全同一类，但可以共享教育场景族下的 profile。
- 资质/证照材料包不是单独场景，而是标书、项目申报的资料包能力放大版。

## 7. 场景族深度定义

### 7.1 中文学术论文 `thesis_cn`

应从当前“学位论文·期刊论文·学术报告”的宽泛描述收窄为中文学术论文。

必备 profile：

- `thesis_cn_default`
- `school_thesis`
- `course_paper`
- `opening_report`
- `review_or_survey`

核心链路：

```text
docx/markdown
→ 分区识别
→ 模板版式
→ 题注/表格/公式/参考文献
→ CountEngine
→ 合规报告
→ final/review/compliance_report
```

边界：

## 8. 现有功能缺口审阅

### 8.1 场景模型层

已具备：

- `InputSourceProfile`
- `ComplianceProfile`
- `ObjectPreflightPolicy`
- `DeliveryPreset`
- `BatchPreset`
- 场景级 feature override
- 规划级 `scene_family_registry` 已覆盖 P1、P1 候选和 P2 场景族

主要缺口：

| 缺口 | 影响 |
| --- | --- |
| 新增规划族仍只是 planning contract | 尚未具备资料包 schema、可执行 profile、UI 编辑和 pipeline 行为 |

已具备：

- `ScenePanel` 复用 `StyledComboBox`、`ToggleSwitch`、`FeatureToggleRow`、`TemplateFormStack`、`SummaryGrid`。
- 概览已能投影输入、合规、对象保护、交付。

主要缺口：

| 缺口 | 影响 |
| --- | --- |

| 处理范围页还缺页码范围、正文起点页、起始关键词等定位方式 | 复杂论文、申报、标书无法表达范围 |

主要缺口：

| 缺口 | 影响 |
| --- | --- |

| compare docx 目前偏文本对比 | 合同、技术、投稿修回需要格式级和修订链路 |

| 输出包结构和 ZIP/PDF 归档还未定义 | 投稿、申报、标书交付包不完整 |

## 9. 场景配置控件样式一致性要求

用户已明确要求场景配置中的控件样式控制必须与模板管理保持一致。这里不是视觉建议，而是架构约束。

### 9.1 统一控件清单

场景配置必须继续使用：

- `StyledComboBox`：策略、profile、类型、preset 选择。
- `ToggleSwitch`：布尔开关。
- `FeatureToggleRow`：能力域开关。
- `TemplateFormStack`、`TemplateFormGrid`、`template_form_row`：详情表单布局。
- `SummaryGrid`：输入、合规、交付、对象保护摘要。
- `StyledSpinBox` 或模板管理已有数值控件：数值参数。
- `OptionToggleChip` 或现有分段控件：少量互斥模式。

不应出现：

- 场景专用的新 combo 样式。
- 场景专用的新 switch 样式。
- 与模板管理不同的表单行高度和 label 对齐。
- 大段说明文字替代可交互控件。
- 卡片套卡片。

### 9.2 行布局规则

模板管理已经形成“短字段同排、强关联相邻”的模式，场景配置应照此执行。

适合同排的控件：

| 同排组合 | 原因 |
| --- | --- |
| 输入格式 / 结构化格式 | 同属输入契约 |
| Markdown 策略 / LaTeX 策略 | 同属导入策略 |
| 资料包 schema / 资料包必需 | 同属资料契约 |
| 合规 profile / 计数 profile | 同属合规口径 |
| 报告粒度 / 失败策略 | 同属执行反馈 |
| 对象预检 / 保护模式 / 高风险跳过 | 同属对象安全 |
| 默认交付 / 交付数量 | 同属输出摘要 |
| 命名模板 / 输出目录模板 | 同属交付命名 |

不适合同排的内容：

- 字段列表、图片角色列表、附件清单。
- 高风险对象映射表。
- delivery preset 列表。
- 分区范围列表。

这些应使用列表或表格式控件，但仍需在同一视觉体系内。

### 9.3 场景 UI 信息架构建议

建议 ScenePanel 长期调整为：

```text

  输入、合规、对象保护、交付摘要

处理范围
  分区选择
  定位方式
  只读/可改范围

  6 个用户能力组
  14 个底层能力域摘要可在详情中投影

输入与资料
  输入格式
  Markdown/LaTeX 策略
  资料包 schema
  字段与图片角色
  缺失策略

公式与专业内容
  formula convert
  formula style/equation numbering
  chem typography
  专业对象边界

校验与合规
  compliance profile
  count profile
  check scopes
  object preflight
  report level/failure policy

输出与交付
  delivery presets
  target template
  artifacts
  content visibility rules
  naming/output package

批量与审阅
  batch preset
```

这可以先在文档和 registry 层定义，不必一次性全部 UI 实现。

## 10. 防遗漏审阅清单

后续新增任何场景族、profile 或能力前，必须过这张清单。

### 10.1 用户任务清单

| 问题 | 如果答案为空，说明 |
| --- | --- |
| 用户会用什么自然语言描述这件事 | 场景命名不清 |
| 这件事是格式化、填资料、合规检查、批量生成、投稿/提交包，还是审阅对比 | 工作流边界不清 |
| 用户期望最终得到哪些文件 | 交付 preset 不清 |
| 用户是否会重复做这件事 | 是否值得 profile 化不清 |
| 是否存在高风险专业判断 | 核心/插件边界不清 |

### 10.2 数据链路清单

| 问题 | 目标 |
| --- | --- |
| 输入格式能否被声明和校验 | 进入 `InputSourceProfile` |
| 资料字段和图片角色能否被声明和校验 | 进入资料包 schema |
| 计数和规则口径能否 profile 化 | 进入 CountEngine profile |
| 产物版本能否由 preset 表达 | 进入 `DeliveryPreset` |
| 批量对象能否隔离失败 | 进入 `BatchPreset` 和批量报告 |
| 高风险对象能否扫描和解释 | 进入 `ObjectPreflightPolicy` |

### 10.3 UI 链路清单

| 问题 | 目标 |
| --- | --- |
| 概览摘要是否能说出输入、合规、对象保护、交付 | 避免只显示“几项功能” |
| 详情控件是否复用模板管理控件体系 | 保持一致性 |
| 用户是否能编辑摘要中显示的关键事实 | 避免只读投影 |
| UI 文案是否使用用户语言而非模块名 | 降低理解成本 |
| 执行报告是否复述场景关键策略 | 保持 UI 和执行一致 |

### 10.4 测试链路清单

| 测试类型 | 必须覆盖 |
| --- | --- |
| registry 测试 | 场景族落点、优先级、边界、是否进入导航 |
| UI projection 测试 | 摘要和控件读取同一份 `SceneWorkspace` |
| resolver 测试 | 场景覆盖模板的顺序正确 |
| scheduler 测试 | module switches 驱动真实模块选择 |
| pipeline 测试 | delivery preset、compare、intermediate、reports 真实输出 |
| batch 测试 | profile+preset artifact 汇总和失败隔离 |
| reporting 测试 | CountEngine、对象保护、跳过模块原因进入报告 |

## 12. 分阶段落地路线

### Phase M1：矩阵补登记（第一版已完成）

- 已扩展 `scene_family_registry`，补齐合同、HR、会议制度、产品售前、长文档、财务报价、专利等 family。
- 已用测试锁定它们不进入 `SCENE_METAS` 和 `SCENE_FACTORIES`。
- 已为每个 family 记录 required closures 和 boundaries。
- 下一步不是继续堆场景名，而是为优先级最高的 family 补资料包 schema、profile、UI 投影和执行报告链路。

### Phase M2：ScenePanel 编辑闭环

- 输入与资料页可编辑 accepted formats、structured formats、material schema、字段、图片角色。
- 校验与合规页可编辑 count profile、object preflight、report level、failure policy。
- 输出设置页从默认产物开关升级为 delivery preset 列表。
- 处理范围页补齐 page ranges、body start page、body start keyword。
- 所有控件继续复用模板管理体系。

### Phase M3：高频 P1 profile 最小闭环

优先顺序建议：

1. `contract_delivery`：因为对比稿、修订保护、字段一致性可复用现有能力。
2. `hr_batch_documents`：因为能验证资料包、批量输出、失败隔离。
3. `journal_en`：因为 CountEngine 和 delivery preset 已有基础，但 Bib/CSL 仍需专项实现。
4. `exam_teaching`：因为需要结构化 schema 和内容显隐规则。
5. `project_application`：因为依赖附件 inventory 和申报 profile 来源。

### Phase M4：插件化能力

- 完整 LaTeX 工程导入。
- 复杂学科图形。
- AI 内容生成。
- 法律、财务、专利专业判断。
- 期刊/申报系统规则更新器。

## 13. 最终验收口径

完善的高层场景能力矩阵，最终应该达到：

1. 用户的高频文档任务都有明确落点。
2. 顶层入口不膨胀，profile 和插件承接复杂差异。
3. 场景、模板、资料包、合规 profile、交付 preset 的职责互不抢位。
4. 每个场景都能说明输入、范围、模板、能力、合规、安全、交付和边界。
5. UI 摘要与执行事实一致。
6. 控件样式与模板管理一致。
7. 报告能解释场景策略、计数口径、对象保护和产物路径。
8. 测试能证明 registry、UI projection、resolver、scheduler、pipeline 和 reporting 的链路没有断。

一句话结论：

```text
场景矩阵不是“更多场景名”，而是“每个高频任务都有可解释、可配置、可执行、可报告、可测试的落点”。
```

## 17. Phase M1.3 Schema 执行前预检与报告落地补记（2026-06-16）

本轮把 schema 缺字段/缺资产从摘要层推进到 Workbench 运行时。

已落地内容：

- `WorkbenchProductionRunner` 执行前会根据 `SceneWorkspace.input_source_profile.material_schema_id`、`required_material_fields`、`required_image_roles` 和当前 `MaterialExecutionContext` 计算 material diagnostics；
- 当 `InputSourceProfile.failure_policy == "warn"` 时，schema 缺项不会阻断执行，但会进入 payload 的 `material_diagnostics`、`diagnostics_count`、`diagnostics_summary`；

- Workbench JSON 报告中的 `diagnostics.items` 会包含 `rule_name="material_schema"`、`change_type="preflight_missing_material_fields"` 或 `preflight_missing_material_assets`；
- batch runner 会聚合每个 profile 的 `material_diagnostics`，并写入 batch JSON/Markdown 汇总报告；
- HR 批量场景已验证：一个 profile 成功、一个 profile 缺 `employee_id` 时，batch 状态为 `partial_success`，汇总报告包含缺项诊断。
