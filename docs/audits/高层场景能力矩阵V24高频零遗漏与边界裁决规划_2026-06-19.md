# 高层场景能力矩阵 V24 高频零遗漏与边界裁决规划（2026-06-19）

## 1. 本轮定位

本轮继续回应“目前功能点过于不完善，不希望出现高频适用场景遗漏或者边界不清晰”的要求。V23 已经给出十个能力槽位和 12 个 coverage pack，但还存在一个产品治理风险：

```text
静态矩阵没有缺口，不等于真实用户高频场景已经产品化可用。
```

因此 V24 不再把重点放在“还有没有新场景名”，而是把高频场景能力提升为一个更高层的能力矩阵：

```text
高频请求宇宙
-> 歧义裁决规则
-> pack / family / profile / schema / preset / plugin gate 落点
-> Word 风险面
-> UI 控件契约
-> 执行 / 报告 / 产物 / repair / 样本 / 测试证据
-> 产品成熟度分级
```

V24 的核心目标是防止两类问题：

1. 高频任务被遗漏，因为它不属于已有顶层场景名称；
2. 高频任务被错误吞并，因为边界词相似，例如“产品手册”“证书材料”“报价方案”“双语文档”“PDF 论文”。

## 3. 高频零遗漏的判定模型

### 3.1 不按“场景名”判断覆盖

高频需求不能只问“有没有这个场景名”，而应拆成六个面：

| 面 | 问题 | 典型值 |
| --- | --- | --- |
| 任务类型 | 用户到底要做什么？ | 排版、计数、生成、多版本、填充、批量、审阅、导入、归档 |
| 文档领域 | 文档属于什么业务域？ | 论文、期刊、试卷、标书、公文、技术手册、申报、合同、表单、披露 |
| 输入事实源 | 机器可信数据来自哪里？ | DOCX、Markdown、JSON、XLSX、BibTeX/CSL、图片/附件、PDF/OCR、LaTeX、插件 |
| 输出形态 | 交付什么版本或产物？ | final、review、compare、signing、student、teacher、answer、archive、manifest、report |
| Word 风险面 | 会碰到什么 OOXML/package 风险？ | 样式、编号、表格、固定行高、域、修订、批注、文本框、内容控件、OLE/VBA |
| 专业边界 | 是否涉及核心不应承诺的判断？ | 法律、财务、审计、专利、翻译质量、AI 内容、OCR/无损转换 |

只有这六个面都有明确落点，才能说“高频需求已覆盖”。

### 3.2 高频需求宇宙

V24 将高频请求抽象成 12 个稳定任务类：

| 高频任务类 | 用户常见说法 | 首选落点 | 防遗漏要求 |
| --- | --- | --- | --- |
| 快速排版清洗 | 套模板、修目录、页码不对、统一格式 | `quick_formatting` | 必须有模板问题、输出目标问题和对象预检 repair 入口 |
| 规则/计数检查 | 字数、词数、图表数、参考文献条数、学校/期刊限制 | CountProfile + report | 必须 profile-driven，多口径并列，不能承诺和 Word/投稿系统完全一致 |
| 结构化文档生成 | 试卷、证明、表单、证书、合同字段 | JSON/XLSX + MaterialSchema | JSON/XLSX 是机器事实源，Markdown 只做预览 |
| 多版本交付 | 学生版、教师版、签署稿、审阅稿、公开版、归档包 | DeliveryPreset + ContentVisibilityRule | 必须同源生成，不能分别生成不一致版本 |
| 资料包填充 | 标书资质、附件、图片、签章、项目材料 | MaterialSchema + AssetsPanel | 必须能报告缺项、角色、路径和残留 |
| 批量生成 | offer、证明、奖状、登记表、套打 | BatchPreset + batch runtime | 必须一记录一输出，失败隔离，不混入成功产物 |
| 专业披露/专业审阅 | 报价、预算、年报、ESG、专利、双语审阅 | `professional_disclosure` + plugin/manual gate | 核心只能做格式、清单、版本、边界报告，不做专业结论 |
| 导入/AI 边界 | PDF 转 Word、OCR、LaTeX、AI 草稿、复杂图形 | `import_ai_boundary` | 必须有置信度、人工确认和 handoff，不能静默进入核心排版 |
| Word 对象保护 | 修订、批注、字段、内容控件、文本框、OLE、宏 | ObjectPreflight + issue queue | 必须预检、降级、跳过或阻断，并解释原因 |
| 固定版位 | 套打表单、证书、答题卡、固定行高表格 | fixed-layout family/profile | `w:trHeight` 只归固定版位，不回普通表格样式 |
| 交付归档 | manifest、报告、附件包、对比稿、失败项 | OutputConfig + DeliveryPreset | 产物必须可定位、可打开、可进入最近结果 |
| 插件生态 | OCR、复杂学科图形、专业审阅、完整 LaTeX | plugin/manual gate | 插件不可用时也要解释边界和人工门 |

## 4. 边界裁决规则

### 4.1 裁决顺序

当用户请求命中多个场景时，按以下顺序裁决：

1. 先判定是否是导入/AI/专业风险；如果是，先进入 plugin/manual gate。
2. 再判定机器事实源；如果必须由 JSON/XLSX/BibTeX/CSL/资料包驱动，不允许落成纯模板配置。
3. 再判定输出形态；如果涉及多版本、签署稿、归档包、学生/教师/答案版，必须进入 DeliveryPreset。
4. 再判定 Word 风险面；如果存在修订、批注、域、内容控件、OLE/VBA、文本框、固定行高，必须进入 ObjectPreflight 或 fixed-layout 策略。
5. 最后才判定视觉模板；只有纯外观、字体、缩进、页眉页脚样式等才归模板管理。

### 4.2 高频歧义裁决表

| 用户说法 | 可能含义 | 首选裁决 | 不能做的事 |
| --- | --- | --- | --- |
| 产品手册 | 技术操作手册 | `technical_long_docs` / `long_document_publishing` | 不把客户售前资料误判为技术文档 |
| 产品手册 | 客户白皮书、售前方案 | `application_reports` / `product_sales_documents` | 不承诺营销文案质量 |
| 报价方案 | 产品/售前方案正文 | `application_reports` / `product_sales_documents` | 不处理金额正确性 |
| 报价方案 | 报价表、预算书、财务附件 | `professional_disclosure` / `finance_quote_documents` | 不做财务审计或价格判断 |
| 证书材料 | 投标资质附件 | `bidding_materials` / `qualification_archive_packages` | 不批量生成新证书 |
| 证书材料 | 奖状、证明、证书套打 | `batch_forms` / `form_batch_documents` | 不验证证书真实性 |
| 双语文档 | 双语排版 | `quick_formatting` | 不检查翻译质量 |
| 双语文档 | 术语一致性、翻译审阅 | `professional_disclosure` / `bilingual_translation_documents` | 不承诺译文专业质量 |
| PDF 论文 | PDF/OCR 导入后排版论文 | 先 `import_ai_boundary`，再 handoff 到 `chinese_academic` | 不承诺无损 PDF 转 Word |
| LaTeX 转 Word | 公式片段或完整工程 | 完整工程走 `import_ai_boundary`；公式片段走 scene formula policy | 不承诺完整工程无损转换 |
| 答题卡 | 与试卷题源绑定的输出版本 | `exam_education` + fixed-layout delivery | 不作为普通表单独立生成 |
| 登记表/申请表 | 批量固定版位套打 | `batch_forms` / `form_batch_documents` | 不吞进项目申报正文 |
| 项目申报书 | 申报正文、附件包、限字 | `application_reports` / `project_application` | 不替代外部申报系统 |
| 项目申请表 | 固定版位字段填充 | `batch_forms` / `form_batch_documents` | 不当成普通申报书排版 |
| 年报/ESG | 公开披露、多版本、归档 | `professional_disclosure` / `regulated_disclosure_documents` | 不做审计或披露充分性判断 |
| 专利说明书 | 专利/IP 文档 | `professional_disclosure` / `ip_patent_documents` | 不判断专利性、权利要求质量或侵权风险 |
| 合同审阅稿 | 修订/批注/字段一致性/签署稿 | `contract_delivery` | 不提供法律意见 |
| 会议纪要/制度汇编 | 公文和政策归档 | `official_policy` / `meeting_policy_documents` | 不判断行政决定实质 |
| 简历/个人陈述 | 个人求职材料排版 | 当前可落 `quick_formatting`；如产品定位面向 C 端，应新增 P2 family | 不混入 HR 批量内部文书 |

这张表是 V24 的防遗漏核心。未来新增自然请求时，必须先在这里确认是否已有裁决，不允许只靠关键词模糊匹配。

## 5. 当前 12 个 pack 的产品成熟度复核

### 5.1 `quick_formatting`

当前覆盖：普通 Word 排版、模板套用、标题编号、目录页码、基础对象预检、输出目标问题队列。

产品化短板：

- 用户说“排版”时可能实际是在要求学校、期刊、公文或合同合规，需要 router 前置询问；
- 模板问题能进 issue queue，但仍需要更深字段级跳转；
- 样本库已有最小 fixture，但真实业务样本还不足。

下一步切片：

- 增加“普通排版 vs 专业合规”的前置 disambiguation；
- Workbench repair 深跳到模板管理具体区域；
- 把 quick formatting 的真实模板样本纳入样本库。

### 5.2 `chinese_academic`

当前覆盖：中文学术场景、学校计数 profile、引用/公式置信度报告、规则来源人工确认。

产品化短板：

- 学校规则来源仍是 first slice，缺少可维护版本库；
- CountProfile 应继续吸收多口径：中文字符、纯汉字、英文词、折算字数、图表公式、脚注尾注、附录范围；
- PDF 论文、完整 LaTeX 工程不能绕过 import boundary。

下一步切片：

- 学校规则 profile 治理 UI；
- 论文结构 section classifier 的用户可见确认；
- 公式低置信度、引用缺失和学校口径差异进入更明确的 issue queue。

### 5.3 `english_journal`

当前覆盖：英文期刊 planned family、BibTeX/CSL、submission package、journal count/profile/report。

产品化短板：

- 期刊规则源要有 reviewed/expired/manual_required 状态；
- cover letter、declaration、response letter、supplementary 的产物组合还需要更完整的 DeliveryPreset；
- 投稿系统最终统计和出版社排版不能承诺一致。

下一步切片：

- 期刊规则来源治理和过期提示；
- 投稿包 manifest 与附件缺项检查；
- revision/response letter 的修订与批注保护。

### 5.4 `exam_education`

当前覆盖：试卷题源 schema、多版本输出、AI/复杂图形边界、学生/教师/答案 first slice。

产品化短板：

- 答题卡属于高频固定版位，当前需要更清楚地接到 fixed-layout；
- 学科图形、公式、图片资产应拆成通用图片、函数/统计图、学科插件三层；
- AI 内容质量不属于核心承诺，但 JSON 结构校验必须强约束。

下一步切片：

- 答题卡 DeliveryPreset + fixed-layout row-height/layout policy；
- 题图资产替换、预览与缺图报告；
- 试卷 JSON schema 的 UI 校验摘要和版本显隐预览。

### 5.5 `bidding_materials`

当前覆盖：标书、资质附件、签章、附件 manifest、缺项报告。

产品化短板：

- 联合体、多主体、多资质版本仍需 schema 细化；
- 正本/副本、签章位置、证照有效期属于资料和专业边界混合点；
- “证书材料”必须和批量证书套打分开。

下一步切片：

- 联合体/多主体 material schema；
- 正副本 DeliveryPreset 与签章残留检查；
- 资质附件过期字段只报告，不判断真实性。

### 5.6 `official_policy`

当前覆盖：通知、函、会议纪要、制度汇编、内部传阅水印状态、政策归档。

产品化短板：

- 公文文种、版记、文号、签发人、主送/抄送字段仍需更完整 schema；
- 水印状态是场景/输出，水印外观与基础控件必须有明确归属；
- “会议纪要/制度汇编”不应膨胀为多个顶层入口。

下一步切片：

- 公文字段 material schema 与归档 metadata；
- 版记/页眉页脚/页码模板边界确认；
- formal/internal/archive DeliveryPreset 的 report evidence。

### 5.7 `technical_long_docs`

当前覆盖：SOP、接口文档、技术手册、验收报告、书稿、chapter inventory。

产品化短板：

- 产品手册与售前资料容易混淆；
- 索引、附注、多文件合并、跨引用仍需边界；
- 复杂嵌入对象、图表和字段需要运行前预检可见。

下一步切片：

- 技术手册与产品售前文档 router 询问；
- chapter inventory 的 ScenePanel/Workbench 可视化；
- 多文件合并和 publisher system boundary。

### 5.8 `application_reports`

当前覆盖：项目申报、评审材料、产品白皮书、售前文档、附件包、限字 profile。

产品化短板：

- 项目申报正文、项目申请表、产品售前方案、报价预算表需要严格分流；
- 附件包和正文限字的事实源不同，不能混在一个开关；
- 外部申报系统规则只能通过 reviewed profile 或 manual gate 表达。

下一步切片：

- 项目申报与固定表单的自然语言裁决测试；
- 产品/售前资料与财务报价的路由确认；
- 附件 completeness report 与正文 section word-limit report 分开展示。

### 5.9 `contract_delivery`

当前覆盖：合同字段一致性、修订/批注保护、签署稿、签章材料、法律边界。

产品化短板：

- 合同字段一致性 currently 主要服务 `contract_parties_v1`，不能泛化到所有业务文档；
- 甲乙方、金额、日期、签章等字段的材料来源需要更强 UI 解释；
- 法律意见边界必须在执行前和报告中都可见。

下一步切片：

- 字段一致性配置和证据 UI；
- signing copy 的签章定位预览；
- compare/review/signing 三类交付产物的 artifact 分组。

### 5.10 `batch_forms`

当前覆盖：HR 批量、固定版位表单、证书/登记表套打、固定行高、占位符残留、批量失败隔离。

产品化短板：

- 答题卡和固定表单共享 fixed-layout 能力，但业务归属不同；
- HR 内部文书与个人简历/求职材料不能混淆；
- 一记录一输出、失败隔离、残留占位符必须成为硬验收。

下一步切片：

- fixed-layout profile 浏览器；
- 表单字段映射可视化；
- 答题卡从 exam_education 调用 fixed-layout，而不是改归 batch_forms。

### 5.11 `professional_disclosure`

当前覆盖：报价/财务、ESG/年报、专利/IP、双语审阅、专业插件边界。

产品化短板：

- 这类场景容易被误解为核心能做专业判断，必须更早显示边界；
- 年报/ESG、专利、翻译、财务各自需要不同 material schema 和 report 文案；
- 插件不可用时，仍需提供格式/清单/归档/人工确认的可用路径。

下一步切片：

- professional boundary banner 进入 ScenePanel/Workbench；
- 各专业 family 的最小 report evidence；
- 插件入口未安装/不可用时的降级策略。

### 5.12 `import_ai_boundary`

当前覆盖：OCR、PDF 转 Word、完整 LaTeX、AI 内容、复杂图形、置信度与人工确认。

产品化短板：

- 目前更像边界解释，还不是完整插件生态；
- PDF/OCR/LaTeX 的结果应该生成 confidence report 和可追踪 handoff；
- AI 结构化输出必须被 schema 校验，不能直接进入 Word。

下一步切片：

- import confidence report artifact；
- handoff 到 thesis/exam/technical 等后续 pack 的 payload；
- AI JSON schema validation 与 Markdown preview 分层。

## 6. 控件样式与参数归属的统一要求

场景配置中的控件必须与模板管理中规定的样式保持一致。原则是：

```text
同名格式参数 = 同一产品语言 = 同一控件语义 = 同一单位和禁用规则。
```

必须继续保持：

| 参数 | 模板控件语言 | 场景控件要求 |
| --- | --- | --- |
| 中文字体 / 英文字体 | `FontCombo` | 场景分区 override 也必须复用 |
| 字号 | `SizeCombo` | 不用普通数字框替代 |
| 左缩进 / 右缩进 | `IndentInput` | 左右缩进必须同一行展示，单位一致 |
| 特殊缩进 | `SpecialIndentInput` | 必须可切换无 / 首行 / 悬挂；无时禁用值但不造成交互断链 |
| 行距 | `StyledComboBox + SpacingInput` | 类型和值耦合，固定值和多倍值按规则启用 |
| 段前 / 段后 | `SpacingInput` | 段前段后应同一行展示，自动值禁用数字编辑 |
| 固定版位行高 | fixed-layout policy | 只在固定版位场景出现，不回普通表格模板 |
| 公式策略 | scene formula policy | 转换、低置信度、fallback 归场景；公式视觉基线归模板 |
| 水印状态 | scene/output status | 状态文本归场景/交付；基础外观需有模板/控件契约 |
| 输出版本 | DeliveryPreset editor | 不用散落的输出开关替代业务版本 |
| 内容显隐 | ContentVisibilityRule | 不通过手动隐藏文字假装多版本 |
| 插件人工门 | Workbench issue + manual confirmation | 高风险能力必须可见、可确认、可报告 |

UI 上的判定：

- 高频能力不得只藏在自由文本区；
- 共享参数不得换控件、换单位或换命名；
- 场景页不能把模板外观参数误写成场景业务参数；
- 场景页也不能把资料事实源、输出版本、插件边界压成一个普通开关。

## 7. 产品成熟度与准入灯号

V24 建议将每个 pack/family 同时记录两套状态：

| 状态 | 含义 |
| --- | --- |
| static closure | 规划槽位是否已声明、测试是否能静态审计通过 |
| product readiness | 用户是否能在界面、执行、报告、产物、样本中稳定使用 |

建议准入灯号：

| 灯号 | 含义 | 可对用户承诺 |
| --- | --- | --- |
| Gray / L1 | 只有规划 family/schema/profile | 只能显示“规划/边界”，不能作为可用能力 |
| Blue / Boundary | 插件或人工门能力 | 可以解释边界和人工确认，不能承诺核心自动完成 |
| Yellow / L3 | UI 可见配置和摘要 | 可配置，但仍需报告/产物/测试补强 |
| Orange / L4 | 执行、报告、issue、artifact 有证据 | 可作为 first slice 能力，但规则源和真实样本可能仍需确认 |
| Green / L5 | 规则来源、真实样本、迁移、CI、插件/人工边界全闭合 | 可以作为稳定产品能力承诺 |

当前多数 planned family 仍应按 Yellow/Orange 之间谨慎表达。`coverage_packs_with_missing_closures()` 为空，只能说明不再有显式 static closure，不应直接升级为 Green。

## 11. V24 结论

完善的高层场景能力矩阵不应被理解成“列更多场景入口”。更稳的做法是：

```text
稳定 12 个 pack
+ 明确 15 个 planned family
+ 扩展高频请求样本和歧义裁决
+ 用 profile/schema/preset/plugin gate 承载能力
+ 用 Word 风险面和控件契约约束实现
+ 用报告、issue、artifact、样本、测试证明闭环
+ 用 product readiness 防止过度承诺
```

V24 的判断是：

```text
高频不遗漏，靠的不是把导航做大；
靠的是每个常见请求都能被裁决，每个裁决都能被证据链证明，每个边界都不被静默吞掉。
```

下一轮如果继续执行，优先应把 V24 的高频请求样本表和 product readiness 字段落到代码层，让“没有遗漏”和“边界清晰”从文档要求变成自动化审计。
