# 方案格式例外必要性与实际工作流边界深度审计

> 日期：2026-07-29  
> 状态：待产品审阅的决策草案  
> 范围：方案规则中的“格式例外”、模板分区样式、执行期临时调整及交付版本差异  
> 目标：不是继续优化现有页面，而是裁决这项能力是否真的应该存在、以什么形态存在、由哪个对象持有
>
> 前提更新：产品尚未发布，不考虑旧配置兼容。`section_styles`、`template_overrides` 和现有用户副本只作为错误模型证据，不作为保留约束。关于“选取对象是否为章节”的进一步裁决见 `docs/audits/格式例外选取对象与章节模型深度审计_2026-07-29.md`。
>
> **纠偏更新：** 删除方案级视觉样式覆盖的结论不等于“完全交给系统自动识别”。当前文档的语义区域必须在载入后经过“自动识别—用户校正—有效结构确认”闭环；复用识别规则只是一层可选沉淀。完整裁决见 `docs/audits/自动识别与用户定义章节边界深度审计_2026-07-29.md`。

## 0. 执行摘要

### 0.1 最终建议

当前“方案格式例外”的完整视觉样式编辑能力，**不具备继续作为 V1.0 主流程能力保留的必要性**。

推荐裁决如下：

1. **方案层保留分区处理策略，不保留绝对格式值。**
   - 方案可以决定某个分区“套用模板 / 保留原格式 / 不处理”。
   - 方案可以决定是否重建、校验、转换、链接、跳过或阻断。
   - 方案不直接保存字体、字号、行距、缩进、边距、边框等最终视觉值。

2. **模板层保留并公开文档分区样式。**
   - 参考文献、摘要、附录、致谢、个人简历等是模板的语义样式角色。
   - 每个角色可“继承正文”或“自定义”。
   - 这是模板组成部分，不应再称为“例外”。

3. **执行期可以有“仅本次任务调整”，但不是当前方案格式例外的直接平移。**
   - 默认不展开。
   - 只记录实际修改字段。
   - 不自动写回方案或模板。
   - 是否在 V1.0 提供完整样式编辑仍应单独评估；当前没有证据证明必须首发。

4. **首发前直接删除方案级 `section_styles` / `template_overrides`。**
   - 当前没有发布版本，不存在用户升级兼容合同。
   - 当前用户副本是开发期样本，应清理或重建，不需要产品化迁移助手。
   - Resolver、UI、报告和测试应同步删除该错误所有权。

5. **首发版本不预建 PlanTemplateAdapter。**
   - 当前没有真实且不可替代的组合适配案例。
   - 未来出现经过验证的需求时再单独建模。
   - 不能为了假设需求保留当前通用覆盖字段。

### 0.2 一句话裁决

```text
方案负责如何处理，模板负责最终长相，交付预设负责版本差异，
执行会话负责本次偏差；方案不应再拥有一套完整视觉格式。
```

### 0.3 证据强度

| 判断 | 证据强度 | 说明 |
| --- | --- | --- |
| 当前内置方案不依赖分区格式例外 | 高 | 当前 9 个内置方案 `section_styles` 全部为空 |
| 当前通用模板覆盖主要表现为用户副本配置膨胀 | 高 | 两个用户方案副本各有 51 项 `template_overrides`，内置方案均为空 |
| 方案级绝对样式与兼容模板切换冲突 | 高 | 多个方案允许 2～3 个兼容模板，而例外是从当前模板深拷贝的完整 `StyleConfig` |
| 模板已有承载分区样式的能力 | 高 | 论文和标书模板已经包含 `references_body`、`abstract_body` 等角色 |
| 所有真实用户都不需要方案级格式差异 | 未证明 | 当前没有用户遥测或正式访谈数据，不能用仓库样本替代全部用户 |
| V1.0 主路径不应保留完整格式例外编辑器 | 高 | 没有不可替代用例，且存在职责冲突、漂移风险和显著维护成本 |

## 1. 本次审计要回答的不是“好不好用”，而是“是否必要”

此前关于分区样式的审计，主要在既定前提下解决以下问题：

- 如何把“覆盖”改成更容易理解的语言；
- 如何对齐模板管理的样式控件；
- 如何显示“跟随模板 / 独立样式”；
- 如何增加差异预览和批量恢复。

这些工作解决的是：

```text
假设这项能力必须存在，怎样把它做得更一致？
```

本次需要回到更上游的问题：

```text
这项能力是否真的必须存在？
它解决的真实任务是什么？
没有它，用户是否无法完成工作？
已有对象能否更稳定地解决同一问题？
它带来的长期成本是否大于独特价值？
```

因此，本审计可能推翻“继续完善独立样式页面”的方向，但不否定此前实现记录的历史价值。

## 2. 必要性的判定标准

一项进入主流程的产品能力，应同时满足以下条件：

| 维度 | 必须回答的问题 |
| --- | --- |
| 真实频率 | 是否有多次、跨用户或跨模式的真实任务反复需要？ |
| 独特价值 | 是否存在其他对象无法合理承载的需求？ |
| 对象稳定性 | 设置放在这里后，切换其他资源时语义是否仍然稳定？ |
| 可预测性 | 用户能否预测修改影响谁、何时生效、如何恢复？ |
| 可迁移性 | 模板升级、方案复制、版本切换后是否不会静默漂移？ |
| 数据证据 | 内置配置、用户配置或任务记录是否真实使用？ |
| 实现成本 | UI、解析、来源追踪、修复路由和测试成本是否与价值相称？ |
| 替代成本 | 删除后是否需要用户付出明显更高的操作成本？ |

只满足“技术上能实现”或“高级用户可能会用”，不足以证明主流程必要性。

## 3. 当前产品的真实工作流

### 3.1 实际执行链

当前产品不是单纯的 Word 样式编辑器，而是资源装配和执行系统：

```text
选择工作模式
  -> 添加原始文档或结构化输入
  -> 选择处理方案
  -> 选择兼容格式模板
  -> 选择可选卷面 / 版式
  -> 选择或填写资料包
  -> 风险与完整性预检
  -> 冻结资源版本
  -> 执行
  -> 生成一个或多个交付版本
```

对应对象职责应固定为：

| 对象 | 正确职责 | 不应负责 |
| --- | --- | --- |
| 工作模式 | 限定业务域、资源集合和默认入口 | 具体格式值 |
| 方案 | 处理范围、动作、风险、资料契约、交付策略 | 一套完整视觉格式 |
| 模板 | 页面、正文、标题、分区、表格、目录等最终视觉基线 | 本次业务资料和执行风险 |
| 卷面 / 版式 | 固定 DOCX 结构、占位符和装配位置 | 通用处理规则 |
| 资料包 | 字段、图片、附件、内容文件等业务数据 | 格式规则 |
| 交付预设 | 最终版、审阅版、答案版等输出差异 | 输入内容编辑 |
| 执行会话 | 冻结本次选择、版本和临时参数 | 长期替代模板或方案 |

### 3.2 三类用户不是同一条编辑路径

#### 文档经办人

核心任务：

```text
选择现成资源 -> 补齐资料 -> 预检 -> 生成 -> 查看结果
```

他不应为了完成普通任务理解：

- `section_styles`；
- 模板基线和方案快照的合并顺序；
- 为什么“独立样式”开启后还和模板完全相同；
- 模板更新后哪些字段会继续继承。

#### 方案维护者

核心任务：

```text
定义一类文档如何处理、哪些模块运行、遇到风险怎么办、生成哪些版本
```

他需要决定的是行为，不是替模板维护者重新定义参考文献字体。

#### 模板维护者

核心任务：

```text
把单位、学校或项目的视觉规范保存成可复用模板
```

他应该拥有页面、字体、标题、目录、参考文献、摘要、附录等全部最终视觉值。

### 3.3 当前格式例外让三类角色重新混在一起

方案维护者一旦能编辑字体、字号、行距，方案就同时变成：

```text
处理程序
+ 半个格式模板
+ 某个模板时点的样式快照
```

文档经办人则必须理解自己改的是：

- 当前任务；
- 当前方案；
- 当前模板；
- 还是方案相对模板的差异。

这与产品“由浅入深”和职责分离的目标相反。

## 4. 当前配置数据是否证明了必要性

### 4.1 当前方案样本

本次只读扫描 `config_library/plans`：

```text
方案配置总数：11
内置方案：9
用户方案副本：2

section_styles 非空：0
template_overrides 非空：2
```

两个非空 `template_overrides` 均来自用户方案副本，并且各包含 51 项字段：

- `config_library/plans/custom/user/通用-默认方案 副本.json`
- `config_library/plans/official/user/公文基础方案 副本.json`

字段集中在：

- 题注；
- 表格；
- 水印；
- 公式表格；
- 公式样式；
- 公式编号。

这组事实意味着：

1. 当前没有任何落盘方案真实使用 `section_styles`。
2. 当前 9 个内置方案没有通过格式例外表达官方业务差异。
3. 用户方案副本的通用覆盖呈现“整组字段被写入”的特征，不像用户只修改少数必要字段。
4. 现有数据更支持“复制或编辑路径产生配置膨胀”，不支持“格式例外是高频方案能力”。

### 4.2 证据限制

必须同时承认：

- 仓库配置不是完整用户遥测；
- `section_styles` 为空不能证明所有未来用户都不需要；
- 当前用户副本也可能包含真实调整，不能直接删除。

因此正确结论不是“永远禁止一切差异”，而是：

```text
当前证据不足以支撑把完整视觉例外作为普通主流程能力；
边缘需求应先通过受约束模型或迁移入口承载。
```

## 5. 当前模型与真实工作流的结构性冲突

### 5.1 多模板方案与绝对样式快照冲突

当前多个内置方案允许切换兼容模板：

| 方案 | 默认模板 | 兼容模板数量 |
| --- | --- | ---: |
| 标书排版 | `bid_engineering` | 3 |
| 公文基础方案 | `official_gbt` | 2 |
| 通用报告 | `report_default` | 2 |
| 技术文档 | `tech_standard` | 2 |
| 论文排版 | `thesis_gbt` | 2 |

而 `enable_section_style_override()` 的行为是：

```text
读取当前模板有效分区样式
-> 深拷贝完整 StyleConfig
-> 存入 scene.section_styles
```

假设用户在 `thesis_gbt` 上只想修改参考文献字号：

1. 系统复制字体、字号、行距、缩进、段距、对齐等完整样式。
2. 用户只改字号。
3. 用户把模板切换为 `thesis_custom`。
4. `scene.section_styles` 仍然保留旧模板快照。
5. 新模板参考文献样式不能完整接管。

这不是偶发 UI 问题，而是对象关系不成立：

```text
方案被设计为可绑定多个模板，
方案格式例外却隐式绑定创建它时的某个模板版本。
```

如果希望格式例外稳定，只有两个方向：

1. 把方案锁死到一个模板；
2. 把例外改为显式的“方案—模板适配关系”。

第一种会削弱方案和模板独立选择的产品设计；第二种才是正确的关系建模。

### 5.2 完整对象快照不等于字段级差异

当前 UI 显示“已调整 1 项 / 2 项”，但存储的是完整对象。

这会产生两个语义层：

```text
用户以为：我只覆盖字号。
系统实际：我持有一份完整参考文献样式，只是目前只有字号和模板不同。
```

如果模板以后修改了一个用户从未碰过的字段：

- 用户预期：该字段继续跟随模板；
- 当前模型：该字段可能被旧快照冻结。

因此当前实现不能被称为严格的“格式例外”，更准确的名称是“分区样式副本”。

### 5.3 通用优先级声明和实际样式合并不完全一致

`resolve_config()` 先合并：

```text
模板
-> 方案 template_overrides
-> 本次 session_overrides
```

随后又通过：

```python
styles={**merged_template.styles, **copy.deepcopy(scene.section_styles)}
```

把 `scene.section_styles` 覆盖到最终样式。

结果是：

- 通用 `session_overrides` 理论上优先；
- 但同一分区的 `scene.section_styles` 在之后整体覆盖；
- 来源追踪基于前面的通用合并，未完整表达最后这次覆盖。

这使“本次调整 > 方案 > 模板”的简单解释不再可靠。

### 5.4 参考文献存在第三条视觉覆盖链

参考文献最终执行时：

1. 先取 `styles["references_body"]`；
2. 没有时回退到正文；
3. 再应用 `reference_style`；
4. 悬挂缩进最终由 `reference_style.hanging_indent_cm` 强制设置。

因此用户可能在分区样式里修改特殊缩进，但运行时又被参考文献规则覆盖。

这说明当前问题不是缺少更多差异说明，而是同一个最终视觉字段存在多个所有者。

### 5.5 代码和测试扩散不能证明产品必要性

当前与 `section_styles` 相关的代码已扩散到：

```text
17 个 src 文件
19 个 tests 文件
```

覆盖范围包括：

- 配置模型；
- resolver；
- UI 编辑；
- 状态投影；
- Workbench 预览；
- 报告；
- 问题路由；
- 字段定位；
- 导航高亮；
- 多组架构测试。

这说明删除或迁移不能粗暴进行，但不能用“已经实现很多”反向证明它应该继续存在。

已经付出的成本属于沉没成本；必要性应由未来用户价值决定。

## 6. 候选真实用例逐项裁决

### 6.1 学校、单位或客户有特殊参考文献格式

示例：

```text
某大学要求参考文献五号字、固定 16 磅、悬挂缩进 2 字符。
```

正确归属：**模板分区样式**。

理由：

- 这是最终视觉规范；
- 对所有使用该学校模板的论文都应一致；
- 与“论文终稿处理方案”无关；
- 如果学校规范变化，应修改一次模板，而不是逐个方案改例外。

必要性结论：

```text
需要分区样式，但不需要方案格式例外。
```

### 6.2 同一论文需要终稿和盲审稿

差异可能包括：

- 隐藏致谢；
- 隐藏个人简历；
- 添加盲审水印；
- 改文件名；
- 额外生成对比稿或检查报告。

正确归属：**交付预设**。

理由：

- 差异属于输出版本，不属于方案对模板的通用偏离；
- 当前 DeliveryPreset 已有目标模板、内容显隐和产物开关；
- 如果终稿和盲审稿视觉基线确实不同，可分别指定目标模板。

必要性结论：

```text
不需要方案格式例外。
```

### 6.3 某类任务要求附录保留原格式

正确归属：**方案分区处理策略**。

应表达为：

```text
附录：保留原文档格式
```

而不是：

```text
附录：开启独立样式并人工重建一套参数
```

必要性结论：

```text
需要方案级策略，但不需要方案级格式值。
```

### 6.4 某一篇文档临时需要不同字号

正确归属：**执行会话的仅本次调整**。

要求：

- 明确“只影响本次生成”；
- 不自动保存；
- 只记录实际修改字段；
- 运行结束后可选择“保存为新模板”。

必要性结论：

```text
可能需要临时调整，但不应污染长期方案。
```

### 6.5 某方案在某个模板上确实必须偏离

示例：

```text
“期刊投稿检查方案”在“期刊 A 模板”上必须把某个特定结构缩小，
但使用“期刊 B 模板”时不需要。
```

这个需求不是方案自身属性，也不是模板全局属性，而是二者之间的关系：

```text
Plan A + Template A -> adapter patch
Plan A + Template B -> no patch
```

正确归属：**PlanTemplateAdapter**。

必要性结论：

```text
只有出现经过验证且无法用派生模板解决的真实案例时才需要。
当前数据没有证明它必须进入 V1.0 普通入口。
```

### 6.6 每个方案都想有一套自己喜欢的样式

这不是支持格式例外的理由，而是说明用户把方案当成“一键预设包”。

可替代路径：

```text
从方案页点击“基于当前模板创建专用模板”
-> 自动复制模板
-> 用户编辑新模板
-> 将新模板绑定为方案默认模板
```

用户仍然能得到“一套方案对应一套样式”的结果，但对象边界保持清晰。

必要性结论：

```text
需要便捷的派生模板流程，不需要把模板字段塞进方案。
```

### 6.7 开发期方案样本已经有格式覆盖

这些文件尚未进入发布兼容合同，应视为开发期错误模型样本。

必要性结论：

```text
不需要兼容读取或产品化迁移。
在删除错误字段前保留只读审计证据，随后重建开发期用户副本。
```

## 7. 模式化任务中的具体边界

### 7.1 论文版

方案负责：

- 是否处理全文或模板识别区域；
- 标题编号保留还是重建；
- 公式是否转换和规范；
- 引文是否链接；
- 风险项如何处理；
- 生成终稿、审阅稿、报告等版本。

模板负责：

- 页面和页边距；
- 正文和标题；
- 摘要；
- 目录；
- 参考文献；
- 附录、致谢、个人简历；
- 表格和题注；
- 页眉页脚。

学校差异应创建学校模板，而不是学校方案中的格式例外。

### 7.2 公文版

方案负责：

- 公文处理路径；
- 文种 profile；
- 资料字段要求；
- 风险和交付策略。

模板负责：

- GB/T 9704 视觉基线；
- 字体字号；
- 页面；
- 标题、正文、版记等样式。

版式负责：

- 红头；
- 发文机关标志；
- 版记；
- 固定占位符结构。

如果“函”和“纪要”确实有视觉结构差异，应优先进入文种 profile、模板或版式，而不是通用分区例外。

### 7.3 试卷版

方案负责：

- 题目装配；
- 学生卷 / 答案版；
- 题源和图片策略；
- 风险与交付版本。

模板负责：

- 题干、选项、答案、解析等语义样式；
- 字体、字号、段距。

卷面负责：

- 密封线；
- 分数栏；
- 固定页头；
- 答题区结构。

“答案版是否显示答案”属于交付可见性，不属于答案分区格式例外。

### 7.4 标书版

方案负责：

- 资料填入；
- 章节装配；
- 附件和风险策略；
- 正本、副本和资料报告。

模板负责：

- 工程类、采购类等视觉规范；
- 正文、标题、表格、摘要、参考文献等角色。

资料包负责：

- 企业、项目、人员、资质、业绩、图片和附件。

客户视觉差异应形成客户模板或项目模板，而不是标书方案内的完整视觉副本。

## 8. 推荐的目标领域模型

### 8.1 方案

建议模型：

```yaml
Plan:
  mode_id: thesis
  default_template_id: thesis_gbt
  compatible_template_ids:
    - thesis_gbt
    - thesis_custom

  application_boundary:
    mode: follow_detected_structure

  section_treatment:
    body: apply_template
    abstract: apply_template
    references: apply_template
    appendix: preserve_source
    acknowledgment: skip

  actions:
    rebuild_heading_numbering: true
    update_toc: true
    normalize_formula: true
    link_citations: true

  risk_policy: ...
  material_contract: ...
  delivery_presets: ...
```

禁止新增：

```yaml
section_styles:
  references_body:
    font_cn: ...
    size_pt: ...
```

### 8.2 模板

建议模型：

```yaml
Template:
  styles:
    body: ...
    heading1: ...
    abstract_body: ...
    references_body: ...
    appendix_body: ...
    acknowledgment_body: ...
    resume_body: ...
```

产品语言：

```text
正文基线
文档分区样式
  摘要        继承正文 / 自定义
  参考文献    继承正文 / 自定义
  附录        继承正文 / 自定义
  致谢        继承正文 / 自定义
  个人简历    继承正文 / 自定义
```

### 8.3 执行期调整

如果确有必要，使用稀疏字段补丁：

```yaml
ExecutionAdjustments:
  scope: this_run
  base_template_id: thesis_gbt
  base_template_revision: sha256:...
  patches:
    styles.references_body.size_pt: 9
```

规则：

- 默认空；
- 不自动持久化；
- 模板切换后必须清空或重新确认；
- UI 显示“仅本次任务”；
- 可显式转换为新模板。

### 8.4 方案—模板适配

只在真实案例证明必要时增加：

```yaml
PlanTemplateAdapter:
  plan_id: journal_submission
  template_id: journal_a
  template_revision: sha256:...
  reason: "期刊 A 投稿系统要求参考文献区域不超过指定版面"
  patches:
    styles.references_body.size_pt: 9
```

约束：

1. 必须绑定模板版本。
2. 必须是稀疏补丁。
3. 模板版本变化后标记待确认。
4. 切换模板时不能继续生效。
5. UI 必须显示具体组合和影响字段。
6. 不能成为通用 `template_overrides` 的新包装。

## 10. 保留现状的成本

### 10.1 用户成本

- 需要理解模板默认和方案独立样式；
- 不知道切换模板后哪些字段仍来自旧模板；
- 不知道模板更新是否会继续继承；
- 需要在模板管理和方案规则之间来回判断入口；
- “独立但与模板一致”是一种没有直接用户价值的中间状态；
- 参考文献还可能被专用规则再次覆盖。

### 10.2 产品成本

- 方案不再能清楚定义为“处理程序”；
- 模板不再是最终视觉规范的唯一事实源；
- 工作台必须解释多层来源；
- 问题修复必须判断跳方案还是跳模板；
- 每新增一种分区，都要同时考虑模板和方案两套编辑入口。

### 10.3 工程成本

- 双重样式编辑 UI；
- 深拷贝和差异计算；
- resolver 特殊合并；
- provenance 不完整；
- Workbench 差异摘要；
- issue 字段定位和修复路由；
- 报告字段来源；
- 兼容迁移；
- 大量控件和架构测试。

### 10.4 信任成本

最严重的不是操作复杂，而是：

```text
界面显示的来源和最终 Word 结果可能不一致。
```

一旦用户不能预测最终格式来自哪里，产品的“可追溯”和“可解释”价值会被削弱。

## 11. 对保留意见的反向审查

### 11.1 “高级用户需要完全自由”

回应：

- 高级能力仍需有明确对象归属；
- 自由不等于允许同一字段拥有多个隐性所有者；
- 可通过派生模板、本次调整或受约束 adapter 提供自由。

### 11.2 “不放在方案里，会产生很多模板”

回应：

- 多个有清晰名称和版本的模板，比一个方案里隐藏 51 项覆盖更可管理；
- 可提供“基于当前模板创建专用模板”的快捷动作；
- 模板库应支持标签、来源、适用方案和归档，而不是用格式例外减少表面数量。

### 11.3 “方案应该是一键包含全部设置”

回应：

- 方案可以引用默认模板，而不必复制模板内容；
- 一键执行依然成立；
- 引用关系比复制字段更能支持模板升级和版本追踪。

### 11.4 “当前已经有很多测试，删除风险高”

回应：

- 工程删除可以分提交完成，但不需要建立运行时兼容分支；
- 但测试数量只能证明技术耦合，不证明产品价值；
- 应同步删除错误字段、UI、resolver、报告和对应实现测试，再用新模型的行为测试替代。

### 11.5 “未来可能有极少数特殊组合”

回应：

- 当前不预建 `PlanTemplateAdapter`；
- 未来真实任务达到明确证据门槛时再单独设计；
- 不能因为未来可能存在边缘需求，把完整复杂度施加给所有普通用户。

## 12. 方案比较与正式裁决

| 方案 | 内容 | 优点 | 缺点 | 裁决 |
| --- | --- | --- | --- | --- |
| A. 保留现状 | 方案拥有完整分区样式副本 | 灵活、已实现 | 职责冲突、模板切换漂移、复杂度最高 | 拒绝 |
| B. 只改 UI 文案 | 把格式例外改得更易懂 | 改动小 | 不解决数据和优先级问题 | 拒绝 |
| C. 只删除覆盖，不补处理策略 | 方案不再保存视觉值 | 模型简单 | 无法表达保留原格式、不处理等合理方案行为 | 不完整 |
| D. 首发前删除视觉覆盖并重建正确边界 | 方案改成处理策略，视觉回模板，不保留旧字段 | 对象清晰、无兼容债、首发模型干净 | 需要同步删除现有 UI、解析和测试 | **推荐** |
| E. 立即引入通用 Adapter | 所有方案—模板组合都可保存补丁 | 表达关系正确 | V1.0 复杂度仍高，缺少真实需求 | 暂缓 |

正式建议采用 D。

## 13. 发布前清理与重构方案

### P0：删除错误持久化字段

目标：

- 首发配置中不存在方案级视觉样式；
- 不把开发期字段带入正式版本。

动作：

1. 从 `SceneWorkspace` 删除 `section_styles`。
2. 从 `SceneWorkspace` 删除通用 `template_overrides`。
3. 删除配置序列化、字段描述和参数所有权中的对应路径。
4. 重建两个开发期用户方案副本，不迁移其中 51 项覆盖。
5. 加载器遇到这些开发期字段时直接报告配置版本不匹配，不建立长期兼容分支。

### P1：建立正确承载对象

1. 模板管理公开“文档部件样式”。
2. 方案新增正式的区域处理策略。
3. 区域处理只允许：
   - 套用模板；
   - 保留原格式；
   - 不处理；
   - 低置信度时确认。
4. 交付版本继续承载内容显隐、目标模板和产物。
5. 工作台只显示资源绑定和本次调整摘要。

### P2：删除错误解析链和编辑表面

删除：

```text
scene.section_styles 的最终样式覆盖
通用 scene.template_overrides 合并
方案格式例外开关和完整样式编辑器
Workbench 的方案样式差异摘要
方案样式来源报告和修复路由
```

同时把参考文献字体、字号、段距和悬挂缩进统一收回模板文档部件样式。

### P3：建立文档结构识别事实源

1. 定义 `DocumentStructureProfile` 的区域类型和识别规则。
2. 运行时生成带起止位置、置信度和证据的 `DetectedRegion`。
3. 正文章节继续由 HeadingTree / ChapterInventory 表达。
4. 方案区域策略作用于识别结果。
5. 模板样式角色只负责最终视觉值。

### P4：真实文档回归

至少验证：

- 中英文摘要；
- 无标题参考文献；
- 多附录；
- 致谢与正文误识别；
- 多级技术文档章节；
- 多 Word 分节公文；
- 无特殊区域普通报告。

## 14. 验收标准

### 14.1 产品边界

- 方案页不出现完整字体、字号、行距、缩进编辑器。
- 模板管理是完整视觉格式的唯一普通编辑入口。
- 分区处理策略和分区视觉样式不再使用同一套开关。
- 用户能从工作台看到当前方案、模板、版式、资料和交付版本。

### 14.2 模板切换

- 没有 adapter 时，切换兼容模板必须完整切换视觉样式。
- 不得残留旧模板创建时的 `StyleConfig` 快照。
- 有本次调整时，切换模板必须要求清除或重新确认。
- 有 adapter 时，只对绑定的模板版本生效。

### 14.3 配置持久化

- 复制内置方案不会产生 51 项模板覆盖。
- 修改模板不会写入方案。
- 修改方案处理动作不会改动模板。
- 本次调整不会自动写入任何长期资源。
- 保存为新模板时生成清晰的新模板 ID、来源和版本。

### 14.4 执行与追踪

- 每个最终视觉字段能报告来源模板或本次调整。
- 每个处理行为能报告来源方案。
- 每个内容值能报告来源资料包或运行字段。
- 每个输出差异能报告来源交付预设。
- 同一冻结执行会话可以复现相同有效配置。

### 14.5 用户理解

用户无需理解内部实现，也能回答：

1. 当前文档为什么使用这个样式？
2. 修改后会影响本次任务、当前方案还是所有使用该模板的任务？
3. 如果结果不对，应该去方案、模板、资料还是本次任务调整中修复？

## 15. 在决定保留 Adapter 前必须满足的证据门槛

如果后续希望保留“方案—模板格式适配”，至少先收集：

1. 三个真实任务案例；
2. 案例来自至少两个工作模式或两个独立用户；
3. 无法通过派生模板、交付预设、处理策略或本次调整合理解决；
4. 每个案例能说明为什么差异属于 plan + template 关系；
5. 模板切换和模板升级时有明确行为；
6. 用户能在可用性测试中正确预测影响范围；
7. 适配字段数量保持小而稀疏，而不是再次出现整组字段复制。

达不到该门槛时，Adapter 只保留设计预留，不进入产品入口。

## 18. 最终结论

当前产品真正需要的是四种能力：

```text
1. 模板分区样式：定义每类文档结构最终长什么样。
2. 方案分区策略：决定该结构套用模板、保留原样还是不处理。
3. 交付版本差异：决定不同输出包含什么、使用什么目标模板。
4. 执行期偏差：解决仅当前文档的临时特殊情况。
```

当前“方案格式例外”把第 1 和第 4 类问题同时塞进第 2 层，导致：

- 方案不再可独立复用；
- 模板不再是唯一视觉基线；
- 模板切换产生旧样式残留；
- 用户无法预测影响范围；
- resolver 和来源追踪复杂化；
- 代码和测试成本持续扩张。

因此本次必要性裁决为：

```text
不保留方案级完整视觉样式编辑器作为普通产品能力。
首发前删除 section_styles、通用 template_overrides 及其 UI / resolver / 报告链路。
用模板分区样式、方案处理策略、交付预设和本次任务调整分别承接真实需求。
不预建 PlanTemplateAdapter；未来只有真实需求成立时再单独建模。
```
