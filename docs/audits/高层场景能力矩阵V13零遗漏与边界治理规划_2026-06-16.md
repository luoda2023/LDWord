## 2. V13 总判断

当前最大风险已经不是“有没有列出足够多的场景名称”，而是：

```text
场景名称已经基本覆盖高频文档族，
但功能点成熟度、参数归属、执行证据和 UI 控件契约还没有形成统一治理。
```

因此，后续规划不能以“再新增几个入口”作为主要动作。完整能力矩阵应满足：

1. 高频用户说法能唯一落到一个场景包；
2. 场景包能说明它是顶层入口、planning family、profile、schema、preset、模板、会话还是插件；
3. 每个参数都能解释归属层，不在模板、场景、输出、资料包和插件之间漂移；
4. 每条链路都能说清 UI、resolver、scheduler/runtime、pipeline、report、tests 的证据；
5. 每个专业判断或生成质量承诺都必须外置到插件、人工确认或明确“不承诺”边界。

一句话规则：

```text
高频不等于新增入口；
功能点不等于场景参数；
可配置不等于可执行；
可执行不等于专业结论。
```

## 3. 当前代码事实

### 3.1 已经具备的上层承载

`SceneWorkspace` 已经不只是模块开关集合，而是承载了多种上层能力：

| 承载字段 | 当前作用 | 矩阵意义 |
| --- | --- | --- |
| `input_source_profile` | 输入格式、结构化格式、Markdown/LaTeX 策略、资料包要求、缺失策略 | 输入契约与事实源 |
| `compliance_profile` | 规则族、计数 profile、检查范围、对象预检策略、失败策略 | 合规与风险治理 |
| `delivery_presets` | 多版本输出、目标模板、命名、报告、显隐规则、中间产物 | 交付形态 |
| `batch_preset` | 多实体资料和输出目录模板 | 批量生成 |
| `format_scope` | 分区、页码、正文起点、关键词范围 | 范围定位 |
| `template_overrides` / feature configs | 场景级覆盖模板基线 | 业务覆盖版式 |
| `table/header_footer/toc/caption/formula/reference/watermark/output` | 同名模块参数 | 需按参数属性重新归属 |

### 3.2 已经存在的规划层

当前已有：

- 14 个 `PlannedSceneFamily`，包括 `journal_en`、`exam_teaching`、`project_application`、`contract_delivery`、`hr_batch_documents`、`form_batch_documents`、`regulated_disclosure_documents` 等；
- 12 个 `SceneCoveragePack`，覆盖快速规范化、中文学术、英文投稿、试卷教学、标书资料、公文制度、技术长文档、申报报告、合同交付、批量表单、专业披露、导入/AI 边界；
- 10 个 `CapabilityAxis`，包括输入事实源、模板基线、资料 schema、范围结构、内容显隐、计数、对象预检、交付 preset、批量 preset、插件边界；
- MaterialSchema 已覆盖标书、公文、技术、期刊、试卷、申报、合同、HR、会议制度、产品售前、长文档、表单、资质附件、财务报价、专利、双语、披露等资料结构；
- CountProfile 已支持 basic、thesis、journal、bid、application、attachment、contract、exam、bilingual、disclosure、word_xml_full 等口径。

### 3.3 当前主要断层

| 断层 | 表现 | 风险 |
| --- | --- | --- |
| planning family 多、应用少 | `scene_family_application.py` 目前只支持 `contract_delivery` 默认应用 | 大量高频 family 仍停在规划层 |
| coverage pack 有缺口任务，但没有全部进入执行报告 | Workbench 已投影部分矩阵信息，报告证据仍需继续深化 | 用户运行后看不到同一套边界解释 |
| 控件样式规则已有文档，但缺少足够强的架构约束 | ScenePanel 已复用部分模板控件，但仍存在原生 `QCheckBox` 等混用 | 场景页容易长出第二套配置语言 |
| 公式、输出、水印被误认为模板细项 | 实际上它们有明显场景/交付/对象风险属性 | 参数归属漂移，后续 UI 会混乱 |
| 固定版式参数仍未收束 | `TableConfig.row_height_pt` 对应 `w:trHeight`，但此前被当作通用表格参数残留 | 表单/套打场景缺核心能力，普通模板又背负噪音参数 |
| 专业判断边界还不够前台化 | 法律、财务、IP、翻译、AI 内容质量、OCR 无损导入等边界主要在文档/registry 中 | 用户可能误以为核心场景承诺专业结果 |

## 4. 零遗漏矩阵的五层模型

后续任何新需求都必须同时过五层判断。

| 层 | 问题 | 例子 | 失败判定 |
| --- | --- | --- | --- |
| 高频任务层 | 用户自然会怎么说？ | “生成教师版和学生版试卷” | 找不到场景包就是遗漏 |
| 工作流层 | 它本质在做什么？ | 结构化生成、多版本显隐、Word 渲染 | 只按文档类型归类就是边界不清 |
| 承载层 | 该放到哪种对象？ | `exam_teaching` + schema + DeliveryPreset | 只有 UI 入口没有模型就是断链 |
| Word 风险层 | 会碰哪些 OOXML/package 面？ | 表格、公式、图片、域、页眉页脚 | 没有对象策略就是执行风险 |
| 证据层 | UI/执行/报告/测试是否闭合？ | summary、preflight、report、pytest | 无报告或无测试就是原型 |

这个模型比“场景列表”更重要。场景名可能变化，但五层判断必须长期稳定。

## 5. 高频场景包 V13 基线

V13 继续保留 V12 的 12 个 coverage pack，但把它们拆成更清晰的“主场景包 + 子视角 + 不承诺边界”。

| 场景包 | 高频子视角 | 首选承载 | 必须闭合的主工作流 | 不承诺边界 |
| --- | --- | --- | --- | --- |
| 快速 Word 规范化 | 普通报告、已有 docx 清理、通用模板套用 | `report` / `custom` / `technical` / `official` | 模板基线、范围、对象预检、输出报告 | 不判断专业合规 |
| 中文学术 | 学位论文、课程论文、开题、综述 | `thesis`，长期 `thesis_cn` profile | 结构排版、引用、公式、题注、计数 | 不吞英文投稿和试卷 |
| 英文投稿 | manuscript、revision、cover letter、submission package | `journal_en` family | Bib/CSL、section count、display items、投稿包 | 不承诺出版社终版，不自动抓规则 |
| 试卷教学 | 学生版、教师版、答案版、解析版、讲义、答题卡 | `exam_teaching` family | JSON 题源、Markdown 预览、显隐、公式图片、多版本 | 不保证 AI 内容质量，不核心生成复杂图 |
| 标书资料 | 商务投标、政府采购、正副本、资质包、签章 | `bidding` + 资料 schema | 资料填充、附件 inventory、正副本、报告 | 不做投标策略、法律结论、证照真伪 |
| 公文制度 | 通知、函、请示、批复、纪要、制度汇编 | `official` + `meeting_policy_documents` profile | 编号保留、字段、正式/内部稿、归档 | 不把每种行政小文种升顶层入口 |
| 技术长文档 | SOP、规范、接口、手册、验收、书稿/手册合集 | `technical` + `long_document_publishing` | 对象保护、图表公式、章节汇编、变更报告 | 不验证技术真实性，不替代出版系统 |
| 申报报告 | 项目申报、可研、产品白皮书、售前方案、案例包 | `project_application` / `product_sales_documents` / `report` | 资料 schema、字数限制、附件包、交付报告 | 不替代申报系统，不承诺营销文案质量 |
| 合同交付 | 合同、协议、NDA、授权书、承诺函、签署稿 | `contract_delivery` | 字段一致、修订/批注保护、审阅/签署/对比稿 | 不提供法律意见，不判断条款有效 |
| 批量表单 | HR offer/证明/邀请函、固定表单、套打、人员档案 | `hr_batch_documents` / `form_batch_documents` | 人员 schema、固定版位、残留占位符、失败隔离 | 不验证人员或业务数据真实性 |
| 专业披露 | 报价预算、年报 ESG、专利、双语审校、审计格式 | P2 family 或插件 | 表格/附件/术语/长文档 inventory | 不做审计、财务、专利、翻译质量判断 |
| 导入与 AI 边界 | PDF/OCR、完整 LaTeX、AI 内容生成、复杂专业图 | 插件或输入助手 | 低置信度、人工确认、结构化中间产物 | 核心不承诺无损导入和内容质量 |

零遗漏检查规则：

```text
一个需求如果落不进上表任何场景包，才考虑新增 coverage pack；
能落进场景包但闭环不足，只补 family/profile/schema/preset/workflow；
涉及专业判断或外部不确定性，必须优先落到插件边界或人工确认。
```

## 6. 场景能力域 V13

当前 `CapabilityAxis` 的 10 个轴已经能做基础审计，但要支撑“不遗漏 + 边界清晰”，建议在规划语义上扩展为 15 个能力域。代码可分阶段实现，不要求一次性改 manifest。

| 能力域 | 核心问题 | 推荐承载 | 高频场景 |
| --- | --- | --- | --- |
| 输入事实源 | 机器可信数据从哪里来？ | `InputSourceProfile`、schema、structured JSON | 试卷、HR、申报、合同 |
| 结构化生成 | 是否需要从 JSON/AI/Excel 生成文档？ | schema validator、Markdown preview、renderer | 试卷、表单、HR、项目申报 |
| 模板版式基线 | 文档默认长什么样？ | `TemplateConfig` | 所有场景 |
| 场景覆盖策略 | 哪些模板参数可因任务覆盖？ | `template_overrides`、scene feature configs | 公文、标书、合同、表单 |
| 资料与资产 | 字段、图片、签章、附件角色是什么？ | `MaterialSchema`、AssetsPanel | 标书、合同、申报、HR |
| 范围与定位 | 处理哪些章节、页码、Word story？ | `FormatScopeConfig`、CountProfile | 论文、申报、长文档 |
| 结构排版 | 标题、目录、编号、题注、引用如何处理？ | module switches + scheduler | 论文、公文、技术、标书 |
| 固定版式 | 表单/套打/行高/文本框/内容控件如何保护？ | `form_batch_documents`、table/form profile | HR、表单、公文、报价 |
| 公式与专业符号 | LaTeX/OMML/公式编号/化学式如何处理？ | formula profile、plugin boundary | 论文、试卷、技术、投稿 |
| 内容显隐 | 一份事实源如何输出多版本？ | `ContentVisibilityRule`、DeliveryPreset | 试卷、合同、公文、标书 |
| 计数与合规 | Word-like 与规则口径如何并列？ | CountProfile、Validation | 论文、投稿、申报、披露 |
| 对象保护 | 宏、OLE、修订、批注、域、文本框如何处理？ | ObjectPreflightPolicy | 技术、合同、披露、表单 |
| 交付与归档 | 输出哪些文件、报告、zip、manifest？ | DeliveryPreset、OutputConfig | 投稿、标书、申报、合同 |
| 批量与失败隔离 | 多记录、多实体失败如何隔离？ | BatchPreset、batch report | HR、标书、表单、证照包 |
| 插件与人工确认 | 哪些能力不属于核心承诺？ | plugin boundary、manual confirmation | OCR、AI、法律、财务、IP、翻译 |

缺任一关键能力域的场景不能宣称 L3。它最多可以作为 planning family 或 profile 出现。

## 7. 参数归属裁决

后续不要按“这个字段现在在 TemplateConfig 还是 SceneWorkspace”来判断归属，而要按用户任务语义裁决。

| 参数/功能点 | 正确归属 | 模板侧负责 | 场景侧负责 | 插件/人工负责 |
| --- | --- | --- | --- | --- |
| 字体、字号、段距、缩进、页边距 | 模板基线，少量场景覆盖 | 默认外观 | 仅当任务规则要求覆盖 | 无 |
| 左缩进/右缩进/段前/段后控件 | 模板控件体系 | 控件样式、单位、交互 | 场景若暴露覆盖必须复用同款控件 | 无 |
| 特殊缩进 | 模板版式参数 | 无/首行/悬挂切换 | 场景只声明覆盖理由 | 无 |
| 表格样式、边框、列宽 | 模板/场景覆盖 | 默认表格视觉 | 标书/技术/表单的业务覆盖 | 无 |
| 表格行高 `w:trHeight` | 固定版式能力 | 普通模板不应把它当常规噪音参数 | 表单/套打/报价/证书场景明确启用 | 无 |
| 公式样式 | 模板 + 公式场景 | 公式字体、编号表外观 | 公式输入、转换策略、低置信度处理 | 完整 LaTeX/复杂专业转换 |
| 公式内容生成 | 输入/插件 | 无 | 只消费结构化内容 | AI/专业插件 |
| 水印 | 场景/交付状态 + 页眉页脚实现 | 水印外观默认值 | 正式/内部/审阅/保密等业务状态 | 权限/法律效力判断 |
| 输出文件 | 交付 preset | 无 | 版本、命名、报告、zip、manifest | PDF 转换或外部提交系统 |
| 资料字段 | MaterialSchema | 无 | 必填字段、图片角色、附件角色 | 数据真实性 |
| CountProfile | 合规 profile | 无 | 统计口径、范围、报告解释 | 官方系统最终口径 |
| PDF/OCR 导入 | 插件边界 | 无 | 只接收确认后的结构化结果 | OCR、低置信度、人审 |
| AI 内容生成 | 输入助手边界 | 无 | 只校验 schema、预览、渲染 | 内容质量与事实正确性 |

特别说明：

- 公式/输出/水印不应继续被视作“先不管的模板参数”。它们在高层矩阵里都属于场景能力域：公式属于专业内容与输入转换，输出属于交付 preset，水印属于版本/状态/交付策略。
- 表格行高不是通用模板“美化参数”，而是固定版式场景的版位保护能力。后续要么在 `form_batch_documents` 中正式实现并测试 `w:trHeight`，要么从通用模型里退场。

## 8. Word/OOXML 风险面视角

场景矩阵不能只看用户文档名称，还要看会触碰哪些 Word package 面。

| OOXML / package 面 | 相关能力域 | 高频场景 | 必须有的说明 |
| --- | --- | --- | --- |
| `word/document.xml` 段落/run | 结构排版、填充、清理 | 所有场景 | 不破坏 run、字段结果和局部样式 |
| `styles.xml` | 模板版式基线 | 模板、论文、公文 | 模板管理为主，场景只做有理由覆盖 |
| `numbering.xml` | 结构排版 | 公文、论文、长文档 | 保留/重建编号策略必须可见 |
| `w:tbl/w:tr/w:tc` | 表格、固定版式 | 标书、试卷、表单、报价 | 合并单元格、列宽、行高、跨页策略 |
| `w:trHeight` | 固定版式 | 表单、套打、证书、报价 | 只在版位保护场景显式启用 |
| `header*.xml/footer*.xml` | 页眉页脚、水印、页码 | 公文、合同、披露、论文 | 水印和页码的业务状态要进入交付 preset |
| drawing/media relationships | 资料资产、图片题注 | 标书、试卷、技术、产品 | 图片角色、缺图、复制关系完整性 |
| `w:fldSimple` / `instrText` | 域、目录、页码、交叉引用 | 论文、合同、公文 | 更新、保留、跳过策略和报告证据 |
| `comments.xml` | 审阅与对象保护 | 合同、技术、投稿 | 默认保护，不静默删除 |
| tracked changes | 审阅与对象保护 | 合同、披露、公文 | 运行前确认，高风险模块可跳过 |
| `w:txbxContent` / shape | 固定版式、双语、表单 | 表单、证书、公文 | 不粗暴重排，需预检和版位保护 |
| `w:sdt` 内容控件 | 资料填充、固定版式 | 表单、合同、HR | 字段映射、残留占位符、保护策略 |
| footnotes/endnotes | 计数、学术、法律文本 | 论文、投稿、合同 | CountProfile 必须声明是否计入 |
| hidden text | 计数、审阅 | 披露、合同、双语 | 预检和计数口径必须说明 |
| embeddings/OLE | 对象保护 | 技术、财务、披露 | 默认保护/阻断，不当普通表格改写 |
| macros/vba | 安全边界 | 外来模板、合同、表单 | 默认阻断或人工确认 |
| `.rels` external links | 资料资产、附件包 | 图片、附件、嵌入对象 | inventory、缺项、复制和报告 |

只有从 Word 风险面反推能力域，才能避免看似“普通格式化”的场景实际破坏复杂对象。

## 9. 两份外部技术记录的吸收结论

### 9.1 Count Engine 技术记录

应吸收：

- 字数统计必须是 profile-driven multi-metric，而不是单一字数；
- Word-like 统计和学校/期刊/申报规则统计必须并列；
- CountProfile 要声明 included/excluded scopes，例如正文、摘要、参考文献、表格、题注、脚注、尾注、页眉页脚、文本框、批注、修订、隐藏文字、域代码、域结果；
- 报告必须说明“与官方系统口径可能不同”的边界。

矩阵落点：

- `count_profile` 是场景能力域，不是模板参数；
- `thesis_cn`、`journal_en`、`project_application`、`exam_teaching`、`regulated_disclosure_documents` 都必须有独立计数 profile；
- CountProfile 没有来源、版本、范围解释时，不能宣称合规检查闭环。

### 9.2 Exam Generator 技术记录

应吸收：

- 试卷不能由 AI 分别生成学生版/教师版/答案版；
- 唯一事实源应是结构化 JSON，Markdown 只是预览和人工检查层，Word 是正式输出；
- Pydantic/schema validation 是试卷场景进入核心闭环的前置条件；
- 答案、解析、知识点永远留在结构化源里，是否显示由 DeliveryPreset/ContentVisibilityRule 控制；
- 通用图片、公式、题图绑定、图片替换是高频能力；
- 复杂几何图、电路图、化学结构式、AI 生图应进入插件或图片资产边界。

矩阵落点：

- `exam_teaching` 的 first slice 不是“套一个 Word 模板”，而是 `JSON schema -> Markdown preview -> Word template render -> student/teacher/answer presets -> report`；
- `formula` 和 `image_assets` 是试卷 L3 的必需能力，但复杂制图不是核心承诺；
- 试卷结构化生成范式可复用于 HR、表单、申报、合同等“数据到文档”场景。

## 10. 场景配置控件一致性要求

场景配置中的控件样式控制必须继续服从模板管理已经形成的控件语言。它不是审美附属问题，而是防止参数边界混乱的产品规则。

### 10.1 硬性复用规则

| 控件类型 | 场景页要求 | 与模板管理的一致性 |
| --- | --- | --- |
| 下拉选择 | 使用 `StyledComboBox` | 同尺寸、同弹层、同禁用态 |
| 开关 | 使用 `ToggleSwitch` 或共享 `FeatureToggleRow` | 不新建场景专用开关 |
| 多列表单 | 使用 `TemplateFormGrid` / `InspectorForm` | 标签、列距、单位对齐一致 |
| 线性表单 | 使用 `TemplateFormStack` + `template_form_row` | 行高和间距一致 |
| 字体/字号 | 使用 `FontCombo` / `SizeCombo` | 不用普通文本框替代 |
| 间距/缩进 | 使用 `SpacingInput` 或同源单位输入 | 左/右、段前/段后可同排，特殊缩进可切换 |
| 摘要 | 使用 `SummaryGrid` / 共享 summary projection | 摘要来自模型，不手写散落 label |
| 风险提示 | 使用统一 issue/summary/report 模型 | 不用长说明文字占据表单主体 |

### 10.2 场景页暴露版式覆盖时的规则

如果场景页因为业务需要暴露版式参数，必须满足：

1. 控件外观和交互与模板管理同款；
2. 字段命名与模板管理一致，例如“左缩进/右缩进”“段前/段后”“特殊缩进”；
3. UI 必须说明这是“覆盖模板默认值”，而不是另一个模板系统；
4. resolver 和报告必须能说明覆盖来源；
5. 测试要锁定 UI 值能进入 `ResolvedConfig`，并能被执行模块消费。

### 10.3 不允许的做法

- 不允许为了场景语义新建第二套输入框、下拉框、开关样式；
- 不允许把参数解释写成大段说明文字，而不提供可验证控件；
- 不允许 UI 显示可配置，但执行链路不消费；
- 不允许同一参数在模板页和场景页使用不同单位、名称或禁用逻辑；
- 不允许用“高级设置”藏掉业务必需能力，例如试卷显隐、合同对象保护、表单固定行高。

## 11. L3 闭环的验收门槛

一个场景包从规划走到 L3，至少要有以下证据：

| 证据 | 必须内容 | 失败表现 |
| --- | --- | --- |
| 模型证据 | SceneWorkspace / family / schema / profile / preset 有字段 | 只存在 UI 文案 |
| UI 证据 | ScenePanel/Workbench 能看见关键策略和缺口 | 用户不知道当前规则 |
| resolver 证据 | 模板、场景、profile、preset 合并顺序清楚 | 同名参数漂移 |
| 运行前证据 | 资料、对象、输出、插件边界能预检 | 执行后才发现问题 |
| pipeline 证据 | 配置被真实模块消费 | UI 可设但无效果 |
| report 证据 | JSON/Markdown 报告说明边界、跳过、缺失和产物 | 无法追溯 |
| failure 证据 | 缺字段、缺图、低置信度、对象风险、输出冲突有失败路径 | 只测成功路径 |
| test 证据 | 架构、语义、报告、失败路径测试锁定 | 回归不可见 |

L3 的最低标准不是“能跑通一次”，而是“用户、执行器和报告对同一事实达成一致”。

## 12. P0/P1/P2 推进顺序

### 12.1 P0：先补闭环，不扩入口

| 优先级 | 目标 | 原因 |
| --- | --- | --- |
| P0-1 | Workbench 问题队列继续合并输出风险、对象风险、插件边界和报告证据 | 高频执行前必须可见 |
| P0-2 | DeliveryPreset 报告证据完整化 | 输出/水印/多版本不能只停在 UI |
| P0-3 | 场景控件一致性测试 | 防止 ScenePanel 长出第二套控件语言 |
| P0-4 | `contract_delivery` L3 收尾 | 当前已有 first slice，最适合闭环示范 |

### 12.2 P1：高频 family 做 first slice

| family | first slice | 必须先做的闭环 |
| --- | --- | --- |
| `form_batch_documents` | 固定表单字段填充 + `w:trHeight` 版位保护 + 残留扫描 | 行高参数正式归属 |
| `exam_teaching` | JSON 题源 + Markdown 预览 + 学生/教师/答案版输出 | 结构化事实源和显隐规则 |
| `hr_batch_documents` | 人员表格导入 + 一人一份 + 失败隔离报告 | 批量 profile 范式 |

| `bidding` 深化 | 证照附件 inventory + 签章缺失报告 + 正副本 preset | P0 标书资料包成熟化 |

### 12.3 P2：插件边界先于核心承诺

| 边界类 | 策略 |
| --- | --- |
| PDF/OCR | 插件化，低置信度必须人工确认 |
| 完整 LaTeX 工程 | 插件化，核心只支持公式片段/局部结构 |
| AI 内容生成 | 输入助手化，核心只校验结构和渲染 |
| 复杂图形 | 图片资产或学科插件，不进入通用核心 |
| 法律/财务/IP/翻译质量 | 只能做格式、字段、一致性、inventory，不做专业结论 |

## 14. V13 最终结论

```text
高频场景包不漏

+ 参数归属清楚
+ Word 风险面可解释
+ UI 控件语言一致
+ 执行链路消费同一配置
+ 报告呈现同一事实
+ 专业边界前台可见
+ 测试锁定成功与失败路径
```

当前高频大类已经基本有归属。接下来最重要的不是新增顶层导航，而是把 `contract_delivery`、`form_batch_documents`、`exam_teaching`、`hr_batch_documents`、`project_application`、`journal_en` 和 `bidding` 资料包深度化推到 L3。
