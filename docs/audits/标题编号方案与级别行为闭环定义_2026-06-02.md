# 标题编号方案与级别行为闭环定义（2026-06-02）

## 1. 背景

当前“标题编号”面板已经做过一轮 Inspector 化重构，结构上从旧的字段平铺转向了“左侧选择级别，右侧编辑当前级别”。这解决了部分阅读负担，但没有解决更根本的闭环问题：

1. 用户无法合理新增、删除、保存一个“编号方案”或“特定编号行为”。
2. `编号库` 看起来像一个可管理的库，实际只是内置预设下拉。
3. 内置预设大多只定义到 4 级，5-8 级虽然 UI 能显示，但语义来自临时默认值。
4. UI 暴露了 `start_at` 等行为字段，但执行层没有完全兑现。
5. 深层标题如果不是 Word 标题样式，识别层文本启发式基本只覆盖到 4 级。

因此，这次要闭环的不是“再调 UI”，而是重新定义标题编号的产品对象、数据边界、交互语义和执行语义。

---

## 2. 当前事实

### 2.1 数据模型已经有 8 级基础

`HeadingModelConfig` 默认包含：

- `level_to_word_style`: `heading1` 到 `heading8`
- `style_alias_to_level`: 中文一级到八级标题
- `max_heading_levels`: 默认 4

这说明底层模型并非只能支持 4 级。

### 2.2 UI 允许调到 8 级

标题编号面板的“最大级数”控件范围为 1-8。用户把最大级数调到 5、6、7、8 时，左侧级别列表会增加。

### 2.3 内置预设没有完整定义 1-8 级

当前 `heading_presets.py` 中：

- `thesis_standard` 只定义到 4 级
- `arabic_dot` 只定义到 4 级
- `cn_chapter` 只定义到 4 级
- `roman` 只定义到 4 级
- `none` 定义到 8 级

当用户把最大级数扩展到 5-8，adapter 会自动补出默认绑定：

- enabled: true
- display_core_style: arabic
- reference_core_style: arabic
- chain: 包含所有上级
- chain_separator: `.`

这个默认值在技术文档里可能勉强合理，但在论文、中文章节、公文等方案中不一定合理。

### 2.4 保存不是保存编号方案

当前面板顶部“保存”最终触发的是整份模板保存。它不是：

- 保存当前级别行为
- 保存当前编号方案
- 保存用户自定义编号库条目

因此用户看到“编号库 + 保存”时，会自然期待“把当前编号配置保存到库里”，但实际并非如此。

### 2.5 执行层没有兑现全部字段

执行模块当前按 `counters[level] += 1` 计数，并在更深层归零。它没有使用：

- `start_at`
- `restart_on`

这会造成 UI 与实际输出语义不一致。

### 2.6 识别层深层级并不完整

标题识别优先使用 Word 样式和 outline level，可以识别深层标题。但文本正则启发式只覆盖到 4 级左右：

- `1.1.1.1`
- `1)`
- `a)`
- 中文章/节/一、/（一）

如果文档里的 5-8 级标题没有 Word 标题样式，仅靠文本形态并不可靠。

---

## 3. 核心判断

标题编号功能至少包含四个层级：

1. **标题识别**：找到哪些段落是标题，以及它们是几级。
2. **编号方案**：定义一套标题层级应该如何编号。
3. **级别行为**：定义某一级如何显示、引用、进目录、起始计数。
4. **模板保存**：把当前模板整体持久化。

当前界面把第 2、3、4 层混在一起，导致用户无法判断：

- 我是在改当前模板，还是在改编号库？
- 我能不能把这套编号保存起来？
- 我能不能只保存某一级的行为？
- 我删除的是一个级别、一个规则，还是一个方案？
- 我调到 6 级后，第 5、6 级从哪里来的？

闭环方案必须先拆清这四层。

---

## 4. 非目标

本轮不建议立刻做以下事情：

1. 不把 `heading_presets.py` 直接改成用户可写代码文件。
2. 不恢复旧的“简单 / 组合 / 专家”顶层模式切换。
3. 不用纯视觉卡片化掩盖对象定义不清的问题。
4. 不在执行层未兑现前继续暴露更多虚假行为字段。
5. 不把标题识别、编号方案、模板保存混成一个“保存”按钮。

---

## 5. 对象定义

### 5.1 编号方案 HeadingNumberingScheme

编号方案是一套可复用的标题编号规则。

建议字段：

| 字段 | 含义 |
|---|---|
| `scheme_id` | 稳定 ID，用户方案可自动生成 |
| `name` | 显示名称 |
| `source` | `builtin` / `user` |
| `max_levels` | 该方案默认启用到几级 |
| `supported_levels` | 该方案完整定义到几级，建议固定为 8 |
| `level_bindings` | `heading1` 到 `heading8` 的绑定 |
| `created_at` | 用户方案创建时间，可选 |
| `updated_at` | 用户方案更新时间，可选 |
| `description` | 方案说明，可选 |

关键约束：

- 内置方案只读。
- 用户方案可新增、重命名、删除、覆盖保存。
- 每个方案必须完整定义 `heading1` 到 `heading8`。
- `max_levels` 只是默认启用级数，不代表方案只支持这些级别。

### 5.2 级别行为 HeadingLevelBehavior

级别行为是某一级标题的编号规则。

它对应当前 `HeadingLevelBindingConfig`，但产品语义需要更明确：

| 字段 | 产品语义 |
|---|---|
| `enabled` | 当前级是否显示编号 |
| `display_template` | 编号最终表达式 |
| `display_core_style` | 当前级计数的显示样式 |
| `reference_core_style` | 被下级链式引用时的样式 |
| `chain` | 是否包含上级编号 |
| `chain_separator` | 多级编号之间的分隔符 |
| `title_separator` | 编号和标题正文之间的分隔符 |
| `include_in_toc` | 是否进入目录 |
| `start_at` | 本级第一次出现时从几开始 |
| `restart_on` | 本级何时重启计数 |

关键约束：

- `enabled=false` 不等于删除级别，只是不显示编号。
- `include_in_toc=false` 不等于不是标题，只是不进入目录。
- `start_at` 必须由执行层兑现，否则 UI 不应强调它。
- `restart_on` 当前没有 UI，也没有执行兑现，应暂时归入待实现高级行为。

### 5.3 标题模型 HeadingModel

标题模型不是编号方案本身。它负责：

- Word 样式到标题级别的映射。
- 非编号标题的识别规则。
- 最大标题层级。

建议把 `max_heading_levels` 与编号方案的 `max_levels` 建立同步规则：

- 应用编号方案时，默认把 `heading_model.max_heading_levels` 设置为方案的 `max_levels`。
- 用户手动改变最大级数时，不改变方案定义，只改变当前模板启用范围。
- 当前启用范围超过方案默认时，使用方案中已定义的深层级规则，而不是临时生成泛化规则。

### 5.4 模板 TemplateConfig

模板保存仍然是整份模板保存。

它应该回答：

- 当前文档最终使用什么配置？
- 当前场景绑定什么模板？
- 当前模板是否 dirty？

它不应该承担“编号方案库管理”的语义。

## 6. 编号方案库定义

### 6.1 为什么需要方案库

用户的真实任务不是只改一次当前模板，而是：

- 我有一套论文标题编号习惯。
- 我想把它保存下来。
- 下次换模板或换文档还能套用。
- 我想删除不再使用的自定义方案。

这要求存在一个独立于当前模板的方案库。

### 6.2 存储边界

推荐新增用户可写目录：

```text
templates/
scenes/
heading_numbering_schemes/
```

或：

```text
presets/heading_numbering/
```

建议优先使用 `heading_numbering_schemes/`，因为它与模板、场景同级，更符合“配置库”的语义。

### 6.3 内置与用户方案

内置方案来源：

- Python 内置目录或种子 JSON。
- 只读。
- 用于初始选择和重置。

用户方案来源：

- JSON 文件。
- 可新增、覆盖、重命名、删除。
- 应在 UI 中明确标记“自定义”或“用户方案”。

### 6.4 方案 ID

建议规则：

- 内置：`builtin.thesis_standard`
- 用户：`user.my_thesis_numbering`

显示名称可重复，但 ID 不应重复。若重名，UI 显示 `名称 (2)` 或要求用户重命名。

## 7. 1-8 级规则定义

### 7.1 原则

每个方案必须完整定义 8 级，即使默认只启用前 4 级。

这样用户从 4 级扩展到 5、6、7、8 时，行为来自当前方案，而不是来自 adapter 的兜底猜测。

### 7.2 推荐内置方案

#### 方案 A：论文标准

默认启用：4 级
完整定义：8 级

| 级别 | 显示建议 | chain |
|---|---|---|
| 1 | `第{cn}章` | current_only |
| 2 | `{chain}` | parent.current |
| 3 | `{cn}、` 或 `（{cn}）` | current_only |
| 4 | `{nn})` | current_only |
| 5 | `（{nn}）` | current_only |
| 6 | `{cc}` | current_only |
| 7 | `{al})` | current_only |
| 8 | `{AL})` | current_only |

说明：

- 论文深层级通常不应无限链成 `1.1.1.1.1.1`。
- 5-8 级更适合使用局部短编号。
- 如果用户选择“纯数字链式”，应切换到另一套方案。

#### 方案 B：纯数字层级

默认启用：4 级
完整定义：8 级

| 级别 | 显示建议 | chain |
|---|---|---|
| 1 | `{nn}` | current_only |
| 2 | `{chain}` | parent.current |
| 3 | `{chain}` | parent.parent.current |
| 4 | `{chain}` | parent.parent.parent.current |
| 5 | `{chain}` | parent x4 + current |
| 6 | `{chain}` | parent x5 + current |
| 7 | `{chain}` | parent x6 + current |
| 8 | `{chain}` | parent x7 + current |

说明：

- 这是技术文档、手册、规范类最自然的深层级方案。
- 当前 adapter 兜底行为只适合这类方案，不适合所有方案。

#### 方案 C：中文章节

默认启用：4 级
完整定义：8 级

| 级别 | 显示建议 | chain |
|---|---|---|
| 1 | `第{cn}章` | current_only |
| 2 | `第{cn}节` | current_only |
| 3 | `{cn}、` | current_only |
| 4 | `（{cn}）` | current_only |
| 5 | `{nn}.` | current_only |
| 6 | `（{nn}）` | current_only |
| 7 | `{cc}` | current_only |
| 8 | `{al})` | current_only |

说明：

- 中文章节方案强调汉语层级表达。
- 不建议 5 级以后突然变成全链式 `1.1.1.1.1`。

#### 方案 D：罗马编号

默认启用：3 或 4 级
完整定义：8 级

| 级别 | 显示建议 | chain |
|---|---|---|
| 1 | `{RN}` | current_only |
| 2 | `{nn}` | parent.current |
| 3 | `{nn}` | parent.parent.current |
| 4 | `{nn}` | parent.parent.parent.current |
| 5 | `{al})` | current_only |
| 6 | `{AL})` | current_only |
| 7 | `{cc}` | current_only |
| 8 | `{nn})` | current_only |

说明：

- 需要避免罗马数字在深层级里过长。

#### 方案 E：无编号

默认启用：8 级
完整定义：8 级

| 级别 | enabled |
|---|---|
| 1-8 | false |

说明：

- 仍然保留标题样式和 outline level。
- 不添加编号。

## 8. 用户交互闭环

### 8.1 顶部方案区

当前“编号库”应改成真正的方案管理区。

建议结构：

```text
编号方案
[方案下拉] [另存为] [重命名] [删除]
最大级数 [4] 级
```

行为：

- 选择方案：应用方案到当前模板。
- 另存为：把当前模板中的标题编号规则保存为用户方案。
- 重命名：只对用户方案可用。
- 删除：只对用户方案可用。
- 内置方案删除按钮禁用，并提示“内置方案不可删除”。

### 8.2 保存按钮语义

需要拆成两类：

1. **保存模板**
   - 保存当前模板配置。
   - 影响页面、正文、表格、目录、题注等所有设置。

2. **保存为编号方案**
   - 只保存标题编号相关规则。
   - 不保存页面边距、正文样式、表格等模板内容。

建议 UI 文案避免只写“保存”：

- 顶部模板动作：`保存模板`
- 方案动作：`另存为编号方案`
- 用户方案覆盖：`更新此方案`

### 8.3 新增级别

不建议让用户在中间随意插入级别。

推荐：

- 主路径：通过“最大级数”增加末尾级别。
- 当从 4 调到 5：启用 heading5，采用当前方案中的 heading5 规则。
- 当从 5 调回 4：不删除 heading5 配置，只是不在当前模板启用范围内。

原因：

- 标题级别是 Word 固定语义，heading1-heading8 不是普通列表项。
- 中间插入会导致后续层级重排，风险很高。

### 8.4 删除级别

不建议提供“删除任意级别”作为普通操作。

推荐定义：

- `减少最大级数`：隐藏末尾级别，不删除配置。
- `停用本级编号`：保留标题级别和样式，但不显示编号。
- `重置本级`：恢复到当前方案默认。

高级操作可选：

- `清除本级自定义规则`
- `删除用户方案`

### 8.5 保存当前级别行为

“保存特定编号行为”有两种理解，必须明确：

1. 保存某一级的行为片段，比如“第 X 章”这种单级规则。
2. 保存整套 1-N 级方案。

建议第一阶段只支持第二种。原因：

- 单级行为脱离上下级 chain 后容易失去上下文。
- 用户真正复用的通常是整套层级规则。
- 单级行为库会引入更多概念负担。

如果未来要做单级行为库，应命名为“级别样式片段”，不要混入“编号方案”。

## 9. 执行语义闭环

### 9.1 `start_at`

当前 UI 已暴露 `start_at`，执行层必须兑现。

建议语义：

- 每个 level 第一次计数时，从 `start_at` 开始。
- 如果 `start_at=1`，行为与现状一致。
- 如果 `start_at=0`，第一个标题显示 0。
- 子级重启时，也按子级自身 `start_at` 重置。

伪逻辑：

```text
if first heading at level:
    counters[level] = start_at
else:
    counters[level] += 1

after counting level:
    for deeper level:
        counters[deeper] = unset
```

注意：

- 不应初始化为 0 再 `+= 1`，否则无法表达 `start_at=0` 或 `start_at=3`。

### 9.2 `restart_on`

建议先定义，但不急于 UI 暴露。

可选值：

| 值 | 含义 |
|---|---|
| `parent` | 遇到上一级标题时重启 |
| `heading1` | 遇到一级标题时重启 |
| `section` | 遇到文档分区时重启 |
| `never` | 全文连续 |

默认行为：

- 子级默认随父级重启。
- 一级标题默认全文连续。

当前实现已经在遇到某一级标题后清零更深层级，因此“子级随父级重启”基本存在，但需要和 `start_at` 结合。

### 9.3 编号生成方式

当前实现是纯文本前缀，不是 Word 原生多级列表编号。

这意味着：

- 输出可控。
- 但不能自动参与 Word 的原生编号更新。
- 交叉引用目前更多是显示样式语义，而非真实 Word REF 编号域。

UI 文案不能暗示“Word 原生多级列表”能力，除非后续实现 OOXML numbering。

### 9.4 `include_in_toc`

当前标题编号模块只设置 outline level，不负责 TOC 过滤。后续必须确认目录模块是否实际读取每级 `include_in_toc`。

如果目录模块不读取，UI 中“计入目录”同样会成为虚假承诺。

验收必须覆盖：

- 某一级 `include_in_toc=false`
- 原生目录或 plain 目录不包含该级
- 但正文仍保留标题样式和编号

## 10. 识别语义闭环

### 10.1 当前识别路径

标题识别来源包括：

1. Word 样式：`Heading 1` 到 `Heading 9`
2. outline level：0-8
3. 文本正则 + 视觉特征

深层级最稳定的是前两种。

产品层仍建议把编号方案上限定义为 1-8 级。若识别到 Word `Heading 9`，应作为超出当前方案范围的标题处理：保留大纲语义，不自动纳入编号方案。

### 10.2 深层文本识别问题

如果用户文档里的 5-8 级标题只是普通正文加手写编号，例如：

- `1.1.1.1.1 标题`
- `（1）标题`
- `① 标题`
- `a) 标题`

当前识别并不完整，且容易误判正文列表。

### 10.3 产品定义

建议明确：

- 1-4 级：允许文本启发式辅助识别。
- 5-8 级：优先依赖 Word 标题样式或 outline level。
- 如果要支持 5-8 级纯文本识别，需要新增更严格规则，并结合视觉特征、上下文层级、段落长度、正文标点排除。

### 10.4 UI 提示

当最大级数超过 4 时，面板应提示：

```text
5 级及更深标题建议先在文档中使用 Word 标题样式，否则可能无法稳定识别。
```

这个提示比单纯增加更多正则更可靠。

## 11. UI 信息架构

### 11.1 顶部概览

保留三块：

- 当前方案
- 最大级数
- 特殊规则

但“当前方案”应显示来源：

```text
论文标准（内置）
自定义论文编号（用户）
当前模板自定义（未保存为方案）
```

### 11.2 编号方案区

建议替代当前单一下拉：

```text
编号方案
[论文标准（内置） v]
[应用] [另存为方案] [更新方案] [删除]
```

状态规则：

| 当前状态 | 应用 | 另存为 | 更新方案 | 删除 |
|---|---|---|---|---|
| 内置方案完全匹配 | 禁用或无变化 | 可用 | 禁用 | 禁用 |
| 内置方案已修改 | 可恢复应用 | 可用 | 禁用 | 禁用 |
| 用户方案完全匹配 | 禁用或无变化 | 可用 | 可用 | 可用 |
| 用户方案已修改 | 可恢复应用 | 可用 | 可用 | 可用 |
| 未匹配任何方案 | 可选择后应用 | 可用 | 禁用 | 禁用 |

### 11.3 级别导航

左侧只保留：

- 级别编号
- 当前编号预览
- 轻量状态：启用/停用、目录/不进目录、自定义/继承

不显示完整样式摘要。

### 11.4 当前级别 Inspector

右侧顺序保持：

1. 结果预览
2. 编号组成
3. 输出与衔接
4. 标题样式
5. 模板表达式

新增两个动作：

- `重置本级为方案默认`
- `复制本级规则到...` 可作为后续增强

不要在普通区放“删除本级”。级别不是可删除普通项。

### 11.5 非编号标题区

它属于标题模型规则，不是编号方案核心。

建议在 UI 上改名为：

```text
不编号标题
```

而不是“特殊规则”。并明确：

- 这些标题仍可作为标题样式处理。
- 它们不会添加编号。
- 是否进入目录需要另行定义，不能默认混同。

## 12. 数据边界

### 12.1 当前模板中的字段

继续保留：

```text
template.heading_numbering.level_bindings
template.heading_model.max_heading_levels
template.heading_model.non_numbered_title_texts
template.heading_model.non_numbered_prefixes
template.styles.headingN
```

### 12.2 用户方案文件

建议文件格式：

```json
{
  "scheme_id": "user.my_thesis_numbering",
  "name": "我的论文编号",
  "source": "user",
  "max_levels": 4,
  "supported_levels": 8,
  "level_bindings": {
    "heading1": {},
    "heading2": {},
    "heading3": {},
    "heading4": {},
    "heading5": {},
    "heading6": {},
    "heading7": {},
    "heading8": {}
  }
}
```

### 12.3 是否包含标题样式

第一阶段不建议编号方案包含字体、字号、行距等标题样式。

原因：

- 编号方案回答“编号怎么长”。
- 标题样式回答“标题文字怎么排版”。
- 混在一起会导致用户应用编号方案时意外改变字体。

如果未来要做“标题编号 + 标题样式”的组合，应命名为“标题体系模板”，不要叫编号方案。

### 12.4 是否包含非编号标题

有两种选择：

1. 不包含，非编号标题只属于模板的 heading_model。
2. 可选包含，作为方案的 `skip_rules`。

建议第一阶段不包含。理由：

- 参考文献、摘要、目录这类规则更像模板/场景语义。
- 编号方案应尽量保持纯粹。

但 UI 可以提供提示：保存编号方案时不保存“不编号标题”列表。

## 13. 状态机

### 13.1 方案匹配状态

| 状态 | 含义 |
|---|---|
| `builtin_exact` | 当前模板规则与某个内置方案完全一致 |
| `builtin_modified` | 来源于内置方案，但已经改动 |
| `user_exact` | 当前模板规则与某个用户方案完全一致 |
| `user_modified` | 来源于用户方案，但已经改动 |
| `custom_unsaved` | 与任何方案都不匹配 |

当前 adapter 只有 `detect_active_preset()` 和 `_last_applied_preset_key`，不足以完整表达这些状态。

需要新增状态来源：

- 当前应用过的 `scheme_id`
- 当前规则是否与该 scheme 匹配
- 当前规则是否与其他 scheme 匹配
- scheme 是否可写

### 13.2 级别状态

| 状态 | 含义 |
|---|---|
| `scheme_default` | 本级与当前方案默认一致 |
| `level_modified` | 本级编号行为已自定义 |
| `disabled` | 本级编号关闭 |
| `out_of_active_range` | 超出当前最大级数，但方案中仍有定义 |

左侧导航可以显示这些状态，但不应让用户在导航里直接完成复杂操作。

## 14. 验收标准

### 14.1 方案库

- 可以列出内置方案和用户方案。
- 内置方案不能删除、不能覆盖保存。
- 用户方案可以新增、重命名、删除、覆盖保存。
- “另存为编号方案”不保存正文样式、页面设置、表格配置。
- 应用方案会更新当前模板的 `heading_numbering.level_bindings` 和 `heading_model.max_heading_levels`。

### 14.2 1-8 级

- 每个内置方案都定义 heading1-heading8。
- 最大级数从 4 调到 8 时，5-8 级来自当前方案。
- 最大级数从 8 调回 4 时，5-8 级规则不丢失。
- 纯数字方案第 8 级可以预览为 `1.1.1.1.1.1.1.1`。
- 论文标准方案第 5-8 级不会退化成纯数字全链路，除非方案明确如此。

### 14.3 执行层

- `start_at=3` 时，本级第一个标题从 3 开始。
- 父级变化后，子级按自己的 `start_at` 重启。
- 禁用编号的级别不添加编号，但仍设置 outline level。
- 超出最大级数的标题不编号，但保留 outline level。
- 非编号标题不添加编号。

### 14.4 识别层

- Word `Heading 5` 到 `Heading 8` 可以被识别并编号。
- outline level 4-7 可以映射到 heading5-heading8。
- 纯文本 5-8 级若暂不支持，UI 必须有提示。

### 14.5 UI

- 用户能区分“保存模板”和“保存编号方案”。
- 删除动作只删除用户方案，不删除标题级别。
- 当前方案来源清楚显示为内置、用户、当前模板自定义。
- 当前级别可重置为方案默认。

## 15. 推荐实施阶段

### Phase 1：定义闭环，不改执行大结构

目标：

- 让 1-8 级方案完整。
- 让 UI 语义不再误导。

3. 将“编号库”文案调整为“编号方案”。
4. 明确“保存模板”和“另存为编号方案”的边界。
5. 对 5 级以上增加识别提示。

### Phase 2：用户方案库

目标：

- 用户可以真正新增、删除、保存编号方案。

动作：

1. 新增 `heading_numbering_schemes/` 配置目录。

3. 支持用户方案新增、重命名、删除。
4. 面板状态区显示方案来源与是否已修改。

- UI 暴露字段和输出结果一致。

4. 补充 1-8 级编号输出测试。

### Phase 4：深层识别增强

目标：

3. 补充误判测试。

## 16. 最终定义

标题编号面板不应被定义为“模板里的一个设置页”，而应定义为：

> 一个用于选择、管理和应用标题编号方案，并检查每一级编号行为的 Inspector。

闭环后的用户心智应该是：

1. 我先选一套编号方案。
2. 我可以调最大级数，但每一级都有清楚规则。
3. 我可以编辑某一级的编号行为。
4. 我可以把整套规则另存为自己的编号方案。
5. 我可以删除自己的方案，但不能删除内置方案。
6. 保存模板和保存编号方案是两件事。
7. 实际输出会兑现界面里承诺的行为。

只有这七点同时成立，标题编号才算真正闭环。
