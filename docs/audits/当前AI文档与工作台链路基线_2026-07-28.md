# 当前 AI 文档与工作台链路基线

> 日期：2026-07-28  
> 状态：当前实现事实的唯一基线  
> 范围：AI 文档助手、快速执行、批量生成、资料包预览、Provider 配置

## 1. 结论

当前实现已经形成三条可解释的产品链路：

1. **AI 文档助手**是独立一级功能，有自己的首页、会话面板和任务记录，不再挂靠工作台中的某个按钮。
2. **快速执行**负责单份文档生成，资料、方案、模板、输出目录和执行反馈均有真实状态来源。
3. **批量生成**负责用同一方案与模板处理多份资料，批次选择、隔离输出、失败重试和取消有实际执行语义。

本轮审阅没有发现“只剩视觉壳、点击后没有后端”的主链路问题。但代码仍处于**可用、可继续收敛，尚不适合直接发布**的状态。最大发布风险不是单个页面，而是工作区存在大量混合修改和未跟踪文件，无法证明一个可复现、可回滚的交付边界。

## 2. 能力边界：明确有什么，也明确没有什么

### 2.1 已实现

- Assistant 在 `PanelRegistry` 中作为独立一级面板注册。
- Assistant 首页负责创建任务；活动会话负责需求确认、生成计划、执行审批、执行反馈和产物交付。
- Provider 使用 OpenAI-compatible Chat Completions 文本接口；支持本地演示配置和远程 Provider 配置。
- API Key 通过凭据引用读取，不把明文密钥写进普通配置对象。
- AI 回复不会直接绕过 Form 执行层写文档。实际链路为：

```text
用户输入
  -> Provider 文本流
  -> Assistant 查询/意图解析
  -> 本地文档计划与执行前检查
  -> 用户确认或审批
  -> Workbench/Form 执行会话
  -> DOCX 产物与执行回执
```

- 快速执行的资料上下文以 `PanelBridge.current_material_context()` 为唯一执行来源。
- 资料包卡片展示的是编辑中的 `MaterialPreviewSnapshot`，用于实时预览；真正执行时使用冻结的 `MaterialExecutionContext`，两者职责不同。
- 批量生成的资料由 Assets 批次选择链路提供；批量页不再伪造“准备资料”入口。
- 批量页不再保留仅供测试读取的隐藏 QLabel，也不再用多个别名指向同一个执行状态控件。

### 2.2 未实现，不应在界面或文档中暗示已经实现

- 没有移植 Alavette Flow 的原生 Tool Call 运行时。
- 没有完整接入 Memory、Skills、Web 搜索、委托代理等 Flow 能力。
- Provider 的“连接成功”只代表已执行过文本流测试，不代表持续在线健康检查。
- UI 借鉴 Alavette Design 的交互与视觉语言，但不是对参考项目的逐文件复制，也不存在对参考项目的运行时依赖。

因此，当前产品应表述为“AI 辅助确认需求并调用现有文档执行链路”，不应表述为“完整移植 Alavette Flow”。

## 3. 状态所有权

| 状态 | 唯一所有者 | 消费方 | 约束 |
|---|---|---|---|
| 当前资料执行上下文 | `PanelBridge` | 快速执行、执行会话、兼容资料编辑页 | 执行不得读取某个页面的私有缓存 |
| 资料包实时预览 | `MaterialPreviewSnapshot` | 快速执行资料预览卡 | 只展示，不作为冻结执行输入 |
| Assets 编辑态到预览快照的转换 | `material_preview_projection.py` | Assets 摘要 Presenter | 纯投影，不依赖 Qt 或控件 |
| Provider 状态与错误文案 | `provider_presentation.py` | Assistant、偏好设置 | 两处界面不得各自维护错误映射 |
| 单次执行生命周期 | `WorkbenchExecutionSessionController` | Workbench | 负责构建、启动、取消和清理 Worker |
| 批次资料选择 | `MaterialBatchSelection` / `PanelBridge` | 批量生成 | 资料准备在 Assets 中完成 |

## 4. UI 与交互完整性

### 4.1 Assistant 一级功能

- 一级入口只表示“AI 文档助手”，不与快速执行混为同一页面。
- Assistant 内部侧栏只保留有闭环的会话能力：新建、置顶、最近任务等。
- 项目、计划、长期记忆、技能中心等未形成真实闭环的入口不应恢复。
- 首页的大输入框是任务创建入口；任务创建后进入独立活动会话，不应在首页卡片内部继续堆执行表单。

### 4.2 快速执行

- 顶部文件选择区负责 DOCX 输入。
- “处理方案与模板”卡片显示并允许切换真实绑定。
- 资料包预览使用紧凑卡片，只展示识别当前资料所必需的信息：
  - 资料包/档案名称；
  - 当前档案或对象；
  - 已填字段数量；
  - 图片、内容资料、附件数量；
  - 冲突或缺失状态。
- 默认状态不展示说明性大段文字，也不使用仅靠 Hover 才能理解的关键内容。
- 输出目录与执行反馈保持独立卡片，避免一个区域同时承担输入、说明和状态。

### 4.3 批量生成

- 它是工作台中的二级功能，与快速执行共享控件、卡片、间距和反馈的视觉语法。
- 两个页面不要求总高度完全一致。快速执行多一个实时资料预览卡，强行等高会引入无意义占位。
- 批量页不提供“准备或调整批次资料”按钮；空状态只说明应先在资料功能中选择批次。
- 批次页允许单独选择共用源文档、方案、模板和输出位置。
- 可执行性由真实批次资料和规则决定；按钮禁用时必须能从当前页面状态理解原因。

## 5. 本轮代码审阅后的收敛

### 5.1 已处理

- 修正快速执行与批量生成“必须整体等高”的错误视觉测试，改为验证共享的控件与卡片语法。
- 抽出 Provider 状态和错误映射，消除 Assistant 与偏好设置两份实现。
- 抽出 Assets 编辑态到资料预览快照的纯投影，Presenter 不再直接承担规范化规则。
- 单次执行改为读取 Bridge 权威资料状态，消除隐藏页面缓存成为执行事实源的风险。
- 删除批量页隐藏语义 QLabel 和状态兼容别名，测试改为公开语义接口。
- 增加架构门禁，限制大型 UI 协调类继续增长，并防止上述重复逻辑回流。

### 5.2 尚存技术债

以下问题没有通过伪装成“已完成”来关闭：

- `AssistantPanel`、`AssistantCreativeHome`、`QuickExecutionDetail`、`WorkbenchPanel` 和 `BatchGenerationDetail` 仍是大型协调类。
- AssetsPanel 通过多个 Presenter/Mixin 拆分职责，虽然主文件不算巨大，但生命周期和私有字段耦合仍较高。
- 一部分测试仍直接读取控件私有成员，导致重构成本偏高。
- 历史审计文档采用追加记录，包含已经失效的阶段性判断。

当前策略是先设置**方法数量不增长**的架构门禁。后续新增能力必须抽到 Presenter、Controller 或领域服务，而不是继续往大型类里加方法。

## 10. 2026-07-28：Assistant 顶层能力契约与试卷链路闭环

> 本节是对第 2 节“统一 DOCX 生产链”表述的后续修正。结构化场景不再被描述为通用 DOCX 输入。

### 10.1 根因修复

本次没有在 `AssistantPanel` 中增加 `mode_id == "exam"` 一类分支，而是新增并接入以下应用层契约：

- `TaskCapabilityRef`：保留路由、场景族、配置、状态和专业边界；
- `SourceArtifactRef`：显式区分生产输入、参考材料和结构化题源；
- `GenerationContract`：声明 AI 允许生成的产物类型、Prompt 和校验器；
- `ProductionContract`：声明唯一终端装配器、母版、文种和输入格式；
- `DeliveryContract`：声明完成任务必须出现的交付物集合。

`DocumentPlan` 已升级为 `form-document-plan-v2`，同时保留 v1 读取兼容。旧试卷计划如果曾把通用临时 DOCX 当作生成结果，恢复时会自动收紧到结构化题源契约，并因输入格式不符而失败关闭，不会继续错误执行。

### 10.2 路由完整性

自然语言路由登记的 22 条路由现在全部能投影为以下三种明确状态之一：

- `executable`：存在可验证的 Assistant 生产闭环；
- `planned`：已有场景规划，但不能冒充当前可执行能力；
- `gated`：必须经过专业能力、插件或导入确认边界。

产品手册、英文期刊、项目申报、合同交付、人事批量、固定表单批量等未闭环场景不再静默回退到通用写作。歧义路由在用户明确选择前也不能启动内容生成。

### 10.3 试卷正确链路

当前试卷 AI 生成链路为：

```text
用户命题需求
  -> exam 专用能力与 Prompt
  -> ExamPaperDraft（Markdown）
  -> exam_items_v1 解析和结构校验
  -> 题源 Hash、方案、模板、试卷母版和交付契约预检
  -> 用户审批
  -> 冻结执行会话
  -> 试卷唯一终端装配器
  -> 学生卷 + 答案卷
  -> 两份 DOCX 可打开性与交付集合校验
```

试卷题源不会再经过通用 `DocumentFragment -> composed.docx` 降级。通用报告、论文、技术文档等叙事型内容仍沿用既有 Markdown、DocumentFragment 和审阅 DOCX 链路。

### 10.4 失败关闭规则

- 试卷 AI 输出没有可识别题目、存在结构错误或无法解析时，不创建生产输入；
- 生成产物类型与计划要求不一致时，不允许绑定到计划；
- 输入 Hash、方案、模板或母版在审批后变化时，不允许执行；
- 试卷只生成学生卷、缺少答案卷时，任务状态改为失败；
- 专业边界或规划中能力不能调用通用执行器兜底；
- UI 不拥有试卷 Schema、编译器或终端装配器选择逻辑。

### 10.5 最终自动化校验

本轮以“能力路由 → 生成契约 → 领域编译 → 计划绑定 → 预检 → 审批 →
终端装配 → 交付集合”为验收边界，完成以下校验：

- Assistant 全量回归：`122 passed`；
- 能力契约、计划、内容生成和生产适配器定向回归：`23 passed`；
- 22 条自然语言场景路由均具有 `executable`、`planned` 或 `gated`
  明确状态，没有未登记的静默通用降级；
- 使用确定性模型网关生成真实试卷 Markdown，经真实本地生产运行时输出学生卷和答案卷，
  两份 DOCX 均存在且可由 `python-docx` 打开；
- 学生卷正文不包含“答案速查”，答案卷包含“答案速查”，证明不是把同一文件复制成两个名称；
- 执行器只返回路径但没有实际写出文件时，即使其报告 `success`，任务仍按
  `delivery_contract_incomplete` 失败；
- 非结构化试卷 Markdown、旧版通用 DOCX 试卷计划、审批后资源变化及缺少交付物均失败关闭；
- 13 个本轮目标 Python 文件通过 AST 解析和尾随空白检查；
- 本地环境没有安装 Ruff，因此本轮没有声称 Ruff 通过；该缺口由 AST 检查、
  pytest 回归和目标文件空白检查显式记录，不以假结果替代。

仍未纳入本轮自动化验收的外部环境项是：真实远程模型账号的网络调用、Windows
多 DPI 视觉截图和正式安装包启动。这些不影响本地“AI 生成到试卷组装”的代码闭环结论，
但仍属于发布前环境验收，而不是由单元/集成测试替代的事项。
