## 1. P3-C：quick execution 缺字段预检与参数归属审计

### 1.1 本轮要回答的问题

公文缺少资料字段时，运行前问题队列是否应该同时出现：

```text
1. material.fields.missing
2. scene.parameter_ownership.audit
```

这个问题不能靠“让测试通过”直接恢复旧项，因为它会改变问题队列的语义。真正要确认的是：

```text
scene.parameter_ownership.audit 是否代表真实参数归属缺口？
还是只是在旧测试里作为一个静态预检项被期待出现？
```

### 1.2 审计证据

直接审计基础 `SceneWorkspace`：

```text
audit_scene_parameter_ownership(SceneWorkspace)

is_clean: True
missing_top_level_paths: ()
missing_required_paths: ()
unknown_spec_paths: ()
invalid_owner_layers: ()
```

说明当前基础方案模型的参数归属表是干净的。此时如果在公文缺字段预检里强行恢复 `scene.parameter_ownership.audit`，反而会把“真实架构缺口”和“资料字段缺失”混成同一个问题队列。

再看当前公文缺字段时的运行前问题队列：

```text
current_issue_items:
- material.fields.missing

label:
运行前问题 1 项：先处理 1；资料字段缺失：title, body, organization, document_no, issue_date

count:
1 项，1 项阻断
```

同时，已有的 `FutureSceneWorkspace` 测试仍能证明：只要未来模型真的新增了未登记字段，`scene.parameter_ownership.audit` 仍会出现。因此该问题项不是被删除，而是只在真实缺口出现时出现。

### 1.3 结论

这次不恢复 `scene.parameter_ownership.audit` 到健康基础模型的公文缺字段预检里。

正确边界是：

```text
material.fields.missing
  -> 当前资料包/字段没填齐，属于运行前用户可修复问题。

scene.parameter_ownership.audit
  -> 方案模型或参数归属注册表存在架构缺口，属于开发/审计问题。
```

所以公文资料字段缺失时，只应该显示 1 个阻断项：

```text
资料字段缺失：title, body, organization, document_no, issue_date
```

## 2. 旧 exam_masters/user 残留目录审阅

### 2.1 用户看到的问题

截图中的目录是：

```text
exam_masters/user
```

当前统计：

```text

config_library/masters/exam/user                 不存在
config_library/masters/official/user             不存在
config_library/plans/exam/user                   不存在
config_library/plans/official/user               不存在
config_library/templates/exam/user               不存在
config_library/templates/official/user           不存在
config_library/material_packages/official/user   不存在
```

因此这 202 个文件不是新配置库里的内置方案，也不是现在的 mode-scoped 用户卷面目录，而是旧试卷卷面池的历史残留。

### 2.2 现有代码对新旧目录的定义

在 `src/shared/engine/exam_paper_style.py` 中：

```text
LEGACY_EXAM_MASTER_ROOT = PROJECT_ROOT / "exam_masters"
LEGACY_USER_EXAM_MASTER_DIR = PROJECT_ROOT / "exam_masters" / "user"

EXAM_MASTER_ROOT = PROJECT_ROOT / "config_library" / "masters" / "exam"
USER_EXAM_MASTER_DIR = PROJECT_ROOT / "config_library" / "masters" / "exam" / "user"
```

这说明当前目标架构已经把用户卷面写入目标迁到：

```text
config_library/masters/exam/user
```

而旧目录被保留为：

```text
legacy fallback
```

### 2.3 为什么会有这么多文件

这些文件名主要是：

```text
user_default_exam_copy.docx
user_default_exam_copy_2.docx
...
user_default_exam_copy_*

user_imported_exam.docx
user_imported_exam_*
```

来源是早期“创建副本/导入卷面”逻辑的自动命名策略：

```text
_unique_docx_path(target_dir / f"{style_id}.docx")
```

如果同名文件已存在，就递增生成：

```text
user_default_exam_copy_2.docx
user_default_exam_copy_3.docx
...
```

在旧阶段，这些文件写入的是 `exam_masters/user`，多次创建副本或反复测试后就积累成现在的 202 个。

### 2.4 当前是否还会污染产品选择器

已有防线：


它会跳过程序创建的历史前缀：


### 2.6 为什么旧目录还不能直接删

现有兼容逻辑：

```text
ensure_current_exam_blank_master_docx(...)
```

如果一个旧方案里记录的 `master_docx_path` 指向 `exam_masters/user/user_default_exam_copy.docx`，并且这个文件真实存在，系统会继续打开它，而不是强迁移。

对应测试：

```text
test_legacy_exam_user_master_path_remains_readonly_fallback
```

说明旧目录目前承担“旧方案可打开”的只读回退职责。

如果旧方案记录的是旧目录路径，但文件已经不存在，则会重建到新目录：

```text
config_library/masters/exam/user
```

对应测试：

```text
test_missing_legacy_exam_user_master_path_redirects_to_mode_scoped_dir
```

### 2.7 这件事对产品意味着什么

不能把 `exam_masters/user` 直接当成现在的产品目录，也不能在 UI 中让用户误以为这里是当前卷面库。

建议产品边界：

```text
当前可管理卷面目录：
config_library/masters/exam/user

旧版只读兼容目录：
exam_masters/user

旧目录用途：
只用于旧方案引用回退、审计、可选清理，不作为新建/导入/打开文件夹的默认入口。
```

如果 UI 需要展示旧目录，只能放在“历史卷面池审阅/清理建议”里，并明确：

```text
未引用程序副本可清理候选
手工文件需人工确认
被旧方案引用的文件不能自动清理
```

### 2.8 不建议现在做的事

```text
不建议直接删除 exam_masters/user。
不建议把 202 个文件迁入 config_library/masters/exam/user。
不建议让方案/卷面下拉展示这些程序副本。
```

正确做法应该是：

```text
1. 保持旧目录只读兼容。
2. 确认所有新写入都进入 config_library/masters/exam/user。
3. 在 MD 中记录清理策略。
4. 后续如需清理，先生成 archive plan，再由用户确认移动到归档目录。
```

### 3.4 方案与模板下拉必须同源

用户指出的“两个地方内容没对应上”本质是这个问题：

```text
方案预览页看到：
默认试卷 / 随堂测验 / 期中期末

快速执行页看到：
试卷-默认
```

这说明两个入口没有完全使用同一个 selector source：

```text
plan_selector_options(mode_id)
```

正确要求：

```text
同一个 mode 下所有方案下拉都来自同一组内置/用户方案 entry。
方案 label 可以因上下文略微压缩，但 value 必须一致。
默认选中项必须一致。
```

试卷版应该统一看到：

```text
默认试卷方案
随堂测验方案
期中期末方案
```

而不是一处显示三项，另一处只显示一个旧 `试卷-默认`。

### 3.5 模板也必须按模式隔离

本轮完整 quick execution detail 测试失败暴露了一个同类风险：

```text

QuickExecutionDetail 默认 _work_mode_id = custom
```

这说明仅仅让顶部 UI 有工作模式还不够，所有接收 `SceneWorkspace` 的内部组件也必须保证：

```text

与组件当前 _work_mode_id 一致。
```

否则会出现：

```text
方案是标书
模板却按 custom 查
状态文案变默认流程
执行时可能拿错模板
```

## 4. P4-A 执行：QuickExecutionDetail 工作模式对齐

### 4.1 修复目标

上一节记录的失败是：

```text
create_bidding_scene()
template_id = bid_engineering

QuickExecutionDetail 默认 _work_mode_id = custom
template_selector_options("custom", template_ids=["bid_engineering", ...])
  -> custom 模板库里查不到 bid_engineering
  -> 状态文案退回 默认流程
```

本轮目标：

```text
QuickExecutionDetail._apply_scene(scene)
  -> 先根据 scene.mode_id 或 work_mode_for_scene_id(scene.scene_id) 对齐工作模式
  -> 再刷新方案下拉
  -> 再按对齐后的 mode 填充模板下拉
```

这样直接传入标书、论文、公文、试卷等方案时，不会再按默认 `custom` 模板库查找。

### 4.2 代码修正

修改：

```text

```

新增导入：

```text
from src.config.work_mode import get_work_mode, work_mode_for_scene_id
```

新增内部方法：

```text
_align_work_mode_for_scene(scene)
_work_mode_id_for_scene(scene)
```

执行顺序：

```text
_apply_scene(scene)
  -> _align_work_mode_for_scene(scene)
```

这里没有调用 `set_work_mode(...)`，因为 `set_work_mode(...)` 会按目标模式重新加载默认方案。P4-A 需要保留调用方传入的当前方案，只修正该方案所属的配置库范围。

## 6. P4-C 深度分析：旧试卷卷面池为什么有大量残留

### 6.1 用户看到的问题

用户在资源管理器中看到：

```text
exam_masters/user/
```

目录内存在大量文件：

```text
user_default_exam_copy.docx
user_default_exam_copy_2.docx
...
user_default_exam_copy_18.docx
...
```

这会造成两个担心：

```text
1. 当前产品是不是还在把试卷卷面写进旧目录。
2. 这些残留会不会进入方案/卷面选择框，污染产品体验。
```

本轮先不删除任何文件，只做只读审阅和文档固化。

### 6.2 目录实测

实际计数：

```text
exam_masters/user:
  program_copy:   125
  program_import: 77
  total:          202
```

当前 mode-scoped 新目录：

```text
config_library/masters/exam/user
```

当前没有可列出的 DOCX 文件，审计结果为 0。

这说明截图中的 202 个文件主要是历史运行期不断创建“试卷卷面副本/导入卷面”留下的旧池残留，而不是当前新目录策略已经失效。

### 6.3 当前代码的写入方向

当前试卷卷面路径常量：

```text
LEGACY_USER_EXAM_MASTER_DIR = exam_masters/user
USER_EXAM_MASTER_DIR        = config_library/masters/exam/user
```

当前默认写入函数：

```text
create_exam_blank_master_copy(...)
import_exam_blank_master_docx(...)
ensure_current_exam_blank_master_docx(...)
```

默认写入目标已经是：

```text
USER_EXAM_MASTER_DIR = config_library/masters/exam/user
```

UI 层也显式传入当前目录：

```text
MastersPanel:
  create_exam_blank_master_copy(..., output_dir=USER_EXAM_MASTER_DIR)
  import_exam_blank_master_docx(..., output_dir=USER_EXAM_MASTER_DIR)

  create_exam_blank_master_copy(..., output_dir=USER_EXAM_MASTER_DIR)

```

因此，当前产品入口不应继续向旧 `exam_masters/user` 写入新副本。

### 6.4 旧目录现在的角色

旧目录没有被直接删除，原因是兼容旧方案：

```text
1. 老方案可能仍保存了 master_docx_path 指向 exam_masters/user。
2. 用户可能曾经手工把可用 DOCX 放进旧目录。
3. 如果直接删除，会让旧方案打开失败，或者丢失用户手工资产。
```

所以当前策略不是“删除旧目录”，而是：

```text
旧目录 = 只读兼容 fallback + 可审计清理对象
新目录 = 当前产品写入和选择入口
```

代码里仍有两个兼容点：

```text
_existing_user_master_docx_path(style_id)
```

会先找当前目录，再找旧目录，用来保证旧方案还能打开历史卷面。

```text
_user_master_discovery_dirs(directory=None)
```

在没有显式传目录时会同时扫描当前目录和旧目录。

这里是一个需要继续约束的工程边界：产品 UI 必须显式传入 `USER_EXAM_MASTER_DIR`，不要依赖无参默认扫描；无参默认只保留给兼容/底层恢复逻辑。

### 6.5 旧目录不会直接进入当前选择框的证据

已有保护逻辑：

```text

  user_default_exam_copy
```

`sync_user_exam_blank_master_files(...)` 在发现用户目录文件时，会跳过这些程序生成前缀，避免历史副本把选择框刷爆。

## 7. 继续深度分析：顶部工作模式接管后，方案 / 模板 / 卷面版式 / 资料包的真实边界

本轮只做审阅和文档记录，不直接改业务代码。

用户继续追问的核心不是单个控件文案，而是：

```text

  论文版 / 试卷版 / 公文版 / 标书版 / ...

原来的“场景”不再承担一级业务选择：
  它应产品化为“方案”。

  方案 selector != 模板 selector != 卷面/版式 selector != 资料包 selector。
```

因此现在的正确产品心智应是：

```text

模板
  -> 选择排版格式基线

卷面 / 版式 / 装配项
  -> 选择 DOCX 外壳或结构化装配壳

资料包
  -> 选择或填写本次任务事实数据 / 样例数据
```

这也解释了为什么“每个选框是不是都应该是内置方案”这个问题不能一刀切回答：

```text

卷面/版式选框：不是，应该来自 config_library/masters/<mode>/...
资料包选框：不是，应该来自 config_library/material_packages/<mode>/...
```

```text
thesis     thesis.json              category=academic    has_exam_paper=True
```

这说明 P3-B 已经把 official 源 JSON 清干净了，但以下非试卷方案仍显式携带试卷专属字段：

```text
config_library/plans/custom/builtin/custom.json
config_library/plans/thesis/builtin/thesis.json
config_library/plans/bidding/builtin/bidding.json
config_library/plans/technical/builtin/technical.json
config_library/plans/report/builtin/report.json
```

这类残留的实际风险分两层：

```text
低层模型风险：
  SceneWorkspace.exam_paper 默认存在，即使 JSON 不写，加载后的对象也仍有默认 exam_paper。
  所以不能用“对象上有没有 exam_paper”作为判断依据。

源数据治理风险：
  非 exam 的内置方案 JSON 主动写出 exam_paper，会让审阅、diff、后续迁移和外部编辑者误以为这些方案支持试卷卷面。
```

正确治理方式：

```text
第一步：
  删除非 exam 内置方案源 JSON 中显式的 exam_paper 块。

第二步：
  加测试守门：
    config_library/plans/exam/builtin/*.json 必须允许 exam_paper。
    config_library/plans/{custom,thesis,bidding,technical,report,official}/builtin/*.json 不应显式声明 exam_paper。

第三步：
  runtime 继续使用 scene_uses_exam_paper_surface(scene) 这类 surface 判定。
  不用 getattr(scene, "exam_paper", None) 判定是否进入试卷链。
```

这一步是安全的小步，因为它只清源 JSON，不拆 `SceneWorkspace` 模型字段。

### 11.1 当前代码事实

```text

  验证“方案预览”可以导入 / 导出资料包。
```

因此问题不是底层资料包服务缺失，而是产品入口位置不够正确。

### 11.2 为什么会变成这样

最早公文版为了快速验证 GB/T 9704 版式装配，把资料包导入 / 导出放在“公文方案预览”里是能理解的：当时需要在同一个卡片里选文种、选版式、填资料、生成样张。

但现在产品结构已经变化：

```text
顶部工作模式：
  负责论文版 / 试卷版 / 公文版 / 标书版切换。

原“场景”：
  已降级为当前工作模式内的“方案”。

方案预览：
  应该主要回答“当前方案会怎么装配、用哪个卷面/版式、默认产物是什么”。

资料包填充：
  应该回答“本次任务事实数据是什么、从哪里导入、要导出成什么资料包”。
```

如果导入 / 导出资料包长期留在“方案预览”，用户会自然误解为：

```text
导入资料包 = 修改当前方案
导出资料包 = 导出当前方案的一部分
```

这和真实数据流不一致。真实数据流应该是：

```text
导入资料包
  -> 读取 JSON
  -> 解析为 MaterialExecutionContext
  -> bridge.set_current_material_context(...)
  -> 刷新资料包填充和预览状态
  -> 不写方案 JSON
  -> 不写模板 JSON

导出资料包
  -> 读取当前 MaterialExecutionContext
  -> 写出资料包 JSON
  -> 不保存为方案
  -> 不保存为模板
```

### 11.3 正确归属

建议把入口定为：

```text
方案预览：
  保留：
    当前方案的卷面/版式预览
    套用内置示例资料
    生成样张
    打开版式 / 打开卷面

  不作为主入口：
    导入资料包
    导出资料包

资料包填充：
  作为主入口：
    导入资料包
    导出资料包
    编辑字段
    查看字段契约 / 占位符映射
```

如果为了过渡期不立即删除“方案预览”的导入 / 导出按钮，也必须满足：


## 14. 继续深度分析：顶部工作模式接管后的方案边界复核

本节按“先分析，不急着执行”的口径记录。当前最容易出错的地方不是单个按钮文案，而是四类资源的选择框被混成同一种东西：

```text
顶部工作模式：论文版 / 试卷版 / 公文版 / 标书版 ...
方案：原场景在当前工作模式内的业务装配方案
模板：格式参数体系
卷面 / 版式 / 装配项：带 DOCX 壳、占位符或固定装配结构的资源
资料包：本次或可复用的业务字段数据
```

因此，不能把所有下拉都理解成“内置方案”。只有“方案”下拉应该来自 `config_library/plans/{mode}/...`；模板下拉、卷面/版式下拉、资料包下拉都必须来自自己的资源目录。

### 14.1 之前规划的核心裁决

此前规划已经形成以下裁决：

```text
1. 顶部下拉负责选择工作模式。
2. 原“场景”在用户可见层改为“方案”。
3. 内部 SceneWorkspace / scene_id / on_scene_changed 先作为兼容层保留，不做大规模类名迁移。
4. 方案、模板、卷面/版式、资料包必须按工作模式分目录。
5. 公文不用为 15 种文种各做一个大文件种子，优先用 profile / contract / 资料包字段区分。
```

这解释了为什么现在的产品语言应当是：

```text
工作模式：试卷版
方案：默认试卷 / 随堂测验 / 期中期末
卷面：A4 标准卷面 / 短测紧凑卷面 / 期末完整卷面
模板：默认格式
资料包：当前暂无内置样例

工作模式：公文版
方案：公文-默认 / 函件方案 / 纪要方案
版式：GB/T 9704 公文格式
模板：GB/T 9704 公文格式 / 自定义公文模板
资料包：通知归档检查 / 函件材料申请 / 纪要协调会
```

### 14.2 当前代码事实

当前工作模式由 `src/config/work_mode.py` 定义：

```text
custom    通用版

technical 技术文档版

```

选择器投影层由 `src/ui/adapters/config_selector_models.py` 收口：

```text

  -> config_library/templates/{mode_id}/...
```

这套设计是对的：顶部工作模式先限定资源域，之后每个选择框只读自己的资源类型。

### 14.3 “方案预览”和“方案与模板”不对应的判定

如果界面里出现下面这种情况：

```text

  默认试卷 / 随堂测验 / 期中期末
```

```text
  exam

```

可能原因按优先级判断：

```text

2. 顶部工作模式切换后，面板没有刷新自己的方案下拉。
```

### 14.4 为什么旧母版文件夹里会有大量项目

现在试卷卷面实际存在两个目录身份：

```text
当前用户卷面池：
  config_library/masters/exam/user

旧兼容用户卷面池：
  exam_masters/user
```

代码事实：

```text
src/shared/engine/exam_paper_style.py

LEGACY_USER_EXAM_MASTER_DIR = PROJECT_ROOT / "exam_masters" / "user"
USER_EXAM_MASTER_DIR = PROJECT_ROOT / "config_library" / "masters" / "exam" / "user"
```

目前新建副本和导入卷面的默认写入方向已经是：

```text
config_library/masters/exam/user
```

截图中 `exam_masters/user` 下大量 `user_default_exam_copy_N.docx` 更像是旧阶段重复点击“创建副本”、导入、测试或调试留下的历史池残留。它不应该再被理解成当前产品的“卷面库主目录”。

它还保留的原因是兼容旧方案：

```text
1. 老方案可能仍保存 master_docx_path 指向 exam_masters/user。
2. 直接删除会让旧方案打不开。
3. 归档前必须先做引用审计。
4. 程序生成副本和用户手工文件必须分开处理。
```

当前产品层已经有两道保护：

```text
1. MastersPanel / ScenePanel 调用时显式传入 USER_EXAM_MASTER_DIR，不把旧池当主目录扫描。
2. sync_user_exam_blank_master_files 即使走兼容扫描，也会跳过 user_default_exam_copy* / user_imported_exam* 等程序生成前缀。
```

所以旧池不会整体进入产品选择框。真正仍可能进入的只有两类：

```text
1. 某个旧方案明确引用了旧池里的某个 DOCX。
2. 某条兼容路径无参扫描旧池，并且发现的是非程序前缀、可打开、可识别的手工 DOCX。
```

这就是为什么 P5-E 只做 dry-run 归档计划，而不能直接删除或移动。

### 14.5 其他工作模式怎么办

### 18.3 为什么选择框和预览会不对应

现在有两组概念正在混用：


用户指出的“不对应”本质上是：


```text

A4 标准卷面：决定标题区、考试信息栏、页眉页脚、密封线、题目插入位。
默认格式模板：决定正文排版、标题编号、表格、页边距等通用格式基线。
```

所以正确产品语义应该是：

```text
顶栏：工作模式
快速执行：方案 + 模板
方案预览：卷面/装配壳预览
场景规则：方案规则
```

“场景”这个词应继续从用户可见配置入口里淡出，内部字段名可以短期保留 `scene_id` 作为兼容实现，但 UI 和 selector 文案要统一叫“方案”。

### 30.2 尚未封口的同类风险

#### A. 用户方案名称为空时仍借用内置元数据

当前有效用户方案虽然不再调用 `_builtin_scene_display_name()`，但名称、描述及部分模板契约的 fallback 仍直接读取 `SCENE_META_MAP`：

```text
user/exam.json + name="" -> descriptor.name = 默认试卷
user/exam.json + description="" -> descriptor.description = 内置试卷说明
```

最小复现结果：

```text
blank user plan -> name='默认试卷', source_type='user'
```

这仍属于“来源是用户，但展示内容来自内置项”的隐式伪装，只是触发条件从普通用户名称缩小为空名称或缺失字段。

建议边界：只有 `builtin` 资源可以从 `SCENE_META_MAP` 获取显示 fallback；用户资源缺少名称时应显示文件 ID 或明确的“未命名方案”，除非未来增加显式 `base_plan_id` / `inherits` 继承契约。

#### B. 损坏的用户同 ID 方案会被内置方案静默顶替

当前 descriptor 去重优先级先比较 `is_available`，再比较来源：

```text
available builtin > broken user
```

最小复现：

```text
plans/exam/user/exam.json 损坏
最终 selector 条目 -> source_type=builtin, load_error=False
```

这保证产品可继续执行，但会隐藏用户覆盖文件已经损坏的事实。建议明确产品策略：

```text
推荐：用户覆盖项仍占位并显示不可用状态，同时提供“恢复内置方案”。
备选：自动回退内置，但必须显示警告和被忽略的用户文件路径。
```

不建议继续无提示地静默回退。

#### C. 用户模板名称为空或等于 ID 时会借用内置 fallback label

`template_selector_options()` 当前在 entry 名称为空或等于 ID 时，无条件使用调用方传入的 `fallback_labels`。快速执行页的 fallback 来自方案元信息，因此可出现：

```text
entry.source_type = user
entry.name = default
selector.label = Builtin Fallback / 内置兼容模板名称
```

最小复现结果：

```text
entry=('default', user)
selector=('default', user, 'Builtin Fallback')
```

建议只允许 `builtin` entry 使用方案元信息 fallback；用户模板应保留自身名称，缺失时使用 config ID 或“未命名模板”。

#### D. 跨工作模式同 ID 方案在全局 descriptor 清单中会误去重

`_list_entries()` 已使用 `(mode_id, config_id)` 作为身份键，但 `_dedupe_scene_descriptors()` 仍只使用 `config_id`。最小复现：

```text
plans/exam/user/shared.json     -> Exam Shared
plans/official/user/shared.json -> Official Shared
list_scene_descriptors()        -> 只剩 Exam Shared
```

当前 UI 主路径始终传入 `mode_id`，因此不会直接影响顶栏模式内 selector；但全局审计、迁移工具或未来资源管理页会漏掉另一个工作模式的同 ID 方案。身份键应统一为 `(mode_id, config_id)`。

#### E. 试卷卷面允许用户 ID 与内置 ID 冲突

`ExamPaperConfig` 只对 `custom_blank_styles` 内部重复 ID 去重，没有拒绝 `default_exam`、`class_quiz_exam`、`term_exam` 等内置 ID。`list_exam_masters()` 又先按内置 ID 解析一次、随后遍历用户项再追加一次。

最小构造 `custom_blank_styles=[style_id=default_exam]` 后：

```text
list_masters(exam)       -> 两个 value=default_exam 的用户条目
master_selector_options  -> 两个 value=default_exam 的用户选项
```

这是当前最明确的同 ID 重复缺口。建议禁止用户卷面占用内置 ID，并在加载旧配置时生成稳定的新用户 ID；如果产品要支持覆盖，则必须像方案/模板一样建立统一的 user-over-builtin 去重和恢复语义，不能同时保留两个相同 selector value。

### 30.3 未发现同类显示名伪装的部分

```text
[x] 正常用户模板：entry 自身具有名称时，selector 保留该名称。
```

## 38. P5-Y 执行记录：PanelBridge 来源通道与资源来源拆分

本轮继续复核同 ID 用户方案的名称与来源。先重新验证第 34、36 节结论：

```text
plans/exam/user/exam.json
  source_type = user
  name        = 用户文件自己的名称
  config_id   = exam

最终 selector
  -> user 条目胜出
  -> 保留用户名称和用户来源前缀
  -> 不套用 builtin 的“默认试卷”显示名
```

配置库、方案预览和快速执行的显示链路仍然正确。进一步发现的结构缺口位于 `PanelBridge`：原来的 `source` 只能表达加载/存储通道，不能表达资源归属。

### 38.1 两个来源维度

现在明确拆为：

```text
source
  library   来自配置库
  file      来自外部文件
  runtime   仅运行时对象
  builtin   无配置库条目时的工厂回退通道

source_type
  builtin   内置资源
  user      用户资源
  legacy    旧目录兼容资源
  external  外部文件
  runtime   仅运行时对象
```

因此同 ID 用户覆盖项的完整身份不再被压扁：

```text
mode_id=exam + source=library + source_type=user + config_id=exam
```

它与内置项：

```text
mode_id=exam + source=library + source_type=builtin + config_id=exam
```

共享存储通道和 ID，但不是同一个来源对象。

### 38.2 已接通的写入点

```text
[x] MainWindow 工作模式默认方案/模板加载
[x] MainWindow 脏配置保存后回写
[x] ScenePanel 方案选择、复制、编辑回写和模板联动
[x] TemplatePanel 模板选择、复制、导入、保存和编辑回写
[x] WorkbenchPanel 快速执行方案/模板绑定
[x] 配置管理的方案/模板另存
```

配置库保存按契约进入 `user` 分桶；旧测试桩或兼容调用若未返回 `source_type`，保存链路以 `user` 作为契约默认值。文件另存路径则由目录权威判断来源：

```text
config_library/.../builtin -> builtin
config_library/.../user    -> user
legacy plans/templates     -> legacy
配置库之外                  -> external
```

### 38.3 权限与上下文防串

方案、模板管理权限现在优先读取当前上下文的 `source_type`：

```text
source_type=builtin -> 只读
source_type=user    -> 可按实际文件权限重命名/删除
source_type=external/runtime/legacy -> 不会因裸 ID 命中 builtin 集合而伪装成内置
```

为兼容尚未迁移的测试或调用者，`source_type` 参数允许省略，但只在方案/模板的 `config_id + path + source` 三元身份完全不变时继承原值；身份发生变化而调用者未提供来源时会清空，不允许把前一个用户项的来源泄漏给下一个内置项。

裸 ID 与 entry/descriptor 回查仍作为“缺失来源上下文”的最后兼容回退存在，不是正常产品主路径。
