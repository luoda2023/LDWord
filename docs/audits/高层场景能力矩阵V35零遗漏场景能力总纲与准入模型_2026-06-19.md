# 高层场景能力矩阵 V35 零遗漏场景能力总纲与准入模型

日期：2026-06-19

## 1. 文档定位

本文继续回应“更高层的场景能力矩阵目前功能点过于不完善，不能出现高频适用场景遗漏或者边界不清晰”的要求。V29-V34 已经形成 12 个 coverage pack、15 个 planned family、10 个 capability axis、17 个 workflow archetype、15 个 Word/OOXML risk surface、9 个 completeness gate、16 个 dashboard source、11 个 drilldown item、20 个 CountProfile 和 27 个 product readiness subject 的自动化基线。

V35 不继续扩张顶层入口，而是把这些资产提升为一套“零遗漏准入模型”：

```text
高频用户任务
-> 场景承载层
-> 能力契约
-> Word/OOXML 风险
-> UI/执行/报告/测试证据
-> 产品成熟度
-> 边界和不承诺项
```

核心判断：

```text
完善的高层场景能力矩阵，不是 pack 越多越好，
而是每个高频任务都能被明确归属、明确解释、明确执行、明确报告、明确边界。
```

## 3. 当前事实基线

当前代码侧的高层矩阵骨架已经存在，但不能直接等价为完整产品能力。

| 维度 | 当前值 | V35 判断 |
| --- | ---: | --- |
| coverage packs | 12 | 顶层入口心智基本稳定，暂不建议盲目新增 |
| planned families | 15 | 高频子场景已有承载层，但多数仍是 L1-L3/L4 |
| capability axes | 10 | 需要升级成 20 个产品能力槽位 |
| workflow archetypes | 17 | 工作流覆盖较好，但前台解释和 journey fixture 仍薄 |
| Word/OOXML risk surfaces | 15 | 风险面充足，下一步要更重视动作闭环 |
| completeness gates | 9 | 静态验收可用，但需扩展到用户旅程 |
| request cells | 51 | 已覆盖 matched/ambiguous/manual/negative，但真实说法仍需扩容 |
| dashboard sources | 16 | 证据源齐，但不是 Green/L5 的充分条件 |
| drilldown items / rows | 11 / 184 | 前台浏览骨架已形成，下一步要补真实场景路径 |
| CountProfiles | 20 | 多口径计数已进入审计，仍需与输入源和规则治理继续打通 |
| product readiness subjects | 27 | 当前 0 个 Green/L5，所有 subject 均有 L5 blocker |

一句话：

```text
当前不是“没有矩阵”，而是“矩阵还没有完全转化成用户可依赖的产品能力”。
```

## 4. V35 的零遗漏定义

V35 将“零遗漏”定义为三件事同时成立。

| 层面 | 定义 | 失败表现 |
| --- | --- | --- |
| 高频任务不遗漏 | 用户高频自然说法能落到 pack、family、profile、schema、preset、plugin、handoff 或 negative | 用户想做的事在导航、搜索、报告里找不到 |
| 能力链路不遗漏 | 输入、模板、范围、资料、计数、对象、公式、图片、输出、批量、报告、修复均有归属 | UI 能配但执行不认，或执行了但报告不解释 |
| 边界不遗漏 | 专业判断、AI/OCR/LaTeX、复杂图形、非 Word 输出有人工门、插件门或负例 | 核心能力越界承诺，后续难以验收 |

V35 不把“所有东西都自动化”当目标。高频任务可以只做到边界完整，但不能边界消失。

## 5. 三轴防遗漏模型

以后新增或审阅任何场景，不再只按“文档类型”判断，而要同时过三条轴。

### 5.1 用户任务轴

用户会怎么说这件事：

- “帮我把论文按学校格式整理”
- “这份英文 manuscript 投稿前检查一下”
- “生成学生版和教师版试卷”
- “把这些人员信息批量套进证明模板”
- “这份 PDF 扫描件能不能转成 Word 再套模板”
- “合同签署版和审阅版都导出来”
- “标书附件和资质清单帮我查缺”

要求：每类高频说法必须有 matched、ambiguous、manual boundary、handoff 或 negative 状态。

### 5.2 文档/业务族轴

这件事属于什么业务族：

- 通用排版和个人文档
- 中文学术
- 英文投稿
- 教育试卷和教学材料
- 标书、资质、附件包
- 公文、会议、制度
- 技术长文档和书稿
- 项目申报、产品售前
- 合同和签署包
- HR 批量、表单套打
- 财务、披露、IP、法律、医疗、翻译等专业边界
- PDF/OCR、LaTeX、AI、复杂图形等导入和插件边界

要求：业务族可以归 pack/family/profile，不一定新增顶层入口。

### 5.3 工作流轴

用户实际要完成什么工作流：

- 快速规范化
- 结构识别和范围定位
- 资料填充和附件 inventory
- 多版本显隐
- 批量生成和失败隔离
- 计数/规则合规
- 对象预检和降级
- 审阅对比和修复确认
- 提交包、归档包和 artifact 浏览
- 插件/人工门 handoff

要求：每个场景至少要说清哪些 workflow 启用、禁用、人工门或插件化。

## 6. 承载层总纲

新增需求先找承载层，不先新增入口。

| 承载层 | 负责什么 | 进入条件 | 不负责什么 |
| --- | --- | --- | --- |
| Coverage Pack | 用户心智中的大类入口 | 高频、稳定、可解释，有独立交付或风险面 | 不承接每个行业别名 |
| Planned Family | pack 内高频子场景或跨 pack 能力组合 | 有稳定业务心智，但还未完整产品化 | 不伪装成已可执行顶层场景 |
| Profile | 同一 family 下的规则/范围/资料/交付组合 | 需要差异化规则，但共享 UI 和执行能力 | 不重新发明模板体系 |
| MaterialSchema | 字段、图片、签章、附件、人员、项目事实 | 需要结构化资料或资产 inventory | 不保存计数规则和版式外观 |
| CountProfile | 字数、词数、字符、图表、参考文献、章节等口径 | 需要规则来源和范围解释 | 不承诺官方系统 100% 一致 |
| DeliveryPreset | 输出版本、命名、目录、DOCX/PDF/ZIP/report/intermediate | 交付物不同或显隐规则不同 | 不保存模板外观和资料事实 |
| BatchPreset | 多记录、多实体、多模板、多版本批量 | 需要失败隔离、续跑和汇总报告 | 不验证业务数据真实性 |
| ObjectPreflight | 字段、批注、修订、文本框、OLE、rels、宏等风险 | 会触碰脆弱 Word 对象 | 不替代人工内容判断 |
| PluginManualGate | AI/OCR/LaTeX、复杂图形、专业判断、非 Word 输出 | 核心无法稳定承诺或需要外部能力 | 不让核心静默承诺自动完成 |
| Negative/Handoff | 明确不支持或转交到目标 pack/plugin | 不属于 Word 核心或需要先导入确认 | 不把拒绝包装成模糊支持 |

新增顶层 pack 必须同时满足：

1. 用户长期稳定按这个大类表达，而不是一次性行业别名。
2. 事实源、交付版本、Word 风险、报告证据至少两项明显不同于现有 pack。
3. 需要独立 schema/profile/preset/report/repair 组合。
4. 已有 request-cell、fixture、测试和 release gate 计划。

不满足时，只进入 family/profile/schema/preset/plugin/manual gate。

## 7. 二十个完整能力槽位

V35 将 V32 的 13 个验收槽位扩展为 20 个产品能力槽位。不是每个场景都要启用每个槽位，但每个槽位都必须给出状态。

状态枚举建议：

```text
enabled / optional / disabled / inherited / manual_gate / plugin_gate / handoff / negative / future_slice
```

| 槽位 | 必须回答 | 稳定承载 | 不清晰时的风险 |
| --- | --- | --- | --- |
| 1. UserIntent | 用户自然说法、matched/ambiguous/manual/negative/handoff | request-cell、task lexicon | 高频需求漏路由 |
| 2. CarrierLayer | 是 pack、family、profile、schema、preset、plugin 还是 negative | coverage manifest、family registry | 顶层入口膨胀 |
| 3. InputFactSource | DOCX、Markdown、JSON、Excel、PDF/OCR、LaTeX、AI、人工资料哪个是真源 | InputSourceProfile | 执行和报告不可复盘 |
| 4. StructuredModel | 是否有 JSON/schema/AST/Markdown 预览或中间产物 | MaterialSchema、question schema、intermediate | AI/Excel/Markdown 被误当最终版式 |
| 5. TemplateBaseline | 外观基线归哪个模板，兼容哪些模板 | TemplateConfig、compatible_template_ids | 场景重新发明模板 |
| 6. ControlContract | 同名参数是否复用模板管理命名、单位、禁用、布局语义 | control_contract_registry | UI 语义分裂 |
| 7. FormatScope | 正文、摘要、目录、参考文献、附录、页眉页脚、脚注、文本框、批注、修订处理范围 | FormatScopeConfig、CountProfile | Word story 漏处理或误伤 |
| 8. MaterialSchema | 字段、人员、公司、项目、签章、图片、附件、术语事实 | material_schema_registry | 缺资料无修复入口 |
| 9. AssetInventory | 图片、证照、签章、图表、题图、附件角色 | AssetsPanel、MaterialExecutionContext | 资料包只剩文字字段 |
| 10. CountRuleProfile | 字数、词数、字符、图表、公式、参考文献、display items 口径 | CountProfile、RuleSource | 单一字数误导用户 |
| 11. FormulaPolicy | 公式片段、OMML、LaTeX fallback、低置信度 | FormulaPolicy、formula_convert | 公式被当普通文本 |
| 12. ReferenceCitation | BibTeX/CSL、引用、参考文献、交叉引用 | citation/reference configs | 学术/投稿链路断裂 |
| 13. FixedLayout | 固定行高、内容控件、文本框、套打、答题卡、证书版位 | fixed-layout profile | `w:trHeight` 等参数残留或乱归属 |
| 14. ObjectPreflight | OLE、嵌入包、宏、字段、批注、修订、hidden text、rels | ObjectPreflightPolicy | 复杂 Word 对象被破坏 |
| 15. ContentVisibility | 答案/解析、正式/内部、审阅/签署、公开/归档显隐 | ContentVisibilityRule、DeliveryPreset | 多版本内容不一致 |
| 16. DeliveryPreset | 输出文件、命名、目录、DOCX/PDF/ZIP/report/manifest/intermediate | DeliveryPreset、OutputConfig | 交付只剩散落开关 |
| 17. BatchJourney | 多记录、多实体、失败隔离、续跑、汇总 | BatchPreset | 一个失败拖垮整批 |
| 18. ReportRepair | 报告字段、问题队列、修复入口、人工确认 | report writer、repair routing | 用户不知道为何失败 |
| 19. FixtureJourney | 成功、降级、失败/人工门样本 | sample fixtures、journey fixtures | 静态闭合冒充真实可用 |
| 20. BoundaryEvidence | 专业、AI/OCR/LaTeX、复杂图、非 Word 的人工门/插件/负例 | PluginManualGate、handoff、negative | 核心能力越界 |

Green/L5 的最低要求不是 20 个槽位全 enabled，而是：

```text
每个槽位都有明确状态；
enabled 槽位具备 UI/执行/报告/测试证据；
manual/plugin/negative 槽位具备用户可见边界和报告字段；
至少覆盖成功、降级、失败/人工门三类 journey。
```

| LaTeX/公式导入 | LaTeX 片段、公式转换、完整工程导入 | `import_ai_boundary` + FormulaPolicy | OMML 优先、图片 fallback、保留原文、人工门 | 完整工程不当普通样式处理 |
| AI 草稿/AI 出题 | AI 生成文档、AI 出题、AI 草稿转 Word | `import_ai_boundary` 或领域插件 | 结构化 JSON、Markdown 预览、人工确认、质量边界 | 核心不承担事实与质量责任 |
| 复杂学科图 | 几何图、电路图、化学结构式、生物流程图、复杂图形 | 插件或图片资产 | 图片占位、上传替换、尺寸题注、插件化图形源 | 核心不自动制图 |
| 非 Word 原生交付 | PPT、网页、海报、最终出版系统、图片设计 | negative / external plugin | 明确拒绝、handoff、替代输出说明 | 不冒充 Word 场景 |

V35 判断：当前表内大类已经覆盖主要高频适用场景。真正的风险不是漏大类，而是每类内的事实源、控件、规则、对象、交付、修复、报告和 journey fixture 不够深。

## 10. 外部技术记录吸纳

### 10.1 Count Engine 技术记录

需要吸纳：

- 不做单一“字数统计器”，而做 profile-driven multi-metric CountEngine；
- 同时保留 Word-like words、中文字符、纯汉字、英文词、含/不含空格字符、参考文献、图、表、公式、章节、段落等指标；
- 场景只保存 profile、范围和规则来源，执行结果进入报告；
- 报告必须说明采用口径、计入范围、排除范围、不确定项和官方系统差异边界。

已落点：

- N2.170 已新增 CountProfile 场景覆盖审计；
- 20 个注册 CountProfile、17 个 family-referenced、11 个 rule-source-backed；
- `basic` 和 `word_xml_full` 保持 warning 视角，不冒充业务默认；
- `bid_package` 作为 rule-source-only profile 显性化。

后续：

- N2.171 要把 CountProfile 的 scope 与 DOCX/JSON/Markdown/XLSX/PDF/OCR/LaTeX/AI 的输入事实源对齐；
- N2.173 要补 count report 的成功、降级、失败/人工门 fixture；
- N2.174 要在用户说“字数/词数/附件数”时给出澄清路径。

### 10.2 试卷生成技术记录

需要吸纳：

- AI 或外部系统只提供结构化源，程序负责校验、预览、渲染和导出；
- JSON 是机器事实源，Markdown 是人工预览，Word 是正式交付；
- 学生版/教师版/答案版/解析版来自同一结构化源和 ContentVisibility/DeliveryPreset；
- 通用图片能力优先于复杂几何图自动生成；
- 复杂几何、电路、化学结构式、AI 生图属于插件或后期能力。

V35 落点：

- `exam_education` 应成为 InputSourceProfile、StructuredModel、ContentVisibility、FormulaPolicy、AssetInventory、DeliveryPreset 的样板；
- 这套“同一结构化源 -> 预览 -> 多版本 Word 交付”的模式也要泛化到合同审阅/签署、披露审阅/公开/归档、投稿初投/修回、批量个性化文档；
- 不把 Markdown 当最终 Word 版式事实源，不把 AI 内容质量纳入核心承诺。

### 10.3 Word 自动生成技术栈视角

虽然分享链接正文不可见，但结合主题和本地技术记录，V35 吸纳以下稳定原则：

```text
结构化事实源
-> 模板/母版渲染
-> Word 后处理
-> 对象预检
-> 多版本交付
-> 报告与人工确认
```

因此，场景能力不应被描述成“字符串替换”或“一个模板按钮”。必须明确：

- 事实源是什么；
- 渲染源是什么；
- 后处理触碰哪些 Word story 和 OOXML 风险；
- 交付物有哪些；
- 失败、低置信、专业边界如何报告。

## 11. 控件一致性准入

场景配置中的控件样式控制必须与模板管理中规定的样式一致。这不是视觉偏好，而是执行链路安全。

| 控件族 | 场景侧准入 | 不允许的情况 |
| --- | --- | --- |
| 左缩进/右缩进 | 可同一行或同组展示，单位、stepper、禁用语义与模板管理一致 | 场景页改名、换单位或执行字段不对应 |
| 段前/段后 | 可同一行或同组展示，命名保持“段前/段后” | 改成前距/后距导致报告和执行无法对应 |
| 特殊缩进 | 必须可交互切换无/首行/悬挂；无时禁用数值并归零 | 只有只读文本或无法切换 |
| 行距类型/行距值 | 类型和值绑定，固定/多倍/最小值有清楚单位 | UI 可选但执行层不消费 |
| 表格固定行高 | 只在 fixed-layout profile 出现，对应 Word `w:trHeight` | 混入通用 TableConfig 模板参数 |
| 内容控件/文本框 | 归 fixed-layout/ObjectPreflight，不当普通段落 | 套打和证书版位被普通格式化破坏 |
| 水印/签章 | 状态和交付语义归场景，外观可复用模板语言 | 既像模板背景又像交付状态 |
| 公式策略 | 片段转换归 FormulaPolicy，完整 LaTeX/OCR/AI 质量归插件 | 把公式当普通文本或模板杂项 |
| 输出版本 | 归 DeliveryPreset/OutputConfig | 散落在模板页或一次性执行按钮 |

成熟度要求：

```text
共享外观控件没有一致性，不能升 Green/L5；
UI 有控件但执行不消费，不能升 Green/L5；
执行消费但报告不解释，不能升 Green/L5。
```

## 12. 边界裁决树

新增高频需求按以下顺序裁决：

1. 是否需要 Word 原生交付。不需要则 negative 或外部插件。
2. 是否只是模板外观。是则归 TemplateConfig/control contract。
3. 是否是资料事实、字段、人员、图片、签章、附件。是则归 MaterialSchema。
4. 是否是字数、图表、公式数量、规则来源、提交要求。是则归 CountProfile/RuleSource。
5. 是否是输出版本、命名、目录、PDF/ZIP、提交包、报告。是则归 DeliveryPreset/OutputConfig。
6. 是否是多记录、多人员、多项目。是则归 BatchPreset。
7. 是否是固定版位、证书、登记表、答题卡、套打。是则归 fixed-layout profile。
8. 是否触达字段、批注、修订、内容控件、文本框、OLE、rels、宏。是则先走 ObjectPreflight。
9. 是否涉及法律、财务、审计、专利、医学、翻译质量、AI 内容质量、OCR/LaTeX 无损转换。是则进入 PluginManualGate。
10. 是否能从导入边界 handoff 到目标 pack。能则必须有 handoff 报告和回退策略。
11. 是否拥有独立用户心智、事实源、交付、风险面、报告和证据链。只有全部成立才考虑新增 coverage pack。

## 13. Green/L5 准入

V35 继续锁定：release gate passed 不等于 Green/L5。

| 等级 | 定义 | 对用户可承诺 |
| --- | --- | --- |
| L1 Gray | 规划存在 | 只说明方向 |
| L2 Blue Boundary | 边界、人工门、插件门或负例明确 | 能解释为什么不能自动完成 |
| L3 Yellow | route/profile/schema/preset/fixture 有 first slice | 可试用，但需要限制提示 |
| L4 Orange | UI/执行/报告/fixture/release gate 基本闭合 | 可作为主流程，但保留明确缺口 |
| L5 Green | 成功、降级、失败/人工门三类 journey 均产品化，真实业务 fixture 足够 | 可稳定推荐给普通用户 |

Green/L5 必须满足：

- 20 个能力槽位均有状态；
- enabled 槽位具备 UI、执行、报告、测试证据；
- manual/plugin/negative 槽位具备用户可见边界；
- 至少一个真实业务 journey 覆盖成功路径；
- 至少一个真实业务 journey 覆盖降级路径；
- 至少一个真实业务 journey 覆盖失败/人工门路径；
- 共享控件与模板管理同语义；
- 报告能解释输入源、规则来源、范围、输出、对象风险和边界。

4. N2.175-N2.178 解决控件一致性、交付、资料修复和 fixed-layout 深水区。

## 15. V35 结论

当前高层场景能力矩阵的大类覆盖已经接近稳定。继续补“按钮”和“顶层入口”不是最优路径。

真正要补的是：

- 高频任务全集到承载层的可解释路由；
- 20 个能力槽位的状态和证据；
- 输入事实源、资料、计数、对象、交付、批量、修复之间的链路；
- 专业、AI/OCR/LaTeX、复杂图形、非 Word 输出的边界；
- 与模板管理一致的控件语义；
- 成功、降级、失败/人工门三类真实用户旅程。

只要这些闭合，场景矩阵才不会在真实使用中出现高频场景遗漏、边界混淆或链路断裂。
