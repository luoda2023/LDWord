# 公文资料派生字段与时间计算逻辑深度分析

日期：2026-07-12

## 一、结论先行

需要继续补充，而且缺口不是“再加几个当前日期按钮”，而是缺少一层统一的**资料字段规则与派生值引擎**。

当前系统已经能定义公文字段、区分固定/浮动字段、保存字符串值并装配 Word，但尚不能稳定表达：

- 当前日期、当前时间、当前日期时间；
- 从某个业务日期加减若干自然日或工作日；
- 两个时间节点之间的中点、等分节点或按权重估算的节点；
- 月末、季度末、下一个工作日、第 N 个星期几；
- 字段之间的复制、回退、条件选择和格式转换；
- 自动值的人工覆盖、执行时冻结、重试复现和计算来源追溯。

正确方向不是把 Python 表达式直接暴露给用户，也不是在每个字段旁边分别实现一套日期逻辑，而是建立：

```text
字段定义
  -> 类型与值来源
  -> 依赖关系图
  -> 受限规则求值
  -> 执行时冻结
  -> 人工确认 / 覆盖
  -> Word 显示值
  -> 归档计算凭据
```

建议把这一能力定义为“资料规则引擎”，先服务公文，再复用到标书、合同、报告和批量表单。

## 三、为什么不能把所有日期都设为“今天”

不同日期的业务语义不同：

- **处理日期**：软件实际运行的日期，可以来自执行时钟。
- **成文日期**：是会议通过或负责人签发等业务事件的日期，不能默认等同于软件运行日期；联合行文还涉及最后签发日期。
- **印发日期**：是实际送印日期，也不一定等于成文日期或文件生成日期。
- **会议时间**：来自会议安排或实际召开时间，通常需要人工或外部系统提供。
- **归档时间**：属于交付或归档阶段的系统事件时间，可以自动生成，但要与成文日期分开。

《党政机关公文处理工作条例》明确区分成文日期、印发日期等要素，并将成文日期定义为会议通过或负责人签发日期；联合行文采用最后签发日期。因此“生成 Word 的当天”只能作为候选默认值，不能静默写入成文日期。[中国政府网条例原文](https://big5.www.gov.cn/gate/big5/www.gov.cn/zhengce/2013-02/22/content_2640088.htm)

GB/T 9704-2012《党政机关公文格式》目前仍为现行标准，且 2025-05-30 复审结论为继续有效。[全国标准信息公共服务平台](https://std.samr.gov.cn/gb/search/gbDetailed?id=lOIe27f77QU%3D&mode=p)

## 四、需要覆盖的规则类型

### 4.1 即时系统值

- 当前日期；
- 当前时间；
- 当前日期时间；
- 当前年份、月份、季度、星期；
- 执行批次号、任务号、源文件名；
- 生成时间、归档时间、审阅稿生成时间。

这些值必须明确使用哪个时钟：预览时钟、执行开始时钟、实际写文件时钟，还是归档时钟。

### 4.2 基于单个锚点的日期计算

- `起始日期 + 3 个自然日`；
- `签发日期 + 5 个工作日`；
- `当前日期的月末`；
- `下一个星期一`；
- `季度末前 2 个工作日`；
- `合同日期 + 1 个月`，并定义月末如何处理。

### 4.3 多锚点和中间节点

“估算中间时间节点”至少有四种不同语义，必须让用户选择，不能统一叫“取中间值”：

1. **时间轴中点**：`start + (end - start) / 2`；
2. **工作日中点**：只在指定工作日历中计算有效工作日；
3. **等分里程碑**：在起止节点之间生成 N 个等距节点；
4. **权重节点**：例如准备 20%、审核 30%、签发 20%、印发 30%。

还必须声明：

- 起止日期是否计入区间；
- 结果按分钟、小时还是日期取整；
- 落到非工作日时向前还是向后调整；
- 同一天内的工作时间范围；
- 开始晚于结束时是报错、交换还是人工确认；
- 节点是否允许重合；
- 计算结果是“计划值”还是“正式业务日期”。

### 4.4 字段组合与条件逻辑

- `落款机关 = coalesce(用户输入, 发文机关1)`；
- `印发机关 = 组织默认办公室`；
- `印发日期 = 用户输入，否则取实际印发事件日期`；
- `联合行文成文日期 = 最后签发日期`；
- `若有附件，则附件截止日期 = 成文日期 + N 个工作日`；
- `若紧急程度为特急，则办理期限采用另一套规则`。

### 4.5 外部事件值

未来可能来自 OA、日历、签批或归档系统：

- 实际签发时间；
- 最后会签完成时间；
- 实际印发时间；
- 回执时间；
- 归档完成时间。

外部值必须记录来源系统、事件编号、拉取时间和是否允许人工覆盖。

## 五、工作日不是“排除周六周日”

中国法定节假日存在调休，周日可能是工作日，周六也可能上班。以 2026 年安排为例，1 月 4 日周日、2 月 14 日周六、2 月 28 日周六等均为上班日。[国务院办公厅关于2026年部分节假日安排的通知](https://big5.www.gov.cn/gate/big5/www.gov.cn/zhengce/zhengceku/202511/content_7047091.htm)

因此工作日计算需要版本化日历，而不是：

```text
weekday < 5
```

建议日历模型至少包含：

```text
calendar_id
region
year
timezone
holidays
adjusted_workdays
organization_overrides
source_url
source_version
loaded_at
```

运行时策略：

- 找不到目标年份日历时，不得静默退化为周一至周五；
- 可以选择“阻止计算”“警告后按普通周历”“要求人工确认”；
- 组织自定义休息日必须叠加在国家/地区日历之上；
- 归档报告应记录实际使用的 `calendar_id + version`。

项目当前没有 `holidays`、`workalendar` 或自有工作日历依赖，因此这部分尚未实现。

## 六、推荐的数据模型

### 6.1 字段身份与显示名称分离

近期已经允许 `{{发文机关1}}、{{发文机关2}}` 等全量自定义字段。后续规则依赖不能直接引用可修改的中文显示名，否则改名会使表达式失效。

建议每个字段具有不可变身份：

```json
{
  "field_id": "fld_01J_OFFICIAL_ORG_1",
  "key": "organization",
  "label": "发文机关",
  "series_index": 1,
  "data_type": "text",
  "scope": "fixed"
}
```

规则引用 `field_id` 或稳定 `key`，Word 占位符显示为 `{{发文机关1}}`。字段改名只改变 label/alias，不改变依赖图。

### 6.2 字段规则

建议在资料档案和运行时上下文中新增 `field_rules`，不要把规则字符串塞进 `entity_data`：

```json
{
  "field_rules": {
    "printing_date": {
      "mode": "execution_date",
      "timezone": "Asia/Shanghai",
      "format": "YYYY年M月D日",
      "freeze": "execution_start",
      "allow_manual_override": true
    },
    "review_due_date": {
      "mode": "derived",
      "operation": "add_business_days",
      "dependencies": ["issue_date"],
      "arguments": {"days": 5, "calendar_id": "CN_OFFICIAL_2026"},
      "allow_manual_override": true
    },
    "mid_review_time": {
      "mode": "derived",
      "operation": "midpoint",
      "dependencies": ["review_start", "review_end"],
      "arguments": {"round_to": "30_minutes"}
    }
  }
}
```

### 6.3 已解析值与计算凭据

仅保存最终字符串无法解释结果从何而来。建议输出：

```json
{
  "field_id": "review_due_date",
  "typed_value": "2026-07-20",
  "display_value": "2026年7月20日",
  "source": "derived",
  "resolved_at": "2026-07-12T03:15:00Z",
  "timezone": "Asia/Shanghai",
  "rule_version": "field-rule-v1",
  "dependency_values": {"issue_date": "2026-07-13"},
  "calendar_version": "CN_OFFICIAL_2026@2025-11-04",
  "manual_override": false
}
```

## 七、推荐的受限操作集

第一版不要支持任意 Python、JavaScript 或 `eval`。建议使用结构化操作白名单：

```text
today(timezone)
now(timezone)
copy(field)
coalesce(field1, field2, constant)
add_days(field, n)
add_business_days(field, n, calendar)
start_of_month(field)
end_of_month(field)
add_months(field, n, month_end_policy)
next_weekday(field, weekday)
midpoint(start, end, rounding)
business_midpoint(start, end, calendar)
split_interval(start, end, count, distribution)
format_date(field, pattern, locale)
if_equals(field, value, then_rule, else_rule)
```

第二版再考虑更复杂的条件组合。所有操作必须具备：输入类型、输出类型、空值策略、错误码和确定性测试。

## 八、运行阶段和冻结策略

同一个“当前日期”在预览、正式执行和重试时可能不同。建议拆成三个阶段：

### 8.1 编辑预览

- 展示临时计算值；
- 明确标记“预览值，执行时冻结”；
- 修改依赖字段时实时重算；
- 不把预览值直接写入正式档案。

### 8.2 执行冻结

- 任务开始时创建唯一 `execution_clock`；
- 同一批次所有记录共享同一个冻结时刻，避免跨午夜不一致；
- 派生规则在必填校验和公文装配之前执行；
- 结果写入 `resolved_entity_data`，原始手工值和规则仍保留。

### 8.3 重试与重放

- 默认沿用原执行会话的冻结时钟和规则版本，保证幂等；
- 若用户选择“按当前时间重新计算”，必须创建新 attempt 并保留差异；
- 不能让失败重试把昨天的公文日期静默改成今天。

现有 `ExecutionSessionSnapshot.created_at` 可以演进为冻结时钟来源，但必须补充本地时区、规则版本和日历版本。

## 九、人工覆盖和确认门禁

每个自动字段应有四种状态：

```text
手工填写
自动建议（待确认）
自动计算（已冻结）
手工覆盖自动值
```

建议默认策略：

| 字段 | 推荐默认 | 是否自动写正式稿 |
| --- | --- | --- |
| 处理日期/生成时间 | 执行时钟 | 可以 |
| 归档时间 | 归档事件时钟 | 可以 |
| 印发日期 | 实际印发事件；没有事件时只给建议 | 需确认 |
| 成文日期 | 会议通过/签发事件或人工输入 | 不得盲取 today |
| 会议时间 | 人工或日历/OA 事件 | 不得盲取 now |
| 计划中间节点 | 显式规则计算 | 标记为计划值 |
| 内容语义估算的节点 | 可选智能建议 | 必须人工确认并记录置信度 |

“按照正文内容大致估一个时间”与“按确定参数计算时间”必须分开：前者属于不确定推断，不能进入基础规则引擎的自动正式值。

## 十、界面建议

在字段行的值输入区旁增加“值来源”入口，而不是继续堆独立按钮：

```text
值来源：手工填写 / 当前日期 / 当前时间 / 引用字段 / 日期计算 / 节点估算
```

选择规则后显示紧凑摘要：

```text
{{印发日期1}}
来源：执行日期（Asia/Shanghai） · 执行时冻结 · 可覆盖

{{复核截止日期1}}
来源：成文日期1 + 5 个工作日 · CN_OFFICIAL_2026 · 待确认
```

必要交互：

- “预览计算结果”；
- “转为手工值”；
- “恢复自动规则”；
- “查看计算依据”；
- 依赖字段被删除或改名时明确报错；
- 循环依赖时阻止保存；
- 批量任务显示哪些字段会按每条记录计算，哪些共享同一执行时钟。

## 十一、执行架构建议

新增独立模块：

```text
src/config/material_field_rules.py
src/shared/engine/material_field_resolver.py
src/shared/engine/business_calendar.py
src/shared/engine/material_field_trace.py
```

推荐执行顺序：

```text
读取资料包
  -> 归一化字段定义和类型
  -> 构建依赖 DAG
  -> 检查缺失依赖 / 循环
  -> 注入 execution_clock 和 calendar registry
  -> 按拓扑顺序求值
  -> 应用人工覆盖
  -> 生成 resolved_entity_data
  -> required 校验
  -> 公文 assembly
  -> 报告和归档凭据
```

不要把这项逻辑放进 `official_document_assembly.py`。装配器应继续只负责把已经解析好的值写入母版，规则求值应当是可被其他场景复用的上游能力。

## 十二、兼容与迁移

### 12.1 向后兼容

- 没有 `field_rules` 的旧资料包继续按手工字符串处理；
- `entity_data` 保留为最终可消费映射；
- 新增 `field_definitions`、`field_rules`、`resolved_field_traces`；
- 老的 `process_date` 占位符继续可用，但改为消费注入时钟；
- 资料包版本升级时提供显式迁移，不静默修改旧日期。

### 12.2 自定义编号字段

- `{{发文机关1}}`继续映射标准 `organization`；
- `{{发文机关2}}`等自定义字段可以拥有独立规则；
- 系列字段可选择“共享同一规则”或“每项独立规则”；
- 删除首项后，规则依赖不能仅靠显示序号重排，必须依赖稳定 `field_id`。

## 十三、优先级建议

### P0：必须先补

1. 类型化字段值：date、datetime、duration、text、list；
2. 可注入且可冻结的执行时钟和明确时区；
3. `manual / constant / today / now / copy / add_days / format / coalesce`；
4. 依赖 DAG、循环检测、缺失依赖错误；
5. 人工覆盖、恢复自动和计算来源记录；
6. 在 required 校验前统一求值；
7. 预览、正式执行、重试的冻结语义。

### P1：高价值补充

1. 版本化工作日历和组织覆盖；
2. 工作日加减、月末、季度末、下一个工作日；
3. 时间中点、工作日中点、等分节点；
4. 条件规则和字段回退；
5. 批量任务的统一时钟与逐记录依赖；
6. 计算凭据进入处理报告和归档 manifest。

### P2：高级能力

1. OA/日历/签批/归档事件连接器；
2. 递归计划、SLA、组织工作时段；
3. 按权重估算多阶段里程碑；
4. 内容语义辅助估算，但必须标注置信度并人工确认；
5. 规则模板库和组织级共享规则。

## 十四、最低验收测试

### 时间与时区

```text
[ ] 同一 execution session 内 today/now 完全一致
[ ] 跨午夜批量任务不出现两种日期
[ ] UTC 与 Asia/Shanghai 转换正确
[ ] 夏令时地区的不存在时间和重复时间有明确策略
[ ] 重试默认复用原冻结时钟
```

### 日历

```text
[ ] 2026 年调休周末可识别为工作日
[ ] 法定假日不计入工作日
[ ] 组织覆盖日历可以增加或取消工作日
[ ] 缺少目标年份日历时按策略阻止或警告
[ ] 日历版本写入计算凭据
```

### 派生节点

```text
[ ] 自然时间中点和工作日中点分别测试
[ ] 奇数日期区间的取整方向明确
[ ] 起止相等、开始晚于结束、空值均有稳定错误码
[ ] 等分节点保持单调且不越过终点
[ ] 权重总和非法时阻止执行
```

### 依赖与覆盖

```text
[ ] A -> B -> C 按拓扑顺序求值
[ ] A -> B -> A 循环依赖被阻止
[ ] 删除依赖字段后规则进入明确错误状态
[ ] 人工覆盖后不再被自动刷新覆盖
[ ] 恢复自动后重新计算并记录新 trace
```

### 公文业务边界

```text
[ ] 成文日期不会因单纯运行程序而自动变为今天
[ ] 联合行文最后签发日期规则可由显式事件配置表达
[ ] 印发日期与成文日期可独立
[ ] 自定义编号字段和内置字段均可使用规则
[ ] 正式 Word、内部审阅稿和归档 manifest 使用同一冻结值
```

## 十五、最终判断

系统确实还需要继续补充逻辑，但不宜继续以“字段旁增加一个特殊按钮”的方式零散实现。

最重要的下一步是 P0：建立类型化字段规则、注入执行时钟、依赖 DAG、人工覆盖和计算 trace。完成这一层后，“当前日期”“当前时间”“日期加减”“中间节点”等只是受限操作符；没有这一层，后续每增加一种时间逻辑都会产生新的状态不一致、重试漂移和审计缺口。

工作日历和中间节点计算应作为 P1；基于内容语义的时间估算应留到 P2，并始终作为待确认建议，而不是自动写入正式公文。
