# 场景样式控件与模板管理高度复用深度分析

日期：2026-06-28

范围：继续审计场景规划页与模板管理页在样式、控件、详情页骨架、状态同步和预览语义上的一致性。本文不重复上一轮“文案可读性”和“功能边界”的分析，重点回答一个更底层的问题：为什么场景页看起来已经用了模板管理同款控件，但仍没有达到优秀设计需要的高度复用。

## 1. 核心结论

当前状态不是“完全不一致”，而是停在了一个很容易误判为完成的中间层：

| 层级 | 当前状态 | 判断 |
| --- | --- | --- |
| 字段语义 | 已经有 `control_contract_registry` 和运行时一致性审计 | 基本成立 |
| 底层控件 | 场景页已使用 `FontCombo`、`SizeCombo`、`SpacingInput`、`IndentInput`、`ToggleSwitch` 等 | 部分成立 |
| 表单布局 | 场景页用了 `template_form_row`、`TemplateFormStack`，但很少用 `InspectorForm` | 不完整 |
| 详情页骨架 | 模板页有 `TemplateSummaryCard + InspectorForm + 语义分组卡片`，场景页多为 `Card + SummaryGrid + 手写行` | 不一致 |
| 样式编辑器 | 模板正文排版和场景分区覆盖各自搭了一套字体、字号、缩进、行距、段距编辑器 | 低复用 |
| 状态语义 | 模板页有保存、恢复、快照、导航定位；场景页多为即时写入 `SceneWorkspace` | 不一致 |
| 预览语义 | 模板页负责“文档长什么样”，场景页负责“这次任务怎么处理”；两者已能跳转，但编辑器和状态模型没有同源 | 未闭环 |

所以这轮的判断是：场景页现在达到了“同名字段、同类输入控件”的一致性，但没有达到“同一个控件系统、同一个编辑体验、同一套状态契约”的高度复用。

如果继续只调文案、换标签或增减说明文字，视觉上会更干净，但架构上仍然会是两套实现。真正要走向优秀设计，需要把模板管理中的“样式编辑能力”抽成可复用组件，让模板页和场景页成为两个不同 owner，而不是两套平行 UI。

## 2. 模板管理已经形成的可复用骨架

模板管理页不是简单堆控件，它已经形成了比较稳定的产品语言。

### 2.1 摘要卡

模板详情页普遍使用 `TemplateSummaryCard`：

- `src/shared/ui/template_summary_card.py:38`
- `src/ui/panels/template_style_detail.py:180`
- `src/ui/panels/template_page_detail.py:188`
- `src/ui/panels/template_table_detail.py:129`

这个摘要卡负责在详情页顶部回答“当前配置结果是什么”，并承载恢复、保存等操作按钮。它不是普通 `Card` 的视觉替代品，而是详情页的状态入口。

### 2.2 表单系统

模板管理的表单布局集中在：

- `src/shared/ui/inspector_form.py:18`
- `src/shared/ui/template_form_layout.py:121`
- `src/shared/ui/template_form_layout.py:233`

`InspectorForm`、`TemplateFormGrid`、`TemplateFormStack`、`template_form_row` 组合起来，解决了以下问题：

- label 宽度与对齐；
- 短字段同排；
- 窄屏自动堆叠；
- 关联字段相邻；
- 控件高度和间距统一；
- 同一个详情页中多张卡片仍保持一致节奏。

### 2.3 正文排版编辑器

正文排版页已经把样式参数分成三组：

- 文字样式：中文字体、英文字体、字号、字形；
- 对齐与缩进：对齐、特殊缩进、左缩进、右缩进；
- 行距与段距：行距类型、行距值、段前、段后。

相关实现集中在：

- `src/ui/panels/template_style_detail.py:280`
- `src/ui/panels/template_style_detail.py:301`
- `src/ui/panels/template_style_detail.py:327`
- `src/ui/panels/template_style_detail.py:339`
- `src/ui/panels/template_style_detail.py:380`
- `src/ui/panels/template_style_detail.py:423`

这部分已经包含大量可以被复用的能力：

- `FontCombo`、`SizeCombo`、`SpecialIndentInput`、`IndentInput`、`SpacingInput` 的组合方式；
- 行距类型变更后，行距值输入框的可编辑状态和单位提示；
- 段前/段后的 `auto` 禁用态；
- 字号变化后缩进输入的 reference size 同步；
- `StyleConfig` 到 UI 的同步；
- UI 到 `StyleConfig` 的回写；
- 导航定位字段映射。

### 2.4 导航和定位

模板正文排版已经有 `focus_navigation_field()`：

- `src/ui/panels/template_style_detail.py:487`

它把 `body.font_cn`、`body.size_pt`、`body.left_indent`、`body.line_spacing` 等字段映射到具体控件。这说明模板页已经不只是“显示控件”，而是在承担跨页问题定位、用户回修和执行反馈的终点。

场景页如果继续自建样式覆盖编辑器，就会很难自然复用这套定位能力。

## 3. 场景规划页目前的真实差距

### 3.1 场景页只复用了低层零件，没有复用详情页骨架

`scene_panel.py` 引入了部分模板表单工具：

- `src/ui/panels/scene_panel.py:97`
- `src/ui/panels/scene_panel.py:104`
- `src/ui/panels/scene_panel.py:106`

但从检索结果看，场景页没有直接使用 `TemplateSummaryCard` 或 `InspectorForm`。大量详情页仍然是：

- `_SimpleFormDetail + Card + SummaryGrid + template_form_row`
- 手写描述 label；
- 手写分组；
- 手写控件 enabled/visible 逻辑；
- 手写摘要刷新。

证据：

- `_SimpleFormDetail`：`src/ui/panels/scene_panel.py:1331`
- `_ScopeDetail`：`src/ui/panels/scene_panel.py:2225`
- `_TableChartDetail`：`src/ui/panels/scene_panel.py:2885`
- `_PageElementsDetail`：`src/ui/panels/scene_panel.py:2979`
- `_FormulaDetail`：`src/ui/panels/scene_panel.py:3106`
- `_CleanupDetail`：`src/ui/panels/scene_panel.py:3225`
- `_ContentDetail`：`src/ui/panels/scene_panel.py:3386`
- `_OutputDetail`：`src/ui/panels/scene_panel.py:3704`

这导致场景页虽然有同款输入控件，却不像模板管理页的同类详情页。

### 3.2 `_ScopeDetail` 混合了两个不同任务

`_ScopeDetail` 当前同时承担：

1. 选择本次处理哪些文档分区；
2. 为分区开启独立样式；
3. 编辑分区的字体、字号、字形、对齐、缩进、行距、段距；
4. 根据模板默认样式计算显示值；
5. 将覆盖结果写回 `SceneWorkspace.section_styles`。

这些任务不应该全部塞在“处理范围”下。处理范围回答的是“改哪里”，样式覆盖回答的是“这些地方相对模板默认样式怎么改”。两者有关联，但不是同一个板块。

当前用户看到的是一个又长又密的配置区，很容易误解为“场景页也可以全面编辑模板样式”。这会破坏模板管理的边界。

### 3.3 场景分区样式编辑器是模板正文排版编辑器的平行复制

场景页在 `_build_section_style_editor()` 中重新创建了一套样式控件：

- `src/ui/panels/scene_panel.py:2316`
- `src/ui/panels/scene_panel.py:2337`
- `src/ui/panels/scene_panel.py:2342`
- `src/ui/panels/scene_panel.py:2366`
- `src/ui/panels/scene_panel.py:2371`
- `src/ui/panels/scene_panel.py:2386`
- `src/ui/panels/scene_panel.py:2400`
- `src/ui/panels/scene_panel.py:2412`
- `src/ui/panels/scene_panel.py:2425`
- `src/ui/panels/scene_panel.py:2468`

这些控件与模板正文排版高度重合，但不是同一个组件。同步逻辑也重新写了一遍：

- `_sync_style_editor()`：`src/ui/panels/scene_panel.py:2595`
- `_set_style_editor_enabled()`：`src/ui/panels/scene_panel.py:2674`
- `_sync_section_spacing_editor()`：`src/ui/panels/scene_panel.py:2698`
- `_sync_section_line_spacing_editor()`：`src/ui/panels/scene_panel.py:2709`

这就是当前“不够优秀”的根因之一：视觉上看似一致，代码上却是两套编辑器。任何一个行距、段距、缩进、禁用态、对象名、导航定位、窄屏布局上的优化，都需要改两处，并且很容易产生微差。

### 3.4 场景页的状态语义与模板页不一致

模板正文排版页有：

- entry snapshot；
- 恢复；
- 保存；
- `set_save_enabled()`；
- `focus_navigation_field()`；
- `_editable_style()`；
- `_sync_from_template()`；
- `_on_form_edited()`。

场景页分区覆盖则更像即时编辑：

- 勾选分区；
- 开启分区独立样式；
- 选择编辑分区；
- 改控件后立即写入 `SceneWorkspace`；
- 发出 `scope_changed`。

即时编辑并不是错，但它没有被包装成与模板页一致的“编辑会话”体验。用户很难判断：

- 当前是跟随模板，还是覆盖模板；
- 覆盖来自哪里；
- 修改是否只影响本场景；
- 是否能恢复到模板默认；
- 是否会影响模板管理中的默认格式；
- 切换模板后覆盖如何更新；
- 输出时实际使用的是哪份样式。

这些都不应该靠长描述解释，而应该靠板块边界、摘要、控件状态和可恢复动作表达。

## 4. 现有一致性审计为什么还不够

项目里已经有很有价值的一致性约束：

- `src/config/control_contract_registry.py:122`
- `src/config/scene_control_runtime_consistency_audit.py:240`

例如：

- `body.font_cn` 同时映射模板正文和场景分区样式；
- `body.size_pt` 同时映射模板字号和场景分区字号；
- `body.left_indent`、`body.right_indent`、`body.line_spacing` 等都有跨模板和场景的契约；
- N2.175 审计覆盖了字体字号、缩进、特殊缩进、行距、段距的运行时一致性。

这类审计解决的是“字段有没有对上”和“运行时有没有消费”。它们不能证明以下事情：

- 场景页和模板页是否使用同一个样式编辑器组件；
- 场景详情页是否使用同一个摘要卡骨架；
- 同类控件是否具有相同 label 对齐和窄屏布局；
- 禁用态、继承态、覆盖态是否用同一种交互表达；
- 同名字段是否支持同一套导航定位；
- 恢复默认、保存、脏状态是否遵守同一套用户预期；
- 场景页是否在信息架构上把“处理范围”和“样式覆盖”混在一起。

因此后续不能只继续扩展 `control_contract_registry`。它应该保留，但需要补一个更高层的 UI 复用契约。

## 5. 应该建立的新分层

### 5.1 第一层：字段契约

继续保留现有 `ControlContract`：

- 字段 id；
- label；
- 单位；
- 模板路径；
- 场景路径；
- 运行时消费者；
- 报告字段；
- 关联测试。

这一层回答“这个参数叫什么、写到哪里、谁消费”。

### 5.2 第二层：编辑器组件

新增共享组件，建议命名为 `ParagraphStyleEditor` 或 `StyleConfigEditor`。

职责：

- 创建字体、字号、字形、对齐、缩进、行距、段距控件；
- 使用 `InspectorForm`、`TemplateFormGrid`、`TemplateFormStack` 统一布局；
- 接收一个 `StyleConfig` 或等价 adapter；
- 提供 `set_style(style)`；
- 提供 `read_style()` 或通过 change signal 输出 patch；
- 提供 `set_editable(enabled, reason=None)`；
- 提供 `focus_field(field_id)`；
- 提供 `summary_items()` 或只暴露给外层 summary projection；
- 统一对象名或 field id；
- 统一行距、段距、特殊缩进、字号 reference size 的同步逻辑。

不应该做的事：

- 不直接知道 `TemplateConfig`；
- 不直接知道 `SceneWorkspace`；
- 不决定保存到模板还是场景；
- 不决定“处理范围”；
- 不决定“是否开启覆盖”。

这层回答“同一个样式怎么编辑”。

### 5.3 第三层：owner adapter

模板页和场景页只需要提供不同的 owner adapter。

模板 owner：

- 读写 `TemplateConfig.styles["body"]`；
- 管理 snapshot；
- 管理保存、恢复；
- 触发模板预览刷新；
- 提供 `body.*` 导航字段。

场景 owner：

- 读写 `SceneWorkspace.section_styles[variant_key]`；
- 读取模板默认样式作为 inherited display style；
- 管理“跟随模板 / 本场景覆盖”；
- 只影响当前场景；
- 提供 `section_styles.*` 或 `body.* + variant` 的导航字段。

这层回答“同一个编辑器改的是哪份数据”。

### 5.4 第四层：详情页骨架

需要把模板管理成熟的详情页骨架泛化为场景也能使用的组件。可以有两种做法：

1. 继续复用 `TemplateSummaryCard`，把它理解为“配置详情摘要卡”，而不是模板专属；
2. 重命名或包一层 `ConfigSummaryCard`，内部复用 `TemplateSummaryCard` 的样式和 action button。

无论命名如何，场景详情页都应逐步从 `_SimpleFormDetail + 普通 Card` 迁移到：

- 顶部 summary card；
- 下方 1 到 3 个语义编辑卡；
- 表单卡内部使用 `InspectorForm`；
- 行为按钮使用 summary action button；
- 摘要内容来自统一 projection，而不是手写散落 label。

这层回答“同类详情页看起来和操作起来是否一致”。

## 6. 推荐的信息架构调整

### 6.1 场景页不应复制模板管理

场景页的边界仍然应该是：

- 选择任务；
- 选择处理范围；
- 决定哪些能力启用；
- 对模板默认样式做少量有业务理由的覆盖；
- 管理输入、校验、对象保护和输出；
- 查看执行风险与交付预期。

它不应该变成第二个模板管理页。

### 6.2 把“处理范围”和“样式覆盖”拆开

建议拆成两个相邻但独立的详情板块：

| 板块 | 回答的问题 | 控件 |
| --- | --- | --- |
| 处理范围 | 这次任务处理哪些文档部分？ | 分区选择、范围摘要、影响说明 |
| 样式覆盖 | 哪些分区需要不跟随模板默认样式？ | 覆盖开关、编辑分区、共享 `ParagraphStyleEditor`、恢复跟随模板 |

这样用户会自然理解：

- 默认情况是“跟随模板”；
- 只有业务需要时才开启覆盖；
- 覆盖只属于本场景；
- 想全面调整文档外观，应进入模板管理。

### 6.3 样式覆盖板块的推荐交互

顶部摘要：

- 当前状态：全部跟随模板 / 已覆盖 2 个分区；
- 覆盖范围：摘要、附录、参考文献等；
- 基准模板：当前关联模板；
- 主动作：恢复跟随模板。

主体：

- 分区选择：只显示已在处理范围中启用的分区；
- 覆盖开关：`跟随模板` / `本场景单独设置`；
- 编辑器：开启覆盖后显示或启用共享 `ParagraphStyleEditor`；
- 状态提示：短句即可，例如“仅影响当前场景输出，不修改模板默认格式”。

要删除的冗余文本：

- 长篇解释控件含义；
- 重复说明“手动控制所有功能开关与处理范围”；
- 内部术语式的契约说明；
- 把 template、scene、material、output 这类内部统计直接放进普通用户主路径。

保留的必要文本：

- 继承/覆盖状态；
- 修改影响范围；
- 不能编辑的原因；
- 进入模板管理的动作。

## 7. 推荐组件重构方案

### 7.1 抽出 `ParagraphStyleEditor`

建议位置：

- `src/shared/ui/paragraph_style_editor.py`

建议 API：

```python
class ParagraphStyleEditor(QWidget):
    style_changed = Signal()

    def set_style(self, style: StyleConfig | None) -> None: ...
    def write_to_style(self, style: StyleConfig) -> None: ...
    def set_editable(self, enabled: bool, reason: str | None = None) -> None: ...
    def focus_field(self, field_id: str) -> bool: ...
    def set_object_name_prefix(self, prefix: str) -> None: ...
```

内部复用：

- `FontCombo`
- `SizeCombo`
- `ToggleSwitch`
- `SpecialIndentInput`
- `IndentInput`
- `SpacingInput`
- `StyledComboBox`
- `InspectorForm`
- `TemplateFormGrid`
- `TemplateFormStack`
- `template_form_row`
- `template_form_pair_row`

迁移后，`template_style_detail.py` 和 `scene_panel.py` 不应再分别创建同一组样式控件。

### 7.2 模板正文排版页变成 owner shell

`TemplateStyleDetail` 保留：

- `TemplateSummaryCard("正文排版")`；
- 恢复/保存按钮；
- snapshot；
- 模板读写；
- 预览刷新；
- 导航高亮调用。

它不再直接关心字体、字号、缩进、行距这些控件怎么排布，而是使用 `ParagraphStyleEditor`。

### 7.3 场景分区覆盖变成 owner shell

场景页保留：

- 当前 scene；
- 当前 template；
- 可覆盖分区；
- 继承模板 / 本场景覆盖的开关；
- variant 选择；
- `SceneWorkspace.section_styles` 回写；
- `scope_changed` 或更精确的 `style_override_changed`。

它不再直接创建 `_section_font_cn`、`_section_size_combo`、`_section_line_value` 这些控件，而是使用同一个 `ParagraphStyleEditor`。

### 7.4 给场景详情页建立共享 detail shell

建议新增：

- `SceneDetailShell`
- 或泛化为 `ConfigDetailShell`

职责：

- 统一 summary card；
- 统一 detail card spacing；
- 统一空态、禁用态、可编辑态；
- 统一 action button；
- 统一 summary projection 接入。

然后分批迁移：

1. `_ScopeDetail` 和新 `StyleOverrideDetail`；
2. `_TableChartDetail`；
3. `_PageElementsDetail`；
4. `_FormulaDetail`；
5. `_ContentDetail`；
6. `_OutputDetail`。

不要一次性重写所有详情页。先把样式覆盖这个最明显的低复用点打透。

## 8. 链路闭环检查

### 8.1 已经打通的部分

| 链路 | 状态 |
| --- | --- |
| 场景选择与模板关联 | 已有 |
| 场景概览到模板预览的语义跳转 | 已推进 |
| 控件字段契约 | 已有 |
| 运行时一致性审计 | 已有 |
| 样式覆盖写入 `SceneWorkspace.section_styles` | 已有 |
| 输出侧消费分区样式覆盖 | 已有审计基础 |

### 8.2 未完全打通的部分

| 链路 | 缺口 |
| --- | --- |
| 模板正文编辑器与场景分区编辑器 | 没有共享同一个 editor |
| 模板详情骨架与场景详情骨架 | 场景页未系统使用 summary card + InspectorForm |
| 模板保存/恢复与场景覆盖恢复 | 语义不一致 |
| 字段导航定位 | 模板页成熟，场景覆盖未形成同源接口 |
| 禁用态说明 | 仍靠局部 hint，缺少统一 inherited/override 状态 |
| 窄屏布局验收 | 底层布局部分复用，但 editor 级验收不足 |
| 视觉预览 | 场景页已能跳模板预览，但没有共享编辑器状态模型 |

### 8.3 真正闭环的标准

同一个样式参数从用户到输出应具备以下链路：

1. 用户在模板管理或场景覆盖中看到同一种控件组合；
2. 控件来自同一个 `ParagraphStyleEditor`；
3. 模板 owner 写 `TemplateConfig.styles["body"]`；
4. 场景 owner 写 `SceneWorkspace.section_styles[variant]`；
5. `control_contract_registry` 能追踪字段语义；
6. 运行时审计能证明输出消费；
7. 预览或摘要能说明最终生效来源；
8. 问题定位能跳回同一个 field id 对应的控件；
9. 继承/覆盖/禁用态有统一表达；
10. 窄屏和桌面布局都没有溢出或错位。

现在缺的是第 2、7、8、9、10 项。

## 9. 优先级建议

### P0：先建立禁止继续复制的守门

目标不是马上大改，而是先防止继续扩大两套实现。

建议新增静态测试或轻量源码守门：

- `scene_panel.py` 迁移后不允许在分区样式编辑区域直接实例化 `FontCombo`、`SizeCombo`、`SpecialIndentInput`、`IndentInput`、`SpacingInput`；
- 分区样式编辑必须通过共享 editor；
- 共享 editor 必须暴露 field map；
- `TemplateStyleDetail` 和场景样式覆盖 detail 必须引用同一个 editor 类。

### P1：抽出共享样式编辑器

这是最关键的一步。

顺序：

1. 从 `template_style_detail.py` 抽出纯 UI editor；
2. 把样式同步逻辑移动到 editor 或 editor helper；
3. `TemplateStyleDetail` 改为 owner shell；
4. 场景 `_ScopeDetail` 改为调用同一 editor；
5. 保持现有外部行为不变。

这一阶段不追求视觉大变，只先让代码事实变成“同一个编辑器，两种 owner”。

### P1：拆分处理范围与样式覆盖

在共享 editor 稳定后，把 `_ScopeDetail` 拆成：

- `ScopeDetail`：只处理分区范围；
- `StyleOverrideDetail`：处理分区覆盖。

左侧导航也应从“处理范围”下面隐含样式覆盖，调整为更清晰的两个入口或一个入口内两个明确子块。

### P2：场景详情页骨架归一

逐步把 `_SimpleFormDetail` 的普通卡片迁移到共享 detail shell：

- 顶部统一 summary card；
- 表单统一 `InspectorForm`；
- 关联字段同排；
- 禁用态和提示统一；
- action button 复用模板 summary action 样式。

优先处理与模板参数最接近的页面：

1. 表格与图表；
2. 页眉页脚、目录、水印；
3. 公式；
4. 输入资料；
5. 输出交付。

### P2：补 UI 级一致性验收

建议增加以下测试：

- editor 结构测试：模板和场景使用同一个 `ParagraphStyleEditor`；
- field map 测试：`body.font_cn`、`body.size_pt`、`body.line_spacing` 等能定位到 editor 控件；
- 禁用态测试：跟随模板时 editor 禁用，开启覆盖后可编辑；
- 数据回写测试：同一 editor 在模板 owner 下写模板，在场景 owner 下写场景；
- 响应式布局测试：620px 宽度下两列表单能正常堆叠；
- 源码守门：场景页不再复制一组段落样式输入控件。

## 10. 非目标

为了避免后续再次走偏，需要明确这些不是目标：

- 不把场景页做成第二个模板管理页；
- 不让场景覆盖直接修改模板默认格式；
- 不在场景概览塞完整模板预览面板；
- 不把水印、输出、资料 schema、plugin gate 等运行时能力塞回模板管理；
- 不用更多说明文字掩盖组件边界不清；
- 不为了视觉接近而继续复制模板页代码。

## 11. 推荐最终体验

理想状态下，用户面对场景页时应形成这样的理解：

1. 模板管理决定文档默认长什么样；
2. 场景规划决定这次任务处理什么、怎么处理、输出什么；
3. 场景可以对少数分区做本次任务专属覆盖；
4. 覆盖默认跟随模板，开启后才可编辑；
5. 覆盖编辑器和模板正文编辑器长得一样、行为一样；
6. 场景覆盖不会改坏模板；
7. 想全面调整样式，就去模板管理；
8. 输出时系统能说清楚最终生效的是模板默认还是场景覆盖。

这比“把所有参数都显示出来”更重要。优秀设计不是把能力摊开，而是让用户在正确边界里做正确动作。

## 12. 落地路线

### 第一步：组件抽取

- 新增 `src/shared/ui/paragraph_style_editor.py`；
- 从 `TemplateStyleDetail` 抽取 UI 和同步逻辑；
- 保留原页面结构和视觉，不做大范围重排；
- 先保证模板页行为不变。

### 第二步：模板页接入

- `TemplateStyleDetail` 使用 `ParagraphStyleEditor`；
- 恢复、保存、snapshot、summary 仍在详情页；
- `focus_navigation_field()` 委托给 editor。

### 第三步：场景页接入

- `_ScopeDetail` 暂时保留，但内部样式编辑区换成 `ParagraphStyleEditor`；
- 删除 `_section_font_cn`、`_section_size_combo`、`_section_line_value` 等重复字段；
- 将 `_sync_section_spacing_editor()`、`_sync_section_line_spacing_editor()` 收敛到共享 editor；
- 保持 `SceneWorkspace.section_styles` 数据结构不变。

### 第四步：板块拆分

- 从 `_ScopeDetail` 拆出 `StyleOverrideDetail`；
- 左侧导航或子导航明确显示“处理范围”和“样式覆盖”；
- 摘要卡分别回答“处理哪些部分”和“哪些部分覆盖模板”。

### 第五步：详情骨架迁移

- 新建 `ConfigDetailShell` 或 `SceneDetailShell`；
- 先迁移 `_TableChartDetail`、`_PageElementsDetail`；
- 再迁移公式、输入、输出等运行时详情；
- 保留场景运行时能力的边界，不混进模板样式。

### 第六步：验收与防回退

- 补源码守门；
- 补 editor 行为测试；
- 补窄屏布局截图或结构测试；
- 补导航定位测试；
- 更新 `control_contract_registry` 的 UI component evidence，记录共享 editor 类名。

## 13. 最终判断

现在的问题不是“还缺几个控件”，而是“控件系统的所有权还没有抽出来”。模板管理已经证明了一个更好的形态：摘要卡、语义分组、表单栅格、保存恢复、字段定位和预览上下文共同组成一个详情页体验。

场景页目前复用了输入控件，却没有复用这个详情页体验。尤其是分区样式覆盖，它事实上是模板正文排版编辑器的另一个 owner，却被实现成了另一套 editor。

下一轮真正值得做的不是继续精修文案，而是完成“一个样式编辑器，两个数据 owner”的重构：

- 模板 owner：编辑默认格式；
- 场景 owner：编辑本场景覆盖；
- editor：完全共享；
- 详情页骨架：逐步共享；
- 运行时契约：继续用现有审计闭环。

做到这一步，场景规划和模板管理才会从“看起来有点像”进入“本质上是一套系统”。
