# 高层场景能力矩阵 V38 完整产品能力矩阵与高频边界深化规划

日期：2026-06-19

## 1. 文档定位

本文回应“更高层的场景能力矩阵目前功能点过于不完善，不能出现高频适用场景遗漏或者边界不清晰”的要求。

V29-V37 已经把矩阵从“场景入口清单”推进到自动化证据链：coverage pack、planned family、request-cell、sample fixture、InputSourceProfile、CountProfile、MaterialSchema、DeliveryPreset、Formula/output/watermark 归属、ObjectPreflight 动作闭环、dashboard、drilldown、release gate。V38 不再继续堆入口，而是定义更严格的完整产品能力矩阵：

```text
用户任务
-> 文档/业务族
-> 工作流族
-> 承载层
-> 能力槽位状态
-> Word/OpenXML 风险
-> UI/执行/报告/fixture/release gate 证据
-> 成功/降级/失败/人工门 journey
-> 明确边界和不承诺项
```

核心结论：

```text
当前顶层 pack 覆盖面基本稳定；
真正不完整的是 pack 下面的产品能力、真实用户旅程、修复入口、交付执行和边界交互。
```

因此，后续完善方向不是先新增第 13、第 14 个顶层场景，而是把现有 12 个 pack 和 15 个 family 按更细的能力槽位补成可验收产品。

## 4. V38 对“完整”的重新定义

V38 不把“有审计源、release gate passed、dashboard 可见”当成完整。完整必须同时满足四层。

| 层 | 定义 | 最低证据 |
| --- | --- | --- |
| 覆盖完整 | 高频用户话术能落到 pack、family、profile、schema、preset、plugin、handoff 或 negative | request-cell、task lexicon、ambiguous/negative/manual 样本 |
| 链路完整 | 输入事实源、模板基线、控件、规则、资料、对象风险、交付、报告能互相追踪 | dashboard、drilldown、source evidence、release gate |
| 产品完整 | 用户能在 UI 中看见、配置、确认、修复和复盘 | ScenePanel/Workbench 控件、issue queue、artifact browser、repair route |
| 旅程完整 | 成功、降级、失败/人工门三类路径均有 fixture 和报告证据 | journey fixture、report anchor、manual confirmation、blocking/skip/preserve behavior |

因此，V38 的 Green/L5 准入是：

```text
不是“没有 issue”，
而是“关键高频路径都有可运行、可解释、可修复、可交付、可回放的证据”。
```

## 5. 五轴防遗漏模型

以后审阅任何新需求，必须同时过五条轴。

### 5.1 用户话术轴

用户会怎么说：

- “帮我把论文按学校格式整理，顺便看字数和参考文献。”
- “英文 manuscript 投稿前检查 display items 和 cover letter。”
- “把这些题生成学生版、教师版、答案版。”
- “把人员 Excel 批量套进证明模板。”
- “合同审阅稿和签署稿都导出来，别破坏修订和批注。”
- “扫描 PDF 能不能转 Word 再排版。”
- “报价方案到底走售前方案还是财务报价？”

要求：每类高频话术必须明确为 matched、ambiguous、manual boundary、handoff 或 negative。

### 5.2 文档/业务族轴

这件事属于哪个业务族：

- 通用排版、个人文档
- 中文学术、英文投稿
- 教育试卷、培训资料
- 标书、资质、附件包
- 公文、会议、制度
- 技术长文档、SOP、书稿
- 项目申报、产品售前
- 合同、签署包
- HR 批量、固定表单、证书套打
- 财务报价、披露、IP、法律、医疗、双语等专业边界
- PDF/OCR、LaTeX、AI、复杂图形等导入或插件边界

要求：业务族不一定新增顶层入口，但必须有稳定承载层。

### 5.3 工作流轴

用户真正要完成什么工作：

- 快速规范化
- 结构识别和范围定位
- 资料填充和附件 inventory
- 多版本显隐
- 批量生成和失败隔离
- 多口径计数和规则合规
- 对象预检和降级/阻断
- 审阅对比和修复确认
- 提交包、归档包和 artifact 浏览
- 插件/人工门 handoff

要求：每个 pack/family 必须声明启用、可选、禁用、人工门或插件化的工作流。

### 5.4 Word/OpenXML 风险轴

这件事触碰哪些 Word 内部结构：

- `word/document.xml` 中的段落、run、表格主体。
- `word/styles.xml` 中的样式和模板基线。
- `word/numbering.xml` 中的标题和列表编号。
- `w:tbl`、`w:tr`、`w:tc`、`w:trHeight` 中的表格和固定行高。
- `w:sectPr`、headers、footers、页码、分节。
- footnotes、endnotes、comments、revisions。
- text box、shape、drawing、media、image rels。
- `w:sdt` 内容控件。
- fields、TOC、PAGE、REF、交叉引用。
- OLE、embedded packages、macros、ActiveX、relationships。

要求：每个风险面必须有 detect、warn、block、skip、preserve、manual、repair、report 中至少一种清晰策略。

### 5.5 交付/边界轴

最终给用户什么，以及不能承诺什么：

- DOCX、PDF、ZIP、report、manifest、compare、intermediate。
- 学生版/教师版/答案版，正式/内部/归档，审阅/签署。
- 单文件、多文件、多记录、多模板、多版本。
- 不做法律、财务、审计、医疗、专利授权、翻译质量、AI 内容质量判断。
- 不承诺 PDF/OCR、完整 LaTeX 工程、复杂图形的无损自动转换。

要求：所有不承诺项必须进入 UI、报告或 manual/plugin gate，不能只藏在文档里。

## 6. V38 的 28 个产品能力槽位

V35 的 20 个槽位已经覆盖骨架。V38 将其拆成 28 个更适合产品落地的槽位。每个高频场景不需要全部 enabled，但每个槽位都必须有明确状态：

```text
enabled / optional / inherited / disabled / manual_gate / plugin_gate / handoff / negative / future_slice
```

| 槽位 | 必须回答 | 稳定承载层 | 缺失风险 |
| --- | --- | --- | --- |
| 1. UserIntent | 用户自然说法和 request-cell 状态是什么 | request-cell、task lexicon | 高频话术遗漏 |
| 2. ScenarioFamily | 属于哪个 pack/family/profile | coverage manifest、family registry | 顶层入口膨胀或错归属 |
| 3. AmbiguityDecision | 是否存在相邻场景歧义，如何澄清 | ambiguous boundary、clarification UI | 产品手册/报价/证书/通知等错路由 |
| 4. InputFactSource | 真正机器事实源是什么 | InputSourceProfile | 执行靠猜 |
| 5. StructuredModel | 是否有 JSON/schema/AST/Markdown 预览 | MaterialSchema、question schema、intermediate | AI/Markdown 被误当最终版式 |
| 6. TemplateBaseline | 外观基线归哪个模板 | TemplateConfig、compatible templates | 场景重新发明模板 |
| 7. ControlContract | 同名控件是否复用模板管理命名、单位、禁用语义 | control_contract_registry | UI 可配但执行不认 |
| 8. SceneControlRuntime | 场景页控件运行时是否和模板页一致 | ScenePanel、Workbench UI tests | 左右缩进、段前段后、特殊缩进语义分裂 |
| 9. FormatScope | 处理范围包括哪些章节和区域 | FormatScopeConfig | 正文、摘要、附录、参考文献误处理 |
| 10. WordStoryScope | 是否处理 header/footer/footnote/endnote/comment/revision/textbox | ObjectPreflight、scope router | Word story 漏处理 |
| 11. MaterialSchema | 字段、人员、项目、签章、图片、附件事实在哪里 | MaterialSchema | 缺资料无修复入口 |
| 12. AssetInventory | 图片、证照、签章、题图、附件角色如何管理 | AssetsPanel、material manifest | 资料包只剩文字字段 |
| 13. CountRuleProfile | 字数、词数、字符、图表、公式、参考文献口径是什么 | CountProfile | 单一字数误导用户 |
| 14. RuleSourceGovernance | 规则来源、版本、审核、适用范围如何记录 | RuleSource registry | 学校/期刊/申报规则不可复盘 |
| 15. FormulaPolicy | 公式片段、OMML、LaTeX fallback、低置信度如何处理 | FormulaPolicy、plugin gate | 公式被当普通文本 |
| 16. ReferenceCitation | BibTeX/CSL、引用、参考文献、交叉引用如何处理 | citation/reference configs | 学术/投稿链路断裂 |
| 17. TableAndFixedLayout | 普通表格和固定版式如何区分 | TableConfig、fixed-layout profile | `w:trHeight` 混进通用模板 |
| 18. ObjectPreflightAction | 风险对象如何 warn/block/skip/preserve/manual/repair/report | ObjectPreflight | 复杂 Word 对象被破坏 |
| 19. ContentVisibility | 答案/解析、内部/正式、审阅/签署如何显隐 | DeliveryPreset、visibility rules | 多版本内容不一致 |
| 20. DeliveryPreset | 输出版本、命名、目录、DOCX/PDF/ZIP/report/manifest 是什么 | DeliveryPreset、OutputConfig | 交付散落为开关 |
| 21. BatchJourney | 多记录失败隔离、续跑和汇总如何做 | BatchPreset | 一个失败拖垮整批 |
| 22. ReportArtifact | 报告字段、锚点、artifact drilldown 是否闭合 | report writer、drilldown | 用户无法复盘 |
| 23. RepairConfirmation | 问题队列、修复入口、人工确认是否闭合 | repair routing、Workbench issue queue | 只有 warning 没有下一步 |
| 24. FixtureJourney | 成功、降级、失败/人工门是否有样本 | sample fixture、journey fixture | 静态闭合冒充可用 |
| 25. ImportHandoff | PDF/OCR/LaTeX/AI 是否有置信度、回退和目标场景 | import handoff | 导入边界被误说成核心能力 |
| 26. ProfessionalBoundary | 法律、财务、医疗、专利、翻译质量等是否人工门 | PluginManualGate | 核心越界承诺 |
| 27. FrontendDiscoverability | 用户能否在场景页/Workbench/drilldown 找到能力和边界 | dashboard、ScenePanel、summary projection | 证据有但用户看不见 |
| 28. ReleaseGovernance | 是否进入 tests、export script、release gate、CI | release gate、workflow | 回归无法阻断 |

Green/L5 最低准入：

```text
28 个槽位均有状态；
enabled 槽位至少有 UI/执行/报告/fixture/release gate 中三类证据；
manual/plugin/negative 槽位必须有用户可见边界；
每个 P1/P1_CANDIDATE family 至少有成功、降级、失败/人工门 journey 证据；
所有共享模板控件必须通过运行时一致性验收。
```

V38 判断：表内大类已经覆盖主要高频适用场景。更大的风险不是漏掉一个大类，而是每类内部的能力槽位仍然不够产品化。

## 8. 吸收 CountEngine 技术记录

CountEngine 记录给出的关键原则必须继续进入场景矩阵：

- 不做单一“字数统计器”，而做 profile-driven multi-metric CountEngine。
- 同时保留 Word-like words、中文字符、纯汉字、英文词、含/不含空格字符、参考文献、图、表、公式、段落、章节等指标。
- 场景只绑定 profile、范围和规则来源，执行报告负责解释口径。
- 报告必须说明计入范围、排除范围、不确定项，以及与 Word/学校/投稿系统统计差异的边界。

V38 对应落点：

| 场景 | CountProfile 要求 |
| --- | --- |
| 中文学术 | 正文、摘要、参考文献、附录、图表题注、公式、脚注是否计入要 profile 化 |
| 英文投稿 | title、abstract、main text、methods、references、display items、highlights 要分项 |
| 项目申报 | 限字、附件数量、成果清单、预算表口径要可报告 |
| 试卷/教学 | 题量、分值、题型、章节、知识点、答案/解析显隐要结构化 |
| 披露/财务/ESG | 表格、附件、版本、隐藏文字、审阅/公开口径要人工门 |
| 技术长文档 | 章节、图表、公式、附录、对象风险要和报告联动 |

CountProfile 不能回流到模板控件，也不能被 MaterialSchema 吞掉。它是规则和范围口径，不是资料事实和版式外观。

## 9. 吸收试卷生成技术栈记录

试卷生成记录给出的核心路线可以泛化到所有结构化生成场景：

```text
结构化事实源
-> 人类可读预览
-> Word 模板渲染
-> Word 后处理
-> 多版本输出
-> 报告和人工确认
```

V38 吸收为五条原则：

1. AI 或外部系统只提供结构化源，核心程序负责校验、预览、渲染和导出。
2. JSON/schema 是机器事实源，Markdown 是人工预览，不应把 Markdown 当最终排版事实。
3. 学生版/教师版/答案版/解析版来自同一结构化源，通过 ContentVisibility/DeliveryPreset 控制显隐，不重复生成不同内容。
4. 通用图片能力优先于复杂学科图自动生成，复杂图进入插件或图片资产边界。
5. 公式应优先走 LaTeX/OMML/OOXML 路径，图片 fallback 必须进入报告并说明可编辑性损失。

这套原则不仅适用于试卷，也适用于合同审阅/签署、披露审阅/公开/归档、投稿初投/修回、批量个性化文档和产品/售前多版本输出。

## 10. 场景控件一致性准入

场景配置页可以根据场景组合、隐藏、禁用控件，但不能改变模板管理已经定义的同名控件语义。所有共享外观参数必须复用同一 control contract。

| 控件族 | 场景侧要求 | 不允许 |
| --- | --- | --- |
| 左缩进/右缩进 | 同行或同组展示；单位、stepper、禁用语义与模板管理一致 | 改名、改单位、拆成另一套模型 |
| 段前/段后 | 同行或同组展示；命名保持“段前/段后” | 改成前距/后距且执行链无法对应 |
| 特殊缩进 | 可交互切换无/首行/悬挂；无时禁用数值并归零 | 只显示文本或无法切换 |
| 行距类型/行距值 | 类型和值绑定；固定/多倍/最小值单位清楚 | UI 可选但执行不消费 |
| 表格固定行高 | 只在 fixed-layout profile 出现，对应 Word `w:trHeight` | 混入通用 TableConfig 模板参数 |
| 水印/盖章/签章 | 状态和交付语义归场景，外观语言复用模板体系 | 同时像模板背景和交付状态，边界不明 |
| 公式策略 | 片段转换归 FormulaPolicy，完整 LaTeX/OCR/AI 质量归插件 | 公式当普通文本或模板杂项 |
| 输出版本 | 归 DeliveryPreset/OutputConfig | 散落在模板页或一次性按钮 |

控件一致性是执行链安全问题，不只是视觉一致性。一个参数必须能从 UI 走到 resolver、pipeline、report、fixture 和 release gate，否则它只能算未闭合。

## 12. 边界裁决树

新增需求按以下顺序裁决：

1. 是否需要 Word 原生交付。不需要则 negative 或外部插件。
2. 是否只是模板外观。是则归 TemplateConfig/control contract。
3. 是否是资料事实、字段、人员、图片、签章、附件。是则归 MaterialSchema/AssetInventory。
4. 是否是计数、图表、公式数量、参考文献、规则来源。是则归 CountProfile/RuleSourceGovernance。
5. 是否是输出版本、命名、目录、PDF/ZIP、报告、归档包。是则归 DeliveryPreset/OutputConfig。
6. 是否是多记录、多人员、多项目。是则归 BatchPreset。
7. 是否是固定版位、证书、登记表、答题卡、套打。是则归 fixed-layout profile。
8. 是否触碰字段、批注、修订、内容控件、文本框、OLE、rels、宏。是则先走 ObjectPreflight。
9. 是否涉及法律、财务、审计、专利、医疗、翻译质量、AI 内容质量、OCR/LaTeX 无损转换。是则进入 PluginManualGate。
10. 是否能从导入边界 handoff 到目标 pack。能则必须有 handoff 报告和回退策略。
11. 是否拥有独立用户心智、事实源、交付、风险面、报告和 journey fixture。只有全部成立才考虑新增 coverage pack。

## 15. V38 判定

V38 的最终判断：

```text
当前高层场景能力矩阵不应继续靠增加入口来显得完整。
它应该通过 28 个产品能力槽位、五轴防遗漏模型、Word/OpenXML 反推矩阵、
以及成功/降级/失败/人工门 journey fixture，把每个高频任务推进到可解释、可执行、可修复、可交付。
```

当前已经具备的优势：

- 12 个 coverage pack 覆盖主要高频用户心智；
- 15 个 planned family 提供子场景承载层；
- 51 个 request-cell 让用户自然话术可审计；
- 18 个 dashboard source 和 13 个 drilldown 提供统一证据入口；
- CountProfile、InputSourceProfile、MaterialSchema、DeliveryPreset、ObjectPreflight、Formula/output/watermark 归属均有 first slice。

当前不能忽略的事实：

- 0 个 subject 达到 Green/L5；
- 静态闭合不能等价为产品闭合；
- 最小 fixture 不能等价为真实业务旅程；
- 控件契约存在不等于场景页运行时一致；
- preset 存在不等于真实多版本交付完整；
- manual/plugin/negative 存在不等于用户已能理解边界。

因此，下一步最优先不是新增 pack，而是执行 N2.173-N2.178：把用户旅程、歧义澄清、控件一致性、交付执行、资料修复和 fixed-layout 产品化逐项闭合。只有这些能力槽位进入 UI/执行/报告/fixture/release gate 的共同证据链，矩阵才能从“高频不遗漏的规划体系”升级为“高频可依赖的产品体系”。
