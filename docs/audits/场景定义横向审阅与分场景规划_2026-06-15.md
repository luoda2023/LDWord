## 2. 总结论

`场景` 不是模板的弱化版，也不是快速执行页里的一个下拉选项。它应该被定义为：

> 场景 = 针对某一类文档任务，定义要处理哪些范围、启用哪些执行能力、采用什么行为策略、生成哪些交付物，以及是否需要资料包/批量生成。

因此，之前暂时说“先不管”的几个对象，应该回到场景板块：

| 对象 | 正确归属 | 原因 |
| --- | --- | --- |
| 公式转换策略 | 场景 | 是否处理公式、低置信度如何处理、是否启用 Office fallback，是执行行为，不是版式模板 |
| 公式表格/编号覆盖 | 模板基线 + 场景覆盖 | 公式密集场景可覆盖模板默认；普通模板只提供外观基线 |
| 化学式处理 | 场景 | 只在论文、技术文档等场景启用，且按正文/表格/题注范围处理 |
| 输出产物 | 场景 + 会话 | 是否生成最终稿、对比稿、报告属于场景；本次输出目录属于会话 |
| 水印 | 场景 + 资料包 | 是否加水印、默认水印策略属于场景；水印文字若来自公司/项目资料，可由资料包提供 |
| 图片插入 | 场景 + 资料包 | 场景决定是否启用图片插入；资料包提供具体图片和用途 |
| 占位符替换 | 场景 + 资料包 | 场景决定是否执行内容填充；资料包提供字段和替换规则 |
| 批量生成 | 场景 + 资料包 + 会话 | 场景决定是否是批量型任务；资料包决定多份资料；会话决定本次输出目录 |

模板仍然只负责“文档长什么样”，例如页面、正文、标题编号、目录样式、题注样式、页眉页脚样式、参考文献样式。场景可以覆盖模板的部分 feature config，但覆盖语义必须是“这类任务需要这样执行”，不能把场景变成第二个模板编辑器。

## 3. 当前事实基线

### 3.1 数据模型已经支持场景承载

`src/config/scene.py::SceneWorkspace` 当前已经包含：

- 元信息：`scene_id/name/category/template_id/compatible_template_ids`
- 处理范围：`format_scope.sections/page_ranges/body_start_*`
- 模块开关：`module_switches`
- 行为细项：`md_cleanup/whitespace/citation_link/formula_convert/chem_typography`
- 场景级 feature override：`table/header_footer/toc/caption/formula_table/formula_style/equation_numbering/reference_style/watermark/output`
- 分区样式覆盖：`section_styles`
- 批量预设：`batch_preset`
- 严格策略：`strict_mode`

`src/config/resolver.py` 会把场景中的 feature override 合入最终 `ResolvedConfig`：

```text
template
→ scene feature overrides
→ scene.template_overrides
→ session_overrides
```

这说明场景不是展示层占位，而是已经进入执行配置合并链路。

### 3.2 执行模块已经按场景开关选择

`src/pipeline/scheduler.py::select_enabled_modules()` 根据 `module_switches` 选择模块，并会自动剪掉缺失硬依赖的模块。

当前注册模块包括：

```text
page_setup, section_format, paragraph_style, header_footer,
heading_recognition, heading_numbering, toc,
caption, table_format, figure_table_center,
entity_fill, source_fill, placeholder_replace,
image_insertion, watermark,
chem_typography, md_cleanup, whitespace_normalize,
validation, citation_link, equation_table_format, reference_format
```

这些模块天然按场景组织，而不是按模板组织。

### 3.3 当前 UI 已有场景板块，但深度不足

当前 `ScenePanel` 结构已经接近正确方向：

```text
场景概览
处理范围
功能开关
功能参数
  表格与图表
  页面元素
  公式规范
  参考文献
  校验与清理（当前 UI 旧称）
  内容与数据（当前 UI 旧称）
输出
  输出设置
```

但目前问题是：

- `公式规范` 只露出字体和统一开关，没有露出 `formula_convert`、编号格式、低置信度策略；
- `内容与数据` 只露出水印启用，没有真正表达资料包、图片、占位符、批量生成；
- `输出设置` 只有产物开关，没有输出命名、对比粒度、报告用途、批量目录模板；
- `处理范围` 有分区开关，但 page ranges/body start 等字段没有产品化；
- `功能开关` 是按能力组展示，但默认模块开关、场景 JSON、工厂定义之间仍存在语义差异；
- `template_overrides` 是真实能力，但 UI 没有“高级覆盖”入口，也没有解释哪些覆盖应迁移回模板；
- `batch_preset` 在模型中存在，但场景 UI 没有承接。

## 4. 概念边界

### 4.1 场景、模板、资料包、会话

| 概念 | 用户语言 | 负责什么 | 不负责什么 |
| --- | --- | --- | --- |
| 场景 Scene | 论文排版、标书排版、公文排版 | 任务类型、处理范围、能力开关、执行策略、输出产物、场景级覆盖 | 具体公司资料、本次文件路径、所有版式细节 |
| 模板 Template | GB/T 7713、工程投标格式 | 文档外观基线、标题编号、正文样式、页面、表格、目录、页眉页脚、题注、参考文献 | 是否执行某项能力、本次输出什么 |
| 资料包 Material | 某公司投标资料包 | 字段、图片、签章、Logo、替换规则、多 profile 资料 | 场景策略、模板版式 |
| 会话 Session | 本次工作快照 | 当前文档、输出目录、场景+模板选择、本次临时覆盖 | 可复用的领域规则 |

### 4.2 字段归属原则

判断一个参数归属时，按下面顺序：

1. 只影响外观默认值：归模板。
2. 决定是否执行、执行哪些区域、失败如何处理：归场景。
3. 来自公司/项目/人员/图片/占位符：归资料包。
4. 只对本次执行有效：归会话。
5. 场景可以覆盖模板，但必须解释为“该场景的任务规则”，否则应回模板。

## 5. 横向审阅：功能组定义

### 5.1 场景概览

现有控件：

- 场景预设
- 关联模板
- 编号策略：重建编号 / 保留原编号
- 摘要：策略、分区数、功能数

建议深化：

- 增加场景类型标签：学术、商务、公文、技术、通用、自定义；
- 摘要从“功能数”升级为“启用能力摘要”；
- 关联模板只显示兼容模板，不把模板参数摘要塞进场景页；
- 编号策略继续留在场景，因为它决定执行行为，不是标题编号外观。

### 5.2 处理范围

处理范围应回答：

> 这类文档默认处理哪些部分？哪些部分只是识别但不改？

建议分三层：

```text
常用范围
  正文、目录、参考文献、附录、摘要、致谢、勘误、简历

定位方式
  自动识别 / 页码范围 / 正文起始页 / 起始关键词

分区样式
  跟随正文 / 独立样式
```

当前模型已有 `FormatScopeConfig.mode/page_ranges_text/body_start_index/body_start_page/body_start_keyword/sections`，但 UI 主要只用了 `sections`。后续需要补齐“定位方式”，否则复杂论文、标书、公文的范围策略无法表达。

### 5.3 功能开关

当前 6 个能力组方向正确，但需要重新校准：

| 能力组 | 应包含 | 说明 |
| --- | --- | --- |
| 表格与图表 | `table_format/caption/figure_table_center` | 图表居中不应永远藏在核心模块里；它对报告、标书、论文都可成为场景策略 |
| 页面元素 | `header_footer/toc` | 页码详细策略归模板；场景只决定是否应用页面元素和目录 |
| 公式规范 | `equation_table_format/chem_typography`，未来包含 `formula_convert` | 公式转换策略现在有模型但无模块/UI，需要补齐 |
| 参考文献 | `reference_format/citation_link` | 论文默认开，技术文档可选，标书/公文默认关 |
| 校验与合规 | `md_cleanup/whitespace_normalize/validation` | 由当前“校验与清理”演化，`validation` 当前默认开，但场景 JSON 不一致，需要统一 |
| 输入与资料 | `entity_fill/source_fill/placeholder_replace/image_insertion/watermark` | 由当前“内容与数据”演化，与资料包协同，水印应在这里有完整策略 |

### 5.4 公式规范

公式不是模板页的边角配置，而是典型场景能力。

建议 UI 分组：

```text
公式处理
  启用公式规范
  转换结果：Word 原生 / 保留原样 / 标记待处理
  低置信度：跳过并标记 / 保留原样 / 强制转换
  Office fallback：关闭 / 开启

公式排版
  公式字体、字号
  公式块对齐
  编号位置
  编号格式

化学式
  启用范围：正文、标题、表格、题注、参考文献
  西文字体
  例外词表
```

归属判断：

- `formula_convert` 归场景；
- `chem_typography` 归场景；
- `formula_table/formula_style/equation_numbering` 由模板提供默认，场景在论文/技术文档中可覆盖；
- 公式页不应在模板中单独作为“模板详情页”的核心入口，除非只编辑外观基线。

### 5.5 输入与资料

输入与资料不是一个“水印开关”。它应是场景与资料包之间的桥。

建议 UI 分组：

```text
内容填充
  是否替换占位符
  是否填入来源信息
  是否使用资料包字段

图片插入
  是否允许插入 Logo/签章/资质/附件图
  缺图时阻塞 / 跳过 / 标记

水印
  不加水印 / 固定水印 / 使用资料包字段 / 使用文档状态
  水印文字、颜色、旋转、字号

资料包联动
  推荐资料包类型
  必填字段角色
  必需图片角色
  是否支持多份生成
```

归属判断：

- 场景决定“需要这些能力吗、缺失时怎么办”；
- 资料包决定“具体填什么、用哪张图、哪个公司/项目”；
- 会话决定“这一次选了哪个资料包、输出到哪里”。

### 5.6 输出交付

输出不是模板能力。它属于场景和会话。

建议 UI 分组：

```text
交付文件
  最终 DOCX
  对比 DOCX
  JSON 报告
  Markdown 报告

对比内容
  文本变化
  格式变化

命名规则
  跟随原文件名
  场景名 + 原文件名
  资料包名 + 原文件名
  自定义表达式

批量输出
  每份资料单独文件夹
  汇总报告
  失败是否继续
```

`OutputConfig` 目前只有产物开关，缺少命名、目录、报告用途和批量策略。建议保持 `OutputConfig` 的 artifact toggles，同时新增场景级 delivery 扩展，或在 `BatchPreset` 中补全批量输出语义。

### 5.7 水印

水印应从“模板其它参数”退出来，成为场景里的内容与交付策略。

建议提供四种模式：

| 模式 | 场景 |
| --- | --- |
| 不加水印 | 论文正式稿、普通报告 |
| 固定水印 | 内部资料、测试稿 |
| 资料包水印 | 标书、公文按公司/项目名生成 |
| 文档状态水印 | 草稿、送审、保密、仅供评审 |

`WatermarkConfig` 当前支持 `enabled/text/color/rotation/font_size`，足够支撑第一版。缺口在 UI 和资料包字段联动。

## 6. 分场景规划

### 6.1 自定义

定位：高级用户或未知文档的手动组合场景。

建议定义：

- 默认模板：`default`
- 编号策略：重建编号
- 处理范围：全部分区可选，默认全开
- 能力开关：建议默认只开核心排版，其他能力由用户打开
- 公式：默认关
- 参考文献：默认关
- 输入与资料：默认关
- 水印：默认关
- 输出：最终稿、对比稿、JSON/Markdown 报告默认开，便于调试

关键 UI：

- 清楚显示“这是手动场景”；
- 功能开关应更靠前；
- 适合提供“从当前设置保存为新场景”。

### 6.2 论文排版

定位：学位论文、期刊论文、学术报告。

建议定义：

- 默认模板：`thesis_gbt`
- 编号策略：重建编号
- 处理范围：摘要、目录、正文、参考文献、致谢、附录
- 表格与图表：开
- 页面元素：开
- 公式规范：开
- 参考文献：开
- 校验与合规：开
- 输入与资料：默认关
- 水印：关，若是盲审/送审可通过会话临时开
- 输出：最终稿、对比稿、报告全开

公式策略：

- `equation_table_format` 开；
- `chem_typography` 开；
- `formula_convert.low_confidence_policy = skip_and_mark`；
- Office fallback 默认关，可在高级中开。

参考文献策略：

- `reference_format` 开；
- `citation_link` 可按论文规范开；
- 参考文献样式仍由模板定义，场景只决定是否处理和是否链接。

### 6.3 标书排版

定位：工程投标、政府采购、商务投标。

建议定义：

- 默认模板：`bid_engineering`
- 编号策略：重建编号
- 处理范围：目录、正文、附录
- 表格与图表：开，表格更偏全框线/紧凑适配
- 页面元素：开
- 公式规范：默认关，可选开
- 参考文献：默认关
- 校验与合规：开
- 输入与资料：强开
- 图片插入：强开
- 水印：默认关，但提供“内部评审/投标草稿/保密”快速水印
- 批量生成：强相关

资料包联动：

- 推荐资料包类型：投标资料包；
- 必填字段：公司名称、项目名称、招标编号、法人、授权代表、日期；
- 必需图片：Logo、公章、法人签名、授权代表签名、资质图片；
- 批量输出：按公司/项目/profile 单独目录。

输出策略：

- 最终 DOCX 必开；
- 对比 DOCX 和报告默认开；
- 支持批量汇总报告。

### 6.4 公文排版

定位：通知、函、批复、报告请示等公文。

建议定义：

- 默认模板：`official_gbt`
- 编号策略：保留原编号
- 处理范围：正文为主
- 表格与图表：开，但不强调题注
- 页面元素：开
- 公式规范：关
- 参考文献：关
- 校验与合规：开
- 输入与资料：开，主要用于单位名称、文号、日期、签发人等字段
- 水印：可选，适合“征求意见稿/内部传阅/保密”
- 输出：最终稿默认开，对比稿可默认开，报告默认开用于审阅

关键边界：

- 公文页眉页脚和版记等外观仍归模板；
- 场景只决定是否保留编号、是否填字段、是否加状态水印。

### 6.5 技术文档

定位：技术规范、操作手册、设计文档、接口文档。

建议定义：

- 默认模板：`tech_standard`
- 编号策略：重建编号
- 处理范围：目录、正文、附录
- 表格与图表：开
- 页面元素：开
- 公式规范：开
- 化学式/技术符号：按场景可开
- 参考文献：默认关，可按文档类型开
- 校验与合规：开
- 输入与资料：开，主要用于版本、项目、模块、责任人、图片附件
- 水印：可选，适合“草稿/内部/保密/已废止”
- 输出：最终稿、对比稿、报告默认开

重点参数：

- 表格倾向 `full_grid`；
- 图片插入和图表居中常用；
- 公式低置信度应保守处理，避免破坏技术表达。

### 6.6 通用报告

定位：汇报、总结、调研报告、普通项目文档。

建议定义：

- 默认模板：`report_default`
- 编号策略：重建编号
- 处理范围：目录、正文
- 表格与图表：开
- 页面元素：开
- 公式规范：关
- 参考文献：关
- 校验与合规：开
- 输入与资料：默认关，可手动开
- 水印：默认关
- 输出：最终稿和对比稿默认开，报告可默认开

体验目标：

- 少参数；
- 快速完成；
- 可作为普通用户默认推荐。

### 6.7 英文期刊投稿（未来独立场景族）

定位：英文论文投稿前检查、材料整理、改投辅助，而不是出版社最终排版。

这个场景不应被塞进“中文毕业论文”里。中文毕业论文通常是学校模板强约束，英文期刊投稿则更像目标期刊 profile 下的合规检查和材料打包。

建议定义：

- 默认模板：`journal_submission_plain` 或 `manuscript_clean`
- 编号策略：保留原编号为主，必要时按 profile 检查连续性
- 处理范围：标题、摘要、正文、方法、参考文献、图表题注、补充材料清单、声明材料
- 表格与图表：开，重点不是美化，而是检查 display items、题注、分辨率、引用顺序和独立文件要求
- 页面元素：低优先级，只做投稿友好的基础清理
- 公式规范：开，但以 LaTeX 片段/公式级兼容为主
- 参考文献：开，重点是完整性、引用链接、样式 profile 和 `.bib` 兼容
- 校验与合规：强开，包含 word count、abstract length、title length、display items、references、declarations、SI、cover letter 等检查
- 输入与资料：开，主要用于作者信息、机构、通讯作者、基金、利益冲突、数据可用性、cover letter 字段
- 输出：manuscript docx、检查报告、投稿材料清单、cover letter/declaration 草稿、可选 PDF

关键边界：

- 不承诺“一键排成 Nature/Science/ACS 最终出版版式”；
- 不把每个期刊做成一个模板，而是做成 `Journal Profile Engine`；
- 支持 LaTeX 输入应定位为过程兼容/片段兼容，不承诺完整 LaTeX 工程无损转 Word；
- 对可编辑 Visio/OLE 对象必须先做风险检测，不能为了投稿检查破坏原稿嵌入对象。

## 7. 当前横向缺口

### 7.1 场景 JSON、工厂定义和 UI 摘要需要统一

当前 `scenes/*.json`、`scene_presets.py` 工厂、`ScenePanel` UI 的能力组存在差异：

- 工厂文档里 `formula` 组是 `equation_table_format + chem_typography`，旧规划里是 `formula_*` 4 个模块；
- 默认模块中 `validation/equation_table_format/reference_format` 为 True，但多个场景 JSON 没有显式打开；
- `figure_table_center` 被当核心模块，但产品上更像表格与图表能力；
- `custom` 场景在旧规划里“能力组默认开”，工厂里“能力组默认关”，JSON 当前也偏少开。

建议先确定一份能力组真表，再反向生成场景 JSON 和摘要。

### 7.2 公式转换有模型但缺 UI 和执行闭环说明

`FormulaConvertOptions` 已存在：

- `output_mode`
- `low_confidence_policy`
- `office_fallback_enabled`
- `office_fallback_timeout_sec`

但当前模块注册里没有独立 `formula_convert` 模块，UI 也没有编辑入口。需要明确：

- 它是未来转换模块的预留；
- 还是合并进 `equation_table_format`；
- 或者作为导入/清洗前置阶段。

### 7.3 输出配置过薄

当前 `OutputConfig` 只有：

- `final_docx`
- `compare_docx`
- `compare_text`
- `compare_formatting`
- `report_json`
- `report_markdown`

缺少：

- 输出目录模板；
- 文件命名模板；
- 批量目录规则；
- 报告详细等级；
- 失败处理策略；
- 是否打开输出目录/是否保留中间件。

这些属于场景/会话交界，需要明确：默认规则归场景，本次路径归会话。

### 7.4 水印和资料包没有打通

当前 `WatermarkConfig.text` 是固定文本。标书、公文、技术文档更常见的是：

- 公司名水印；
- 项目名水印；
- 文档状态水印；
- 保密等级水印。

这些文本可能来自资料包字段。建议水印支持：

```text
fixed_text
material_field
document_status
custom_template
```

### 7.5 场景级模板覆盖需要治理

`template_overrides` 很强，但若无限制暴露，会把场景变成第二个模板编辑器。

建议：

- 普通 UI 不直接展示 `template_overrides`；
- 在每个功能参数页只展示允许场景覆盖的少量字段；
- 其它覆盖放“高级：场景覆盖”；
- 保存时标记来源，摘要中显示“本场景覆盖了模板的 X 项参数”。

### 7.6 输入来源、结构化中间层和渲染边界不够明确

共享对话里的一个核心判断需要纳入当前场景规划：文档自动生成不是“字符串替换”，而是：

```text
内容来源
→ 结构化中间层
→ Word 模板渲染
→ python-docx/lxml 后处理
→ 输出与校验报告
```

当前项目已经有资料包、占位符替换、图片插入和 Markdown 清理，但场景层还没有显式表达输入来源 profile。后续应区分：

- `docx 原稿`：以保护原结构为主，只做局部格式化和填充；
- `Markdown 预览稿`：适合人工编辑和 AI 生成内容预览，但不应直接决定最终 Word 版式；
- `JSON/结构化数据`：适合多版本输出、批量生成和资料包渲染；
- `LaTeX 片段`：适合公式、引用、局部结构导入；
- `完整 LaTeX 工程`：只能作为高风险导入源，不承诺无损转换。

因此，`md_cleanup` 不能代表全部输入能力。场景未来需要一个更明确的 `input_source_profile` 或同等级能力组，用来声明本场景接受什么输入、如何降级、是否保留中间产物、失败时是阻断还是标记。

### 7.7 英文期刊场景缺少 profile 化合规视角

当前内置场景以中文论文、标书、公文、技术文档和报告为主。英文期刊不能简单复用“论文排版”：

- 它不以统一模板为中心，而以 `Journal Profile` 为中心；
- 初投稿阶段常常更关注结构、字数、图表、参考文献、声明、补充材料和投稿包，而不是最终出版版式；
- 改投场景需要知道从一个 profile 转到另一个 profile 会影响哪些材料；
- count engine、reference checker、figure/table compliance 和 package builder 都应该挂在场景合规链路上。

这意味着未来至少要支持“英文期刊投稿”作为独立场景族，或者在“论文”下拆出 `thesis_cn` 与 `journal_en` 两种 profile 体系。二者不能共用一套 UI 文案和默认假设。

### 7.8 可编辑 Visio/OLE 对象保护缺口

共享对话补出一个当前文档之前没有明确记录的技术红线：含可编辑 Visio/OLE 对象的 `.docx` 不能走全量转换、全量重建或不受控资源清理。

可编辑 Visio 对象通常不仅是页面上一张图，还可能包含：

```text
word/embeddings/oleObject*.bin
word/media/*.emf 或预览图
word/_rels/document.xml.rels 中的嵌入关系
w:object / o:OLEObject / v:shape / drawing 相关节点
```

如果执行链路重写 drawing、丢失 embeddings、清理 media/rels、或通过 Pandoc/LibreOffice 来回转换，可能出现图还能看但不能双击编辑、关系链断裂、甚至 Word 提示文档损坏。

当前 `strict_mode` 只表达严格策略，不足以表达对象保护。后续建议新增文档预检能力：

- 检测 `word/embeddings`、OLE 关系、EMF/WMF、Visio 相关对象；
- 在摘要和执行页标记“含复杂嵌入对象”；
- 高风险场景默认进入保守模式；
- 禁止或跳过会重写整文、重建 package、清理 rels/media 的模块；
- 报告中说明哪些模块因对象保护被跳过。

这个能力属于场景执行安全策略，不属于模板外观，也不属于资料包。

## 10. 后续判断标准

后续场景板块改动需要遵守：

- 用户看到的是任务语言，不是 dataclass 字段名；
- 模板只解释外观，场景只解释任务和执行；
- 水印、输出、公式转换、资料包联动优先归场景；
- 输入来源、合规 profile、对象保护策略优先归场景；
- 具体资料值不写入场景，写入资料包或会话；
- 场景覆盖模板必须有明确业务理由；
- 每个内置场景必须能回答：处理哪些范围、启用哪些能力、默认用哪个模板、输出哪些文件、是否需要资料包。

## 11. 外部技术记录吸纳判断

本节针对 `count_engine_tech_record.md`、`exam_generator_tech_stack_record.md` 与共享对话做横向审阅。外部记录与共享对话并非当前项目代码事实，因此只吸收可迁移的产品原则和能力边界。

### 11.1 多口径统计与规则检查记录

需要吸纳的部分：

- `不要争论唯一正确的字数，而是声明采用什么口径`。这应进入场景里的 `校验与合规` 语义，而不是做成一个全局“字数统计”按钮。
- `Profile-driven Multi-metric Count Engine` 的思想可以迁移为场景级合规 profile：论文、期刊、投标、公文、技术报告可以采用不同统计口径、纳入范围和合规阈值。
- 统计链路应按结构化阶段表达：文档解析、区块识别、章节分类、元素分类、多口径统计、规则匹配、报告输出。这与当前场景的处理范围、模块开关、输出交付天然匹配。
- 场景配置里应允许声明“检查哪些范围”，例如正文、摘要、参考文献、附录、表题、图题、脚注、页眉页脚、文本框、批注、修订、隐藏文字等；但具体 Word XML 抽取和计数执行属于后续执行模块。
- 合规报告应说明采用口径、计入范围、排除范围、异常提示和目标规则差异，不能只给单一数字。

不建议本轮直接吸纳的部分：

- 不把完整 CountEngine 作为场景板块第一阶段核心，因为当前场景板块更紧急的是场景定义、功能开关、资料包、输出交付和执行链路打通。
- 不承诺与 Word、学校系统或投稿系统统计结果完全一致；只能承诺当前 profile 的可解释、可复现。
- 不在场景里存储具体统计结果。统计结果属于本次执行报告；场景只存 profile、范围和默认规则。

对场景规划的影响：

- `校验与合规` 应承接原 `校验与清理`，并新增合规检查、计数 profile、对象保护预检等语义。
- 内置场景的摘要除了“启用哪些能力”，还应能说明是否启用合规检查、采用什么规则 profile、报告输出到哪里。
- `OutputConfig` 需要预留报告粒度和报告格式配置，支撑 Markdown/JSON 报告以及未来的可视化合规摘要。

### 11.2 试卷生成技术栈记录

需要吸纳的部分：

- `AI/外部生成结构化数据，程序负责校验、规范化、预览和导出` 这个原则可迁移到资料包和内容生成类场景。场景只声明数据入口和执行策略，不直接绑定某个生成模型。
- `JSON 是机器源，Markdown 是人工预览，Word 是正式输出` 可作为输出交付的通用心智：场景应区分结构化中间产物、人工审阅稿和最终 Word 交付物。
- `多版本输出来自同一份结构化源` 应吸收到输出交付设计。类似学生卷/教师卷/答案卷的差异，在本项目中对应最终稿、对比稿、清洁稿、带报告稿、批量个性化稿等版本，不应通过重复生成或手动删除实现。
- 公式处理应被视为场景执行能力：LaTeX 到 OMML 是理想路径，LaTeX 到图片可以作为 MVP 或低置信度 fallback，但具体执行仍需要与现有 `formula_convert`、公式表格和编号模块对齐。
- 图片能力应作为通用资料/内容能力：占位符、上传、替换、尺寸、居中、题注、预览和资料包图片角色，优先级高于复杂几何图或 AI 生成图。
- PDF 输出可以作为可选交付物，但 DOCX 仍是主交付物；PDF 更适合放在 `输出交付` 的可选项里，而不是模板管理里。

不建议本轮直接吸纳的部分：

- 不直接引入 `docxtpl` 作为当前渲染路径结论。当前项目已有 `python-docx`、模板配置、占位符、图片、资料包和执行模块体系，是否引入新渲染层需要单独技术评估。
- 不把 `Pydantic` 作为必须依赖写入规划。可以吸收“结构化 schema 校验”的原则，但实现上应先尊重当前 dataclass、迁移和配置保存体系。
- 不把复杂几何绘图、AI 图片生成或题库专属能力纳入当前场景核心，只保留为未来插件化能力。

对场景规划的影响：

- `输入与资料` 不应只理解为占位符替换，还应覆盖结构化数据源、资料包字段、图片角色和人工预览之间的关系。
- `输出交付` 需要从单纯复选框升级为版本预设：最终稿、对比稿、报告、结构化中间产物、批量输出、可选 PDF。
- `公式规范` 需要同时描述转换策略、低置信度处理、fallback 策略和输出形态，不能只描述公式外观。

### 11.3 共享对话的新增吸纳判断

共享对话比两份导出的 MD 更完整，新增了几条此前没有充分展开的判断。

#### 11.3.1 Word 自动生成是渲染系统，不是替换脚本

需要吸纳的部分：

- 当前产品应被理解为 `Word 模板渲染 / 文档自动生成系统`，不是简单的 `paragraph.text.replace()`。
- `python-docx` 适合局部结构操作和后处理，但不等于完整模板引擎；`docxtpl`、Jinja2、Pandoc 等可以作为外部参考，但不能不经评估直接替换当前执行管线。
- 稳定性的核心问题包括占位符跨 run、格式丢失、表格循环、图片尺寸、页眉页脚、目录/编号、交叉引用、批量输出和可视化校验。

对当前项目的落点：

- 资料包、占位符替换、图片插入和输出交付应通过场景串成完整链路；
- 模板继续定义外观基线，场景定义任务和执行策略，会话定义本次数据和输出位置；
- 如果未来引入新的渲染引擎，应作为 `render strategy` 或插件能力进入，而不是直接改写模板管理语义。

#### 11.3.2 Markdown、JSON、Word 的三层关系

需要吸纳的部分：

- Markdown 适合作为 AI 输出和人工预览层，但不应直接成为最终 Word 版式来源。
- JSON/结构化数据适合作为机器源，支撑校验、版本输出、批量生成和资料包渲染。
- Word 是正式交付物，最终排版应由模板基线、场景策略和后处理模块共同决定。

对当前项目的落点：

- `md_cleanup` 需要从“清理 Markdown 痕迹”扩展为输入链路的一环；
- `输入与资料` 应能表达本场景是否接受 Markdown、结构化 JSON、资料包字段、LaTeX 片段和图片角色；
- `输出交付` 应支持保留结构化中间产物和人工预览稿，不能只是一组 docx/report 复选框。

#### 11.3.3 多版本输出应成为通用交付模型

需要吸纳的部分：

- 同一份结构化源可以渲染成多个版本。试卷里的学生版/教师版/答案版，在本项目中可泛化为清洁稿、审阅稿、对比稿、带报告稿、投稿包、批量个性化稿。
- 版本差异不应通过重复生成或删除内容实现，而应通过版本 preset 控制显示字段、模板、报告粒度和命名规则。

对当前项目的落点：

- `OutputConfig` 需要从 artifact toggles 升级为 delivery preset；
- 每个 preset 至少应能定义：目标模板、显示/隐藏内容、是否生成报告、命名模板、输出目录规则；
- 资料包批量输出应复用这套 delivery preset，而不是单独再做一套批量逻辑。

#### 11.3.4 英文期刊不是统一模板，而是 Journal Profile

需要吸纳的部分：

- 英文期刊投稿场景不能被理解为“高级期刊统一模板”。更合理的产品定位是投稿前合规检查、投稿包整理和改投辅助。
- `Journal Profile Engine` 比 `Journal Template Library` 更重要。profile 应描述 article type、长度限制、display items、reference rule、figure/table rule、cover letter、declarations、SI 等。
- 初投稿、修回、改投和最终接受后的出版社排版是不同阶段，场景应先覆盖初投稿和改投前检查。

对当前项目的落点：

- 英文期刊投稿建议作为未来独立场景族；
- `校验与合规` 需要服务学校论文、英文期刊、申报书等多类 profile；
- 参考文献、图表、公式、输出交付在英文期刊场景里都应以 profile 检查为主，而不是以外观编辑为主。

#### 11.3.5 LaTeX 是过程兼容/片段兼容，不是完整工程无损迁移

需要吸纳的部分：

- LaTeX 对英文论文、数学、物理、工程、统计等场景很重要，但完整 `.tex` 工程到 Word 的无损转换不现实。
- 最合理的兼容等级是：公式级兼容必须做，内容块级导入可以做，完整 LaTeX 工程兼容暂缓。
- 公式级兼容应优先支持 LaTeX 到 OMML；失败时可降级为图片、保留原文或标记待处理。

对当前项目的落点：

- `formula_convert` 要明确输入源、输出模式、低置信度策略和 fallback；
- `输入与资料` 应声明是否允许 LaTeX 片段；
- 完整 LaTeX 工程导入如果未来支持，必须进入高风险导入流程，并输出不支持项报告。

#### 11.3.6 数学图和复杂几何图应插件化，不进核心 MVP

需要吸纳的部分：

- 通用图片能力、图片占位、上传替换、尺寸控制、居中、题注和资料包图片角色是高复用能力，应优先做稳。
- 函数图/坐标图可作为中期增强；复杂几何图自动生成难度高、复用面窄，应插件化。
- 如果未来做几何图，正确路线是结构化图形描述到可控 SVG/PNG 渲染，再插入 Word，而不是让 AI 直接生成不可控图片。

对当前项目的落点：

- `image_insertion` 和资料包图片角色应优先完善；
- 场景可以预留 `generated_visuals` 或插件位，但不应把复杂几何图作为基础场景参数；
- 对公式密集、数学试卷、技术图示等场景，先支持用户提供图片/图表和可控替换。

#### 11.3.7 Visio/OLE 保护是新的执行安全边界

需要吸纳的部分：

- 可编辑 Visio/OLE 对象是 Word 里的脆弱嵌入对象，不能和普通图片等同处理。
- 安全风险大致从低到高：只读检查、局部文本渲染、python-docx 局部后处理、Pandoc 重建、LibreOffice 回写、解压后全量重包。
- 含复杂嵌入对象的文档应先预检，再决定是否允许模块执行。

对当前项目的落点：

- 新增 `复杂对象预检 / Object Preservation` 能力；
- 场景需要声明对象保护策略，例如 `preserve_embedded_objects = strict`；
- 执行管线需要能根据预检结果跳过高风险模块，并在报告中说明原因；
- 这项能力应进入 `校验与合规`，不是模板管理参数。

## 12. 场景配置控件样式一致性要求

场景定义页属于应用内配置面板，视觉和交互必须继承模板管理已经形成的控件体系。它不能因为场景语义更偏“任务”就另起一套卡片、输入框、下拉框或开关样式。

### 12.1 当前差异判断

当前 `ScenePanel` 已经使用 `MasterDetailShell`、`NavigationCard`、`Card`、`TemplateFormStack`、`template_form_row`、`StyledComboBox`、`ToggleSwitch` 和 `FeatureToggleRow`，方向正确，但深度仍不够：

- 模板详情页已经用 `TemplateSummaryCard` 在顶部表达“当前配置结果”，场景详情页目前更多是普通卡片和说明文本，摘要规则不够统一。
- 模板详情页的表单逐步统一到 `InspectorForm`、`TemplateFormGrid`、`SpacingInput`、`FontCombo`、`SizeCombo`、`StyledComboBox`、`ToggleSwitch`；场景页仍需要逐项确认是否存在自造组合控件或局部样式。
- 模板管理强调右侧摘要、左侧概览和实际字段来自同一套 summary projection；场景也需要类似 `scene_summary_projection`，避免左侧导航、概览摘要和详情页状态各说各话。
- `FeatureToggleRow` 可以继续使用，但要被视为共享设计系统组件；如果它只服务场景页，就需要和模板页开关行的尺寸、间距、文字层级和禁用态保持一致。

### 12.2 必须复用的控件与布局

场景配置应按以下规则实现：

- 页面骨架继续使用 `MasterDetailShell` 和 `NavigationCard`，左侧导航保留分组结构。
- 每个详情页顶部使用 `TemplateSummaryCard` 或同等级共享摘要组件，摘要内容来自统一 projection，而不是手写散落 label。
- 表单区域优先使用 `Card + InspectorForm`；需要多列字段时使用 `TemplateFormGrid`，线性字段使用 `TemplateFormStack` 和 `template_form_row`。
- 下拉选择统一使用 `StyledComboBox`；开关统一使用 `ToggleSwitch`；数值和单位输入优先使用 `SpacingInput` 或模板管理已有的单位输入组件。
- 字体、字号、行距、段距、缩进等与版式相关的控件，如果在场景覆盖中出现，必须使用模板管理同款 `FontCombo`、`SizeCombo`、`SpacingInput` 和命名规则。
- 摘要区按钮使用模板管理的 summary action button 样式；不要新增只在场景页出现的胶囊按钮、彩色标签按钮或装饰性卡片。
- 不做卡片套卡片；不把长说明文字放进配置区；状态、解释和风险提示应进入摘要或报告，而不是挤占表单主体。

### 12.3 与模板管理的语义一致性

控件一致不只等于外观一致，还包括字段组织方式一致：

- 与 Word 版式直接相关的参数仍由模板管理定义，场景页只在“这类任务需要覆盖模板默认行为”时暴露少量覆盖项。
- 如果场景页暴露缩进、段距、行距等覆盖项，命名、单位、行内排布和交互应与模板管理保持一致，例如左缩进/右缩进可同排，段前/段后可同排，特殊缩进必须支持“无、首行、悬挂”的明确切换。
- 场景页中的水印、输出、公式、资料包不是模板样式，但其控件仍应遵守模板管理的尺寸、间距、禁用态和摘要反馈规则。
- 场景配置的复杂度应通过分组和高级覆盖收纳，不通过创造新控件来承载。

### 12.4 验收与测试口径

后续实现场景 UI 时建议增加架构测试：

- `ScenePanel` 不直接使用原生 `QComboBox`、`QCheckBox` 等未封装控件，除非有明确共享组件包装理由。
- 场景详情页源码中应出现 `TemplateSummaryCard` 或共享摘要组件、`InspectorForm`/`TemplateFormGrid`、`StyledComboBox`、`ToggleSwitch` 等统一控件。
- 快照或结构测试应覆盖场景概览、处理范围、执行能力、公式规范、输入与资料、输出交付和高级覆盖。
- 对窄宽度布局做基本断言：同排字段不重叠，长标签不挤压输入框，单位控件和下拉箭头不漂移。
- 场景 summary、左侧导航摘要和 resolver 实际输出应有一致性测试，避免 UI 显示“开”但执行链路未启用。

## 13. 高层场景能力矩阵规划

当前功能点的问题不是“少几个开关”，而是抽象层级不够。高频使用场景会跨越模板、资料包、输入源、合规 profile、输出版本和执行安全。如果仍用 6 个粗能力组承载，必然出现：

- 高频场景找不到归属；
- 一个开关同时代表输入、资料、执行和输出；
- UI 显示启用，但执行链路没有模块；
- 模板、场景、资料包和会话互相抢字段；
- 复杂对象、LaTeX、期刊规则、批量交付等边界不清。

因此，场景能力矩阵应从“功能组”升级为“场景族 + 能力域 + profile/preset”的组合。

### 13.1 矩阵基本单位

建议拆成五类对象：

| 对象 | 含义 | 示例 | 是否用户可复用 |
| --- | --- | --- | --- |
| 场景族 | 一类任务的高层心智 | 中文论文、英文期刊、标书、试卷、公文 | 是 |
| 场景 profile | 场景族下的具体规则组合 | 硕士论文、Nature Article、工程投标、学生版试卷 | 是 |
| 能力域 | 可组合的执行能力集合 | 输入、范围、表格、公式、合规、输出、安全 | 是 |
| 合规 profile | 校验规则和计数口径 | 学校字数规则、期刊投稿规则、标书审查清单 | 是 |
| 交付 preset | 输出版本和文件组织规则 | 最终稿、对比稿、投稿包、教师版、批量包 | 是 |

不要把所有差异都做成“场景”。例如“生成 PDF”是交付 preset，“公司 Logo”是资料包资产，“首行缩进 2 字符”是模板样式，“Nature Article 字数限制”是合规 profile，“英文期刊投稿”才是场景族。

### 13.2 能力域完整定义

高层矩阵至少要覆盖以下 10 个能力域：

| 能力域 | 应回答的问题 | 当前已有基础 | 主要缺口 |
| --- | --- | --- | --- |
| 输入来源 | 本场景接受什么输入，失败如何降级 | `md_cleanup`、资料包导入、docx 执行入口、`input_source_profile` | UI 尚未展示 Markdown/JSON/LaTeX 分级策略 |
| 处理范围 | 处理哪些区域，只读哪些区域，跳过哪些区域 | `FormatScopeConfig.sections/page_ranges/body_start_*` | UI 主要只露出 sections，缺 footnote/textbox/comment/revision 等范围语义 |
| 结构与编号 | 标题、目录、题注、列表、引用顺序如何处理 | heading/toc/caption/reference/citation 模块 | 场景摘要和实际执行开关仍需统一 |
| 版式执行 | 页面、正文、表格、页眉页脚等是否应用 | page/section/paragraph/table/header_footer 模块 | 场景覆盖模板的治理粒度还不够 |
| 公式与专业符号 | 是否转换公式、处理化学式、低置信度怎么办 | `formula_convert` 模型、`equation_table_format`、`chem_typography` | 缺独立公式转换执行闭环和输入来源策略 |
| 内容与资料 | 是否填字段、插图、签章、水印、占位符 | entity/source/placeholder/image/watermark 模块，资料包面板 | 水印字段联动、图片角色、缺失策略仍需场景化 |
| 合规检查 | 检查哪些规则，报告如何解释 | `validation`、报告 writer、`compliance_profile`、对象预检 | 缺 count engine 和完整 journal/school/bid 规则执行 |
| 输出交付 | 生成哪些版本，如何命名和打包 | `OutputConfig`、执行报告、批量报告、`delivery_presets` | 多版本 preset 尚未驱动真实输出 |
| 执行安全 | 是否允许全量转换、是否保护嵌入对象 | `strict_mode`、对象预检 policy、`PipelineContext.object_preflight`、`skip_modules_by_finding` | 跳过策略已接入 Pipeline，仍需按真实模块风险继续细化映射和 UI |
| 可扩展插件 | 哪些能力不进核心，作为插件 | 暂无明确插件位 | 复杂几何图、完整 LaTeX 工程、AI 内容生成、法律条款审查应插件化 |

Phase B 之前，`SceneWorkspace` 已能承载部分能力，但缺少三个高层结构：`input_source_profile`、`compliance_profile`、`delivery_presets`。本轮已经补上承载结构和迁移链路；后续重点转为 UI 摘要、执行消费和多版本输出。

### 13.3 高频场景族覆盖矩阵

下面是建议覆盖的高频场景族。不是所有场景都必须第一阶段内置，但矩阵中必须有归属，避免未来扩展时边界混乱。

| 场景族 | 高频子场景 | 核心价值 | 必备能力域 | 默认归属判断 |
| --- | --- | --- | --- | --- |
| 自定义/手动 | 未知文档、一次性格式化、调试配置 | 给高级用户自由组合 | 输入、范围、能力开关、输出、安全 | 内置 P0 |
| 中文毕业论文 | 本科/硕士/博士论文、课程论文、开题/综述 | 学校模板强约束、目录编号、参考文献、字数检查 | 范围、结构、版式、公式、参考文献、合规、输出 | 内置 P0，需补合规 profile |
| 英文期刊投稿 | 初投稿、修回、改投、投稿包 | Journal Profile、材料齐套、字数/图表/声明检查 | 输入、参考文献、公式、合规、输出、安全 | P1 独立场景族 |
| 试卷/教学材料 | 学生版、教师版、答案版、解析版、答题卡、教案 | 一份结构化数据，多版本输出 | 输入、结构化数据、公式、图片、交付 preset | P1 独立场景族或教育 profile |
| 标书/商务投标 | 工程投标、政府采购、商务方案、陪标批量 | 资料包填充、图片/签章、批量交付、审查清单 | 资料、图片、水印、批量、合规、输出 | 内置 P0，需补交付/资料 schema |
| 项目申报/评审材料 | 基金、课题、项目建议书、验收材料 | 规则清单、材料打包、附件/签章、版本留痕 | 输入、资料、合规、输出、安全 | P1，可与标书/学术共享能力 |
| 公文/行政文书 | 通知、函、请示、批复、会议纪要、制度办法 | 保留原编号、公文模板、字段填充、状态水印 | 范围、版式、资料、水印、输出 | 内置 P0，需细分会议/制度 profile |
| 技术/工程文档 | 技术规范、SOP、接口文档、操作手册、验收报告 | 表格、图表、版本信息、技术符号、附录 | 表格、图片、公式、资料、合规、安全 | 内置 P0，需补对象保护 |
| 通用报告/计划 | 调研报告、总结、周报、可研、商业计划 | 快速规范化、图表、目录、清洁输出 | 范围、版式、表格、输出 | 内置 P0，少参数 |
| 合同/协议/法律类文档 | 合同、协议、授权书、承诺函 | 字段填充、版本对比、签章、风险提示 | 资料、对比、输出、安全 | P2；不做法律判断，先做格式和资料一致性 |
| 简历/档案/证书/批量函件 | 简历、成果清单、证明、邀请函、录取/通知批量 | 结构化字段、多 profile、批量生成 | 资料、结构化数据、交付 preset | P2，可作为资料包批量 profile |

矩阵判断：

- P0 是当前产品已经有入口或应马上治理的场景族；
- P1 是高频且与现有能力高度相邻，应尽快规划数据模型；
- P2 是高频但风险/差异较大，应先作为 profile 或插件，不急于放进顶层内置场景。

### 13.4 场景族与能力域矩阵

| 场景族 | 输入来源 | 资料包 | 合规 profile | 交付 preset | 安全策略 |
| --- | --- | --- | --- | --- | --- |
| 中文毕业论文 | docx、Markdown、LaTeX 片段 | 作者/学校/课题可选 | 学校/学院/学位类型 | 最终稿、送审稿、对比稿、规则报告 | 保护修订、批注、嵌入对象 |
| 英文期刊投稿 | docx、LaTeX 片段、`.bib`、可选 Markdown | 作者、机构、基金、声明 | Journal/Profile/Article Type | manuscript、cover letter、declaration、SI 清单、检查报告 | 禁止全量转换破坏原稿 |
| 试卷/教学材料 | JSON、Markdown、题库、LaTeX 公式 | 学校/班级/教师/Logo | 题型/分值/答案完整性 | 学生版、教师版、答案版、解析版、答题卡 | 保留题目源数据，版本只控制渲染 |
| 标书/商务投标 | docx 模板、资料包、Excel/表格数据 | 公司、项目、资质、签章 | 招标清单/材料完整性 | 正本、副本、对比稿、批量包、汇总报告 | 缺关键签章/资质可阻断 |
| 项目申报/评审 | docx、表格、附件清单 | 项目、团队、预算、成果 | 申报指南/字数/附件 | 申报书、附件包、审查报告 | 附件缺失阻断或标记 |
| 公文/行政文书 | docx、资料字段 | 单位、文号、日期、签发人 | 公文要素/流程状态 | 正式稿、征求意见稿、内部稿 | 默认保留原编号和关键字段 |
| 技术/工程文档 | docx、Markdown、图片/图表、LaTeX 片段 | 项目、版本、模块、责任人 | 技术审查项/术语/图表 | 正式稿、审阅稿、变更报告 | 保护 Visio/OLE/嵌入 Excel |
| 通用报告/计划 | docx、Markdown | 项目/部门可选 | 基础格式检查 | 最终稿、对比稿、报告 | 少做破坏性操作 |
| 合同/协议 | docx 模板、资料包 | 甲乙方、金额、日期、签章 | 字段一致性/空项检查 | 正式稿、审阅稿、差异报告 | 不做法律结论，强保留修订 |
| 简历/档案/函件 | JSON/Excel/资料包 | 人员/成果/单位/批量名单 | 字段完整性 | 单份/批量/汇总表 | 批量失败隔离 |

这张矩阵的重点不是马上实现所有行，而是让每个高频需求都有清晰落点：是内置场景、场景 profile、资料包 schema、合规 profile、交付 preset，还是插件。

### 13.5 当前能力组应如何重构

当前 6 个 UI 能力组不应直接等同于最终矩阵。建议重构为 8 个用户心智更清晰的能力域：

| 新能力域 | 由当前能力演化 | 包含模块/未来模块 | 说明 |
| --- | --- | --- | --- |
| 处理范围 | 当前“处理范围” | `FormatScopeConfig`、未来 section/textbox/footnote detector | 每个场景必须先明确范围 |
| 结构与目录 | 页面元素 + 标题编号 | heading、toc、caption、reference order | 处理文档骨架 |
| 表格与图表 | 当前表格与图表 | table、caption、figure_table_center、future figure compliance | 图表作为高频能力独立存在 |
| 公式与专业符号 | 当前公式规范 | formula_convert、equation_table、chem_typography | 支持 LaTeX 片段、OMML、fallback |
| 参考文献与引用 | 当前参考文献 | reference_format、citation_link、future bib/csl | 论文/期刊核心 |
| 输入与资料 | 当前内容与数据 | entity/source/placeholder/image/watermark、input_source_profile | 拆掉“数据”模糊词 |
| 校验与合规 | 当前校验与清理 | validation、md/whitespace、count engine、object preflight | `validation` 必须纳入用户心智 |
| 输出交付 | 当前输出设置 | OutputConfig、delivery presets、batch reports | 不属于模板 |

其中 `md_cleanup` 更像输入规范化，`whitespace_normalize` 更像文本清理，`validation` 更像合规/质量检查。UI 可以放在同一页，但底层摘要必须分别表达，否则用户无法判断“清理”和“检查”到底发生了什么。

### 13.6 不应进入核心场景的能力

以下能力很有价值，但不应变成基础场景开关：

| 能力 | 原因 | 建议归属 |
| --- | --- | --- |
| 完整 LaTeX 工程无损转 Word | 技术风险高、宏包差异大、无法稳定承诺 | 高级导入插件 |
| 复杂几何图自动生成 | 领域窄、约束求解和排版难度高 | 教育/数学插件 |
| AI 内容生成 | 外部模型和质量责任边界复杂 | 输入来源插件或内容助手 |
| 法律条款审查 | 高风险专业判断，不能由格式工具承诺 | 只做字段/格式/版本检查 |
| 投稿指南自动抓取更新 | 依赖外部网站变化，需维护数据源 | Journal profile 更新器 |
| 全量 docx 重建/转换 | 容易破坏 OLE、Visio、修订、域和关系 | 仅在用户确认的高风险模式 |

判断标准：高复用、低破坏、可解释、可测试的能力进核心；窄领域、高风险、依赖外部或难以承诺结果的能力进插件。

### 13.7 一个场景算“完善”的验收标准

每个内置场景或 P1 场景 profile 必须能回答 12 个问题：

1. 任务目标是什么，用户用什么语言理解它？
2. 默认输入是什么，允许哪些输入，哪些输入只做高风险导入？
3. 默认处理范围是什么，哪些区域只读、哪些区域跳过？
4. 默认模板是什么，兼容哪些模板，模板只负责哪些外观？
5. 默认启用哪些能力域，哪些能力是可选高级项？
6. 场景会覆盖哪些模板参数，覆盖的业务理由是什么？
7. 需要什么资料包 schema，哪些字段/图片/签章是必填？
8. 启用什么合规 profile，检查结果如何解释？
9. 输出哪些交付 preset，命名和目录规则是什么？
10. 批量或多版本输出如何保证来自同一份数据源？
11. 有哪些执行安全红线，检测到复杂对象时怎么办？
12. UI 摘要、resolver、scheduler 和报告是否能说出同一套事实？

如果某个场景不能回答以上问题，它就还不是完整场景，只能算“能力组合草稿”。

### 13.8 分期路线

建议按四个阶段补齐，而不是一次性实现所有场景。

Phase A：矩阵对齐

- 把当前 6 个 UI 能力组映射到 8 个能力域；
- 把 `validation` 纳入 `校验与合规`；
- 明确 P0/P1/P2 场景族；
- 为每个 P0 场景补齐 12 问摘要。

Phase B：核心模型补洞

- 新增或预留 `input_source_profile`；
- 新增或预留 `compliance_profile`；
- 新增或预留 `delivery_presets`；
- 新增对象保护预检结果结构；
- 保持旧 `SceneWorkspace` 可迁移，不强行破坏现有 JSON。

Phase C：高频 P1 场景落地

- 拆出 `thesis_cn` 与 `journal_en`；
- 新增 `exam_teaching` 或教育资料场景族；
- 新增 `project_application` profile；
- 标书、公文、技术文档补齐资料 schema 和交付 preset。

Phase D：插件化扩展

- 复杂几何图；
- 完整 LaTeX 工程导入；
- 期刊 profile 自动更新；
- 法律/合同专业审查；
- AI 内容生成。

### 13.9 本轮矩阵带来的直接修正建议

对当前规划和实现，优先修正以下问题：

- `校验与清理` 命名应更新为 `校验与合规`，并把 `validation` 纳入该能力域；
- `内容与数据` 命名应更新为 `输入与资料`，并拆分输入来源、资料包字段、图片角色、水印策略；
- `figure_table_center` 不应永久当作不可见核心模块，至少在摘要里归入表格与图表；
- `formula_convert` 不能只停留在模型，必须在场景矩阵里明确为公式输入/转换策略；
- `OutputConfig` 不能只是一组产物开关，应向 delivery preset 演进；
- P1 高频场景至少要纳入矩阵：英文期刊投稿、试卷/教学材料、项目申报；
- P2 高频但高风险场景要有边界：合同/协议、简历/证书/批量函件；
- 执行前预检必须覆盖 Visio/OLE、嵌入 Excel、修订、批注、文本框、域、宏等复杂对象。

## 23. Phase C3.1 目标模板交付落地记录（2026-06-16）

本轮补齐 `DeliveryPreset.target_template_id` 的执行语义。它不再只是场景模型里的残留字段，而是成为“同一源文档、多目标模板、多交付版本”的第一条可执行链路。

### 23.1 已落地内容

- WorkbenchProductionRunner 在执行前读取 `scene.delivery_presets`，按 `target_template_id` 分组；
- preset 未指定目标模板时回落到当前场景模板；目标模板等于当前模板时继续复用当前 `TemplateConfig`；
- 目标模板不同于当前模板时，通过 `load_template_from_library(target_template_id)` 加载模板库配置；
- 每个目标模板组克隆原场景，仅保留本组 delivery presets，再走 `resolve_config(template, scene, session_overrides, material_context)`；
- 每个目标模板组独立创建 enabled modules 并执行 Pipeline，避免不同模板的样式、页眉页脚、表格、题注等 resolved config 相互污染；
- Pipeline 新增 `force_delivery_presets`，保证分组后单 preset 也能继续按 `DeliveryPreset.filename_template/output_dir_template/artifacts` 保存，而不是退回旧单输出逻辑；
- Workbench payload 会聚合所有组的 `output_paths`、`report_paths`、`failed_count`、`diagnostics_count` 和摘要；
- 默认 `output_path` 仍按 `scene.default_delivery_preset_id` 选择，保持旧 UI 和批量链路兼容；
- 目标模板加载失败会进入聚合失败文本，不会误报为已生成目标版本。
