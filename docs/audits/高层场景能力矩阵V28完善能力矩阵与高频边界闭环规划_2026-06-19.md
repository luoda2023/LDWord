# 高层场景能力矩阵 V28 完善能力矩阵与高频边界闭环规划（2026-06-19）

## 1. 本轮判断

本轮继续回应“目前功能点过于不完善，不能出现高频适用场景遗漏或者边界不清晰”的要求。V28 的重点不是继续增加场景名字，而是定义一张真正可闭环的高层能力矩阵：

```text
用户自然请求
-> request-cell 路由状态
-> coverage pack / family / profile / preset / plugin gate
-> workflow archetype
-> capability axis
-> Word/OOXML risk surface
-> control contract
-> UI / execution / report / fixture / release gate
```

只有这条链路能从用户说法一路追到执行证据，才算“高频场景没有遗漏”。如果只是有一个 pack 名、一个下拉框或一个文档段落，还不能算完整。

## 3. “完善”的八层准入

一个高频能力要进入完善矩阵，至少要同时满足八层准入。

| 层 | 必须回答 | 不满足时的风险 |
| --- | --- | --- |
| 用户请求 | 用户会怎样自然表达，是否有 matched、ambiguous、manual boundary、negative 样本 | 内部命名完整，真实用户说法丢失 |
| 承载层 | 是 pack、family、profile、schema、preset、template、session 还是 plugin gate | 所有东西都挤进顶层场景，边界发散 |
| 输入事实 | 哪个 DOCX/JSON/XLSX/资料包/规则 profile 是事实源 | 执行时靠猜，报告无法解释 |
| 工作流 | 需要资料填充、批量、固定版位、对比审阅、归档、计数、对象安全中的哪些路线 | 一个“排版”按钮吞掉多个业务流程 |
| Word 风险 | 会碰哪些 OOXML 面，是否有预检、降级、阻断和报告 | 复杂对象被普通文本逻辑误伤 |
| 控件契约 | 场景控件是否复用模板管理的控件语言、单位、禁用规则和布局 | 同一参数在模板和场景里表现不一致 |
| 执行证据 | 是否有 resolver、pipeline、runner、report、repair 或 artifact 链路 | UI 能配但运行层断链 |
| 验收证据 | 是否有 request-cell、DOCX fixture、report anchor、release gate、pytest | 文档口头规划替代真实证据 |

这八层是 V28 的最低完整性模型。以后新增或升级场景，不应只问“有没有这个功能”，而要问“这八层是否都能解释”。

## 5. 控件样式一致性准入

场景配置中的控件必须和模板管理保持同一产品语言。这里不是视觉偏好，而是语义契约：同一参数如果在两个地方长得不同、单位不同、禁用规则不同，用户会认为它们是不同能力。

| 控件契约 | 模板侧定义 | 场景侧准入 |
| --- | --- | --- |
| 左缩进 / 右缩进 | `IndentInput`，单位 `chars/pt/cm`，左右成对 | 必须同一行或同一组展示，不能拆成两个孤立长行 |
| 特殊缩进 | `SpecialIndentInput`，可切换 `none/first_line/hanging` | 必须可交互切换；`none` 时禁用数值并回到 0 |
| 段前 / 段后 | `SpacingInput`，单位 `pt/lines/cm/mm/in/auto` | 必须成对展示；`auto` 时禁用数值 |
| 行距 | 类型下拉 + 数值输入绑定 | `single/one_half/double` 锁定数值，`exact/multiple` 才允许编辑 |
| 固定版位行高 | `FixedLayoutRowHeightPolicy + w:trHeight` | 只在固定版位表单/证书/报价等 profile 出现，不回到通用模板表格字段 |
| 输出版本 | `DeliveryPreset` | 场景拥有业务版本，模板只提供视觉基线 |
| 水印状态 | scene/delivery policy | 状态文本和启用归场景；字体/颜色等外观要说明是否复用模板语言 |
| 公式转换 | scene policy + plugin boundary | 公式片段可有转换策略；完整 LaTeX/OCR/AI 质量进入 plugin/manual gate |

本轮与模板管理相关的 UI 反馈应进入 N2.157C：左/右缩进同行、段前/段后同行、特殊缩进可切换、行距类型和值绑定。这些应被视为场景矩阵的控件契约，不是单个页面的排版问题。

## 6. 高频遗漏防线

V28 把“高频不遗漏”拆成四道防线：

1. request-cell 防线：每个 pack 至少 3 条 matched；高风险 pack 必须有 manual boundary；容易混淆的 pack 之间必须有 ambiguous 样本。
2. 子场景全集防线：每个 pack 都要列出高频子场景全集，新增需求先落 family/profile/schema/preset/plugin，不轻易新增顶层入口。
3. Word 风险防线：只要场景会触碰某个 OOXML 面，就必须有 UI 预检、执行策略、报告证据和测试中的至少一条闭环。
4. 证据链防线：每条高频说法应能追到 fixture、report artifact、release gate；如果只有规划文本，就不能升 L4/L5。

当前 N2.157B 只完成第一道防线中的“matched 深度下限”。接下来要补第二、第三、第四道防线。

## 7. 边界裁决规则

边界不清通常来自四类误判：

| 误判 | 正确裁决 |
| --- | --- |
| 行业名就是新场景 | 先判断它是否只是已有 pack 的 family/profile/schema/preset |
| 专业判断可以放进核心 | 法律、财务、医学、专利、翻译质量进入 plugin/manual gate |
| 导入转换等于目标场景 | PDF/OCR/LaTeX/AI 先进入 `import_ai_boundary`，再 handoff 到目标 pack |
| 样式参数可以在场景里重新发明 | 与模板共用的外观参数必须走 control contract |

新增顶层入口必须同时满足：

1. 用户心智长期稳定，且不是现有 pack 的自然子场景；
2. 输入事实源、交付版本、OOXML 风险面至少两项与现有 pack 明显不同；
3. 需要独立 schema/profile/preset/report/repair 组合；
4. 已有 request-cell、fixture、测试和 release gate 计划。

否则只能进入 family/profile/schema/preset/plugin。

### 12.3 对高层能力矩阵的补强结论

高频场景不能只按“行业/文种”补入口。完整矩阵必须同时回答：

1. 这个请求落在哪个 `pack/family/profile/schema/preset/plugin gate`；
