# 样式控件与模板管理高复用第六轮深度分析

日期：2026-06-30

## 1. 本轮判断

这一轮继续验证用户反馈的核心问题：当前样式与控件规划已经开始复用底层组件，但还没有达到“像模板管理的一部分”。

结论是：问题不再是没有抽组件，而是复用边界还不够硬，当前态反馈还没有完全闭环，部分页面仍把同一件事拆成不同说法。模板管理已经形成了较清晰的“对象 -> 参数 -> 预览”心智模型；场景规划和执行复核则还残留“策略矩阵、契约、证据、内部 key”的工程视角。

本轮已先补上一个真实链路断点：场景分区样式切换当前分区时，同步 `StylePolicyControlDeck` 的当前策略行。这样用户从模板式选择器、策略行、字段跳转看到的是同一个分区，而不是三个各自独立的控件状态。

## 2. 当前复用现状

### 2.1 已经真正复用的部分

| 层级 | 共享对象 | 当前状态 |
| --- | --- | --- |
| 样式对象投影 | `StyleObjectProjection` | 已用于模板、场景、执行前复核的样式对象表达 |
| 预览容器 | `StylePreviewSurface` | 已承载模板预览、场景分区预览、执行前复核预览 |
| 策略控制 | `StylePolicyControlDeck` | 已抽象为通用策略 deck，`StyleRuleControlDeck` 变为场景薄包装 |
| 策略行 | `StylePolicyToggleList` | 已支持 `activated`、`current_policy_key`、当前行属性 |
| 编辑外壳 | `StyleEditingSection` | 已把 owner toolbar、预览、编辑 surface 收束到同一 shell |
| 页面卡片 | `StyleManagementBlock` | 已提供 source、policy、difference、preview 等命名槽位 |

这些说明底层方向是对的：样式控件已经从“某个页面临时拼控件”进入“投影驱动共享控件”的阶段。

### 2.2 还只是表面一致的部分

| 现象 | 用户感知 | 根因 |
| --- | --- | --- |
| 场景页能跳到字段，但策略行不跟随当前分区 | 看起来像两个系统 | 选择器 current key 与 policy current key 没有绑定 |
| 执行前复核能看策略，但跳回场景页后反馈不够强 | 不知道当前修改的是哪一项 | 跨面板同一 variant 的视觉当前态没有统一守门 |
| 场景概览仍出现契约数、coverage、schema 等词 | 不说人话 | 工程证据没有从第一屏下沉到详情或诊断层 |
| 模板管理是参数清单，场景规划是策略矩阵 | 心智模型断裂 | 页面板块没有按同一组槽位重排 |
| 部分按钮文案仍是“恢复/撤销恢复/全部跟随模板”混用 | 动作边界不清 | 动作类型没有按模板管理的“应用、还原、查看来源”统一命名 |

## 3. 本轮补齐的链路

### 3.1 修改前

```text
ScenePanel.focus_navigation_field(...)
-> _set_style_editor_variant("references_body")
-> StyleEditingSection.current_key = references_body
-> 字段或 toggle 高亮

StylePolicyControlDeck.current_policy_key 仍可能为空或停留在旧值
```

这会造成一个细微但关键的体验问题：页面跳转已经到了“参考文献正文”，但策略列表没有把“参考文献正文”标成当前行。

### 3.2 修改后

```text
ScenePanel.focus_navigation_field(...)
-> SceneStyleRulesBlock.set_current_variant(...)
-> SceneStyleOverrideSection.set_current_variant(...)
-> StyleEditingSection.current_key = references_body
-> StylePolicyControlDeck.current_policy_key = references_body
-> StylePolicyToggleList.rows["references_body"].style_policy_row_current = True
```

同时，用户手动改下拉框也会触发：

```text
StyleEditingSection.current_key_changed
-> SceneStyleOverrideSection._on_current_variant_changed(...)
-> StylePolicyControlDeck.set_current_policy_key(...)
-> current_variant_changed.emit(...)
```

这样选择器、策略行和页面跳转终于共用同一个当前态。

### 3.3 代码落点

| 文件 | 变更 |
| --- | --- |
| `src/ui/panels/scene_style_override_sections.py` | 新增当前 variant 与当前 policy key 同步；初始化时同步默认当前分区；暴露 `set_current_policy_key()` / `current_policy_key()` |
| `src/ui/panels/scene_style_rules_block.py` | 向外层稳定对象透传 `set_current_policy_key()` / `current_policy_key()` |
| `tests/test_scene_panel_architecture.py` | 增加当前策略行守门：初始态、手动切换、通过 policy key 切换、页面跳转后都必须同步 |

## 4. 与模板管理的一致性差距

### 4.1 板块应统一为五个稳定槽位

后续样式相关页面都应按同一套板块表达，不再按“模板页一种、场景页一种、执行页一种”组织。

| 槽位 | 用户问题 | 模板管理 | 场景规划 | 执行前复核 |
| --- | --- | --- | --- | --- |
| source | 当前样式从哪里来 | 当前模板 | 关联模板 + 当前场景覆盖 | 本次执行使用的模板/场景 |
| policy | 哪些对象单独处理 | 可为空或模板级锁定策略 | 分区是否独立样式 | 只读策略列表 |
| editor | 现在能改什么 | 模板参数编辑 | 当前分区样式编辑 | 不直接编辑 |
| preview | 改完大概长什么样 | 模板预览 | 分区预览 | 执行前预览 |
| receipt | 与基线有什么差异 | 模板摘要 | 与模板差异 | 本次执行差异确认 |

当前最重要的不是再增加说明文字，而是强制页面都走这五个槽位。用户不应该在不同页面学习三套控件语法。

### 4.2 控件协议应进一步收紧

建议后续继续把页面自由拼装收束为以下协议：

| 协议 | 必须提供 | 目的 |
| --- | --- | --- |
| `StyleObjectProjection` | source、preview、policy、difference | 页面只声明状态，不拼 UI |
| `StylePolicyProjection` | toggles、actions、difference | 策略区由投影驱动，不由页面手动建行 |
| `StylePresentationEnvelope` | summary、detail、owner、variant | 预览和回执使用同一套人话摘要 |
| `focus_navigation_field(field_id)` | 返回是否命中 + 高亮稳定控件 | 模板、场景、执行问题队列统一跳转 |
| `current_policy_key` | 当前策略行 | 所有入口都能反馈“正在看哪一项” |

本轮补上的 `current_policy_key` 属于这个协议的关键一环。

## 5. 冗余文案删除方向

场景规划页不应该继续把工程证据放在第一层。建议删除或下沉以下类型文本：

| 当前文本类型 | 建议处理 |
| --- | --- |
| `template 13 / scene 37 / material 6 / output 17` | 下沉到诊断详情，不在主卡片显示 |
| `custom_basic`、`quick_formatting`、`Green/L5` | 转成人话标签，内部 key 放 tooltip 或调试详情 |
| `16 个契约` | 改为“覆盖范围已确认”或“还有 N 项待确认”，契约明细下钻查看 |
| `General formatting must preserve...` | 改为中文边界摘要，英文原文放证据层 |
| `manual / 提示`、`preset / final` | 改为“需要人工确认”“最终输出方案” |

页面第一屏应只保留三类信息：

1. 当前要处理什么。
2. 现在会按哪个模板和规则处理。
3. 哪些地方需要用户确认或可以直接执行。

其余内容都属于详情、证据或调试层。

## 6. 后续必要功能

### P0：统一样式板块蓝图

把模板管理、场景分区样式、执行前复核都显式声明为同一个 `StyleManagementBlock` 内容计划。

验收标准：

- 页面层不再直接拼 `toggle list + preview + difference`。
- 所有样式页面都能报告自身槽位：source、policy、editor、preview、receipt。
- 只读态和可编辑态只通过 mode/projection 决定。

### P0：策略行与预览变体双向绑定

当前已经补齐场景页的 `current_policy_key`。下一步要把模板管理和执行前复核也统一到同一协议：

- 点击策略行，预览切换到同一 variant。
- 跳转到字段，策略行切到同一 variant。
- 切换编辑对象，策略行切到同一 variant。
- 执行前复核点击只读策略行，跳回场景页后仍定位到同一 variant。

### P1：模板管理引入只读策略槽

模板本身不一定需要“开关”，但需要显示哪些场景正在覆盖模板样式。建议模板详情页增加只读策略槽：

```text
模板样式
-> 被哪些场景覆盖
-> 点击进入对应场景分区
```

这样模板管理不再只是“基线编辑页”，还能成为场景覆盖关系的总入口。

### P1：清理页面文案层级

把文案拆成三层：

| 层级 | 放什么 |
| --- | --- |
| 主文案 | 用户目标、当前状态、下一步动作 |
| 辅助文案 | 影响范围、是否可编辑、差异摘要 |
| 证据文案 | schema、契约、覆盖数、内部 key、英文规则原文 |

主文案不再出现内部 key、英文长句、契约数量堆叠。

### P2：截图级验收

结构测试已经覆盖当前态同步，但还缺桌面与窄屏截图验收。后续应补：

- 场景页分区样式当前行截图。
- 执行前复核策略行点击后预览变化截图。
- 从执行前复核跳回场景页后同一分区当前态截图。
- 模板管理、场景规划、执行复核三页首屏对照截图。

## 8. 当前结论

这轮不是视觉润色，而是把“复用”从代码名义推进到用户感知：

- 当前分区不再只存在于下拉框。
- 策略行能同步表达当前分区。
- 页面跳转、高亮、策略当前态开始共用一个 key。
- 后续可以基于 `current_policy_key` 继续打通模板管理、场景规划、执行前复核之间的同一对象反馈。

下一轮最值得做的是统一三页的内容板块蓝图：少解释，多复用；少矩阵，多对象；少内部证据，多当前状态和可执行动作。
