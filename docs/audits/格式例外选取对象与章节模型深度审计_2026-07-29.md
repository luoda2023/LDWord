## 0. 最终结论

### 0.1 直接回答

方案规则里“格式例外”当前列出的：

- 参考文献；
- 致谢；
- 摘要；
- 附录；
- 个人简历；

**不是章节定义，也不是当前文档中已经识别出的具体章节。**

它们在当前实现中的准确含义是：

```text
五个预先写死的“语义区域段落样式角色”。
```

用户勾选某一项时，系统实际执行的是：

```text
为某个 style key 创建一份方案级 StyleConfig 副本。
```

例如：

```text
参考文献 -> references_body
摘要     -> abstract_body
附录     -> appendix_body
```

勾选动作不会：

- 创建参考文献章节；
- 声明当前文档存在参考文献；
- 指定参考文献从哪一段开始、到哪一段结束；
- 修改章节识别规则；
- 决定该区域是否参与处理；
- 建立 Word 分节符；
- 建立标题层级；
- 选择当前文档里的某一个具体章节。

### 0.2 当前真实语义

当前能力更准确的技术描述是：

```text
如果运行时之后识别出某类语义区域，
则该区域的段落格式优先使用方案中保存的同名样式角色。
```

它是一个条件式样式查找规则：

```text
if detected_region.role == "references":
    style_key = "references_body"
    style = scene.section_styles.get(style_key) or template.styles.get(style_key)
```

因此，“选取例外”不是定义章节，而是预先覆盖一个可能被运行时使用的样式槽位。

### 0.3 正确裁决

在不考虑兼容的前提下：

1. 删除方案中的完整“格式例外”选择和编辑能力。
2. 删除 `SceneWorkspace.section_styles`。
3. 删除通用 `SceneWorkspace.template_overrides`。
4. 模板管理承载“文档部件样式”。
5. 方案只承载“某类识别区域如何处理”的策略。
6. 实际识别出的区域由执行前结构识别结果承载。
7. 真正的章、节由标题层级模型承载。
8. Word 分节由页面/分节模型承载。

## 1. 为什么这个问题会显得模糊

当前界面把四种不同对象压成了一个词：

```text
分区 / 章节 / 样式 / 处理范围
```

但它们在文档系统中不是同一件事。

### 1.1 “章节”至少有四种可能含义

| 对象 | 示例 | 是否有起止范围 | 是否属于当前格式例外 |
| --- | --- | --- | --- |
| 标题章节 | 第一章、1.1、1.1.1 | 有层级，可推导范围 | 否 |
| 语义区域 | 摘要、正文、参考文献、附录 | 有段落范围 | 只间接关联 |
| Word 分节 | 封面节、正文节、横向页面节 | 由 `sectPr` 和分节符定义 | 否 |
| 样式角色 | `references_body`、`abstract_body` | 没有范围，只是一组格式值 | **是** |

当前 UI 使用“参考文献、摘要、附录”这些像章节的名称，但底层保存的是第四种：样式角色。

### 1.2 中文产品语言进一步放大了歧义

以下词在 Word 产品中很容易混淆：

- 章节：通常让人想到第一章、第二章和标题层级；
- 分区：可能让人想到页面区域，也可能想到 Word 分节；
- 区域：可能是运行时识别出的段落范围；
- 样式：可能是 Word Style，也可能是应用内部配置；
- 例外：意味着相对某个基线的少量差异。

当前“格式例外”列表实际上是“样式角色列表”，却使用了语义区域名称展示，导致用户自然理解为：

```text
我正在选择哪些章节要设为例外。
```

这个理解与真实行为不一致。

## 2. 当前五个选项在代码里是什么

### 2.1 固定元数据

`src/config/style_variant_semantics.py` 中定义了五个 `StyleVariantMeta`：

| UI 标签 | `variant_key` | `section_type` |
| --- | --- | --- |
| 参考文献 | `references_body` | `references` |
| 致谢 | `acknowledgment_body` | `acknowledgment` |
| 摘要 | `abstract_body` | `abstract_cn` |
| 附录 | `appendix_body` | `appendix` |
| 个人简历 | `resume_body` | `resume` |

`StyleVariantMeta` 的类注释已经说明它是：

```text
Metadata for a section-specific paragraph style variant.
```

即“面向某类区域的段落样式变体”，不是章节对象。

### 2.2 勾选动作

UI 勾选某项后：

```text
_on_variant_toggled()
-> set_scene_section_style_override()
-> enable_section_style_override()
```

`enable_section_style_override()` 做的事情只有：

1. 读取当前模板对应样式；
2. 深拷贝完整 `StyleConfig`；
3. 写入 `scene.section_styles[variant_key]`。

它没有接收：

- 输入文档；
- 段落列表；
- 章节 ID；
- 起始段落；
- 结束段落；
- 标题文本；
- 识别置信度；
- 文档结构树。

因此从函数契约上就能确定：

```text
它不可能定义当前文档章节。
```

### 2.3 当前 UI 也没有检查区域是否存在

当前状态投影中：

```python
section_enabled = True
```

差异投影的 `_section_enabled()` 也只判断：

```text
scene is not None and meta is not None
```

它没有判断当前文档是否识别出了：

- 参考文献；
- 摘要；
- 附录；
- 致谢；
- 个人简历。

所以用户可以在还没有选择输入文档时，为一个当前任务可能根本不存在的区域开启“例外”。

这进一步证明它是样式槽位，而不是文档区域选择。

## 3. 当前文档的真实区域由谁定义

### 3.1 当前实现不是模板定义区域

此前产品文档中有过：

```text
模板定义结构，运行时识别当前文档。
```

这可以作为目标方向，但不是当前完整实现事实。

当前 `TemplateConfig` 主要提供：

- 页面；
- 样式；
- 标题编号；
- 表格；
- 页眉页脚；
- 目录；
- 题注；
- 公式等格式配置。

模板的 `styles` 中存在：

```text
references_body
abstract_body
appendix_body
...
```

但这些只是样式角色，不包含：

- 区域识别锚点；
- 区域顺序；
- 基数约束；
- 起止规则；
- 标题匹配规则；
- 区域嵌套关系。

### 3.2 当前区域类型由代码中的固定分类表定义

`src/config/section_semantics.py` 定义：

```text
SECTION_TYPE_ALIASES
SECTION_STYLE_KEY_MAP
STYLE_ALIAS_GROUPS
```

它规定：

```text
references  -> references_body
abstract_cn -> abstract_body
abstract_en -> abstract_body
appendix    -> appendix_body
...
```

这里的第一个对象是语义区域类型，第二个对象是样式查找键。

二者是映射关系，不是同一对象。

### 3.3 当前具体区域由运行时识别器生成

`HeadingRecognitionModule` 在拿到真实文档后调用：

```text
rebuild_document_index()
```

运行时通过：

- 标题文本；
- Word 标题样式；
- 大纲级别；
- 固定语义标题；
- 内容模式；
- 区域大致位置；
- 顺序约束；
- 置信度评分；

生成：

```python
DocSection(
    section_type="references",
    start_index=...,
    end_index=...,
    confidence=...,
    title_confident=...,
)
```

这些 `DocSection` 才是当前文档里的实际语义区域。

### 3.4 运行时识别规则目前也是代码硬编码

`heading_recognition.py` 中存在：

- `SPECIAL_SECTION_TITLES`；
- `SECTION_ANCHORS`；
- `SECTION_ORDER`；
- 前置区域和后置区域分类；
- 参考文献内容聚类回退；
- 目录识别；
- 摘要位置评分；
- 区域顺序冲突过滤。

因此当前真实结构链是：

```text
代码内置区域分类和识别规则
-> 读取当前文档
-> 生成 DocTree / DocSection
-> 将每个段落归入某个 section_type
-> 将 section_type 映射到模板 style key
```

方案“格式例外”只插入最后一个样式查找环节。

## 4. 从勾选到最终格式的完整链路

### 4.1 配置阶段

用户在没有输入文档的方案页勾选“摘要”：

```text
摘要
-> variant_key = abstract_body
-> 从模板复制 StyleConfig
-> scene.section_styles["abstract_body"] = copied_style
```

此时系统并不知道：

- 当前文档有没有摘要；
- 有没有中文摘要；
- 有没有英文摘要；
- 摘要从哪一段开始；
- 中英文摘要是否连续；
- 摘要识别是否可靠。

### 4.2 执行阶段

输入文档进入 Pipeline：

```text
HeadingRecognitionModule
-> 构建 DocTree
-> 识别 abstract_cn / abstract_en 等区域
```

### 4.3 段落样式模块

`ParagraphStyleModule` 对每个段落执行：

```text
doc_tree.get_section_for_paragraph(index)
-> 获得 section_type
-> style_key_for_section(section_type)
-> 获得 abstract_body / references_body 等 key
-> config.styles.get(style_key)
-> 应用格式
```

### 4.4 方案例外插入的位置

`resolve_config()` 会把：

```text
scene.section_styles
```

覆盖进最终：

```text
config.styles
```

因此最终链路是：

```text
UI 预先创建样式角色覆盖
                    ↓
运行时识别实际语义区域
                    ↓
将区域类型映射到样式角色
                    ↓
命中方案覆盖或模板样式
```

这说明当前选项定义的是：

```text
识别成功后使用哪个样式值。
```

不是：

```text
文档中有哪些章节。
```

## 5. 它为什么也不能被叫作“具体区域选择”

### 5.1 一个样式角色可能对应多个语义区域

当前映射：

```text
abstract_cn -> abstract_body
abstract_en -> abstract_body
```

中文摘要和英文摘要是两个不同的运行时区域，但共享同一个样式角色。

所以 UI 中的“摘要”不是一个具体 `DocSection`。

### 5.2 一个语义区域可能包含多个真正章节

例如附录：

```text
附录 A
附录 B
附录 C
```

运行时可能把它们整体归入 `appendix` 区域，但内部仍然可以有多个标题和章节。

`appendix_body` 只是一套附录正文样式，不能表示：

- 附录 A；
- 附录 B；
- 附录 C；
- 其中某一个附录。

### 5.3 参考文献不等于章节

参考文献通常是一个文档组成部分。

它可以有一个标题和若干条目，但它不属于正文的“第一章 / 第二章”层级。

将它和章节混为一谈，会影响：

- 标题编号；
- 目录；
- 页码阶段；
- 分节；
- 内容显隐；
- 样式范围。

### 5.4 个人简历、致谢、摘要也是文档部件

它们更接近：

```text
front matter / back matter document parts
```

即前置或后置文档部件，不应当使用“章节选择器”的心智。

## 6. 真正的章节模型在哪里

### 6.1 标题章节

正文中的“章、节、小节”由以下对象表达：

```text
HeadingInfo
  para_index
  level
  text
  confidence
```

以及：

```text
DocTree.headings
DocTree.heading_map
```

这套模型回答：

- 哪一段是标题；
- 标题是第几级；
- 标题文本是什么；
- 哪些一级标题构成正文章节。

### 6.2 技术长文档章节清单

技术文档还有独立的：

```text
TechnicalChapterInventoryItem
TechnicalChapterInventoryResult
```

它基于正文标题构建章节清单。

这进一步证明项目内部已经把：

```text
chapter
```

和：

```text
abstract / references / appendix region
```

视为不同对象。

### 6.3 Word 分节

Word 的分节是页面布局对象：

- 封面节；
- 正文节；
- 横向表格节；
- 不同页眉页脚节；
- 不同页码阶段。

它由 `section_format`、页码规划和 `sectPr` 处理。

它与 `references_body` 等段落样式角色没有直接等价关系。

## 7. 当前设计实际混合了四层对象

### 7.1 区域类型定义

回答：

```text
论文里允许有哪些功能区域？
```

例如：

- 封面；
- 声明；
- 摘要；
- 目录；
- 正文；
- 参考文献；
- 附录；
- 致谢；
- 个人简历。

当前来源：代码硬编码分类。

### 7.2 当前文档区域实例

回答：

```text
这篇文档实际识别出了哪些区域？
每个区域从哪里开始、到哪里结束？
识别有多可信？
```

当前来源：`DocTree.sections`。

### 7.3 区域处理策略

回答：

```text
当前方案要如何处理该类区域？
```

例如：

- 套用模板；
- 保留原格式；
- 不处理；
- 处理前确认。

当前缺少干净、正式的独立模型。

### 7.4 区域样式角色

回答：

```text
该类区域最终应使用什么格式？
```

当前来源：

- `TemplateConfig.styles`；
- 被 `scene.section_styles` 再次覆盖。

### 7.5 当前格式例外的错误

它用“区域名称”展示“样式角色”，又放在“方案规则”里，使用户误以为自己同时在做：

```text
定义区域
+ 选择区域
+ 设置处理策略
+ 设置格式
```

实际上只做了最后一项中的一部分。

## 8. 正确的四层结构模型

### 8.1 文档结构 Profile

建议新增清晰的领域对象：

```yaml
DocumentStructureProfile:
  profile_id: thesis_default
  mode_id: thesis
  region_types:
    - role_id: abstract_cn
      label: 中文摘要
      cardinality: "0..1"
      order_group: front_matter
      style_role: abstract_body
      detector_id: thesis_abstract_cn

    - role_id: abstract_en
      label: 英文摘要
      cardinality: "0..1"
      order_group: front_matter
      style_role: abstract_body_en
      detector_id: thesis_abstract_en

    - role_id: body
      label: 正文
      cardinality: "1"
      order_group: body
      style_role: body

    - role_id: references
      label: 参考文献
      cardinality: "0..1"
      order_group: back_matter
      style_role: references_body
      detector_id: thesis_references
```

它负责定义：

- 当前模式有哪些语义区域类型；
- 区域顺序；
- 是否可重复；
- 如何识别；
- 使用哪个样式角色；
- 支持哪些处理策略。

它不负责具体字体值。

### 8.2 运行时区域实例

建议对象：

```yaml
DetectedRegion:
  region_id: references@184
  role_id: references
  start_paragraph: 184
  end_paragraph: 226
  confidence: 0.91
  evidence:
    - title_match: "参考文献"
    - position: back_matter
```

它是当前输入文档的事实，不应持久化进通用方案。

### 8.3 方案处理策略

建议对象：

```yaml
PlanRegionPolicy:
  role_id: references
  treatment: apply_template
  on_low_confidence: require_confirmation
```

可用处理策略：

```text
apply_template       套用模板
preserve_source      保留原格式
skip                 不处理
confirm_before_apply 识别不确定时确认
```

方案不包含 `StyleConfig`。

### 8.4 模板样式映射

建议对象：

```yaml
Template:
  role_styles:
    body: ...
    abstract_body: ...
    abstract_body_en: ...
    references_body: ...
    appendix_body: ...
```

模板负责最终视觉值。

### 8.5 章、节标题树

正文的章节结构仍然是：

```yaml
HeadingNode:
  heading_id: paragraph@42
  level: 1
  text: "第一章 绪论"
  children:
    - level: 2
      text: "1.1 研究背景"
```

它与文档区域类型相互关联，但不能合并。

例如：

```text
references 区域内可能没有正文标题树；
appendix 区域内可能有多个一级附录标题；
body 区域内可能有几十个章、节。
```

## 9. 无兼容约束下的数据模型裁决

### 9.1 从 `SceneWorkspace` 删除

建议删除：

```python
section_styles: dict
template_overrides: dict
```

理由：

- 没有发布兼容压力；
- 当前内置方案没有使用；
- 它们破坏方案与模板边界；
- 继续保留会让错误模型进入公开版本。

### 9.2 重新裁决 `reference_style`

当前 `ReferenceStyleConfig` 包含：

- 中文字体；
- 英文字体；
- 字号；
- 条目段后；
- 悬挂缩进。

这些都是最终视觉值，应并入：

```text
Template.role_styles.references_body
```

方案保留：

```text
citation_link
reference validation
reference conversion / renumber behavior
```

即：

```text
参考文献长什么样 -> 模板
参考文献怎么处理 -> 方案
```

### 9.3 重新裁决 `FormatScopeConfig.sections`

在无兼容约束下，不应继续保留一组容易被理解为章节定义的布尔字典。

建议替换为：

```text
application_boundary
+ region_policy_by_role
```

而且当前只有 `full_document` 可执行，方案页没有必要展示单选项控件。

在真正支持以下模式前：

- 按模板/结构 Profile；
- 仅正文；
- 选择区域；

## 11. 如果用户真的想给某一章设置例外

这与当前功能完全不同。

### 11.1 当前功能无法表达

当前 `section_styles` 的 key 只有：

```text
references_body
acknowledgment_body
abstract_body
appendix_body
resume_body
```

它不能表达：

- 第一章；
- 第二章；
- 某个标题 ID；
- 某个页码范围；
- 某个段落范围；
- 某个附录实例。

### 11.2 真正章级例外必须绑定当前文档

如果未来确有需求，模型应类似：

```yaml
DocumentRunAdjustment:
  document_revision: sha256:...
  target:
    kind: heading_subtree
    heading_id: paragraph@42
  action:
    preserve_source_format: true
```

或：

```yaml
  target:
    kind: paragraph_range
    start: 42
    end: 87
```

它只能属于：

- 当前执行会话；
- 当前文档项目；
- 或显式保存的文档级任务。

不能属于可跨文档复用的通用方案。

### 11.3 章级“视觉不同”仍应谨慎

如果用户希望“第三章使用另一种字体”，应先判断：

- 是不是源文档异常，需要保留原样；
- 是不是一个新的语义角色；
- 是不是模板本身缺少某种标题/正文样式；
- 是不是仅当前文档的特殊情况。

不应立即扩张为长期方案格式覆盖。

## 12. 正确的执行顺序

推荐目标链：

```text
工作模式
-> 选择 DocumentStructureProfile
-> 读取输入文档
-> 识别 DetectedRegion 和 HeadingTree
-> 预检低置信度区域
-> 应用 PlanRegionPolicy
```

这条链中：

- Template 定义“长什么样”；
- SessionAdjustment 定义“本次偏差”。

每一层只回答一个问题。

## 14. 验收标准

### 14.1 对象语义

- UI 中不再把样式角色描述成章节定义。
- “章节”只用于标题层级或章节清单。
- “文档部件”用于摘要、参考文献、附录、致谢等功能区域类型。
- “识别区域”用于当前文档里的具体起止范围。
- “Word 分节”只用于页面布局分节。

### 14.2 配置

- 方案 JSON 不包含 `StyleConfig`。
- 方案 JSON 不包含通用模板字段覆盖。
- 模板是字体、字号、间距和缩进的唯一长期事实源。
- 当前文档区域实例不会写入通用方案。

### 14.3 运行时

- 结构识别在输入文档加载后执行。
- 每个 DetectedRegion 有起止范围、类型、置信度和证据。
- 样式应用以 DetectedRegion 的 role 映射模板 style role。
- 未识别出某区域时，对应模板样式自然不被使用。
- 低置信度区域不会静默大范围修改。

### 14.4 用户理解

用户能够正确回答：

1. “参考文献”是模板里的样式角色，还是当前文档里的一个实际区域？
2. 当前文档是否真的识别出了参考文献？
3. 参考文献从哪一段到哪一段？
4. 当前方案会套用模板、保留原样还是不处理？
5. 最终字体和缩进来自哪个模板？
6. 第一章、第二章在哪里查看和选择？

### 14.5 回归场景

至少验证：

1. 有中文摘要和英文摘要的论文；
2. 只有中文摘要的论文；
3. 没有参考文献标题但存在编号文献条目的论文；
4. 多个附录的论文；
5. 致谢标题误出现在正文句子中的文档；
6. 技术文档的多级章节；
7. 带多个 Word 分节的公文；
8. 未识别出任何特殊区域的普通报告。

## 17. 最终裁决

当前“选取例外”的真实对象是：

```text
预定义的语义区域段落样式角色。
```

它不是：

```text
章节定义
当前文档区域实例
处理范围选择
Word 分节
标题章节选择
```

正确产品模型应拆成：

```text
DocumentStructureProfile
  定义可能有哪些文档部件，以及如何识别。

DetectedRegion / HeadingTree
  表示当前文档实际有哪些区域和章节。

PlanRegionPolicy
  决定每类区域如何处理。

Template role_styles
  决定每类区域最终长什么样。
```

由于产品尚未发布，不需要为错误模型保留兼容路径。应在首发前删除方案级 `section_styles`、通用 `template_overrides` 和完整格式例外编辑器，避免把样式角色继续伪装成章节选择。
