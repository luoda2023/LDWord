# 工作模式与母版管理配置分层规划

日期：2026-07-09

## 1. 背景判断

本轮讨论从公文场景展开，但真正暴露的问题不是“公文要不要多做几个模板”，而是当前产品对象的层级需要重新命名和分离。

此前已经明确：

- 试卷场景可以继续走“装配页面 + 母版 + 输出版本”的路线。
- 公文场景不能只定义成一个粗粒度“公文排版”，因为公文存在通知、函、请示、报告、批复、纪要等多种文种；这些文种不应该全部变成独立大模板，而应该成为母版之上的轻量装配种子或文种 profile。
- 论文、试卷、标书、公文的使用者通常相对独立，顶层应允许切换“论文版 / 试卷版 / 标书版 / 公文版”等工作模式。
- 顶部标题栏 `Alavette Form V1.0` 右侧适合放一个当前工作模式选择器，例如“试卷版 v”。

最新修正是：这里讨论的核心对象应叫“母版”，不是“模板”。模板体系仍然需要继续规划，但不是当前阶段的主要问题。当前阶段要先把工作模式、母版、场景规则、资料包和现有配置文件边界拆清楚，避免后续迁移时丢功能。

## 2. 术语裁决

### 2.1 工作模式

工作模式是产品顶层入口，表示用户当前主要处理哪类文档。

建议初始工作模式：

- 论文版
- 试卷版
- 标书版
- 公文版

工作模式负责决定：

- 左侧导航展示哪些页面。
- 默认进入哪个装配/执行页面。
- 可选母版库范围。
- 可选资料包 schema 范围。
- 默认运行规则 profile。
- 默认输出版本。

工作模式不是一个运行时格式配置，也不是一个 Word 母版文件。

### 2.2 母版

母版是用户能理解、能选择、能复制、能打开文件夹、能生成样张的版式壳。

母版可以包含：

- 可打开的 DOCX 母版文件。
- 母版 manifest。
- 占位符定义。
- 可视预览信息。
- 可绑定的资料字段。
- 母版适用范围，例如试卷、公文函件、公文纪要、标书正本等。

试卷中的“默认试卷母版”、公文中的“GB/T 9704 通用公文母版”、标书中的“商务标母版”，都属于母版。

母版不应该承载：

- 运行时模块开关。
- 资料包校验策略。
- 输出版本集合。
- 审核/归档/法律有效性。
- 复杂模板参数体系的全部细节。

### 2.3 模板

模板是更细的格式参数体系，当前代码中主要对应 `TemplateConfig`：

- 页面设置。
- 正文样式。
- 标题编号。
- 表格。
- 页眉页脚。
- 目录。
- 题注。
- 参考文献样式。

产品文案上，模板暂时不应作为顶层用户对象继续放大。它可以作为母版背后的技术参数层，后续再专门规划。

关键裁决：当前阶段不要把“母版管理”直接等同于现有 `TemplatePanel` 改名。`TemplatePanel` 管的是格式参数，母版管理还应该管理 DOCX 壳、占位符、样张、文件夹和装配入口。

### 2.4 场景规则

现有 `SceneWorkspace` 更像“运行规则 profile”，而不是母版。

它现在承载：

- `input_source_profile`
- `compliance_profile`
- `delivery_presets`
- `module_switches`
- `exam_paper`
- `template_overrides`
- `section_styles`
- `strict_mode`

这些都是“怎么运行、怎么检查、怎么交付”的规则，不是母版本体。

因此，现有“场景配置”不应直接改名成“母版管理”。更合适的产品改名是“模式规则”或“规则配置”，长期可以成为工作模式下的高级设置。

### 2.5 资料包

资料包是一次运行或一类运行的业务数据上下文。

例如：

- 试卷：题库、题图、答案、解析、考试字段。
- 公文：发文机关、文号、主送、抄送、附件、归档信息、印章素材。
- 标书：企业资质、人员、业绩、授权书、盖章页、附件清单。
- 论文：学校规则、作者、导师、学院、专业、参考文献规则来源。

资料包不应写入母版文件本身；母版只声明需要哪些槽位，资料包提供实际值。

## 3. 当前项目边界

当前相关代码和配置大致如下：

```text
src/config/scene.py          SceneWorkspace，运行规则与资料/交付 profile
src/config/template.py       TemplateConfig，格式参数基线
src/config/resolver.py       template -> scene -> session 合并
src/config/library.py        scenes/ 和 templates/ 的配置库管理
src/ui/bridge.py             当前 scene/template 的全局桥接状态
src/ui/title_bar.py          顶部标题栏，可放工作模式选择器
src/ui/panel_registry.py     左侧导航 panel 注册
src/ui/panels/scene_panel.py 场景配置 UI，含试卷装配、规则、资料包、输出
src/ui/panels/template_panel.py 模板参数管理 UI
exam_masters/                当前试卷母版 DOCX 资源
scenes/                      当前场景 JSON，平铺
templates/                   当前模板 JSON，平铺
```

现有优点：

- `resolve_config()` 已经有清晰合并顺序，运行时不必第一阶段动。
- `SceneWorkspace` 和 `TemplateConfig` 已经分开。
- 试卷母版已经有 `exam_masters/builtin` 与用户副本概念。
- `PanelBridge` 已经集中管理当前 scene/template，适合追加 work mode 状态。

现有问题：

- `scenes/`、`templates/` 都是平铺目录，不利于区分论文、试卷、公文、标书。
- UI 里“场景配置”含义过重，既像业务域，又像规则，又像装配页。
- UI 里“模板管理”容易被误解为母版管理，但它实际上主要编辑 `TemplateConfig`。
- `src/config/library.py` 当前只把 `default` 与 `thesis_gbt` 种为模板库文件，并把 `official_gbt`、`bid_engineering` 等旧模板文件列入 obsolete；这对“按工作模式管理母版”是不够的。
- 工作台、修复导航、场景面板、资料包面板中有大量 `panel_id="scene"` 和 `panel_id="template"` 的隐式依赖，不能贸然改 id。

## 4. 目标信息架构

## 5. 配置目录分层建议

不同工作模式的配置文件应该分文件夹放置，但不建议第一刀就迁移所有现有文件。目标目录可以先定义，迁移分阶段执行。

### 5.1 目标目录草案

建议引入新的产品配置根目录，避免继续扩大 `scenes/` 和 `templates/` 的语义混乱。

```text
config_library/
  work_modes/
    exam/
      mode.json
    thesis/
      mode.json
    bidding/
      mode.json
    official/
      mode.json

  scene_profiles/
    exam/
      default.json
      answer_sheet.json
    thesis/
      default.json
      school_rule.json
    bidding/
      default.json
      qualification_archive.json
    official/
      default.json
      notice.json
      letter.json
      meeting_minutes.json

  masters/
    exam/
      builtin/
        default_exam.master.json
        default_exam.docx
      user/
    official/
      builtin/
        gbt_9704_standard.master.json
        gbt_9704_standard.docx
        official_letter.master.json
        official_letter.docx
      user/
    bidding/
      builtin/
      user/
    thesis/
      builtin/
      user/

  material_schemas/
    exam/
    official/
    bidding/
    thesis/

  templates/
    internal/
      default.json
      thesis_gbt.json
```

其中：

- `work_modes/` 放顶层工作模式声明。
- `scene_profiles/` 放原 `SceneWorkspace` 类配置的下一代分目录版本。
- `masters/` 放母版 manifest 和 DOCX 壳。
- `material_schemas/` 可以先不迁，当前仍由 `src/config/material_schema_registry.py` 提供。
- `templates/internal/` 表示当前 `TemplateConfig` 技术层，暂不作为主要产品对象。

### 5.2 兼容期目录

第一阶段不要立刻删除旧目录，采用双读或投影：

```text
scenes/        旧场景规则，继续可读
templates/     旧模板参数，继续可读
exam_masters/  旧试卷母版资源，继续可读

config_library/ 新目录，只先放新增 work_modes 与少量母版 manifest
```

兼容策略：

- 新 UI 先从 `work_modes` 读取工作模式。
- 每个工作模式仍映射到旧 `scene_id`。
- 母版库先读取新 `masters/<mode>/`，找不到时回退旧 `exam_masters/` 或内置工厂。
- `SceneWorkspace` 文件仍从 `scenes/` 读取。
- `TemplateConfig` 文件仍从 `templates/` 读取。

### 5.3 为什么不能第一刀迁文件

不能第一刀迁文件，原因有四个：

1. 现有测试和运行时大量依赖 `scenes/*.json` 与 `templates/*.json`。
2. `library.py` 现在还承担 seed、obsolete prune、fallback builtin factory 等职责，直接换目录会影响场景加载。
3. 试卷母版已有 `exam_masters/` 资源与用户副本逻辑，贸然移动会影响打开母版文件夹、创建副本、生成样张。
4. 工作台修复跳转依赖 `panel_id` 与当前 scene/template 上下文，配置迁移应晚于 UI 兼容层。

## 6. 配置对象建议

### 6.1 WorkModeSpec

新增工作模式声明，不直接替换 `SceneWorkspace`。

```json
{
  "mode_id": "official",
  "label": "公文版",
  "description": "公文、通知、批复、函、纪要等正式文档装配",
  "default_scene_profile_id": "official/default",
  "default_master_id": "official/gbt_9704_standard",
  "master_family_ids": ["official"],
  "material_schema_ids": ["official_document_v1", "administrative_meeting_fields_v1"],
  "visible_panels": ["workbench", "scene", "masters", "assets"],
  "default_entry_panel": "workbench"
}
```

注意：`visible_panels` 中可以先继续使用旧 `scene` / `template` panel id，产品文案再显示为“模式规则 / 母版管理”。

### 6.2 MasterSpec

母版 manifest 管母版资产，而不是运行规则。

```json
{
  "master_id": "official/gbt_9704_standard",
  "mode_id": "official",
  "label": "GB/T 9704 通用公文母版",
  "family": "official",
  "docx_path": "gbt_9704_standard.docx",
  "preview_sample_path": "gbt_9704_standard_sample.docx",
  "placeholders": [
    "organization",
    "document_no",
    "title",
    "recipient",
    "body",
    "issue_date"
  ],
  "supported_assembly_types": [
    "notice",
    "report",
    "request",
    "approval"
  ],
  "template_config_id": "official_gbt",
  "boundaries": [
    "does not certify official release validity",
    "does not verify seal legality"
  ]
}
```

这里的 `template_config_id` 只是母版背后的格式参数基线，不等同于母版本身。

### 6.3 SceneProfileSpec

下一代场景规则文件可以继续承载 `SceneWorkspace`，但目录上归入工作模式。

```json
{
  "profile_id": "official/default",
  "mode_id": "official",
  "legacy_scene_id": "official",
  "runtime_config": {
    "strict_mode": false,
    "input_source_profile": {},
    "compliance_profile": {},
    "delivery_presets": []
  }
}
```

第一阶段可以不引入这个包装，先由 `work_mode.default_scene_id` 指向旧 `scenes/official.json`。

## 7. UI 执行方案

### 7.1 标题栏工作模式选择器

位置：标题栏应用名右侧。

形态：

```text
Alavette Form V1.0   [试卷版 v]
```

行为：

- 显示当前工作模式。
- 点击后列出论文版、试卷版、标书版、公文版。
- 切换前检查 scene/template/master dirty 状态。
- scene/template dirty 时提供“保存并切换 / 放弃更改 / 取消”三态决策；保存失败时必须回退到原工作模式并保留 dirty。
- 切换后加载该工作模式默认 scene profile 和默认母版。

第一阶段不需要根据模式重排全部导航，只需要保证上下文切换正确。

### 7.2 左侧导航命名

短期建议：

```text
工作台
模式规则   原 scene panel，id 仍为 scene
母版管理   新产品对象，短期可先落在原 template panel 或试卷母版页，但必须谨慎
资料包
主题
偏好设置
```

重要：`panel_id` 不要第一阶段改。只改显示文案，降低工作台跳转和测试破坏风险。

### 7.3 原 ScenePanel 的定位

原 `ScenePanel` 不应叫母版管理。它更适合变成：

- 模式概览
- 装配规则
- 风险检查
- 资料包要求
- 生成结果

其中 `scn_exam_paper` 这类装配页后续可以抽到模式专属装配页中。

### 7.4 母版管理的定位

母版管理应围绕母版对象，而不是只围绕 `TemplateConfig` 字段：

- 当前母版选择。
- 创建副本。
- 打开母版文件夹。
- 打开母版 DOCX。
- 导入母版。
- 生成样张。
- 母版预览。
- 占位符/字段槽位检查。
- 绑定的格式参数摘要。

这与现有试卷装配页的母版卡片更接近，而不是现有模板参数面板。

### 7.5 TemplatePanel 的阶段定位

`TemplatePanel` 当前仍然有价值，但产品上应暂时降为高级格式参数编辑。

短期可选策略：

- 保留入口，但显示为“格式参数”或“高级样式”。
- 在母版管理中提供“编辑格式参数”的跳转。
- 不把它当成母版管理最终形态。

## 8. 迁移路线

### Phase 0：文档和边界冻结

目标：

- 明确工作模式、母版、模板、场景规则、资料包的术语。
- 明确不能把 `SceneWorkspace` 直接改成母版。
- 明确不能把 `TemplateConfig` 直接宣传成母版。
- 明确旧目录暂不迁移。

当前文档即为 Phase 0 记录。

### Phase 1：新增工作模式 registry

动作：

- 新增 `src/config/work_mode.py`。
- 定义 `WorkModeSpec`。
- 提供 `list_work_modes()`、`get_work_mode()`、`default_work_mode()`。
- 增加从当前 scene 推导 work mode 的 helper。

不做：

- 不改 resolver。
- 初始阶段不改 pipeline；后续仅允许按模式做窄口 runtime 接入，并保留原有输出/报告兼容。
- 不迁移配置文件。
- 不删除旧 scene/template。

### Phase 2：PanelBridge 增加工作模式状态

动作：

- 在 `PanelBridge` 增加 `work_mode_changed`。
- 增加 `current_work_mode_id()`。
- 增加 `set_current_work_mode()`。
- 工作模式切换时同步加载默认 scene/template/master。

兼容：

- `current_scene()` 继续存在。
- `current_template()` 继续存在。
- 旧面板继续监听 `scene_changed` 和 `template_changed`。

### Phase 3：标题栏选择器

动作：

- 在 `src/ui/title_bar.py` 加工作模式胶囊。
- 连接 `PanelBridge.work_mode_changed`。
- 切换时检查 dirty 状态。

验收：

- 切换到试卷版后，工作台当前 scene 为 `exam`。
- 切换到公文版后，工作台当前 scene 为 `official`。
- 切换不丢当前 `PanelBridge` scene/template 状态。

### Phase 4：母版库抽象

动作：

- 新增 `src/config/master_library.py` 或相似模块。
- 定义 `MasterSpec`。
- 先读取 `config_library/masters/<mode>/`。
- 试卷回退读取现有 `exam_masters/`。
- 公文/标书/论文暂时可由内置 MasterSpec 包装现有 builtin template factory。

不做：

- 不移动 `exam_masters/`。
- 不删除 `templates/`。
- 不强制生成全部公文母版。

### Phase 5：配置目录试点

动作：

- 只为试卷或公文做一个新目录试点。
- 例如：

```text
config_library/masters/exam/builtin/default_exam.master.json
config_library/work_modes/exam/mode.json
```

验收：

- 新目录存在时优先读取新 manifest。
- 新目录不存在时回退旧逻辑。
- 打开母版文件夹、创建副本、生成样张仍可用。

### Phase 6：UI 分拆

动作：

- 原 `ScenePanel` 改产品文案为“模式规则”。
- 新增或重构“母版管理”页面。
- 试卷装配页从 ScenePanel 中逐步抽出为试卷版专属装配页。
- 公文版新增公文装配页，支持文种 + 母版 + 资料包。

验收：

- 工作台修复问题仍能跳转到模式规则、母版管理、资料包。
- `panel_id` 迁移前保持兼容别名。

### Phase 7：旧目录迁移

只有在 Phase 1-6 稳定后，才考虑迁移旧配置文件。

迁移策略：

- 复制，不移动。
- 建立 alias。
- 加版本字段。
- 加迁移报告。
- 测试全部通过后再考虑隐藏旧目录。

## 9. 风险清单

### 风险 1：把 SceneWorkspace 改名成母版导致功能丢失

`SceneWorkspace` 中有资料 schema、交付 preset、对象预检、模块开关、试卷装配规则。这些不是母版。

缓解：

- UI 文案改为“模式规则”。
- 保留 scene 运行时模型。
- 新增母版模型，不复用 scene 模型。

### 风险 2：把 TemplateConfig 当成母版

`TemplateConfig` 是格式参数，不是可打开的 DOCX 母版壳。

缓解：

- 母版必须有 `MasterSpec`。
- 母版可绑定 `template_config_id`，但两者不是同一个对象。
- TemplatePanel 暂时定位为高级格式参数。

### 风险 3：配置目录迁移破坏加载

`library.py` 现在承担很多兼容职责，直接迁目录会造成 scene/template 找不到。

缓解：

- 新目录先双读。
- 旧目录继续可读。
- 先做 work mode registry，再做 master library，再迁文件。

### 风险 4：导航跳转失效

工作台 issue repair 当前依赖 `panel_id="scene"` 和 `panel_id="template"`。

缓解：

- 第一阶段不改 panel id。
- 新文案先不动内部 id。
- 后续改 id 时提供 alias map。

### 风险 5：母版文件与参数配置漂移

DOCX 母版、母版 manifest、TemplateConfig 可能不一致。

缓解：

- `MasterSpec` 增加 `template_config_id`。
- 增加占位符扫描。
- 增加样张生成和母版预检。
- 报告中输出母版 id、文件路径、占位符状态。

### 风险 6：不同工作模式配置互相污染

论文、公文、标书、试卷的母版和资料包需求不同，平铺目录会越来越混乱。

缓解：

- 新配置按 `mode_id` 分目录。
- 母版选择器按当前工作模式过滤。
- 资料包 schema 按当前工作模式过滤。

## 12. 当前结论

这次调整应该被视作“产品对象分层”，不是简单 UI 改名。

最终目标是：

```text
用户切换工作模式
  -> 看到该模式自己的装配页、母版库、资料包和规则
  -> 选择母版
  -> 填资料包或导入内容
  -> 按模式规则生成输出
```

当前阶段必须坚持三条线：

1. 母版不是模板。
2. 场景规则不是母版。
3. 配置可以按工作模式分目录，但不能第一刀迁移旧文件。

只有这样，试卷、公文、标书、论文四类业务才能逐步独立，而现有运行能力、修复导航、报告证据和资料包链路不会被打散。

## 13. 试卷链路基准补充

补充文档：[`试卷链路基准验收与母版视角补充_2026-07-09.md`](试卷链路基准验收与母版视角补充_2026-07-09.md)

以试卷链路复盘后，本规划还需要额外强调这些验收视角：

- 母版生命周期要作为一等对象：内置、用户副本、导入、手动发现、无效忽略、样张生成、删除都要有边界。
- 占位符契约要进入 `MasterSpec`，并支持必填项、可选项、运行时字段、生成字段和旧版占位符兼容。
- 运行时字段、资料包字段、母版占位符和交付版本字段必须分开，不要混到同一个配置对象。
- 样张是验收产物，不是母版本体；正式输出、样张、报告也需要分清。
- 用户母版目录必须按“只复制、不移动、不批量删除”的原则保护。
- 报告证据需要能追溯 `mode_id`、`scene_id`、`master_id`、母版文件路径、占位符检查和输出版本。
- 第一阶段可以改产品文案和增加工作模式 selector，但不要急着改 `scene`、`template`、`scn_exam_paper` 等内部 ID。
- 试卷当前以 DOCX/XML/文本测试为主，后续母版产品化后应补 DOCX 渲染截图或 PDF/PNG 样张验收。

因此，试卷应作为第一条 `WorkModeSpec + MasterSpec` 包装试点：先用新 registry 包住现有 `exam_masters/` 和 `ExamBlankStyleSpec`，保持旧目录可读、旧 UI 可用、旧测试可过，再逐步把这个模式推广到公文、标书和论文。

## 19. 方案与模板按工作模式独立存储确认

本轮将原先只在规划层成立的“不同工作模式独立配置”推进到代码和目录结构。现在不再只有母版按 `config_library/masters/<mode>/...` 分层，方案和模板也已进入同一套 mode-scoped library。

最终边界：

```text
工作模式（论文版 / 试卷版 / 公文版 / 标书版 / ...）
  -> 方案库：config_library/plans/<mode>/builtin|user
  -> 模板库：config_library/templates/<mode>/builtin|user
  -> 母版库：config_library/masters/<mode>/builtin|user
```

这意味着：
- 试卷版只列出试卷方案和试卷可用模板。
- 论文版只列出论文方案和论文可用模板。
- 公文版只列出公文方案和公文可用模板。
- 标书版、技术文档版、报告版同理。
- 用户复制/新建出的方案和模板落到当前 mode 的 `user` 目录，不污染其他模式。

旧目录策略：
- `scenes/` 和 `templates/` 不迁移、不批量删除。
- 它们仍作为历史兼容 fallback 存在，但传入明确 `mode_id` 的前台列表不会再混入这些扁平目录。
- 无 mode 的全局读取继续可用于迁移审计和历史兜底，并对重复 builtin descriptor 做去重。

这次修正也补上了一个切换风险：dirty 配置在切换工作模式前保存时，应写回旧 active mode，而不是写入用户即将切到的目标 mode。该逻辑已在 `MainWindow` 修正。

## 20. 工作模式选择与方案选择层级复审

本轮继续复核“顶部工作模式选择”和“原场景改方案”之间的关系。结论是：顶部下拉确实已经承担了原先一部分“场景大类选择”的任务，但它不能、也不应该替代工作模式内部的方案选择。

更准确的分层应为：

```text
顶部工作模式
  -> 论文版 / 试卷版 / 公文版 / 标书版 / 通用版 / ...

当前方案
  -> 原 SceneWorkspace
  -> 用户侧显示为“方案”
  -> 承载处理范围、装配策略、资料要求、交付版本、当前母版绑定等长期规则

当前模板
  -> TemplateConfig
  -> 承载页面设置、正文排版、标题编号、表格、页眉页脚、目录、题注等格式参数

当前母版
  -> MasterSpec / DOCX shell / manifest / placeholder contract
  -> 承载可装配版式壳、占位符、样张、preflight、生命周期动作

当前资料包
  -> MaterialExecutionContext / schema payload
  -> 承载本次或本类业务数据，不写入母版本体
```

### 20.1 顶部选择器的职责边界

顶部选择器负责的是工作模式，而不是具体方案。

它应该做：

- 切换论文版、试卷版、公文版、标书版等顶层产品入口。
- 决定当前可见的方案库、模板库、母版库和资料 schema 范围。
- 成功切换后加载该工作模式的默认方案和默认模板。
- 在当前方案或模板 dirty 时，触发保存、放弃、取消的切换保护。

它不应该做：

- 展开所有试卷方案、所有公文文种、所有学校论文规则。
- 直接替代方案配置页里的方案下拉。
- 把公文 15 类文种升级成 15 个顶层工作模式。
- 把方案、模板、母版、资料包强行合并成一个对象。

因此，“试卷版”是工作模式；“默认试卷 / 随堂测验 / 期中期末”是该模式下的方案或母版族选项，不是新的工作模式。

### 20.2 原场景改方案的技术含义

当前内部 `SceneWorkspace` 仍然可以保留 `scene` 命名，这是兼容历史导航、运行时 resolver、问题修复入口和测试链路的技术名。用户可见层应继续收敛为“方案”。

也就是说：

```text
内部：scene_id / SceneWorkspace / scene_changed / panel_id="scene"
外部：方案 / 方案配置 / 当前方案 / 方案与模板
```

短期不建议重命名内部 ID。真正需要收敛的是所有用户可见文案、下拉选项和状态摘要，而不是立刻重写底层数据结构。

### 20.3 当前代码状态判断

当前主链路方向基本正确：

- `WorkModeSpec` 已经定义工作模式为产品顶层入口，不替代 `SceneWorkspace` 或 `TemplateConfig`。
- 标题栏下拉只写入 `PanelBridge.current_work_mode`，不在标题栏层直接改 scene/template。
- `MainWindow` 监听 `work_mode_changed` 后，负责加载目标模式的默认方案和默认模板，并处理 dirty 切换保护。
- `ScenePanel` 使用 `list_scene_descriptors(mode_id=current_work_mode_id)` 列当前模式方案。
- `QuickExecutionDetail` 也会在工作模式变化时刷新自己的 `_scene_descriptors`。
- `config_library/plans/<mode>/...` 与 `config_library/templates/<mode>/...` 已经让不同工作模式拥有独立方案和模板目录。

当前仍需警惕的不是底层方向，而是 selector 契约没有集中：

```text
ScenePanel 有自己的方案下拉刷新逻辑
QuickExecutionDetail 有自己的方案下拉刷新逻辑
TemplatePanel 有自己的模板下拉刷新逻辑
MastersPanel / 方案预览还有自己的母版列表逻辑
```

它们都知道要按 `mode_id` 过滤，但还没有共享一个统一的投影模型。因此 UI 上仍可能出现：

- 方案配置页和快速执行页显示名不一致。
- 一个地方显示内置方案，另一个地方只显示单个默认方案。
- 默认选中逻辑不一致。
- 工作模式切换后某个面板刷新了，另一个面板仍保留旧缓存。
- “方案”和“母版”选项名称过于相似，导致用户误以为两个下拉应该完全相同。

### 20.4 试卷版的正确解释

试卷版当前应作为基准：

```text
工作模式：试卷版
  -> 方案：
      默认试卷方案
      随堂测验方案
      期中期末方案
  -> 模板：
      默认格式
  -> 母版：
      默认试卷母版
      随堂测验母版
      期中期末母版
  -> 交付：
      学生卷
      答案版
```

这里需要特别区分“方案”和“母版”：

- 方案决定长期装配规则，例如题源方式、答题区策略、交付结果、当前绑定母版。
- 母版决定 DOCX 版式壳和占位符。

如果方案和母版都叫“默认试卷 / 随堂测验 / 期中期末”，用户会自然期待两个下拉完全对应。后续 UI 应尽量写成：

```text
方案：默认试卷方案
使用母版：默认试卷母版
```

而不是让两个下拉都只显示“默认试卷”。

### 20.5 公文版的正确解释

公文版不能把复杂度压到顶部，也不能第一刀做 15 个 DOCX 种子。

正确结构是：

```text
工作模式：公文版
  -> 方案：
      通用发文方案
      函件方案
      纪要方案
  -> 文种 profile：
      通知 / 请示 / 报告 / 批复 / 函 / 纪要 / ...
  -> 母版族：
      通用发文母版
      函件母版
      纪要母版
  -> 资料包 schema：
      official_document_v1
      administrative_meeting_fields_v1
  -> 交付版本：
      正式 Word
      内部审阅稿
      归档清单
```

公文的复杂度应由“方案 + 文种 profile + 母版族 + 资料包 schema + 交付版本”共同承载，而不是做成 15 个顶层场景，也不是做成 15 个互不相干的 DOCX 母版。

### 20.6 后续执行建议

下一步不建议继续散改文案。应先补一层共享选择器投影：

```text
WorkModeSelectorModel
  -> 来源：list_work_modes()
  -> 用于：标题栏

PlanSelectorModel(mode_id)
  -> 来源：list_scene_descriptors(mode_id=mode_id)
  -> 用于：方案配置页、快速执行页、配置管理摘要

TemplateSelectorModel(mode_id, plan_id=None)
  -> 来源：list_template_entries(mode_id=mode_id)
  -> 用于：快速执行页、模板管理页、方案规则里的目标模板选择

MasterSelectorModel(mode_id, plan_id=None)
  -> 来源：list_masters(mode_id) 与当前方案绑定
  -> 用于：方案预览里的母版选择、母版生命周期动作
```

这样可以保证同一个工作模式下：

- 方案配置页和快速执行页看到同一批方案。
- 方案下拉只列方案，不混入模板或母版。
- 模板下拉只列模板，不混入母版。
- 母版选择能清楚说明“当前方案使用哪个母版”。
- 工作模式切换时，各面板使用同一套刷新规则。

## 24. 再审阅：顶层工作模式与方案选择的最终关系

本轮继续复核后，需要把一个关键口径钉住：标题栏下拉负责的是“工作模式/产品版本”，不是具体业务方案。

正确关系应为：

```text
标题栏工作模式
  -> 论文版 / 试卷版 / 公文版 / 标书版 / 通用版

方案配置页或快速执行页的“方案”
  -> 当前工作模式下的内置方案或用户方案
  -> 来源：config_library/plans/<mode>/builtin|user

模板管理或快速执行页的“模板”
  -> 当前工作模式下的格式模板
  -> 来源：config_library/templates/<mode>/builtin|user

方案预览里的“母版”
  -> 当前工作模式下的 DOCX shell / manifest / placeholder contract
  -> 来源：config_library/masters/<mode>/builtin|user，或试卷版兼容的 exam_masters
```

也就是说，“试卷版”不是方案，“默认试卷方案 / 随堂测验方案 / 期中期末方案”才是方案；“公文版”不是方案，“公文-默认 / 函件方案 / 纪要方案”才是方案。

### 24.1 为什么之前容易混

之前混乱主要来自三个名字同时使用“默认试卷”：

```text
默认试卷方案
默认试卷母版
默认格式模板
```

如果 UI 下拉只显示“默认试卷”，用户会自然认为多个下拉应该完全对应。后续所有 selector 必须在文案上带对象名：

- 方案下拉：`默认试卷方案`、`随堂测验方案`、`期中期末方案`。
- 母版下拉：`默认试卷母版`、`随堂测验母版`、`期中期末母版`。
- 模板下拉：`默认格式`、`GB/T 9704 公文格式`。

这不是单纯文案问题，而是防止三个配置对象被误合并。

### 24.2 当前代码状态判断

当前方向基本正确：

- `TitleBar` 的下拉只写入 `PanelBridge.current_work_mode`，不直接替代方案选择。
- `MainWindow` 在工作模式切换后加载该模式的默认方案和默认模板，并处理 dirty 保存/放弃/取消。
- `ScenePanel` 与 `QuickExecutionDetail` 已按 `mode_id` 列方案，不再把论文、试卷、公文、标书的方案混在一起。
- `TemplatePanel` 与快速执行目标模板选择已按 `mode_id` 找模板，跨模式模板不再被悄悄当成可选项。
- `config_selector_models.py` 已集中提供方案、模板、母版 selector 的显示文案，避免各面板各写一套 label。

但仍需注意：

- `SceneWorkspace`、`scene_id`、`scene_changed` 属于内部兼容命名，短期不迁移；用户可见层继续叫“方案”。
- `scn_exam_paper` 这个内部卡片 id 可以先保留，用户可见标题叫“方案预览”。
- 公文的“方案预览”不能只复用试卷母版 UI；它需要自己的文种、母版族、资料包契约和样张动作。

### 24.3 方案预览里到底应该选什么

“方案预览”一级面板本身对应当前方案，但面板内部不能再放一个与顶部或左侧完全冲突的对象。

推荐结构：

```text
方案预览
  当前方案：默认试卷方案 / 公文-默认方案
  使用母版：默认试卷母版 / GB/T 9704 通用公文母版
  使用模板：默认格式 / GB/T 9704 公文格式
  资料状态：本次信息或资料包字段完成度
  预览/动作：打开母版、生成样张、套用示例资料
```

如果面板顶部出现“方案”下拉，它必须与快速执行页的“方案”下拉来自同一个 `PlanSelectorModel(mode_id)`；如果它只是选择母版，就必须明确叫“使用母版”，不能再叫“方案”。

### 27.2 为什么会出现方案与预览下拉不对应

试卷版最典型：

```text
左侧方案列表
  exam
  exam_quiz
  exam_term

方案预览里的试卷母版下拉
  default_exam
  class_quiz_exam
  term_exam
```

这两组本来就不是同一类对象。前者是方案，后者是母版。它们可以默认绑定，例如：

```text
默认试卷方案 -> 默认试卷母版
随堂测验方案 -> 随堂测验母版
期中期末方案 -> 期中期末母版
```

但绑定不等于同一对象。用户在某个方案中改用另一个母版时，应该理解为：

```text
当前方案没有变。
当前方案内部的“使用母版”变了。
```

因此 UI 上更稳的表达是：

```text
方案预览
  当前方案：随堂测验方案
  使用母版：期中期末母版
  使用模板：默认格式
```

不建议在方案预览里再放一个“方案”下拉。方案切换已经由顶部工作模式下的左侧方案列表、工作台“方案与模板”区域承担。

### 27.3 `exam_masters/user` 残留的真实来源

当前 `exam_masters/user` 大量 `user_default_exam_copy_*.docx` 与 `user_imported_exam_*.docx` 的来源是：

```text
创建副本
  -> create_exam_blank_master_copy()
  -> 复制当前母版 DOCX 到 exam_masters/user
  -> _unique_docx_path() 遇到重名后自动追加 _2、_3、...

导入母版
  -> import_exam_blank_master_docx()
  -> 复制外部 DOCX 到 exam_masters/user
```

这些文件是运行期 / 用户态副本，不是产品内置资源。当前已有防线：

```text
.gitignore 忽略 exam_masters/user/
scripts/check_public_release.py 将 exam_masters/user 作为 runtime/user path 警告
sync_user_exam_blank_master_files() 跳过 user_default_exam_copy / user_imported_exam 前缀
```

所以它们不会默认污染母版下拉，也不应进入正式产品包。真正需要修的是认知入口：

```text
内置母版 -> 打开 builtin 母版所在文件夹
用户副本 -> 打开 user 母版所在文件夹
方案文件夹 -> 打开 config_library/plans/<mode>/<source>
模板文件夹 -> 打开 config_library/templates/<mode>/<source>
```

如果用户从内部母版页的“打开当前母版文件夹”进入 `exam_masters/user`，那应该意味着当前选中的确实是用户副本；如果当前选中内置母版，就不应把用户带到旧 user 目录。方案预览主链路已进一步收敛为“打开当前母版 DOCX”，不再把 user 文件池作为默认入口。

### 27.4 当前不能急着做的迁移

不建议现在把 `exam_masters/user` 批量迁移到 `config_library/masters/exam/user`，原因是：

- 旧方案可能仍引用其中某个 `master_docx_path`。
- 有些文件可能是用户手工改过的有效母版。
- 试卷链路仍兼容旧 `exam_masters/`，移动会影响打开文件夹、生成样张和历史方案。

正确做法是后续单独做“用户母版清理 / 归档工具”：

```text
1. 扫描 user 母版目录
2. 区分程序生成副本、用户手工母版、仍被方案引用的母版
3. 只列出未引用项
4. 让用户确认归档或删除
5. 不做静默迁移和静默删除
```

## 28. 再审阅：顶部工作模式接管后，方案选择器与母版选择器的最终裁决

本轮继续按“先审阅，不急着执行”的原则复核。用户指出的问题是对的：标题栏已经接管了论文版、试卷版、公文版、标书版等工作模式后，原来的“场景”不再是顶层产品场景，而应全部降为当前工作模式下的“方案”。因此内部任意选框如果仍让用户感觉是在选工作模式，或者把方案、母版、模板混在一起，就是设计不对。

### 28.1 当前证据

当前目录和代码已经出现正确方向：

```text
config_library/plans/exam/builtin/exam.json
config_library/plans/exam/builtin/exam_quiz.json
config_library/plans/exam/builtin/exam_term.json

config_library/templates/exam/builtin/default.json

config_library/masters/exam/builtin/default_exam.master.json
exam_masters/builtin/default_exam_v20.docx
```

试卷版已经有三个内置方案：

```text
exam       -> 默认试卷方案
exam_quiz  -> 随堂测验方案
exam_term  -> 期中期末方案
```

同时试卷母版库里也有三个可选母版 ID：

```text
default_exam      -> 默认试卷母版
class_quiz_exam   -> 随堂测验母版
term_exam         -> 期中期末母版
```

这就是截图里“两个地方内容明明没对应上”的根因：方案和母版使用了相似业务名称，但它们不是同一个对象。

### 28.2 正确对象关系

后续必须按下面四层固定理解：

```text
工作模式
  -> 由标题栏选择
  -> 论文版 / 试卷版 / 公文版 / 标书版 / 通用版

方案
  -> 由当前工作模式下的方案库提供
  -> config_library/plans/<mode>/builtin|user
  -> 决定本次任务的处理范围、资料要求、交付版本、默认模板、默认母版

模板
  -> 由当前工作模式下的模板库提供
  -> config_library/templates/<mode>/builtin|user
  -> 决定格式参数、页面设置、标题、表格、页眉页脚等样式规则

母版
  -> 由当前工作模式下的母版库提供
  -> config_library/masters/<mode>/builtin|user
  -> 试卷版第一阶段兼容 exam_masters/
  -> 决定 DOCX shell、manifest、placeholder contract
```

所以：

- “试卷版”不是方案。
- “默认试卷方案 / 随堂测验方案 / 期中期末方案”才是方案。
- “默认试卷母版 / 随堂测验母版 / 期中期末母版”不是方案，它们只是方案预览里当前方案使用的 DOCX 外壳。
- “默认格式”是模板，不是方案，也不是母版。

### 28.3 方案预览页的选框应该如何显示

方案预览页本身已经位于“当前方案”之内，因此它不应该再放一个和左侧、工作台重复的“方案”下拉，除非该下拉确实来自 `config_library/plans/<mode>` 并且会切换当前方案。

推荐最终结构：

```text
方案预览
  当前方案：默认试卷方案
  使用母版：默认试卷母版
  使用模板：默认格式
  本次信息：标题、科目、年级、考试时间、满分
  预览：学生卷 / 答案版
```

如果用户在方案预览里看到一个下拉：

- 它若选择 `exam / exam_quiz / exam_term`，标题必须叫“方案”，并同步切换当前方案。
- 它若选择 `default_exam / class_quiz_exam / term_exam`，标题必须叫“使用母版”或“试卷母版”，不能叫“方案”。
- 它若选择 `default / official_gbt / thesis_gbt`，标题必须叫“模板”或“格式模板”。

当前试卷页更适合保留“使用母版”下拉，而不要在方案预览内部再放“方案”下拉。方案切换已经由左侧方案列表和工作台“方案与模板”完成。

### 28.4 为什么左侧方案与方案预览母版可能不完全同步

这是允许的，但必须可解释：

```text
当前方案 = 默认试卷方案
当前方案默认母版 = 默认试卷母版

用户在方案预览里把使用母版改为期中期末母版
  -> 当前方案仍然是默认试卷方案
  -> 当前方案的 exam_paper.blank_style_id 被改为 term_exam
  -> 这是一种方案内配置修改
```

因此“默认试卷方案 + 期中期末母版”并不一定是错，但 UI 必须让用户知道这是“当前方案正在套用另一个母版”，而不是让用户以为左侧方案和内部下拉本来就应该一一对应。

更稳的显示方式：

```text
方案预览
  当前方案：默认试卷方案
  使用母版：期中期末母版
  状态：当前方案已改用非默认母版
```

### 28.5 `exam_masters/user` 为什么有很多文件

`exam_masters/user` 中大量 `user_default_exam_copy_*.docx` 不是内置产品资源，而是历史运行时副本。形成路径是：

```text
创建副本
  -> create_exam_blank_master_copy()
  -> 复制当前 DOCX 母版到 exam_masters/user/
  -> _unique_docx_path() 遇到重名自动追加 _2、_3、...、_100

导入母版
  -> import_exam_blank_master_docx()
  -> 复制外部 DOCX 到 exam_masters/user/
```

这些文件之所以会堆很多，是因为调试和验收时反复点击“创建副本/导入母版”，每次都会生成一个新 DOCX。它们属于本机用户态资产，不属于内置母版库。

当前防护已经存在：

- `.gitignore` 忽略 `exam_masters/user/`。
- `scripts/check_public_release.py` 把 `exam_masters/user` 作为 runtime/user path 警告。
- release 测试覆盖 `exam_masters/user` 和 `config_library/*/*/user`。
- `sync_user_exam_blank_master_files()` 会跳过 `user_default_exam_copy*`、`user_imported_exam*` 这类程序生成前缀，避免它们自动污染母版下拉。

因此这些残留默认不会进入产品；真正的风险是“打开母版文件夹”把用户带到这个历史运行时目录后，会造成认知误判。后续 UI 应优先贯彻“打开当前母版 DOCX”：方案预览打开当前文件本身，归档 / 清理页再提供受控的文件夹入口。

### 28.6 不应立即做的事

暂时不要一刀切把 `exam_masters/user` 删除或迁移到 `config_library/masters/exam/user`：

- 里面可能有用户手工修改过、仍被某个方案引用的 DOCX。
- 当前试卷链路仍兼容 `exam_masters/`，贸然移动会破坏历史方案里的 `master_docx_path`。
- 清理应做成显式工具：先列出“未被任何方案引用的用户母版”，再让用户确认归档或删除。

暂时也不要把试卷三个内置方案再复制成三套独立完整 DOCX 种子。当前更合理的是：

```text
多个方案
  -> 可引用同一套或不同的母版
  -> 方案决定题型/交付/默认字段
  -> 母版决定 DOCX 外壳
```

只有当随堂测验、期中期末在版式外壳上确实出现稳定差异时，才补齐独立母版 DOCX 和 manifest。

### 28.7 其他工作模式怎么办

同样适用四层结构，但成熟度不同：

## 30. 再审：工作模式接管场景后，当前断点在哪里

这轮复核的重点不是继续改文案，而是确认“顶部工作模式 + 原场景改方案”这条线是否真的跑通。结论是：目录分层方向已经基本正确，但有两个运行时断点和一个历史目录治理问题，解释了当前截图里“方案选择”和“方案预览 / 资料填充 / readiness”不对应的现象。

### 30.1 当前应该稳定下来的对象边界

后续所有实现都应按下面这组边界判断归属：

```text
工作模式 WorkMode
  用户入口：论文版、试卷版、公文版、标书版、通用版
  作用：决定当前可见的方案、模板、母版、资料 schema 集合

方案 Plan
  存储：config_library/plans/<mode>/{builtin,user}
  技术对象：SceneWorkspace
  用户命名：方案
  作用：决定当前任务策略、默认文种 / 资料 profile、默认模板、交付版本、场景规则

模板 Template
  存储：config_library/templates/<mode>/{builtin,user}
  技术对象：TemplateConfig
  作用：格式规则、页面、标题、表格、页眉页脚等可复用外观基线

母版 Master
  存储：config_library/masters/<mode>/{builtin,user}
  技术对象：MasterSpec + manifest + DOCX shell
  作用：可装配的 Word 外壳、占位符契约、样张基线

资料包 / 本次资料 Material
  技术对象：MaterialExecutionContext
  作用：本次任务填写的数据、文件、字段映射；不反向污染方案 JSON

公文文种 Profile
  存储：official document profiles
  示例：通知、函、纪要、报告、请示
  作用：字段契约和装配语义；不升格为工作模式
```

这意味着：顶部下拉只管工作模式；左侧“方案配置”和 Workbench 的左侧选框都选方案；模板页只管模板；资料包填充只管本次资料；母版只在方案预览或母版选择区域出现。

### 30.5 历史目录问题：exam_masters/user 为什么有 202 个 DOCX

`exam_masters/user` 当前有 202 个 `.docx`，主要是 `user_default_exam_copy_N.docx`。它们不是新的 `config_library` 内置方案，也不是公文方案；它们是旧试卷母版链路中“创建副本 / 导入母版”产生的用户可编辑 DOCX 文件。

代码路径是：

```text
create_exam_blank_master_copy()
  -> ensure_current_exam_blank_master_docx()
  -> _unique_docx_path(USER_EXAM_MASTER_DIR / f"{style_id}.docx")
  -> copy2(source, target)
```

每次点击创建副本都会物理复制一份 DOCX，文件名冲突时自动加 `_2`、`_3`、`_100`。这保护了用户修改过的 Word 文件，但缺少“是否已有同名副本 / 是否归档旧副本 / 是否只显示当前方案引用副本”的产品治理，所以在文件夹里变成大量残留。

这批文件不应进入正式产品包：`.gitignore` 已忽略 `exam_masters/user/`，`scripts/check_public_release.py` 也把它列为 runtime/user path。但用户从“打开母版文件夹”进入时会看到它们，所以体验上仍然必须治理。

不要把 202 个 DOCX 扫成 202 个可选内置母版
