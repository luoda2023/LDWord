# 公文文档深度审阅与规划

日期：2026-07-09

## 1. 结论先行

公文版当前已经具备一条可继续扩展的骨架：工作模式、方案、模板、母版、文种 profile、资料包 schema、DOCX 装配 runtime、报告证据和测试都已经有落点。它不再是纯规划状态。

但是它还没有达到“像试卷链路一样可完整验收”的程度。当前更准确的状态是：

- 配置隔离已成立：公文方案、模板、母版已经按 `official` 工作模式独立存储。
- 文种建模方向正确：15 个公文类型已经做成 profile/contract，不需要马上扩成 15 份 DOCX 文件种子。
- 装配能力已有最小闭环：可由公文资料字段替换 `official_*` 占位符并生成 DOCX。
- 产品入口仍偏临时：公文动作主要挂在 `MastersPanel` 的通用母版列表里，尚未融入“方案预览 / 资料包填充 / 执行预览”的主链路。
- 验收缺口集中在 UI 编排、资料包字段填充、视觉合规验证、交付版本和人工确认边界。

因此下一步不应第一刀继续改底层 storage，也不应做 15 个文件种子；应该把公文版按“方案预览 + 文种 profile + 母版族 + 资料包填充 + 执行证据”补成可验收链路。

## 2. 当前资产清单

### 2.1 工作模式

`src/config/work_mode.py` 已定义 `official` 工作模式：

- label：公文版
- 默认方案：`official`
- 默认模板：`official_gbt`
- 母版域：`official_master`
- 资料包 schema：`official_document_v1`、`administrative_meeting_fields_v1`
- 语义边界：通知、请示、报告、批复、函、纪要等公文装配入口

这说明“公文版”已经是顶层工作模式，不应再作为论文、标书、试卷的子配置混在一起。

### 2.2 方案 / 模板 / 母版存储

当前公文版实际文件：

```text
config_library/plans/official/builtin/official.json
config_library/templates/official/builtin/official_gbt.json
config_library/templates/official/builtin/official_custom.json
config_library/masters/official/builtin/official_gbt_standard.docx
config_library/masters/official/builtin/official_gbt_standard.master.json
```

结论：公文版已经按工作模式独立存储。方案、模板、母版不再需要和试卷版、论文版共享目录。

仍需注意：

- `SceneWorkspace` 仍是内部技术名，用户侧继续称“方案”。
- `TemplateConfig` 仍代表格式模板，不等同于母版。
- 公文母版目前只有 1 个内置通用母版，还不是完整母版族。

### 2.3 方案配置

`config_library/plans/official/builtin/official.json` 继承自 `create_official_scene()`：

- `scene_id`: `official`
- `template_id`: `official_gbt`
- `compatible_template_ids`: `official_gbt`, `official_custom`
- `material_schema_id`: `official_document_v1`
- required material fields：`organization`, `document_no`, `issue_date`
- compliance rule family：`official_document`
- delivery presets：`formal`, `internal_review`
- module switches：table/page/cleanup/content_fill 开启，formula/citation 关闭

这说明方案层已能表达“公文需要资料包、需要编号保留、需要正式/内部稿交付”的基本策略。

### 2.4 文种 profile

`src/config/official_document_profiles.py` 已覆盖 15 个常见公文类型：

```text
决议、决定、命令（令）、公报、公告、通告、意见、通知、通报、
报告、请示、批复、议案、函、纪要
```

当前实现将 15 个文种抽象为 profile，而不是每个文种一份 DOCX。这是正确方向。原因是大多数公文在版头、文号、标题、正文、署名、日期、版记上的结构相近，真正差异更多来自：

- 文种 profile：字段约束、提示词、默认语气、标题/正文规则。
- 母版族：通用发文、函件、纪要/会议材料等布局差异。
- 资料包 schema：普通公文字段和会议字段的差异。
- 交付版本：正式稿、内部审阅稿、归档清单。

### 2.5 资料包 schema

`src/config/material_schema_registry.py` 已有两套公文相关 schema：

- `official_document_v1`
  - title, body, organization, document_no, issue_date 为核心字段。
  - issuer, recipient, attachment_note, document_type, security_level, urgency, signer, copy_scope, printing_org, printing_date, archive_status, archive_no, retention_period 等为扩展字段。
  - seal 作为可选 asset role。

- `administrative_meeting_fields_v1`
  - meeting_title, meeting_date, participants 等会议/纪要字段。
  - 同样带有文号、签发、密级、抄送、归档字段。

结论：资料包 vocabulary 已经存在；缺的是产品层填充、导入、校验、预览和 unresolved 字段提示。

### 2.6 母版与占位符

当前内置母版：

```text
official_gbt_standard
```

它的 manifest 描述了：

- `mode_id`: `official`
- `template_config_id`: `official_gbt`
- 必需占位符：`official_title`, `official_body`
- 可选占位符：发文机关、发文字号、主送机关、附件说明、署名机关、成文日期、抄送范围、印发机关、印发日期、会议时间、参会人员等。
- 支持 assembly types：包含 `notice`、`minutes` 等。
- 边界：不认证正式签发有效性，不验证盖章合法性，不替代归档审批。

生成器 `src/shared/engine/official_document_master.py` 已能写出通用 GB/T 风格 shell，并附带占位符说明页。当前它更像“通用公文母版壳”，还不是严格意义上覆盖所有文种细节的成熟母版库。

### 2.7 装配 runtime

`src/shared/engine/official_document_assembly.py` 已具备：

- 根据 profile 找 assembly contract。
- 检查母版必需占位符。
- 检查资料包必填字段。
- 替换 `{{official_*}}` 占位符。
- 删除占位符说明页。
- 返回 `OfficialDocumentAssemblyResult`，包含 status、profile、master、schemas、输出路径、已替换占位符、缺失字段、未解析占位符。

`src/pipeline/runner.py` 已接入 runtime：

- 只有当 input profile 包含 `official_document_v1` 或 `administrative_meeting_fields_v1`，并且 `entity_data` 有公文资料信号时才触发。
- 文种优先从 `official_document_type` / `document_type` 读取。
- 若无明确文种，会议 schema 默认 `minutes`，普通公文默认 `notice`。
- 成功时 output_paths 记录为 `official_docx`。

这个触发逻辑相对安全，但产品层必须让“资料包填充”显式写入文种和字段，否则用户可能不知道为什么没有触发装配。

### 2.8 报告证据

`src/reporting/document_sections.py` 已有公文装配报告：

- 标题：公文母版装配证据
- status
- profile
- master
- material schemas
- output DOCX
- replaced placeholders
- missing required fields
- unresolved placeholders

同时已有公文编号保留证据：

- rule family
- profile
- strategy
- heading numbering module
- manual confirmation
- changed heading samples

结论：报告证据的基础不错；后续要把“正式稿 / 内部审阅稿 / 归档清单”的产物证据补实，而不是只停在 delivery preset 名字。

## 3. 当前缺口

### 3.1 产品主链路还没有合体

公文样张动作目前在 `MastersPanel`：

- 文种下拉
- 套用示例资料
- 生成公文样张
- 打开 DOCX

这证明底层能力可用，但它不像试卷链路那样自然地嵌在方案配置页。用户真正需要的是：

```text
公文版
  -> 方案预览
    -> 选择文种
    -> 选择母版族
    -> 查看模板/母版/资料包字段契约
    -> 套用资料包或示例资料
    -> 生成样张/预检
  -> 方案规则
    -> 编号保留、处理范围、交付结果
  -> 工作台执行
    -> 明确使用当前方案 + 当前资料包 + 当前文种
```

也就是说，公文的“母版管理”不应该另开新页面，应该作为方案配置中的一级面板“方案预览”存在。

### 3.2 资料包填充仍是最大断点

schema 有了，但用户还缺一个强交互入口：

- 字段表单：标题、正文、发文机关、文号、主送、成文日期等。
- 文种联动：选纪要时显示会议时间、参会人员等字段。
- 必填校验：缺 title/body/organization/document_no/issue_date 时提前拦截。
- 占位符映射预览：告诉用户哪些字段会进哪些 `official_*` 占位符。
- 未解析占位符提示：母版里还有哪些占位符没有值。
- 资料来源：手填、JSON、从 Word 正文抽取、从资料包导入。

所以用户提出“资料包填充”这个命名是对的，它是公文版能不能跑通的关键。

### 3.3 母版族还不足

当前只有 `official_gbt_standard`。建议下一阶段不要扩到 15 个种子，而是先做 2-3 个母版族：

1. 通用发文母版
   - 覆盖通知、通报、报告、请示、批复、意见、决定等大多数正文类公文。

2. 函件母版
   - 覆盖函，重点处理主送、事项、结尾语和较轻的版式差异。

3. 纪要 / 会议材料母版
   - 覆盖纪要，增加会议时间、参会人员、议定事项等资料字段。

后续再视真实样本扩展“公告/公报类”“命令令类”“议案类”，但不应第一阶段铺满。

### 3.4 视觉与合规验证仍偏轻

当前测试主要验证：

- 15 个 profile 存在。
- contract 与 schema / placeholder 对齐。
- DOCX 占位符能替换。
- pipeline 能记录证据。
- 缺字段能阻断。

还缺：

- 公文 DOCX 渲染截图基线。
- 页边距、字号、红头线、版记表格等可视检查。
- 占位符说明页删除后的结构确认。
- 不同文种样张的版式差异截图。
- Word 字段、页眉页脚、批注、关系包等对象预检和装配后的保留验证。

所以现阶段不能把它描述为“GB/T 9704 全合规生成器”，只能描述为“GB/T 风格公文母版壳 + 可审计装配链路”。

### 3.5 交付版本还没完全落地

方案层有 `formal`、`internal_review`；contract 层有 `official_docx`、`review_pdf`、`archive_manifest`。

但当前明确生成的是 `official_docx`。后续需要补：

- 正式 Word：去除内部提示、保留正式字段。
- 内部审阅稿：带水印/提示/差异说明。
- 归档清单：记录文号、标题、签发、密级、保管期限、输出文件、资料包来源。
- 可选 PDF：作为审阅或归档预览，不宣称替代正式盖章版。

### 3.6 边界文案需要保持克制

公文涉及真实签发、盖章、归档审批和行政效力。系统最多能做：

- 格式装配。
- 字段填充。
- 占位符检查。
- 编号保留证据。
- 输出版本记录。
- 风险提示和人工确认。

不能做：

- 认证公文真实有效。
- 判断行政决定内容是否合法。
- 验证印章合法性。
- 替代办公室/档案室审批。

这些边界已经写在 schema、profile、master manifest 里，后续 UI 和报告要继续保留。

## 4. 推荐执行路线

### Phase 0：锁定当前合同

目标：把已经成立的链路固定住，避免后续 UI 改造丢功能。

验收点：

- `official` 工作模式仍能找到默认方案、默认模板、默认母版。
- 公文方案只列公文模板，不混入试卷/论文模板。
- 公文母版仍在 `config_library/masters/official/...`。
- 15 个文种 profile 不丢。
- `official_document_v1` 与 `administrative_meeting_fields_v1` 不丢字段。
- 现有装配测试继续通过。

建议测试：

```text
test_official_mode_keeps_plan_template_master_isolated
test_official_profiles_keep_15_document_types
test_official_contracts_bind_schema_fields_to_master_placeholders
test_official_assembly_runtime_records_output_and_report_evidence
```

### Phase 1：把公文装配入口并入“方案预览”

目标：不另开页面，把当前 `MastersPanel` 的公文动作迁回方案配置主链路。

推荐 UI：

```text
方案预览
  当前方案：公文-默认
  文种：通知 / 请示 / 报告 / 批复 / 函 / 纪要 / ...
  母版族：通用发文 / 函件 / 纪要
  格式模板：GB/T 9704 / 自定义公文模板
  资料状态：必填字段 5 项，已填 N 项
  操作：套用示例资料 / 打开母版 / 生成样张 / 预检
```

这一阶段先不追求所有文种差异，只要把“文种选择 -> contract -> schema -> 母版 -> 样张”串起来。

### Phase 2：做“资料包填充”

目标：让公文资料从隐式 `entity_data` 变成用户可见、可校验、可复用的数据包。

最小字段：

- 文种
- 标题
- 正文
- 发文机关
- 发文字号
- 主送机关
- 成文日期
- 附件说明
- 署名机关
- 抄送范围
- 印发机关
- 印发日期

纪要扩展：

- 会议标题
- 会议时间
- 参会人员
- 议定事项 / 正文

交互要求：

- 必填字段缺失时在执行前提示。
- 字段变化后能刷新占位符映射预览。
- 支持“套用示例资料”，但必须标记为示例。
- 支持保存到当前 mode 的资料上下文，不污染其他模式。

### Phase 3：扩展 2-3 个公文母版族

目标：用少量母版族覆盖主要差异，而不是做 15 份种子。

推荐新增：

```text
official_gbt_standard        通用发文
official_letter_standard     函件
official_minutes_standard    纪要 / 会议材料
```

每个母版都需要：

- `.docx`
- `.master.json`
- placeholder contract
- supported assembly types
- preflight 测试
- 样张生成测试
- 视觉验证输出

### Phase 4：工作台执行显式化

目标：用户在快速执行页能清楚知道当前使用的是哪个公文方案、文种、母版、资料包。

要求：

- “方案与模板”里的“场景”口径继续改为“方案”。
- 公文版执行前展示：当前方案、文种、母版、资料包字段完成度。
- 只有资料字段有信号时才运行装配；若用户选择公文版但没填资料，应提示去“资料包填充”。
- pipeline 不要默默根据空字段生成默认通知。

### Phase 5：交付版本与报告补齐

目标：把 contract 里的交付版本从规划变成真实产物。

交付建议：

- `official_docx`：正式 Word。
- `internal_review_docx`：内部审阅 Word，可带状态提示或水印。
- `archive_manifest`：归档 JSON/MD 清单。
- `review_pdf`：可选，只有渲染环境可用时生成。

报告必须记录：

- 文种 profile。
- 母版 id / version。
- 资料包 schema。
- 缺失字段。
- 替换占位符。
- 未解析占位符。
- 输出文件路径。
- 人工确认边界。

### Phase 6：视觉验收

目标：让公文版从“能生成 DOCX”升级为“能看图验收”。

建议验收样本：

- 通知样张。
- 函样张。
- 纪要样张。

每个样本至少检查：

- DOCX 可打开。
- 占位符说明页已删除。
- 必填占位符全部替换。
- PNG/PDF 渲染非空。
- 红头、标题、正文、署名、日期、版记区域没有明显错位。

## 5. 公文版验收清单

```text
[ ] 公文版切换后，只出现 official 方案、模板、母版
[ ] 方案预览中能选择文种
[ ] 方案预览中能看到当前母版族和模板
[ ] 资料包填充能编辑 official_document_v1 字段
[ ] 纪要能额外编辑 administrative_meeting_fields_v1 字段
[ ] 缺必填字段时执行前拦截或警告
[ ] 通知样张能生成 DOCX
[ ] 纪要样张能生成 DOCX 并替换会议字段
[ ] 执行报告写入公文母版装配证据
[ ] 编号保留证据仍能写入报告
[ ] 输出文件路径记录为 official_docx
[ ] 公文版不污染试卷/论文/标书模板列表
[ ] UI 文案不再把用户对象叫“场景”，统一叫“方案”
[ ] 边界文案不宣称签发、盖章、归档审批有效
```

## 6. 不建议做的事

- 不建议把 15 个文种立刻做成 15 个顶层场景。
- 不建议把 15 个文种立刻做成 15 份 DOCX 种子。
- 不建议把模板和母版混成一个对象；模板负责格式规则，母版负责可装配版面壳。
- 不建议第一阶段就迁移或删除旧 `scenes/`、`templates/` 目录。
- 不建议把公文装配做成静默自动触发；应由方案预览/资料包填充显式给出文种和资料信号。
- 不建议在没有视觉验证前宣传为完整 GB/T 合规。

## 7. 文档视角补充

此前 `高层场景能力矩阵N2_372...` 已记录公文会议元数据和正式/内部/归档报告闭环，但它更偏场景矩阵成熟度，不够贴近当前“工作模式 + 方案 + 模板 + 母版 + 资料包”的新架构。

此次补充后的关键视角是：

- 公文版已经是工作模式，不是普通场景卡片。
- 用户侧对象应叫“方案”，内部 `SceneWorkspace` 保持兼容。
- 公文复杂度由“文种 profile + 母版族 + 资料包 schema + 交付版本”承载。
- 资料包填充是公文链路成败的核心，不是附属功能。
- 当前只有通用公文母版，下一步应扩 2-3 个母版族，而不是直接扩 15 个文件种子。
- 公文版已经有 mode-scoped 存储基础，下一步风险主要是 UI/执行链路改造时丢失现有 contract 和报告证据。

## 8. 再审阅：公文版在新架构下的正确落点

本轮根据“标题栏负责工作模式，原场景改为方案”的新口径，重新审阅公文版。结论是：公文不应该被做成一堆顶层场景，也不应该先铺满 15 份文件种子；它应当落在“公文版工作模式”之下，用方案、文种 profile、母版族、资料包 schema 共同承载复杂度。

### 8.1 对象分层

```text
公文版
  -> 工作模式，决定只显示公文方案、公文模板、公文母版、公文资料 schema

公文-默认方案 / 函件方案 / 纪要方案
  -> 方案，决定长期处理规则、默认文种、默认母版族、交付版本、编号策略和资料要求

通知 / 请示 / 报告 / 批复 / 函 / 纪要 ...
  -> 文种 profile，决定字段契约、默认提示词、必填字段和可用占位符

GB/T 9704 公文格式
  -> 模板，决定格式参数，例如页边距、字体、标题、正文、版记等

通用发文母版 / 函件母版 / 纪要母版
  -> 母版族，决定 DOCX shell、placeholder contract、preflight 和可装配版面

official_document_v1 / administrative_meeting_fields_v1
  -> 资料包 schema，决定本次输入数据结构
```

这里最重要的是：文种不是工作模式，母版不是模板，资料包也不是方案。它们可以互相绑定，但不能被合并成一个大对象。

### 8.2 方案预览里的选框应该如何对应

公文版的“方案与模板”或“方案预览”里，如果显示“方案”选框，它必须列出内置/用户方案：

```text
公文-默认方案
函件方案
纪要方案
```

而不是列出母版，也不是只显示一个从其他页面来的单项。

同一区域如果还需要选母版，应该另起明确字段：

```text
方案：公文-默认方案
文种：通知
使用母版：GB/T 9704 通用公文母版
格式模板：GB/T 9704 公文格式
资料包：official_document_v1，必填 5 项，已填 N 项
```

这样用户才能理解：

- 换方案 = 换长期业务策略。
- 换文种 = 换字段契约和生成语气。
- 换母版 = 换 DOCX 可装配版面壳。
- 换模板 = 换格式规则基线。
- 换资料包 = 换本次或本类任务的数据。

### 8.3 当前不能贸然宣称完成的点

虽然底层已有 `official_document_profiles`、`official_document_assembly`、`official_gbt_standard` 和资料 schema，但产品主链路还没有完全闭合：

- 方案预览中的公文入口还没有正式验收。
- 资料包填充还没有成为用户可编辑的主入口。
- `MastersPanel` 中已有动作更像能力验证页，不应作为最终产品入口。
- 当前内置母版仍只有 `official_gbt_standard`，还不能覆盖函件、纪要等明显不同版面族。
- 视觉验收仍不足，不能宣传为完整 GB/T 合规生成器。

所以当前更准确的状态应写成：

```text
已有：公文资料 schema、文种 profile、通用公文母版、装配 runtime、报告证据基础。
未闭合：公文方案预览入口、资料包填充 UI、2-3 个母版族、交付版本产物、视觉验收。
```

### 8.4 为什么不能直接做 15 个文件种子

15 个文种如果第一阶段都做成独立 DOCX，会带来几个问题：

- 大量重复版头、正文、版记和占位符，维护成本会爆炸。
- 真实差异常常不是版面壳，而是字段、语气、审批/签发边界和资料要求。
- 后续一旦 GB/T 格式细节调整，需要同时改很多 DOCX。
- 用户会以为选文种就是选母版，反而更难理解方案、模板、资料包之间的边界。

更稳的路线是先做 2-3 个母版族：

```text
official_gbt_standard      通用发文母版
official_letter_standard   函件母版
official_minutes_standard  纪要 / 会议材料母版
```

文种 profile 负责细化差异，母版族只承载真正有版面结构差异的部分。

### 8.5 下一步执行前置条件

真正动手改公文主链路前，建议先满足这些条件：

```text
[ ] 方案 selector 已确认同一来源：PlanSelectorModel(mode_id="official")
[ ] 公文版快速执行页和方案配置页看到同一批公文方案
[ ] 方案预览明确区分“当前方案”和“使用母版”
[ ] 资料包填充能读写 MaterialExecutionContext.entity_data
[ ] 文种 profile 能驱动必填字段、schema 和占位符说明
[ ] 通知样张、纪要样张至少各有一条可生成路径
[ ] 生成失败时报告缺字段，而不是静默回退默认通知
[ ] 公文输出报告继续记录 profile、master、schema、replaced placeholders、missing fields
[ ] 试卷版已有链路不因公文入口改造而退化
```

执行顺序建议为：

1. 先补“方案预览”的公文只读信息和 selector 对齐。
2. 再补“资料包填充”的字段表单与必填校验。
3. 再把样张生成动作接入当前资料包。
4. 最后扩 2-3 个母版族并做视觉验收。

这样可以避免一开始就陷入“15 个文种都要做文件种子”的重工程，也能保护试卷链路不被公文复杂度拖乱。

## 11. 再审阅：公文版在“工作模式 / 方案 / 文种 / 母版 / 模板”五层中的位置

本轮继续复核用户提出的核心问题：国标公文有十几种文种，如果照试卷一样简单做一个“场景”肯定不够；但如果把每个文种都做成独立工作模式或独立文件种子，又会过早把系统复杂度打爆。

### 11.1 最终分层

公文版应按五层处理：

```text
工作模式
  -> 公文版

方案
  -> 公文-默认方案
  -> 函件方案
  -> 纪要方案
  -> 后续可扩：请示报告方案、批复方案、通知通报方案

文种 profile
  -> 通知、通报、报告、请示、批复、意见、函、纪要、决定、命令、公报、公告、通告、议案、决议
  -> 决定字段契约、默认称谓、正文结构、版记字段、资料必填项

母版
  -> GB/T 9704 通用公文母版
  -> 函件母版
  -> 纪要母版
  -> 后续再视稳定差异增加

模板
  -> GB/T 9704 公文格式
  -> 公文自定义格式
  -> 决定页面、字体、行距、标题、版记等格式参数
```

其中“文种 profile”是公文版特有的一层。它不是工作模式，也不一定是方案，更不一定是母版 DOCX。

### 11.2 为什么不能直接做十几个公文文件种子

不建议第一阶段做 15 个 DOCX 母版种子，原因如下：

- GB/T 9704 的大部分版式规则是共用的。
- 很多文种差异更多体现在字段、语气、正文结构和资料契约，而不是 DOCX shell。
- 过早做 15 个母版会让维护面膨胀：每次修页边距、版记、字体、占位符都要同步 15 份。
- 用户选择时也会困惑：到底是在选文种、选方案、选母版，还是选模板。

更合理的增量方式：

```text
第 1 阶段
  一个通用公文母版
  多个文种 profile
  一个公文默认方案
  资料字段填充 + 样张生成

第 2 阶段
  增加 2-3 个高频方案
  函件方案
  纪要方案
  通知/报告仍可先走通用方案

第 3 阶段
  只有当版式外壳真的稳定不同，才增加独立母版
  official_letter_standard
  official_minutes_standard
```

### 11.3 公文方案里选框应该怎么对应

公文版里最容易错的是“方案与模板”选框。

正确结构：

```text
快速执行 / 方案配置
  方案：公文-默认方案 / 函件方案 / 纪要方案
  模板：GB/T 9704 公文格式 / 公文自定义格式

方案预览
  文种：通知 / 报告 / 函 / 纪要 ...
  使用母版：GB/T 9704 通用公文母版
  使用模板：GB/T 9704 公文格式
  资料状态：缺字段 / 必填字段已齐
```

如果某个下拉显示 `公文-默认`，它应该是方案；如果显示 `GB/T 9704 通用公文母版`，它应该是母版；如果显示 `GB/T 9704 公文格式`，它应该是模板。三者不能用同一组数据源。

### 11.4 当前状态与问题判断

当前代码已有的方向：

- 公文版方案位于 `config_library/plans/official/builtin/official.json`。
- 公文版模板位于 `config_library/templates/official/builtin/official_gbt.json` 等。
- 公文版母版位于 `config_library/masters/official/builtin/official_gbt_standard.*`。
- 方案预览里公文母版使用 `master_selector_options("official")`，不会混入试卷母版。
- 资料包填充已能写入 `MaterialExecutionContext.entity_data`。

当前仍不完整的地方：

- 公文版方案库目前只有 `official.json`，所以方案下拉只有一个“公文-默认方案”是合理现状，但不代表文种不完整。
- 方案预览里有文种下拉，但它还没有和多个内置方案形成强绑定。
- 执行前 readiness 已有最小投影：快速执行页能显示方案、文种、母版、模板和资料字段完成度，但还没有扩展为独立 readiness 面板。
- 函件、纪要还没有独立母版族，只能通过通用公文母版生成样张。

### 11.5 公文版下一步不要做什么

短期不建议：

- 不把 15 个文种做成 15 个工作模式。
- 不把 15 个文种一次性做成 15 个 DOCX 母版。
- 不把文种下拉和方案下拉合并。
- 不把模板当母版使用。
- 不在资料包填充里修改方案 JSON 或模板 JSON。

这些都会破坏已经建立起来的边界。

### 11.6 公文版下一步该做什么

下一步应优先补“执行前 readiness”，因为它能把五层关系真正落到用户心智里：

```text
执行前检查
  当前工作模式：公文版
  当前方案：公文-默认方案
  当前文种：通知
  当前母版：GB/T 9704 通用公文母版
  当前模板：GB/T 9704 公文格式
  资料字段：标题、正文、发文机关、发文字号、成文日期已齐
  风险：无 / 缺字段 / 母版缺占位符 / 模板不属于当前模式
```

随后再补两个高价值内置方案：

```text
函件方案
  默认文种：函
  默认母版：先用 GB/T 9704 通用公文母版
  资料字段：标题、正文、发文机关、成文日期、主送机关

纪要方案
  默认文种：纪要
  默认母版：先用 GB/T 9704 通用公文母版
  资料字段：标题、正文、会议时间、参会人员、发文机关、成文日期
```

最后再根据样张验收结果决定是否做：

```text
official_letter_standard.docx
official_minutes_standard.docx
```

### 11.7 公文版验收口径更新

后续公文版每轮执行都按以下口径判断：

```text
[ ] 顶部只选择公文版，不选择具体文种
[ ] 方案下拉只来自 config_library/plans/official
[ ] 模板下拉只来自 config_library/templates/official
[ ] 母版下拉只来自 config_library/masters/official
[ ] 文种下拉只来自 official document profiles
[ ] 文种 profile 决定字段契约，不直接等同于母版
[ ] 资料包填充写 MaterialExecutionContext，不写方案或模板
[x] 执行前 readiness 能展示方案、文种、母版、模板、资料字段完成度
[x] 缺必填字段时阻断或强提示
[ ] 只有高频且版式差异稳定的文种才升级为独立方案或独立母版
```

### 11.8 本轮公文裁决

公文确实比试卷复杂，但复杂度不应该全部堆到“文件种子”上。正确的复杂度承载方式是：

```text
文种多
  -> profile 多

工作流多
  -> 方案多

版式外壳稳定不同
  -> 母版多

格式规则不同
  -> 模板多

每次内容不同
  -> 资料包多
```

这套分层能让公文继续扩展，同时不破坏试卷版已经跑通的链路。

## 12. 执行记录：快速执行页公文 readiness 最小闭环

本轮执行第 11.6 节的第一步，把公文版 readiness 接入快速执行页。实现范围保持克制：不新增独立页面，不改变执行器，不扩母版族，只把执行前用户最需要确认的五层关系投影出来。

已落地内容：

```text
快速执行
  -> 公文资料与装配
    -> 方案
    -> 文种
    -> 母版 / 模板
```

## 13. 再审阅：公文版不要把复杂度压成文件种子

本轮只记录分析，不继续执行公文代码改造。重新审阅后，公文版的关键风险不是“国标文种很多，所以文件种子不够”，而是几类对象容易混用：

```text
工作模式：公文版
方案：公文-默认方案 / 函件方案 / 纪要方案
文种 profile：通知 / 请示 / 报告 / 批复 / 函 / 纪要
母版：GB/T 9704 通用公文母版 / 后续函件母版 / 后续纪要母版
模板：GB/T 9704 公文格式 / 公文自定义格式
资料包：标题、正文、发文机关、发文字号、成文日期、主送机关等
```

文种多，并不等于母版文件必须多。更合理的承载是：

```text
文种差异
  -> official document profile
  -> 字段契约、默认称谓、装配规则

工作流差异
  -> 方案
  -> 默认文种、默认母版、默认模板、交付版本

版式外壳稳定差异
  -> 母版
  -> docx shell + placeholder manifest

格式规则差异
  -> 模板
  -> 页边距、字体、标题、页眉页脚等格式参数
```

### 13.1 当前公文链路的实际状态

当前主路径已经有：

```text
config_library/plans/official/builtin/official.json
config_library/templates/official/builtin/official_gbt.json
config_library/templates/official/builtin/official_custom.json
config_library/masters/official/builtin/official_gbt_standard.docx
config_library/masters/official/builtin/official_gbt_standard.master.json
```

这说明公文版已经有独立的方案 / 模板 / 母版文件夹。但方案库只有一个 `official.json`，所以所有方案选择框里只有“公文-默认方案”是当前正常结果，不是文种缺失。

真正缺的是：

```text
公文方案还不能声明“默认文种 profile”
  -> 方案预览可能默认 notice
  -> 快速执行 readiness 也可能默认 notice

公文方案还没有高频方案分支
  -> 函件方案 / 纪要方案尚未落库

公文母版族还只有通用 GB/T 9704
  -> 函件 / 纪要可先复用通用母版
  -> 等视觉样张稳定后再升级独立母版
```

### 13.2 公文下拉应该如何各归其位

公文版里每个下拉的数据源应固定如下：

```text
顶部工作模式
  数据源：WorkModeSpec
  示例：公文版

方案下拉
  数据源：config_library/plans/official
  示例：公文-默认方案、函件方案、纪要方案

文种下拉
  数据源：official document profiles
  示例：通知、报告、函、纪要

母版下拉
  数据源：config_library/masters/official
  示例：GB/T 9704 通用公文母版

模板下拉
  数据源：config_library/templates/official
  示例：GB/T 9704 公文格式、公文自定义格式
```

如果“方案与模板”区域中左侧选框显示 `公文-默认`，它是方案；右侧显示 `GB/T 9704 公文格式`，它是模板。这里不应该出现母版。母版应出现在“方案预览”或专门的“使用母版”区域。

### 13.3 方案默认文种是当前最大缺口

公文方案要想真正独立，不能只靠 `scene_id=official`。它需要能表达：

```text
公文-默认方案
  default_profile: notice
  default_master: official_gbt_standard
  default_template: official_gbt

函件方案
  default_profile: letter
  default_master: official_gbt_standard
  default_template: official_gbt

纪要方案
  default_profile: minutes
  default_master: official_gbt_standard
  default_template: official_gbt
```

这里的 `default_profile` 不应临时塞进 `MaterialExecutionContext`，因为资料包是本次任务数据，不是长期方案配置。更稳的做法是给 `SceneWorkspace` 增加一个小而通用的方案级字段，例如：

```text
default_material_profile_id: "official:letter"
```

或放入一个更明确的方案级对象：

```text
material_profile:
  default_profile_id: "official:letter"
```

这个字段的用途是“方案默认文种 / 默认资料契约”，不是保存本次资料内容。

### 13.4 不建议的实现路径

短期不要做：

```text

把 15 个文种一次性做成 15 份 DOCX 母版

把文种 profile 存进资料包作为唯一长期来源
```

```text

   - 后续 official_minutes.json 默认 minutes

3. 再新增两个高频内置方案
   - 函件方案
   - 纪要方案

   - official_letter_standard
   - official_minutes_standard

   - 正式稿
   - 内部审阅稿
   - 归档清单 / 资料清单
```

### 13.7 本轮裁决

## 14. 再审：为什么公文方案选框和预览仍然对不上

### 14.1 每个选框到底应该选什么

公文版正确的选框归属应固定为：


### 14.2 当前实际状态

当前文件层有：

```text
config_library/plans/official/builtin/official.json
config_library/plans/official/builtin/official_letter.json
config_library/plans/official/builtin/official_minutes.json

config_library/templates/official/builtin/official_custom.json
```

这个方向是对的。问题在于：

```text

official_minutes.json 里写了 default_material_profile_id = official:minutes

但 load_scene_from_library() 后：
```

根因是 `normalize_scene_payload()` 的 `_SCENE_META_KEYS` 没包含 `default_material_profile_id`。所以 UI 读当前方案时拿不到默认文种，只能按 fallback 走 `notice`。

### 14.3 为什么“方案预览”和“资料包填充”会不同步

当前理想链路应该是：

```text
用户选择：函件方案
  -> load SceneWorkspace(official_letter)
  -> default_material_profile_id = official:letter
  -> 方案预览文种 = 函
  -> 资料包填充默认 profile = 函
  -> 快速执行 readiness 文种 = 函
  -> 缺字段按函件字段检查
```

现在实际链路是：

```text
用户选择：函件方案
  -> load SceneWorkspace(official_letter)
  -> default_material_profile_id 被 migration 丢掉
  -> 方案预览找不到方案默认文种
  -> 资料包填充找不到方案默认文种
  -> readiness 找不到方案默认文种
  -> fallback = notice
```

所以两处内容“明明没对应上”的真实原因，不是 selector 控件没刷新，而是共同数据源被清空了。

### 14.4 内置方案排序也要一起修

当前 `list_scene_descriptors(mode_id="official")` 实际返回：

```text

official_minutes

```

这不符合产品心智。默认方案应该在最前，后面是更细的高频方案。原因是内置排序只来自 `SCENE_METAS`，新增的 `official_letter`、`official_minutes` 不在该顺序表里，于是被当成未知项排到了前面。

正确顺序：

```text
公文-默认
函件方案
纪要方案
```

这一步不应该通过改文件名、加前缀或把方案硬编码进 UI 解决，而应该在配置库排序规则里声明“公文版内置方案补充顺序”。

### 14.5 公文文种不应该扩成十五个工作模式

用户担心国标公文类型很多，这个担心是对的，但解决方式不是一次性造 15 个顶层入口。更稳的是三层递进：

```text

  当前先复用 official_gbt_standard
```

这样可以避免“十几个文件种子”把产品变复杂，也避免模板、母版、文种三者混用。

## 24. 执行记录：公文资料表批量导入与一行一输出

第 23 节已经把单份导入与批量执行明确分开。本轮沿用该边界实现批量最小闭环，没有把多行表格塞回单份 `MaterialExecutionContext`。

### 24.1 复用审阅结论

项目原有通用批量能力包括：

```text

WorkbenchBatchProductionRunner
逐档案失败隔离
JSON / Markdown 批量报告
```

但原链路围绕“同一份源 DOCX + 多个实体档案”设计，并且前台“批量生成”只跳转到工作台；工作台执行按钮仍固定进入单份执行，`_start_batch_execution()` 没有真实入口。

公文资料表不能直接套用这个假设：每一行资料本身决定标题、正文和文种，公文装配也不应要求一份无关 DOCX 充当种子。因此本轮只复用通用批次的选择对象、失败隔离投影和汇总报告，不复用“必须先选择源 DOCX”的执行前提。

### 24.2 批次身份契约

新增：

```text
load_official_document_material_batch(path, fallback_profile_id=...)
```

当前批量入口接受横向 CSV / XLSX / XLSM；每一行转成独立任务。身份分为两层：

```text
item_id / EntityProfile.profile_id
  -> 批次任务身份
  -> 来自 task_id / record_id / 资料编号，缺失时使用 row_0001
  -> 重复值自动形成 _2 / _3，保证本批次唯一

entity_data.document_type
  -> 公文文种身份
  -> notice / letter / minutes / 其他注册文种
  -> 不会被 item_id 覆盖
```

这避免再次出现“来源 ID、显示 ID、业务类型 ID 被压成同一个字符串”的问题。

`MaterialBatchSelection` 只增加运行时证据：

```text
source_kind = official_document_table
source_path = 原始资料表
item_metadata[item_id] = 行号、文种、导入状态、缺失字段、未知字段、问题
```


不再要求源 DOCX。每行使用独立输出目录，目录名前缀包含唯一 `item_id`；同名标题不会互相覆盖。

执行状态：

```text

至少一行成功、一行失败 -> partial_success
全部失败              -> failed
用户中止              -> cancelled
```

缺必填字段、未知文种、未解析占位符或单行异常只记录到该行，不阻断其余行。成功行会产生正式 DOCX、内部审阅稿和归档清单；审阅 PDF 继续服从当前方案的可选 `review_pdf` 配置。

## 26. 国标合规复核纠偏：PNG 稳定不等于 GB/T 合规

2026-07-10 使用“请示 / 批复”两份正式装配样张，重新按 GB/T 9704—2012 做了 Word 有效格式、OOXML 结构和最终渲染的逐项复核。结论是：

```text
当前 A4、页边距、正文 3 号仿宋和正文首行缩进基本正确；
但版头位置和顺序、上行文签发人、标题字体、附件间距、署名用印、版记和页码存在实质性不符合项。
```

因此第 21 节的：

```text
visual_baseline_ok
shared_master_accepted
```

只能继续解释为“当前页壳在固定渲染环境中可以稳定复现、多个 profile 当前共享同一页壳”，不能解释为“该页壳符合 GB/T 9704”或“一个母版可以合规覆盖所有文种”。现有 PNG 基准在新合规母版建立前属于历史稳定性参考。

整改正式拆为两条建设线：

1. 模板 / 母版线：重建普通行文、上行文、信函、命令、纪要等结构族。
2. 方案 / 系统线：补齐文种方向、签发人和用印条件、母版解析、合规预检和正式稿发布门禁。

完整证据、目标合同、阶段计划和验收清单见：
