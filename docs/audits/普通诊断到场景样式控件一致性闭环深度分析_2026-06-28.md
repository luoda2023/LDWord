# 普通诊断到场景样式控件一致性闭环深度分析

日期：2026-06-28

## 1. 本轮继续分析的核心问题

上一轮已经把场景页的“处理范围”和“样式覆盖”拆开，并让模板正文排版与场景分区样式复用同一个 `ParagraphStyleEditor`。但这还不能称为优秀设计，因为用户并不是从控件源码进入系统，而是从“执行后发现问题”进入系统。

本轮发现的关键断点是：批量执行诊断已经可以生成 `WorkbenchIssueItem`，并从工作台跳到场景字段；普通执行诊断却只保留 `diagnostics_count` 和 `diagnostics_summary`，没有保留 `diagnostics.items`。这导致同样的场景样式问题，在批量路径里是可点击、可定位、可修复的，在普通路径里却只是日志文字。

这类不一致会直接伤害可读性：

- 用户看到“诊断提示”却不知道该去哪里改。
- 工作台像在说内部术语，而不是给出下一步动作。
- 场景页虽然复用了模板控件，但普通诊断没有把用户带到那些控件。
- 设计表面一致，链路行为不一致。

因此，本轮重点不是继续堆页面文案，而是补齐“普通诊断 -> 工作台问题 -> 场景字段 -> 共享控件”的闭环。

## 2. 应保持的产品边界

### 2.1 模板管理是样式基准层

模板管理负责定义全局正文样式，例如字体、字号、缩进、行距、段前段后。它应该是“默认怎么排”的地方。

对应实现：

- `src/shared/ui/paragraph_style_editor.py`
- `src/ui/panels/template_style_detail.py`

模板管理里的正文排版控件不应该只存在于模板页内部。它已经抽成共享编辑器，场景页只要表达同类段落样式，就应复用同一套控件、字段归一化和导航高亮。

### 2.2 场景管理是范围与覆盖层

场景页不应该重新定义一套“模板样式管理”。它只回答两个问题：

- 本场景处理哪些文档分区。
- 哪些分区要偏离模板默认样式。

因此，场景页里的样式控件必须有清晰前提：先选处理范围，再决定该分区是否覆盖模板样式。没有覆盖时，用户应该看到“跟随模板”，而不是看到一堆像模板管理一样的重复设置。

对应实现：

- `src/ui/panels/scene_panel.py`
- `_ScopeDetail` 中拆分为“处理范围”和“样式覆盖”
- `scene.section_styles.*` 通过 `ParagraphStyleEditor` 复用模板正文排版控件

### 2.3 工作台是问题入口层

工作台不应该重新解释样式规则，也不应该把内部诊断名堆给用户。它的职责是把运行时问题转换成可操作 Issue，然后把用户送到真正的设置位置。

这意味着：

- 工作台保留诊断证据，例如 `parameter_path`。
- 工作台生成用户能理解的 Issue，例如“场景样式需要确认”“场景处理范围需要确认”。
- 工作台不直接编辑场景样式，只发出导航 intent。
- 场景页接收 intent 后定位到共享控件。

对应实现：

- `src/ui/adapters/workbench_execution_adapter.py`
- `src/ui/panels/workbench/execution_runtime.py`
- `src/ui/panels/workbench/execution_worker.py`
- `src/ui/panels/workbench/execution_controller.py`
- `src/ui/panels/workbench/panel_v2.py`

## 3. 本轮补齐的链路

### 3.1 旧链路的问题

普通执行结果原来大致是：

```text
PipelineResult
  -> build_execution_diagnostics(result)
  -> diagnostics_count / diagnostics_summary
  -> Workbench 日志文本
```

如果诊断里包含场景字段路径，例如：

```text
scene.section_styles.references_body.font_cn
scene.section_styles.*.line_spacing_pt
scene.format_scope.sections.references
```

这些路径不会进入工作台 Issue 队列，也就不会跳转到场景页。

### 3.2 新链路

本轮补齐后，普通执行结果变为：

```text
PipelineResult
  -> build_execution_diagnostics(result)
  -> diagnostics_items
  -> execution_diagnostic_issue_items(...)
  -> WorkbenchIssueItem
  -> workbench_issue_action_target(...)
  -> ScenePanel.handle_navigation_intent(...)
  -> _ScopeDetail.focus_navigation_field(...)
  -> ParagraphStyleEditor.focus_field(...)
```

其中字段类型归一化为：

```text
scene.format_scope.sections.references
  -> scene_scope_field
  -> format_scope.sections.references

scene.section_styles.references_body.font_cn
  -> scene_style_field
  -> scene.section_styles.references_body.font_cn

scene.section_styles.*.line_spacing_pt
  -> scene_style_field
  -> scene.section_styles.*.line_spacing_pt
```

这让普通执行和批量执行在用户体验上保持一致：只要诊断有场景字段路径，用户就能从问题进入对应控件。

## 4. 本轮代码调整

### 4.1 新增普通诊断 Issue 转换

文件：`src/ui/adapters/workbench_execution_adapter.py`

新增：

```python
execution_diagnostic_issue_items(...)
```

它只转换可定位到场景字段的诊断：

- `scene_scope_field` 生成“场景处理范围需要确认”。
- `scene_style_field` 生成“场景样式需要确认”。
- 没有字段路径的普通诊断不强行生成 Issue，仍保留在摘要日志。

这样可以减少冗余文本和无效入口，避免“每一条日志都变成一个看似可修复的问题”。

### 4.2 保留普通诊断明细

文件：

- `src/ui/panels/workbench/execution_runtime.py`
- `src/ui/panels/workbench/panel.py`

普通运行路径现在会把 `diagnostics.items` 放进：

```text
diagnostics_items
```

失败、成功、多交付目标、材料预检失败路径都保留这份结构化明细。

### 4.3 Worker 透传结构化诊断

文件：`src/ui/panels/workbench/execution_worker.py`

Worker 现在会从以下位置读取诊断明细：

- `diagnostics_items`
- `diagnostics.items`
- 普通非批量结果里的 `material_diagnostics`

同时避免批量结果重复生成普通诊断 Issue：如果 payload 已经有 `batch_issue_items`，就不再把 `material_diagnostics` 作为普通诊断透传。

### 4.4 Controller 接入统一入口

文件：

- `src/ui/panels/workbench/execution_controller.py`
- `src/ui/panels/workbench/panel.py`

工作台 Controller 在构建 `ExecutionResultState` 时传入 `diagnostics_items`，由 adapter 统一转换成 Issue。

## 5. 对样式、控件规划的一致性影响

### 5.1 一致性从“控件长得像”提升为“路径行为一致”

本轮之前，场景页和模板页已经共用了控件，但普通诊断不会带用户进入控件。用户仍然会觉得系统“不说人话”，因为看到的是结果日志，不是下一步动作。

本轮之后，一致性变成三层：

```text
字段契约一致
  template.styles.body.* / scene.section_styles.*.*

控件实现一致
  ParagraphStyleEditor

问题入口一致
  WorkbenchIssueItem -> scene_scope_field / scene_style_field
```

这比单纯统一 UI 样式更重要，因为它保证了用户无论从模板页、场景页、批量执行还是普通执行进入，最终面对的是同一套设置语言。

### 5.2 可读性从“解释规则”转向“给出动作”

普通诊断 Issue 不直接展示内部 rule 名作为标题，而使用：

- 场景样式需要确认
- 场景处理范围需要确认

内部信息放到详情里作为证据：

- 规则
- 类型
- 对象
- 分区
- 参数路径

这比把 `preflight_scene_style`、`section_styles.references_body.font_cn` 直接放在主视觉区域更适合普通用户。

### 5.3 冗余文本的删除方向

后续 UI 文案应该继续遵守这个原则：

- 主标题说用户动作。
- 辅助摘要说影响。
- 技术路径只放详情或 tooltip。
- 不在场景页重复解释模板页已经表达过的样式概念。
- 不把“规则名、字段名、配置层级”当作用户主文案。

## 6. 当前仍不够完善的地方

### 6.1 诊断源还不是全部带字段路径

`build_execution_diagnostics(result)` 当前主要从 tracker record 和 failed_items 中提取诊断。很多 record 只有 `rule_name`、`target`、`section`、`change_type`、`reason`，没有 `parameter_path`。

本轮只保证“只要有字段路径就能闭环”。下一步应推进诊断源本身补齐字段路径，让更多普通诊断可以定位到控件。

建议下一步：

- 为高频 preflight 记录补 `parameter_path`。
- 为样式类 tracker record 增加字段路径映射。
- 为无法定位的诊断明确标记为“仅报告”，避免用户误以为可以一键修复。

### 6.2 Issue 队列还缺少更好的分组展示

现在普通诊断已经可以进入 Issue 队列，但展示层仍可能把不同来源的问题混在一起。

建议后续把工作台 Issue 分为：

- 需要先处理：阻断执行或会导致输出失败。
- 建议确认：样式、范围、对象风险。
- 仅供查看：报告型诊断。

这会比单纯按技术 category 展示更符合用户认知。

### 6.3 场景样式覆盖还需要更强的“跟随模板”表达

当前已经拆出“样式覆盖”，但用户仍需要更清楚地知道：

- 当前分区是否跟随模板。
- 开启覆盖后哪些字段与模板不同。
- 一键恢复模板默认会影响哪些设置。

这部分应继续复用 `ParagraphStyleEditor`，但外层需要更明确的覆盖状态条，而不是把所有字段始终摊开。

### 6.4 模板预览与场景预览仍需统一渲染投影

模板管理的样式预览已经更像“最终排版效果”。场景侧如果只显示控件，不显示“该分区覆盖后实际是什么效果”，用户仍然难以判断改动是否正确。

建议抽一层共享预览投影：

```text
TemplateConfig + optional SceneSectionOverride
  -> ParagraphPreviewProjection
  -> Template preview / Scene override preview
```

这样模板页和场景页不仅控件一致，预览也一致。

## 8. 结论

本轮把一致性问题从“页面控件是否复用”继续推进到了“用户从执行问题进入时，是否仍然走同一套场景/模板字段语言”。

当前已经形成更完整的边界：

- 模板管理定义默认样式。
- 场景管理定义处理范围和必要覆盖。
- 共享控件承载同类段落样式编辑。
- 工作台只负责把诊断转成可操作入口。

后续最重要的工作不是继续加说明文字，而是继续减少用户看到内部术语的机会：让诊断源携带字段路径，让 Issue 队列按用户动作分组，让场景样式覆盖用“跟随模板/已覆盖/恢复默认”的状态语言组织界面。
