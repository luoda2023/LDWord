# 高层场景能力矩阵 V17 完备能力定义与高频边界验收规划（2026-06-18）

## 1. 本轮结论

当前问题不是“场景名字太少”，而是很多功能点还停在规划、摘要或局部 UI 层，尚未形成完整能力。高层场景能力矩阵要避免两类失败：

```text
遗漏：高频用户任务没有入口、没有 profile、没有 workflow，或者只在文档里出现。
混淆：模板外观、场景策略、素材事实源、输出版本、插件边界被塞进同一个场景开关。
```

因此，V17 把“完善”定义为：

```text
任意高频文档任务，都能被稳定归入正确层级，并说明它需要哪些事实源、工作流、Word/OOXML 风险策略、UI 控件契约、执行链、报告/问题/产物和测试证据。
```

新增代码化审计落点：

- `src/config/scene_coverage_manifest.py`
  - `SceneCompletenessGate`
  - `WorkflowArchetype`
  - `WordRiskSurface`
  - `audit_scene_pack_completeness()`
- `tests/test_scene_coverage_manifest.py`
  - 完备门槛、工作流原型、Word 风险面、关键边界测试

## 2. 完整能力的 9 个准入门槛

一个 coverage pack 只有同时回答 9 个问题，才可以称为“完整能力”；否则只能称为规划、可见配置或 first slice。

| 门槛 | 必须回答 | 证据面 |
| --- | --- | --- |
| 自然请求别名 | 用户会怎样自然提出这个任务 | coverage pack、导航或 planned family、文档 |
| 归属层级 | 属于 scene、template、material、output 还是 plugin | parameter ownership、control contract |
| 事实源 | 哪个输入是机器可信事实源 | input profile、material schema、delivery preset |
| 工作流槽位 | 需要哪些可复用工作流 | workflow registry、scene family、测试 |
| Word 风险面 | 触碰哪些 Word/OOXML 面 | object preflight、runtime、report |
| UI 控件契约 | 同名参数是否与模板管理同控件、同单位、同禁用规则 | control contract、ScenePanel、TemplatePanel |
| 执行链 | 是否真正经过 resolver、scheduler、pipeline、runner | provenance、runtime event |
| 报告/问题/产物 | 用户能否理解输出、风险、缺口和产物 | JSON/Markdown report、issue queue、artifact |
| 测试证据 | 是否有 registry/UI/runtime/report 的 first slice 测试 | pytest、trace token、closure task |

## 3. 三层防遗漏扫描

### 3.1 用户自然请求层

这层防止“用户高频说法”没有被场景体系吸收。

| 请求簇 | 应落点 | 不应做的事 |
| --- | --- | --- |
| 快速规范化 Word | `custom/report/technical/official` | 不为每种普通报告建顶层入口 |
| 中文论文/综述/开题 | `thesis` + `thesis_cn` profile | 不吸收英文期刊、试卷生成 |
| 英文期刊投稿 | `journal_en` planned family | 不承诺出版社最终版式或未审规则抓取 |
| 试卷/讲义/答案版 | `exam_teaching` planned family | 不让 AI 分别生成学生版和教师版 |
| 标书/资质/盖章材料 | `bidding` + 资质包 workflow | 不判断投标策略、证照真实性 |
| 公文/纪要/制度汇编 | `official` + 行政 profile | 不扩散成很多小顶层场景 |
| 技术长文档/手册/SOP | `technical` + 长文档 profile | 不替代出版系统 |
| 项目申报/白皮书/售前 | `report/project_application/product_sales_documents` | 不承诺营销文案质量 |
| 合同审阅/签署包 | `contract_delivery` planned family | 不提供法律意见 |
| HR/证书/固定表单批量 | `hr_batch_documents/form_batch_documents` | 不把固定版位行高塞回通用表格样式 |
| 财务/披露/IP/双语 | professional planned families + plugin boundary | 不做审计、法律、专利、翻译质量判断 |
| PDF/OCR/LaTeX/AI/复杂图形 | import/plugin/manual gate | 不承诺无损导入或内容正确性 |

### 3.2 工作流原型层

这层防止“场景名字有了，但横向能力漏了”。

| 工作流原型 | 高频来源 | 完整信号 |
| --- | --- | --- |
| 模板规范化 | 所有现有 Word | 有模板基线、范围、对象风险决策 |
| 范围定位 | 论文、公文、长文档、计数 | section/story/page 范围可解释 |
| 结构化输入 | 试卷、HR、表单、合同、申报 | JSON/XLSX/schema 是事实源 |
| 素材填充 | 标书、合同、申报、公文 | 缺字段、缺图、缺附件可进入 issue/report |
| 图片/签章/附件清单 | 标书、资质、试卷、技术文档 | asset role 和 manifest 完整 |
| 内容显隐/多版本 | 试卷、合同、披露、售前 | 同一事实源生成多版本 |
| 批量生成 | HR、表单、证书 | 一记录一产物、失败隔离 |
| 多口径计数 | 论文、期刊、申报、试卷 | CountProfile 多指标，不是单字数函数 |
| 引用/参考文献 | 学术、期刊、技术 | Bib/CSL、缺项、样式和边界明确 |
| 公式/符号 | 学术、技术、试卷 | LaTeX/OMML、低置信度、复杂图形边界 |
| 固定版位表格 | 表单、证书、报价、套打 | `w:trHeight`、内容控件、文本框单独治理 |
| 对象保护 | 外来模板、技术、财务、合同 | OLE/VBA/修订/批注 block/warn/skip |
| 审阅对比 | 合同、技术、投标修回 | compare docx、review copy、修订保护 |
| 提交归档 | 投稿、申报、标书、披露 | DeliveryPreset、manifest、zip、命名 |
| 插件/人工确认 | OCR、AI、法律、财务、IP、复杂图形 | 置信度、人工确认、边界报告 |

这层防止“业务规划完整，但实际 Word 结构被破坏”。

| 风险面 | 高频遗漏 | 必须策略 |

## 5. 从两份技术记录吸收的要点

### 5.1 计数引擎记录

需要吸收：

- CountEngine 必须是 profile-driven multi-metric；
- 中文论文、英文期刊、试卷、申报、披露不能共享一个“字数”口径；
- Word-like 统计和规则统计要并存；
- CountProfile 必须声明范围、排除项和解释口径；
- 报告要展示多指标，不只输出一个数字。

对应落点：

- `count_profile` capability axis；
- `count_compliance` workflow archetype；
- `chinese_academic`、`english_journal`、`application_reports`、`exam_education`、`professional_disclosure` 等 pack。

### 5.2 试卷生成技术栈记录

需要吸收：

- JSON 是机器事实源，Markdown 是人工预览，Word 是正式输出；
- AI 不应直接生成 Word；
- 学生版/教师版/答案版必须来自同一个结构化事实源；
- 答案、解析、分数、知识点必须保留在结构化数据中，由 delivery/visibility 决定是否显示；
- 复杂几何图和 AI 内容质量必须进入插件或人工确认边界。

对应落点：

- `input_fact_source`、`material_schema`、`content_visibility`、`delivery_preset`、`plugin_boundary`；
- `structured_input`、`content_visibility`、`formula_symbol`、`plugin_manual_gate`；
- `exam_education` pack 的边界测试。

## 6. 场景配置与模板管理控件一致性

必须遵守下面的裁决：

```text
外观基线属于 TemplateConfig；
场景只决定是否处理、处理范围、业务策略、风险策略、输出版本；
当场景确实需要 section override 时，必须复用模板管理同源控件和同单位规则。
```

当前已推进：

- `ScenePanel` 分区样式 override 已复用：
  - `FontCombo`
  - `SizeCombo`
  - `build_emphasis_widget`
  - `SpecialIndentInput`
  - `IndentInput`
  - `SpacingInput`
  - `LINE_SPACING_OPTIONS`
- 同排规则已覆盖：
  - 中文字体 / 字号；
  - 英文字体 / 字形；
  - 对齐 / 特殊缩进；
  - 左缩进 / 右缩进；
  - 行距类型 / 行距值；
  - 段前 / 段后。

仍需继续推进：

- 控件实例事件到 resolver provenance、runtime event 的端到端 trace；
- issue queue 打开具体源码行或 contract 编辑器；
- 固定版位行高 `w:trHeight` 已由 N2.97 建立专属 policy/helper first slice，后续要继续接 UI/profile/report 深链路；
- 工作流原型在 ScenePanel/Workbench 的可视化矩阵。

## 9. Phase N2.97 固定版位 `w:trHeight` 行高 policy/helper first slice（2026-06-18）

V17 的下一优先级是 `batch_forms` 固定版位能力。此前 `TableConfig.row_height_pt` 已经从通用表格模型退场，但 `fixed_layout.table_row_height` 仍主要停留在控制契约与 coverage 缺口里。本轮补上固定版位专属的 `w:trHeight` policy 和 OOXML helper，明确它不回流到模板管理普通表格样式。

已完成：

- 新增 `src/config/fixed_layout.py`：
  - `FixedLayoutRowHeightPolicy`；
  - `FIXED_LAYOUT_ROW_HEIGHT_POLICIES`；
  - `fixed_layout_row_height_policy_for_family()`；
  - `audit_fixed_layout_row_height_policies()`；
- `form_batch_documents` 默认行高策略为 `preserve_existing`：
  - 保留模板里已有 `w:trHeight`；
  - 不在普通 `TableConfig` 里暴露 `row_height_pt`；
  - 只有固定版位 profile 显式声明时才可 enforce；
- 新增 `src/shared/engine/fixed_layout_tables.py`：
  - `set_fixed_layout_row_height()`；
  - `clear_fixed_layout_row_height()`；
  - `row_height_state()`；
  - `apply_fixed_layout_row_height_policy()`；
  - 支持 `preserve_existing`、`enforce_exact`、`enforce_at_least`、`clear`；
- `form_batch_documents` planned family 新增 `row_height` OOXML touchpoint；
- 控制契约 `fixed_layout.table_row_height` 从 planned control 更新为 `FixedLayoutRowHeightPolicy + OOXML helper`；
- `batch_forms` coverage pack 将 `w:trHeight row-height execution policy` 移入 `implemented_closures`，剩余缺口保留为内容控件/文本框 runtime 与逐记录问题中心；
- 测试证明：
  - helper 可写入 `w:trHeight w:val=360 w:hRule=exact`；
  - preserve policy 不会改写已有行高；
  - `ResolvedConfig().table` 仍没有 `row_height_pt`；
  - fixed-layout policy registry 自检干净；
  - coverage missing closures 不再包含 `w:trHeight`。

对 V17 的意义：

```text
固定版位行高现在有了自己的承载层和 OOXML 执行入口。
它没有回到通用模板表格参数，也没有被伪装成普通表格样式；这正好符合“固定版位能力必须单独治理”的边界要求。
```

仍未闭合：

- `w:trHeight` policy 还没有进入 ScenePanel 可视化 profile 编辑；
- policy 执行结果还没有写入 Workbench/report 的专属摘要；
- `w:sdt` 内容控件、textbox/shape 映射 runtime、placeholder residue、per-record issue center 仍是 `batch_forms` 的后续缺口。

## 10. Phase N2.98 `w:sdt` / textbox 占位符替换与残留检测 first slice（2026-06-18）

N2.97 已经让固定版位行高 `w:trHeight` 有了专属 policy/helper。`batch_forms` 的下一条链路是内容控件、文本框和占位残留。此前 `entity_fill` 与 `placeholder_replace` 主要处理普通段落、页眉页脚段落；固定版位表单里常见的 `w:sdt` 和 textbox XML surface 仍容易漏替换、漏残留检查。本轮补一个窄但真实的 runtime first slice。

已完成：

- 新增 `src/shared/engine/fixed_layout_text.py`：
  - `replace_fixed_layout_placeholders()`；
  - `iter_fixed_layout_text_blocks()`；
  - 支持 `content_controls` 与 `textboxes` 两类 fixed-layout surface；
  - 使用 XML path 做稳定去重，避免 lxml 代理对象 id 复用导致漏处理；
- `entity_fill` 接入 fixed-layout surface：
  - 支持在 `w:sdt` / textbox 中替换 `{{key}}` 与 `${key}`；
  - 替换成功后同步写入 `context.entity_values`；
- `placeholder_replace` 接入 fixed-layout surface：
  - 用户自定义替换规则同样覆盖 `w:sdt` / textbox；
- `material_field_consistency` 接入 fixed-layout 文本抽取：
  - 合同字段一致性检查可以看到内容控件/textbox 中残留的 `{{field}}`；
- `batch_forms` coverage pack 将 `content control and textbox placeholder replacement runtime first slice` 移入 implemented closure；
- 剩余 closure 精确收窄为 `content control tag mapping and textbox anchored mapping runtime`。

对 V17 的意义：

```text
固定版位表单不再只靠普通 paragraph 替换。
内容控件和文本框中的基础占位符替换、残留扫描已经有同一条 runtime helper 链路，后续 tag mapping、anchored mapping 和批量问题中心可以沿这条链继续扩展。
```

仍未闭合：

- `w:sdt` 的 tag/alias 到 MaterialSchema 字段的映射；
- textbox/shape 的锚点、位置、角色化映射；
- placeholder residue 的 Workbench issue center 汇总；
- per-record batch issue center。
