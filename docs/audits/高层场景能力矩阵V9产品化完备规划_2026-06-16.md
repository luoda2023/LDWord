## 2. 一句话结论

完善的场景能力矩阵不是“场景名足够多”，而是：

```text
高频任务族
→ 明确承载层
→ 明确工作流
→ 明确模型字段
→ 明确 UI/执行/报告/测试证据
→ 明确不承诺边界
```

如果一个需求只能说“加个开关”，但不能说清它属于哪个任务族、哪个 profile、哪个资料 schema、哪个 count profile、哪个 DeliveryPreset、哪个 ObjectPreflight 风险面、哪个报告证据，它还不是完整场景能力。

## 3. 当前事实基线

### 3.1 可执行 P0 顶层入口

当前 `SCENE_METAS` 有 6 个可执行入口：

| 入口 | 继续保留 | 收口要求 |
| --- | --- | --- |
| `custom` 自定义 | 是 | 只做手动组合，不暗含专业规则 |
| `thesis` 论文排版 | 是 | 应收窄为中文学术论文，不再吞英文投稿 |
| `bidding` 标书排版 | 是 | 强化资料包、附件 inventory、正副本/报告 |
| `official` 公文排版 | 是 | 强化编号保留、状态水印、正式/内部稿 |
| `technical` 技术文档 | 是 | 强化对象保护、图表公式、变更报告 |
| `report` 通用报告 | 是 | 保持轻量，不吞所有专业 profile |

这 6 个入口是主工作流，不等于全部场景能力。

### 3.2 规划级 family

当前规划级 registry 已覆盖 14 个 family：

```text
journal_en
exam_teaching
project_application
contract_delivery
hr_batch_documents
meeting_policy_documents
product_sales_documents
long_document_publishing
form_batch_documents
qualification_archive_packages
finance_quote_documents
ip_patent_documents
bilingual_translation_documents
regulated_disclosure_documents
```

本轮新增的两个 family 是 V8 已点名但尚未进入 registry 的高频边界族：

- `bilingual_translation_documents`：双语合同、双语说明书、译文审校稿等；核心只做双语版式、术语一致性和对照审阅，不保证翻译质量。
- `regulated_disclosure_documents`：年报、ESG、社会责任、披露材料等；核心只做长文档结构、表格/附件 inventory、审阅/归档包，不做审计或披露结论。

### 3.3 已有模型槽位

当前模型已经具备承载完整矩阵的基础：

| 槽位 | 当前模型 |
| --- | --- |
| 输入契约 | `InputSourceProfile` |
| 资料契约 | `MaterialSchema` |
| 处理范围 | `FormatScopeConfig` |
| 合规与计数 | `ComplianceProfile` + CountEngine profile |
| 对象安全 | `ObjectPreflightPolicy` |
| 多版本交付 | `DeliveryPreset` |
| 内容显隐 | `ContentVisibilityRule` |
| 批量预设 | `BatchPreset` |
| 模板基线 | `TemplateConfig` |

后续重点不是再发明大模型，而是让这些槽位在高频场景中被同一套 UI、执行、报告和测试消费。

## 4. 完整场景的 20 个验收槽位

一个高频场景从“名字覆盖”变成“产品能力”，至少要过 20 个槽位。

| 槽位 | 必须回答 | 主要落点 |
| --- | --- | --- |
| 1. 用户任务 | 用户自然会怎么说这件事 | scene/family/profile |
| 2. 入口层级 | 顶层、profile、preset、schema、插件哪一层承载 | registry |
| 3. 输入格式 | docx、markdown、json、xlsx、bibtex、PDF/OCR、LaTeX 哪些可用 | `InputSourceProfile` |
| 4. 结构化事实源 | 是否有 JSON/XLSX/schema/intermediate | structured source |
| 5. 资料字段 | 需要哪些字段、签章、图片、附件、多实体 | `MaterialSchema` |
| 6. 处理范围 | 正文、摘要、目录、参考文献、附录、页眉页脚、附件 | `FormatScopeConfig` |
| 7. 定位方式 | 自动、页码、关键词、样式锚点、内容控件 | scope UI/parser |
| 8. 模板基线 | 外观基线和兼容模板是什么 | `TemplateConfig` |
| 9. 场景覆盖 | 哪些模板参数因业务策略覆盖 | scene feature overrides |
| 10. 能力组合 | 标题、页面、表格、公式、引用、清理、填充 | `module_switches` |
| 11. 专业对象 | 公式、化学式、题注、文献、图片、内容控件怎么处理 | feature config |
| 12. Count profile | 字数、词数、图表数、附件数口径 | CountEngine |
| 13. Profile 来源 | 学校、期刊、招采、申报指南、企业规则版本 | profile governance |
| 14. 对象风险面 | OLE、Visio、Excel、宏、修订、批注、域、文本框 | ObjectPreflight |
| 15. 缺失策略 | 缺字段、缺图、缺附件、低置信度、残留占位符怎么办 | failure policy |
| 16. 显隐规则 | 答案/解析、内部/正式、审阅/签署、水印状态 | `ContentVisibilityRule` |
| 17. 交付版本 | final、review、student、teacher、signing、submission、archive | `DeliveryPreset` |
| 18. 批量策略 | 多实体、多模板、多文件、失败隔离、汇总报告 | `BatchPreset` |
| 19. 可见证据 | Workbench、报告、artifact browser 能解释结果 | UI/report payload |
| 20. 测试证据 | registry、UI、pipeline、report、artifact 是否锁定 | pytest |

成熟度判定：

- 缺 1-8：边界不清；
- 缺 9-15：执行行为不清；
- 缺 16-18：交付不可验收；
- 缺 19-20：只能算规划，不算产品承诺。

## 5. 承载层裁决规则

后续任何新需求先走裁决，不先加入口。

| 判断问题 | 归属 |
| --- | --- |
| 用户反复用一个业务名描述它 | scene family / profile |
| 只是同一任务下的输出版本、命名、显隐、报告 | `DeliveryPreset` |
| 只是字段、图片、签章、附件、人员/公司/项目资料 | `MaterialSchema` / Assets |
| 只是字数、附件数、图表数、规则口径 | `ComplianceProfile` / CountEngine |
| 只是文档外观默认值 | 模板管理 |
| 只是本次运行状态、当前文件、输出目录、用户确认 | Workbench / Session |
| 涉及 OCR、AI 内容生成、完整 LaTeX、法律/财务/IP 判断 | Plugin / 人工确认 |
| 触碰 OLE、Visio、宏、修订、批注、域等 | ObjectPreflight + 报告 |

硬边界：

- 场景不是第二个模板编辑器。
- 模板只管外观基线。
- 场景管任务策略和执行行为。
- 资料包管事实值和资产角色。
- DeliveryPreset 管同源内容的交付形态。
- CountProfile 管统计口径。
- Workbench 管本次运行证据。
- Plugin 管外部依赖和专业判断。

V9 判断：

- 高频场景大类已经基本有归属；
- 真正缺口转为“first slice 是否闭合”和“边界是否在 UI/报告可见”；
- 不应继续新增顶层入口，先推进 P0/P1/P2 family 的最小可验收切片。

## 8. Word/OOXML 风险面必须前置

高层场景不是抽象标签，它最终会触碰 Word package。规划 family 必须声明 `ooxml_touchpoints`，并尽量映射到 ObjectPreflight。

| 风险面 | 高频来源 | 必须处理 |
| --- | --- | --- |
| `field` / 域 | 目录、页码、交叉引用、合同编号、披露字段 | 保留、更新策略、报告 |
| `comment` / 批注 | 合同、投稿修回、审阅稿、双语审校 | 保留、摘要、禁止静默删除 |
| `revision` / 修订 | 合同、技术审阅、公文内审、披露 | 默认保护、跳过高风险模块 |
| `textbox` / 文本框 | 表单、套打、双语说明、复杂模板 | 预检、版位保护 |
| `content_control` | 表单、合同、公文、HR | 字段映射、残留检查 |
| `drawing` / Visio | 技术、标书、论文、披露 | 高风险预检、必要时跳过重排 |
| `embedded_workbook` | 财务报价、披露、技术表格 | 预检、避免破坏嵌入对象 |
| `relationship` / package part | 附件、OLE、宏、嵌入包 | 报告、阻断或跳过 |

V9 要求：任何新增 family 如果触碰这些对象，不能只在文档里写“注意保护”，必须进入 `ooxml_touchpoints`、ObjectPreflight 推荐目标、Workbench 摘要、报告和测试。

## 9. 场景配置控件一致性

场景配置要继续继承模板管理的控件语言，尤其是你前面指出的缩进、段前段后、特殊缩进、行距类型等命名和交互问题。

| 参数类型 | 场景页要求 |
| --- | --- |
| 单选策略 | radio 或 segmented control |
| 多选能力 | checkbox / flow checkbox |
| 数值 + 单位 | 与模板管理一致的 spin/spacing input |
| 左/右缩进、段前/段后 | 同行排布和同名单位，不能换叫法 |
| 特殊缩进 | 必须可交互切换：无、首行、悬挂 |
| 行距类型 | 固定值、倍数、最小值等必须可切换 |
| 版本 preset | 列表 + 详情，不散落按钮 |
| 风险策略 | combo + 状态 badge + 报告话术 |
| 高风险确认 | 独立确认区，不混入普通表单 |

控件一致性不是视觉问题，而是语义一致问题：同一类参数在模板和场景中出现时，必须让用户知道哪个是外观默认值、哪个是业务策略覆盖。

## 10. 当前功能不完善的真正原因

现在的问题不是“功能点少”，而是高频链路缺少闭环。

| 缺口 | 为什么严重 | 建议闭合方式 |
| --- | --- | --- |
| `thesis` 描述仍过宽 | 英文投稿和中文论文会混 | 改为 `thesis_cn` 语义，`journal_en` 独立 |
| CountProfile 治理弱 | 不同学校/期刊/申报口径会混 | profile 来源、版本、范围解释 UI |
| 资料 schema 前台弱 | 缺字段/缺图/缺附件不可预测 | ScenePanel/AssetsPanel/报告同源展示 |
| ObjectPreflight 运行前确认仍需深化 | 运行后摘要、明细和运行前确认第一版已可见，但用户仍缺详情页、筛选、定位和可编辑跳过矩阵 | finding->skip->artifact 前台链路 + 运行前确认详情区 |
| DeliveryPreset 还需更强交付视图 | 多版本产物难验收 | 按 preset 展示文件、manifest、报告、显隐差异 |
| 结构化输入不足 | 试卷/HR/表单/项目无法稳定 | JSON/XLSX schema 校验与预览 |
| 表单/套打行高版位未闭合 | 固定版式高频痛点 | `row_height_pt` 去向明确：模板默认或场景锁定 |
| 公式转换链仍未闭合 | 学术/技术/试卷场景不完整 | LaTeX fragment MVP + 低置信度报告 |
| 审阅对比仍偏文本级 | 合同/技术/投稿不够 | 格式级对比、修订保留策略 |
| plugin boundary UI 不足 | 用户误以为核心能做 AI/OCR/法律/财务/IP | 插件边界可见，报告明确不承诺 |

## 13. 最终验收句

后续任何场景需求都按这句话验收：

```text
一个高频任务族，必须映射到明确承载层；
一个承载层，必须映射到明确工作流；
一个工作流，必须映射到模型字段、UI 控件、执行消费、报告证据和测试；
一个专业风险，必须映射到清晰的不承诺边界或插件。
```

这条链路成立，才算进入高层场景能力矩阵。否则它只是一个未归位的功能点。
