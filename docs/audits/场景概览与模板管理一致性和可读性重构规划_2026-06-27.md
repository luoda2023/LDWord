# 场景概览与模板管理一致性和可读性重构规划

日期：2026-06-27
范围：再次对照模板管理功能，重新规划场景概览的信息架构、可读性、一致性和后续实现路径。

## 1. 核心判断

上一次把场景概览里的内部术语翻译成了更可读的中文，但这只是“词变好了”，还没有解决真正的问题。

真正的问题是：模板管理页在表达“用户要得到的格式结果”，而场景概览页仍在表达“系统内部怎么证明自己做到了”。这两个信息层级不一样，所以即使把 `Green/L5` 改成“可直接使用”，用户仍然会觉得页面不像一个好用的功能，而像一个审计报告。

更准确的重构方向应该是：

- 模板管理负责“文档长什么样”。
- 场景管理负责“这次任务怎么跑”。
- Workbench 负责“把文件跑起来并处理问题”。
- 审计矩阵负责“开发和发布为什么能相信它”。

场景概览首屏必须从“审计状态集合”改成“任务执行说明书”。

## 2. 模板管理为什么相对更容易理解

当前模板管理页的首屏结构是：

1. 当前模板
2. 参数概览
3. 样式预览

这套结构天然符合用户认知：

- 当前模板：我现在选的是哪个格式。
- 参数概览：这个格式有哪些关键设置。
- 样式预览：这些设置看起来是什么效果。
- 编辑入口：点某一行就去改对应参数。

它的优点不是文案多好，而是信息层级非常稳定：

| 层级 | 用户问题 | 模板页回答 |
| --- | --- | --- |
| 选择 | 我现在用哪个模板？ | 当前模板 |
| 摘要 | 模板里设置了什么？ | 参数概览 |
| 结果 | 最后文档长什么样？ | 样式预览 |
| 行动 | 哪里能改？ | 参数行的编辑入口 |

这就是模板页像产品功能、而不是配置转储的原因。

## 3. 场景概览当前为什么还是不好懂

当前场景概览页把这些内容混在同一层：

- 场景预设
- 关联模板
- 编号策略
- 输入格式
- 合规/处理方式
- 对象保护
- 输出版本
- 参数归属
- 控件契约
- 场景族
- 覆盖矩阵
- 产品成熟度
- 样本覆盖
- 请求样本
- 样本边界
- 请求边界
- 样本详情
- 请求证据

这里的问题不是“信息不重要”，而是它们不是同一类信息。

| 信息类型 | 应该出现的位置 | 当前问题 |
| --- | --- | --- |
| 用户选择 | 首屏顶部 | 已出现，但下面立即被大量状态淹没。 |
| 任务结果 | 首屏核心 | 目前没有清楚表达“跑完会发生什么”。 |
| 可编辑参数 | 概览行/详情页 | 目前散在卡片里，缺少“点这里去改”的直觉。 |
| 风险提醒 | 首屏次级或折叠区 | 现在和普通能力卡混在一起，导致用户不知道是错误、提醒还是边界。 |
| 审计证据 | 高级/证据页 | 现在直接进入首屏，占据注意力。 |

所以现在的问题可以总结为一句话：

场景页把“给开发者证明的证据”放在了“给用户决策的入口”里。

## 4. 场景页应该对齐模板页的哪种一致性

场景页不应该机械复制模板页，因为二者对象不同。

模板页的对象是“格式配置”，所以它适合用“参数概览 + 样式预览”。
场景页的对象是“任务执行”，所以它应该用“任务概览 + 执行预览”。

建议建立下面的对应关系：

| 模板管理 | 场景管理应对齐的模块 | 说明 |
| --- | --- | --- |
| 当前模板 | 当前任务 | 选场景、选模板、选编号策略。 |
| 参数概览 | 执行参数概览 | 输入、范围、模板来源、风险处理、输出版本、人工确认。 |
| 样式预览 | 执行预览 | 文件会按什么步骤被处理，而不是再堆状态卡。 |
| 参数详情页 | 场景详情页 | 输入与资料、处理范围、格式与模板、风险与边界、输出版本。 |
| 编辑按钮 | 跳转设置按钮 | 每一行都能跳到对应设置页。 |
| 模板 summary card | 场景 summary card | 统一标题、图标、状态、摘要语气。 |

真正的一致性不是“长得完全一样”，而是两者都遵守同一条规则：

先让用户知道结果，再让用户改参数，最后才给证据。

## 5. 建议的新内容板块

### 5.1 首屏重规划

建议场景概览首屏改成 4 个板块：

1. 当前任务
2. 执行预览
3. 关键设置
4. 风险与边界

证据、样本、发布门禁、drilldown 不再直接铺在首屏，而是进入“高级证据”或折叠面板。

### 5.2 板块一：当前任务

目的：回答“我现在要让程序做什么？”

包含：

- 场景预设
- 关联模板
- 编号策略
- 一句任务摘要
- 适合处理什么
- 不负责什么

示例：

```text
当前任务：通用格式清理
使用模板：默认格式
编号处理：重建编号

适合：把已有 Word / Markdown 统一成当前模板格式。
注意：会保留域、批注、修订和宏等高风险对象，不会静默改写。
```

这个板块不应该出现：

- pack
- fixture
- proxy
- Green/L5
- maturity
- contract
- drilldown
- source evidence

### 5.3 板块二：执行预览

目的：回答“点运行后会发生什么？”

这里不应该用 12 个状态卡，而应该像流程预览。

建议 5 步：

1. 读取文件
2. 检查风险对象
3. 套用模板格式
4. 生成检查报告
5. 输出文件

示例：

```text
1. 读取 Word / Markdown
2. 检查域、批注、修订、宏、嵌入对象
3. 按默认格式统一页面、正文、标题、表格和页眉页脚
4. 遇到高风险对象时先提醒或跳过
5. 生成最终 Word 和报告
```

这对应模板页的“样式预览”。模板页预览视觉结果，场景页预览执行结果。

### 5.4 板块三：关键设置

目的：回答“哪些设置会影响这次运行？去哪里改？”

建议采用和模板“参数概览”一致的行式结构，而不是多列卡片。

建议行：

| 行 | 显示内容 | 跳转 |
| --- | --- | --- |
| 输入与资料 | 支持 Word / Markdown；是否需要资料包 | 输入与资料 |
| 处理范围 | 正文、表格、标题、页眉页脚等 | 处理范围 |
| 模板与样式 | 当前模板；场景是否覆盖模板设置 | 格式与模板 |
| 风险处理 | 宏阻断、修订保留、高风险对象跳过 | 风险与边界 |
| 输出版本 | 最终 Word、审阅稿、报告、资料清单 | 输出设置 |
| 人工确认 | 是否需要插件、人工门或外部规则确认 | 风险与边界 |

这一层应该只展示用户能理解的摘要：

```text
输入与资料    Word / Markdown，可选资料包
处理范围      9/9 个区域会处理
模板与样式    使用“默认格式”，场景不覆盖模板样式
风险处理      宏会阻断；批注、修订会保留
输出版本      最终 Word
人工确认      无需人工确认
```

### 5.5 板块四：风险与边界

目的：回答“有哪些事情程序不会擅自做？”

这个板块应该短而明确，默认只显示 2 到 3 条最重要提醒。

示例：

```text
会提醒：
- 文档里有宏、嵌入对象、修订或隐藏文字时，会先报告。

不会替你做：
- 不判断法律、审计、专利、财务或翻译质量。

需要确认：
- 如果目标规则来自学校、期刊、投标方或外部系统，需要人工确认来源。
```

详细证据可以放到“查看证据”。

## 6. 左侧导航也需要重规划

当前左侧导航是：

- 场景概览
- 处理范围
- 功能开关
- 功能参数
- 输出设置

这里的问题是“功能开关 / 功能参数”太像工程配置，不像用户任务。

建议改成：

| 新导航 | 目的 | 对应旧内容 |
| --- | --- | --- |
| 场景概览 | 当前任务、执行预览、关键设置 | 场景概览 |
| 输入与资料 | 文件类型、资料包、字段、图片角色 | 部分功能参数 |
| 处理范围 | 哪些文档区域会被处理 | 处理范围 |
| 格式与模板 | 模板绑定、编号策略、场景样式覆盖 | 当前模板 + 功能开关中样式相关项 |
| 风险与边界 | 对象预检、高风险跳过、人工确认 | 对象保护、合规、边界 |
| 输出版本 | final/review/report/package 等 | 输出设置 |
| 高级证据 | 样本、请求证据、发布门禁、drilldown | 当前首屏的大量审计卡 |

如果短期不想大改导航，至少应把“高级证据”从首屏分离出来，放到场景概览下面的可折叠区域。

## 7. 和模板管理保持一致的具体规则

### 7.1 首屏只回答五个问题

场景首屏只回答：

1. 这是用来做什么的？
2. 它会处理哪些内容？
3. 它使用哪个模板？
4. 它遇到风险怎么办？
5. 它会输出什么？

任何不能回答这五个问题的信息，都不该默认铺在首屏。

### 7.2 行动必须跟着摘要走

模板页的“参数概览”好懂，是因为每一行都能去编辑。

场景页也应该做到：

- 输入与资料 -> 跳到输入与资料页
- 处理范围 -> 跳到处理范围页
- 模板与样式 -> 跳到格式与模板页
- 风险处理 -> 跳到风险与边界页
- 输出版本 -> 跳到输出设置页
- 人工确认 -> 跳到风险与边界或插件确认页

如果一张卡只是显示状态但不能行动，它应该放到证据层，而不是首屏。

### 7.3 文案层级分三层

第一层：用户话术
第二层：产品解释
第三层：开发证据

示例：

| 层级 | 示例 |
| --- | --- |
| 用户话术 | 宏会阻断，批注和修订会保留。 |
| 产品解释 | 为避免破坏文档对象，高风险对象会进入预检报告。 |
| 开发证据 | object_preflight.scan_targets = macros / comments / tracked_changes |

当前场景页最大的问题，是第三层经常跑到第一层。

### 7.4 禁止一层文案出现的词

首屏和二级摘要中应避免：

- pack
- fixture
- proxy
- drilldown
- source evidence
- Green/L5
- Blue/Boundary
- maturity
- static closure
- contract
- OOXML
- handoff
- gate
- registry
- profile id

这些词可以保留在 tooltip、证据页、开发者模式、导出报告里。

### 7.5 状态词统一

模板页里有“执行 / 跳过”。场景页可以扩展为：

| 状态 | 含义 |
| --- | --- |
| 会处理 | 本次会自动执行。 |
| 会保留 | 不改写，只保护。 |
| 会提醒 | 发现风险后提示用户。 |
| 会阻断 | 风险太高时停止执行。 |
| 需确认 | 需要人工或插件确认。 |
| 不处理 | 明确不属于当前场景。 |

这些状态比“已守门”“可直接使用”“边界说明”更像用户操作语言。

## 8. 建议的投影模型

为了避免继续手写散落文案，建议新增一层场景首屏 projection，类似模板的 `template_summary_projection.py`。

建议文件：

```text
src/ui/panels/scene_overview_projection.py
```

建议模型：

```text
SceneOverviewSpec
SceneOverviewSectionSpec
SceneOverviewRowSpec
SceneRunStepSpec
SceneRiskNoticeSpec
SceneEvidenceLinkSpec
```

建议输出：

```text
build_scene_task_summary(scene)
build_scene_run_preview_steps(scene)
build_scene_key_setting_rows(scene)
build_scene_risk_notices(scene)
build_scene_evidence_links(scene)
```

重点是把“用户首屏 projection”和“审计证据 projection”拆开。

当前 `build_scene_overview_summary_items()` 不应该继续承担所有事情。它现在把输入、合规、控件契约、覆盖矩阵、样本、请求证据、产品成熟度都拼到一个 SummaryGrid 里，天然会膨胀。

## 10. 高级证据应该怎么放

高级证据不是不要，而是不能压在首屏。

建议高级证据页包含：

- 参数归属
- 控件契约
- 覆盖矩阵
- 产品成熟度
- 样本覆盖
- 请求样本
- 样本详情
- 请求证据
- release gate 摘要
- drilldown 链接

这里可以继续使用 SummaryGrid，因为这就是给开发/实施/验收的人看的。

建议入口文案：

```text
高级证据
这些信息用于验证当前场景为什么可发布，普通运行前不需要逐项阅读。
```

## 11. 与模板详情页的组件一致性

模板详情页已经使用：

- `TemplateSummaryCard`
- `SummaryGrid`
- `template_form_row`
- 统一图标
- 统一详情页顶部摘要
- 统一参数行跳转

场景页建议：

1. 抽出 `SceneSummaryCard`，视觉上和 `TemplateSummaryCard` 一致，但标题语义更偏“任务”。
2. 复用 `template_form_row`，保持表单行密度和模板页一致。
3. 场景详情页顶部也放“本页摘要”，而不是只有控件。
4. 左侧导航状态使用统一标签：会处理 / 会跳过 / 需确认 / 会阻断。
5. 场景概览的关键设置行复用模板概览 `_SummaryRow` 的交互模式，点击编辑跳转对应详情页。

## 12. 可读性验收标准

建议后续实现时增加这些测试：

1. 首屏禁词测试

   对场景概览首屏 projection 做断言，不能出现：

   ```text
   pack, fixture, proxy, Green/L5, Blue/Boundary, contract, drilldown, OOXML
   ```

2. 首屏数量测试

   默认展开内容不超过：

   - 1 个当前任务卡
   - 1 个执行预览
   - 6 行关键设置
   - 3 条风险提醒

3. 行动入口测试

   每个关键设置行必须有目标：

   - 输入与资料
   - 处理范围
   - 模板与样式
   - 风险与边界
   - 输出版本

4. 模板一致性测试

   场景里出现的模板相关字段，必须能说明：

   - 来自模板
   - 被场景覆盖
   - 跟随当前模板
   - 输出版本另选模板

5. 截图回归

   后续进展：执行预览已从长文本标签升级为步骤行，详见 `docs/refactor-records/场景概览执行预览步骤化执行记录_2026-06-29.md`。

   桌面和窄窗口检查：

   - 关键设置行不溢出
   - 风险文案不压住按钮
   - 已完成：执行预览步骤不再挤成一团，当前以 5 个步骤行展示。
   - 高级证据默认折叠

## 13. 分阶段落地建议

### 阶段 1：先拆 projection，不动大 UI

新增 `scene_overview_projection.py`，输出：

- 当前任务摘要
- 执行步骤
- 关键设置行
- 风险提醒
- 高级证据链接

同时保留现有 `build_scene_overview_summary_items()`。

### 阶段 2：重做场景概览首屏

把 `_SceneOverviewDetail` 从一个大 Card 改成 4 个 Card：

- 当前任务
- 执行预览
- 关键设置
- 风险与边界

旧 SummaryGrid 移入“高级证据”折叠区。

### 阶段 3：调整左侧导航

短期：

- 保留旧导航，但新增“高级证据”入口。

中期：

- 把“功能开关 / 功能参数”改为“格式与模板 / 风险与边界 / 输入与资料”。

落地状态：

- 本轮已完成中期导航语义调整：顶部保留“场景概览 / 高级证据”，编辑入口按“格式与模板 / 风险与边界 / 输入与资料 / 输出”重新分组。

### 阶段 5：接 Workbench

场景概览的“执行预览”最终应该和 Workbench 运行流程一致：

- 读取
- 预检
- 格式化
- 报告
- 输出

这样用户在场景页看到的步骤，和真正运行时看到的步骤一致。

## 14. 这次不建议继续做的事

不建议继续只做这些：

- 继续增加 SummaryGrid 卡片。
- 继续在首屏显示发布门禁数字。

这些会让页面越来越完整，但不会越来越好用。

## 15. 最终目标

模板管理页让用户相信：

```text
我知道文档会长什么样。
```

场景管理页应该让用户相信：

```text
我知道这次运行会做什么、不会做什么、遇到风险怎么办、最后得到什么。
```

只要这个目标不成立，再多“状态卡”都是噪音。

所以这次场景页真正合适的优化，不是继续打磨单张卡片，而是把首屏从“证据看板”重构成“任务执行说明 + 可编辑设置概览 + 风险边界说明”。
