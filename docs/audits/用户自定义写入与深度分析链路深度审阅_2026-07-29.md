# 用户自定义写入与深度分析链路深度审阅

- 审阅日期：2026-07-29
- 审阅范围：用户自定义任务保存、需求输入、附件绑定、自然语言路由、深度分析上下文、披露/澄清/确认、模型续接、会话持久化与异常恢复
- 审阅方式：代码静态审阅、状态机审阅、定向动态探针、现有测试回归
- 文档状态：初审确认的 13 项缺陷已完成整改并复验
- 本次变更：保留初审事实、复现与风险记录，并在第八节追加整改实现和最终验收证据

## 一、结论

初审时，“正常短输入、附件持续存在、单一模型、无中断”的主路径可以完成，但不能确认“所有用户自定义写入链路均成功，也不能确认用户始终可以快速、完整地进行深度分析与确认”。截至本次整改复验，以下 13 项已全部关闭；当前可以确认已实现且受支持的用户自定义写入、深度分析、披露和确认链路通过自动化验收。planned/gated 场景及未配置的真实公网模型仍属于明确能力边界，不包含在“已成功”的范围内。

本轮共确认 13 项缺陷：

| 级别 | 数量 | 含义 |
|---|---:|---|
| P0 | 0 | 未发现无条件破坏原文或绕过执行批准的缺陷 |
| P1 | 9 | 会导致错误路由、材料不完整却显示成功、确认续接失效、数据边界不清或恢复后链路失败 |
| P2 | 4 | 会导致失败不可见、选项不可达、持久化数据失控或损坏会话静默消失 |

核心判断：

1. 正常 happy path 已通过，但异常路径存在“静默成功”“静默失败”和“状态不可恢复”。
2. 深度分析最大风险不是模型回答质量，而是材料可能未完整送达，界面仍把任务标记为完成。
3. 用户确认链路最大风险是续接游标在请求成功前即被清除，失败重试无法延续原确认上下文。
4. 自定义任务能够保存中文、多行提示词，但缺少长度、重复项和版本结构治理。
5. 能力矩阵并非全量可执行：23 条路由 × 6 类操作共 138 个组合，其中 25 个 executable、65 个 planned、48 个 gated。planned/gated 是能力边界，不应被解释为写入故障；但产品不能宣称所有场景均可直接自动生产。

## 二、已通过的基线

以下检查已通过，说明主路径基础能力存在：

- Assistant 相关测试：193 passed。
- 关键端到端用例：9 passed。
- QSettings 自定义任务中文、多行内容真实落盘与重读通过。
- 自定义任务选择 → 输入框填充 → 提交 → 分析响应 → 草稿清空通过。
- 正常模型选择事件会同步当前会话模型；程序化 `select_provider()` 阻断信号的现象不属于真实用户缺陷。
- 附件披露指纹校验、执行前审批、输出不覆盖输入文件等既有安全守卫仍有效。

这些通过项不能覆盖本报告中的边界与失败场景。

## 三、P1 缺陷

### D-01 普通论文分析被误判为 PDF 论文导入门禁

- 严重级别：P1
- 链路：需求输入 → 自然语言路由 → 能力门禁
- 复现输入：附加普通 DOCX，输入“分析这份论文”。
- 实际结果：`response_closed / import_pdf_thesis_boundary / gated`。
- 期望结果：进入普通文档或论文审阅分析；只有出现 PDF、扫描、OCR、转换或导入意图时才进入 PDF 导入门禁。
- 动态证据：`DEFECT_ROUTE response_closed transform import_pdf_thesis_boundary gated`
- 代码证据：
  - `src/config/scene_natural_request_router.py:510-518` 的导入路由把“论文”本身列为上下文命中词。
  - `src/assistant/application/capability_registry.py:113-129` 仅把“分析问题”识别为 review，未覆盖普通“分析”表达。
- 影响：用户上传可直接读取的 DOCX 论文后，无法进入深度分析，且会收到错误的专业能力边界提示。
- 建议验收：
  - 导入门禁必须要求至少一个介质/转换强信号。
  - “分析这份论文”“审阅这篇论文”必须进入 review/advisory。
  - 补充正反例参数化路由测试。

### D-02 附件在提交前失效时被静默移除，任务仍可无材料完成

- 严重级别：P1
- 链路：附件选择 → 提交冻结 → 深度分析
- 复现步骤：选择 DOCX；提交前删除或移动文件；输入“请深入分析这份文档并列出待确认项”。
- 实际结果：请求返回 True，模型收到 0 个附件，响应状态为 completed，界面没有“附件已失效”阻断。
- 动态证据：`MISSING_ATTACHMENT True 1 0 False completed`
- 代码证据：`src/assistant/ui/turn_flow_mixin.py:778-787` 只保留 `Path.is_file()` 的引用，失效引用直接被丢弃。
- 影响：用户认为系统在分析所选文档，实际模型只依据一句需求自由回答，形成最危险的“无材料深度分析成功”。
- 建议验收：
  - 曾显式选择附件但提交时不存在，必须阻断请求并保留草稿。
  - 展示失效路径/文件名和重新选择动作。
  - 不得自动降级为无附件 general chat。

### D-03 附件正文超过 40,000 字符后静默截断

- 严重级别：P1
- 链路：附件读取 → 上下文组装 → 深度分析
- 复现：使用正文超过 50,000 字符的 DOCX 发起分析。
- 实际结果：仅发送 40,000 字符；审计字段记录 `attachment_text_truncated=True`，但发给模型的材料没有截断标记，用户界面也无提示。
- 动态证据：`DEFECT_TEXT_TRUNCATION True 40000 has_marker=False`
- 代码证据：
  - `src/assistant/runtime/turn_runner.py:62` 定义 40,000 字符上限。
  - `src/assistant/runtime/turn_runner.py:202-259` 截取材料并只更新内部审计字段。
  - `src/assistant/ui/turn_flow_mixin.py:1072-1120` 未把正文截断状态投影为用户可见消息。
- 影响：模型与用户都可能把部分文档分析误认为全文分析，结论完整性不可证明。
- 建议验收：
  - 在模型上下文和 UI 中同时声明截断范围。
  - 优先采用分块、摘要索引或分段分析，而不是无提示截尾。
  - “全文分析”在未覆盖全文时不得显示为完成。

### D-04 复杂格式证据超预算后被整段丢弃，任务仍显示 completed

- 严重级别：P1
- 链路：标准样稿 → 格式证据提取 → AI 格式分析
- 复现：构造格式证据 JSON 大于 20,000 字符的复杂 DOCX。
- 实际结果：生成了 29,229 字符证据，实际发送证据数为 0；审计记录 `context_budget_exceeded`，任务状态仍为 completed，模型上下文不含 `<document_format_evidence>`。
- 动态证据：`DEFECT_FORMAT_BUDGET 29229 0 ... completed evidence_sent=False`
- 代码证据：
  - `src/assistant/runtime/turn_runner.py:63` 定义格式证据预算。
  - `src/assistant/runtime/turn_runner.py:268-270` 超预算时只记录错误，不发送压缩或部分证据。
  - `src/assistant/ui/turn_flow_mixin.py:1088-1118` 只渲染成功摘要，不渲染预算错误。
- 影响：系统可能声称已完成标准样稿格式分析，实际模型没有收到任何格式证据。
- 建议验收：
  - 超预算时压缩、分页或阻断，禁止无证据 completed。
  - UI 必须显示已覆盖/未覆盖的证据范围。
  - 增加复杂样式、表格、分节和直接格式组合测试。

### D-05 “分析标准样稿并套用到另一文档”会把样稿误当生产输入

- 严重级别：P1
- 链路：组合需求 → 附件角色绑定 → 本地计划
- 复现：只附加一份标准样稿，输入“先分析这份标准文件的格式要求，再套用到另一份文档”。
- 实际结果：直接生成 `plan_ready`；唯一附件角色为 `production_input`；计划把标准样稿自身作为生产输入；缺少目标文档却没有 blocking issue。
- 动态证据：`COMBINED_ROLE True plan_ready production_input True [] 0`
- 代码证据：
  - `src/assistant/domain/docx_format_evidence.py:91-96` 只要包含 mutation term 就否定格式要求分析。
  - `src/assistant/application/attachment_policy.py:18-48` 对 document_action 的单附件绑定为 production_input。
- 影响：后续执行可能格式化样稿副本，而不是用户尚未提供的目标文档；参考和生产对象发生角色反转。
- 建议验收：
  - 组合请求拆成“参考分析”和“目标生产”两个明确阶段。
  - 未提供目标文档时必须进入澄清/阻断。
  - 参考样稿不得因 mutation term 自动降级为 production_input。

### D-06 确认续接游标在请求成功前被清除，失败重试无法续接

- 严重级别：P1
- 链路：模型提问 → 用户确认 → 续接调用 → 失败重试
- 复现：
  1. 首次模型响应返回 `continuation_id=cursor-1` 和 question。
  2. 用户提交选择，第二次调用带 `cursor-1`，但模型临时失败。
  3. 点击“重新发送”。
- 实际结果：三次调用游标依次为 `["", "cursor-1", ""]`；失败后 pending continuation 已为空。
- 动态证据：`CONTINUATION_RETRY cursor-1 ['', 'cursor-1', ''] {} completed`
- 代码证据：
  - `src/assistant/ui/turn_flow_mixin.py:119-133` 在启动续接请求前清空 pending continuation。
  - `src/assistant/ui/turn_flow_mixin.py:1009-1058` 失败分支不恢复游标。
  - `src/assistant/ui/assistant_panel.py:960-967` 重试只重发文本。
- 影响：模型端状态机无法知道用户回答的是哪一个待确认问题，可能重新起题、答非所问或重复执行。
- 建议验收：
  - 游标采用“in-flight + committed”两阶段状态。
  - 只有续接成功或被服务端明确消费后才清除。
  - retry 必须复用原 provider、model、cursor、问题 ID 和用户回答。

### D-07 切换到另一模型服务时，历史对话会无确认地全部发送

- 严重级别：P1
- 链路：模型切换 → 会话同步 → 新模型请求
- 复现：先在模型 A 发送私有内容；切换到模型 B；再发送第二条消息。
- 实际结果：模型 B 收到 3 条历史消息，包含模型 A 下的首条私有用户消息；没有历史迁移披露或清空选项。
- 动态证据：`CROSS_PROVIDER_HISTORY cloud-main cloud-model 3 True ['user', 'assistant', 'user']`
- 代码证据：
  - `src/assistant/ui/assistant_panel.py:1790-1800` 直接替换当前会话 provider/model。
  - `src/assistant/ui/turn_flow_mixin.py:441-447` 把完整 `session.messages` 写入请求。
  - `src/assistant/runtime/turn_runner.py:400-406` 把所有可见历史序列化给新 provider。
- 影响：当两个 profile 指向不同公司或不同受控域时，旧会话内容跨数据边界披露；现有附件披露卡不覆盖历史消息。
- 建议验收：
  - 跨 provider/base URL 切换必须明确提示“携带历史”或“新建空白会话”。
  - 默认最小披露，至少按 provider 数据域隔离历史。
  - 审计中记录历史消息数量、字符数和目标 provider。

### D-08 用户输入和完整历史没有请求预算上限

- 严重级别：P1
- 链路：自定义输入 → 历史组装 → 模型调用
- 复现：40 条每条约 10,000 字符的历史，再提交约 120,000 字符的新需求。
- 实际结果：41 条消息、520,070 个字符全部进入 provider request。
- 动态证据：`DEFECT_UNBOUNDED_CONTEXT 41 520070`
- 代码证据：
  - `src/assistant/runtime/turn_runner.py:400-406` 无截断、摘要、token 预算或窗口裁剪。
  - `src/assistant/ui/creative_home.py:493-505` 的输入设置/读取无长度限制。
- 影响：易触发模型上下文溢出、超时、高延迟、高费用和超大本地会话文件，直接损害“快速写入和分析”。
- 建议验收：
  - 建立字符/token 双预算和 provider-specific context window。
  - 超限前给出可见提示，允许摘要旧历史或新建会话。
  - 单条输入、自定义任务 prompt 和会话总量分别设限。

### D-09 崩溃恢复只修复 turn_status，遗留 provider_running 作业导致后续本地计划失败

- 严重级别：P1
- 链路：附件分析中断 → 启动恢复 → 新文档请求
- 复现：持久化 `turn_status=provider_running` 且 `document_job.status=provider_running` 的会话，重新初始化面板，再发起本地格式化请求。
- 实际结果：恢复后 turn_status 为 failed，但 document_job 仍为 provider_running；后续抛出 `Unsupported document job transition: 'provider_running' -> 'plan_ready'`。
- 动态证据：`RECOVERY_STALE_JOB failed provider_running ValueError:... provider_running`
- 代码证据：`src/assistant/application/session_recovery.py:140-154` 只更新 turn_status 并追加恢复消息，没有把关联 document_job 转为 failed/cancelled。
- 影响：应用异常退出后，同一会话可能无法进入本地生产计划；从 composer 提交时该异常还会被静默吞掉，表现为“点发送没有反应”。
- 建议验收：
  - 恢复时原子协调 turn 与 document_job 两套状态。
  - provider_running 中断必须进入允许重试和重新规划的终态。
  - 增加重启后“重试分析”和“改发本地文档动作”测试。

## 四、P2 缺陷

### D-10 提交/草稿持久化异常缺少用户可见反馈

- 严重级别：P2
- 链路：输入 → 会话创建/保存 → 提交反馈
- 复现：让 submission handler 抛出 `OSError("disk full")`。
- 实际结果：草稿保留是正确的，但无错误消息、无 gate、无 toast、无日志上下文；按钮仍显示普通“发送任务”提示。
- 动态证据：`SUBMIT_EXCEPTION_FEEDBACK important requirement [] <empty> <normal send tooltip>`
- 代码证据：
  - `src/assistant/ui/creative_home.py:454-470` 捕获所有 Exception 后只设 accepted=False。
  - `src/assistant/ui/assistant_panel.py:477-483` 草稿自动保存没有异常处理。
- 影响：磁盘满、权限变化、会话 JSON 写入失败时，用户只能反复点击，无法判断需求是否已写入。
- 建议验收：
  - 保留草稿，同时显示可行动错误和重试入口。
  - 记录失败阶段、会话 ID 和安全化错误原因。
  - 草稿自动保存失败不得从 Qt 事件槽裸抛。

### D-11 模型返回超过 4 个确认选项时，第 5 项以后不可见

- 严重级别：P2
- 链路：模型确认请求 → 交互卡投影 → 用户选择
- 复现：confirmation request 返回 5 个 options。
- 实际结果：presentation 持有 5 项，但界面只创建 4 个按钮，且没有“还有 1 项”、分页或其他输入提示。
- 动态证据：`QUESTION_CHOICES 5 4 ['0', '1', '2', '3']`
- 代码证据：`src/assistant/ui/interaction_card.py:233` 使用 `self.presentation.choices[:4]`。
- 影响：合法选项可能不可达，用户提交的确认不能表达真实选择。
- 建议验收：
  - 协议层显式限制并验证最多 4 项，或 UI 完整渲染/分页。
  - 被裁剪时必须拒绝卡片或显示清晰提示，不能静默隐藏。

### D-12 自定义任务持久化缺少长度、重复项和结构版本校验

- 严重级别：P2
- 链路：自定义任务保存 → QSettings → 加载 → 快捷写入
- 复现：持久化两个同名任务，其中一个 prompt 为 200,000 字符。
- 实际结果：两项均加载，同名未去重，200,000 字符 prompt 完整进入内存和 UI。
- 动态证据：`CUSTOM_TASK_VALIDATION 2 ['Dup', 'Dup'] 200000`
- 代码证据：
  - `src/assistant/ui/creative_home.py:1221-1301` 新增/编辑只校验非空和交互时重名，不限制长度。
  - `src/assistant/ui/creative_home.py:1349-1364` 加载外部持久化值时不去重、不限长、无 schema version。
  - `src/assistant/ui/creative_home.py:1366-1379` 直接序列化整个 payload。
- 影响：异常或旧版本数据可制造重复选择、超大输入、卡顿和超大模型请求。
- 建议验收：
  - 定义 versioned schema、label/prompt 长度、总字节数和规范化去重。
  - 加载时迁移或隔离非法项，并给出可恢复提示。

### D-13 损坏会话文件会从侧边栏静默消失

- 严重级别：P2
- 链路：会话落盘 → 启动枚举 → 恢复/可见性
- 复现：在 sessions 目录放置损坏 JSON。
- 实际结果：文件仍存在，直接 load 抛 JSONDecodeError，但 `list_summaries()` 返回 0，用户看不到损坏会话及恢复入口。
- 动态证据：`CORRUPT_SESSION_VISIBILITY 0 JSONDecodeError True`
- 代码证据：`src/assistant/storage/session_store.py:23-32` 枚举时捕获解析错误后直接 continue。
- 影响：会话可能被用户误认为丢失；没有隔离副本、告警或导出原始文件的路径。
- 建议验收：
  - 损坏会话进入 quarantine/repair 列表，不得静默消失。
  - 保留原文件并显示恢复或导出入口。
  - 增加截断 JSON、错误 schema、身份不一致三类恢复测试。

| 探针 | 结果 |

| 标准样稿分析并套用到另一文档 | 样稿被绑定为 production_input，无 blocker |
| 确认续接失败后重试 | 第三次请求丢失 cursor |
| 跨 provider 切换 | 新 provider 收到旧 provider 全历史 |
| 中断会话启动恢复 | document_job 残留 provider_running |
| submission handler 写入异常 | 草稿保留，但无任何失败反馈 |
| 5 个确认选项 | UI 仅显示 4 个 |
| 重复/超长自定义任务 | 同名两项及 200k prompt 均被加载 |
| 损坏 session JSON | 文件存在但侧边栏静默隐藏 |

## 六、建议整改顺序

### 第一批：材料真实性与状态正确性

优先修复 D-02、D-03、D-04、D-06、D-09。共同准入条件：

- 任何未覆盖完整材料的分析都不能无提示 completed。
- 任何确认续接都必须可幂等重试。
- 中断恢复后的状态必须允许重试、重新规划或显式关闭。

### 第二批：路由和对象角色

修复 D-01、D-05。建立“介质意图、任务意图、附件角色”三层独立判定，避免单个关键词决定专业门禁或生产对象。

### 第三批：数据边界与容量治理

修复 D-07、D-08。建立 provider 数据域、历史迁移确认、上下文预算、摘要/分块策略和可见审计。

### 第四批：写入与交互健壮性

修复 D-10 至 D-13。补齐可见失败、协议约束、版本化持久化和损坏数据恢复。

## 七、修复完成后的最低回归门槛

1. 本报告 13 个动态探针全部转为自动化回归测试。
2. Assistant 现有 193 项测试和 9 项关键 E2E 保持全绿。
3. 路由新增至少 20 组“分析/论文/PDF/OCR/导入/套用”正反例。
4. 深度分析必须输出材料覆盖声明：附件数、已读字符/分块、截断与失败项。
5. 模型切换必须验证同 provider、跨 provider、跨 base URL 三类历史披露策略。
6. 恢复测试覆盖 provider stream 中断、披露后中断、确认续接中断、写盘失败和损坏 JSON。
7. 在上述门槛通过前，不建议对外表述为“所有用户自定义写入与深度分析链路均成功”。

### 8.3 最终确认边界

本次 13 项缺陷已全部整改并通过复验。对当前产品已实现的 executable 与 advisory 链路，可以确认用户能够正常、快速地写入需求，并在附件有效性、材料覆盖、格式证据、历史披露和模型确认均可审计的前提下进行深度分析与确认。

以下内容仍不能被扩大表述为“所有场景均已生产可用”：

- 能力矩阵中的 planned/gated 组合仍应按既有边界澄清或阻断，而不是伪装成功。
- 本机自动化使用确定性或模拟 Provider；未配置用户真实公网 Profile，因此不把 DNS、TLS、鉴权、模型名称和公网 SSE 质量计入本次通过结论。
- 32,000 字单条需求和 80,000 字历史窗口是明确容量合同；超限会可见阻断或裁剪，不承诺无限上下文。
