# 工作台导航目标面存在性审计记录

日期：2026-06-28

## 本轮目标

上一轮已经建立了两张表之间的一致性：

- `scene_repair_routing`：说明 target type 属于哪个修复归属面。
- `workbench_issue_navigation`：说明 target type 点击后进入哪个 panel/card。

但仍有一个缺口：导航 registry 虽然写了 `panel_id`、`card_id`、`feature_card_id`，却没有自动证明这些目标真实存在。

本轮目标是继续加深审计：

- panel id 必须存在于 `PANEL_SPECS`。
- scene card 必须存在于 `ScenePanel.CARD_DEFINITIONS`。
- template card 必须存在于 `TemplatePanel.CARD_DEFINITIONS`。
- workbench feature card 必须存在于 Workbench 静态卡片或能力卡片定义。

这样可以避免“路由表看起来有目标，但点击后目标卡片不存在”的问题。

## 执行结论

已扩展 `WorkbenchIssueNavigationAuditResult`，新增三类目标面存在性检查：

- `invalid_panel_targets`
- `invalid_card_targets`
- `invalid_feature_card_targets`

`audit_workbench_issue_navigation_routes(...)` 现在不仅检查：

- 修复归属表 target 是否有导航。
- 修复归属表 target 是否静默 fallback。
- 导航表额外 target 是否被允许。

还会检查：

- panel 是否真实存在。
- scene/template card 是否真实存在。
- workbench feature card 是否真实存在。

## 当前真实目标来源

| 目标类型 | 来源 |
| --- | --- |
| panel id | `src/ui/panel_registry.py` 的 `PANEL_SPECS` |
| scene card | `src/ui/panels/scene_panel.py` 的 `CARD_DEFINITIONS` |
| template card | `src/ui/panels/template_panel.py` 的 `CARD_DEFINITIONS` |
| workbench feature card | `CAPABILITY_FEATURE_CARD_DEFINITIONS` + `quick_execute` + `config_management` |

## 新增审计字段

| 字段 | 含义 |
| --- | --- |
| `invalid_panel_targets` | 导航 projection 指向不存在的 panel |
| `invalid_card_targets` | 导航 projection 指向不存在的 scene/template card |
| `invalid_feature_card_targets` | 导航 projection 指向不存在的 workbench feature card |

`is_clean` 已经包含这些字段；只要任一字段非空，审计就失败。

## 这一步对产品设计的意义

用户前面提出“功能分布应该更合理，边界应该更加清晰”。这不仅是视觉问题，也是路由契约问题。

现在链路已经是：

1. `scene_repair_routing` 说明谁负责修。
2. `workbench_issue_navigation` 说明点了去哪修。
3. `audit_workbench_issue_navigation_routes` 说明这个目标是否真实存在。

这让工作台问题从“字符串分支”变成了可审计的产品导航模型。

## 当前仍未覆盖

### 1. card 内部 field focus 尚未审计

现在能证明 `scene / scn_scope` 存在，但还不能证明：

- `scene.section_styles.references_body.font_cn` 一定能被 focus。
- `format_scope.sections.references` 一定能定位到具体控件。

下一层可以做 field-level focus registry。

### 2. Assets panel 内部目标尚未审计

现在能证明 `assets` panel 存在，但还不能证明：

- `field/company_name` 一定能定位到资料字段控件。
- `asset/company_logo` 一定能定位到资料资产行。
- profile scoped repair payload 一定能定位到对应 profile。

这需要 AssetsPanel 自己暴露目标消费审计。

### 3. Workbench feature card 是静态集合校验

当前 workbench feature card 的有效集合来自：

- `quick_execute`
- `config_management`
- `CAPABILITY_FEATURE_CARD_DEFINITIONS`

这能证明卡片 id 合法，但不能证明卡片在某个场景下当前可见。可见性还受功能开关影响。

## 推荐下一步

下一轮建议做“field focus 审计”：

1. 为 `scene_scope_field` / `scene_style_field` 增加可解析 field path 的 registry。
2. 检查 workbench navigation target key 能否被 ScenePanel focus。
3. 把无法定位的 key 标成 `scn_cleanup` fallback 或显式待设计。
4. 文档记录哪些 field path 已能端到端定位。
