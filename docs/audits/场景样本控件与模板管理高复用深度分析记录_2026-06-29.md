# 场景样本控件与模板管理高复用深度分析记录

日期：2026-06-29

## 1. 本轮判断

上一轮已经把场景证据卡片从“显示内部 id”改成“主文案可读、技术证据进 tooltip”。继续往下看，真正影响体验的不是某一两句文案，而是场景规划页的功能分布还没有完全向模板管理的成熟结构靠齐。

模板管理目前比较稳定的模式是：

- 顶部回答“当前对象是什么”。
- 中段用摘要卡回答“参数是否完整、哪些项在执行、哪些项跳过”。
- 预览区用真实控件表达页面/正文/标题/表格等效果。
- 证据、来源、内部编号放在 tooltip 或审计层，不占用主阅读路径。

场景规划页已经有同样的基础控件，但样本/请求样本区仍然把三件事混在一起：

- 用户判断：这个场景有没有足够样本和常见说法覆盖。
- 操作入口：生成样本库、打开样本、打开证据目录。
- 工程证据：fixture id、sample id、manifest 路径、manual gate id。

所以用户会看到 `contract_delivery_revisions`、`contract_signing_consistency`、`manifest: ...` 这类信息。功能是通的，但它不像模板管理那样“先说人话，再保留证据”。

本轮结论：场景样本区必须拆成“可读投影层 + 控件展示层 + 证据追踪层”，并让场景面板和 Workbench 共用同一套投影函数。否则界面看起来相似，真实行为仍会分叉。

## 2. 当前链路走到哪一步

已打通：

| 链路 | 当前状态 | 说明 |
| --- | --- | --- |
| 模板正文样式管理 | 已复用 `StyleManagementBlock` | 模板正文页以 `template_baseline_edit` 模式接入 |
| 场景分区样式管理 | 已复用 `StyleManagementBlock` | 场景分区样式以 `scene_section_rules` 模式接入 |
| 执行中心样式回执 | 已复用样式回执 block | 执行结果能显示样式差异和来源 |
| 最近结果样式复核 | 已接入同类回执 | 最近执行结果不再另写样式展示 |
| 场景概览摘要 | 已初步中文化 | 输入、输出、资料规则、证据卡片主文案已下沉技术 id |
| 样本覆盖摘要 | 已可读 | “已有样本文档 / 常见说法已覆盖”已经是用户语言 |
| 样本明细与请求列表 | 本轮推进 | 从 raw id 主显示改为中文语义显示 |

尚未完全打通：

| 链路 | 缺口 | 风险 |
| --- | --- | --- |
| 场景样本区的布局模式 | 仍是局部控件组合，没有形成共享证据 block | 后续场景页和 Workbench 可能再次拼出不同结构 |
| 样本证据明细 | tooltip 能追踪，但还没有可展开证据面板 | 证据多时 tooltip 会过长 |
| 样本库生成状态 | 主文案已清理，但仍缺少统一的 artifact 状态组件 | 未来导出、下载、重试、打开目录可能继续分散 |
| 请求样本筛选 | 场景页和 Workbench 现在共用显示投影，但筛选控件仍各自定义 | 过滤项、数量说明、空态仍可能漂移 |
| 模板预览跳转 | 场景到模板的入口已存在，但还没有把“样式 envelope/差异证据”作为跳转上下文完整传递 | 用户从场景定位到模板时仍可能不知道该看哪一块 |

## 3. 与模板管理的功能边界

推荐边界如下。

| 层 | 应该归谁 | 应显示什么 | 不应显示什么 |
| --- | --- | --- | --- |
| 模板管理 | 样式基线、页面预览、正文/标题/表格等排版规则 | 页面、正文、标题、表格、页眉页脚、目录等可视样式 | 场景 pack、fixture、request-cell |
| 场景规划 | 处理范围、资料规则、输出版本、风险边界、常见说法覆盖 | 资料包、用户说法、覆盖方式、是否需人工确认 | `schema_id`、`preset_id`、`fixture_id`、`sample_id` |
| Workbench | 执行前后状态、问题队列、样式/证据回执 | 当前执行结果、可打开证据、失败原因、下一步动作 | 直接拼接 registry 字段作为标题 |
| 共享投影层 | 同一个对象在不同面板中的显示名、tooltip、证据文本 | 中文显示名、数量摘要、证据编号分层 | 面板私有字符串拼接 |
| 审计/测试层 | 可追溯 id、路径、registry 完整性 | raw id、路径、gate id、manifest | 面向用户的主阅读文本 |

这意味着场景规划不应该复制模板管理的每个控件，而应该复制模板管理的表达原则：

```text
主文案 = 用户结论
辅助文案 = 业务含义
tooltip / evidence = 技术证据
data role / registry = 内部追踪
```

## 6. 后续必要功能

### 6.1 抽共享 SampleEvidenceBlock

当前样本区仍由面板手工组合：

- 详情文本
- 生成按钮
- 打开样本
- 打开目录
- 请求样本筛选
- 请求样本列表
- 打开证据
- 状态 label

建议抽成共享 block：

```text
SampleEvidenceBlock
  Summary: 样本覆盖 / 常见说法覆盖
  Actions: 生成样本库 / 打开目录 / 打开当前证据
  Browser: 样本文档列表 / 请求说法列表
  Evidence: tooltip 或可展开证据详情
```

这样场景页、Workbench、未来执行回执都可以复用同一组合，而不是只复用几个显示函数。

### 6.2 做可展开证据明细，不继续依赖长 tooltip

现在 raw id 已从主文案下沉，但 tooltip 会越来越长。优秀设计不应把所有证据塞进 hover。

建议下一步做：

- 主卡片：`2 个样本文档 / 4 个常见说法 / 1 个需澄清`
- 列表项：中文显示名
- 右侧/下方证据明细：编号、路径、manual gate、report id、fixture id

这样既能给普通用户干净界面，也能给开发/审计保留完整证据。

### 6.3 请求样本筛选控件统一

场景页和 Workbench 的筛选项仍各自定义：

- 全部
- 直接证据
- 人工确认
- 容易误解
- 不处理样本
- 借用样本

建议把筛选选项与显示名也收进共享投影层，避免后续其中一个入口新增状态后另一个入口漏掉。

### 6.4 场景到模板预览的上下文继续打通

场景规划里的样式入口应该更明确：

- 场景只回答“哪个分区跟随模板、哪个分区启用独立样式、哪里有差异”。
- 点进模板管理时，应带上明确上下文，例如“查看正文基线”“查看参考文献分区差异”“查看执行回执差异”。
- 模板管理继续负责真实样式预览，不让场景页再发明一套预览。

### 6.5 删除冗余解释文本

后续可以继续删除这些类型的文本：

- “手动控制所有功能开关与处理范围”这类说明句。
- “点击各参数行的编辑可跳转”这类使用说明。
- `manifest`、`fixture`、`request-cell`、`pack` 等主文案技术词。

替代方式：

- 用分组标题说明对象。
- 用按钮和图标表达动作。
- 用 disabled state / tooltip 表达不可用原因。
- 用 summary value/detail 表达当前状态。

## 7. 当前设计状态

这一轮之后，样本/请求样本区已经从“工程登记表”推进到“用户可读的证据入口”：

- 主文案不再暴露 fixture/sample id。
- 场景和 Workbench 使用同一套显示投影。
- 技术证据仍可追踪，没有被删掉。
- 样本库状态主文案不再展示路径。

但距离优秀设计还有两步：

1. 把样本证据区抽成真正的共享 block。
2. 把长 tooltip 升级为可展开证据面板。

这两步完成后，场景规划页才会真正接近模板管理的成熟度：控件可复用、语义可复用、状态可复用，用户只看结论，工程证据仍完整可追踪。
