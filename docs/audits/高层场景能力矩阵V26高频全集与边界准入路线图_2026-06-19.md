# 高层场景能力矩阵 V26 高频全集与边界准入路线图（2026-06-19）

## 1. 本轮定位

本轮继续回应“目前的功能点过于不完善，不希望出现高频适用场景遗漏或者边界不清晰”的要求。

V25 已经定义了完整能力的十个槽位和 L5 准入门槛。V26 不再重复证明“场景不是模板”，也不继续增加顶层入口，而是把高层矩阵收敛成一张可执行路线图：

```text
高频请求全集
-> 顶层 pack / planned family / profile / preset / plugin gate
-> 子场景边界
-> OOXML 风险面
-> 控件契约
-> request-cell / fixture / report / repair / release gate
-> L5 升级条件
```

V26 的目标是回答两个问题：

1. 怎样才算“高频适用场景没有遗漏”；
2. 怎样才算“边界清楚，不把专业判断、导入转换、输出版本、模板外观、资料事实混在一起”。

## 2. 本轮事实基线

当前矩阵的事实源来自代码 registry、测试门禁、V25 文档、两份外部技术记录和此前场景规划对话。外部记录只吸收产品边界和能力分层，不直接当作当前项目已实现能力。

| 事实层 | 当前状态 | 对 V26 的含义 |
| --- | --- | --- |
| coverage pack | 12 个 pack：`quick_formatting`、`chinese_academic`、`english_journal`、`exam_education`、`bidding_materials`、`official_policy`、`technical_long_docs`、`application_reports`、`contract_delivery`、`batch_forms`、`professional_disclosure`、`import_ai_boundary` | 顶层入口已经覆盖主要高频心智，不应继续轻易膨胀 |
| planned family | 15 个 family：P1/P1 candidate/P2 混合，均未直接冒充顶层可执行场景 | 高频子场景应优先落 family/profile，而不是新增导航入口 |
| request-cell | 47 条高频样本：42 matched、4 ambiguous、1 negative | 高频说法已有验收基线，下一步是扩充真实业务样本和全局浏览 |
| coverage level | 31 direct family fixture、11 manual boundary、4 ambiguous、1 negative、0 pack proxy | 已摆脱“只有 pack proxy”的假覆盖，但边界样本仍要更强 UI/report |
| readiness | pack：7 orange/L4、3 yellow/L3、2 blue/boundary；family：2 orange、9 yellow、4 blue；0 green/L5 | 当前不能对外宣称全矩阵完整稳定 |
| sample fixture | 14 个 DOCX fixture 覆盖 12 个 pack 和主要 OOXML 风险面 | 样本库是最小证据，不等于真实业务模板深度 |
| release gate | 本地 release gate 与 GitHub Actions workflow 已有 first slice | 仍缺远端状态、分支保护、真实发布治理 |

结论：当前问题不是“没有矩阵”，而是“矩阵还没有全部达到可承诺的产品成熟度”。

## 3. 完善的定义

高层场景能力矩阵的完善，不等于场景名足够多。完善应同时满足五个条件：

| 条件 | 合格标准 | 失败形态 |
| --- | --- | --- |
| 高频全集 | 用户高频说法能落到 pack/family/preset/plugin gate，且正例、歧义例、反例齐全 | 只覆盖内部命名，用户换个说法就丢失 |
| 归属清晰 | 每个参数和能力能说明属于 template、scene、material、output、plugin 或 session | 一个开关同时管样式、输出、资料和专业判断 |
| 风险可解释 | 会触碰的 Word/OOXML 面进入预检、执行、报告和修复 | UI 说支持，实际破坏域、修订、内容控件、固定版位 |
| 证据可追溯 | request-cell、fixture、artifact、report、repair route、test、release gate 接通 | 只有文档规划，没有可跑证据 |
| 边界可承认 | 专业判断、OCR/PDF/LaTeX、AI 内容、外部规则更新有 plugin/manual gate | 核心静默承诺自己做不到的事 |

因此，V26 的主张是：

```text
顶层 pack 稳定，子场景 family 扩充，能力槽位补深，边界门显性化。
```

## 5. 不新增顶层入口的裁决规则

新增场景入口必须同时满足以下四个条件：

1. 用户心智长期稳定，且不是已有 pack 的自然子场景；
2. 输入事实源、交付版本、OOXML 风险面至少两项与现有 pack 明显不同；
3. 需要独立的 schema/profile/preset/report/repair 组合；
4. 已有 request-cell、fixture、测试和 release gate 计划。

否则：

| 请求类型 | 落点 |
| --- | --- |
| 新行业名但只是套模板 | `quick_formatting` + template |
| 新学校/期刊/招采规则 | 对应 pack + rule source profile |
| 新资料字段 | material schema |
| 新输出版本 | DeliveryPreset |
| 新固定版位 | `batch_forms` / fixed-layout profile |
| 新专业判断 | plugin/manual gate |
| 新导入格式 | `import_ai_boundary` + confidence report |

这条规则用于防止“入口越多越完整”的错觉。

## 8. 两份外部技术记录的吸收结论

### 8.1 Count Engine 记录

需要吸收：

- 计数不是单一函数，而是 `Profile-driven Multi-metric Count Engine`；
- 中文论文、英文期刊、项目申报、试卷等都需要 profile 驱动的口径；
- 计数结果必须并列展示多口径指标，而不是只给一个数字；
- report 必须说明计入口径、排除范围、不确定项和人工确认项；
- profile 决定学校/期刊/文档类型规则，不能硬编码成一个全局算法。

进入矩阵的位置：

| 位置 | 结论 |
| --- | --- |
| `count_profile` 槽位 | 必须支持多口径、范围、规则来源 |
| `rule_source` 槽位 | 学校/期刊/申报规则必须可追溯 |
| `report_issue_artifact` 槽位 | 报告要解释采用何种口径 |
| `chinese_academic` / `english_journal` / `application_reports` | P1/P0 L5 缺口 |

不直接吸收：

- 不照搬外部模块目录；
- 不把尚未验证的 LaTeX/Pandoc 提取当作当前已实现；
- 不承诺与 Word、学校系统、投稿系统统计结果完全一致。

### 8.2 Exam Generator 记录

需要吸收：

- AI 不直接生成 Word，结构化 JSON 是机器事实源；
- Markdown 是人工预览，不是最终排版事实；
- Word 母版和渲染配置负责正式输出；
- 学生版、教师版、答案版、解析版不应重新生成不同内容，而应由同一题源通过 content visibility / delivery preset 控制；
- 通用图片上传、预览、替换、尺寸和题号绑定优先于复杂几何图自动生成；
- 复杂几何、AI 生图、学科图形应作为 plugin/manual gate 或后期插件。

进入矩阵的位置：

| 位置 | 结论 |
| --- | --- |
| `exam_education` | 结构化题库 schema、内容显隐、多版本输出是一等能力 |
| `delivery_preset` | student/teacher/answer/analysis/answer_sheet 应成为 preset |
| `material_schema` | 题目、答案、解析、图片资产要有 schema |
| `plugin_boundary` | 复杂几何图、AI 内容质量、学科图形插件化 |

不直接吸收：

- 不把 `docxtpl` 选型直接写成当前项目事实；
- 不把复杂几何图自动生成纳入核心 L5；
- 不让 AI 生成的 Markdown 成为最终 Word 排版依据。

## 9. OOXML 风险反推全集

高频场景是否完整，必须从 Word 包结构反推。

| OOXML 面 | 高频触发 | 必须进入的矩阵槽位 |
| --- | --- | --- |
| `w:styles` / `w:pPr` / `w:rPr` | 全部排版、论文、公文、技术、合同 | template baseline、control contract、repair route |
| `w:numbering` | 标题编号、合同条款、技术章节、公文层级 | numbering strategy、strict mode、report |
| `w:sectPr` / headers / footers | 论文、公文、合同签署稿、归档版 | template + delivery preset |
| `w:tbl` / `w:trHeight` | 表单、证书、答题卡、报价表 | fixed-layout profile，不回普通 table |
| `w:fldSimple` / `w:instrText` | TOC、页码、交叉引用、合同字段 | object preflight、field refresh、report |
| `w:ins` / `w:del` / comments | 合同审阅、期刊返修、技术评审 | review/compare preset、object preflight |
| `w:sdt` | 表单、合同、HR、资料包 | material schema、placeholder residue |
| drawing / textbox | 试卷、签章、产品资料、技术图 | image asset、figure binding、plugin boundary |
| OLE / VBA / embedded workbook | 报价、技术、导入 | block/warn/skip policy |
| hidden text | 盲审、答案版、审阅版、披露资料 | content visibility、delivery report |
| relationships / hyperlinks | 附件包、引用、图片、外链 | artifact manifest、link audit |
| footnotes / endnotes / bibliography | 学术、期刊、政策、专利 | reference profile、rule source |

判断规则：如果一个 pack 的高频工作会触碰某个 OOXML 面，但 UI、执行、报告或测试任一层没有策略，则该 pack 不能升 L5。

## 10. 控件一致性准入

场景配置中的控件必须继承模板管理中的同名控件语言。

| 控件/参数 | 场景要求 | 不合格表现 |
| --- | --- | --- |
| 左/右缩进 | 同行布局、同单位、同 stepper、同禁用说明 | 场景里拆行、换单位、名称不一致 |
| 特殊缩进 | 可交互切换无/首行/悬挂，值输入随类型启禁 | 只能显示，不能切换 |
| 行距类型/行距值 | 类型和值耦合，固定值/倍数语义清楚 | 类型和值互相脱节 |
| 段前/段后 | 同行展示、同单位、同命名 | 场景里叫“前距/后距”而模板叫“段前/段后” |
| 固定行高 | 只在 fixed-layout profile 出现 | 普通 TableConfig 暗藏 `row_height_pt` |
| 输出版本 | 用 DeliveryPreset，不用散落 checkbox | final/review/signing/archive 无法解释 |
| 水印 | 状态/版本归 scene/delivery，外观归 template/control contract | 水印文本、视觉、版本混成一个开关 |
| 公式 | 转换策略归 scene，视觉基线归 template，复杂转换归 plugin | 把完整 LaTeX/OCR 当普通公式样式 |
| 资料 schema | registry combo + 字段/图片/附件摘要 | 自由文本输入 schema id |
| plugin/manual gate | 必须可见、可确认、可进入 report | 高风险能力只有后台日志 |

控件一致性不是视觉洁癖，而是防止同一个参数在模板、场景、执行三层被解释成三件事。

## 11. 高频歧义裁决表

| 用户说法 | 先判定 | 裁决 |
| --- | --- | --- |
| 产品手册 | 技术操作手册还是客户/售前资料 | 技术进 `technical_long_docs`，客户/售前进 `application_reports` |
| 报价方案 | 正文方案还是金额/预算/财务判断 | 正文进 `application_reports`，金额正确性进 `professional_disclosure` |
| 证书材料 | 投标资质附件还是批量套打证书 | 资质进 `bidding_materials`，套打进 `batch_forms` |
| 双语文档 | 普通排版还是术语/翻译质量审阅 | 普通进 `quick_formatting`，质量进 `professional_disclosure` |
| PDF 论文 | 导入来源还是目标论文场景 | 先 `import_ai_boundary`，再 handoff 到学术/期刊 |
| 答题卡 | 试卷交付版本还是普通表单 | 优先 `exam_education`，fixed-layout 复用 `batch_forms` 能力 |
| 会议材料 | 行政会议纪要还是普通总结汇报 | 行政进 `official_policy`，普通进 `quick_formatting`/`application_reports` |
| 简历/个人陈述 | 只是格式还是求职内容质量 | 格式进 `quick_formatting`，内容质量不承诺 |
| 法律/医疗/专利 | 格式归档还是专业判断 | 格式可做，判断必须 plugin/manual gate |
| 完整 LaTeX | 公式片段还是完整项目转换 | 片段可进公式策略，完整项目进 `import_ai_boundary` |

裁决顺序固定为：

```text
专业/导入边界
-> 输入事实源
-> 输出版本
-> Word 风险
-> 业务 family
-> 模板样式覆盖
```

## 12. L5 准入检查表

一个 pack/family 要升 L5，至少要回答以下问题：

1. 高频 request-cell 是否覆盖正例、歧义例和反例？
2. 是否还有 pack proxy 或 family proxy？
3. 是否有 per-scene 和全局 request-cell 浏览？
4. 是否可从 request-cell 打开 DOCX fixture？
5. 是否可从 request-cell 打开 report artifact 段落？
6. 是否有真实业务模板 fixture 或脱敏样本计划？
7. material schema 是否可选择、解释、校验和修复？
8. CountProfile 是否解释多口径、范围和规则来源？
9. DeliveryPreset 是否覆盖业务版本？
