# 工作模式、方案、模板、母版落盘审阅

本文承接此前关于“论文版 / 试卷版 / 公文版由顶部切换，原场景配置下沉为方案配置”的讨论，只做审阅与规划记录，不直接执行清理或迁移。

## 1. 当前产品语义应如何稳定

新的信息架构应固定为四层：

```text
工作模式 mode
  决定用户当前在论文版、试卷版、公文版、标书版、技术文档版、报告版还是通用版。
  顶部下拉负责这个选择。

方案 plan
  原“场景”在 UI 上改名后的业务装配方案。
  只在当前工作模式内选择，例如试卷版只看默认试卷、随堂测验、期中期末；公文版只看公文排版、函件方案、纪要方案。

模板 template
  负责格式参数、样式、页面、标题、表格、页眉页脚等排版规则。
  也应按工作模式隔离，例如试卷版模板不进入公文版，公文版模板不进入论文版。

母版 master
  负责有占位符的 DOCX 壳，尤其是试卷装配页、公文红头/版记等固定版面。
  母版不等于模板；母版是装配壳，模板是格式参数。
```

因此，后续 UI 命名应保持：

```text
顶部：试卷版 / 公文版 / 论文版 / 标书版 ...
方案配置页：当前方案、方案预览、方案规则、资料包填充
模板管理页：当前模板、页面设置、正文排版、标题编号 ...
母版/方案预览面板：显示当前方案绑定或可用的母版壳
```

“场景”这个词应逐步退出用户可见层，只保留在历史代码类名、模型字段或兼容层中。

## 2. 当前目录结构事实

当前已经存在新配置库三分层：

```text
config_library/plans/<mode>/{builtin,user}/
config_library/templates/<mode>/{builtin,user}/
config_library/masters/<mode>/{builtin,user}/
```

其中 plans 和 templates 的模式目录已经较完整：

```text
plans:
  bidding, custom, exam, official, report, technical, thesis

templates:
  bidding, custom, exam, official, report, technical, thesis

masters:
  exam, official
```

这说明“不同工作模式各自独立方案和模板”的方向已经落地到目录层。

但是母版层还处在迁移中间态：

```text
config_library/masters/official/builtin/
  official_gbt_standard.docx
  official_gbt_standard.master.json

config_library/masters/exam/builtin/
  default_exam.master.json

exam_masters/builtin/
  default_exam_v20.docx 等真实试卷母版 DOCX

exam_masters/user/
  大量 user_default_exam_copy_N.docx 用户副本残留
```

也就是说，公文母版已经基本采用新目录，试卷母版目前只有 manifest 进入 `config_library/masters/exam`，真实 DOCX 仍在旧的 `exam_masters` 根目录。

## 3. 方案和模板是否已经互相独立

结论：方案和模板的“新保存目录”已经按工作模式隔离，但仍有兼容读取和模型遗留字段，需要后续收口。

### 已完成的部分

`src/config/library.py` 明确将配置库定义为：

```text
config_library/plans/<mode>/{builtin,user}/
config_library/templates/<mode>/{builtin,user}/
```

并且新保存入口使用：

```text
scene_user_dir(mode_id)    -> config_library/plans/<mode>/user
template_user_dir(mode_id) -> config_library/templates/<mode>/user
```

这满足“论文版、试卷版、公文版之间的方案和模板不互相污染”的核心要求。

### 仍需注意的部分

旧目录仍可读取：

```text
scenes/
templates/
```

这是为了兼容旧版本配置，不是最终用户新增配置的目标目录。后续执行时要检查：

```text
新建方案、创建副本、重命名、保存方案
  必须写入 config_library/plans/<当前工作模式>/user

新建模板、创建副本、重命名、保存模板
  必须写入 config_library/templates/<当前工作模式>/user

旧 scenes/、templates/
  只能作为 legacy fallback 读取
  不应继续作为新增配置写入目标
```

另外，很多非试卷方案 JSON 仍带有 `exam_paper.blank_style_id`、`custom_blank_styles` 等字段。这是 `SceneWorkspace` 序列化的历史遗留，不代表论文/公文会显示试卷母版。短期可接受，条件是所有 UI 入口和执行入口都按 `mode_id` 过滤；长期应考虑按模式裁剪保存结构，避免误读。

## 4. 内置方案现状

试卷版已经有 3 个内置方案：

```text
config_library/plans/exam/builtin/exam.json       -> 默认试卷
config_library/plans/exam/builtin/exam_quiz.json  -> 随堂测验
config_library/plans/exam/builtin/exam_term.json  -> 期中期末
```

公文版已经有 3 个内置方案：

```text
config_library/plans/official/builtin/official.json         -> 公文排版，default_material_profile_id=official:notice
config_library/plans/official/builtin/official_letter.json  -> 函件方案，default_material_profile_id=official:letter
config_library/plans/official/builtin/official_minutes.json -> 纪要方案，default_material_profile_id=official:minutes
```

这直接支持此前产品判断：

```text
不是为十几种公文文种各建一个顶部场景。
顶部只选“公文版”。
公文版内部用方案、profile、资料 schema 和交付策略处理文种差异。
```

后续 UI 中所有“方案”下拉，都应从当前工作模式的 `plan_selector_options(mode_id)` 或同等数据源取得选项。不能再把文种 profile、母版 id 或旧 scene 文案混在同一个“方案”下拉里。

## 5. 为什么 exam_masters/user 有 202 个文件

当前 `exam_masters/user` 下存在大量文件：

```text
user_default_exam_copy.docx
user_default_exam_copy_2.docx
...
user_default_exam_copy_N.docx
```

原因不是 config_library 复制出错，而是历史试卷母版链路仍以 `exam_masters` 为真实文件池：

```text
src/shared/engine/exam_paper_style.py
  EXAM_MASTER_ROOT = PROJECT_ROOT / "exam_masters"
  BUILTIN_EXAM_MASTER_DIR = EXAM_MASTER_ROOT / "builtin"
  USER_EXAM_MASTER_DIR = EXAM_MASTER_ROOT / "user"
```

创建试卷母版副本时：

```text
create_exam_blank_master_copy()
  -> create_exam_blank_style_copy()
  -> copy2(source_path, exam_masters/user/<style_id>.docx)
  -> style.master_docx_path 指向该 DOCX
```

导入试卷母版时：

```text
import_exam_blank_master_docx()
  -> copy2(source_docx, exam_masters/user/<style_id>.docx)
  -> style.master_docx_path 指向该 DOCX
```

所以这些文件主要是之前测试、调试、手动反复点击“创建副本”时积累的用户母版文件池残留。

## 6. 这些残留会不会进入产品

短期判断：不会全部自动进入选择框，但会造成目录噪音和迁移风险。

当前自动发现函数有保护：

```text
sync_user_exam_blank_master_files()
  会扫描用户目录
  但会跳过 user_default_exam_copy* 和 user_imported_exam* 这类程序生成名前缀
```

因此，`exam_masters/user` 中 202 个 `user_default_exam_copy_N.docx` 不会因为扫描目录而全部进入方案下拉或母版下拉。

真正会进入 UI 的，是当前方案的：

```text
scene.exam_paper.custom_blank_styles
```

如果某个方案 JSON 里引用了某个副本，它就会显示；如果没有引用，它只是孤立残留。

但是风险仍然存在：

```text
1. 打开母版文件夹时用户会看到大量无意义副本。
2. 若将来改扫描策略，残留可能重新污染列表。
3. 旧目录和新 config_library/masters 并存，会让“母版到底存在哪里”变得不透明。
4. 清理时不能直接删除，因为其中可能有某个用户方案仍在引用。
```

## 7. 正确的迁移方向

不要第一刀删除 `exam_masters/user`。正确顺序应是：

```text
第一步：建立引用审计
  扫描 config_library/plans/exam/{builtin,user}
  扫描 legacy scenes/
  收集所有 exam_paper.custom_blank_styles.master_docx_path
  标记 referenced / unreferenced / invalid

第二步：建立新试卷母版物理目录
  config_library/masters/exam/builtin/
    default_exam.docx
    class_quiz_exam.docx
    term_exam.docx
    *.master.json

  config_library/masters/exam/user/
    用户副本 DOCX
    用户副本 master.json

第三步：修改写入入口
  创建副本、导入母版不再写 exam_masters/user
  改写 config_library/masters/exam/user
  SceneWorkspace 只保存 master_id 或 qualified_id
  不把裸 DOCX 路径塞回方案字段作为长期事实源

第四步：保留只读兼容
  旧 exam_masters/builtin 和 exam_masters/user 只作为 legacy resolve fallback
  已被引用的旧文件可继续打开和装配
  新创建文件不再落旧目录

第五步：提供清理报告，不自动删除
  输出可删除候选列表
  默认只显示建议，不直接删
  用户确认后再归档或删除 unreferenced program_copy_unreferenced
```

这样能避免功能丢失，也能解释为什么现在文件夹里看起来“很脏”。

## 8. 公文版后续规划边界

公文版比试卷复杂，但不应该变成十几套文件种子同时堆积。当前更合理的分层是：

```text
official 工作模式
  plans:
    official         -> 通用公文 / 通知类默认
    official_letter  -> 函件方案
    official_minutes -> 纪要方案

  profiles:
    notice, letter, minutes, report, request, approval 等文种 profile

  material schemas:
    official_document_v1
    administrative_meeting_fields_v1

  masters:
    official_gbt_standard 先作为共享母版
```

是否拆出：

```text
official_letter_standard
official_minutes_standard
```

应由真实样张、视觉基准和差异报告决定，不能因为国标文种多就直接创建十几份 DOCX 种子。

当前已经有公文多交付、样张基准门、母版族拆分决策报告、资料包 JSON 服务。下一步如果执行，应优先补：

```text
1. 公文资料包填充 UI 的导入 / 导出 JSON。
2. 方案下拉和顶部工作模式完全对齐，所有“方案”均选当前模式内置/用户方案。
3. 公文样张基准入库后，再决定是否拆母版族。
```

## 10. 执行验收标准

后续真正修改时，验收不能只看 UI 文案，应按以下标准：

```text
1. 顶部切到试卷版
   方案下拉只出现默认试卷、随堂测验、期中期末和试卷用户方案。
   模板下拉只出现试卷模板。
   母版选择只出现试卷母版。

2. 顶部切到公文版
   方案下拉只出现公文排版、函件方案、纪要方案和公文用户方案。
   模板下拉只出现公文模板。
   母版选择只出现 official_gbt_standard 或后续公文母版族。

3. 顶部切到论文版 / 标书版
   不显示试卷母版或公文母版。
   若该模式暂无母版族，应明确显示“暂无登记母版”，不能 fallback。

4. 新建或复制方案
   文件落在 config_library/plans/<当前模式>/user。

5. 新建或复制模板
   文件落在 config_library/templates/<当前模式>/user。

6. 新建或导入母版
   新实现后应落在 config_library/masters/<当前模式>/user。
   迁移前试卷仍可能落 exam_masters/user，但必须在文案和规划中标为 legacy。

7. 残留治理
   先生成 inventory/report。
   不做无引用证明前，不删除用户 DOCX。
```

## 13. 继续审阅：顶部工作模式、方案、模板、母版池的真实边界

本轮不继续急着改 UI，先把当前代码事实和用户看到的错位感拆清楚。

### 13.1 当前四层对象

```text
工作模式 mode
  用户顶部选择：通用版、试卷版、论文版、标书版、公文版等。
  责任：限定当前用户进入哪一套业务域。
  文件夹隔离：不直接保存业务配置，但决定下面三类配置从哪个 mode 文件夹读取。

处理方案 plan
  代码仍叫 SceneWorkspace / scene，这是历史模型名。
  用户可见应叫“方案”或更明确叫“处理方案”。
  责任：定义本次任务怎么做，包括处理范围、资料包、交付结果、默认模板、默认卷面/公文版式。
  文件夹：config_library/plans/<mode>/{builtin,user}/

格式模板 template
  用户可见叫“模板”仍然合理。
  责任：定义字体、页边距、标题、目录、题注、页眉页脚等格式基线。
  文件夹：config_library/templates/<mode>/{builtin,user}/

母版 shell / master
  用户最终不一定叫“母版”，但工程上它是带占位符的 DOCX 外壳。
  责任：定义试卷卷面、公文红头/版记等可装配结构。
  文件夹目标：config_library/masters/<mode>/{builtin,user}/
  当前兼容：试卷内置 DOCX 仍包在 exam_masters/builtin；试卷旧用户池是 exam_masters/user。
```

这个边界意味着：顶部选的是 `mode`，快速执行里的“方案”选的是 `plan`，模板选的是 `template`，方案预览里真正选择的是 `master/shell`。如果三处都叫“方案”，用户一定会觉得两个下拉内容对不上。

### 13.2 为什么两个选框内容看起来不对应

用户截图里的错位，本质不是一个单点 bug，而是命名和对象层级叠在一起了：

```text
快速执行 / 方案与模板
  方案下拉：应选择当前工作模式内置/用户 plan。
  例：试卷版下应是 默认试卷、随堂测验、期中期末，以及用户保存的试卷方案。

方案配置 / 方案预览
  当前实现里的第一个下拉实际选择 exam blank master，也就是试卷 DOCX 外壳。
  例：默认试卷、随堂测验、期中期末三项也会出现，但它们是母版/卷面壳，不是 plan 文件。
```

所以“内容明明没对应上”的根因是：`plan` 和 `master` 现在共用了过于相似的中文显示名。短期不建议把这两者强行合并，因为它们落盘、作用范围和生命周期都不同。更稳的做法是改显示语法：

```text
顶部：工作模式
  试卷版 / 公文版 / 论文版 / 标书版

快速执行：处理方案 + 格式模板
  处理方案：默认试卷方案 / 随堂测验方案 / 期中期末方案
  格式模板：默认格式 / GB/T 公文格式 / 论文国标格式

方案配置里的预览入口
  一级卡片：方案预览
  具体选择项：卷面方案 / 公文版式方案 / 装配版式
```

如果仍然把 master 的 selector 标签写成“方案”，就会和快速执行里的 plan 发生正面冲突。推荐 UI 口径是：

```text
通用名：版式方案
试卷域：卷面方案
公文域：公文版式
工程名：master
```

这样既不直接暴露“母版”，也不和“处理方案”混。

### 13.3 当前文件夹隔离状态

从当前工作区看，方案和模板已经基本按工作模式隔离：

```text
config_library/plans/
```

### 13.4 为什么 exam_masters/user 会有 202 个残留

### 13.5 会不会进入产品列表

## 17. 继续审阅：顶部工作模式接管后的真实分层边界

### 17.1 正确的四层对象

当前最稳的边界应固定为：

```text

  用户在标题栏选择：通用版 / 论文版 / 试卷版 / 公文版 / 标书版 ...
  责任：决定当前可见的方案、模板、版式/卷面、资料包 schema 和默认入口。
  代码对象：WorkModeSpec。
  不应保存为用户可编辑的方案文件。

处理方案 plan
  用户在快速执行或方案配置中选择。
  责任：定义这类任务怎么处理，包括输入范围、资料包要求、交付结果、默认模板、默认卷面/公文版式。

  落盘目录：config_library/plans/<mode>/{builtin,user}/。

格式模板 template
  用户在模板页或快速执行中选择。

  落盘目录：config_library/templates/<mode>/{builtin,user}/。

  用户不一定看到“母版”这个词。
```

```text
  term_exam        -> 期中期末
```

这不是同一个对象。处理方案落在 `plans/exam/builtin/*.json`，卷面方案来自 `BUILTIN_EXAM_BLANK_STYLE_IDS` 和 `MasterSpec` 包装。

但是用户看到时会有强烈疑问：一个地方叫“默认试卷”，另一个地方也叫“默认试卷”，到底是不是同一组选项？所以后续 UI 必须做两件事：

```text

  option 显示为“默认试卷方案 / 随堂测验方案 / 期中期末方案”

  label 固定为“卷面方案”
  option 显示为“默认卷面 / 随堂测验卷面 / 期中期末卷面”
  或继续保留用户自定义原名，但内置项必须拉开语义。
```

更重要的是绑定关系要明确：

```text
exam plan       默认绑定 exam_paper.blank_style_id = default_exam
exam_quiz plan  默认绑定 exam_paper.blank_style_id = class_quiz_exam
exam_term plan  默认绑定 exam_paper.blank_style_id = term_exam
```

### 17.5 公文版后续不能靠堆十几份种子解决

```text

  official_letter    函件方案

  official:notice
  official:letter
  official:minutes
  official:report
  official:request
  official:approval
  ...

再拆资料包 schema：
  official_document_v1
  administrative_meeting_fields_v1
  后续按字段差异增加 schema，而不是按文种无脑复制 DOCX。

最后才拆公文版式：
  official_gbt_standard 先作为共享 GB/T 9704 版式壳。

```

也就是说，公文复杂度优先由 `plan + profile + material schema` 承接，`master` 只承接真实版式差异。这样可以避免“十几种文种 = 十几份 DOCX 种子”的膨胀。

### 20.4 为什么截图中的两处内容没对应上

截图里快速执行下拉和方案预览下拉看起来没对应上，根因有两层。

第一层是语义层：

```text
快速执行下拉：应该是处理方案。
方案预览下拉：当前实际是卷面方案。

它们天然不是同一个对象。默认试卷方案默认绑定默认卷面，随堂测验方案默认绑定随堂测验卷面，期中期末方案默认绑定期中期末卷面；但用户也可以在某个处理方案内手动换卷面。
```

第二层是实现/状态层：

```text
当前仓库里 plan_selector_options("exam") 已能返回 3 项。
如果运行界面中快速执行只显示 1 项，则不是目录缺文件，而是 UI 实例状态或刷新链路没有进入 exam mode scoped descriptors。
```

因此下一步修复时不能把“方案预览下拉”强行改成 plan 下拉。更稳的修法是：

```text
1. 快速执行和方案配置的“当前处理方案”都从 plan_selector_options(mode_id) 取值。
2. 方案预览内部保留卷面/版式 master 下拉。
3. 当用户切换处理方案时，加载该 plan 自己绑定的默认 blank_style_id / master contract。
4. 当用户只改卷面/版式时，只改当前 plan 内部的 master 引用，不切换 plan 本身。
```

### 20.5 正确的试卷交互链路

以试卷版为基准，正确链路应该是：

```text
顶部切换：试卷版
  -> mode_id = exam

快速执行：处理方案
  -> options = exam / exam_quiz / exam_term
  -> 用户选 exam_quiz
  -> load_scene_from_library("exam_quiz", mode_id="exam")
  -> 当前 scene.exam_paper.blank_style_id = class_quiz_exam

快速执行：模板
  -> options = templates/exam/builtin/default.json
  -> load_template_from_library("default", mode_id="exam")

方案配置：方案预览
  -> 显示当前处理方案绑定的卷面 class_quiz_exam
  -> 卷面下拉 options = default_exam / class_quiz_exam / term_exam / 用户卷面副本
  -> 手动改卷面只更新当前 scene.exam_paper.blank_style_id
```

这个链路能解释“为什么两个下拉内容相似但不该完全合并”：处理方案是一个业务预设，卷面方案是这个业务预设里的一项版式壳参数。

### 20.6 正确的公文交互链路

公文版也同理，但公文的复杂度不应由十几份 DOCX 种子直接承接：

```text
顶部切换：公文版
  -> mode_id = official

  -> options = official / official_letter / official_minutes
  -> 用户选 official_letter
```

```text
  它不是“工作场景”了，而是当前工作模式下的一套处理策略：
  处理范围、模块开关、资料包 profile、生成结果、默认模板、默认卷面/版式。

模板 Template
  格式基线。
  负责页面、正文、标题、表格、页眉页脚、目录、题注等格式参数。

装配壳 Assembly Shell
  对试卷显示为“卷面”，对公文显示为“版式”。
  不建议通用显示为“母版”，避免和模板混。
  它负责 DOCX 占位符、版心外框、密封线、公文红头/版记等可装配结构。

资料包 Material Pack / Profile
  负责本次或本类文档需要填入的数据字段。
  公文的通知、函、纪要等优先走 profile/schema，而不是一文种一文件种子。
```

### 24.3 现在最容易误解的地方

误解一：处理方案下拉和方案预览下拉长得太像。

```text
快速执行 / 方案与模板：
  方案下拉 = 处理方案。
  例如试卷版：默认试卷、随堂测验、期中期末。
  例如公文版：公文-默认、函件方案、纪要方案。

方案配置 / 方案预览：
  试卷里下拉 = 卷面。
  公文里下拉 = 版式。
  它不是处理方案。
```

如果处理方案和卷面都叫“默认试卷 / 随堂测验 / 期中期末”，用户会自然认为两处内容应该一一对应。这里不是数据错误，而是命名设计容易撞车。建议后续把卷面命名改得更像“壳”，例如：

```text
处理方案：
  默认试卷
  随堂测验
  期中期末

卷面：
  A4 标准卷面
  短测紧凑卷面
  期末完整卷面
```

这样用户就能理解：处理方案决定“怎么处理”，卷面决定“套哪张卷壳”。

误解二：方案预览这个名字有两层含义。

```text
一级导航的“方案预览”：
  是装配壳入口。
  试卷显示卷面，公文显示版式。

右侧内容卡片的“方案预览”：
  如果里面还出现卷面/版式下拉，应明确卡片标题或字段标题：
  试卷卷面
  公文版式
```

建议不要再出现“母版管理”作为一级产品词。底层 diagnostics、manifest、测试名里保留 master 没问题；用户界面应该按工作模式翻译为卷面/版式/装配壳。

误解三：公文国标有十几种文种，不等于要十几份文件种子。

现有代码已经有 `official_document_profiles.py`，里面覆盖决议、决定、命令、公报、公告、通告、意见、通知、通报、报告、请示、批复、议案、函、纪要等 profile。正确路径是：

```text
文种差异：
  优先进入 profile / material schema / field binding。

处理路径差异：
  才进入 plan。
  例如：函件方案、纪要方案。

版式结构确实不同：
  才拆 official master。
  需要样张视觉证据和占位符契约证据后再拆。
```

所以公文不应该第一刀就做十几份 DOCX 种子。当前 `official / official_letter / official_minutes` 三个 plan 作为起点是合理的。

### 27.5 公文为什么不应马上拆成十几份 DOCX

```text

3. 字段是否需要填写。
4. 正文和尾部区块显隐。
5. runtime 装配逻辑。
```

还没有证据证明它们都需要独立 DOCX 版式壳。更稳妥的判断标准是：

```text
先共用 GB/T 9704 通用公文版式；

当样张视觉验收证明某类文种的红头、版记、会议字段、附件结构或签发区结构不能由 profile 控制时，再拆独立版式。
```

因此 P4 的正确顺序仍是：

```text
1. 先补全公文文种 profile。
2. 再补资料包 schema 与字段绑定。
3. 再跑样张视觉基准。
4. 最后决定是否拆出函件版式、纪要版式等独立 DOCX。
```

## 30. 深度分析：顶部工作模式接管后，方案/模板/卷面版式的正确边界

本轮继续按“先分析、写入文档，不急着执行”的节奏复核。核心问题是：顶部 `论文版/试卷版/公文版/...` 已经承担“工作模式”选择，原来的“场景”产品概念已经改成“方案”，因此不能再把 `场景 = 方案 = 模板 = 母版` 混在一起。

### 30.1 当前应采用的四层模型

```text
工作模式 WorkMode
  产品入口：论文版 / 试卷版 / 公文版 / 标书版 / 技术文档版 / 报告版
  负责选择命名空间、默认方案、默认模板、默认卷面/版式域。

方案 Plan
  原 SceneWorkspace 的产品化名字。
  负责处理流程、资料要求、执行规则、交付结果、默认卷面/版式引用。
  落盘在 config_library/plans/<mode>/{builtin,user}/。

模板 Template
  普通格式模板 / 样式基线。
  负责页面设置、正文排版、标题编号、表格、页眉页脚等通用格式规则。
  落盘在 config_library/templates/<mode>/{builtin,user}/。

装配壳 Shell
  内部仍可能叫 master，但产品上不能再统一叫“母版”。
  试卷版叫“卷面”，公文版叫“版式”，未定义模式暂叫“装配项/装配契约”。
  落盘在 config_library/masters/<mode>/{builtin,user}/；历史兼容文件池另行处理。
```

这四层之间的关系应是：

```text
工作模式控制候选集合
方案选择当前处理策略
模板提供通用格式基线
卷面/版式提供文种或试卷装配壳
```

也就是说，顶部工作模式切到“试卷版”后：

```text
方案下拉只能看试卷方案：默认试卷 / 随堂测验 / 期中期末
模板下拉只能看试卷模板：默认格式
卷面下拉只能看试卷卷面：A4 标准卷面 / 短测紧凑卷面 / 期末完整卷面 / 用户卷面
```

顶部工作模式切到“公文版”后：

```text
方案下拉只能看公文方案：公文-默认 / 函件方案 / 纪要方案
模板下拉只能看公文模板：GB/T 9704 公文格式 / 自定义公文模板
版式下拉只能看公文版式：GB/T 9704 通用公文版式 / 后续用户版式
```

### 30.5 公文版不应一次性堆十几份 DOCX 种子

公文国标文种多，但“文种多”不等于“必须立刻有十几份 Word 种子”。当前比较稳的策略是：

```text

  15 个文种：决议、决定、命令、公报、公告、通告、意见、通知、通报、报告、请示、批复、议案、函、纪要。

第二层：资料契约
  通用公文字段 official_document_v1。
  纪要等会议类额外叠加 administrative_meeting_fields_v1。

第三层：共享版式
  先用 official_gbt_standard 覆盖 GB/T 9704 通用结构。

第四层：视觉样张决策
  对通知 / 函 / 纪要等代表文种生成样张。
  若共享版式视觉基线通过，则继续共享。
  若某类文种反复出现稳定差异，再拆分专用版式，例如 official_letter_standard、official_minutes_standard。
```

也就是说，公文的优先级不是“建很多文件”，而是先把下面这条链路闭环：

```text
方案 default_material_profile_id
  -> 文种 profile
  -> 资料 schema
  -> 字段到占位符绑定
  -> 公文版式 placeholder_contract
  -> 样张验证
  -> 是否拆分版式的证据
```

## 36. 继续审阅：顶部工作模式接管后，为什么会出现“旧池很多文件”和“两个选择框不对应”

本轮按“继续深度分析，不急着执行”的要求，只更新文档判断，不改业务代码、不移动旧文件池。

### 36.1 先把三个选择框的职责重新钉死

当前产品层次应按下面理解：

```text
顶部工作模式：
  选择命名空间。
  例：通用版 / 论文版 / 试卷版 / 公文版 / 标书版 / 技术文档版 / 报告版。
  它决定后续能看到哪些方案、模板、卷面/版式、资料 schema。

处理方案：
  原“场景”降级后的业务对象。
  回答“这次任务怎么处理”。
  例：试卷版里的 默认试卷方案 / 随堂测验方案 / 期中期末方案；
      公文版里的 公文排版 / 函件方案 / 纪要方案。
  落盘：config_library/plans/<mode>/{builtin,user}/。

格式模板：
  回答“基础格式参数是什么”。
  例：试卷默认格式、公文 GB/T 9704 格式、论文国标格式。
  落盘：config_library/templates/<mode>/{builtin,user}/。

装配壳：
  内部仍可叫 master，但用户界面不要泛称“母版”。
  试卷版叫“卷面”，公文版叫“版式”。
  回答“生成的 Word 用哪张壳承载内容”。
  目标落盘：config_library/masters/<mode>/{builtin,user}/。
```

因此截图里“快速执行里的方案”和“方案预览里的下拉内容不对应”，不是一个简单文案错误，而是两个对象本来就不同：

```text
快速执行：处理方案
  选的是 plan。

方案预览：卷面/版式
  选的是 shell/master。
```

如果两处都叫“方案”，用户会自然期待二者选项完全一致；但工程上它们不能完全一致。更稳的 UI 口径是：

```text
快速执行卡片：
  处理方案
  格式模板

试卷方案配置：
  方案预览
  卷面

公文方案配置：
  方案预览
  版式
```


### 36.3 为什么 exam_masters/user 会有 202 个文件

根因是历史试卷卷面链路曾长期把用户副本写到旧目录：

```text
legacy 用户卷面池：
  exam_masters/user

新 active 用户卷面池：
  config_library/masters/exam/user
```

当前代码里已经分出了两个常量：

```text
LEGACY_USER_EXAM_MASTER_DIR = exam_masters/user
USER_EXAM_MASTER_DIR        = config_library/masters/exam/user
```

并且 `create_exam_blank_master_copy()`、`import_exam_blank_master_docx()` 默认已经指向新的 `USER_EXAM_MASTER_DIR`。所以从现在的主路径看，新增或导入试卷卷面不应该继续写进 `exam_masters/user`。

那 202 个文件为什么还在？

```text
1. 它们是旧版本/旧阶段反复“创建副本”“导入卷面”留下的真实 DOCX。
2. 它们不是当前的内置卷面。
3. 它们不会因为存在于文件夹里就自动成为顶部工作模式、处理方案或卷面 selector 的选项。
4. 它们仍然会污染文件系统体验，因为用户手动打开旧目录时会看到大量副本。
```

这里要特别区分：

```text
不会进入产品 selector
  不代表可以直接删除。

可以作为 cleanup_candidate
  不代表已经获得用户确认。
```

此前 dry-run 已经证明当前扫描未发现方案引用这些旧文件，但真实移动仍会改变用户可见文件系统，所以仍必须等待用户明确确认。

### 36.4 为什么不是“把每个文件都变成内置方案”

这里最容易误判。`exam_masters/user` 里的 202 个 DOCX 是“卷面文件副本”，不是 plan JSON。

真正的试卷内置处理方案是：

```text
config_library/plans/exam/builtin/
  exam.json
  exam_quiz.json
  exam_term.json
```

真正的试卷内置卷面 manifest 是：

```text
config_library/masters/exam/builtin/
  default_exam.master.json
  class_quiz_exam.master.json
  term_exam.master.json
```

其中 `class_quiz_exam` 和 `term_exam` 目前还是通过 manifest + 参数差异复用同一个 `exam_masters/builtin/default_exam_v20.docx`。这属于兼容阶段的实现折中，不等于它们没有独立卷面概念；只是物理 DOCX 尚未拆成三份。

因此正确路线不是：

```text
把 exam_masters/user 的 202 个文件导入为 202 个方案。
```

而是：

```text
1. 保留 3 个内置处理方案。
2. 保留 3 个内置卷面 manifest。
3. 新用户卷面进入 config_library/masters/exam/user。
4. 旧 exam_masters/user 只作为 legacy fallback 和归档候选。
```

### 36.5 其他工作模式怎么办

其他模式不能照搬“试卷卷面”的模型。应该按是否需要固定 Word 装配壳来判断。

```text
论文版 thesis：
  目前更像格式模板驱动。
  先保持 plans/thesis + templates/thesis。
  暂不需要 masters/thesis。
  如果后续出现“学校封面页、原创声明页、授权页、固定签名页”这类占位符装配，再新增 masters/thesis。
  用户可见名不要叫母版，可叫“封面页/声明页/学校版式”。

公文版 official：
  已经需要装配壳。
  现阶段先用 official_gbt_standard 共享版式承接通知、请示、报告、批复、函、纪要等。
  文种差异优先由 plan + profile + material schema 表达。
  只有样张基准证明某类文种存在稳定视觉差异时，再拆 official_letter_standard、official_minutes_standard 等专用版式。

试卷版 exam：
  已经需要装配壳。
  用户词固定为“卷面”。
  新用户卷面必须进入 config_library/masters/exam/user。
  legacy exam_masters/user 等用户确认后再归档。

标书版 bidding：
  未来很可能需要装配壳，但现在不应抢先套“母版”。
  可以先把能力放在 plans/bidding + templates/bidding + materials/bidding。
  等封面、目录、商务册、技术册、资格审查等固定结构明确后，再设计 masters/bidding。
  用户可见词建议从“册式 / 装订版式 / 封面版式 / 分册结构”里选，不建议叫母版。

报告版 report / 技术文档 technical：
  当前以模板和处理规则为主。
  若未来出现固定封面、审批页、版本记录页、附录占位符，再建立 masters/<mode>。
```

### 36.6 当前仍需警惕的边界

从这次复核看，主线方向是对的，但还有几个边界要继续守：

```text
1. 所有 UI 主路径读取方案时必须传 mode_id。
   正确：list_scene_descriptors(mode_id=current_mode)

4. 未进入装配壳阶段的模式，不应 fallback 到 exam 或 official。
   正确：masters/thesis、masters/bidding 不存在时显示暂无登记装配项，或根本不显示该控件。
   错误：自动给论文版、标书版塞试卷卷面或公文版式。

5. 旧池归档只能在用户确认后执行。
   dry-run 可继续保留；真实移动必须单独确认。
```

### 36.7 本轮判断

```text

```

## 40. 执行记录：工作模式切换保存脏配置沿用原模式


## 42. 深度分析：顶部工作模式接管“场景”后的真实边界

本轮按“先审阅、先记录、不急着扩大执行”的口径继续看。核心判断是：

```text

原场景配置：改为方案配置
原场景对象：改为方案对象
模板管理：仍然是格式模板，不和方案、卷面/版式混用
卷面/版式/装配壳：按工作模式独立，不能再用一个全局母版池表达
```

这里最关键的变化不是改文案，而是对象归属改变了：

```text
过去：场景像一级业务入口，模板是它的附属格式。
现在：工作模式才是一级业务入口；方案、模板、卷面/版式都挂在工作模式下面。
```

### 42.1 当前代码已经接近的部分

已确认的结构：

```text

```

已经定义了顶层工作模式：

```text

official

report
```

每个工作模式带有：

```text

```

这说明顶部下拉不是单纯 UI 筛选器，而是产品层的工作模式切换器。

### 42.2 方案与模板的独立性

当前 `src/config/library.py` 的目标目录已经是正确方向：

```text

config_library/templates/<mode>/{builtin,user}/
```

对应 API 已经具备 mode scope：

```text

list_template_entries(mode_id=...)

save_template_to_library(..., mode_id=...)
```

因此，“论文版、试卷版、公文版之间的方案和模板应互相独立”这件事，目前在存储模型上已经基本成立。

仍然要守住的风险点是：

```text
1. UI 入口必须始终传 mode_id。
2. 测试、临时脚本、兼容 API 不能用不带 mode_id 的全局列表冒充当前工作模式列表。
3. legacy scenes/templates 只能作为兼容 fallback，不能重新成为主路径。
4. 自定义保存必须落到当前工作模式的 user 目录，而不是 custom 或旧 flat 目录。
```

这也是前面新增静态守门的意义：防止页面层回到不带 `mode_id` 的全局读取。

### 42.5 legacy 池的兼容边界

试卷卷面逻辑中仍保留 legacy fallback，主要用于两类情况：

```text

```

已有防泛滥措施：

```text

```

会跳过程序批量生成前缀：

```text

```

这能避免旧池 202 个程序副本全部涌入选择器。

但它仍会保留：

```text

2. 可能是用户手工放入的可识别文件。
```

这说明 legacy 池现在应该被看作“迁移兼容区”，而不是“当前产品资料库”。

### 42.6 公文版下一步不能照搬试卷

公文比试卷复杂，但不应该马上拆成十几份文件种子。更稳的结构是：

```text
工作模式：official 公文版
方案：official / official_letter / official_minutes / 后续扩展
模板：official_gbt / official_custom 等格式模板
版式：official_gbt_standard 等公文装配壳
资料包：按公文类型选择 profile/schema，再填字段
```

公文的“十几种类型”更适合先放在 profile/schema 层，而不是每一种都立刻做独立 DOCX 版式。

原因：

```text
1. 多数公文类型共享 GB/T 9704 的基本页面与版记规则。
2. 真正变化大的是字段、标题语气、主送/抄送/成文日期/印发机关等资料包字段。
3. 只有当某类公文的固定结构差异足够大时，才新增独立版式或版式族。
4. 先把十几类都做成 DOCX 种子，容易造成维护爆炸，也容易把“方案”和“版式”混起来。
```

因此公文建议分三步：

```text
P0：保留一个通用 GB/T 9704 版式，覆盖通知、请示、报告、批复、函、纪要等基础样张。
P1：把公文类型细分放进 official_document_profiles.py 和资料包 schema。
P2：当某类公文结构确实无法由通用版式承载时，再新增版式族。
```

### 45.1 当前正确模型

产品语义应按四层拆开：

```text
工作模式 mode：
  顶部切换。决定当前只看论文版、试卷版、公文版或标书版等资料域。

方案 plan：
  原“场景”的用户可见名称。表达本次做什么、走什么流程、用哪些资料字段、生成哪些交付。
  代码内部 SceneWorkspace / scene_id 暂时保留为兼容名，不做全局硬改。

模板 template：
  文档格式基线。论文、试卷、公文、标书应按 mode 独立候选。

卷面 / 版式 / 装配项 master：
  试卷叫“卷面”，公文叫“版式”。不要在 UI 上泛称母版，避免和模板混。
```

因此当前下拉关系应是：

```text
顶部 mode -> plan_selector_options(mode_id)
顶部 mode -> template_selector_options(mode_id)
顶部 mode -> master_selector_options(mode_id)
```

也就是：试卷版只能看到试卷方案、试卷模板、试卷卷面；公文版只能看到公文方案、公文模板、公文版式。

### 45.2 exam_masters/user 为什么会有 202 个文件

这不是新方案模型自然需要 202 个卷面，而是旧路径长期积累的结果。

审阅到的事实：

```text
exam_masters/user = 202 files, 9331760 bytes
config_library\masters\exam\user = 0 files (missing)
config_library\masters\official\user = 0 files (missing)
```

原因判断：

```text
1. 早期“创建副本 / 导入母版”把用户试卷 DOCX 都写进 exam_masters/user。
2. 文件名走 _unique_docx_path 递增，所以多次点击会形成 user_default_exam_copy_2.docx、_3.docx 等残留。
3. 旧目录是扁平池，没有按 mode / plan / source 分层。
4. 旧逻辑为了保护用户文件，不会自动删除历史副本。
```

结论：

```text
202 个文件是历史运行/测试/手动副本池，不代表新版产品要内置 202 个试卷种子。
新版内置试卷卷面仍应保持少量、可解释的 2-3 个，例如：
  - A4 标准卷面
  - 短测紧凑卷面
  - 期末完整卷面
```

## 48. 继续审阅：顶层工作模式接管后，“方案 / 模板 / 卷面版式 / 资料包”不能再混成一个对象

本轮继续按“先审阅、先记录、不急着执行”的方式复核。用户指出的核心问题不是单个文案错，而是顶层工作模式已经承担了过去“场景选择”的职责后，原来的 `SceneWorkspace` 不能再作为用户心智里的“场景”，它应该被产品化为“方案”。但“方案”也不能吞掉模板、卷面/版式和资料包。

### 48.1 当前应固定的对象层级

当前最稳的产品模型应是：

```text
工作模式 WorkMode
  例如：试卷版 / 公文版 / 论文版 / 标书版
  作用：决定当前用户进入哪个产品域，过滤下面所有资源。

方案 Plan
  兼容实现仍是 SceneWorkspace / scene_id。
  用户侧叫方案。
  作用：定义本模式下的一套处理策略、默认模板、默认卷面/版式、资料包策略、交付版本。

模板 Template
  实现仍是 TemplateConfig。
  作用：排版样式基线，例如页面、正文、标题、表格、目录、题注等。
  不等于方案，也不等于卷面/版式。

卷面 / 版式 Master
  实现是 MasterSpec 包装真实 DOCX 或 manifest。
  试卷版用户侧叫“卷面”，公文版用户侧叫“版式”。
  作用：承载强版式壳、占位符和装配入口。

资料包 Material Package
  作用：结构化业务资料、实体字段、附件清单等。
  公文、标书更需要；试卷更多是题稿/题库输入，不应强行混成同一种资料包。
```

因此，截图里“方案与模板”这两个下拉不应该都显示“内置方案”。正确关系是：

```text
方案下拉：选当前工作模式里的处理方案。
模板下拉：选当前工作模式里的格式模板。
卷面/版式下拉：选当前工作模式里的装配壳。
资料包下拉/入口：选当前工作模式里的资料样例或用户资料包。
```

它们应当同 mode 隔离、可被方案默认值联动，但不是同一个资源类型。

### 48.3 为什么之前会出现错位

错位来自三层迁移叠在一起：

```text
第一层：旧系统把 SceneWorkspace 叫场景。
第二层：新系统把顶部下拉变成工作模式。
第三层：原场景页被产品化为方案配置。
```

这会导致两类自然错觉：

```text
错觉 1：既然“场景”改成“方案”，那所有下拉都应该选方案。
修正：不对。只有原 SceneWorkspace 选择器是方案；模板和卷面/版式仍是独立资源。

错觉 2：既然方案是内置的，那卷面/版式下拉也应该显示同一批内置方案。
修正：不对。方案可以引用默认卷面/版式，但卷面/版式下拉显示的是装配壳，不是方案。
```

用试卷举例，正确联动是：

```text
选择方案：默认试卷
  -> 默认模板：默认格式
  -> 默认卷面：A4 标准卷面
  -> 交付版本：学生卷 / 答案版

选择方案：随堂测验
  -> 默认模板：默认格式
  -> 默认卷面：短测紧凑卷面
  -> 交付版本：学生卷 / 答案版

选择方案：期中期末
  -> 默认模板：默认格式
  -> 默认卷面：期末完整卷面
  -> 交付版本：学生卷 / 答案版
```

用户仍然可以手动切换模板或卷面，但它们属于“当前方案的配置项”，不是另一个方案下拉。

```text
   内置 manifest 已在 config_library/masters/exam/builtin，但内置 DOCX 仍在 exam_masters/builtin。
```

### 48.6 exam_masters/user 的 202 个文件再判断

`exam_masters/user` 的 202 个文件仍然应判定为 legacy 用户卷面池残留：

```text
它们不是内置方案。
它们不是内置模板。
它们不是新 config_library 下的用户卷面。
它们不应在产品发布包中出现。
它们不应被默认下拉全部展示。
```

它们之所以还在，是因为旧的创建副本/导入卷面策略会不断生成 `user_default_exam_copy_N.docx`，为了避免覆盖用户曾经修改过的 DOCX，文件名会递增。这个策略保护了用户文件，但造成了文件夹观感污染。

```text
第一步：保留 dry-run 审计。
第二步：确认没有当前方案引用。
第三步：用户确认后移动到 archive，而不是删除。
第四步：产品入口只打开当前卷面文件或 active user 目录，不再暴露 legacy 池。
```

## 51. P1 后半段：快速执行方案/模板同源与跨模式串入复核

### 51.1 本轮复核对象

需要钉牢的关系是：

```text
顶部工作模式:
  thesis / exam / official / bidding / ...

处理方案:
  plan_selector_options(<当前工作模式>)
  例：exam -> 默认试卷、随堂测验、期中期末
  例：official -> 公文排版、函件方案、纪要方案

格式模板:
  template_selector_options(<当前工作模式>)
  例：exam -> 默认格式
  例：official -> GB/T 9704 公文格式、公文自定义格式

  official -> 版式

```

也就是说，快速执行里的“处理方案”不能直接拿模板列表，模板下拉也不能因为 bridge 里残留旧 `template_id` 就把别的工作模式模板塞进来。

### 51.2 发现的问题

问题不在 `plan_selector_options("official")`，而在快速执行页的模板同步逻辑：

```text
旧链路:
  当前工作模式 = official
  template_selector_options("official") 先加载 official 模板
  bridge / 当前 SceneWorkspace 里残留 template_id = default
  _ensure_combo_value(...) 认为需要保证该值可见
  把 default 作为额外项注入 official 模板下拉
```

这会造成两个问题：

```text
1. 公文快速执行页看起来出现了非公文模板。
2. 用户会误以为“方案”和“模板”没有按顶部工作模式隔离。
```

这类错位尤其危险，因为它不是列表源头错，而是后置同步时悄悄插入。只看初始 selector 函数会误判为已经没问题。

```text
如果 template_id 在其他工作模式存在:
```

保留第三条是为了不破坏已有外部模板链路。例如测试中的 `custom_saved` 不是库内模板，但代表用户或运行时临时保存的模板引用，不能被误杀。

## 54. P3-B 执行：official.json 中 exam_paper 残留字段治理

本轮执行第 53.6 节的 P3-B。目标不是把 `SceneWorkspace` 模型里的 `exam_paper` 字段立刻拆掉，而是先确认并切断它对公文链路的污染风险。

### 54.1 审阅结论

当前模型现实：

```text
SceneWorkspace 默认带 exam_paper: ExamPaperConfig
```

因此，即使某个公文 JSON 不显式写 `exam_paper`，加载后 Python 对象上仍然会有默认 `scene.exam_paper`。所以本轮不能用“对象上没有 exam_paper”作为完成标准。

正确完成标准应是：

```text
1. 内置公文方案 JSON 不再显式携带试卷专属 exam_paper 块。
2. UI 方案预览不因默认 exam_paper 属性显示试卷卷面。
3. 快速执行不因默认 exam_paper 属性把公文 Markdown 当试卷题稿。
4. 试卷方案仍能正常走 Markdown 题稿入口。
```

### 54.2 发现的真实污染点

审阅发现 UI 大多数地方已经使用固定 surface 判断：

```text
scene_uses_exam_paper_surface(scene)
scene_uses_official_document_surface(scene)
```

这类判断是正确方向，因为它依赖 `scene_id/category`，不是依赖 `exam_paper` 字段是否存在。

但 runtime 中有一处旧判断：

```text
_is_exam_markdown_input(scene, input_path)
  -> category == "exam_paper"
  -> scene_id == "exam"
  -> getattr(scene, "exam_paper", None) is not None
```

第三条是污染点。由于 `SceneWorkspace` 默认总有 `exam_paper`，这会导致：

```text
公文方案 + .md 输入
  -> 被误判为试卷 Markdown 题稿
  -> 进入 exam_markdown_import / exam_items_schema
```

这与顶部工作模式和方案语义冲突：公文版目前只接受 Word / 资料包，不应该因为模型默认字段进入试卷链。

### 54.3 修正

修改：

```text
src/ui/panels/workbench/execution_runtime.py
```

旧逻辑：

```text
return bool(
    category == "exam_paper"
    or scene_id == "exam"
    or getattr(scene, "exam_paper", None) is not None
)
```

新逻辑：

```text
return scene_uses_exam_paper_surface(scene)
```

也就是让 runtime 与方案配置页、快速执行页使用同一套 surface 判定：

```text
exam / exam_quiz / exam_term -> 试卷 surface
official / government        -> 公文 surface
```
