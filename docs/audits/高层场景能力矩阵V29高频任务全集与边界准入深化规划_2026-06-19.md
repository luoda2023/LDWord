# 高层场景能力矩阵 V29 高频任务全集与边界准入深化规划（2026-06-19）

## 1. 本轮判断

本轮继续处理“当前功能点过于不完善，不能出现高频适用场景遗漏或者边界不清晰”的问题。V28 已经把场景能力矩阵推进到九个 lens 的 dashboard 和多条 release gate；V29 不再继续按“功能名”横向加开关，而是把矩阵提升为一套高频任务全集和边界准入规则。

完善的场景能力矩阵应回答：

```text
用户自然说法
-> 高频任务族
-> coverage pack / family / profile / schema / preset / plugin gate
-> 工作流原型
-> 模板/资料/输出/场景/插件归属
-> Word/OOXML 风险面
-> UI 控件契约
-> 执行、报告、fixture、release gate 证据
```

如果一条高频需求只在文档中出现，但没有 route、request-cell、fixture、报告或 release gate，它只能算规划项，不能算完整能力。如果一条需求涉及专业判断、外部识别或生成质量，但没有插件/人工门，它就是边界不清。

## 3. V29 完整性定义

一个高频场景要进入“完善矩阵”，至少满足十个条件：

| 条件 | 必须回答 | 不满足时的表现 |
| --- | --- | --- |
| 高频说法 | 用户会怎么说，是否有 matched、ambiguous、manual boundary、negative 样本 | 内部命名完整，真实需求遗漏 |
| 唯一优先落点 | 首选 pack/family/profile/schema/preset/plugin 是什么 | 一个需求被多个入口同时吸收 |
| 事实源 | DOCX、JSON、XLSX、资料包、规则 profile 哪个是事实源 | 执行时靠猜，报告无法复盘 |
| 工作流 | 是排版、资料填充、附件清单、计数、批量、多版本、归档还是审阅 | 一个按钮吞掉多个业务流程 |
| Word 风险 | 会触碰哪些 OOXML 面，是否预检、降级、阻断或报告 | 复杂对象被普通文本逻辑误伤 |
| 控件契约 | 是否复用模板管理控件语言 | 模板和场景对同一参数解释不同 |
| 执行链 | resolver、pipeline、runner、report、repair、artifact 是否可追踪 | UI 能配，执行层断链 |
| 报告链 | JSON/Markdown/Workbench 是否解释边界和风险 | 用户看不到为什么阻断或降级 |
| fixture 链 | 是否有 DOCX fixture 或明确 manual-boundary fixture | 只有规划，没有样本证据 |
| release gate | 是否进入测试和门禁 | 后续改动容易把链路打断 |

V29 的核心原则：高频不等于进入核心实现，完整不等于全部自动化。高频专业判断可以只做到“插件/人工门完整”，但不能被核心静默承诺。

## 4. 高频任务全集视角

下面的任务全集用于防遗漏。它不是要求每一项都立刻成为独立 UI 入口，而是要求每一项都有稳定落点、边界和证据路线。

| 高频任务族 | 用户自然说法 | 首选承载层 | 必须闭合 | 不承诺边界 |

| 快速排版修复 | 套模板、修目录页码、统一格式、清洗样式 | `quick_formatting` | 模板基线、scope、对象预检、报告 | 不做学校/期刊/法律/财务判断 |
| 个人文档格式 | 简历、个人陈述、求职信排版 | `quick_formatting` family 候选 | 模板基线、基础结构、输出文件 | 不做求职内容质量判断 |
| 中文论文与课程论文 | 毕业论文、课程论文、开题、综述 | `chinese_academic` / `thesis_cn` | CountProfile、引用、公式、学校 profile | 不宣称所有学校规则最新 |
| 英文期刊投稿 | manuscript、cover letter、revision、BibTeX | `english_journal` / `journal_en` | rule source、投稿包、引用、display item count | 不做 publisher-final layout |
| 试卷与教学材料 | 学生版、教师版、答案版、解析版、答题卡 | `exam_education` / `exam_teaching` | 题源 schema、多版本、固定版位、人工门 | 不承诺 AI 出题质量和复杂图自动生成 |
| 标书与资质包 | 标书正副本、证照、签章、附件清单 | `bidding_materials` | 资料 schema、附件 inventory、签章资产、归档 manifest | 不判断投标策略和证照真实性 |
| 公文与制度材料 | 通知、函、纪要、制度汇编、归档版 | `official_policy` | 文号、版记、编号、正式/内部/归档 preset | 不把所有行政小类变成顶层入口 |
| 技术长文档 | SOP、接口文档、验收报告、技术手册、书稿 | `technical_long_docs` | 章节库存、目录、附录、对象预检、多文件边界 | 不保证技术事实正确 |
| 项目申报与评审 | 申报书、评审材料、附件包、限字 | `application_reports` / `project_application` | 限字、附件、资料事实、提交包 | 不替代外部申报系统 |
| 产品与售前材料 | 白皮书、客户方案、产品手册、售前方案 | `application_reports` / `product_sales_documents` | 客户/内部版本、资料证据、图片/附件 | 不承诺营销内容质量 |
| 合同与签署包 | 审阅稿、签署稿、字段一致性、修订批注 | `contract_delivery` | 字段一致性、修订保护、签署包、法律边界 | 不提供法律意见 |
| HR 与人员批量文档 | offer、证明、批量通知、员工材料 | `batch_forms` / `hr_batch_documents` | BatchPreset、单记录失败隔离、批量报告 | 不验证人员资料真实性 |
| 固定版位表单证书 | 证书、奖状、登记表、套打、固定行高 | `batch_forms` / `form_batch_documents` | fixed-layout profile、`w:trHeight`、内容控件、文本框 | 不回到通用模板表格字段 |
| 财务报价与预算附件 | 报价单、预算书、金额表、报价方案 | `professional_disclosure` / `finance_quote_documents` | 资料证据、交付包、专业人工门 | 不判断财务正确性 |
| ESG/年报/披露 | 年报、ESG、披露归档、董事会审阅 | `professional_disclosure` / `regulated_disclosure_documents` | 审阅/公开/归档版本、hidden text、人工门 | 不做审计或保证 |
| 专利与 IP 材料 | 专利交底、说明书、权利要求 | `professional_disclosure` / `ip_patent_documents` | 专业人工门、资料证据、版本记录 | 不判断授权性、侵权或专利质量 |
| 法律文书 | 法律意见书、诉状、法律文书 | `professional_disclosure` plugin/manual boundary | 专业人工门、报告边界 | 不被合同场景吸收 |
| 医疗/药品/监管材料 | 医疗注册、药品注册、器械注册申报资料 | `professional_disclosure` plugin/manual boundary | 专业人工门、证据归档 | 不被项目申报泛化吸收 |
| 双语与术语审阅 | 双语审阅、术语一致性、翻译审阅 | `professional_disclosure` / `bilingual_translation_documents` | 对照、术语、人工门 | 不承诺翻译质量结论 |
| PDF/OCR 导入 | 扫描件、PDF 转 Word、低置信度 OCR | `import_ai_boundary` | 置信度报告、人工确认、handoff | 不承诺无损转换 |
| LaTeX 与公式转换 | LaTeX 转 Word、公式片段、完整工程 | scene policy + `import_ai_boundary` | 公式片段策略、完整工程人工门 | 不把完整工程当普通样式 |
| AI 草稿与生成内容 | AI 写作、AI 出题、AI 草稿导入 | `import_ai_boundary` 或领域插件 | JSON/Markdown 预览、人工确认 | 核心不承担事实和质量责任 |
| 复杂学科图形 | 几何图、电路图、结构式、复杂图形 | 专用插件或图片资产 | 图形 schema、预览、插入/替换证据 | 核心不自动制图 |
| Excel/数据到 Word | 数据表生成报告、批量函件、报价明细 | MaterialSchema / BatchPreset / 对应 pack | 字段映射、单记录隔离、报告 | 不把数据正确性当排版能力 |
| 非 Word 原生交付 | PPT、网页、图片海报、最终出版系统 | negative 或外部插件 | 明确拒绝或 handoff | 不静默冒充 Word 场景 |

这张全集的用途是防遗漏：新增需求必须先落到其中一类，或明确说明为什么它是新任务族。不能因为用户说了一个行业名，就立刻创建新顶层入口。

## 5. 承载层裁决规则

| 判断问题 | 落点 |
| --- | --- |
| 是否只是格式外观、段落、字体、页眉页脚、目录页码 | TemplateConfig / control contract |
| 是否是特定业务版本，如学生版、客户版、正式版、归档版 | DeliveryPreset / ContentVisibilityRule |
| 是否是字段、人员、公司、项目、签章、附件事实 | MaterialSchema / MaterialExecutionContext |
| 是否是字数、页数、显示项、规则来源 | CountProfile / rule source governance |
| 是否是多记录输入和批量输出 | BatchPreset |
| 是否是固定版位、套打、证书、答题卡 | fixed-layout profile，不进通用模板表格字段 |
| 是否是 PDF/OCR/LaTeX/AI/复杂图形导入 | `import_ai_boundary` plugin/manual gate |
| 是否是法律、财务、审计、专利、医学、翻译质量判断 | `professional_disclosure` plugin/manual gate |
| 是否只是已有 pack 的子场景 | family/profile/schema/preset，不新增顶层入口 |
| 是否拥有独立用户心智、事实源、交付、风险面和报告组合 | 才考虑新增 coverage pack |

新增顶层入口必须满足四个条件：

1. 用户长期稳定地按这个大类表达，不只是行业别名。
2. 事实源、交付版本、OOXML 风险面至少两项明显不同于现有 pack。
3. 需要独立 schema/profile/preset/report/repair 组合。
4. 已有 request-cell、fixture、测试和 release gate 计划。

否则只进入 family/profile/schema/preset/plugin。

## 6. 高频边界样本必须增加的类型

当前 request-cell 已能覆盖大类，但 V29 要继续补四类边界样本：

| 样本类型 | 目的 | 示例 |
| --- | --- | --- |
| 易混淆样本 | 防止错误落点 | 产品手册是技术手册还是客户材料；报价方案是金额表还是售前方案 |
| 人工门样本 | 防止核心越界承诺 | 法律意见书、医疗注册、OCR 低置信度、AI 复杂图形 |
| 负例样本 | 防止无根据吸收 | PPT 设计、网页发布、未知材料、出版系统最终排版 |
| Handoff 样本 | 防止导入和目标场景混同 | PDF 论文先走导入人工门，再 handoff 到中文论文 |

每个高风险 pack 至少应保留：

```text
3 条 matched
1 条 ambiguous
1 条 manual boundary
必要时 1 条 negative 或 handoff
```

这不是硬性数量崇拜，而是为了让边界能够被测试和解释。

## 7. 插件/人工边界统一确认

V29 将 N2.160 定义为下一条必须闭合的链路。三类 gate 需要统一到同一审计模型：

| gate | 覆盖 pack | 风险域 | 必须证据 |
| --- | --- | --- | --- |
| `exam_ai_complex_diagram_gate` | `exam_education` | `ai_content_quality`、`complex_diagram_generation` | route、request-cell、manual fixture、置信度报告、manual_decision |
| `professional_disclosure_review_gate` | `professional_disclosure` | `audit_assurance`、`legal_opinion`、`financial_assurance`、`ip_patent_quality`、`medical_regulatory`、`translation_quality` | 专业审阅元数据、报告边界、manual fixture |
| `import_ai_conversion_gate` | `import_ai_boundary` | `ocr_confidence`、`pdf_conversion`、`full_latex_conversion`、`ai_content_quality`、`complex_diagram_generation` | 置信度报告、人工确认、handoff 和回退策略 |

统一确认状态：

```text
accepted
rejected
needs_plugin_handoff
```

统一报告字段至少包含：

```text
manual_decision
boundary_text 或 confidence_level
unsupported_core_inputs
confirmation_scope
```

这一步的关键不是做插件本身，而是确保核心不会把插件/人工风险伪装成普通场景参数。

## 8. 控件一致性继续作为场景准入

用户反馈的左缩进、右缩进、段前段后、特殊缩进切换，本质不是单页 UI 问题，而是场景控件契约问题。V29 继续沿用 N2.157C 的规则：

| 参数 | 场景侧准入 |
| --- | --- |
| 左缩进/右缩进 | 同一行或同组展示，单位和 stepper 与模板管理一致 |
| 段前/段后 | 同一行或同组展示，不改名为前距/后距 |
| 特殊缩进 | 可切换无/首行/悬挂，无时禁用数值并归零 |
| 行距类型/行距值 | 类型和值绑定，固定类型禁用自由值 |
| 固定行高 | 只通过 fixed-layout profile 暴露并写 `w:trHeight` |
| 水印 | 状态和交付语义归场景，外观归模板语言 |
| 公式 | 片段转换策略归场景，完整 LaTeX/AI/OCR 质量归插件 |

场景配置只要出现与模板管理共享的外观参数，就必须复用 control contract，不能重新发明控件。

## 10. V29 结论

更高层的场景能力矩阵不能只看“有没有功能点”。它必须用任务全集防遗漏，用承载层裁决防边界发散，用 Word/OOXML 风险防执行误伤，用控件契约防 UI 语义分裂，用插件/人工门防核心越界承诺。

当前 12 个 pack 不应急着扩成更多顶层入口。下一步应优先把高频任务族、边界样本、插件人工门、handoff、真实 fixture 和 dashboard drilldown 做深。只有当一类需求拥有独立事实源、交付、风险面、报告和证据链时，才值得升级为新的顶层场景。
