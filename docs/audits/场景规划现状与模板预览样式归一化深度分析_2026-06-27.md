# 场景规划现状与模板预览样式归一化深度分析

日期：2026-06-27
范围：场景规划进度、后续必要功能、模板预览样式归一化实现方式、项目内相关文档索引。

## 1. 一句话结论

当前项目的“场景规划”已经越过了概念设计阶段，进入了“可审计、可发布门禁校验、可在前台投影展示”的阶段。

截图中的场景概览页不是静态展示，而是把场景矩阵、能力审计、边界治理、样本覆盖、交付状态等证据投影到前台；模板概览页也不是散落的手写说明，而是通过统一 projection、共享 SummaryGrid、共享 TemplateSummaryCard，把模板参数摘要和详情页摘要逐步归一。

但这不等于全部能力都已经产品化完成。当前更准确的阶段判断是：

- 核心场景模型、能力矩阵、审计链路和发布门禁已经成型。
- 高频场景覆盖、证据源、drilldown、边界治理读数已经闭环。
- 用户可感知的“配置、运行、产物浏览、边界解释、资料修复、插件交接”等产品化入口仍需要继续深化。
- 模板预览的摘要样式归一已经落地到代码层；更精细的运行时格式保真、截图回归和跨模块视觉验收仍需要补齐。

## 3. 场景规划走到哪一步了

### 3.1 阶段 A：边界和对象模型已经定义清楚

早期文档已经把几个核心对象拆开：

- Scene：定义任务意图、处理范围、能力开关、边界策略、交付链路。
- Template：定义页面、排版、标题、表格、页眉页脚、目录、参考文献、题注等格式基线。
- Material / Assets：定义外部资料、图片、题源、结构化输入和修复流程。
- Session / Preset：定义一次运行中的场景、模板、覆盖参数、输出策略组合。

这一步解决的是“场景不是模板，模板也不是运行批次”的问题。截图中的“当前场景 + 关联模板”正是这个拆分的前台表达。

### 3.2 阶段 B：场景运行配置已经进入代码

代码层已经出现 `SceneWorkspace`、场景 resolver、feature configs、style semantics、feature group、scope/output/module switch 等对象。场景页的卡片也不是随意堆叠，而是被固定为：

- 场景概览
- 处理范围
- 功能开关
- 功能参数
- 输出设置

这说明场景规划已经进入“配置面板和运行参数模型”的阶段，而不是停留在文档草图。

### 3.3 阶段 C：高频场景能力矩阵已经建立审计口径

当前项目围绕高频使用场景建立了大量矩阵和审计文件，覆盖：

- 高频任务包和请求话术
- 自然语言请求到场景的路由
- 输入来源和资料族
- Word/OOXML 风险
- 对象预检动作
- 控件契约和运行时一致性
- 业务能力矩阵
- 边界能力矩阵
- 插件边界和外部 handoff
- 交付 preset 和交付执行
- 公式、输出、水印归属
- 产品成熟度和 L5 阻断项
- drilldown、证据源、发布验收证书

发布门禁通过，且显示 `drilldowns=37/37`、`drilldown_rows=556/556`、`drilldown_sources=107/107 ready`。这说明“场景规划”已被转成了可机器检查的发布证据。

### 3.4 阶段 D：已经采用“边界治理式发布”

项目里有些读数不是满格，例如：

- `count_profiles=14/15 ready`
- `delivery_families=14/15 ready`
- `maturity_l5_blocked=6/27`

这些不能简单理解为“未完成”。现有 N2 系列文档和门禁输出把它们归入：

- accounted
- governed
- enveloped
- receipt aligned
- release allowed

也就是说，当前版本采用的是“把可自动完成的能力做成绿色闭环，把不能承诺的能力用边界说明、回执、外部插件或人工确认治理起来”的发布方式。

这对产品表达很重要：前台不能把边界治理项伪装成全自动能力，也不能把它们直接显示成失败。更合适的表达是“已守门”“边界说明”“需外部确认”“可跳过高风险模块”“保留 gap 已封套”。

### 3.5 阶段 E：前台已经开始把审计结果投影出来

截图 1 的“场景概览”页已经在做这件事：

- 当前场景：选择场景 preset。
- 关联模板：选择格式模板。
- 编号策略：重建编号 / 保留原编号。
- 输入、合规、对象保护、交付、参数归属、边界守门、控件契约、覆盖矩阵、产品成熟度、样本覆盖等卡片：对应后端场景矩阵和投影函数。

从实现看，这类摘要来自 `scene_summary_projection.py`、场景 fixture、request cell、object preflight、delivery 和 boundary 相关注册表。它的价值是让用户在运行前看到“这个场景到底承诺什么、跳过什么、需要人工确认什么”。

## 4. 现在模板预览样式归一化是怎么实现的

### 4.1 旧问题：模板摘要曾经分散在不同页面

早期规划文档 `docs/audits/模板详情预览统一规划_2026-06-02.md` 关注的问题是：

- 模板概览页一套摘要写法。
- 各详情页顶部又有另一套摘要写法。
- 页面、正文、标题、表格、页眉页脚、目录、参考文献、题注之间的 tile 数量、高度、间距、图标和文本截断规则不统一。
- 容器宽度变化时容易产生换行、挤压、抖动和视觉不一致。

### 4.2 现在的归一化链路

当前实现已经形成四层链路：

1. 数据投影层：`template_summary_projection.py`

   这里定义统一的摘要模型：

   - `TemplateSummaryTileSpec`
   - `TemplateDetailSummarySpec`
   - `DETAIL_ORDER`
   - `build_template_detail_summary()`
   - `all_template_detail_summaries()`
   - `summary_grid_items()`
   - `build_template_detail_summary_items()`

   它把页面、正文排版、标题编号、表格、页眉页脚、目录、参考文献、题注这 8 个模块的摘要，统一从 `TemplateConfig` 投影出来。

2. 兼容适配层：`template_format.py`

   `build_template_preview_groups()` 不再自己拼接一套独立摘要，而是调用 `all_template_detail_summaries()`，再映射成模板概览页仍在使用的 `TemplatePreviewGroup`。

   这一步很关键：它保留了旧概览页的数据结构，同时把摘要来源收口到统一 projection。

3. 共享视觉组件层：`TemplateSummaryCard` + `SummaryGrid`

   `TemplateSummaryCard` 负责统一详情页顶部摘要卡的外框、标题、图标、操作按钮和内容高度同步。

   `SummaryGrid` 负责统一 tile 布局：

   - 12 列基础网格。
   - `single_row_preferred` 布局策略。
   - 根据 tile 数量自动分配 span。
   - 窄宽度下自动降为 1 列或 6 列。
   - 模块 tile 有固定高度、统一图标容器、统一 value/detail 行高。
   - 长文本使用 elide 和 tooltip，减少撑爆布局。

4. 消费页面层：各模板详情页复用同一套摘要

   已经接入 `TemplateSummaryCard` 和 projection 的页面包括：

   - `template_page_detail.py`
   - `template_style_detail.py`
   - `heading_numbering_panel.py`
   - `template_table_detail.py`
   - `template_elements_detail.py`
   - `template_reference_detail.py`
   - `template_caption_detail.py`

   这说明“模板预览样式归一化”已经不只是文档规划，而是落到了主要模板详情页面。

### 4.3 截图 2 中的两类预览要分开理解

截图 2 包含两种不同的“预览”：

- 参数概览：页面、排版、标题、表格、页眉与页脚、目录、参考文献、题注这些行，来自统一模板摘要 projection。
- 样式预览：A4 页面、页边距、页眉页脚距离、标题层级和正文样例的视觉模拟，来自 `TemplateStylePreview`。

参数概览解决的是“当前模板配置是什么”；样式预览解决的是“这些配置看起来大概是什么效果”。两者都属于模板预览，但技术路径不同。

### 4.4 当前归一化做到的程度

已经做到：

- 摘要数据来源统一。
- 模板概览和详情页摘要共享同一套 projection。
- 主要模块都接入 `TemplateSummaryCard`。
- tile 布局、图标、文本截断和响应式策略统一。
- 有测试覆盖 `template_format_projection`、`summary_grid`、多个模板详情页接入情况。

还没完全做到：

- 样式预览与真实 Word 运行时渲染之间还需要更强的视觉回归校验。
- 场景侧样式 override 与模板侧控件还需要进一步做控件级 parity 验收。
- 超长中文、英文、混排和小窗口下的截图级不重叠验证仍需要持续补。
- 概览页、详情页、运行结果报告之间的同一字段解释还可以更强，例如点击摘要项直接跳到证据、控件或输出产物。

## 5. 后续必要功能建议

### 5.1 P0：短期必须继续补的产品闭环

1. 场景概览卡片 drilldown

   截图 1 中的覆盖矩阵、产品成熟度、样本覆盖、边界说明等卡片目前已经能表达状态，但下一步需要让用户点击卡片后进入对应证据：

   - 对应场景包
   - 对应 request cell
   - 对应 fixture
   - 对应 boundary receipt
   - 对应 delivery preset
   - 对应 release gate 读数

   目标是从“看见状态”升级为“能解释状态”。

2. 发布门禁诊断和增量模式

   当前 `scripts/verify_scene_matrix_release_gate.py` 能给出非常完整的发布结论，但输出体量和运行链路较重。建议增加：

   - 进度输出
   - 快速逻辑校验模式
   - fixture 重建和纯审计校验拆分
   - 单个 audit 的定位参数
   - 前台可读的失败摘要

3. 运行产物浏览器

   场景能力已经覆盖到报告、交付 preset、delivery execution、artifact drilldown，但用户需要一个更自然的产物入口：

   - 输入文件
   - 中间版本
   - 修复报告
   - 最终 Word
   - 对比文件
   - 边界警告
   - 外部 handoff 回执

4. 场景侧样式 override 控件归一

   模板侧已经有较成熟的 `FontCombo`、`SizeCombo`、`SpacingInput`、`IndentInput`、`SpecialIndentInput` 等控件。场景侧凡是涉及字体、字号、缩进、行距、段前段后、固定行高、页眉页脚、水印等字段，都应该尽量复用同一控件契约和校验规则。

5. 模板预览截图回归

   对模板概览页、主要详情页、摘要卡、A4 样式预览做桌面和小窗口截图回归，重点检查：

   - tile 不抖动
   - 文本不互相覆盖
   - 长文本有 tooltip 或截断
   - 8 个模板模块视觉密度一致
   - 场景关联模板后，模板摘要值和场景 override 表达不冲突

### 5.2 P1：中期应该深化的能力

1. CountProfile 用户级配置

   现在 `count_profiles=14/15 ready` 但 `15/15 accounted`，说明边界已治理。下一步可以把计数口径做成用户可读、可保存、可复用的 profile，而不是只存在于矩阵和审计结果里。

2. Material Schema 和资料修复 UI

   资料包、图片、题源、固定版式、结构化素材已经有大量闭环文档。后续要把 schema 校验、缺失修复、远端缓存、批量失败恢复等能力沉到普通用户能操作的界面。

3. ContentVisibilityRule

   对学生版、教师版、评审版、内部版、交付版等内容显隐规则，需要在场景、模板和输出 preset 间形成稳定模型。

4. 公式、OCR、AI、导入 handoff 的运行时入口

   当前 `formula_output_watermark=3/3` 说明归属和可见性已经进入矩阵，但完整公式解析、OCR、AI 改写、导入插件能力仍属于边界项或外部 handoff。后续要把“为什么不能自动做、交给谁做、回执如何回来”做成用户流程。

5. 水印策略产品化

   当前水印状态已经进入能力归属，但不同 preset 的水印样式、位置、审阅版/最终版差异、去水印权限，还需要进一步落产品。

6. Session Preset 保存与恢复

   早期规划中提到场景、模板、参数覆盖和输出策略的组合。后续应支持保存当前组合，形成可复用 preset。

### 5.3 P2：后续增强方向

- 新场景 / 新模板 authoring。
- 外部插件连接器和 handoff 协议可视化。
- 报告模板自定义。
- 大文档性能缓存。
- 发布证据的可搜索索引。
- 多用户或团队共享配置。

## 6. 主要风险和产品表达注意点

1. 不要把“发布门禁通过”说成“所有场景都全自动完成”

   当前发布方式包含边界治理、外部 handoff、人工确认和保留 gap。产品文案应区分：

   - 已自动支持
   - 已守门
   - 需人工确认
   - 需外部插件
   - 当前版本不承诺

2. 不要隐藏非满格读数

   `14/15 ready`、`6/27 blocked` 这类数字反而是当前体系成熟的地方：它们被解释、归因、封套、回执和发布准入治理了。隐藏它们会降低可信度。

3. 文档数量已经很大，需要入口索引

   `docs` 里 N2 文档非常多，后续建议维护一个“场景矩阵文档导航页”，否则新开发者很难知道哪些是历史规划、哪些是最新闭环证据。

4. 模板摘要归一不等于 Word 渲染完全一致

   `TemplateSummaryCard` 和 `SummaryGrid` 解决的是前台摘要 UI 归一；真正的 Word 输出仍需要对运行时生成、OOXML 风险、样式继承、表格行高、域代码、题注、目录等做端到端验证。

5. 截图中的信息密度已经接近上限

   场景概览卡片很多，价值高，但需要更强的层次：

   - 第一层给用户结论。
   - 第二层给证据入口。
   - 第三层给开发/审计明细。

   否则普通用户会觉得“全是状态词”，但不知道下一步要点哪里。

## 7. 建议下一阶段路线

### Sprint 1：模板预览归一收口

- 给模板概览和详情页补截图回归。
- 固化 8 个模板模块的摘要字段。
- 检查小窗口、长文本、中英混排。
- 明确 `TemplateStylePreview` 与真实 Word 输出的差异说明。

### Sprint 2：场景概览 drilldown

- 点击场景概览卡片进入证据明细。
- 把 release gate、drilldown、fixture、request cell、boundary receipt 做成用户可读索引。
- 对“边界说明”卡片提供可解释文本和相关文档链接。

### Sprint 3：运行产物和交付链路

- 做交付产物浏览器。
- 串起 input、intermediate、report、final、receipt。
- 将 delivery preset 和 delivery execution 从矩阵读数转成前台流程。

### Sprint 4：资料和计数 profile 产品化

- CountProfile 编辑器。
- Material Schema 校验和修复 UI。
- 固定版式和题源资料的导入诊断。

### Sprint 5：边界 / 插件 / 外部 handoff

- 插件边界确认页。
- 外部 handoff 合同和回执展示。
- AI/OCR/公式/水印等非完全内置能力的用户流程。

## 9. 建议补一个文档导航页

当前 `docs` 目录已经积累大量规划和闭环文档。建议后续新增：

```text
docs/audits/场景矩阵与模板体系文档导航.md
```

导航页只维护四类入口：

- 体系总览：场景 / 模板 / 会话 / 资料边界。
- 最新发布口径：release gate、requirement dimensions、drilldown counts。
- 前台实现：scene panel、template panel、summary projection、control contract。
- 历史审计：N2 闭环文档索引。

这样后续开发时不会在几十份 N2 文档里迷路。
