## 2. 总判断

当前矩阵的问题已经不是“完全没有高频场景归属”。代码和规划里已经有：

- 6 个 P0 可执行场景：自定义、论文、标书、公文、技术、报告；
- 14 个 planning family：英文投稿、试卷教学、项目申报、合同、HR、会议制度、产品售前、长文档、表单套打、资质包、财务报价、专利、双语、披露；
- 12 个 coverage pack：快速规范化、中文学术、英文投稿、教育试卷、标书资料、公文制度、技术长文档、申报报告、合同交付、批量套打、专业披露、导入/AI 边界；
- MaterialSchema 和 CountProfile 已覆盖多数 P1/P2 的资料与计数口径。

真正的问题是：

```text
名字和 registry 已经铺开，但大多数 family 仍停留在 L1 planning contract。
```

所以后续重点不是继续新增入口，而是把高频场景逐个推过成熟度门槛。一个高频场景如果只有 registry、schema 或 UI 文案，仍然不能算完善。

## 3. 当前代码事实基线

### 3.1 SceneWorkspace 已具备高层承载能力

`SceneWorkspace` 当前已经有下列核心承载：

| 承载 | 字段 | 矩阵意义 |
| --- | --- | --- |
| 输入契约 | `input_source_profile` | 支持格式、结构化格式、资料包要求、Markdown/LaTeX 策略、失败策略 |
| 合规契约 | `compliance_profile` | 规则族、计数 profile、检查范围、对象预检、报告粒度 |
| 对象安全 | `ObjectPreflightPolicy` | OLE、宏、修订、批注、文本框、内容控件、域等风险对象策略 |
| 多交付 | `delivery_presets` | 输出版本、目标模板、命名、产物开关、显隐规则、中间产物 |
| 内容显隐 | `ContentVisibilityRule` | 同一事实源生成不同版本 |
| 批量 | `batch_preset` | 多实体输出目录策略 |
| 范围 | `format_scope` | 分区、页码、正文起点、关键词 |
| 场景覆盖 | `table/header_footer/toc/caption/formula/reference/watermark/output/template_overrides` | 对模板基线的业务覆盖 |

这说明场景不是一个展示下拉项，而已经具备成为“工作流配置层”的模型基础。

### 3.2 规划层已经足够宽，但成熟度偏低

`scene_family_registry.py` 中 14 个 `PlannedSceneFamily` 均有 `maturity_level="L1"`。这很重要：即便某些 family 已经有 first slice 或局部执行证据，registry 的成熟度仍未同步上调，说明治理资产还没有成为唯一事实源。

当前只有 `scene_family_application.py` 对 `contract_delivery` 提供可应用 defaults；`journal_en` 等 family 可识别但 `apply_planned_scene_family_defaults()` 明确 no-op。这是正确的边界保护，但也说明大量高频 family 仍不能被用户当成可执行场景。

### 3.3 ScenePanel 已有高层控件，但仍有样式和语义债

`ScenePanel` 已经使用 `MasterDetailShell`、`Card`、`SummaryGrid`、`TemplateFormStack`、`template_form_row`、`StyledComboBox`、`ToggleSwitch`、`FeatureToggleRow`，方向正确。

但仍需治理：

- 仍有 `QCheckBox` 用于分区和扫描目标，虽然使用共享 stylesheet，但长期应收敛为共享多选/Chip 组件；
- 编号策略已在 N2.77 迁移到共享 `ThemedRadioButton`；Workbench QuickExecution 的执行台单选也已在 N2.78 同步迁移；
- `QLineEdit`/`TextArea` 用于 schema、显隐规则、交付模板等结构化字段，能快速落地，但后续应提供受控编辑器、变量插入和校验反馈；
- 如果场景页暴露缩进、段距、行距、字体、字号等模板同源参数，必须直接复用模板管理中的 `FontCombo`、`SizeCombo`、`SpacingInput`、段落缩进组合控件，不能再造控件语言。

## 4. V14 完善定义

高层场景能力矩阵的完善度可以写成一个公式：

```text
完善 = 高频任务覆盖
     × 工作流归属
     × 能力槽位完整
     × Word 风险面策略
     × 证据链闭合
     × 边界前台化
```

任何一项为 0，都不能称为完善。

### 4.1 高频任务覆盖

用户自然会说出的高频请求必须有落点。落点不一定是顶层入口，可以是：

- P0 可执行场景；
- planning family；
- profile；
- MaterialSchema；
- CountProfile；
- DeliveryPreset；
- 插件边界；
- 人工确认流程。

但不能是“未来再说”。

### 4.2 工作流归属

同一个文档族可能包含多个工作流。比如“标书”不是一个功能点，它至少包含：

- 资料字段填充；
- 资质附件 inventory；
- 签章/图片资产；
- 正副本或评审稿/正式稿；
- 批量输出；
- 输出目标预检；
- 对象保护；
- 报告证据。

如果只把它归为“标书模板”，就是边界不清。

### 4.3 能力槽位完整

一个场景至少要回答本文第 7 节的 20 个槽位。槽位不是都要实现到最高级，但必须知道：

- 当前由谁承载；
- 是否可见；
- 是否执行；
- 是否报告；
- 是否测试；
- 如果没有实现，边界在哪里。

### 4.4 Word 风险面策略

场景矩阵必须从 Word/OOXML 反推，不只看用户文档名称。任何会触碰 `numbering.xml`、`styles.xml`、`w:tbl`、页眉页脚、域、批注、修订、文本框、内容控件、OLE、宏、关系文件的能力，都必须在场景层有风险策略。

### 4.5 证据链闭合

完整链路至少包括：

```text
registry/model
→ ScenePanel/Workbench 可见
→ resolver/scheduler 消费
→ pipeline/runtime 执行
→ JSON/Markdown report 解释
→ issue queue 或 artifact 可追踪
→ pytest 锁定
```

只有 UI 或只有文档规划，都不能算闭合。

### 4.6 边界前台化

专业判断、AI 内容质量、OCR 无损、完整 LaTeX 工程、复杂学科图形、法律/财务/专利/翻译/审计结论，必须进入插件或人工确认边界。边界不能只藏在 md 规划里，最终要进入 ScenePanel、Workbench 问题队列和执行报告。

## 5. 成熟度模型

后续建议所有 scene family、coverage pack 和关键 profile 都使用同一套成熟度定义。

| 等级 | 名称 | 最低要求 | 不能宣称 |
| --- | --- | --- | --- |
| L0 | 未归属 | 只有用户需求或讨论记录 | 不能进入矩阵 |
| L1 | Planning contract | registry/文档有稳定定义、边界和 first slice | 不能作为可执行能力宣传 |
| L2 | 可配置可见 | ScenePanel/Workbench 能看到关键 profile/schema/preset/边界 | 不能保证执行 |
| L3 | 可执行 first slice | 模型、UI、resolver、runtime、report、测试闭合一条最小链 | 不能宣称全场景完整 |
| L4 | 工作台闭环 | 运行前预检、问题队列、修复/忽略、artifact 展示和失败路径可操作 | 不能宣称规则治理长期稳定 |
| L5 | Profile 治理闭环 | profile 来源、版本、更新、迁移、审阅、历史可追溯 | 不能承诺外部系统 100% 一致 |

当前目标不应是把所有 family 一次性推到 L5，而是优先把高频 P1 的 first slice 推到 L3，再挑 `contract_delivery`、`form_batch_documents`、`exam_teaching`、`journal_en` 进入 L4。

## 6. 高频覆盖雷达

下面不是导航入口清单，而是“不能遗漏的用户请求雷达”。

| 高频请求 | 推荐落点 | 为什么不是简单新增入口 |
| --- | --- | --- |
| 把现有 Word 统一成某种格式 | P0 `report/custom/technical/official` | 这是快速规范化工作流，不是专业场景 |
| 中文论文、课程论文、开题、综述 | P0 `thesis`，长期收敛为 `thesis_cn` profile | 中文学术与英文投稿口径完全不同 |
| 英文投稿、修回、cover letter、submission package | P1 `journal_en` | 需要 journal profile、Bib/CSL、投稿包，不应塞进论文模板 |
| 学生版、教师版、答案版试卷 | P1 `exam_teaching` | 核心是结构化事实源与显隐规则，不是模板套壳 |
| 标书、政府采购、正副本、资质包 | P0 `bidding` + 资料包 profile | 高频且可执行，但资料包和附件 inventory 仍需深化 |
| 通知、函、请示、批复、纪要、制度 | P0 `official` + 行政 profile | 不为每种行政文种开顶层入口 |
| SOP、接口文档、技术手册、验收报告 | P0 `technical` + 长文档 profile | 技术真实性不由核心判断 |
| 项目申报、可研、验收材料 | P1 `project_application` | 资料、附件、字数限制和申报包是主线 |
| 合同、协议、NDA、授权书 | P1 `contract_delivery` | 做字段一致、对象保护、交付包，不做法律意见 |
| Offer、证明、邀请函、人员档案批量 | P1 `hr_batch_documents` | 关键是 xlsx/json 多记录、失败隔离和一人一份 |
| 固定表单、套打、证书、登记表 | P1 `form_batch_documents` | 关键是固定版位、内容控件、行高和残留扫描 |
| 企业资质、证照、附件目录 | 横切 `qualification_archive_packages` | 它是附件 inventory，不是单独文档入口 |
| 报价单、预算、结算附件 | P2 `finance_quote_documents` | 核心只做格式和数字一致性，不做财务审计 |
| 专利交底书、权利要求草稿 | P2 `ip_patent_documents` | 不判断专利法律质量 |
| 双语/翻译审校材料 | P2 `bilingual_translation_documents` | 只做对照、术语、版式和审阅，不判断翻译质量 |
| 年报/ESG/披露材料 | P2 `regulated_disclosure_documents` | 只做长文档、附件、表格和归档，不做审计或披露结论 |
| PDF/OCR/扫描件整理 | 插件/导入助手 | 核心不承诺无损重建 |
| 完整 LaTeX 工程导入 | 插件 | 核心只承诺公式片段或局部结构 |
| AI 生成正文/试题/标书内容 | 输入助手/插件 | 核心只校验结构、预览、渲染，不保证内容质量 |
| 复杂几何图、电路图、结构式 | 学科插件/图片资产 | 核心优先通用图片和图表 |

零遗漏规则：

```text
新增需求先查上表；
能落到已有高频请求，就补 profile/schema/preset/闭环；
落不到任何请求，才新增 coverage pack；
涉及专业判断，默认进插件或人工确认。
```

## 7. 完整场景的 20 个能力槽位

一个可宣称 L3 的场景，至少要对下面 20 个槽位给出明确答案。

| 槽位 | 必须回答 | 推荐承载 |
| --- | --- | --- |
| 1. 用户任务别名 | 用户自然会怎么说 | coverage pack `natural_requests` |
| 2. 顶层归属 | 是顶层场景、family、profile、schema、preset 还是插件 | scene/family/manifest |
| 3. 输入事实源 | 机器可信源是 docx、json、xlsx、markdown、bibtex 还是人工选择 | `InputSourceProfile` |
| 4. 结构化模型 | 是否有 schema、AST、中间 JSON、Markdown 预览 | MaterialSchema/未来 schema/intermediate |
| 5. 资料契约 | 必填字段、图片、签章、附件、多实体数据 | `MaterialSchema` |
| 6. 模板基线 | 使用哪些模板，哪些模板兼容 | `TemplateConfig`、`compatible_template_ids` |
| 7. 场景覆盖 | 哪些模板参数可被场景覆盖，理由是什么 | feature override / `template_overrides` |
| 8. 范围定位 | 处理哪些 section、页码、关键词、样式锚点、Word story | `FormatScopeConfig` / CountProfile |
| 9. 模块组合 | 哪些模块开启，顺序和依赖如何 | `module_switches` / scheduler |
| 10. 专业内容 | 公式、图表、题注、参考文献、化学式如何处理 | formula/reference/caption configs |
| 11. 计数口径 | Word-like 与业务规则如何并列 | CountProfile |
| 12. 对象保护 | 宏、OLE、Visio、修订、批注、文本框、内容控件、域如何处理 | ObjectPreflightPolicy |
| 13. 缺失策略 | 缺字段、缺图、缺附件、低置信度、输出冲突如何处理 | failure policy / diagnostics |
| 14. 内容显隐 | 一份事实源如何生成不同角色版本 | ContentVisibilityRule |
| 15. 多交付 | 输出哪些 docx、compare、report、manifest、zip、中间件 | DeliveryPreset / OutputConfig |
| 16. 批量策略 | 多记录如何输出、命名、失败隔离、汇总 | BatchPreset / MaterialBatchSelection |
| 17. UI 控件契约 | 控件、单位、命名是否与模板管理一致 | ScenePanel/shared UI |
| 18. 运行前证据 | 问题队列是否提示资料、对象、输出、插件边界风险 | Workbench issue queue |
| 19. 报告证据 | JSON/Markdown 是否解释配置、跳过、边界、产物 | report_writer |
| 20. 测试证据 | 架构、语义、失败、报告、UI 是否有测试 | pytest |

任何场景如果只能回答 1-6，仍只是配置草案。能回答 1-13，才有执行语义。能回答 1-20，才可以进入 L3/L4 讨论。

| 导入与 AI | 插件/输入助手 | 低置信度预检 + 人工确认 + 结构化中间产物 | 不应进入核心承诺，需统一插件入口和边界报告 |

## 9. 参数归属裁决规则

以后不要问“这个字段现在在哪个 dataclass”，而要问“它对用户任务意味着什么”。

| 参数/功能 | 模板 | 场景 | 资料包 | 会话 | 插件/人工 |
| --- | --- | --- | --- | --- | --- |
| 字体、字号、段距、缩进 | 默认外观基线 | 只有业务规则要求时覆盖 | 无 | 临时覆盖 | 无 |
| 左缩进/右缩进/段前/段后 | 使用模板管理同款控件与单位 | 场景若暴露必须同款控件 | 无 | 可临时调整 | 无 |
| 特殊缩进 | 模板中用“无/首行/悬挂 + 值”交互 | 场景覆盖也必须能切换，不允许只显示文本 | 无 | 可临时调整 | 无 |
| 表格边框、列宽、布局 | 默认表格样式 | 标书/技术/表单可因业务覆盖 | 无 | 可临时输出覆盖 | 无 |
| `w:trHeight` 行高 | 普通模板不应作为噪音参数 | 表单/套打/证书/报价的固定版位能力 | 无 | 可按记录覆盖 | 无 |
| 公式字体/编号外观 | 默认样式 | 论文/技术/试卷可覆盖 | 无 | 无 | 完整 LaTeX/复杂专业转换 |
| 公式输入/转换策略 | 无 | LaTeX/OMML/低置信度/Office fallback | 无 | 无 | 完整工程导入 |
| 参考文献外观 | 样式基线 | 是否处理、链接、检查范围 | Bib/CSL 来源可关联 | 本次文件 | citeproc/期刊规则插件 |
| 水印外观 | 默认颜色、角度、字号可作为基线 | 草稿/保密/内部/送审等状态策略 | 水印文字可来自字段 | 本次是否打开 | 权限/法律效力不判断 |
| 输出文件 | 无 | 交付版本、命名、报告、manifest | 资料包影响命名/目录 | 输出目录 | PDF/外部提交系统 |
| 资料字段 | 无 | 必填字段、缺失策略 | 具体值、图片、签章、附件 | 本次选用资料包 | 数据真实性不判断 |
| CountProfile | 无 | 计数口径、范围、报告解释 | 可带机构/期刊资料 | 本次 profile 选择 | 官方系统最终口径 |
| PDF/OCR/AI/复杂图形 | 无 | 只接收确认后的结构化结果 | 资产引用 | 本次导入文件 | 插件和人工确认 |

裁决句：

```text
影响“长什么样”先归模板；
影响“做不做、在哪做、失败怎么办、输出什么”归场景；
影响“具体填什么、用哪张图、哪份附件”归资料包；
影响“这一次路径和临时选择”归会话；
影响“专业判断、低置信度外部能力”归插件或人工确认。
```

## 11. 场景配置控件一致性规则

场景配置页必须继续继承模板管理控件体系。控件一致性不是视觉细节，而是参数边界治理。

### 11.1 必须复用

| 控件类型 | 场景页要求 |
| --- | --- |
| 下拉选择 | `StyledComboBox` |
| 开关 | `ToggleSwitch` / `FeatureToggleRow` |
| 线性表单 | `TemplateFormStack` + `template_form_row` |
| 多列版式参数 | `InspectorForm` / `TemplateFormGrid` |
| 字体 | `FontCombo` |
| 字号 | `SizeCombo` |
| 段距/行距/缩进/单位输入 | `SpacingInput` 或模板管理同源段落输入组件 |
| 长文本或多项列表 | `TextArea`，但必须有结构化校验摘要 |
| 多选对象 | 长期应抽成共享 multi-select/chip group，不在各页复制 `QCheckBox` 逻辑 |
| 单选策略 | 使用项目统一 radio/segmented control，不长期依赖原生 `QRadioButton` |

### 11.2 段落控件特别要求

如果场景页未来暴露段落样式覆盖：

- 左缩进、右缩进可以同一行；
- 段前、段后可以同一行；
- 特殊缩进必须可交互切换“无 / 首行 / 悬挂”；
- 特殊缩进为“无”时，值输入禁用并清晰置灰；
- 单位必须与模板管理一致；
- 不允许同一参数在模板页叫“左缩进”、场景页叫“左缩进值”或用不同单位；
- 不允许 UI 能设置，但 resolver/pipeline 不消费。

### 11.3 禁止模式

```text
禁止新建场景专用控件样式；
禁止用普通 QLineEdit 替代已有领域控件；
禁止同一参数在模板页和场景页单位不同；
禁止只写说明文字不提供可验证控件；
禁止显式展示“可配置”，但执行链路不消费；
禁止把业务必需能力藏进无结构的“高级设置”文本区。
```

## 12. 外部记录吸收结论

### 12.1 Count Engine 记录

必须吸收：

- 计数不是单一“字数”，而是 profile-driven multi-metric；
- Word-like 统计和学校/期刊/申报系统口径必须并列展示；
- CountProfile 必须有 included/excluded scopes；
- 报告必须说明口径差异，不承诺与官方系统 100% 一致；
- 中文学术、英文投稿、项目申报、试卷、披露等都需要自己的计数 profile。

落点：

```text
CountProfile 是场景合规能力，不是模板参数。
```

### 12.2 Exam Generator 记录

必须吸收：

- 试卷场景唯一事实源应是结构化 JSON；
- Markdown 只是预览/人工检查层；
- Word 是正式输出层；
- 学生版/教师版/答案版不能分别生成，必须同源显隐；
- 图片、公式、题图绑定是高频核心；
- 复杂几何图、AI 生图、专业学科制图进入插件边界。

落点：

```text
exam_teaching 的 L3 first slice 必须是
JSON schema -> Markdown preview -> Word render -> DeliveryPreset 显隐 -> report。
```

## 16. 最终结论

高层场景能力矩阵的下一阶段不应追求更多入口，而应追求更高成熟度：

```text
P0 场景稳定执行；
P1 family 逐个 L3 first slice；
P2 专业能力只进插件/人工确认边界；
所有参数有归属裁决；
所有 Word 风险面有策略；
所有高频请求有落点；
所有可见配置能被执行和报告消费。
```

当前最应该优先推进的不是“再列更多文档类型”，而是：

1. `form_batch_documents`：用 `w:trHeight`、内容控件、文本框预检、残留占位符和批量失败隔离闭合固定版式场景；
2. `exam_teaching`：用结构化题源和 DeliveryPreset 显隐闭合同源多版本；
3. `journal_en`：用 CountProfile、Bib/CSL first slice 和投稿包 manifest 闭合英文投稿；
4. `project_application` / `bidding`：用附件 inventory 和 package manifest 闭合资料包类高频场景；
5. `contract_delivery`：把已有 first slice 的成熟度、签署包和法律边界前台化补齐。

一句话收束：

```text
完善的矩阵不是“有很多功能点”，而是用户任何高频文档任务进来，
都能被放到正确层级，并沿着模型、控件、执行、报告、问题队列和测试
走到一个可解释的闭环。
```
