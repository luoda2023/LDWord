# 高层场景能力矩阵 V27 完整能力图谱与防遗漏规划（2026-06-19）

本轮继续围绕“目前功能点过于不完善，不能出现高频适用场景遗漏或边界不清”的要求做更高层规划。V27 不再把场景能力矩阵理解成一组导航入口，而是定义为一张可验收的业务地图：

```text
用户自然请求
-> 高频 coverage pack
-> workflow archetype
-> capability axis
-> Word/OOXML risk surface
-> ownership/control contract
-> request-cell / fixture / report / release gate
```

只有这条链路能解释清楚，才算一个高频场景被完整覆盖。

## 2. 完整能力矩阵的六个维度

### 2.1 用户自然请求维度

一个高频需求不能只靠内部场景名覆盖，必须有 request-cell：

| 状态 | 必须说明 |
| --- | --- |
| matched | 推荐落点、pack、family/profile、必要 preset |
| ambiguous | 需要用户选择的分歧点，例如“产品手册”到底是技术手册还是客户交付手册 |
| manual boundary | 为什么需要插件或人工确认 |
| negative | 为什么不应静默归入任何现有场景 |

当前 47 条样本已经形成基线，所有 pack 的 matched request-cell 深度都已达到至少 3 条；但这只是最低防遗漏线，不等于每个高频子场景都已达到 L5。后续仍要继续补真实业务说法、歧义裁决、人工边界和报告 drilldown。

### 2.2 高频场景包维度

12 个 pack 仍建议保持稳定：

| pack | 完整覆盖时必须能解释 |
| --- | --- |
| `quick_formatting` | 快速排版、模板基线、结构范围、对象安全、交付产物 |
| `chinese_academic` | 学校论文、字数口径、参考文献/公式/图表、提交包 |
| `english_journal` | 投稿规则来源、cover letter/revision、BibTeX/CSL、专业/外部规则边界 |
| `exam_education` | 题源事实、学生/教师/答案多版本、答题卡、复杂图形插件边界 |
| `bidding_materials` | 资质附件、正副本、签章素材、批量和资料包 |
| `official_policy` | 通知/函/纪要/制度汇编、编号/文号、正式/内部/归档版本 |
| `technical_long_docs` | SOP/接口/验收/书稿、目录/附录/索引、对象预检 |
| `application_reports` | 项目申报、产品售前、客户版/内部版、附件与限字 |
| `contract_delivery` | 字段一致性、修订/批注保护、签署包、法律意见边界 |
| `batch_forms` | HR、证明、登记表、固定版位、内容控件、批量失败隔离 |
| `professional_disclosure` | 报价、预算、ESG、专利、双语审阅，专业判断外置 |
| `import_ai_boundary` | PDF/OCR/LaTeX/AI/复杂图，置信度报告和人工确认 |

新增需求优先落到这些 pack 的 family/profile/schema/preset/plugin，不优先新增导航入口。

### 2.3 工作流维度

高频场景经常不是一种文档，而是一条工作流。至少要覆盖这些主路线：

| 主路线 | 高频触发 | 首选承载层 |
| --- | --- | --- |
| 模板规范化 | 套模板、统一格式、目录页码不对 | TemplateConfig + quick_formatting |
| 结构定位 | 只处理正文、附录、某些页、某些标题下 | FormatScopeConfig / CountProfile |
| 资料填充 | 公司、人员、项目、合同字段、签章素材 | MaterialSchema |
| 附件清单 | 资质、证照、图片、证明材料 | MaterialSchema attachment inventory |
| 规则计数 | 字数、页数、摘要限字、投稿口径 | CountProfile |
| 对象安全 | 域、修订、批注、OLE、内容控件、文本框 | ObjectPreflight |
| 多版本显隐 | 学生版/教师版、客户版/内部版、正式稿/审阅稿 | DeliveryPreset + ContentVisibilityRule |
| 批量生成 | Excel/JSON 一人一份、一项目一包 | BatchPreset |
| 对比审阅 | 修订稿、对比稿、审阅意见保留 | review_compare + ObjectPreflight |
| 提交归档 | ZIP、manifest、报告、资料包 | DeliveryPreset + artifact browser |
| 插件人工门 | OCR、PDF 转 Word、完整 LaTeX、AI 生成、法律/财务/IP | PluginManualGate |

规划原则：如果一个 pack 声称覆盖某个场景，但没有列出经过哪些工作流，就仍然是不完整覆盖。

### 2.4 能力轴维度

10 条能力轴是“完整”的最小问题集：

| 能力轴 | 不完整时的典型症状 |
| --- | --- |
| `input_fact_source` | Markdown/截图/人工口述被误当事实源 |
| `template_baseline` | 场景偷偷改外观，和模板管理冲突 |
| `material_schema` | 字段、图片、签章、附件没有契约 |
| `structure_scope` | 不知道处理哪些节、页眉页脚、脚注尾注 |
| `content_visibility` | 多版本靠散落 checkbox 或手工删除 |
| `count_profile` | 字数/页数只有一个数字，没有口径解释 |
| `object_preflight` | 域、修订、批注、OLE 被静默破坏 |
| `delivery_preset` | 输出版本、文件名、报告和资料包没有业务语义 |
| `batch_preset` | 批量失败不能隔离，无法追踪单记录 |
| `plugin_boundary` | 高风险导入和专业判断被核心静默承诺 |

L5 场景必须能回答所有相关能力轴；不相关的轴也要说明“不适用”的原因。

### 2.5 Word/OOXML 风险维度

完整矩阵必须从 Word 包结构反推风险，而不是只看 UI 参数：

| Word 面 | 高频场景 | 必须进入链路 |
| --- | --- | --- |
| `w:pPr` / `w:rPr` / styles | 全部排版任务 | 模板基线、控件契约、修复路由 |
| numbering | 公文、标书、技术、论文 | 编号保留/重建策略 |
| tables / grid / `w:trHeight` | 表单、试卷、标书、合同 | 表格策略、固定版位 profile |
| fields | 目录、页码、交叉引用、合同字段 | ObjectPreflight + 报告 |
| comments / revisions | 合同、投稿修回、审阅稿 | 保留/阻断/报告 |
| content controls | 套打表单、合同模板 | tag/alias 映射与残留检查 |
| textboxes / shapes | 固定表单、证书、版式稿 | anchored field mapping |
| headers / footers / sectPr | 公文、论文、签署稿、归档版 | 模板外观与交付版本边界 |
| relationships / media | 图片、附件、签章、OLE | 资料包 inventory + object preflight |
| hidden text | 多版本、审阅、内部稿 | 显隐规则与版本报告 |

因此 `TableConfig.row_height_pt` 这类参数不能作为普通表格样式游离存在：它只有在 `batch_forms`、`exam_education`、证书/套打等 fixed-layout profile 中才有业务含义，并且必须接 `w:trHeight` 执行、UI、报告和测试。

## 3. 边界裁决规则

| 需求类型 | 应归属 | 不应归属 |
| --- | --- | --- |
| 左右缩进、段前段后、行距、字体、表格基础线 | TemplateConfig / control contract | 场景专属私有控件 |
| “学生版/教师版/答案版/客户版/内部版/签署版” | DeliveryPreset | 普通输出 checkbox |
| 字段、图片、签章、附件事实 | MaterialSchema | 模板样式 |
| 字数、页数、摘要限字、投稿规则 | CountProfile / rule source governance | 模板或自由文本说明 |
| 水印状态、内部/正式/归档业务语义 | Scene / DeliveryPreset | 模板视觉参数 |
| 水印颜色、角度、大小、版心外观 | TemplateConfig | 场景业务开关 |
| 公式输出策略、低置信度处理 | Scene + Plugin boundary | 字体样式控件 |
| 公式字体、字号、间距 | TemplateConfig | 导入/转换策略 |
| PDF/OCR/完整 LaTeX/AI 内容质量 | PluginManualGate | 核心排版场景 |
| 法律、财务、专利、医学判断 | PluginManualGate + 人工确认 | 合同/申报/报告普通场景 |

硬规则：一个参数如果同时影响外观、业务版本、事实来源或专业判断，必须拆到对应承载层；不能为了 UI 简单把它做成一个“场景开关”。

## 4. 场景配置控件样式一致性

场景配置必须继承模板管理中的控件语言。这里的“一致”包含命名、布局、单位、启禁逻辑、写回语义和报告解释。

| 控件/参数 | 场景配置必须做到 | 不完整表现 |
| --- | --- | --- |
| 左缩进 / 右缩进 | 同行布局，单位和 stepper 与模板管理一致 | 分两行、名称不同、单位不同 |
| 段前 / 段后 | 同行展示，使用模板管理同名控件 | 场景里改叫前距/后距 |
| 特殊缩进 | 有无/首行/悬挂的可交互切换，值输入随类型启禁 | 只能显示“无”，不能切换 |
| 行距类型 / 行距值 | 类型和值绑定，固定值/倍数/最小值语义清楚 | 类型和值互相脱节 |
| 表格行高 | 仅 fixed-layout profile 暴露，写入 `w:trHeight` | 普通表格里暗藏残留参数 |
| 水印 | 状态和版本归场景/交付，视觉归模板 | 一个控件同时改文本、颜色、版本 |
| 输出版本 | DeliveryPreset 编辑器和 artifact 开关 | 多个散落 checkbox 无法解释业务版本 |
| 公式策略 | 转换/置信度归场景，样式归模板，复杂转换归插件 | 把完整 LaTeX 当普通样式 |

这条约束的目的不是视觉统一，而是防止模板、场景、执行、报告四层对同一个参数产生不同解释。

## 6. 成熟度准入

| 等级 | 准入条件 | 禁止行为 |
| --- | --- | --- |
| L0 | 只在文档中观察到高频需求 | 进入 UI 或执行 |
| L1 | 有 planning family、边界、能力轴草案 | 冒充可执行场景 |
| L2 | 有 schema/preset/profile 草案和 request-cell | 宣称完整闭环 |
| L3 | UI、执行、报告、测试至少一条主链路可跑 | 忽略边界和对象风险 |
| L4 | 真实 fixture、repair route、artifact browser、release gate | 对高风险插件能力静默放行 |
| L5 | 9 个 completeness gate、相关能力轴、Word 风险面、request-cell drilldown 全部闭合 | 继续使用口头规划代替证据 |

完整的 L5 不要求所有专业能力都由核心实现，但要求所有不承诺项都能在 UI、报告和测试中被用户看见。

## 9. 本轮结论

完善的高层场景能力矩阵不是“把更多行业名塞进侧边栏”，而是让每个高频用户请求都能回答：

1. 它属于哪个 pack、family/profile、preset 或 plugin；
2. 它经过哪些工作流；
3. 它依赖哪些资料事实源；
4. 它会触碰哪些 Word/OOXML 风险面；
5. 它的 UI 控件是否复用模板管理语言；
6. 它的边界和不承诺项是否在 UI、报告、测试里同现；
7. 它是否能从 request-cell 追到 fixture、report artifact 和 release gate。
