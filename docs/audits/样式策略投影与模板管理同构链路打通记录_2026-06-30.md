## 1. 本轮判断

这轮问题不再是单个卡片文案“不说人话”，而是样式区的状态入口没有完全和模板管理保持同构。

模板管理已经形成了比较清晰的链路：

```text
build_template_body_style_projection(...)
-> StyleObjectProjection
-> StyleManagementBlock.apply_style_object_projection(...)
-> 来源 / 状态 / 编辑区 / 预览区
```

而场景分区样式在上一轮之前仍有一段分散链路：

```text
场景面板手动 set toggle checked
场景面板手动 set row visible
场景面板手动 set restore button
场景面板手动 apply comparison projection
```

这会导致三个问题：

1. 样式对象看起来已经统一，但控件状态仍散落在业务面板里。
2. 模板管理的组件复用边界不清晰，场景样式仍像独立实现。
3. UI 文案很容易堆成解释型文本，因为状态来源没有被结构化表达。

本轮目标是把策略控件也纳入样式对象投影，让样式区真正靠一份 projection 驱动。

## 2. 本轮已打通的主链路

新增后的场景分区样式链路为：

```text
build_scene_section_style_projection(...)
-> StyleObjectProjection.policy
-> StyleManagementBlock.apply_style_object_projection(...)
-> StyleRuleControlDeck.apply_projection(...)
-> StylePolicyControlDeck / StylePolicyToggleList / StyleDifferenceSummarySlot / 批量动作按钮
```

也就是：

```text
样式对象投影
  ├─ owner_state       驱动当前样式归属与编辑状态
  ├─ preview_projection 驱动样式预览
  ├─ difference        驱动差异摘要
  └─ policy            驱动策略开关与批量动作
```

这一步之后，策略控件不再只是“场景样式自己的控件”，而是 `StyleManagementBlock` 能够统一分发的样式对象子投影。

## 3. 代码落点

### 3.1 StyleObjectProjection 增加 policy

文件：

```text
src/shared/ui/style_object_projection.py
```

新增字段：

```text
policy
```

它用于承载策略区状态，包括开关、可见性、差异摘要和批量恢复动作。

### 3.2 StyleManagementBlock 统一分发 policy

文件：

```text
src/shared/ui/style_management_block.py
```

新增分发逻辑：

```text
if style_object.policy is not None:
    self._apply_slot_projection(self._rule_control, style_object.policy)
```

这让规则控件和来源、预览、差异、回执一样，都从统一样式对象入口进入。

### 3.3 场景样式 builder 产出 policy

文件：

```text
src/ui/panels/style_object_projection_builders.py
```

新增：

```text
build_scene_section_style_policy_projection(...)
```

它负责生成：

- 每个分区样式开关的 `checked`
- 每个分区样式开关的 `visible`
- 当前选中分区的差异摘要
- “全部跟随模板”按钮状态
- “撤销恢复”按钮状态

`build_scene_section_style_projection(...)` 已把这份 policy 放入 `StyleObjectProjection.policy`。

### 3.4 场景面板补齐撤销快照输入

文件：

```text
src/ui/panels/scene_panel.py
```

`_sync_style_editor()` 调用 builder 时传入：

```text
undo_restore_all_labels=self._restore_all_style_snapshot_labels()
```

这样“撤销恢复”不再只能靠面板后置手动设置，至少已经能进入 projection 链路。

## 4. 职责边界重新划分

### 4.1 Builder 负责状态解释

`style_object_projection_builders.py` 负责把业务状态翻译成 UI 可消费的 projection：

- 分区是否启用
- 分区是否独立样式
- 哪些分区可见
- 哪些批量动作可用
- 当前分区和模板的差异

它不关心 QWidget，也不操作控件。

### 4.2 StyleManagementBlock 负责分发

`StyleManagementBlock` 只做 projection 分发：

- source 发给来源槽
- difference 发给差异槽
- preview 发给预览槽
- policy 发给规则控件
- receipt 发给回执槽

它不解释业务含义。

### 4.3 StylePolicyControlDeck 负责控件执行

`StylePolicyControlDeck` 只负责把 policy projection 落到控件状态：

- 创建或更新开关项
- 同步 checked
- 同步 visible
- 同步差异摘要
- 同步批量动作按钮

它不读取场景，也不读取模板。

### 4.4 StyleRuleControlDeck 只保留场景文案包装

`StyleRuleControlDeck` 现在应该只是场景分区样式的薄包装：

```text
StyleRuleControlDeck -> StylePolicyControlDeck
```

它只提供场景特有文案，例如“全部跟随模板”“独立样式”。

## 5. 和模板管理的一致性

本轮之后，两条链路的形状更接近了。

模板正文样式：

```text
build_template_body_style_projection
-> StyleObjectProjection
-> StyleManagementBlock
-> editor / owner status
```

场景分区样式：

```text
build_scene_section_style_projection
-> StyleObjectProjection
-> StyleManagementBlock
-> owner status / policy controls / difference / preview / editor
```

差异只应该来自业务能力不同，而不是组件组织方式不同。

场景样式比模板样式多出来的部分应该是：

- 分区开关
- 分区差异
- 跟随模板/独立样式动作

这些现在被收束到 `policy`，而不是散落在场景面板里。

## 6. 可读性优化方向

界面上不应该继续出现大段解释型文本。用户真正需要的是：

```text
当前对象是什么
当前是否跟随模板
哪些分区已独立
当前能不能编辑
点哪里能恢复
预览是否和当前状态一致
```

建议后续把样式策略区规划成三个板块：

```text
当前分区
  状态：跟随模板 / 独立样式 / 未处理
  操作：开启独立样式 / 跟随模板

全部分区
  每个分区一个短标签开关
  隐藏未启用处理范围的分区

差异与恢复
  差异摘要
  全部跟随模板
  撤销恢复
```

需要删除或迁移到 tooltip/status 的冗余文本包括：

- “手动控制所有功能开关与处理范围”
- “策略：重建编号 · 9/9个分区 · 0项功能”
- 英文式的内部字段描述
- 大段风险说明直接塞进卡片正文

界面正文应该说结果和动作，内部解释应该进入 tooltip、状态属性或文档。

## 7. 当前仍未彻底完成

这轮已经打通 policy 主链路，但还不能声明完全优秀。

仍存在以下兼容层：

1. `_refresh_style_override_summary()` 已不再直接调用 `set_summary_items(...)` 和批量按钮 setter，但 wrapper API 仍保留。
2. `SceneStyleRulesBlock` / `SceneStyleOverrideSection` 仍暴露旧的直连 API，便于兼容现有跳转和测试。
3. `StylePolicyToggleList` 已落地，旧 `StyleOverrideToggleList` 仅作为兼容包装保留。
4. 场景样式 summary 已并入 `build_scene_section_style_projection(...)`，但初始化空态仍使用 summary helper。
5. UI 可见文案还没有做最终减法，当前只是结构链路先归一。

这些点不是 bug，但说明系统仍处于“兼容迁移期”。

## 8. 下一轮必要功能

建议下一轮继续做四件事：

1. 逐步让 `SceneStyleRulesBlock` / `SceneStyleOverrideSection` 的旧 setter 只作为兼容入口。
2. 通用 policy API 已进入主链路，旧 override API 作为场景兼容别名保留。
3. 对样式区可见文案做一次减法，只保留状态、动作和必要标签。
4. 检查执行前复核是否需要同样的 policy/summary 只读区，而不是继续堆说明文本。

目标形态应为：

```text
scene state changed
-> build_scene_section_style_projection(...)
-> StyleManagementBlock.apply_style_object_projection(...)
-> all slots update
```

场景面板只负责响应用户意图，不再手动维护每个控件的状态。
