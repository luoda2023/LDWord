本文继续深化高层场景能力矩阵。V7 已经回答了“应该有哪些高频任务族、哪些归顶层、哪些归 planning family、哪些归插件边界”。V8 进一步回答：

## 2. 一句话结论

当前矩阵的问题不再是“完全没有覆盖”，而是：

```text
名字覆盖已经开始变多，但很多场景还没有被拆成可执行、可验证、可解释的能力单元。
```

完善的场景能力矩阵应同时满足五个条件：

1. 高频文档任务没有大类遗漏；
2. 高频工作流都有归属，不被误做成孤立功能；
3. 每个场景都有输入、资料、范围、模板、合规、安全、交付和报告槽位；
4. 模板、场景、资料包、合规 profile、交付 preset、插件边界清楚；
5. UI、resolver、pipeline、Workbench、report、tests 能证明它们消费的是同一套事实。

如果一个需求只能落到“加一个开关”，但不能落到“哪个任务族、哪个工作流、哪个能力槽位、哪个 first slice、哪个报告证据”，它就还没有进入高层场景矩阵。

## 3. 当前事实基线

### 3.1 已有可执行顶层场景

`src/ui/panels/workbench/scene_presets.py` 当前有 6 个可执行入口：

| 场景 | 当前定位 | 主要风险 |
| --- | --- | --- |
| `custom` | 手动组合 | 容易被滥用成“所有未规划能力的兜底” |
| `thesis` | 论文排版 | 描述仍含“期刊论文·学术报告”，边界过宽 |
| `bidding` | 标书排版 | 资料包、签章、附件 inventory 还需更完整 |
| `official` | 公文排版 | 状态水印、编号保留、正式/内部稿仍需交付语义 |
| `technical` | 技术文档 | OLE/Visio/嵌入 Excel 保护与 Workbench 可见性仍需强化 |
| `report` | 通用报告 | 需要保持轻量，不能承接所有专业 profile |

这 6 个入口是合理 P0，但不能代表矩阵完整。

### 3.2 已有 planning family

`src/config/scene_family_registry.py` 已登记 12 个 planning family：

```text
journal_en
exam_teaching
project_application
contract_delivery
hr_batch_documents
meeting_policy_documents
product_sales_documents
long_document_publishing
form_batch_documents
qualification_archive_packages
finance_quote_documents
ip_patent_documents
```

这说明高频场景覆盖面已经从“6 个入口”扩展到“入口 + family + profile”。但 majority 仍处于 L1/L2：有规划契约，不等于可执行承诺。

### 3.3 已有模型槽位

`SceneWorkspace` 已经具备较好的承载基础：

| 模型 | 已能承载 |
| --- | --- |
| `InputSourceProfile` | 输入格式、Markdown/LaTeX 策略、资料包要求、缺失策略 |
| `ComplianceProfile` | 合规 profile、count profile、检查范围、失败策略 |
| `ObjectPreflightPolicy` | OLE、宏、修订、批注、文本框、域等对象风险策略 |
| `DeliveryPreset` | 多版本输出、目标模板、产物开关、结构化中间产物 |
| `ContentVisibilityRule` | 不同交付版本的内容显隐 |
| `MaterialSchema` | 字段、图片、签章、附件、多实体资料契约 |

因此后续的重点不是再发明一套大模型，而是让这些槽位被所有高频场景明确使用，并在 UI、执行和报告里闭合。

## 4. 完备性审计模型

V8 建议把场景矩阵拆成三条轴、一张验收表。

### 4.1 任务族轴

回答“用户自然会说自己在做什么”。

示例：

```text
写论文、改投稿、做标书、出公文、生成试卷、填合同、批量出证明、整理资质包、汇编制度、整理书稿。
```

任务族决定产品心智和入口归属。

### 4.2 工作流轴

回答“这件事的主要动作是什么”。

示例：

```text
快速规范化、结构识别、资料填充、多版本生成、批量生成、计数合规、审阅对比、对象保护、附件 inventory、投稿/提交包。
```

工作流决定能力组合。很多高频需求不是新场景，而是横切工作流。

### 4.3 风险与边界轴

回答“哪些不能被核心系统承诺”。

示例：

```text
法律意见、财务审计判断、专利授权质量、AI 内容质量、完整 LaTeX 工程无损转换、复杂学科图形生成、OCR 无损版式复原。
```

风险轴决定哪些归插件、专业扩展或人工确认流程。

### 4.4 能力槽位验收表

每个可承诺场景至少要回答 18 个槽位：

| 槽位 | 必须回答 | 主要承载 |
| --- | --- | --- |
| 1. 用户任务 | 用户到底在完成什么文档工作 | scene/family/profile 名称 |
| 2. 输入契约 | docx、markdown、json、xlsx、bibtex、LaTeX、PDF/OCR 中哪些可用 | `InputSourceProfile` |
| 3. 结构化事实源 | 是否有 JSON/schema/intermediate/Markdown preview | 结构化输入、intermediate artifact |
| 4. 资料契约 | 字段、图片、签章、附件、多实体资料是什么 | `MaterialSchema` |
| 5. 处理范围 | 正文、摘要、目录、参考文献、附录、页眉页脚哪些处理 | `FormatScopeConfig` |
| 6. 定位方式 | 自动识别、页码范围、关键词、样式锚点、内容控件 | scope UI / parser |
| 7. 模板基线 | 外观基线和兼容模板是什么 | `TemplateConfig` |
| 8. 场景覆盖 | 哪些模板参数可被业务任务覆盖 | scene feature overrides |
| 9. 能力组合 | 标题、页面、表格、公式、引用、填充、清理等哪些启用 | `module_switches` |
| 10. 专业对象 | 公式、化学式、图片、题注、参考文献、内容控件如何处理 | feature config + modules |
| 11. 计数合规 | 字数、词数、图表数、附件数采用什么口径 | CountEngine profile |
| 12. 对象安全 | OLE、Visio、嵌入 Excel、宏、修订、批注、域如何处理 | ObjectPreflight |
| 13. 缺失策略 | 缺字段、缺图、缺附件、低置信度、残留占位符怎么办 | failure policy / diagnostics |
| 14. 内容显隐 | 答案/解析、内部段落、签署内容、水印状态如何按版本切换 | `ContentVisibilityRule` |
| 15. 多版本交付 | final/review/student/teacher/signing/submission 等如何生成 | `DeliveryPreset` |
| 16. 批量策略 | 多实体、多模板、多文件、失败隔离、汇总报告 | `BatchPreset` |
| 17. 可见证据 | Workbench、报告、artifact browser 能否解释结果 | payload/report/UI state |
| 18. 测试证据 | registry、UI、pipeline、report、artifact 是否有测试 | pytest |

成熟度判断：

- 缺 1-8：场景边界不清；
- 缺 9-13：执行行为不清；
- 缺 14-16：交付不可验收；
- 缺 17-18：只能算规划，不能算承诺。

| 表单/套打批量 | 申请表、登记表、证明表、固定版式批量 | P1 候选 `form_batch_documents` | registry 有 | 固定版位填充 + 残留占位符 + 行高/版位保护 | 不替代表单系统 |
| 资质/证照材料包 | 企业资质、证书扫描件、附件清单 | P1 横切 `qualification_archive_packages` | registry 有 | 附件 inventory + 缺项报告 + archive manifest | 不鉴别证照真伪 |
| 长文档/书稿出版 | 书稿、手册合集、章节汇编、索引 | P1 候选 `long_document_publishing` | registry 有 | chapter inventory + 域/交叉引用保护 + proof/archive | 不替代出版社排版 |
| 财务/报价/审计格式 | 报价单、预算说明、结算附件 | P2 `finance_quote_documents` 或插件 | registry 有 | 表格字段 + 附件报告 + 专业边界提示 | 不做财务审计判断 |
| 知识产权材料 | 专利交底、说明书、权利要求草稿 | P2 `ip_patent_documents` 或插件 | registry 有 | 章节/图号 inventory + review copy | 不判断专利法律质量 |
| 年报/ESG/披露材料 | 年报、社会责任、ESG、合规披露 | P2 profile 组合 | V7 提及，registry 尚无专属 family | 长文档 + 表格 + 附件 + 审阅包 | 不做审计或披露结论 |
| 翻译/双语材料 | 双语合同、双语说明书、译文审校稿 | P2 profile/插件 | 当前缺显式落点 | 双语段落/表格样式 + 术语表 + 对照审阅稿 | 不保证翻译质量 |
| PDF/扫描件整理 | PDF 转 Word、扫描件 OCR、版式复原 | P2/插件 | 当前作为边界项 | 导入预检 + OCR 置信度 + 人工确认 | 不承诺无损重建 |
| 完整 LaTeX 工程 | `.tex` 学位论文、投稿工程 | 插件 | 明确边界 | 高级导入 + 宏包/class 风险报告 | 核心只支持公式片段 |
| 复杂学科图形 | 几何图、电路图、结构式、流程图 | 插件 | 明确边界 | 图形 schema + 预览 + 插入 | 核心优先通用图片 |
| AI 内容生成 | 生成正文、生成试卷、生成标书内容 | 插件/输入助手 | 明确边界 | 结构化输出 + 人工确认 + 来源记录 | 不作为核心排版承诺 |

本轮新增的防遗漏判断：

- “翻译/双语材料”应被显式记录。它不一定是顶层场景，但在合同、说明书、投稿和公文中高频；核心只做双语版式、术语字段和对照审阅，不承诺翻译质量。
- “年报/ESG/披露材料”应继续保留为 P2 profile 组合，避免在通用报告或财务材料中消失。
- “PDF/扫描件整理”是高频输入入口，但不是场景本体，应归高级导入或 OCR 插件。
- “培训/课程资料”不能完全被试卷吞掉，应作为教育 profile 覆盖讲义、练习册、教师手册。

## 6. 工作流覆盖矩阵

高频工作流也必须有落点，否则用户会看到场景名，却找不到真实能力。

| 工作流 | 高频使用场景 | 应归属 | 当前风险 | 完整化要求 |
| --- | --- | --- | --- | --- |
| 快速规范化 | 通用报告、技术、公文、自定义 | P0 场景 + 模板 | 容易过度开启专业能力 | 保守默认、清楚显示启用能力 |
| 结构识别 | 论文、长文档、标书、书稿 | scope + parser | 只露出 sections，不足以处理正文起点和关键词 | 页码范围、关键词、样式锚点产品化 |
| 资料填充 | 标书、公文、合同、HR、项目 | material schema + fill modules | schema 与执行/报告仍不够统一 | 缺字段/缺图策略必须进入报告和 Workbench |
| 图片/附件 inventory | 标书、申报、资质包、产品资料 | material schema + compliance | 图片角色和 PDF 附件还没有完整验收 | 角色、缺项、路径、manifest、归档包 |
| 同源多版本 | 试卷、合同、公文、投稿、标书 | DeliveryPreset + visibility rules | 显隐规则已开始，但结构化源不足 | 同一事实源、多 preset 输出、差异报告 |
| 批量生成 | HR、表单、标书陪标、证明 | BatchPreset + entity profiles | 成功/失败隔离与汇总还需增强 | 单项失败不污染其他输出 |
| 多口径计数 | 论文、投稿、申报、试卷 | CountEngine profile | profile 来源和范围解释仍弱 | 报告解释计数口径和纳入/排除范围 |
| 对象保护 | 技术、合同、标书、长文档 | ObjectPreflight | 报告侧增强，运行前 UI 仍不够 | finding -> skip -> artifact 的前台可见链 |
| 审阅对比 | 合同、技术、投稿修回、公文内审 | compare artifacts | 文本级已有，格式级/修订策略不足 | review preset、变更报告、修订保留策略 |
| 提交/投稿包 | 投稿、申报、标书、资质包 | DeliveryPreset + manifest | 包结构 profile 未稳定 | package manifest、缺项报告、目标模板 |
| 固定版式套打 | 表单、证书、报价单、申请表 | form_batch profile | 行高/版位仍是残留缺口 | 内容控件、表格行高、占位符残留 |
| 归档复用 | 长文档、项目、标书、HR | intermediate + archive package | artifact browser 汇总不足 | 报告、manifest、中间产物统一呈现 |

结论：工作流覆盖不应被动跟随场景。`CountEngine`、`ObjectPreflight`、`DeliveryPreset`、附件 inventory、批量失败隔离都应作为横切能力进入矩阵，而不是分散在个别场景里。

## 7. 能力域 V8

V8 建议稳定为 18 个能力域，其中 16 个来自 V7，新增“导入转换”和“附件 inventory”两个显式域，用于避免 PDF/OCR、附件包、资质包这类高频需求消失。

| 能力域 | 说明 | 不应误解为 |
| --- | --- | --- |
| `input_contract` | 输入格式、来源、结构化程度 | 文件选择器 |
| `import_conversion` | PDF/OCR/LaTeX/Markdown 导入风险与降级 | 核心无损转换承诺 |
| `structured_source` | JSON/XLSX/schema/intermediate 事实源 | Markdown 最终排版源 |
| `material_schema` | 字段、图片、签章、附件角色 | 本次具体资料值 |
| `attachment_inventory` | PDF/图片/证照/补充材料清单与缺项报告 | 证照真伪判断 |
| `template_baseline` | 页面、样式、页眉页脚、表格等外观基线 | 场景策略 |
| `processing_scope` | 正文、摘要、目录、附录、附件范围 | 简单模块开关 |
| `structure_formatting` | 标题、编号、目录、分节 | 专业内容判断 |
| `table_figure_caption` | 表格、图片、题注、图表目录 | 图像内容识别真伪 |
| `formula_symbol` | OMML、LaTeX 片段、化学式、公式编号 | 完整 LaTeX 工程转换 |
| `citation_reference` | 引用、参考文献、Bib/CSL | 自动保证学术合规 |
| `count_compliance` | 多口径计数、规则匹配、范围解释 | 单一字数统计器 |
| `object_safety` | OLE、Visio、宏、修订、批注、域保护 | 全量重建 Word |
| `field_fill` | 字段替换、来源填充、残留扫描 | 资料真实性验证 |
| `visibility_variant` | 答案/解析、内部/正式、签署/审阅显隐 | 重新生成不同内容 |
| `review_compare` | 对比稿、修订稿、变更报告 | 法律/技术审查结论 |
| `delivery_package` | 多版本输出、manifest、ZIP、归档结构 | 单一输出路径 |
| `batch_orchestration` | 多实体、多文件、失败隔离、汇总 | 一次性循环执行 |
| `profile_governance` | 学校、期刊、申报指南、招采规则来源与版本 | 无来源硬编码 |
| `plugin_boundary` | AI、OCR、法律、财务、复杂图形等专业扩展 | 核心功能逃避实现 |

注：`plugin_boundary` 是治理能力，不是具体功能。它必须在 UI 和报告中解释“核心做什么、不做什么、可交给什么扩展”。

## 8. 场景与模板边界再收紧

场景配置不能变成第二套模板管理。建议继续按下面规则判断归属。

| 参数族 | 模板侧负责 | 场景侧负责 | 资料/会话侧负责 |
| --- | --- | --- | --- |
| 段落/标题样式 | 字体、字号、缩进、段前段后、行距 | 哪些分区使用哪类样式策略 | 本次临时覆盖 |
| 表格 | 边框、默认列宽、默认行高、表头样式 | 固定表单/套打是否锁定行高和版位 | 表格数据 |
| 公式 | 字体、字号、编号样式、表格布局 | 是否转换 LaTeX 片段、低置信度如何处理 | 本次公式源 |
| 输出 | 默认 artifact 开关 | final/review/student/signing/submission preset | 输出目录、文件名临时覆盖 |
| 水印 | 视觉样式、颜色、角度、透明度 | 草稿/内部/保密/签署版是否启用 | 水印文字来自资料或本次状态 |
| 页眉页脚 | 版式、字段样式、页码样式 | 公文/投稿/签署版是否切换内容策略 | 当前文档字段值 |
| 引用/参考文献 | 参考文献段落样式 | 是否启用引用链接、Bib/CSL、顺序检查 | 本次 Bib/CSL 文件 |
| 对象保护 | 不负责 | 预检、阻断、跳过、降级、解释 | 本次用户确认 |

特别补充：

- `TableConfig.row_height_pt` 不能继续作为无人消费的残留参数。V8 下它应有两个明确去向：模板默认表格行高，或表单/套打场景的行高锁定策略。否则应从模型中退场。
- 水印不是“模板里的装饰开关”。模板定义水印长相，场景定义文档状态和交付版本是否启用水印。
- 输出不是模板能力。模板只定义外观，场景和会话定义产物形态与输出目标。

## 9. 场景配置控件一致性要求

场景配置中的控件样式必须与模板管理保持同一套语言。原因不是视觉统一本身，而是防止同一参数在两个地方呈现出不同语义。

### 9.1 控件语义

| 参数类型 | 控件要求 |
| --- | --- |
| 单选策略 | radio 或 segmented control |
| 多选能力 | checkbox 或 flow checkbox |
| 数值 + 单位 | 与模板管理一致的 spin/spacing input |
| 文本字段 | 统一 line edit / text area |
| 版本 preset | 列表 + 详情，不用散落按钮 |
| 开关能力组 | 与模板管理一致的 toggle/checkbox 视觉 |
| 风险策略 | 组合框 + 明确状态 badge |
| 高风险确认 | 独立确认区，不混入普通表单 |

### 9.2 单位与命名

必须统一：

- 字符单位：字、词、字符、characters no spaces 要在 CountEngine 报告中解释；
- Word 尺寸单位：磅、厘米、字距、行距不能在不同页面换叫法；
- 左缩进、右缩进、段前、段后等布局项与模板管理保持相同命名；
- 特殊缩进、行距类型、水印模式、输出版本必须可交互切换，而不是只展示文字。

### 9.3 不允许出现的 UI 形态

- 场景页重新发明一套不同样式的输入框、下拉框、开关；
- 用一个“功能参数”大表单承载公式、输出、水印、资料、批量等完全不同语义；
- 把专业边界写成普通说明文字但不进入报告；
- 让用户看到“场景支持某能力”，但 Workbench 结果、报告和 artifact browser 没有证据。

## 10. 外部技术记录吸收边界

### 10.1 CountEngine 记录

必须吸收：

- 不做单一字数统计器，做 profile-driven multi-metric CountEngine；
- 同时支持 Word-like words、中文字符、英文 words、字符数、段落、章节、图、表、公式、参考文献、附件等口径；
- 报告必须说明纳入/排除范围；
- `thesis_cn`、`journal_en`、`project_application`、`exam_teaching` 共用引擎但使用不同 profile。

不能吸收为：

- 独立“字数统计场景”；
- 写死在论文场景里的学校规则；
- 承诺与 Word、学校系统、投稿系统完全一致。

### 10.2 试卷技术记录

必须吸收：

- JSON/结构化数据是机器事实源；
- Markdown 只做预览和人工检查；
- Word 是正式交付；
- 学生版、教师版、答案版、解析版必须同源渲染；
- 答案、解析、知识点永远保留在结构化数据中，显隐由 DeliveryPreset 控制。

不能吸收为：

- AI 内容生成核心承诺；
- 分别生成多个版本；
- 复杂几何图、电路图、结构式自动生成的一次性核心需求。

## 11. 当前最需要补的断点

## 12. 推荐推进顺序

### 12.1 先做场景收口，不先加入口

近期不建议继续增加顶层场景。应先把 P0 和关键 P1 的 first slice 做成闭环。

优先队列：

1. `contract_delivery`：字段一致性 + 修订/批注保护 + review/signing preset + Workbench 可见；
2. `count_compliance`：CountEngine profile governance，覆盖 thesis/journal/project 三类；
3. `exam_teaching`：结构化题源 + student/teacher/answer 同源渲染；
4. `form_batch_documents`：固定版式填充 + 残留占位符 + 行高/版位保护；
5. `qualification_archive_packages`：附件 inventory + 缺项报告 + 归档 manifest；
6. `journal_en`：word/display count + Bib/CSL + submission package。

### 12.2 再做边界场景 registry 补记

建议后续至少补两个 planning 归属，不一定立即写代码：

| 建议补记 | 推荐落点 | 原因 |
| --- | --- | --- |
| `bilingual_translation_documents` | P2 profile/plugin boundary | 双语合同、双语说明书、译文审校高频，但核心不保证翻译质量 |
| `regulated_disclosure_documents` | P2 profile combination | 年报、ESG、披露材料高频，涉及长文档/财务/附件/审阅组合 |

这两类不应抢顶层入口，但应进入矩阵，防止后续被遗漏。

### 12.3 每个 first slice 都必须有四件证据

任何 family 从 L1 推进到 L3/L4，必须同时补：

1. registry/schema 证据；
2. ScenePanel 或 Workbench 可见证据；
3. pipeline/report 输出证据；
4. pytest 锁定证据。

缺其中任何一个，都只算“局部实现”，不能算场景能力闭环。

## 13. 最终验收句

V8 后续所有场景需求都按这句话验收：

```text
一个高频任务族，必须能映射到明确工作流；
一个工作流，必须能映射到能力槽位；
一个能力槽位，必须能映射到模型字段、UI 控件、执行消费、报告证据和测试。
```

只有这条链路成立，才算高层场景能力矩阵的一部分。
