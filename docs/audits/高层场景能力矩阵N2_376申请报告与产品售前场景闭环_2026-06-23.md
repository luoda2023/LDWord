## 2. 本轮实现内容

### 2.1 MaterialSchema

`project_application_materials_v1` 新增可选字段：

- `submission_system_id`
- `submission_rule_source_id`
- `submission_system_status`
- `external_submission_boundary_note`

`product_assets_v1` 新增可选字段：

- `asset_source_manifest`
- `asset_consistency_policy`
- `customer_internal_version_policy`
- `quote_boundary_signal`

`case_study_assets_v1` 新增可选字段：

- `case_evidence_source`
- `case_approval_status`

这些字段用于让项目申报和产品售前资料包保留规则来源、申报系统边界、资产一致性和报价/正文歧义处理证据；它们不改变既有必填字段，不把外部平台状态或营销真实性变成核心自动判定。

### 2.2 Sample Fixture

项目申报 fixture 增强：

- `application_reports_project_attachment_degraded` 增加 `submission_system_boundary_report`
- `application_reports_project_budget_manual_boundary` 增加 `rule_source_governance`、`submission_system_boundary_report`

产品/售前 fixture 增强：

- `application_reports_product_sales_assets` 增加 `asset_consistency_report`、`quote_body_disambiguation`
- `application_reports_product_asset_degraded` 增加 `asset_consistency_report`、`quote_body_disambiguation`
- `application_reports_product_version_manual_boundary` 增加 `asset_consistency_report`、`quote_body_disambiguation`

这样项目规则来源、外部申报系统边界、产品资产一致性、报价与正文歧义不再是成熟度文案里的缺口，而是可被 fixture、报告和场景概览引用的证据。

### 2.3 场景概览投影

新增 `build_application_report_evidence_summary_items(scene)`，并接入 `build_scene_overview_summary_items(scene)`。

它会在 `application_reports`、`project_application`、`product_sales_documents` 场景中显示：

- schema：`project_application_materials_v1`、`product_assets_v1`、`case_study_assets_v1`

- fixture：项目申报和产品/售前相关 DOCX fixtures

## 3. 场景视角复核

项目申报核心链路：

1. 用户选择项目申报场景。
2. 场景默认应用 `project_application_materials_v1`、附件清单、字数/章节限制和交付 preset。
3. rule source governance 显示本地默认规则和人工确认边界。
4. submission-system boundary report 说明外部系统状态不可由核心自动承诺。
5. 缺附件、预算附件或外部系统状态不确定时进入 degraded/manual boundary，而不是直接 Green 输出。

产品/售前核心链路：

1. 用户选择产品/售前场景。
2. 场景默认应用 `product_assets_v1`、`case_study_assets_v1` 和 customer/internal delivery preset。
3. asset consistency report 覆盖产品图、案例图、资料来源和版本一致性。
4. quote/body disambiguation 把报价、预算、财务判断类请求导向边界/专业场景，而不是混入普通正文润色。
5. 客户版/内部版差异通过 `customer_internal_version_report` 和人工确认 fixture 保持可追责。
