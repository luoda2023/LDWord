## 2. 当前总判断

当前项目已经不是“没有规划”。代码和文档里已经存在很宽的承载面：

- `SceneWorkspace` 已能承载输入契约、合规契约、对象预检、多交付、显隐、批量、范围、模块开关、模板覆盖；
- `PLANNED_SCENE_FAMILIES` 已登记 14 个高频 family；
- `SCENE_COVERAGE_PACKS` 已登记 12 个高频 coverage pack；
- `MATERIAL_SCHEMAS` 已覆盖投标、公文、技术、期刊、试卷、申报、合同、HR、表单、资质、财务、专利、双语、披露等资料形态；
- `count_profiles/builtin.json` 已有中文论文、英文期刊、标书、申报、合同、试卷、双语、披露、Word XML 审计等 profile；
- `SCENE_PARAMETER_OWNERSHIP_SPECS` 已开始把参数归属、UI surface、execution consumer、模板基线关系登记为可审计事实。

真正的问题是：

```text
矩阵的“宽度”已经有了，但大量单元格仍停在 L1 planning contract；
用户高频任务能找到名字，却不一定能走完 UI → resolver → runtime → report → issue/artifact → tests；
边界原则已经写在文档里，但还没有成为所有 family 的准入门槛。
```

所以 V16 的核心不是继续加场景名字，而是建立一套“完备准入模型”：

```text
先证明高频请求不漏；
再证明归属层级清楚；
再证明工作流槽位完整；
再证明 Word/OOXML 风险面有策略；
最后证明可见、可执行、可解释、可验收、可测试。
```

## 3. 完备矩阵的定义

高层场景能力矩阵不能被定义为：

```text
有多少个场景入口
有多少个模板
有多少个 UI 开关
```

它应该被定义为：

```text
对任意高频文档任务，系统能把它稳定落到正确层级，
并说明它需要哪些工作流、事实源、Word 风险策略、交付版本、边界声明和验收证据。
```

因此，一个能力单元只有同时满足下面 9 条，才可以称为“完备单元”：

| 序号 | 准入项 | 必须回答 |
| --- | --- | --- |
| 1 | 高频请求别名 | 用户自然会怎么说这件事 |
| 2 | 归属层级 | 顶层场景、planned family、profile、schema、preset、横切工作流还是插件 |
| 3 | 事实源 | 可信输入是 docx、json、xlsx、markdown、bib/csl、asset package 还是人工确认 |
| 4 | 工作流槽位 | 需要范围、资料、计数、显隐、批量、输出、审阅、对象保护中的哪些 |
| 5 | Word 风险面 | 触碰 paragraph/run/table/field/header/footer/sdt/textbox/rels/OLE/vba 中哪些 |
| 6 | UI/控件契约 | 前台能看见，且同名参数与模板管理同控件、同单位、同禁用规则 |
| 7 | 执行链 | resolver/scheduler/pipeline/runner 至少有一条真实消费链 |
| 8 | 报告/问题/产物 | JSON/Markdown report、Workbench issue queue、artifact 展示能解释结果 |
| 9 | 测试证据 | registry、UI、resolver、runtime、report、失败路径至少有 first slice 测试 |

缺任意一项时，最多只能称为规划、可见配置或局部 first slice，不能称为完整能力。

## 4. 防漏网的三层扫描法

高频遗漏通常不是因为少写了一个场景名，而是因为只按“文档名称”扫描，没有按“用户任务 + 工作流 + Word 风险”交叉扫描。V16 建议固定三层扫描。

### 4.1 第一层：用户自然请求扫描

先从用户语言出发，不从代码类名出发。

| 高频请求口径 | 示例 | 初始落点 |
| --- | --- | --- |
| 快速规范化 | “帮我把这个 Word 调成统一格式” | P0 `custom/report/technical/official` |
| 中文学术 | “毕业论文、课程论文、开题报告、综述” | P0 `thesis` + `thesis_cn` profile |
| 英文投稿 | “投稿稿、修回、cover letter、声明、投稿包” | P1 `journal_en` |
| 试卷教学 | “学生版、教师版、答案版、讲义、答题卡” | P1 `exam_teaching` |
| 标书资料 | “投标文件、正副本、资质、签章、附件包” | P0 `bidding` + 资质包 |
| 项目申报 | “申报书、预算、团队、附件、字数限制” | P1 `project_application` |
| 公文行政 | “通知、函、请示、批复、纪要、制度汇编” | P0 `official` + 行政 profile |
| 合同协议 | “审阅稿、签署稿、字段一致、金额日期核对” | P1 `contract_delivery` |
| 技术长文档 | “SOP、接口文档、验收报告、手册、书稿” | P0 `technical` + `long_document_publishing` |
| HR 批量 | “offer、证明、邀请函、人员档案一人一份” | P1 `hr_batch_documents` |
| 固定表单 | “套打、证书、登记表、固定版位表格” | P1 `form_batch_documents` |
| 产品售前 | “产品白皮书、方案、客户版、内部版” | P1 `product_sales_documents` |
| 报价财务 | “报价单、预算表、结算附件” | P2 `finance_quote_documents` |
| 专利/IP | “交底书、说明书、图号、术语、权利要求草稿” | P2 `ip_patent_documents` |
| 双语翻译 | “中英对照、术语一致、翻译审阅” | P2 `bilingual_translation_documents` |
| 披露/年报 | “年报、ESG、董事会稿、公开稿、归档包” | P2 `regulated_disclosure_documents` |
| 导入/AI | “PDF/OCR、LaTeX、AI 生成正文、复杂图形” | 插件/输入助手 |

这张表必须作为用户请求归类入口。新增需求先查它，不能直接新建顶层场景。

### 4.2 第二层：工作流原型扫描

同一个文档族会同时命中多个工作流。只有文档名，没有工作流，就会漏能力。

| 工作流原型 | 高频来源 | 必备能力 |
| --- | --- | --- |
| 模板规范化 | 所有现有 Word | 模板基线、范围、模块开关、对象预检、报告 |
| 范围定位 | 论文、标书、公文、长文档、计数 | section、页码、关键词、正文起点、Word story |
| 结构化输入 | 试卷、HR、表单、合同、申报、报价 | JSON/xlsx/schema、预览、校验、失败策略 |
| 资料填充 | 标书、公文、合同、HR、申报 | MaterialSchema、缺字段、占位符残留、资料来源 |
| 图片/签章/附件 | 标书、资质、申报、试卷、技术 | asset role、路径、尺寸、缺图、manifest |
| 内容显隐 | 试卷、合同、投稿、公文、披露 | 同源多版本、规则预览、产物差异 |
| 批量生成 | HR、表单、证明、陪标 | 一记录一产物、失败隔离、汇总报告 |
| 多口径计数 | 论文、投稿、申报、试卷、披露 | CountProfile、范围解释、多指标并列 |
| 参考/引用 | 中文学术、英文投稿、技术 | Bib/CSL、引用链接、样式、缺项报告 |
| 公式/符号 | 学术、技术、试卷、工程 | LaTeX/OMML、低置信度、公式编号、化学式 |
| 表格/固定版位 | 标书、报价、表单、证书、套打 | 列宽、合并、表头、`w:trHeight`、内容控件 |
| 对象保护 | 技术、财务、合同、披露、外来模板 | OLE、Visio、宏、修订、批注、文本框、域 |
| 审阅对比 | 合同、技术、投稿、公文、披露 | compare docx、修订保护、review copy |
| 提交归档 | 投稿、申报、标书、资质、披露 | DeliveryPreset、manifest、ZIP、命名 |
| 插件/人工确认 | OCR、AI、法律、财务、IP、复杂图形 | 置信度、人工确认、边界报告 |

矩阵缺口常出现在横切工作流，而不是文档族。比如 `form_batch_documents` 的核心不是“表单”两个字，而是固定版位、`w:trHeight`、内容控件、文本框、批量失败隔离和残留扫描。

### 4.3 第三层：Word/OOXML 风险扫描

Word 文档能力不能只按业务规划，必须按 package 风险面反推。

| Word 风险面 | 容易遗漏的高频场景 | 必须有的策略 |
| --- | --- | --- |
| paragraph/run | 全部 | run 不被粗暴重建；字段结果、局部样式、残留占位符可报告 |
| `styles.xml` | 模板、论文、公文 | 外观归模板；场景覆盖必须有业务理由 |
| `numbering.xml` | 论文、公文、合同、长文档 | 保留/重建/局部修复策略可见并报告 |
| `w:tbl/w:tr/w:tc` | 标书、试卷、表单、报价 | 合并、列宽、跨页、表头重复、行高 |
| `w:trHeight` | 表单、证书、报价、套打 | 固定版位能力；不能回到通用模板噪音 |
| `w:sdt` 内容控件 | 表单、合同、HR、公文 | 字段映射、填充、残留扫描、保护 |
| textbox/shape | 表单、证书、公文、双语 | 预检；不能当普通段落重排 |
| drawing/media/rels | 标书、试卷、技术、资质 | 图片角色、缺图、关系复制、manifest |
| field | 目录、页码、交叉引用、合同编号 | 保留/刷新/跳过策略 |
| headers/footers | 论文、公文、合同、水印、披露 | 模板外观 + 场景状态/版本解释 |
| comments/revisions | 合同、技术审阅、投稿修回 | 默认保护；运行前确认 |
| footnotes/endnotes | 学术、法律、书稿 | CountProfile 声明是否计入 |
| hidden text | 合同、披露、双语 | 预检、计数、报告说明 |
| OLE/embedded workbook/Visio | 技术、财务、标书、披露 | block/warn/skip，不静默破坏 |
| vba/macros | 外来模板、表单、合同 | 默认阻断或人工确认 |
| package relationships | 图片、附件、外链 | inventory、复制、缺项、外链风险 |

L3 以上 family 必须声明 `ooxml_touchpoints`，并且 touchpoint 必须能映射到对象预检、模块策略或报告解释。

## 5. 顶层入口、family、profile、workflow 的边界

高频不等于都要做顶层入口。入口泛滥会让边界更模糊。

### 5.1 顶层场景准入

只有同时满足以下条件，才考虑顶层场景：

```text
用户极高频直接搜索；
工作流独立，不能自然落入已有 P0 入口；
默认模板、范围、模块组合、资料/输出策略足够稳定；
至少能闭合 L3 first slice；
不会把 profile/preset/schema 问题伪装成新场景。
```

当前 P0 顶层入口保持 `custom/thesis/bidding/official/technical/report` 是合理的。P1/P2 大多数应该先做 planned family 或 profile，不急着上导航。

### 5.2 Planned family 准入

适合 planned family 的情况：

```text
高频，但执行链尚未闭合；
需要独立 schema/profile/preset；
与现有顶层入口有复用关系；
需要先明确边界和不承诺项。
```

`journal_en`、`exam_teaching`、`project_application`、`hr_batch_documents`、`form_batch_documents`、`contract_delivery` 等都属于这个层级。

### 5.3 Profile 准入

适合 profile 的情况：

```text
同一工作流下的规则差异；
学校、期刊、机构、行政类型、文档角色不同；
主要差异是范围、阈值、字段要求、输出版本或风险策略。
```

例如中文论文不应拆成每个学校一个场景；英文投稿不应拆成每个期刊一个场景；公文不应拆成通知、函、批复、纪要等多个顶层入口。

### 5.4 横切工作流准入

适合横切工作流的情况：

```text
多个文档族都会用；
本质是处理方式而不是文档类型；
能通过 schema/profile/preset/issue/report 复用。
```

例如 CountEngine、DeliveryPreset、MaterialSchema、ObjectPreflight、ContentVisibility、BatchPreset、Artifact Browser、插件边界，都应成为横切治理轴，而不是藏在某个场景里。

### 5.5 插件/人工确认准入

适合插件或人工确认的情况：

```text
需要专业判断；
依赖外部系统或低置信度识别；
不能承诺无损或正确；
失败成本高。
```

OCR/PDF 重建、完整 LaTeX 工程、AI 内容质量、法律意见、财务审计、专利有效性、翻译质量、复杂学科图形，都必须进入插件/人工确认边界。

## 6. 场景、模板、资料、输出、会话的裁决规则

这个裁决规则必须成为所有新增能力的第一步。

| 层级 | 负责 | 不负责 |
| --- | --- | --- |
| TemplateConfig | 字体、字号、段距、缩进、页边距、表格样式、目录、题注、页眉页脚等外观基线 | 做不做、失败怎么办、输出什么 |
| SceneWorkspace | 范围、模块开关、执行策略、风险策略、计数口径、显隐、多版本、批量、交付状态 | 具体业务字段值、当前文件路径 |
| MaterialSchema/MaterialContext | 字段、图片、签章、附件、多记录资料、资料缺口 | 排版样式和执行策略 |
| DeliveryPreset/Output | final/review/student/signing/submission/archive 等版本、命名、manifest、报告、中间产物 | 模板外观编辑 |
| Workbench Session | 本次文件、输出目录、临时选择、覆盖确认、运行状态 | 可复用领域规则 |
| Plugin/人工确认 | OCR、AI、法律、财务、IP、翻译、复杂图形、外部提交 | 核心排版承诺 |

裁决句：

```text
影响“长什么样”优先归模板；
影响“做不做、在哪做、失败怎么办、输出什么”归场景；
影响“具体填什么、哪张图、哪份附件、哪条记录”归资料；
影响“本次路径、临时选择、覆盖确认、运行状态”归会话；
影响“专业判断、低置信度和外部能力”归插件或人工确认。
```

## 7. 需要补齐的高频能力面

下面不是“新增导航清单”，而是当前最应该补齐的能力面。

### 7.1 P0 通用规范化闭环

当前已有 P0 可执行场景，但要达到完善，还缺：

- 输出目标 issue queue 与 artifact browser 真正闭环，而不是只在日志/最近结果里展示；
- 参数最终生效值、模块消费 trace、报告解释继续细化到字段级；
- 模板/场景/Workbench 控件契约自动化，防止同名参数漂移；
- 对象预检结果与模块跳过、报告、问题队列联动更直观。

最低完备目标：

```text
用户拖入任意 Word → 选择 P0 场景和模板 → 执行前看到风险和输出 → 执行后能打开所有产物 → 报告解释启用、跳过、覆盖、产物。
```

### 7.2 中文学术与英文投稿必须拆边界

中文学术：

- 重点是学校 profile、中文/英文摘要、正文范围、参考文献、题注、公式、Word XML 计数；
- 不应吞掉英文投稿、cover letter、submission package。

英文投稿：

- 重点是 journal profile、Bib/CSL、section-aware word count、display item、声明、cover letter、投稿包；
- 不承诺出版社最终排版；
- 完整 LaTeX 工程必须插件化或明确只支持片段。

缺口：

- `journal_en` 仍是 L1，Bib/CSL、投稿包 runtime、规则来源治理未闭合；
- `thesis_cn` 作为 profile 的来源、版本、学校规则治理仍不足。

### 7.3 试卷教学必须建立结构化事实源范式

试卷/教学是高频，但不能做成“模板套壳”。最低完整形态：

```text
Paper JSON 是事实源；
Markdown 是人工预览；
Word 是正式输出；
DeliveryPreset 控制学生版/教师版/答案版/解析版；
ContentVisibilityRule 控制答案、解析、知识点显隐；
公式与图片作为题目 asset；
复杂几何图进入插件边界。
```

缺口：

- 题目 schema runtime 校验；
- 学生/教师/答案 delivery preset 执行；
- 答题区、分值、题型表格、公式图片 first slice；
- 生成后残留占位符扫描。

### 7.4 表单/HR/套打是固定版位，不是普通表格样式

`form_batch_documents` 和 `hr_batch_documents` 应优先补 L3，因为它们覆盖大量办公高频：

- offer/证明/邀请函；
- 人员档案；
- 登记表；
- 证书；
- 固定版位套打；
- 一人一份/一记录一份。

关键不是“有表格”，而是：

- `w:trHeight` 行高策略；
- 内容控件 `w:sdt`；
- 文本框/shape；
- 固定版位不被自动排版破坏；
- xlsx/json 多记录；
- 逐记录失败隔离；
- 残留占位符和空字段报告。

`TableConfig.row_height_pt` 不应回到通用模板面板作为噪音参数。它应成为固定版位 family 的一项场景策略：只有表单、证书、报价、套打等需要时才启用、预检和报告。

### 7.5 标书/申报/资质包需要附件 inventory 主轴

标书和项目申报不是单纯排版：

- 资料字段；
- 公司/项目/团队/预算；
- Logo/签章；
- 资质证照；
- 附件完整性；
- 正副本/评审稿/正式稿；
- 归档包和 manifest。

缺口：

- 资质包 inventory 的目录规则和过期/缺项报告；
- 项目申报附件、计数和申报包 runtime；
- 多公司/多 profile 批量失败隔离 UI；
- 交付包 artifact browser。

### 7.6 合同、公文、会议制度要重视保留策略

合同和公文的重点不是“重排漂亮”，而是：

- 保留编号；
- 保留/保护修订和批注；
- 字段一致性；
- 页眉页脚/文号/日期；
- 审阅稿/签署稿/正式稿；
- 法律或行政判断边界。

缺口：

- 合同签署包和签章位置 manifest；
- 法律边界在每份报告中可见；
- 公文/会议制度的编号保留证据进入 report；
- 行政 profile 的材料字段和归档 preset。

### 7.7 技术长文档与披露类必须先保护对象

技术、长文档、财务、披露类文档常见高风险对象：

- OLE/embedded workbook；
- Visio；
- 图表；
- 交叉引用；
- 域；
- 批注修订；
- 多章节。

缺口：

- 长文档 chapter inventory；
- proof/review/final/archive preset；
- OLE/Visio/外链关系的更强预检与跳过说明；
- 披露类 board/public/archive 交付包；
- 财务、审计、披露结论必须作为插件/人工边界。

### 7.8 专业 P2 不要空白，但必须边界前台化

财务、专利、双语、披露这类 P2 不是“不做”，而是：

```text
核心只做格式、结构、清单、一致性、审阅/归档产物；
专业结论进入插件或人工确认。
```

缺口：

- 专业插件入口；
- 人工确认 gate；
- 每类专业边界的 report wording；
- 不同专业 family 的 MaterialSchema 与 CountProfile 来源治理。

## 8. 控件一致性必须升级为准入门槛

场景配置控件样式必须与模板管理一致。这不是视觉统一，而是防止参数语义漂移。

| 参数 | 模板管理要求 | 场景配置要求 |
| --- | --- | --- |
| 字体 | `FontCombo` | 复用同一控件，不用自由输入 |
| 字号 | `SizeCombo` | 复用同一控件和字号体系 |
| 左缩进/右缩进 | 同一行，单位一致 | 同一行，命名一致 |
| 段前/段后 | 同一行，单位一致 | 同一行，命名一致 |
| 特殊缩进 | “无/首行/悬挂”可切换 | 必须可交互切换，不能只显示文字 |
| 特殊缩进值 | “无”时禁用并置灰 | 同样禁用规则 |
| 行距类型/行距值 | 组合语义 | 固定值/倍数/最小值等同控件 |
| 表格行高 | 普通模板不暴露为噪音 | 固定版位 family 可暴露，必须解释 `w:trHeight` |
| 输出版本 | 不属于模板样式控件 | DeliveryPreset 编辑器 |
| 水印状态 | 模板可给视觉基线 | 场景用状态/交付策略表达 |
| 资料字段 | 不属于模板 | Schema 驱动表单/表格 |

建议建立 `ControlContractRegistry`：

```text
parameter_path
canonical_label
canonical_control
unit_set
paired_fields
disabled_state_rule
template_surface
scene_surface
workbench_surface
owner_layer
runtime_consumer
report_evidence
```

有了它，才能自动检查：

```text
同名参数是否同控件；
左右缩进、段前段后是否同排；
特殊缩进是否可切换；
场景页是否用自由文本替代结构化控件；
UI 可配置的字段是否进入 resolver、runtime 和 report。
```

## 9. 完善度分级与升级门槛

V16 继续使用 L0-L5，但把每级门槛写硬。

| 等级 | 状态 | 最低证据 | 不能宣称 |
| --- | --- | --- | --- |
| L0 | 未归属 | 只有需求或讨论 | 不能展示为能力 |
| L1 | Planning contract | registry/manifest/文档有边界、schema/profile/preset 名称 | 不能作为可执行能力 |
| L2 | 可见配置 | ScenePanel/Workbench 可见关键配置和边界 | 不能保证执行 |
| L3 | 可执行 first slice | UI、resolver、runtime、report、tests 闭合一条最小链 | 不能宣称全规则完整 |
| L4 | 工作台闭环 | issue queue、修复/忽略、artifact browser、失败路径可操作 | 不能宣称长期规则治理 |
| L5 | 治理闭环 | profile 来源、版本、迁移、审阅、历史审计 | 不能承诺外部系统 100% 一致 |

升级门槛：

```text
L1 → L2：前台能看见，并且边界可见；
L2 → L3：至少一条真实执行链闭合；
L3 → L4：失败、跳过、忽略、修复、产物浏览闭合；
L4 → L5：profile/规则/插件治理可长期更新。
```

降级门槛：

```text
UI 暴露但执行不消费，降到 L2；
执行消费但报告不解释，不能超过 L3；
触碰高风险 OOXML 但无预检，不能超过 L2；
涉及专业判断但没有插件/人工边界，不能超过 L1；
同名参数控件不一致，不能进入 L3；
输出产物不可验收，不能进入 L4。
```
