# 高层场景能力矩阵 N2.373 技术长文档索引附录与多文件边界证据闭环

日期：2026-06-23

## 目标

本轮承接 `technical_long_docs` pack 与 `long_document_publishing` family 的相邻 L5 blocker：`index/appendix handling`、`multi-file merge boundary`、`index handling` 与 `multi-file import boundary`。

此前技术长文档已经具备章节 inventory、对象预检、交付 preset、高危嵌入对象降级样本和章节/交叉引用人工确认样本。但“索引/附录是否进入结构化证据、多个来源文件或嵌入包是否只作为边界报告而非无损合并承诺、场景概览能否看到这条证据链”仍未闭合。N2.373 将这组能力推进为可验证闭环，并把 `technical_long_docs` 与 `long_document_publishing` 升级为 `green_l5`。

本轮不声明系统可以判断技术内容正确性，不声明已经替代出版社排版系统，也不声明已经支持真实多 DOCX 无损合并、索引重建或跨文件引用自动修复。

## 闭合内容

1. 技术长文档结构化字段
   - `technical_document_v1` 新增 `index_scope`、`appendix_scope`、`source_file_manifest`。
   - `long_document_metadata_v1` 新增 `index_scope`、`appendix_scope`、`source_file_manifest`、`merge_boundary_notes`。
   - schema boundary 明确不承诺无损多文件合并或未经复核的索引重建。

2. DOCX fixture 与 Word/OOXML 证据
   - 新增 `technical_long_docs_index_appendix_merge_boundary` fixture，绑定 `technical_product_manual` 高频请求样本。
   - fixture 覆盖 `paragraph_run`、`fields`、`comments`、`headers_footers`、`embedded_packages`、`package_relationships`。
   - expected preflight 覆盖 `fields`、`comments`、`embedded_packages`，表达索引/附录、跨文件包和嵌入来源需要交付前复核。

3. 报告与 UI 证据
   - 新 fixture 声明 `chapter_inventory`、`index_appendix_inventory`、`multi_file_merge_boundary_report`、`cross_reference_status_report`、`archive_package`、`object_preflight`。
   - 场景概览新增 `technical_long_doc_evidence` summary item，直接展示 `technical_document_v1`、`long_document_metadata_v1`、四类报告项和技术长文档证据 fixture。
   - 用户旅程新增 `manual_boundary:technical_product_manual`，让产品手册类请求有“索引/附录/多文件边界人工确认”路径。

4. 成熟度同步
   - `technical_long_docs` evidence 新增 `index/appendix handling` 与 `multi-file merge boundary`，remaining gaps 清零，升级为 `green_l5`。
   - `long_document_publishing` evidence 新增 `index/appendix handling` 与 `multi-file import boundary`，remaining gaps 清零，升级为 `green_l5`。
   - 矩阵摘要推进为 11 个 Green/L5、16 个 L5-blocked、31 个 remaining gaps、36 个 DOCX fixtures、53 个 request cells、96 条 user journeys。

## Word/OOXML 视角

- 技术长文档的索引、附录和多文件来源不能只被当成普通段落样式；它们需要进入 schema、fixture、报告和概览证据。
- `fields` 和 `comments` 用于承载索引/交叉引用/人工标注，`headers_footers` 与 `package_relationships` 用于证明长文档交付包边界，`embedded_packages` 用于表达来源文件或嵌入包存在。
- `multi_file_merge_boundary_report` 是边界报告，不是无损合并引擎。系统可以提示、记录、要求人工确认；不能自动承诺跨文件引用、索引页码、附录范围都已正确重建。

## 场景边界

- `technical_long_docs` 覆盖技术手册、接口验收文档、SOP、产品技术说明和长文档归档，不扩展成“出版社系统”。
- `long_document_publishing` 是长文档发布家族，负责章节、索引、附录、对象安全、交叉引用和归档包证据；技术内容正确性和外部发布系统提交结果不归入核心格式化能力。
- “产品说明书/销售手册”如果以客户素材和营销版本为主，仍可进入 `application_reports` / `product_sales_documents`；如果以章节、附录、索引和技术对象安全为主，进入 `technical_long_docs`。

## 后续边界

`technical_long_docs` 与 `long_document_publishing` 当前不再保留索引/附录处理和多文件导入/合并边界缺口。后续增强应转向真实多 DOCX 合并引擎、索引页码重建、跨文件引用自动修复、出版社级版式系统 handoff、外部发布回执和长文档多文件批量导入 UI，而不是继续把索引/附录 inventory 或多文件边界报告列为未打通。
