# 高层场景能力矩阵 V18 高频完备能力矩阵与边界规划（2026-06-18）

## 1. 本轮定位

V17 已经把场景覆盖从“有哪些场景名”推进到“coverage pack + workflow + Word 风险面 + closure task”。但目前仍有一个更高层的问题：很多功能点虽然在 UI、配置、计划族或执行模块里出现了，却还没有被定义成可验收的场景能力。

V18 的目标是建立一套更高层的场景能力矩阵，用来回答三件事：

```text
1. 高频用户请求有没有稳定落点，不能只靠人工解释。
2. 每个落点需要哪些能力原子、事实源、Word/OOXML 风险策略、报告和产物。
3. 哪些事情明确不属于核心场景能力，必须进入插件、人工确认或边界报告。
```

## 2. 完备能力的定义

一个“场景能力”不能等同于一个按钮、一个参数或一个场景名称。完整能力必须同时满足：

```text
自然请求可归类
事实源可声明
模板与场景职责可分离
工作流可复用
Word/OOXML 风险面可解释
UI 控件契约一致
执行链可到达
报告/问题/产物可追踪
测试证据可复验
边界可被用户理解
```

因此后续判断“功能是否完善”时，不能只问“有没有这个功能点”，而要问：

```text
它属于模板、场景、素材、输出、执行、报告还是插件？
它有没有从 UI 到 resolver、pipeline、runner、report 的链路？
它触碰哪些 Word XML surface？
失败时用户会在哪里看到，能不能修复？
它承诺了什么，又不承诺什么？
```

## 3. 15 个能力原子

下表是高层矩阵的最小能力原子。所有高频场景都应由这些原子组合，而不是为每类文档重新造一套孤立功能。

| 能力原子 | 完备定义 | 主要证据面 | 典型边界 |
| --- | --- | --- | --- |
| A01 模板基线 | 外观规则由 TemplateConfig 管理，场景只选择模板和必要覆盖 | template registry、control contract、ScenePanel | 不把业务策略塞进模板样式 |
| A02 范围与结构定位 | 能解释 body、toc、abstract、references、appendix、headers、footers、page/story 范围 | FormatScopeConfig、section classifier、count profile | 不假定全文都属于同一处理范围 |
| A03 多口径计数 | 使用 profile-driven multi-metric CountEngine，而不是单一字数 | count_profiles、CountEngineResult、report counts | 不承诺与 Word 或投稿系统完全一致 |
| A04 结构化事实源 | JSON/XLSX/material schema 是机器事实源，Markdown 只做预览或人工中间层 | InputSourceProfile、MaterialSchema | 不让 AI 或 Markdown 直接成为不可校验事实源 |
| A05 素材与附件 | 字段、图片、签章、PDF、资质附件有角色、缺失检查和 manifest | MaterialSchema、MaterialExecutionContext、package manifest | 不验证素材真实性 |
| A06 内容显隐与多版本 | 同一事实源通过规则生成学生版、教师版、答案版、审阅版、签署版等 | ContentVisibilityRule、DeliveryPreset | 不为不同版本重新生成互相漂移的内容 |
| A07 批量生成与失败隔离 | 一记录一产物，失败记录隔离，批量问题能定位到 profile/record/field | BatchPreset、batch issue center | 不把失败记录混入成功产物 |
| A08 引用与参考文献 | 支持引用源、缺项、编号、样式、参考文献范围和报告 | citation workflow、reference style、field risk | 不承诺未审期刊规则或 EndNote 全量替代 |
| A09 公式、符号与学科图形 | 公式转换、符号规范、低置信度和复杂图形边界可报告 | formula modules、confidence report、plugin gate | 复杂几何图、化学结构式等进入插件 |
| A10 固定版位 | `w:trHeight`、`w:sdt`、textbox、shape、占位符残留独立治理 | fixed layout policy、fixed_layout_text helper | 不回流成通用表格样式参数 |
| A11 对象安全 | OLE、VBA、嵌入工作簿、修订、批注、外链等能 block/warn/skip | ObjectPreflight、risk report | 不静默破坏高风险对象 |
| A12 审阅与对比 | review copy、compare docx、修订保护、批注策略明确 | DeliveryPreset、report、artifact browser | 不把审阅语义当普通最终稿处理 |
| A13 交付与归档 | final、review、report、manifest、zip、package 命名和目录可配置 | OutputConfig、DeliveryPreset、artifact report | 不替代外部投稿或业务系统 |
| A14 插件与人工确认 | OCR、PDF、AI、专业判断、复杂图形有插件入口和人工确认门 | plugin boundary、manual gate、confidence report | 不在核心链路承诺内容质量或专业结论 |
| A15 报告与问题中心 | 失败、风险、缺口、边界、修复入口都能进入 report/issue queue | JSON/Markdown report、Workbench issue center | 不只在日志或控制台里说明问题 |

### 4.2 不建议新增的顶层入口

以下请求高频，但不应直接变成顶层场景，否则导航会膨胀且边界会混乱：

| 用户说法 | 应归属 | 原因 |
| --- | --- | --- |
| 课程论文、文献综述、开题报告 | `thesis` + academic profile | 与中文学术结构、计数、引用共享能力 |
| 会议纪要、制度汇编 | `official` + policy profile | 公文族内的结构和归档差异，不需要新顶层 |
| 白皮书、售前方案、产品手册 | `report/technical` + product family | 内容来源、素材和交付差异大于版式差异 |
| offer、证明、证书、登记表 | `batch_forms` + HR/form profile | 本质是结构化事实源和固定版位 |
| 资质证照包 | `bidding/application` + qualification family | 是附件和归档 inventory，不是独立排版场景 |
| 年报、ESG、披露材料 | professional disclosure boundary | 涉及专业判断和审阅责任，不能伪装为通用排版 |
| PDF/OCR/LaTeX 导入 | import/AI boundary | 导入质量和置信度问题大于格式问题 |

## 5. 高频防遗漏扫描法

以后新增或审阅一个场景时，必须用下面四层扫描。

### 5.1 自然请求层

检查用户是否可能用这些高频说法提出需求：

```text
规范化 Word
论文排版
字数/词数/页数/图表数检查
参考文献和引用修复
公式和符号整理
期刊投稿包
试卷多版本生成
标书和资质附件包
合同审阅和签署包
公文和纪要归档
长文档审阅和定稿
项目申报和附件清单
HR 或证书批量生成
双语/披露/专利/财务专业文档
PDF/OCR/LaTeX/AI 导入
```

如果某个说法找不到 coverage pack、planned family、profile 或插件边界，就属于高频遗漏。

### 5.2 能力原子层

每个 pack 至少要回答：

```text
需要模板基线吗？
需要范围定位吗？
需要计数 profile 吗？
需要结构化事实源吗？
需要素材或附件吗？
需要多版本显隐吗？
需要批量隔离吗？
需要引用或公式吗？
需要固定版位吗？
需要对象安全和审阅对比吗？
需要交付包或归档吗？
需要插件或人工确认吗？
```

如果一个 pack 声明了能力轴，却没有对应 workflow、risk surface、report 或 test evidence，就是“看似覆盖，实际断链”。

### 5.3 Word/OOXML 风险层

每个场景必须至少列出会触碰哪些 Word surface：

```text
w:p / w:r / w:rPr / w:pPr
styles.xml
numbering.xml
w:tbl / w:tr / w:tc / w:gridCol
w:trHeight
w:sdt / w:tag / w:alias
w:txbxContent / v:shape / wps:txbx
w:drawing / media / rels
w:fldSimple / w:instrText / TOC / PAGE / REF
header*.xml / footer*.xml / sectPr
comments.xml / revisions
footnotes.xml / endnotes.xml
w:vanish hidden text
embeddings / vbaProject.bin / oleObject
package relationships / externalLink
```

只要触碰这些 surface，就必须说明策略：preserve、repair、replace、block、warn、skip 或 plugin gate。

### 5.4 产物与修复层

一个场景不是跑完就算闭合。它必须解释：

```text
产物在哪里？
缺口在哪里？
哪些字段、素材、引用、公式、对象风险需要用户处理？
能否从 Workbench issue 跳回对应配置、素材或 profile？
报告里有没有 boundary wording？
```

这就是为什么 `A15 报告与问题中心` 是能力原子，而不是附加功能。

## 6. 层级归属规则

### 6.1 Template 层

模板层负责可复用外观基线：

```text
字体、字号、段落、标题、目录、题注、页眉页脚、参考文献样式、普通表格样式
```

场景可以选择模板，也可以在有业务理由时做 section override，但不能复制一套与模板管理不一致的样式控件。

### 6.2 Scene 层

场景层负责业务策略：

```text
处理范围
编号策略
计数 profile
对象风险策略
引用/公式策略
水印状态和版本语义
素材要求
显隐规则
批量策略
交付 preset
插件边界
```

公式、输出、水印不应继续散落在模板或通用参数里。它们在高层矩阵中应这样归属：

| 参数簇 | 归属 | 说明 |
| --- | --- | --- |
| 公式样式外观 | Template + Scene override | 基础外观属模板，学科策略、转换置信度、unsupported 边界属场景 |
| 输出产物 | Scene + OutputConfig | 场景决定版本和业务语义，OutputConfig 承载具体 artifact 开关 |
| 水印 | Scene + Output delivery | “审阅版、内部版、签署版、草稿版”是交付语义，不应只是页眉页脚装饰 |
| 引用/参考文献 | Scene + Template | 样式基线属模板，引用源、缺项、编号和置信度属场景 |
| 固定行高 | Fixed-layout scene/profile | 不属于通用 TableConfig |

### 6.3 Material 层

素材层负责事实字段和资产角色：

```text
party_a、contract_amount、seal、question_figure、attachment、qualification、product_image
```

素材层不判断真实性，只判断是否存在、是否映射、是否能进入 manifest 和 issue queue。

### 6.4 Output 层

输出层负责 artifact 形态：

```text
final_docx
review_copy
compare_docx
report_json
report_markdown
material_manifest
material_package
zip/archive
```

输出层不决定业务边界，业务边界由场景和插件声明。

### 6.5 Plugin 层

插件层负责核心系统不应承诺的能力：

```text
OCR/PDF/LaTeX 无损导入
AI 内容质量
复杂几何图
物理电路图
化学结构式
审计/法律/专利/翻译质量判断
```

插件层也必须有 manual gate、confidence report 和边界文案。

## 7. 控件样式一致性要求

场景配置中的控件样式控制必须与模板管理保持一致。这个要求不是 UI 美观问题，而是参数归属和可维护性问题。

必须遵守：

```text
同一类样式参数使用同源控件
同一数值使用同一单位和步进
同一禁用状态使用同一规则
同一特殊枚举使用同一文案和内部值
同一参数必须能追踪到 control contract
```

当前已对齐的方向：

```text
FontCombo
SizeCombo
build_emphasis_widget
SpecialIndentInput
IndentInput
SpacingInput
LINE_SPACING_OPTIONS
```

后续必须继续补齐：

| 控件区域 | 必须一致 | 风险 |
| --- | --- | --- |
| 字体字号 | 模板和场景同控件、同预览、同写入路径 | 样式 override 写出不可解释 |
| 缩进和段前段后 | 同一行布局、同单位、特殊缩进可切换 | 用户以为改了，resolver 没接住 |
| 行距 | 类型和值的启用规则一致 | 固定值、多倍行距写出错误 |
| 表格 | 普通表格样式不出现固定版位行高 | `w:trHeight` 边界回流 |
| 水印 | 版本语义和页眉页脚外观分离 | 把业务状态误当装饰 |
| 公式和引用 | 外观控件与场景策略分离 | 模板样式和转换策略混淆 |

验收标准：

```text
ScenePanel 中任何与模板管理同名或同义的控件，都必须有 control contract。
如果没有 contract，要么补 contract，要么证明它是场景专属业务策略而非样式参数。
```

## 8. 对两份技术记录的吸收

### 8.1 计数引擎记录

应吸收为矩阵级约束：

```text
计数能力必须是 profile-driven multi-metric。
中文论文、英文期刊、申报、试卷、披露不能共享一个“字数”口径。
Word-like 统计和规则统计要并存。
CountProfile 必须声明 included/excluded scopes、primary metrics、notes。
报告必须说明口径，不承诺与 Word 或投稿系统完全一致。
```

对应能力原子：

```text
A02 范围与结构定位
A03 多口径计数
A08 引用与参考文献
A15 报告与问题中心
```

当前代码已有 first slice：

```text
CountProfile
CountEngineResult
count_profiles/builtin.json
word_xml_full audit profile
ValidationModule count_engine event
JSON/Markdown counts report
```

仍需补强：

```text
中文论文学校 profile 的显式拆分
英文期刊 journal profile governance
section-aware limits 的报告证据
引用和公式置信度合并到场景报告
```

### 8.2 试卷生成记录

应吸收为矩阵级约束：

```text
JSON 是机器事实源。
Markdown 是预览和人工检查层。
Word 是正式输出。
学生版、教师版、答案版必须来自同一结构化源。
答案、解析、分值、知识点不能从学生版里删除，只能通过显隐规则控制。
通用图片能力优先于复杂几何图自动生成。
复杂几何、物理电路、化学结构、生物流程图应插件化。
```

对应能力原子：

```text
A04 结构化事实源
A05 素材与附件
A06 内容显隐与多版本
A09 公式、符号与学科图形
A13 交付与归档
A14 插件与人工确认
```

当前缺口：


## 10. 完备等级

后续不要用“有/没有”描述场景，而用等级描述。

| 等级 | 定义 | 可对用户承诺吗 |
| --- | --- | --- |
| L0 不可见 | 没有 pack、family、profile、boundary | 不可承诺 |

| L2 配置可见 | schema、count profile、delivery preset、control contract 已有 | 可作为受限配置能力 |
| L3 first slice 可执行 | 能经过 resolver/pipeline/runner/report，有测试证据 | 可承诺有限闭环 |
| L4 产品化闭环 | UI 可配置、问题中心可修复、报告可解释、产物可归档 | 可作为正式场景能力 |

## 12. 验收清单

任何新增场景、profile 或功能点，在合并前必须回答：

```text
1. 归属哪个 coverage pack？
2. 有没有自然请求别名？
3. 属于哪个能力原子？
4. 事实源是什么？
5. 是否需要 MaterialSchema 或 CountProfile？
6. 是否需要 DeliveryPreset？
7. 是否触碰 Word XML surface？
8. 失败时进入哪个 report 或 issue queue？
9. 是否需要插件或人工确认？
10. 是否与模板管理控件契约一致？
11. 是否有至少一条 registry/UI/runtime/report 测试？
12. 边界文案是否能阻止过度承诺？
```

如果无法回答第 1、4、7、8、12 条，就不能称为完整场景能力。

## 13. 本轮结论

当前功能点确实还不完善，但问题不在于“再多加几个场景按钮”，而在于很多高频任务还没有从能力原子、事实源、Word 风险、执行链、报告和边界上形成闭环。

V18 的核心判断是：

```text
场景矩阵要保持 12 个高层 pack 的稳定性。
新增能力应优先补 pack 内部链路，而不是扩展顶层导航。
公式、输出、水印、计数、引用、固定版位、AI/导入都要归入场景能力矩阵，但必须明确哪些是核心，哪些是插件或交付语义。
高频无遗漏的关键不是列更多文档类型，而是把每个自然请求映射到能力原子和边界。
```

下一轮最优先的工程闭环建议推进 `exam_education` 的 student/teacher/answer delivery presets；随后补 `english_journal` 的 BibTeX/CSL parser。
