## 2. 总判断

当前的问题不是“没有场景名字”，而是：

```text
场景名、family、profile、schema、DeliveryPreset、插件边界已经散布在代码和文档中，
但很多高频任务还没有被推进到可执行、可解释、可报告、可测试的闭环。
```

所以完善矩阵不能继续靠新增入口堆叠。真正的目标是：

```text
每个高频用户任务都有落点；
每个落点都知道自己属于顶层场景、family、profile、schema、preset、横切能力还是插件；
每个可见配置都能被 resolver / pipeline / report / issue queue / tests 追到；
每个专业边界都能在前台和报告中被用户看见。
```

V15 的关键结论：

- 顶层入口保持克制，避免把每个行业文档都做成导航项；
- 高频 family 要补 L3 first slice，而不是只停留在 planning registry；
- 横切工作流要成为矩阵的主轴，尤其是计数、资料、显隐、多版本、批量、对象保护、交付包；
- 公式、输出、水印不是“先不管”的边角项，必须拆成模板基线、场景策略、资料值、会话选择和插件边界；
- 场景配置控件必须继承模板管理控件体系，同名参数同控件、同单位、同交互；
- `execution_consumer` 已有 N2.84 静态代码锚点审计，最终生效值报告已有 N2.85 first slice；运行时事件追踪仍是下一阶段缺口。

## 3. V15 矩阵本体

高层场景能力矩阵不应是一张“文档类型列表”，而应是五维结构。

| 维度 | 要回答的问题 | 典型承载 |
| --- | --- | --- |
| 用户任务族 | 用户自然会怎么说这件事 | coverage pack / natural request aliases |
| 工作流原型 | 这件事本质上是哪类流程 | normalize / fill / count / batch / delivery / review / plugin |
| 数据事实源 | 机器可信输入是什么 | docx / json / xlsx / markdown / bibtex / assets |
| Word 风险面 | 会触碰哪些 OOXML 或 package 部件 | paragraph / run / table / numbering / field / sdt / rels / vba |
| 验收证据 | 用户和测试如何确认它真的闭环 | UI / runtime / report / issue queue / pytest |

因此，一个矩阵单元不是：

```text
“试卷教学：有”
```

而必须是：

```text
exam_teaching
→ 结构化题源 / 内容显隐 / 多版本输出 / 公式图片 / 插件边界
→ Paper JSON + assets
→ paragraph, table, drawing, numbering, rels
→ ScenePanel 可见 + runtime 渲染 + DeliveryPreset 产物 + report + tests
```

如果任一维度缺失，就只能称为 planning contract，不能称为完善能力。

## 4. 分层归属规则

后续任何新增能力都必须先做归属裁决。

| 层级 | 负责什么 | 不能负责什么 |
| --- | --- | --- |
| 顶层场景 | 高频、宽口径、可执行的任务入口 | 每个行业细分和每种输出版本 |
| Planned family | 高频但尚未可执行的任务族 | 伪装成已完成能力 |
| Profile | 某个场景内的规则变体，如学校、期刊、行政、表单 | 业务事实值 |
| MaterialSchema | 字段、图片、签章、附件、多记录资料契约 | 排版样式和执行策略 |
| CountProfile | 多口径计数、范围、包含排除、报告解释 | 普通 validation 开关 |
| DeliveryPreset | final/review/student/signing/submission 等产物版本 | 模板外观编辑 |
| TemplateConfig | 字体、段距、页边距、表格、页眉页脚等外观基线 | 做不做、失败怎么办、输出什么 |
| Workbench Session | 本次文件、输出目录、临时选择、运行状态 | 可复用领域规则 |
| Plugin / 人工确认 | OCR、完整 LaTeX、AI 内容、法律、财务、IP、审计、复杂图形 | 核心排版承诺 |

硬规则：

```text
影响“长什么样”优先归模板；
影响“做不做、在哪做、失败怎么办、输出什么”归场景；
影响“具体填什么、哪张图、哪份附件、哪条记录”归资料；
影响“这一次路径、临时开关和运行状态”归会话；
影响“专业判断、低置信度和外部能力”归插件或人工确认。
```

| 完整 LaTeX 工程 | 插件 | 宏包/class 风险、局部结构、公式 | formula fragment MVP + 风险报告 | 不承诺完整工程无损 |
| AI 内容生成 | 输入助手/插件 | JSON schema、Markdown 预览、人工确认 | schema validation + preview + provenance | 核心不担保内容质量 |
| 复杂学科图形 | 学科插件/图片资产 | 图形 schema、预览、图片插入 | 图片资产绑定 + 图题/尺寸 | 核心不自动复杂制图 |

防遗漏规则：

```text
新增需求先查自然语言别名；
能归入既有任务族，就补 profile/schema/preset/闭环；
不能归入时，先判断是横切工作流还是插件边界；
只有频率高、工作流独立、能闭合 L3，才考虑新增 family；
只有频率极高、入口价值清晰、不是 profile/preset 能承载，才考虑顶层场景。
```

## 6. 横切工作流矩阵

高频遗漏往往不是漏了“某个文档名”，而是漏了横切工作流。V15 要把横切能力作为矩阵第二主轴。

| 工作流原型 | 高频来源 | 现有承载 | 完善要求 |
| --- | --- | --- | --- |
| 快速规范化 | 所有现有 Word | P0 scene + TemplateConfig | 能解释启用模块、跳过项、输出和风险 |
| 范围定位 | 论文、标书、公文、长文档 | `FormatScopeConfig` | 页码、正文起点、关键词、样式锚点、Word story 可见 |
| 结构化输入 | 试卷、HR、表单、合同、申报 | `InputSourceProfile` / MaterialSchema | JSON/xlsx/schema 校验、预览和失败策略 |
| 资料填充 | 标书、合同、公文、HR | MaterialSchema + fill modules | 缺字段、缺图、残留占位符进 UI/report |
| 图片/签章/附件 | 标书、申报、合同、资质 | asset roles + manifest | role、路径、缺项、复制、ZIP、报告 |
| 同源多版本 | 试卷、合同、公文、投稿 | DeliveryPreset + visibility | 一个事实源、多版本、显隐预览、产物差异 |
| 批量生成 | HR、表单、证明、陪标 | BatchPreset | 逐记录隔离、失败不污染成功、汇总报告 |
| 多口径计数 | 学术、投稿、申报、披露 | CountProfile | Word-like 与规则口径并列，范围可解释 |
| 对象保护 | 技术、合同、财务、披露 | ObjectPreflightPolicy | finding、block/warn/skip、运行前确认、报告 |
| 固定版位 | 表单、证书、报价、套打 | form family + table/sdt/textbox | `w:trHeight`、内容控件、文本框、残留扫描 |
| 审阅对比 | 合同、公文、技术、投稿 | compare + DeliveryPreset | review preset、修订/批注保护、变更报告 |
| 提交归档包 | 投稿、申报、标书、资质、披露 | DeliveryPreset + manifest | 包结构、缺项、命名、ZIP、路径预检 |
| 插件边界 | OCR、AI、法律、财务、IP、LaTeX | plugin boundary | 前台可见、报告可见、人工确认可追踪 |

横切工作流必须能被 `SceneCoveragePack.capability_axis_ids` 表达。若某个能力只能在文档里说清，不能进 manifest、UI 或 report，就还不是可治理资产。

## 7. Word/OOXML 视角下的完整性

场景矩阵必须从 Word 本体反推。只按业务名称规划，必然会漏边界。

| OOXML / Package 面 | 高频任务 | 场景必须声明什么 |
| --- | --- | --- |
| `word/document.xml` paragraph/run | 所有 | 是否改写 run、是否保护字段结果、是否扫描残留 |
| `styles.xml` | 模板、论文、公文 | 外观归模板，场景覆盖要有业务理由 |
| `numbering.xml` | 论文、公文、长文档、合同 | 保留/重建/局部修复策略和报告证据 |
| `w:tbl/w:tr/w:tc` | 标书、试卷、表单、报价 | 合并单元格、列宽、表头重复、跨页、行高 |
| `w:trHeight` | 表单、证书、报价、套打 | 固定版位能力，不回到通用模板噪音 |
| `w:sdt` 内容控件 | 表单、合同、HR、公文 | 字段映射、填充、残留扫描、保护 |
| textbox / shape | 表单、公文、证书、双语 | 不能当普通段落粗暴重排，必须预检 |
| drawing/media/rels | 标书、技术、试卷、资质 | 图片角色、缺图、关系复制和 manifest |
| field | 目录、页码、交叉引用、合同编号 | 保留/刷新/跳过策略 |
| headers/footers | 论文、公文、合同、水印、披露 | 外观归模板，状态和版本归场景 |
| comments/revisions | 合同、技术审阅、投稿修回 | 默认保护，运行前确认 |
| footnotes/endnotes | 学术、书稿、法律附注 | CountProfile 声明是否计入 |
| hidden text | 合同、披露、双语 | 预检、计数和报告说明 |
| OLE / embedded workbook / Visio | 技术、财务、标书、披露 | block/warn/skip，不能静默破坏 |
| vba/macros | 外来模板、表单、合同 | 默认阻断或人工确认 |
| package relationships | 图片、附件、外链 | inventory、复制、缺项、外链风险 |

完善规则：

```text
L2 以上 family 必须声明 ooxml_touchpoints；
touchpoint 必须映射到 ObjectPreflightPolicy、模块消费或报告解释；
触碰高风险对象但没有预检策略，不能进入 L3。
```

## 8. 公式、输出、水印的重新归属

这三个对象不能再作为“暂不管”的剩余项。它们是场景矩阵横切能力。

| 对象 | 模板负责 | 场景负责 | 资料负责 | 会话负责 | 插件负责 |
| --- | --- | --- | --- | --- | --- |
| 公式外观 | 字体、字号、编号样式、间距基线 | 是否处理、范围、来源、低置信度、编号规则 | 本次题源或材料中的公式内容 | 本次是否降级或跳过 | 完整 LaTeX、专业转换、复杂公式识别 |
| 输出 | 默认 artifact 开关的基线可选 | final/review/student/signing/submission preset、命名、显隐、manifest | 资料包影响文件名和目录 | 输出目录、覆盖确认 | 外部提交系统、PDF/OCR 管线 |
| 水印 | 颜色、角度、字号等视觉基线 | 草稿、内部、保密、评审、签署等状态策略 | 水印文字、项目名、公司名 | 本次临时启用/关闭 | 权限、法律效力、DRM |

场景页不能只暴露“水印开关”或“输出开关”。正确形态是：

- 水印进入交付状态与 DeliveryPreset；
- 输出进入 DeliveryPreset、Workbench 路径预检和 artifact browser；
- 公式进入输入策略、转换策略、低置信度报告和专业插件边界；
- 模板只提供外观基线，不承诺专业内容处理。

## 9. 控件一致性作为矩阵准入门槛

场景配置控件样式控制必须与模板管理保持一致。这不是视觉统一问题，而是防止同一 Word 参数在两个地方变成不同语义。

| 参数/控件 | 场景页准入要求 |
| --- | --- |
| 字体 | 复用 `FontCombo`，单位和默认值跟模板一致 |
| 字号 | 复用 `SizeCombo` |
| 左缩进/右缩进 | 同一行，命名与模板一致，单位一致 |
| 段前/段后 | 同一行，复用数值+单位控件 |
| 特殊缩进 | 必须能切换“无 / 首行 / 悬挂”，不能只展示文字 |
| 特殊缩进值 | 选择“无”时禁用并置灰，选择首行/悬挂时启用 |
| 行距类型/行距值 | 作为组合语义呈现，固定值/倍数/最小值可切换 |
| 表格边框/列宽/行高 | 普通模板是样式基线，表单套打是版位策略 |
| 输出版本 | 使用 DeliveryPreset 编辑器，不用模板样式控件承载 |
| 风险策略 | 使用 summary、badge、combo、确认区，不伪装成普通 checkbox |
| 资料字段 | 使用 schema 驱动表单或表格，不靠自由文本 |

禁止模式：

```text
禁止同名参数使用不同控件；
禁止同名参数使用不同单位；
禁止场景页用自由文本替代已有领域控件；
禁止 UI 可配置但 resolver/pipeline/report 不消费；
```

## 10. 完善度分级

V15 建议继续使用 L0-L5，但每一级要有硬门槛。

| 等级 | 状态 | 最低证据 | 用户承诺 |
| --- | --- | --- | --- |
| L0 | 未归属 | 只有需求或讨论 | 不展示为能力 |
| L1 | Planning contract | registry / manifest / 文档有边界 | 只能说规划中 |
| L2 | 可见配置 | ScenePanel/Workbench 能看见 profile/schema/preset/边界 | 只能受限预览 |
| L3 | 可执行 first slice | UI、resolver、runtime、report、tests 闭合最小链 | 可作为受限能力 |
| L4 | 工作台闭环 | issue queue、确认、跳转、artifact browser、失败路径 | 可作为稳定工作流 |
| L5 | 治理闭环 | profile 来源、版本、迁移、回归、历史审计 | 可产品化推广 |

升级门槛：

```text
L1 -> L2：前台能看见，且边界可见；
L2 -> L3：至少一条真实执行链闭合；
L3 -> L4：失败、跳过、忽略、修复、产物浏览闭合；
L4 -> L5：profile/规则/插件治理可长期更新。
```

降级门槛：

```text
如果 UI 暴露但执行不消费，降到 L2；
如果执行消费但报告不解释，不能超过 L3；
如果触碰高风险 OOXML 但没有预检，不能超过 L2；
如果涉及专业判断但没有插件/人工边界，不能超过 L1。
```
