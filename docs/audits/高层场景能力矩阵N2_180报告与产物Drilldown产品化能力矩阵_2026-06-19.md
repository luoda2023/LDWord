# 高层场景能力矩阵 N2.180 报告与产物 Drilldown 产品化能力矩阵

日期：2026-06-19

## 1. 定位

N2.180 承接 V39 的 P0 缺口：把 output、compare、report、structured intermediate、material manifest、material package、scene sample manifest 和 output-target warning，从“执行 payload 中存在”推进到“用户可浏览、可分组、可打开、可报告、可回到修复入口”的产品化闭环。

它不替代 N2.176 DeliveryPreset execution。N2.176 证明“按 preset 能产出”；N2.180 证明“产出后能被看见、追踪和处理”。

## 2. 覆盖对象

| Artifact kind | 业务意义 | 当前承载 |
| --- | --- | --- |

| `scene_sample_docx` | 样本 DOCX | sample manifest child item |
| `request_cell_report` | 请求样本证据报告 | sample manifest child item |
| `planned_output` | 输出目标预检/即将覆盖目标 | output-target issue repair |

## 3. 当前产品化通道

N2.180 新增并锁定 9 个 report/artifact drilldown channel：

| Channel | 目的 |
| --- | --- |
| `artifact_state_model` | 统一 `ArtifactItemState`、`ExecutionResultState`、`RecentRunState` |
| `runtime_delivery_artifact_maps` | 将 output/compare/report/intermediate/material paths 保留到 runtime payload |
| `artifact_grouping_and_report_inference` | 根据 preset/group 推断报告归属，避免多产物散落 |
| `recent_run_artifact_browser` | RecentRunPanel 显示产物行，并提供打开文件/目录动作 |
| `quick_execution_artifact_log` | QuickExecutionDetail 日志仍能展示产物路径 |

| `sample_manifest_child_drilldown` | 样本 manifest 展开为 fixture DOCX 和 request-cell report |
| `output_target_warning_repair` | 输出目标预警进入 issue queue，并路由到 output delivery |
| `matrix_browse_report_artifact_drilldown` | dashboard、drilldown、summary、release gate 可浏览该能力 |

## 5. 边界裁决

- N2.180 不承诺所有 artifact 都能自动语义解释；它承诺路径、类型、分组、状态和打开动作可见。
- N2.180 不替代 report 内容质量审计；报告内容仍由各源审计、report writer 和具体 runtime 测试证明。
- N2.180 不替代 MaterialSchema 修复；资料缺口仍走 N2.177，artifact drilldown 只把 material manifest/package 纳入可见链。
- N2.180 不替代 fixed-layout profile；固定版式对象仍由 N2.178 管理，artifact drilldown 只负责输出后可浏览。
- 输出覆盖、目标目录冲突等风险进入 `output_target` repair route，但不自动替用户改写输出策略。

## 6. 仍非 Green/L5 的原因

N2.180 现在是“artifact 可见性与门禁闭环”，但还不是完整 Green/L5：

- artifact browser 仍主要承载最近一次执行结果，不是完整历史产物库。
- report 到具体 artifact 的双向跳转仍可继续细化，例如从报告某条 issue 直接定位到 compare/intermediate/package 文件。
- 多 profile 批量执行的 artifact tree 仍需要更丰富的失败隔离、重试入口和筛选能力。
- 真实业务 fixture 仍需要覆盖成功、降级、失败、人工确认四类 journey。

## 8. 结论

N2.180 已把“报告和产物只是执行 payload 里的路径”推进为“矩阵可见、门禁可验、前台可浏览、问题可回到修复入口”的闭环。

下一步仍应继续补真实业务 fixture 深度和 report-to-artifact 的双向 drilldown，而不是继续扩张顶层场景入口。
