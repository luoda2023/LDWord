# 标准样稿格式要求 AI 分析链路执行与验证

> 执行日期：2026-07-29  
> 场景：用户上传一份 DOCX，并输入“这个是标准的规划文件，帮我看看确定对应的格式要求”  
> 目标：可靠识别标准样稿的格式证据，由 AI 生成可审阅的格式要求说明；不把分析请求误执行为排版、生成或覆盖文档。

## 1. 最终结论

该场景现在采用独立的“格式证据分析”链路：

```text
用户上传 DOCX + 明确要求分析格式
  → 识别为只读格式分析
  → 将本轮附件标记为标准样稿
  → 获取正文与结构化格式证据的披露授权
  → 本地确定性提取 DOCX 格式证据
  → 证据随本轮上下文发送给模型
  → 模型按“已确认 / 冲突 / 待确认 / 下一步”归纳
  → 对话正文 + 精简格式证据卡片
```

它不会：

- 把标准样稿当作待修改的目标文档；
- 自动创建生产计划；
- 自动执行快速排版、组卷或文档生成；
- 把“未读取到的属性”猜成默认规范；
- 把本机绝对路径发送给模型；
- 在用户没有指定目标文档时，声称已经完成格式应用。

因此，“确定格式要求”链路已通；“把这些格式应用到另一份文档”是下一条显式生产链路，需要目标文档和用户确认，不能与本次只读分析暗中合并。

## 2. 原有缺口

此前链路只会把 DOCX 正文作为普通附件文本发送给模型。正文可以说明内容，却不能可靠证明页面、段落、标题、页眉页脚、表格和编号的格式。

主要问题包括：

1. 附件没有语义角色，无法区分“标准样稿”和“待处理文档”；
2. 披露授权只有正文，没有格式证据字段；
3. AI 可能仅凭可见文字猜测纸张、边距、字号或行距；
4. “确定格式要求”可能被普通格式化关键词误导为生产任务；
5. UI 没有展示“本轮确实读取到了哪些格式证据”；
6. 工具层无法按需返回结构化格式信息；
7. 缺少正向、反向和端到端测试。

## 3. 架构职责

| 层级 | 职责 | 不负责 |
|---|---|---|
| `domain/docx_format_evidence.py` | 意图识别、附件语义角色、披露字段、DOCX 格式证据提取、模型约束 | UI 状态、生产执行 |
| `runtime/turn_runner.py` | 校验授权、构造模型上下文、记录审计摘要 | 猜测格式、修改文档 |
| `application/capability_registry.py` | 将该请求分类为 review | 生成生产计划 |
| `application/plan_builder.py` | 明确阻断误入生产链路 | 执行格式分析 |
| `adapters/form_tools.py` | 为本地工具调用提供可选结构化证据 | 决定用户意图 |
| `ui/assistant_panel.py` | 绑定本轮角色、展示模型回复与证据卡片 | 持有 DOCX 解析规则 |

核心格式规则只有一个所有者：`docx_format_evidence.py`。运行时、UI 和工具层只消费它的结果，避免复制多套判断形成补丁堆叠。

## 4. 意图与附件角色

### 4.1 只读分析的命中条件

以下表达会进入格式证据分析：

- “这个是标准的规划文件，帮我看看确定对应的格式要求”
- “分析这份标准样稿的格式规范”
- “按这份参考样稿总结格式要求”

以下表达不会误命中：

- “什么是 Word 格式规范？”——没有指向附件；
- “把这个文档统一格式”——这是修改意图；
- “按这个样稿套用到目标文档”——这是生产意图；
- 下一轮与格式分析无关的普通消息——附件角色会被清除，不会永久污染会话。

### 4.2 附件角色

本轮命中后，附件被标记为：

```text
semantic_role = standard_format_reference
semantic_role_source = assistant_intent
```

这个角色只表示“格式证据来源”，不等于待处理输入，也不自动升级成系统模板。

## 5. 结构化格式证据范围

当前提取内容覆盖：

### 5.1 文件与页面

- 文件名与 SHA-256；
- 节数、段落数、表格数；
- 纸张宽高、方向；
- 上下左右页边距；
- 页眉、页脚距离；
- 分节起始方式；
- 页码、总页数等字段指令；
- 奇偶页、首页不同等设置。

### 5.2 段落与标题

- 实际使用的段落样式；
- 样式层级和大纲级别；
- 中文、英文和复杂文字字体；
- 字号、粗体、斜体；
- 对齐方式；
- 首行缩进、左右缩进；
- 段前、段后；
- 行距及其规则；
- 属性来自当前样式还是继承样式。

这保证了正文、一级标题、二级标题等要求来自文档证据，而不是只读取样式名称。

### 5.3 表格与编号

- 表格样式、行列数量；
- 表格宽度、对齐、布局；
- 单元格边距和边框配置概况；
- 编号段落与编号层级；
- 编号格式、起始值、文本模式；
- 编号层级的字体和段落属性。

### 5.4 直接格式

- 非样式控制的字号、字体、粗斜体和对齐等直接格式；
- 直接格式出现次数和代表性样例；
- 用于提示“样稿内部是否存在样式与手工格式并存”。

## 6. AI 输出约束

模型收到的不是一句“请分析格式”，而是带版本号的结构化证据：

```text
<document_format_evidence>
{
  "schema_version": "docx-format-evidence-v1",
  ...
}
</document_format_evidence>
```

系统约束要求：

1. 只依据结构化证据确认格式；
2. `null` 或缺失值必须写入“待确认”，不得补猜；
3. 区分样式定义、继承值和直接格式；
4. 发现同层级不一致时归入“冲突/例外”；
5. 输出“已确认、冲突、待确认、下一步”；
6. 本轮只分析，不修改、不生成、不宣称已应用；
7. 没有格式证据时要求用户补充 DOCX 标准样稿。

## 7. UI 结果

一次成功分析会产生两类结果：

1. AI 正文：面向用户解释最终格式要求、冲突和待确认项；
2. “格式证据”卡片：只展示样稿名称、节数、使用样式数、表格数、编号段落数和短哈希。

证据卡片不是第二份冗长报告，而是用于确认“系统读取了哪份样稿、读到了什么规模的结构”。格式细节仍由 AI 正文承载。

## 8. API 与隐私边界

普通附件仍只申请：

```text
document_text
```

被识别为标准样稿的附件，本轮申请：

```text
document_text
document_format_evidence
```

格式证据通过既有附件披露授权进入模型上下文。发送内容包含文件名和文件哈希，不包含本地绝对路径。

这使 API 配置边界保持清晰：

- 模型配置继续使用既有 Provider、模型和密钥链路；
- 不要求模型直接读取本机文件；
- DOCX 解析由本地确定性代码完成；
- 模型只负责基于证据进行归纳；
- 审计记录可以证明发送了哪些字段，而不记录文件路径。

## 9. 与格式应用链路的边界

本次只读分析完成后，如果用户进一步要求“按这个标准样稿处理另一份规划文件”，合理链路应是：

```text
已确认格式证据
  + 明确的目标 DOCX
  → 创建可审阅的应用计划
  → 标准样稿作为 reference
  → 目标文档作为 input
  → 预检差异
  → 用户批准
  → 执行
  → 输出新文件并验证
```

当前实现没有为了“看起来完整”而把这条生产链路偷偷接到分析请求后面。这样可以避免标准样稿被覆盖、输入角色颠倒和未经批准写文件。

## 10. 验证矩阵

| 场景 | 预期 |
|---|---|
| 标准样稿 + 明确格式分析请求 | 提取格式证据，调用模型，显示证据卡片 |
| 普通 DOCX 对话 | 只披露正文，不额外解析格式证据 |
| 泛知识问题“什么是格式规范” | 不将附件自动标为标准样稿 |
| 修改请求“统一这个文档格式” | 不走只读分析 |
| 分析完成后的无关下一轮 | 清除临时标准样稿角色 |
| 没有生产目标 | 不创建计划，不执行，不写文件 |
| 强制绕过 UI 做生产预检 | 以 `assistant_capability_not_executable` 阻断 |
| 本地工具显式请求格式证据 | 返回同一结构化证据模型 |
| 证据包含本地路径 | 必须为否 |
| 标题、正文、页面、页眉页脚、表格、编号、直接格式 | 均有结构化覆盖 |

## 11. 验证方式

验证覆盖：

- DOCX 结构提取单元测试；
- 意图正反例测试；
- 附件角色生命周期测试；
- 披露授权字段测试；
- Runtime → Provider 上下文测试；
- UI 端到端对话与证据卡片测试；
- Plan Builder 安全边界测试；
- Form Tool 结构化输出测试；
- Assistant 全量回归；
- 场景路由、文案、编码、架构边界和产品定位回归；
- Python 编译检查；
- 真实大型 DOCX 的只读提取与本地路径泄漏检查。

本轮结果：

- 格式分析链路及直接关联回归：`70 passed in 52.34s`；
- 扩大到 Assistant、场景路由、文案、编码、架构边界和产品定位：`197 passed`；
- 扩大回归同时发现 1 个不在本次修改路径内的既有 UI 文案守卫失败：`src/ui/adapters/workbench_material_issues.py` 命中旧文案禁用词；本轮没有用修改无关页面的方式掩盖该结果；
- 相关 Python 模块 `compileall` 通过；
- 变更文档 UTF-8 读取正常；
- 真实大型 DOCX 证据提取完成，结构化证据不含本地绝对路径。

## 12. 已知边界

当前证据链可以可靠说明 OOXML 中可读取的格式属性，但以下内容仍不能被夸大为已自动解决：

- Word 最终分页、孤行控制和字体替换后的打印效果；
- 嵌入对象、文本框、复杂域、宏和第三方插件产生的视觉结果；
- 扫描件或图片中的视觉格式；
- 仅凭一个样稿判断哪些差异是强制规范、哪些只是个案；
- 将分析结果持久化为可复用模板；
- 对另一份文档执行格式迁移。

前四项需要渲染或人工确认；后两项应由独立、显式、可预检的生产能力承担。
