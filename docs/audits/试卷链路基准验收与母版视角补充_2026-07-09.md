# 试卷链路基准验收与母版视角补充

日期：2026-07-09

## 1. 验收结论

试卷链路可以作为后续工作模式和母版管理改造的第一条基准链路。

原因不是“试卷最简单”，而是它已经具备一个完整闭环：

```text
工作模式/场景入口
  -> 试卷装配规则
  -> 母版选择
  -> 母版复制 / 导入 / 发现 / 删除
  -> 占位符契约
  -> 运行时字段填写
  -> 结构化试题源
  -> 学生卷 / 答案速查多版本输出
  -> 样张预览
  -> Pipeline output_paths
  -> 报告与证据
```

这条链路已经说明：未来“母版管理”不能只理解成一个 DOCX 文件列表，也不能退回到现有“模板管理”的参数面板。母版必须是一个带生命周期、占位符契约、运行时装配规则、预览样张和输出证据的产品对象。

## 2. 当前试卷链路盘点

### 2.1 配置对象

当前试卷链路的核心配置对象主要在 `src/config/scene.py` 和 `src/shared/engine/exam_paper_style.py`。

`ExamPaperConfig` 是场景级装配规则：

- `blank_style_id`：当前选择的试卷母版。
- `question_structure_mode`：题目结构装配方式。
- `answer_policy`：生成学生卷、答案速查，还是两者都生成。
- `custom_blank_styles`：用户拥有的母版副本或导入母版。
- `runtime_fields`：工作台每次执行时需要填写的字段，例如标题、科目、年级、考试时间、满分。

这里已经有一个很重要的边界：`ExamPaperConfig` 只保存长期稳定的装配规则，不保存每次运行时的具体标题、科目、时间等值。

`ExamBlankStyleConfig` 是用户侧母版记录：

- `style_id`
- `label`
- `base_style_id`
- `master_docx_path`

它更接近未来 `MasterSpec` 的用户资产部分，但还不是完整的通用母版模型。

`ExamBlankStyleSpec` 是解析后的母版规格：

- 母版 ID、名称、摘要、状态。
- 是否只读。
- 内置 DOCX 文件名。
- 页面边距、字号、行距等基础版式参数。

这说明试卷链路里已经隐含了三层：

```text
SceneWorkspace.exam_paper      长期装配规则
ExamBlankStyleConfig           用户母版资产记录
ExamBlankStyleSpec             可解析、可预览、可写入的母版规格
```

后续通用化时，不应该把这三层压扁成一个“模板”对象。

### 2.2 文件资产

当前试卷母版文件按旧目录放置：

```text
exam_masters/
  builtin/
    default_exam_v20.docx
    exam_content_generation_prompt.md
    exam_master_conversion_prompt.md
  user/
    user_default_exam_copy*.docx
    user_imported_exam*.docx
    手动放入的可识别母版.docx
```

这个现状暴露两个验收点：

1. 内置母版资产和用户母版资产必须分开。
2. 用户目录里可能已经有大量历史副本、导入文件和手动放入文件，迁移时不能批量清理、覆盖或重命名。

所以新规划中的 `config_library/masters/exam/` 第一阶段只能作为 manifest 试点或只读 registry，不能直接搬迁 `exam_masters/user/`。

### 2.3 占位符契约

试卷母版已经有明确占位符契约：

```text
{{af_title}}
{{af_version}}
{{af_subject}}
{{af_grade}}
{{af_duration}}
{{af_total_score}}
{{af_questions}}
{{af_answer_area}}
```

其中：

- `{{af_title}}`、`{{af_subject}}`、`{{af_grade}}`、`{{af_duration}}`、`{{af_total_score}}` 来自工作台运行时字段。
- `{{af_version}}` 来自生成结果版本，例如学生卷或答案版。
- `{{af_questions}}` 是题目插入点。
- `{{af_answer_area}}` 是作答区插入点。

代码里还保留了旧版占位符兼容，例如“【试卷标题】”“题目会在正式生成时从这里开始。”等。这一点对后续迁移非常关键：母版管理不只是读取新 manifest，还要识别旧母版、旧占位符和用户手工改造过的文档。

未来 `MasterSpec` 至少应该包含：

```text
placeholder_contract:
  required:
    - af_title
    - af_questions
  optional:
    - af_answer_area
  runtime_fields:
    - title
    - subject
    - grade
    - duration
    - total_score
  generated_fields:
    - version
  legacy_aliases:
    - 旧版占位符集合
```

### 2.4 UI 链路

试卷链路当前在 `ScenePanel` 的 `scn_exam_paper` 卡片中呈现，用户能完成这些动作：

- 选择当前母版。
- 恢复默认母版。
- 创建母版副本。
- 重命名用户母版。
- 打开用户母版文件夹。
- 删除用户母版。
- 查看学生卷 / 答案版预览。
- 复制 AI 提示词。
- 跳转工作台填写运行时字段。

这说明未来“母版管理”页面不应该只是文件表格，而至少需要覆盖：

```text
母版列表
  -> 当前选择
  -> 内置/用户状态
  -> 复制/导入/打开文件夹/删除
  -> 预览
  -> 样张生成
  -> AI 改造提示词
  -> 运行时字段提示
```

### 2.5 运行时与输出链路

试卷运行时由结构化题源和工作台字段共同驱动。

关键链路：

- `input_source_profile.material_schema_id = "exam_items_v1"` 定义试题资料源。
- 工作台 `entity_data` 填入标题、科目、年级、考试时间、满分等运行时字段。
- `inspect_exam_question_schema()` 校验题源结构。
- `build_exam_delivery_runtime()` 构建试卷交付运行时。
- `write_exam_paper_docx_files()` 生成学生卷和答案速查。
- `Pipeline.execute()` 将结果暴露为 `output_paths["student"]` 和 `output_paths["answer_key"]`。

这说明“母版”只决定承载和插入点，不能替代资料 schema，也不能替代交付策略。

## 3. 试卷基准应沉淀的通用能力

以下能力应作为其他工作模式的对照基准。

### 3.1 模式内母版仓库

试卷已经有 `exam_masters/builtin` 和 `exam_masters/user`。

通用化后应形成：

```text
MasterLibrary(mode_id="exam")
  -> builtin masters
  -> user masters
  -> imported masters
  -> discovered manual masters
  -> generated samples
```

公文、标书、论文也应该按自己的 `mode_id` 过滤，而不是共享一个平铺模板池。

### 3.2 母版生命周期

试卷当前已经存在这些状态：

- 内置母版：只读、可复制。
- 用户副本：可重命名、可删除。
- 导入母版：从外部 Word 复制进入用户目录。
- 手动发现母版：用户放入文件夹后被识别。
- 无效 Word 文件：不应登记为母版。
- 样张文件：用于预览验收，不等同于母版本体。

这应该补入通用规划。否则后续公文母版会很容易陷入“文种太多，所以文件种子无限膨胀”的问题。

### 3.3 占位符契约前置

试卷证明了占位符契约是母版能否被程序装配的核心。

未来公文和标书也需要类似契约，例如：

- 公文：标题、发文字号、主送机关、正文、附件说明、发文机关署名、成文日期、版记等。
- 标书：项目名称、招标编号、投标人、章节目录、响应内容、附件清单等。
- 论文：题名、作者、摘要、关键词、正文、参考文献、附录等。

不能只说“有一个 DOCX 母版”，必须能回答：

```text
程序从哪里插入正文？
哪些字段由资料包提供？
哪些字段由工作台运行时填写？
哪些字段由交付版本生成？
缺少占位符时如何报错？
旧占位符如何兼容？
```

### 3.4 同源多版本输出

试卷已经通过 `answer_policy` 从同一份题源生成：

- 学生卷
- 答案速查
- 仅学生卷
- 仅答案速查

这对公文也有借鉴意义。公文可能不是学生卷/答案版，而是：

- 正式发文稿
- 审阅稿
- 套红稿
- 清稿
- 归档资料包

所以通用模型里应保留“同源多交付版本”的能力，不要把它藏进某个母版文件。

### 3.5 AI 边界

试卷现在已经分成两类提示词：

- 生成试卷内容：输出 Markdown / 结构化题源，不写页眉、页脚、页码、密封线等版式信息。
- 改造母版：保留 Word 版式，删除真实题目和答案，替换为占位符。

这是非常好的产品边界。未来公文也应该类似：

- 公文内容生成：按文种生成正文和要素，不负责套红和版记细节。
- 公文母版改造：保留红头、版心、版记、页边距、机关标识等，替换为占位符。

AI 可以帮助生成或改造，但最终验收对象仍然是母版契约和样张结果。

### 3.6 证据链路

试卷链路已有测试覆盖：

- 母版副本是否能被选择。
- 导入母版是否复制到用户目录。
- 手动放入母版是否能被发现。
- 无效 Word 文件是否被忽略。
- 学生卷和答案速查是否按策略生成。
- `Pipeline` 是否暴露对应 `output_paths`。
- 题图数量和 alt text 是否进入运行时报告。

这说明未来每个工作模式都要有“生成了什么、由哪个母版生成、哪些字段可见、哪些内容被隐藏、哪些资料缺失”的证据输出。

## 4. 上一份总规划的视角缺失

上一份《工作模式与母版管理配置分层规划》已经把“工作模式、母版、模板、场景规则、资料包”拆开了，但以试卷链路复盘后，还需要补足以下视角。

### 4.1 缺少母版生命周期状态机

原规划提到了 `builtin/user` 目录，但还没有把母版生命周期作为一等对象。

建议补入：

```text
builtin -> copy_to_user -> user_editable -> selected
external_docx -> imported -> selected
manual_file -> discovered -> selected
selected -> sample_generated -> verified
user_editable -> deleted
invalid_file -> ignored_with_reason
```

这对保护 `exam_masters/user` 非常重要。

### 4.2 缺少占位符契约验收

原规划提到了母版 manifest，但还没有强调“占位符契约”必须可检测、可报告、可兼容旧版。

建议把 `placeholder_contract` 放进 `MasterSpec`，并在样张生成前做 preflight。

### 4.3 缺少运行时字段与资料包字段的分界

试卷里标题、科目、年级、考试时间、满分是运行时字段；试题列表是结构化资料源。两者不应混在母版配置里。

未来公文也要明确：

- 发文机关、成文日期、文号可能是运行时字段。
- 正文、附件、依据材料可能来自资料包。
- 红头、版心、版记位置属于母版。
- 文种规则属于场景规则或文种 profile。

### 4.4 缺少样张与母版本体的分离

试卷有 `write_exam_blank_style_sample_docx()`。样张是验收产物，不是母版本体。

通用规划需要明确：

- 母版 DOCX：可编辑的壳。
- 样张 DOCX：用示例数据渲染后的检查件。
- 正式输出 DOCX：用户本次运行的结果。
- 报告 JSON/MD：证据件。

这些文件不能混放成一个概念。

### 4.5 缺少用户资产安全策略

试卷用户目录已经有大量副本和导入件。后续迁移必须默认用户资产不可破坏。

建议原则：

- 新目录先双读，不迁移。
- 只复制，不移动。
- 不批量删除。
- 程序生成文件用稳定前缀识别。
- 手动文件只在明确满足占位符契约时登记。
- 删除操作只能删除当前用户选择的、位于用户母版目录内的文件。

### 4.6 缺少证据与报告作为验收对象

母版改造不是 UI 切换成功就算完成。至少要能在报告或运行时结果中回答：

```text
使用了哪个 mode_id？
使用了哪个 scene_id？
使用了哪个 master_id？
母版文件路径是什么？
母版是否内置/用户/导入/发现？
占位符检查是否通过？
生成了哪些 output_paths？
哪些交付版本隐藏了哪些内容？
资料包字段是否完整？
```

### 4.7 缺少 UI 导航和修复入口稳定性

现有测试和修复入口依赖 `scene`、`template`、`scn_exam_paper` 等 ID。

所以第一阶段可以改产品文案和新增模式选择器，但不要急着改内部 ID。后续如果把“场景管理”改成“模式规则”或“母版管理”，也要保留 alias map。

### 4.8 缺少视觉验收层

当前试卷测试主要检查 DOCX 文本、XML、输出路径和运行时证据。对于母版管理来说，这已经足够保护功能链路，但还不能完全证明视觉排版无误。

后续如果要把母版作为产品核心，建议增加：

- DOCX 转 PDF 或 PNG 的样张渲染检查。
- 首屏/第一页布局验收。
- 占位符是否残留的可视化检查。
- 页眉、页脚、密封线、页码、题区位置的截图基准。

这不是第一阶段必须做，但应进入验收视角。

## 5. 试卷基准验收矩阵

| 维度 | 当前试卷状态 | 后续改造要求 |
| --- | --- | --- |
| 工作模式入口 | 还没有顶层 `exam` work mode selector | 先新增只读/轻量 registry，再接标题栏 |
| 场景规则 | `SceneWorkspace.exam_paper` 已保存装配规则 | 保留为模式规则，不改名成母版 |
| 内置母版 | `default_exam_v20.docx` 可用 | 包装成 `MasterSpec`，不移动文件 |
| 用户母版 | 支持复制、导入、发现、删除 | 用户资产只复制不搬迁 |
| 占位符契约 | 代码中已有必需占位符和旧版兼容 | manifest 中显式声明并可报告 |
| 预览 | 支持学生卷 / 答案版预览 | 通用母版管理也应有预览态 |
| 样张 | 可生成示例 DOCX | 样张与母版本体分目录 |
| AI 提示词 | 内容生成和母版改造已分离 | 各模式沿用双提示词边界 |
| 资料源 | `exam_items_v1` 支持结构化题源 | 资料 schema 按 mode 分目录 |
| 运行时字段 | 工作台填写，不存入场景长期配置 | 继续保持 owner 分离 |
| 多版本输出 | 学生卷 / 答案速查 | 通用为 delivery versions |
| 报告证据 | output paths 和 runtime evidence 已有 | 增加 master_id/path/placeholder evidence |
| UI 导航 | `scn_exam_paper` 已稳定 | 第一阶段保留 ID，文案逐步调整 |
| 视觉验收 | 以 DOCX/XML/文本为主 | 后续补 DOCX 渲染截图基准 |

## 6. 以试卷为起点的执行建议

### Phase E0：冻结现状认知

只做文档和测试确认，不改运行时代码。

验收：

- 试卷基准文档存在。
- 总规划文档补充试卷基准引用。
- 不改动 `exam_masters/` 文件。

### Phase E1：新增 `WorkModeSpec(exam)`

新增工作模式 registry，但不改变 resolver、pipeline 和旧 scene/template 加载。

`exam` 模式先只描述：

```text
mode_id: exam
label: 试卷版
default_scene_id: exam
default_template_id: default
master_domain: exam_blank_master
material_schema_ids:
  - exam_items_v1
```

验收：

- 能列出 `exam` 工作模式。
- 不影响现有试卷生成测试。

### Phase E2：用 `MasterSpec` 包装现有试卷母版

新增 `master_library`，先从现有 `ExamBlankStyleSpec` 包一层，不迁移目录。

验收：

- `default_exam` 能以 `MasterSpec` 形式列出。
- 仍然走 `exam_masters/builtin/default_exam_v20.docx`。
- 仍然识别 `exam_masters/user` 里的用户母版。

### Phase E3：试点 mode-scoped manifest

可以新增只读 manifest：

```text
config_library/masters/exam/builtin/default_exam.master.json
```

但第一阶段只允许作为补充描述，不作为唯一事实来源。

验收：

- manifest 存在时增强展示。
- manifest 不存在时旧链路照常工作。
- 用户母版不被迁移、不被重命名。

### Phase E4：补运行时证据

在报告或运行时结果中增加：

```text
mode_id
master_id
master_label
master_source_type
master_docx_path
master_version
placeholder_contract_status
```

验收：

- 生成学生卷 / 答案速查后能追溯使用的母版。
- 占位符缺失时能看到明确错误，而不是静默生成坏文件。

### Phase E5：再接标题栏工作模式切换

标题栏可以显示“试卷版”，但切换逻辑要在 registry、bridge 和兼容测试稳定后再接。

验收：

- 切到试卷版后仍打开现有试卷装配。
- 旧 `scene` panel id 不变。
- 旧 `scn_exam_paper` 导航和修复跳转不变。

## 7. 对后续公文规划的直接启发

公文不应该创建十几个完整大模板来应对所有文种。

更稳的结构是：

```text
公文版
  -> 公文母版族
      -> 通用发文母版
      -> 函件母版
      -> 纪要母版
      -> 会议材料母版
  -> 文种 profile
      -> 通知
      -> 请示
      -> 报告
      -> 批复
      -> 函
      -> 纪要
  -> 资料包 schema
      -> 发文要素
      -> 附件清单
      -> 依据材料
      -> 主送/抄送/版记信息
  -> 交付版本
      -> 审阅稿
      -> 正式稿
      -> 套红稿
      -> 归档包
```

也就是说，公文的复杂度应该拆到“母版族 + 文种 profile + 资料包 + 交付版本”，而不是直接膨胀成十几个互不相干的文件种子。

## 8. 当前结论

试卷链路已经证明了一个可行范式：

```text
母版负责承载版式和占位符
场景规则负责长期装配策略
资料包负责结构化内容
工作台负责每次运行时字段
交付策略负责多版本输出
报告负责可追溯证据
```

## 14. 再审：exam_masters/user 残留副本与试卷母版治理

本轮用户打开 `exam_masters/user` 后看到 202 个 `.docx`，其中大量文件名类似 `user_default_exam_copy_100.docx`。这不是新的方案库，也不是公文或论文母版库，而是试卷旧链路中用户母版副本的物理文件池。

### 14.1 为什么会产生这么多

试卷母版“创建副本”当前走的是物理复制：

```text
用户点击创建副本
  -> create_exam_blank_master_copy()
  -> create_exam_blank_style_copy()
  -> ensure_current_exam_blank_master_docx()
  -> _unique_docx_path(exam_masters/user/user_default_exam_copy.docx)
  -> copy2(source, target)
```

`_unique_docx_path()` 的设计是：如果目标文件存在，就不断加 `_2`、`_3`、`_100`。这能保证不覆盖用户已经改过的 Word 母版，但如果用户反复创建副本、测试、删除配置引用而没有清理文件，就会留下大量 DOCX。

### 14.2 它们会不会成为产品内置项

不应该，也不应进入正式产品包。

当前已有两个保护：

```text
.gitignore:
  exam_masters/user/

scripts/check_public_release.py:
  LOCAL_ONLY_PATHS 包含 exam_masters/user
```

也就是说，发布检查会把它视为 runtime/user path，而不是产品内置资产。

代码里也有扫描保护：

```text
sync_user_exam_blank_master_files()
  会跳过 user_default_exam_copy*
  会跳过 user_imported_exam*
```

这表示程序生成的历史副本不会被自动反向发现成大量可选母版。它们主要是“文件夹观感”和“本地空间治理”问题，不是“产品会内置 202 个母版”的问题。

### 14.3 但当前体验仍然不合格

虽然它们不应进入发布包，但用户从“打开母版文件夹”进入后看到 202 个文件，会自然认为产品库脏了。这说明现在的母版文件池还缺少产品化治理：

```text
缺少当前方案引用文件的高亮
缺少未引用副本清单
缺少程序生成副本和用户手工放入文件的区分展示
缺少归档入口
缺少安全清理前的引用检查
```

因此不能把“不会发布”当成最终答案。它解释了风险边界，但不能解决用户体验。

### 14.4 正确治理方式

不要第一步直接删 `exam_masters/user`。正确做法是先建立只读盘点：

```text
1. 被当前方案引用
   - config.exam_paper.blank_style_id 当前选中
   - config.custom_blank_styles 中有 master_docx_path

2. 程序生成但未引用
   - user_default_exam_copy*
   - user_imported_exam*

3. 用户手工放入且可发现
   - 非程序前缀
   - docx 可打开
   - 包含试卷母版占位符或可识别契约

4. 不可识别 / 风险文件
   - docx 不可打开
   - 缺占位符
   - 与当前方案无引用关系
```

清理动作只能在盘点后提供：

```text
归档到 archive 目录
从当前方案移除引用
删除未引用程序副本
打开所在文件夹
```

其中“删除”必须有确认，不应自动执行。

### 14.5 与新 config_library 的关系

新的方向是：

```text
内置母版 manifest：
  config_library/masters/exam/builtin/default_exam.master.json

试卷内置 DOCX：
  exam_masters/builtin/default_exam_v20.docx

用户运行期 DOCX：
  exam_masters/user/*.docx
```

这是一个过渡结构。更理想的最终结构是：

```text
config_library/masters/exam/builtin/*.master.json
config_library/masters/exam/user/*.master.json
用户 DOCX 文件由 manifest 指向本地 app-data 或用户确认目录
```

但迁移时不能强行搬文件，因为已有方案可能引用旧路径。短期应保留兼容，只把 UI 和清理工具做好。

### 14.6 对“方案预览”的影响

试卷版“方案预览”不应该把 `exam_masters/user` 文件夹里的每个 DOCX 都当成一级产品对象展示。它应该展示：

```text
内置方案：
  默认试卷
  随堂测验
  期中期末

当前方案使用的母版：
  默认试卷母版
  或当前用户副本

可管理动作：
  创建副本
  打开当前母版
  归档 / 清理时打开所在文件夹
  归档 / 清理未引用副本
```

用户需要看到的是“当前方案使用哪份母版”，不是整个历史副本池。

### 14.7 后续验收

试卷链路后续应新增验收：

```text
[ ] 方案预览只显示当前方案相关母版，不把 202 个文件变成主列表
[ ] 创建副本后只新增 1 个配置引用和 1 个 DOCX
[ ] 删除副本时先确认，并只删除当前方案引用的用户副本
[ ] 未引用程序副本可被盘点出来
[ ] exam_masters/user 不进入发布包
[ ] 打开文件夹入口优先打开当前选中母版所在位置，并提示这是用户副本目录
```

### 14.8 本轮裁决

`exam_masters/user` 的大量文件是历史试卷母版副本策略造成的，不是当前“方案 / 模板 / 母版”分层规划本身错了。真正要修的是副本治理和 UI 暴露方式：保留用户安全，不自动删除；收敛产品视图，不让运行期文件池变成用户看到的主对象。
