# 页眉页脚页面信息架构重构规划（2026-06-04）

状态：规划记录，不执行代码修改。

范围：模板编辑中的“页眉与页脚”详情页。本文只讨论该页面的信息架构、交互语义、控件分组和后续实现路径，不讨论目录、参考文献、标题编号等其它页面。

## 1. 背景

当前页眉页脚页面经历了几轮局部优化：

- 补齐了页眉、页脚、页码、首页不同、奇偶页不同、分区排除等配置链路；
- 将部分折叠高级区改成普通卡片；
- 将 `first/even/default` 等 Word 能力接入到配置模型和执行层；
- 删除了一些明显多余的说明文本。

但最新界面仍然不符合用户直觉。问题已经不是“某个字段放错位置”，而是页面整体仍在按照 Word 技术模型组织，而不是按照用户完成任务的路径组织。

当前界面让用户同时面对：

- 应用方案；
- 页眉；
- 页脚；
- 首页与奇偶页；
- 分区排除；
- 页码规则；
- 文字样式；
- 顶部摘要；
- 总开关。

这些对象之间的主次、因果和生效关系不清晰，导致用户无法判断自己到底在配置“页眉页脚”、“页码”、“页面例外”还是“Word 分节规则”。

## 2. 根本判断

页眉页脚页面不应被定义为：

> 一个 HeaderFooterConfig 字段编辑器。

也不应被定义为：

> 一个 Word 页眉页脚对象模型编辑器。

它应该被定义为：

> 一个用于配置文档页面顶部、底部和页码显示规则的结果导向型设置页。

用户进入这个页面时，心里想的不是 `header/footer/first/even/section/page field`，而是：

1. 我的文档要不要页眉？
2. 我的文档要不要页脚？
3. 我的文档要不要页码？
4. 封面、目录、声明页这些地方要不要隐藏？
5. 页码从哪里开始、用什么编号？
6. 首页或奇偶页有没有特别要求？
7. 字体字号是否符合学校或单位要求？

因此，UI 必须按这个任务路径组织，而不是按底层配置结构组织。

## 3. 当前页面的主要问题

### 3.1 总开关语义冲突

截图中顶部“页眉与页脚”总开关处于关闭状态，但下面仍然显示大量可编辑配置：

- 页眉内容；
- 页眉横线；
- 页脚内容；
- 页脚对齐；
- 首页不同；
- 奇偶页不同；
- 页码模板。

这对用户是第一层认知冲突。

用户会自然理解为：

- 开关关闭：这个功能不生效；
- 开关开启：下面配置生效。

如果开关关闭时仍然展示一堆可编辑表单，用户会无法判断：

- 这些设置是否会被保存？
- 保存后是否会在下次开启时生效？
- 当前预览摘要为什么还显示页眉页脚信息？
- 禁用状态和配置状态哪个更重要？

结论：

总开关必须成为页面信息架构的最高优先级。关闭时，页面应进入“关闭态”，只显示简洁摘要和启用入口；开启后才展示完整配置。

### 3.2 “页脚内容 = 仅页码”不符合用户直觉

当前把页码放在“页脚内容”里，例如：

- 页脚内容：仅页码；
- 页脚对齐：居中。

这是 Word 实现视角，因为页码通常写入 footer part。但普通用户不会把“页脚”和“页码”理解成同一个东西。

用户更直觉的模型是：

- 页眉：顶部文字；
- 页脚：底部文字；
- 页码：页码，可以放在页脚，也可能放在页眉。

因此“页脚内容”里出现“仅页码”会造成歧义：

- 我选了“仅页码”，是不是代表没有页脚文字？
- 页脚是不是就等于页码？
- 如果我要页脚文字 + 页码，应该在哪里配？

结论：

UI 层应拆开：

- 页眉显示；
- 页脚文字；
- 页码显示与位置。

底层仍可以把页码写到 footer，但 UI 不应暴露这种实现事实。

### 3.3 “页码模板 {page}”过于工程化

`{page}` 是模板表达式，不是用户语言。

普通用户更容易理解：

- `1`
- `第 1 页`
- `第 1 页 / 共 10 页`
- `Page 1`
- 自定义

只有当用户选择“自定义”时，才应该出现模板输入框，并且模板输入框应配合示例预览。

结论：

页码模板不能作为默认一等控件直接暴露。它应成为“页码显示格式”的高级分支。

### 3.4 “首页与奇偶页”位置和语义都不稳

首页不同、奇偶页不同不是常规主流程，而是特殊页面例外。

它应该出现在用户完成普通页面设置之后，而不是紧跟页眉页脚主配置直接出现。否则用户会被迫先理解 Word 的 first/even 机制。

更符合直觉的表达应是：

- 先设置普通页面；
- 再设置哪些页面例外；
- 最后才处理首页、奇偶页这样的特殊例外。

结论：

“首页与奇偶页”应归入“特殊页面”或“页面例外”组，而不是作为独立主模块插在页脚之后。

### 3.5 “分区排除”是技术词

“分区排除”来自执行模型和文档结构模型，但用户更关心的是：

- 哪些页面不显示页眉？
- 哪些页面不显示页脚？
- 哪些页面不显示页码？

尤其在论文模板中，用户最熟悉的是：

- 封面不显示；
- 声明页不显示；
- 目录页可能不显示；
- 摘要页可能使用罗马页码。

“分区排除”这个词让用户需要先理解“分区”。

结论：

卡片命名应改为“隐藏范围”或“不显示页面”。具体选择项可以仍然映射到 selectors，但 UI 不应优先使用“分区”。

### 3.6 应用方案位置过重

当前“应用方案”是一张独立卡片，且出现在所有配置之前。

方案本质是快速起点，而不是最终配置对象。用户选完方案后，真正要确认的是页面显示结果。

如果方案卡片占用过多空间，会让用户误以为“方案”是这个页面的主体，而不是“页眉页脚规则”。

结论：

应用方案应变成更轻量的“快速方案”入口，可以放在顶部结果区下方，或者作为常规配置区的首行，但不应成为视觉重量过大的主卡片。

### 3.7 摘要区不应重复制造概念

顶部摘要目前把“页眉”和“页脚内容”拆成两张卡，但下面又有“页眉”“页脚”“首页与奇偶页”等卡片。

摘要里的“页脚内容：仅页码”进一步强化了“页脚 = 页码”的误解。

结论：

摘要区应服务于结果确认，而不是复述内部配置对象。更适合的摘要是：

- 顶部：跟随 1 级标题，横线开启；
- 底部：页码居中；
- 隐藏：封面及声明页；
- 编号：正文从 1 起，阿拉伯数字。

## 4. 用户心智模型

用户配置页眉页脚时，最自然的路径是：

### 第一步：是否启用

用户先决定这份模板是否需要页眉、页脚、页码。

如果不需要，页面应停在关闭态。

### 第二步：普通页面显示什么

用户先配置最常见页面，也就是正文普通页面：

- 顶部显示什么；
- 底部显示什么；
- 页码放在哪里。

这是主结果。

### 第三步：页码如何编号

当用户开启页码后，才需要设置：

- 编号格式；
- 起始编号；
- 前置部分和正文是否分段编号；
- 页码显示格式。

### 第四步：哪些页面不显示

用户再处理封面、声明、目录、摘要等特殊范围。

### 第五步：首页和奇偶页例外

只有当用户确实需要时，才配置：

- 首页是否不同；
- 偶数页是否不同；
- 这些特殊页的页眉页脚是否沿用普通页面。

### 第六步：文字样式

最后处理字体、字号、加粗、斜体。

样式是结果的视觉层，不应打断结构配置。

## 5. 推荐信息架构

推荐将页面重构为以下顺序：

1. 顶部结果区；
2. 快速方案；
3. 普通页面；
4. 页码；
5. 不显示页面；
6. 特殊页面；
7. 文字样式。

### 5.1 顶部结果区

目的：让用户立刻知道当前最终效果。

建议结构：

```text
页眉与页脚  [开关]

顶部：跟随 1 级标题，横线开启
底部：页码居中
隐藏：封面及声明页
编号：正文阿拉伯数字从 1 起
```

关闭态：

```text
页眉与页脚  [关闭]

当前模板不会输出页眉、页脚和页码
```

关闭态下：

- 保留“快速方案”或“启用”入口；
- 其它配置整体禁用或不展示；
- 不应继续展示活跃字段。

### 5.2 快速方案

目的：提供起点，不主导页面。

建议控件：

- 快速方案：论文常用 / 全文页码 / 无页眉页脚 / 自定义；
- 方案旁显示轻量状态：已修改 / 内置 / 自定义。

不建议：

- 用独立大卡片占据过多空间；
- 把方案当作保存对象；
- 与标题编号的“编号方案库”混淆。

页眉页脚这里的方案更像 preset，不是 scheme library。

### 5.3 普通页面

目的：配置大多数页面的顶部和底部显示。

建议卡片名：普通页面。

字段：

| 字段 | 控件 | 说明 |
| --- | --- | --- |
| 顶部内容 | 下拉 | 不显示 / 跟随章节标题 / 固定文字 |
| 标题级别 | 下拉 | 仅当顶部内容为跟随章节标题时显示 |
| 顶部文字 | 输入框 | 仅当顶部内容为固定文字时显示 |
| 顶部横线 | 开关 | 仅当顶部内容不是不显示时启用 |
| 底部文字 | 下拉 | 不显示 / 固定文字 |
| 底部文字内容 | 输入框 | 仅当底部文字为固定文字时显示 |

关键变化：

- 不再使用“页眉内容”“页脚内容”作为主标签；
- 不再让“页脚内容”承载页码；
- 先让用户建立“普通页面”的基准结果。

### 5.4 页码

目的：单独配置页码，不把页码藏进页脚。

建议卡片名：页码。

字段：

| 字段 | 控件 | 说明 |
| --- | --- | --- |
| 显示页码 | 开关 | 关闭后隐藏下方页码字段 |
| 位置 | 下拉 | 页脚居中 / 页脚右侧 / 页眉右侧 / 页眉居中 |
| 编号格式 | 下拉 | 1,2,3 / I,II,III / i,ii,iii / A,B,C |
| 起始编号 | 数字输入 | 默认 1 |
| 编号范围 | 下拉或分段编辑 | 全文连续 / 前置罗马正文阿拉伯 / 自定义分段 |
| 显示格式 | 下拉 | 1 / 第 1 页 / 第 1 页 / 共 10 页 / 自定义 |
| 自定义模板 | 输入框 | 仅当显示格式为自定义时显示 |

页码分段规则较复杂，可以采用渐进式：

- 默认只显示“全文连续”；
- 选择“前置罗马正文阿拉伯”时展开前置/正文设置；
- 选择“自定义分段”时进入高级分段编辑器。

### 5.5 不显示页面

目的：配置哪些页面不输出顶部、底部和页码。

建议卡片名：不显示页面。

字段：

| 字段 | 控件 | 说明 |
| --- | --- | --- |
| 封面及声明页 | 开关 | 默认开启 |
| 目录页 | 开关 | 可选 |
| 摘要页 | 开关 | 可选 |
| 自定义范围 | 多选 | 展开后选择具体分区 |

不建议：

- 使用“分区排除”作为主标题；
- 默认暴露复杂 selector 编辑器；
- 把“不显示页面”和“页码分段编号”混在一起。

### 5.6 特殊页面

目的：处理普通页面之外的显示例外。

建议卡片名：特殊页面。

字段：

| 字段 | 控件 | 说明 |
| --- | --- | --- |
| 首页不同 | 开关 | 开启后显示首页配置 |
| 首页顶部 | 下拉 | 沿用普通页面 / 不显示 / 跟随章节标题 / 固定文字 |
| 首页底部文字 | 下拉 | 沿用普通页面 / 不显示 / 固定文字 |
| 首页页码 | 下拉 | 沿用普通页面 / 不显示 / 显示 |
| 奇偶页不同 | 开关 | 开启后显示偶数页配置 |
| 偶数页顶部 | 下拉 | 沿用普通页面 / 不显示 / 跟随章节标题 / 固定文字 |
| 偶数页底部文字 | 下拉 | 沿用普通页面 / 不显示 / 固定文字 |
| 偶数页页码 | 下拉 | 沿用普通页面 / 不显示 / 显示 |

这里要避免一个误区：

Word 的“首页不同”和“奇偶页不同”是结构开关；但用户关心的是特殊页面上哪些内容不同。

因此 UI 应该先问：

- 是否需要特殊页面？

再问：

- 特殊页面上顶部、底部文字、页码分别怎么处理？

### 5.7 文字样式

目的：控制页眉页脚共同文字样式。

建议保持当前样式卡，但放在最后。

字段：

- 中文字体；
- 英文字体；
- 字号；
- 加粗；
- 斜体。

后续如需更完整 Word 能力，再考虑：

- 页眉样式与页脚样式是否拆开；
- 页码字体是否单独覆盖；
- 页眉横线样式是否高级化。

## 7. 模型映射建议

UI 不应完全等于现有 `HeaderFooterConfig`，但需要清晰映射。

### 7.1 普通页面

| UI | 当前模型 |
| --- | --- |
| 顶部内容 | `header.mode` |
| 顶部固定文字 | `header.fixed_text` |
| 标题级别 | `header.styleref_level` |
| 顶部横线 | `header.border` / `header.border_style.enabled` |
| 底部文字模式 | 需要新增或由 `footer.content_mode` 映射 |
| 底部固定文字 | `footer.fixed_text` |

注意：当前 `footer.content_mode` 混合了承载页码和底部文字，建议逐步拆为 UI view model。

### 7.2 页码

| UI | 当前模型 |
| --- | --- |
| 显示页码 | `footer.content_mode` 或独立 view model |
| 页码位置 | `footer.alignment`，未来需支持 header/footer 位置 |
| 编号格式 | `page_number_plan.phases[].number_format` |
| 起始编号 | `page_number_plan.phases[].start_value` |
| 编号范围 | `page_number_plan.phases[].selectors` |
| 显示格式 | `footer.page_number_template` |

建议新增中间层：

```python
HeaderFooterUiState
```

该对象负责把用户语言转换成当前 `HeaderFooterConfig`，避免 UI 直接被底层字段绑架。

### 7.3 不显示页面

| UI | 当前模型 |
| --- | --- |
| 封面及声明页 | `suppress_header_footer_selectors=["pre_numbering"]` 或拆分 selector |
| 目录页 | `toc` selector |
| 摘要页 | `abstracts` selector |
| 自定义范围 | `suppress_header_footer_selectors` |

### 7.4 特殊页面

| UI | 当前模型 |
| --- | --- |
| 首页不同 | `behavior.different_first_page` |
| 首页顶部 | `variants.first.header` |
| 首页底部文字 | `variants.first.footer` 的文字部分 |
| 首页页码 | `variants.first.footer` 的页码部分 |
| 奇偶页不同 | `behavior.different_odd_even_pages` |
| 偶数页顶部 | `variants.even.header` |
| 偶数页底部文字 | `variants.even.footer` 的文字部分 |
| 偶数页页码 | `variants.even.footer` 的页码部分 |

当前模型里 `HeaderFooterContentConfig.mode` 仍把页脚文字与页码合并。UI 若要清晰表达“底部文字”和“页码”两个对象，后续需要更细的 view model 或模型扩展。

## 8. 需要谨慎处理的决策

### 8.1 页脚文字与页码是否拆模型

短期可以只拆 UI，不拆底层模型。

但长期看，底层也应拆分：

```text
footer_text:
  enabled
  text
  alignment

page_number:
  enabled
  position
  format
  template
  plan
```

这样能避免 `footer.content_mode = page_number_with_text` 这类组合状态继续扩散。

### 8.2 页码位置是否支持页眉

如果 UI 提供“页眉右侧”等位置，就需要执行层支持把 PAGE 字段写入 header。

如果短期执行层不支持，应先只提供当前可稳定输出的位置：

- 页脚居中；
- 页脚右侧；
- 页脚左侧。

不要在 UI 里承诺暂时做不到的 Word 输出。

### 8.3 首页/偶数页页码是否独立开关

用户会期待：

- 普通页显示页码；
- 首页不显示页码；
- 偶数页显示不同位置或不同文字。

当前模型通过 `variants.first.footer.mode` 可以表达一部分，但不够直观。

后续应在 UI view model 中显式表示：

```text
special_page.page_number_mode = inherit | hidden | visible
```

再映射到底层 footer content。

### 8.4 “应用方案”是否保留

建议保留，但从“方案管理”降级为“快速方案”。

它不是编号方案库那种可保存对象，至少短期不应引入“另存为方案、更新方案、删除方案”等交互。

## 9. 推荐实施路径

### 阶段 1：只重构 UI 信息架构

目标：先让页面符合用户直觉，不扩大执行层能力。

动作：

1. 将页面顺序调整为：
   - 顶部结果区；
   - 快速方案；
   - 普通页面；
   - 页码；
   - 不显示页面；
   - 特殊页面；
   - 文字样式。
2. 将“页眉/页脚”文案改为“顶部/底部文字/页码”。
3. 隐藏 `{page}` 模板输入，改为“显示格式”下拉。
4. 将“分区排除”改为“不显示页面”。
5. 总开关关闭时进入关闭态，不展示活跃表单。
6. 保持底层 `HeaderFooterConfig` 不变，通过面板内 helper 做映射。

验收：

- 用户不需要理解 Word header/footer/first/even 也能完成常见设置；
- 页面上不再出现 `{page}` 这种默认工程表达；
- “页脚内容 = 仅页码”不再出现；
- 关闭态不再显示可编辑配置；
- 原有输出测试保持通过。

### 阶段 2：抽出 HeaderFooterUiState

目标：阻断 UI 继续被底层技术模型牵着走。

动作：

1. 新增纯 UI view model；
2. 提供 `from_config(config)`；
3. 提供 `apply_to_config(config)`；
4. 将面板读写改为先读写 UI state，再落到底层配置。

验收：

- UI 测试可以直接断言用户语义；
- 底层字段变化不再直接影响控件排列；
- 页脚文字与页码的组合逻辑集中在一个映射层。

### 阶段 3：模型语义拆分

目标：从根上拆开页脚文字和页码。

动作：

1. 新增 `PageNumberDisplayConfig`；
2. 新增 `FooterTextConfig` 或扩展 footer；
3. 保留迁移函数，将旧 `footer.content_mode` 映射到新结构；
4. 更新执行层渲染页脚文字和页码。

验收：

- “页脚文字”和“页码”可以独立开启、独立隐藏；
- 首页/偶数页可以独立决定页码是否沿用；
- 不再需要 `page_number_with_text` 这种组合枚举。

### 阶段 4：预览与结果校验

目标：用户修改任何配置都能看懂结果。

动作：

1. 在顶部结果区显示普通页预览；
2. 特殊页面开启后显示首页/偶数页摘要；
3. 页码格式下拉显示实际示例；
4. 对无法输出的组合给出禁用状态，不用说明文本堆砌。

验收：

- 用户能从摘要判断最终页面效果；
- 不需要阅读说明文本；
- 控件禁用和隐藏逻辑清晰。

## 10. 文案规范

推荐用词：

| 不推荐 | 推荐 |
| --- | --- |
| 页眉内容 | 顶部内容 |
| 页脚内容 | 底部文字 |
| 仅页码 | 页码：显示 |
| 分区排除 | 不显示页面 |
| 页码模板 | 页码显示格式 |
| 应用方案 | 快速方案 |
| 奇偶页不同 | 奇偶页不同 |
| 首页不同 | 首页不同 |
| 沿用默认页眉 | 沿用普通页面 |
| 沿用默认页脚 | 沿用普通页面 |

保留“首页不同”“奇偶页不同”，因为这是 Word/WPS 用户相对熟悉的术语。

## 11. 不应继续做的方向

1. 不应继续在当前卡片结构里小范围挪字段。
2. 不应把 Word 技术对象继续直接暴露成 UI 分组。
3. 不应把页码藏在“页脚内容”里。
4. 不应默认暴露 `{page}` 模板。
5. 不应让总开关关闭时仍显示活跃编辑表单。
6. 不应引入“页眉页脚方案库”的增删改保存链路。
7. 不应靠长说明文本解释复杂控件。

## 12. 最终目标

这个页面完成后，用户应能用一句话理解：

> 我在设置文档每一页顶部、底部和页码怎么显示。

而不是：

> 我在编辑 Word 的页眉页脚对象、分节排除和字段模板。

只有达到这个目标，页眉页脚页面才算真正符合用户直觉。
