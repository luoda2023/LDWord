## 2. 一句话结论

完善的场景能力矩阵应定义为：

```text
高频文档任务族
× 输入/资料契约
× Word 对象风险面
× 能力域组合
× 多版本交付形态
× 可验收证据链
```

如果一个需求只能回答“要加哪个开关”，但不能回答“属于哪个任务族、触碰哪些 Word 对象、由哪个 profile/preset 承载、报告如何解释、测试如何锁定”，它就还不是完整场景能力。

## 3. 完整性判定门槛

每个 L3 以上场景能力必须同时过 12 个门槛：

| 门槛 | 必须回答的问题 | 当前落点 |
| --- | --- | --- |
| 用户任务 | 用户自然会怎么说这个需求 | scene family / preset |
| 输入来源 | docx、json、xlsx、markdown、LaTeX、附件包中哪些被接受 | `InputSourceProfile` |
| 资料契约 | 必填字段、图片、签章、附件、批量实体是什么 | `MaterialSchema` |
| 模板基线 | 外观、样式、页眉页脚、页码、表格默认形态由谁管 | `TemplateConfig` |
| 场景策略 | 哪些参数因业务任务变化，而不是纯外观变化 | `SceneWorkspace` |
| 处理范围 | 正文、目录、摘要、参考文献、附录、附件如何纳入或排除 | `FormatScopeConfig` |
| 对象风险 | OLE、Visio、宏、修订、批注、文本框、域、内容控件如何处理 | `ObjectPreflightPolicy` |
| 计数合规 | 字数、词数、图表数、公式数、附件数如何解释 | CountEngine profile |
| 多版本交付 | final、review、teacher、student、signing、submission 等如何同源生成 | `DeliveryPreset` |
| 执行降级 | 命中高风险对象后阻断、跳过、警告还是人工确认 | pipeline + report |
| 用户可见 | ScenePanel / Workbench 能否展示关键策略和风险 | UI summary/detail |
| 测试证据 | 是否有 registry、UI、执行、报告测试 | pytest |

缺一项，成熟度不能超过 L2；缺报告或测试，不能超过 L3；缺真实执行消费，不能超过 L2。

## 4. 场景与模板的边界

### 4.1 模板管理负责什么

模板管理负责稳定版式事实：

- 页面尺寸、边距、页眉页脚版式、页码样式；
- 标题、正文、表格、题注、参考文献等样式；
- 默认行距、缩进、段前段后、表格边框、表格默认行高；
- 水印的视觉样式、字体、颜色、角度、透明度；
- 公式表格或公式文本的默认外观；
- 输出格式开关的基础默认值。

这些是“文档长什么样”的基线，不应因为某个业务任务临时变成场景入口。

### 4.2 场景配置负责什么

场景配置负责业务任务策略：

- 选择哪个资料 schema；
- 使用哪个合规 profile 和 count profile；
- 本次处理哪些范围；
- 本次保护哪些 Word 对象；
- 命中风险后阻断、跳过还是仅报告；
- 生成哪些交付版本；
- 某个交付版本是否显示答案、解析、内部段落、修订痕迹、保密水印；
- 某些模板参数是否因业务状态被覆盖。

因此，公式、输出、水印不应继续被“先不管”处理，而要拆成两层：

| 参数族 | 模板侧 | 场景侧 |
| --- | --- | --- |
| 公式 | 字体、字号、编号样式、表格布局 | 是否处理 LaTeX 片段、低置信度如何降级、哪些场景必须保留公式对象 |
| 输出 | 默认是否生成 DOCX/JSON/Markdown/PDF | final/review/student/teacher/signing/submission 等多版本 preset |
| 水印 | 样式、颜色、角度、位置 | 草稿、内部、保密、签署版、审阅版是否启用 |
| 表格行高 | 默认表格版式 | 固定表单、套打、报价单是否要求锁定行高 |
| 页眉页脚 | 版式和字段样式 | 公文状态、投稿包、签署版是否切换内容或编号策略 |

### 4.3 控件样式一致性

场景配置中的控件必须继续继承模板管理的控制体系：

- 单选用 radio 或 segmented control；
- 多选用 checkbox + flow layout；
- 数值用统一 spin/spacing input；
- 单位与模板管理一致，避免“字、磅、厘米”在不同页面呈现不同；
- 业务动作按钮只用于明确命令，例如“应用推荐目标”；
- 场景详情不能发明第二套输入框、下拉框、开关和表单行样式。

这不是视觉洁癖，而是防止用户把“同一类参数”误解成不同语义。

## 6. 能力域完整清单

后续所有场景都应映射到以下 16 个能力域，避免把横切能力误做成顶层场景：

| 能力域 | 说明 | 典型承载 |
| --- | --- | --- |
| input_contract | 输入格式、来源、结构化程度 | `InputSourceProfile` |
| material_schema | 字段、图片、签章、附件角色 | `MaterialSchema` |
| template_baseline | 样式、页面、页眉页脚、表格、题注 | `TemplateConfig` |
| processing_scope | 正文、摘要、参考文献、附录等范围 | `FormatScopeConfig` |
| structure_formatting | 标题、编号、目录、分节 | modules |
| table_figure_caption | 表格、图片、题注、图表目录 | table/caption modules |
| formula_symbol | 公式、LaTeX 片段、OMML、专业符号 | formula configs |
| citation_reference | 引用、参考文献、Bib/CSL | reference modules |
| count_compliance | 多口径计数、规则匹配、合规报告 | CountEngine |
| object_safety | OLE、宏、修订、批注、域、内容控件 | ObjectPreflight |
| field_fill | 占位符、实体字段、图片替换 | fill modules |
| visibility_variant | 答案/解析/内部段落/签署内容显隐 | `ContentVisibilityRule` |
| review_compare | 修订稿、对比稿、审阅包 | compare/report |

| plugin_boundary | AI、OCR、复杂 LaTeX、法律/财务/IP 等扩展边界 | plugin registry |

任何新增场景必须声明它使用哪些能力域。任何新增能力域必须证明至少服务两个高频任务族，否则先放插件或局部功能。

## 7. 场景族成熟度规则

| 等级 | 含义 | 允许暴露 |
| --- | --- | --- |
| L0 | 文档设想或讨论中 | 不暴露 |
| L1 | registry 有 family、workflow、first slice、OOXML touchpoints、boundaries | 只在规划摘要中展示 |
| L2 | ScenePanel 可见关键摘要，可编辑部分 profile 字段 | 可在高级配置中出现 |
| L3 | resolver、pipeline、report 至少闭合一个 first slice | 可作为 profile/preset 暴露 |
| L4 | Workbench 能执行，报告有证据，测试覆盖主要路径 | 可进入用户主工作流 |
| L5 | 有可视化预览、失败恢复、批量汇总和用户确认闭环 | 可作为正式高阶场景承诺 |

当前 12 个 planning family 大多处于 L1 到 L2。`contract_delivery` 因为 ObjectPreflight 推荐目标、scan target 编辑、报告证据、Workbench 对象预检摘要以及合同字段一致性报告与 Workbench 可见性第一段已接通，已经成为 L3 first slice 的优先推进对象；签署/审阅交付仍需继续闭合。

## 9. 吸收两份技术记录后的原则

### 9.1 CountEngine 记录

必须吸收：

- 不做单一“字数统计器”，而做 profile-driven multi-metric CountEngine；
- 同时保留 Word-like words、中文字符、英文 words、characters no spaces、参考文献、图、表、公式、章节等多口径；
- 报告必须解释计数范围，例如 title、abstract、main text、references、figure legends、appendix 是否计入；
- thesis、journal、project application、exam teaching 可以共用引擎，但不能共用同一规则口径。

矩阵影响：

- `count_compliance` 是横切能力，不是顶层场景；
- 中文论文、英文投稿、项目申报、试卷教学都必须声明自己的 count profile；
- CountEngine 输出必须进入报告，不能只显示一个数字。

### 9.2 试卷生成技术记录

必须吸收：

- AI 或外部输入只作为结构化源，不直接生成最终 Word；
- JSON 是机器事实源，Markdown 是人工预览，Word 是正式交付；
- 答案、解析、难度、知识点永远留在结构化数据中，是否显示由 DeliveryPreset 显隐规则决定；
- 学生版、教师版、答案版必须同源渲染，不能分别生成；
- 复杂几何图、电路图、化学结构自动生成先放插件或专用扩展，不进入核心闭环。

矩阵影响：

- `exam_teaching` 的第一切片应优先做同源多版本渲染；
- 公式和图片能力要作为可选对象能力进入，而不是一开始承诺复杂图形生成；
- Markdown 不能成为最终排版事实源。

## 10. 当前主要缺口

| 缺口 | 风险 | 建议动作 |
| --- | --- | --- |
| 多数 P1 family 仍只有 registry，不具备可执行 first slice | 高频场景看似覆盖，实际不可用 | 每个 family 只推进一个 first slice |
| material schema 与 UI/执行的关系仍浅 | 用户不知道需要哪些字段和资产 | ScenePanel 展开 schema requirements |
| CountEngine profile 仍未形成多场景 UI 治理 | 论文/投稿/申报边界会混 | 建立 count profile selector 和报告解释 |
| DeliveryPreset 的 artifact browser 仍不够完整 | 多版本输出难验收 | Workbench 展示 preset 下的文件、报告、manifest、显隐差异 |
| ObjectPreflight 缺运行前确认 | 高风险对象策略不够透明 | Workbench 预检确认 UI |
| `skip_modules_by_finding` 不可视化 | 用户不知道为什么某模块没跑 | 报告已补 finding -> skipped module 证据；后续补 UI 展示与编辑 |
| 公式转换链未闭合 | 学术/技术/试卷场景不完整 | 只做 LaTeX fragment MVP，低置信度报告化 |
| 水印还未按状态进入 delivery preset | 审阅/内部/签署版语义弱 | 将 watermark state 作为 preset override |
| 表格行高仍未形成正式策略 | 固定表单和套打会有残留参数 | 模板默认 + 场景锁定策略二选一闭合 |
| 插件边界缺产品化表达 | 用户误以为核心承诺法律/财务/AI/复杂 OCR | 建立 plugin boundary 文案与占位入口 |

5. 测试覆盖中文论文、英文投稿、项目申报。

### N3.3 Exam 同源多版本

目标：验证 `exam_teaching` 的核心原则。

最小闭环：

1. 结构化题源 schema；
2. student/teacher/answer presets；
3. answer/analysis/knowledge_points 显隐；
4. Markdown preview 仅作为预览；
5. Word 输出同源一致性测试。

### N3.4 Workbench 交付验收

目标：让多版本输出不是“后台生成了文件”，而是用户能验收。

最小闭环：

1. preset 分组 artifact browser；
2. final/report/manifest/compare/intermediate 文件状态；
3. 输出目标预检；
4. 对象预检确认；
5. 失败隔离与批量汇总。

## 12. 最终验收句

后续不再按“功能点”补场景，而按下面这句判断：

```text
一个高频任务族，至少要有一个 first slice 能从输入契约开始，
经过模板基线、场景策略、对象保护、执行降级、多版本交付，
最终在报告和测试里留下可解释证据。
```

只有满足这句话，才算进入高层场景能力矩阵的可承诺范围。
