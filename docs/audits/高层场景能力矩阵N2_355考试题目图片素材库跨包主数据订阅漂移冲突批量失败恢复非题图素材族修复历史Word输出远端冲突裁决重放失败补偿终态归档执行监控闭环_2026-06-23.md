日期：2026-06-23

## 1. 定位

N2.354 已把 terminal archive 后的 durable scheduler 建成前台可记录的调度事实源：dead-letter、authorization refresh 与 remote snapshot review 都能进入带 retry/backoff、lock 状态和 execution monitor route 的调度记录。剩余断点在于：调度项进入队列后，表格仍缺少“已经被监控系统接手”的事实记录，Manifest 也只能停在 scheduler 级别，无法说明后续该去人工归档、授权刷新连接器还是远端快照治理结果收口。

N2.355 闭合的是 terminal archive execution monitor 首片。它不声明真实后台 worker、外部授权刷新、远端快照重拉、失败重试执行或最终结果归档已经完成；本轮只承诺已 scheduled 的 terminal archive items 可以从前台显式记录监控快照、heartbeat、resume/result route、retryable 分类、manifest 和 metadata。

## 2. 本轮闭环

- durable scheduler 记录后，表格从 `scheduled` 状态显示 `Monitor` 与 `Manifest`。
- `Monitor` 消费 latest durable scheduler record，而不是新建第二套调度事实源。
- dead-letter 项进入 `dead_letter_manual_followup_monitor_recorded`，执行监控状态为 `manual_followup_required`，结果路由为 `manual_dead_letter_followup_result_archive`。
- authorization refresh 项进入 `authorization_refresh_connector_monitor_recorded`，执行监控状态为 `connector_resume_pending`，结果路由为 `authorization_refresh_result_collector`。
- remote snapshot review 项进入 `remote_snapshot_governance_monitor_recorded`，执行监控状态为 `governance_resume_pending`，结果路由为 `remote_snapshot_result_collector`。
- 监控记录统一写入 `worker_scope = cross_archive_terminal_archive_execution_monitor`、`heartbeat_status = monitor_heartbeat_recorded`、`resume_status = resume_result_pending`、`result_archive_status = terminal_archive_result_pending`。
- execution monitor manifest 独立写入 `artifacts/subscription_drift_non_question_asset_family_word_output_remote_conflict_decision_retry_replay_failure_compensation_terminal_archive_execution_monitors`。
- profile metadata 回写 execution monitor status、id、worker scope、heartbeat、resume、result archive status、item count 和 manifest path。
- monitor 记录后，表格状态推进为 `monitored`，动作收敛为 `Manifest`，并阻止重复 Monitor、重复 Schedule、重复 Archive、重复 Connector、重复 Audit、重复 Execute 和重复 Queue。

## 3. 链路视角

N2.355 后链路变为：

```text
... -> Terminal Archive
          |
          v
Terminal Archive Durable Scheduler
          |
          v
Terminal Archive Execution Monitor
          |
          +--> dead-letter manual follow-up result archive (next)
          +--> authorization refresh result collector (next)
          +--> remote snapshot result collector (next)
```

这个链路把“已调度”推进为“已被监控接手”。它仍然保留边界：本轮不把待人工处理、待授权刷新或待远端快照治理的结果伪装成已完成；下一轮应处理 result finalization，把 monitor items 的结果收口为最终归档事实。

## 5. 控件样式与场景一致性

本轮继续沿用模板管理/素材管理已经形成的控件契约：

- 行动作使用紧凑表格按钮：`Monitor` 与 `Manifest`。
- 状态继续复用原状态列：`scheduled` 推进为 `monitored`。
- manifest drilldown 复用既有 `locate_manifest` 行动作，并优先打开 execution monitor manifest。
- retry/backoff/heartbeat/result route 暂时保持为 manifest/metadata 中的只读事实，不新增临时表单控件。
- 后续 result finalization 若需要暴露人工确认、远端结果选择或 retry guard，也应沿用表格动作、状态列、只读 manifest drilldown 和必要 confirmation guard。
