## 0. 纠偏说明

前一轮分析虽然正确识别出“格式例外”当前保存的是样式角色覆盖，不是文档中的具体章节，但随后过早把问题收敛为：

```text
删除格式例外
-> 新建 DocumentStructureProfile
-> 运行时自动识别
```

这条结论漏掉了决定产品是否可用的核心问题：

```text
系统如何知道当前文档的摘要、正文、参考文献、附录究竟在哪里？
识别错误时，用户在哪里、以什么方式纠正？
纠正只对本篇文档有效，还是会改变以后所有文档？
```

因此，本审计对前两份文档作出如下修正：

1. “格式例外不是章节定义”仍然成立。
2. “当前代码主要依靠运行时自动识别”仍然成立。
3. “只要新增结构 Profile 即可”不成立，至少不完整。
4. 正确答案不是“自动识别”和“用户自定义”二选一。
5. 正确产品必须是“系统自动提出结构判断，用户有权校正当前文档，必要时再把通用规律沉淀为规则”。
6. Profile 只可能是复用规则的承载方式，不能替代当前文档确认工作流，更不应先于工作流被产品化。

## 1. 直接裁决

### 1.1 当前产品事实上是什么

当前实现是：

```text
系统硬编码语义区域类型
        +
系统硬编码标题、位置、顺序和内容启发式
        +
运行时自动生成 DocSection
        +
用户无法在正式 UI 中校正识别结果
```

所以它既不是完整的“自动识别”，也不是“用户自定义”。

更准确地说，它是：

```text
不可配置、不可确认、不可纠错的自动猜测。
```

### 1.2 正确答案

V1 的正确产品模型应为：

```text
语义角色：系统按工作模式预定义
当前区域：系统自动识别
本次错误：用户可校正
长期规律：用户可选择保存为复用规则
最终样式：模板提供
处理行为：方案提供
```

一句话：

> 自动识别是默认入口，用户校正是必要安全阀，可复用自定义规则是进阶能力；三者不是互斥模式。

### 1.3 “用户自定义”究竟允许自定义什么

必须把“用户自定义”拆成三种：

| 自定义对象 | 是否应支持 | 生命周期 | 示例 |
| --- | --- | --- | --- |
| 自定义新的任意语义类型 | V1 不建议 | 产品级 | 新建“导师意见区”并期待所有模块理解它 |
| 校正当前文档的区域角色与起止边界 | 必须 | 当前任务/当前文档 | 把第 186—224 段改判为参考文献 |
| 保存可复用识别规则 | 应支持，但可后置 | 规则集/方案引用 | “参考资料”也视为参考文献标题 |

V1 不建议允许用户任意创造语义类型，原因不是限制自由，而是当前模块只理解封闭的角色词汇。

例如 `reference_format`、`citation_link`、目录、编号、页码和内容显隐都需要明确知道一个区域是不是 `references`、`toc`、`appendix`。如果用户创造一个 `source_list_2`，系统并不知道它应触发什么行为。

用户真正需要的通常不是“发明新类型”，而是：

```text
把当前文档中的某一段正确归入一个系统支持的角色。
```

## 2. 为什么“自动识别还是用户自定义”不能设计成二选一

### 2.1 只做自动识别不可靠

真实文档会出现：

- “参考资料”“引用文献”“主要参考书目”而不是“参考文献”；
- “结语”既可能是正文章节，也可能被误判为后置区域；
- 摘要没有独立标题，而是“摘要：……”同行出现；
- 中英文摘要顺序不同；
- 附录分为“附件”“附表”“补充材料”；
- 致谢放在参考文献之前；
- OCR、复制粘贴或错误 Word 样式导致标题证据缺失；
- 一篇标书里出现大量“参考文献”字样，但它们不是文档后置参考文献区；
- 文档有两个同名标题，只有其中一个是区域锚点。

系统只能给出候选判断，不能把启发式当成不可争议事实。

### 2.2 只让用户手工定义也不正确

如果每篇文档都要求用户逐项框选：

- 摘要从哪里开始；
- 正文从哪里开始；
- 参考文献从哪里开始；
- 附录到哪里结束；

那么“一键排版”会退化为“排版前先做一遍人工标注”。

对于结构规范的论文、报告和长文档，大多数区域完全可以被可靠识别。系统应承担重复劳动，用户只处理歧义。

### 2.3 正确的人机分工

```text
机器负责发现候选和提供证据
用户负责裁决歧义和纠正边界
系统负责记住用户明确要求复用的规律
```

这不是折中，而是由工作对象决定的正确分工：

- 当前文档结构是运行时事实，必须读取文档后才能知道；
- 用户是最终责任人，需要能纠错；
- 相同单位、学校或客户的命名习惯可重复，值得沉淀；
- 单篇文档的段落编号、页码和边界不应污染通用方案。

## 3. 当前代码和产品文档的真实证据

### 3.1 原始产品要求本来就不是单一路径

逆向 PRD 的 FR-042 明确要求方案适用范围包括：

```text
自动识别
页码范围
正文起点
正文 / 摘要 / 目录 / 参考文献 / 附录等章节
```

这表明原始意图至少包含：

- 自动定位；
- 用户给出范围约束；
- 用户选择处理哪些语义区域。

当前 UI 只剩“处理全文”，不是需求已经被正确简化，而是能力被压扁。

### 3.2 配置模型曾经预留自动与人工定位字段

`FormatScopeConfig` 仍有：

```python
mode
page_ranges_text
body_start_index
body_start_page
body_start_keyword
sections
```

但当前 `resolve_config()` 不再从方案读取这些值，而是只根据 `application_boundary` 重新生成 `FormatScopeConfig`。

当前 UI 又强制把所有模式归一化成：

```text
full_document
```

而运行时明确只有：

```text
full_document
```

可执行。

所以现状不是“已经确定自动识别最正确”，而是：

```text
原本多维的范围问题被收缩成了一个假单选项。
```

### 3.3 当前识别器没有读取用户规则

`heading_recognition.py` 直接使用：

```text
SPECIAL_SECTION_TITLES
SECTION_ANCHORS
SECTION_ORDER
SECTION_MIN_ACCEPT_SCORE
```

识别链读取文档段落、Word 样式、标题文本、位置和内容模式，最后生成：

```python
DocSection(
    section_type=...,
    start_index=...,
    end_index=...,
    confidence=...,
    title_confident=...,
)
```

该链路没有读取：

- 用户确认结果；
- 方案中的区域别名；
- 学校或单位识别规则；
- 当前文档的人工边界修正；
- 模板中的区域锚点。

所以当前系统的区域识别是内置自动识别，不是用户自定义。

### 3.4 “章节识别确认”目前只是契约名称

仓库已有：

```text
section_classifier_decisions
section_classifier_confirmation
manual_boundary:chinese_thesis_count
```

但它们主要存在于：

- MaterialSchema；
- 场景摘要投影；
- fixture 报告期望；
- 用户旅程和成熟度审计。

既有审计甚至明确写明：

```text
section_classifier_confirmation 是确认链路，不是自动语义理解引擎。
```

然而当前主流程没有一个真正可操作的“文档结构确认器”，也没有把用户修正写回 `DocTree` 的正式模型。

因此，当前所谓“确认闭环”更多是审计和材料契约闭环，不是实际交互闭环。

## 4. 先定义对象，再决定 UI

### 4.1 系统语义角色目录

建议使用封闭的、按工作模式裁剪的角色目录：

```yaml
RegionRoleCatalog:
  mode_id: thesis
  supported_roles:
    - cover
    - statement
    - authorization
    - abstract_cn
    - abstract_en
    - toc
    - body
    - references
    - appendix
    - acknowledgment
    - resume
```

它回答：

```text
系统能理解和处理哪些文档组成部分？
```

它不回答当前文档是否真的存在这些部分。

### 4.2 自动识别结果

```yaml
DetectedRegion:
  region_id: references@186
  role_id: references
  start_paragraph: 186
  end_paragraph: 224
  source_start_page: 47
  confidence: 0.91
  evidence:
    - title_exact_match: "参考文献"
    - position: back_matter
    - reference_entry_cluster: 31
  status: auto_detected
```

它回答：

```text
系统认为当前文档的参考文献在哪里，为什么？
```

### 4.3 用户对当前文档的校正

```yaml
RegionCorrection:
  region_id: references@186
  role_id: references
  start_paragraph: 188
  end_paragraph: 224
  action: boundary_adjusted
  applies_to: current_document
  confirmed_by: user
```

它回答：

```text
用户确认后，当前任务真正采用什么边界？
```

校正结果必须覆盖自动判断，但默认只对当前文档有效。

### 4.4 可复用识别规则

```yaml
RecognitionRuleSet:
  rule_set_id: school_x_thesis
  role_aliases:
    references:
      - 参考资料
      - 主要参考书目
    appendix:
      - 补充材料
  order_constraints:
    - abstract_cn before abstract_en
    - references before acknowledgment
  confidence_policy:
    uncertain: require_confirmation
```

它回答：

```text
以后遇到同类文档，系统应采用哪些长期规律？
```

用户校正当前文档后，系统不能偷偷学习。只有用户明确点击“保存为识别规则”时，才进入规则集。

### 4.5 方案的处理策略

```yaml
PlanRegionPolicy:
  role_id: references
  treatment: apply_template
  on_missing: ignore
  on_uncertain: require_confirmation
```

它回答：

```text
识别出这类区域后，方案要怎么处理？
```

它不保存当前文档的起止段落，也不保存字体字号。

### 4.6 模板样式

```yaml
TemplateRoleStyle:
  role_id: references
  paragraph_style_key: references_body
```

它回答：

```text
确认是参考文献后，最终使用什么视觉格式？
```

## 5. 正确的实际工作流

### 5.1 配置方案时

方案页没有当前输入文档，不能展示“已识别出的摘要/参考文献”，也不能让用户保存当前文档页码。

这里应配置：

```text
结构来源
  识别输入文档
  使用母版/结构化输入

识别规则
  内置规则
  指定规则集

不确定项策略
  自动处理高置信度项
  不确定时要求确认
  无法识别时保留原格式

区域处理策略
  摘要：套用模板
  目录：更新
  参考文献：套用模板并规范条目
  附录：保留 / 套用模板 / 不处理
```

这里不应出现：

- 当前文档的页码范围；
- 当前文档的段落起止位置；
- “系统已经识别出五个分区”的假象；
- 区域字体字号编辑器。

### 5.2 选择文档后、正式执行前

系统先进行只读结构扫描：

```text
读取文档
-> 生成标题树
-> 生成语义区域候选
-> 计算证据和置信度
-> 套用已有人工校正
-> 展示结构检查
```

用户看到的是当前文档事实：

| 区域 | 识别结果 | 范围 | 状态 | 操作 |
| --- | --- | --- | --- | --- |
| 中文摘要 | 已识别 | 第 4—5 页 | 高置信 | 查看 |
| 英文摘要 | 已识别 | 第 6—7 页 | 高置信 | 查看 |
| 正文 | 已识别 | “第一章 绪论”起 | 高置信 | 调整起点 |
| 参考文献 | 疑似 | 第 48—51 页 | 待确认 | 确认为参考文献 / 改边界 |
| 附录 | 未识别 | — | 可选 | 指定区域 |

这才是“章节识别确认”的正确位置。

### 5.3 用户校正时

用户操作应是业务语言：

- “此处是正文起点”；
- “将这一段标记为参考文献”；
- “参考文献从这里开始”；
- “附录到这里结束”；
- “这不是目录”；
- “本篇没有个人简历”。

不应让用户编辑：

- `section_type` 字符串；
- 段落下标；
- 内部 style key；
- 探测器分数；
- YAML 或 JSON。

### 5.4 执行时

只有经过解析的“有效结构”才能进入写入模块：

```text
自动识别结果
-> 应用当前文档人工校正
-> 通过置信度门
-> 生成 EffectiveDocumentStructure
-> 方案决定处理或跳过
-> 模板提供最终格式
-> 模块执行
```

写入模块不应再次各自猜测边界。

当前 `reference_format` 在缺少 `DocTree` 范围时还有自身回退识别，这会产生“双识别事实源”。目标模型中，专用模块只能消费统一结构结果；识别失败应回到结构确认环节，而不是在写入过程中悄悄重猜。

### 5.5 执行后

报告至少要说明：

- 自动识别了哪些区域；
- 哪些区域由用户校正；
- 哪些低置信度区域被跳过或保留；
- 实际处理了哪些范围；
- 使用了哪个识别规则集；
- 使用了哪个模板样式；
- 哪些区域未出现。

## 6. “自动、规则、手动”不是三个平级按钮

### 6.1 自动识别是基础引擎

只要输入是已有 Word 文档，系统就应先扫描，而不是要求用户先标注。

### 6.2 页码、关键词和正文起点是约束或修正

这些字段更合理的语义是：

```text
自动识别的搜索范围和人工提示
```

而不是完全替代自动识别的孤立模式。

例如：

```text
只在源文档第 3 页以后寻找正文起点
只在“第一章”之后处理正文
只在第 40—60 页内寻找参考文献和附录
```

系统仍然可以在该约束内识别结构。

### 6.3 手动指定是兜底，不是默认工作量

当文档没有可靠标题、来自 OCR、结构严重损坏或业务本身没有固定语义时，用户可直接指定范围。

因此建议 UI 文案是：

```text
识别不到？
  指定正文起点
  指定处理范围
  标记当前区域
```

而不是在配置页让用户提前选择“自动模式 / 手动模式”。

### 6.4 页码不能作为最终持久化边界

格式化会改变分页。

用户输入“第 20—30 页”时，系统应：

1. 在源文档只读阶段解析这些页对应的段落范围；
2. 转换成稳定的段落锚点、标题锚点或书签；
3. 再执行格式化；
4. 报告中同时保留“源页码”和“实际段落范围”。

不能在每个写入模块里动态按格式化后的页码重新计算，否则前面模块改变分页后，后面模块的作用对象会漂移。

## 7. 不同工作模式不能共用同一套五项列表

### 7.1 论文排版

结构通常较规范，适合：

```text
内置论文规则自动识别
-> 学校规则集提供别名和顺序约束
-> 用户确认低置信度区域
```

“摘要、目录、参考文献、附录、致谢、简历”是合理角色。

### 7.2 技术长文档、报告、标书

这类文档的章节名称高度开放。

正确重点是：

- 标题树；
- 正文起点；
- 附件/附录边界；
- 合并来源边界；
- 保留区域；
- 当前文档手工校正。

固定展示“致谢、个人简历”会暴露论文模型泄漏。

### 7.3 公文、表单、试卷和母版装配

如果文档是由结构化输入和母版生成，区域角色来自装配节点，不应再靠标题猜测。

链路应为：

```text
母版节点 / 内容槽位
-> 已知结构角色
-> 直接执行
```

只有导入一份已有、未知结构的 Word 文档时，才需要识别器。

所以方案首先应声明“结构来源”，而不是所有场景统一展示五个自动识别区域。

## 8. 重新裁决“格式例外”

### 8.1 当前选项不定义章节

当前“参考文献、致谢、摘要、附录、个人简历”列表是固定样式角色列表。

它既不是：

- 自动识别结果；
- 用户自定义章节；
- 当前文档实际存在的区域；
- 当前文档范围选择。

### 8.2 它也不应该改造成章节定义器

不能简单把“跟随模板”开关改名为“自动识别”，因为开关现在控制的是样式来源，不是识别行为。

也不能给这五项加“自定义章节名称”输入框就宣称完成，因为仍缺少：

- 当前文档；
- 区域起止边界；
- 识别证据；
- 置信度；
- 校正结果；
- 作用生命周期。

### 8.3 正确去向

当前页面应拆成三处：

```text
方案规则
  结构来源、识别策略、低置信度策略、区域处理策略

工作台
  当前文档的识别结果、边界校正和确认

模板管理
  区域角色对应的字体、段落、编号和页面样式
```

因此，删除当前“格式例外”样式编辑能力的裁决仍成立，但删除后不能只留下“系统自动识别”一句话，必须同时建立工作台结构确认能力。

## 9. 最小正确版本

如果 V1 只做必要闭环，不追求完整规则编辑器，最小范围应是：

### P0：统一结构事实源

- 保留系统支持的语义角色目录；
- `heading_recognition` 产生统一候选；
- 所有写入模块只消费有效结构；
- 禁止参考文献等模块各自静默重猜。

### P0：当前文档结构确认

- 文档载入后显示已识别区域；
- 显示起点、终点、标题证据和置信状态；
- 支持“不是此区域”“指定起点”“指定终点”“改为某角色”；
- 校正结果只作用于当前任务。

### P0：安全执行门

- 高置信度：可自动继续，但执行前摘要可见；
- 中置信度：要求用户确认后才修改该区域；
- 低置信度或冲突：默认保留原格式或跳过；
- 不允许“识别不到就当正文”后直接全量改写高风险区域。

### P1：方案策略

- 配置不确定项策略；
- 配置各支持角色的处理行为；
- 不保存具体页码和段落边界；
- 不保存视觉样式值。

### P2：可复用规则

- 用户可把明确的标题别名、顺序规律保存为规则；
- 规则有名称、适用模式和来源；
- 方案引用规则集；
- 当前文档校正默认不自动写入规则。

这一路径比先建立完整 `DocumentStructureProfile` 更正确，因为先闭合用户能看到、能纠错、能安全执行的链路。

- 当前文档是否存在参考文献；
- 当前文档从哪一段开始；

## 11. 验收标准

### 11.1 用户理解

用户能明确回答：

1. 系统支持识别哪些文档组成部分；
2. 当前文档实际识别出了哪些部分；
3. 哪些结果是系统判断，哪些是自己校正；
4. 校正是只影响本篇，还是保存为长期规则；
5. 识别出区域后，方案会如何处理；
6. 最终格式来自哪个模板。

### 11.2 生命周期

- 方案中不保存当前文档段落范围；
- 单篇校正不污染其他文档；
- 规则集只有显式保存才更新；
- 模板不保存运行时识别结果；
- 报告可追溯自动判断与人工校正。

### 11.3 执行安全

- 中低置信度区域不会被静默大范围改写；
- 用户否定某区域后，所有模块都遵守该否定；
- 页码输入在写入前解析为稳定锚点；
- 写入模块共享同一份有效结构；
- 自动识别失败时有可见回退，不把所有段落默认当正文后继续修改。

### 11.4 场景适配

- 论文显示论文角色；
- 技术长文档重点显示标题树和附录/合并边界；
- 公文、试卷、表单的母版结构不重复自动识别；
- 通用快速排版不强迫用户理解论文专属区域。

## 12. 待产品审阅的最终决策

- [ ] 同意“自动识别为默认、当前文档人工校正为必备、可复用规则为进阶”的总模型。
- [ ] 同意 V1 不允许用户任意新增系统不理解的语义角色。
- [ ] 同意方案只保存识别策略和处理策略，不保存具体文档边界。
- [ ] 同意工作台承载当前文档结构确认。
- [ ] 同意模板只承载角色样式，不承载当前文档识别结果。
- [ ] 同意页码范围只作为源文档输入提示，执行前必须解析为稳定锚点。
- [ ] 同意先建立最小确认闭环，再决定是否把复用规则独立为 `RecognitionRuleSet` 或 Profile。
- [ ] 同意当前“格式例外”不能通过改名继续保留为章节识别入口。

## 13. 最终结论

关于“自动识别还是用户自定义”，真正正确的裁决是：

```text
不是二选一。

系统定义它能理解的角色，
系统自动识别当前文档，
用户校正本次识别结果，
用户选择是否把通用规律保存为规则，
方案决定识别后怎么处理，
模板决定处理后的视觉格式。
```

当前设计最严重的问题不是按钮长得不像整体 UI，而是把本应发生在“文档载入之后”的结构识别与校正，伪装成了“文档载入之前”的固定格式例外列表。

因此，正确重构顺序不是：

```text
把五个开关画得更清楚。
```

而是：

```text
先建立当前文档结构识别事实
-> 再让用户确认和校正
-> 再由方案选择处理行为
-> 最后由模板提供格式。
```
