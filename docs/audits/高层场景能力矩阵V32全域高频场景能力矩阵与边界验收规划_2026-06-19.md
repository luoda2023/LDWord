# 高层场景能力矩阵 V32 全域高频场景能力矩阵与边界验收规划（2026-06-19）

本文件继续回应“更高层的场景能力矩阵仍不完善，不能出现高频适用场景遗漏或者边界不清晰”的要求。

V29/V30/V31 已经把矩阵从“几个场景入口”推进到 pack、family、request-cell、Word/OOXML risk、MaterialSchema、DeliveryPreset、plugin/manual gate、dashboard/drilldown 和 release gate。V32 再往上收一层：不再只问某个功能有没有登记，而是问每个高频用户任务是否拥有完整产品能力，并且是否能解释哪些能力归核心、哪些归模板、哪些归资料、哪些归交付、哪些必须进入插件/人工边界。

## 1. V32 核心结论

当前不宜继续盲目增加顶层 pack。真正的缺口在于：许多高频任务虽然已有归属，但还没有在“输入事实源、模板控件、规则 profile、对象风险、交付版本、报告证据、失败/人工边界、前台可见性”之间形成完整闭环。

V32 的完善标准是：

```text
用户自然说法
-> 高频任务域
-> coverage pack / planned family / profile / schema / preset / plugin / negative
-> 输入事实源
-> 模板基线与控件契约
-> 处理范围与 Word story
-> 规则、计数、资料、对象、公式、图片、固定版式
-> 交付 preset、批量、报告、artifact
-> 成功 / 降级 / 失败 / 人工门证据
-> 前台 drilldown 与 release gate
```

如果一项高频需求不能走完这条链，它就只能算规划项、边界项或 first slice，不能宣称 Green/L5 完整能力。

## 3. 场景能力矩阵的十三个验收槽位

每个高频场景域必须逐项回答以下槽位。不是每个槽位都要启用，但必须明确状态：启用、可选、禁用、人工门、插件、handoff 或 negative。

| 槽位 | 必须回答的问题 | 稳定承载层 | 不清晰时的风险 |
| --- | --- | --- | --- |
| UserIntent | 用户会怎么说，是否 matched/ambiguous/negative/handoff | request-cell、task lexicon、natural router | 高频说法遗漏或错路由 |
| CarrierLayer | 是 pack、family、profile、schema、preset、plugin 还是 negative | coverage manifest、family registry | 行业名膨胀成顶层入口 |

## 5. 外部技术记录吸收为能力原则

两份外部记录不作为当前实现事实，但必须吸收为矩阵原则。

### 5.1 CountEngine 原则

需要吸纳：

- 不做单一“字数统计器”，而做 profile-driven multi-metric CountEngine；
- 同时保留 Word-like words、中文字符、纯汉字、英文词、含/不含空格字符、参考文献、图、表、公式、章节、段落等指标；
- 场景只保存 profile、范围和规则来源，执行结果进入报告；
- 报告必须说明采用口径、计入范围、排除范围、不确定项和官方系统差异边界。

V32 落点：

- CountProfile 是横向能力域，至少服务中文论文、英文期刊、项目申报、标书、披露、试卷、技术文档；
- 后续 N2.170 必须补 CountProfile 场景覆盖审计；
- 计数不进入 MaterialSchema，也不回流到模板控件。

### 5.2 试卷生成技术栈原则

需要吸纳：

- AI 或外部系统只提供结构化源，程序负责校验、预览、渲染和导出；
- JSON 是机器事实源，Markdown 是人工预览，Word 是正式交付；
- 学生版/教师版/答案版/解析版来自同一结构化源和 ContentVisibility/DeliveryPreset，不重复生成不同内容；
- 通用图片能力优先于复杂几何图自动生成；
- 复杂几何、电路、化学结构式、AI 生图属于插件或后期能力。

V32 落点：

- `exam_education` 是验证 InputSourceProfile、MaterialSchema、FormulaPolicy、AssetAndImagePolicy、ContentVisibility、DeliveryPreset 的样板；
- 这套“结构化源 -> 预览 -> Word 多版本交付”的模式应泛化到合同审阅/签署、披露审阅/公开/归档、投稿初投/修回、批量个性化文档；
- 不把 Markdown 当最终 Word 版式事实源，不把 AI 质量纳入核心承诺。

### 5.3 Word 自动生成技术栈视角

外部分享链接当前只能确认其主题为 Word 文档自动生成技术栈，正文未能被本地读取；V32 按该主题和现有两份技术记录吸收以下稳定原则：

```text
结构化事实源
-> 模板渲染
-> Word 后处理
-> 对象预检
-> 多版本交付
-> 报告与人工确认
```

因此，场景能力不应把“生成 Word”简化成字符串替换。所有高频场景都要区分：

- 事实源：JSON、Excel、资料包、DOCX 本体还是人工确认；
- 渲染源：模板、母版、fixed-layout profile、图片资产；
- 后处理：样式、目录、编号、题注、页眉页脚、对象风险；
- 交付：DeliveryPreset、BatchPreset、报告、manifest、package；
- 边界：AI/OCR/LaTeX/专业判断是否进入插件/人工门。

## 6. 控件一致性作为场景准入

场景配置页可以按场景组合和隐藏控件，但不能改变模板管理已经定义的控件语义。任何共享外观参数必须复用同一 control contract。

| 控件族 | 场景侧要求 | 不允许的情况 |
| --- | --- | --- |
| 左缩进/右缩进 | 同一行或同组展示，单位、stepper、禁用语义与模板管理一致 | 场景页改名或拆成另一套单位 |
| 段前/段后 | 同一行或同组展示，命名保持“段前/段后” | 改成前距/后距且执行链无法对应 |
| 特殊缩进 | 必须可交互切换无/首行/悬挂；无时禁用数值并归零 | 只有只读文本或无法切换 |
| 行距类型/行距值 | 类型和值绑定；固定/多倍/最小值有清楚单位 | UI 可选但执行层不消费 |
| 表格固定行高 | 只在 fixed-layout profile 出现，对应 Word `w:trHeight` | 混入通用 TableConfig 模板参数 |
| 水印/盖章/签章 | 状态与交付语义归场景，外观可复用模板语言 | 既像模板背景又像交付状态，边界不明 |
| 公式策略 | 片段转换归 FormulaPolicy，完整 LaTeX/OCR/AI 质量归插件 | 把公式当普通文本或模板杂项 |
| 输出版本 | 归 DeliveryPreset/OutputConfig | 散落在模板页或一次性执行按钮 |

控件一致性不是 UI 美观问题，而是执行链安全问题：同一参数在模板管理、场景配置、resolver、pipeline、report 中必须使用同一语义，否则会出现“UI 可配、执行不认、报告不解释”的断链。

## 7. 边界裁决树

新增高频需求必须按以下顺序裁决：

1. 是否需要 Word 原生交付。不需要则 negative 或外部插件。
2. 是否只是模板外观。是则归 TemplateConfig/control contract。
3. 是否是资料事实、字段、人员、图片、签章、附件。是则归 MaterialSchema。
4. 是否是字数、图表、公式数量、规则来源、提交要求。是则归 CountProfile/RuleSource。
5. 是否是输出版本、命名、目录、PDF/ZIP、提交包、报告。是则归 DeliveryPreset/OutputConfig。
6. 是否是多记录、多人员、多项目。是则归 BatchPreset。
7. 是否是固定版位、证书、登记表、答题卡、套打。是则归 fixed-layout profile。
8. 是否触达字段、批注、修订、内容控件、文本框、OLE、rels、宏。是则先走 ObjectPreflight。
9. 是否涉及法律、财务、审计、专利、医学、翻译质量、AI 内容质量、OCR/LaTeX 无损转换。是则进入 PluginManualGate。
10. 是否能从导入边界 handoff 到目标 pack。能则必须有 handoff 报告和回退策略。
11. 是否拥有独立用户心智、事实源、交付、风险面、报告和证据链。只有全部成立才考虑新增 coverage pack。

## 8. 产品成熟度验收

V32 继续区分“静态闭合”和“产品闭合”。

| 等级 | 定义 | 最低证据 |
| --- | --- | --- |
| L1 Gray | 文档或规划存在 | 规划文档、backlog |
| L2 Blue Boundary | 明确边界、人工门或负例 | plugin/manual gate、negative control、handoff |
| L3 Yellow | 有 route、profile、schema、preset 或 first-slice 执行证据 | request-cell、fixture、审计 row |
| L4 Orange | UI/执行/报告/fixture/release gate 基本闭合 | 前台可见、执行可消费、报告可解释 |
| L5 Green | 成功、降级、失败/人工门三类用户旅程均产品化 | journey fixtures、修复入口、批量/交付闭环 |

禁止用 dashboard passed、request-cell 数量或 release gate passed 直接等同 Green/L5。release gate 只能证明不明显断链，不能证明真实用户旅程完备。

## 11. V32 判定

完善的高层场景能力矩阵不是“多几个按钮”或“多几个顶层场景”。它应该是一套防遗漏、防越界、防断链的产品能力系统：

- 高频任务全集负责防遗漏；
- 承载层裁决负责防入口发散；
- control contract 负责防 UI 语义分裂；
- MaterialSchema、CountProfile、InputSourceProfile 负责事实源；
- ObjectPreflight、Word risk、FormulaPolicy、fixed-layout profile 负责 Word/OOXML 安全；
- DeliveryPreset、BatchPreset 负责交付与批量；
- PluginManualGate、handoff、negative control 负责边界；
- dashboard/drilldown/release gate 负责证据链；
- journey fixture 和 maturity audit 负责判断是否能从静态闭合升级为真实产品能力。

因此，V32 的行动方向不是扩大顶层 pack，而是把每个高频场景域按十三个验收槽位逐项补齐。只有当一个任务域具备清楚承载层、事实源、控件契约、Word 风险、交付、报告、失败/人工边界和真实用户旅程证据时，才能被标记为完整的 Green/L5 场景能力。
