# 高层场景能力矩阵 V25 完整能力定义与高频边界闭环规划（2026-06-19）

## 1. 本轮定位

本轮继续回应“目前功能点过于不完善，不希望出现高频适用场景遗漏或者边界不清晰”的要求。

V24 已经把高频请求样本、request-cell fixture、样本库和前台可见摘要串起来。V25 不再继续扩展场景名称，而是定义一个更高层的产品能力矩阵：

```text
用户高频说法
-> request-cell
-> pack / family / profile / schema / preset / plugin gate
-> Word/OOXML 风险面
-> 场景控件契约
-> Workbench 执行、报告、修复、样本、测试、发布门
```

只有这条链路都能回答“谁负责、怎么执行、哪里可见、如何修复、什么不承诺”，才算高频场景覆盖完整。

本轮基于当前代码和规划文档重新盘点，不以主观场景清单作为唯一事实源。

| --- | --- | --- |

## 3. 完整矩阵的十个槽位

一个高频场景不能只写“有这个功能”。每个 pack/family 至少要能回答十个槽位。

| 槽位 | 必须回答 | 合格证据 | 不合格表现 |
| --- | --- | --- | --- |
| request alias | 用户自然会怎么说？ | `scene_high_frequency_request_samples.py`、router 正例/歧义/反例 | 只按内部场景名匹配 |
| profile/family | 谁承接这个任务？ | coverage pack、planned family、profile、scene preset | pack 和 family 混用，归属不清 |
| material schema | 机器事实从哪里来？ | material schema、字段、图片/签章/附件 role | 用自由文本冒充结构化事实 |
| count/profile | 有无计数、限字、附件库存口径？ | CountProfile、inventory profile、报告证据 | 只输出全局字数，忽略分节/附件 |
| delivery preset | 用户要交付哪些版本？ | final/review/compare/signing/archive/student/teacher 等 preset | 用散落开关替代业务版本 |
| Word risk surface | 会碰哪些 OOXML 面？ | ObjectPreflight、fixed-layout、样本 fixture | 不检查修订、批注、域、OLE、宏等风险 |
| UI control contract | 场景控件是否和模板管理一致？ | control contract、ScenePanel summary、Workbench summary | 同名参数换控件、换单位、换禁用规则 |
| rule source | 规则来源是否可信？ | rule source registry、manual review、plugin gate | 把学校/期刊/招采/监管规则写死 |
| report/issue/artifact | 用户如何知道结果和边界？ | Workbench issue queue、report、artifact manifest | 只有运行日志，没有解释和定位 |
| repair/test/release | 如何修复并防回归？ | repair route、pytest、fixture、release gate | UI 有但执行/报告/测试缺席 |

槽位状态应区分 `ok`、`not_applicable`、`boundary`、`gap`。`not_applicable` 必须说明原因；`boundary` 必须有 manual/plugin gate；`gap` 不能被“后续再做”当作已覆盖。

## 4. 高频请求宇宙

当前 12 个 pack 可以覆盖主要高频任务，但必须按“请求类”而不是“场景名”理解。

| 高频请求类 | 常见用户说法 | 首选承接 | 边界 |
| --- | --- | --- | --- |
| 快速排版清洗 | 套模板、目录页码、统一格式、简历排版 | `quick_formatting` | 不承诺个人求职内容质量；C 端求职若成为产品方向再设 P2 family |
| 中文学术 | 论文、开题、课程论文、学校格式、字数统计 | `chinese_academic` / `thesis_cn` | 学校规则需要来源和人工确认 |
| 英文期刊 | manuscript、cover letter、response、supplementary | `english_journal` / `journal_en` | 不自动保证目标期刊最新规则 |
| 试卷教育 | 试卷、答案版、解析版、答题卡 | `exam_education` / `exam_teaching` | 复杂学科图形和 AI 出题质量走 plugin/manual gate |
| 标书/资质 | 投标文件、证照、正副本、资质附件包 | `bidding_materials` / `qualification_archive_packages` | 不判断证照真实性、有效期法律效力 |
| 公文/制度 | 通知、函、会议纪要、制度汇编、内部传阅 | `official_policy` / `meeting_policy_documents` | 正式公文元数据和版记仍需 schema 深化 |
| 技术长文档 | 产品手册、接口文档、SOP、验收材料 | `technical_long_docs` / `long_document_publishing` | 产品手册若面向客户销售，应转 `application_reports` |
| 申报/售前/产品资料 | 项目申报、白皮书、售前方案、客户版资料包 | `application_reports` / `project_application`、`product_sales_documents` | 不替代外部申报系统，不承诺营销文案质量 |
| 合同交付 | 审阅稿、签署稿、字段一致性、甲乙方金额 | `contract_delivery` | 不提供法律意见 |
| 批量表单/固定版位 | offer、证明、证书、登记表、套打、行高保护 | `batch_forms` / `hr_batch_documents`、`form_batch_documents` | `w:trHeight` 只归固定版位，不回普通模板表格 |
| 专业披露/审阅 | 报价、预算、年报、ESG、专利、双语审阅、医疗注册 | `professional_disclosure` + plugin/manual gate | 核心只做格式、清单、版本、边界报告，不做专业结论 |
| 导入/AI 边界 | PDF 转 Word、OCR、完整 LaTeX、AI 草稿、复杂图形 | `import_ai_boundary` | 必须有置信度、人工确认和 handoff，不能静默进入核心排版 |

这张表的目的不是把所有场景都顶层化，而是确保每个高频说法都有入口、歧义裁决和不承诺边界。

## 5. 高频歧义裁决规则

边界不清通常不是缺一个名称，而是用户说法同时命中多个承载层。

| 用户说法 | 应先问/判定 | 裁决 |
| --- | --- | --- |
| 产品手册 | 是技术操作/接口/SOP，还是客户白皮书/售前资料？ | 技术操作进 `technical_long_docs`；客户/售前进 `application_reports/product_sales_documents` |
| 报价方案 | 是正文方案，还是金额/预算/财务表？ | 正文进 `application_reports`；金额正确性和财务判断进 `professional_disclosure` |
| 证书材料 | 是投标资质附件，还是批量套打证书？ | 资质归 `bidding_materials`；套打归 `batch_forms/form_batch_documents` |
| 双语文档 | 只是格式排版，还是翻译质量/术语一致性？ | 普通排版进 `quick_formatting`；质量审阅进 `professional_disclosure/bilingual_translation_documents` |
| PDF 论文 | 是导入源，还是目标论文场景？ | 先走 `import_ai_boundary`，转换后再进入 `chinese_academic` 或 `english_journal` |
| 答题卡 | 是试卷交付版本，还是普通表单？ | 优先 `exam_education` + fixed-layout delivery，不独立泛化为普通表单 |
| 会议材料 | 行政会议纪要/制度，还是普通总结汇报？ | 行政归 `official_policy`；普通总结可归 `quick_formatting` 或 `application_reports` |
| 法律/医疗/专利材料 | 是格式归档，还是专业判断？ | 格式可做；专业判断必须 plugin/manual gate |

裁决顺序建议固定为：

```text
专业/导入边界
-> 输入事实源
-> 输出版本
-> Word 风险
-> 业务 family
-> 模板样式覆盖
```

这个顺序能避免把 PDF/OCR、法律判断、输出版本、表格行高、段落缩进都塞进“场景开关”。

## 6. Word/OOXML 反推的完整性

完整矩阵必须从 Word 本身反推，否则会漏掉用户肉眼最在意的破坏。

| Word/OOXML 面 | 高频受影响场景 | 必须策略 |
| --- | --- | --- |
| `w:styles`、`w:pPr`、`w:rPr` | 全部排版、论文、技术、合同、公文 | 模板基线 + 场景覆盖；同名参数复用控件契约 |
| `w:numbering` | 论文、技术、公文、标书、长文档 | 保留/重建编号策略必须可见 |
| `w:sectPr`、headers/footers | 论文、公文、合同、签署稿、归档版 | 版式归模板；状态/版本归 scene/delivery |
| `w:tbl`、`w:trHeight` | 表单套打、证书、答题卡、报价单 | 只作为 fixed-layout 能力，不作为普通 TableConfig 残留参数 |
| `w:fldSimple`、`w:instrText` | 目录、页码、交叉引用、合同字段、长文档 | 预检、保留、跳过或报告 |
| `w:ins`、`w:del`、comments | 合同审阅、期刊返修、技术评审 | 修订/批注策略必须进入 ObjectPreflight 和报告 |
| `w:sdt` 内容控件 | 表单、合同、HR、证照、资料包 | schema 映射、填充、残留占位符检查 |
| drawing/textbox | 试卷、技术图、产品资料、签章 | 普通图片与专业图形插件边界分开 |
| embedded objects / OLE / VBA | 技术、报价、申报、导入边界 | 默认预检阻断或降级，不静默改写 |
| hidden text | 论文盲审、试卷答案、审阅版、资料包 | 输出版本和内容显隐规则必须可报告 |
| relationships / hyperlinks | 参考文献、附件包、技术文档 | 外链和附件关系应进入 report/artifact manifest |
| footnotes/endnotes/bibliography | 学术、期刊、政策、专利 | 引用和规则来源必须分层治理 |

V25 的核心判断：只要一个高频场景可能触碰这些 OOXML 面，就不能只用“格式统一”四个字概括。

## 7. 场景控件样式一致性

场景配置里的控件样式控制必须保持与模板管理规定的样式一致。当前 16 个 control contract 是准绳。

| 参数/能力 | 控件要求 | 场景边界 |
| --- | --- | --- |
| 中文/英文字体、字号 | 复用 `FontCombo`、`SizeCombo` | 场景只能做覆盖，不重写控件语言 |
| 左/右缩进 | 同行展示、同单位、同禁用态 | 不能一边用字符，一边用磅且无解释 |
| 特殊缩进 | 必须可切换无/首行/悬挂 | 禁用值时要清楚说明原因 |
| 行距类型/行距值 | 类型和值为耦合控件 | 固定值、多倍、单倍等不能拆散成无关输入 |
| 段前/段后 | 同行展示、同单位 | 和模板管理命名保持一致 |
| 固定行高 | `FixedLayoutRowHeightPolicy` | 只出现在固定版位/表单/证书/答题卡 |
| 公式策略 | 转换、低置信度、fallback 归 scene；视觉归 template | 不把完整 LaTeX 转换伪装成普通公式样式 |
| 水印状态 | 状态/版本归 scene/delivery；外观基线归 template/control contract | 不把水印文本、状态、视觉混成一个开关 |
| 输出版本 | `DeliveryPreset` 编辑器 | 不用散落 checkbox 代替业务版本 |
| 资料 schema | registry combo + summary + repair action | 不把字段、图片、附件 role 塞进自由文本 |
| plugin/manual gate | Workbench issue + report payload | 高风险能力必须可见、可确认、可追踪 |

结论：同名格式参数必须同控件、同单位、同交互；场景私有业务控件也必须继承同一尺寸、边框、焦点、下拉和摘要投影体系。

## 8. 当前不完善的真实含义

当前“不完善”不是 registry 没有东西，而是多数能力还没有达到可稳定承诺的 L5。

| `english_journal` | `yellow_l3` | reviewed journal profile 更新流、完整 submission package 深度 |

| `official_policy` | `yellow_l3` | 公文元数据 schema、正式/内部/归档报告深度 |
| `technical_long_docs` | `orange_l4` | 索引/附录、多文件合并边界 |

## 9. L5 准入门槛

一个 pack/family 想从 L3/L4 升到 L5，至少需要满足：

1. request-cell：高频正例、歧义例、反例齐全；0 proxy；歧义能在 UI 说明。
2. fixture：有最小 DOCX fixture，也有真实业务模板 fixture 或脱敏样本。
3. schema/profile：资料、计数、输出、规则来源都可解释，不能靠硬编码。
4. UI：ScenePanel 可见，Workbench 可见，QuickExecution 摘要可见，问题队列可修复。
5. execution：Pipeline 执行、跳过、降级、阻断有一致语义。
6. report：JSON/Markdown 报告能解释产物、边界、证据、残留。
7. repair：每类问题有明确 owner surface 和跳转目标。
8. control contract：共享参数不分叉控件。
9. release：独立脚本和 pytest 之外，还要进入 CI/发布流程。
10. boundary：专业判断、AI、OCR、完整 LaTeX、法律/财务/医疗/专利等不被核心能力过度承诺。

任一项缺失，都只能叫 first slice 或 L4，不应叫“完整支持”。

## 11. 完整性验收问卷

每新增或升级一个高频场景，必须回答：

1. 用户会怎么说？是否有 request-cell？
2. 是否有正例、歧义例、反例？
3. 应落 pack、family、profile 还是 plugin/manual gate？
4. 是否只是输出版本，应该归 DeliveryPreset？
5. 是否只是样式基线，应该归 Template？
6. 是否只是本次路径/临时选择，应该归 Session？
7. 机器事实来自 DOCX、JSON、XLSX、BibTeX/CSL、资料包、PDF/OCR、LaTeX 还是插件？
8. 是否需要 material schema？
9. 是否需要 CountProfile 或附件 inventory？
10. 会触碰哪些 Word/OOXML 面？
11. 是否需要对象预检、降级、跳过或阻断？
12. 是否有公式、水印、输出等横切能力？
13. 同名控件是否复用模板管理控件语言？
14. Workbench 是否能解释风险？
15. 报告是否能解释产物、缺项、边界和跳过原因？
16. 是否有修复入口和 owner surface？
17. 是否有 DOCX fixture？
18. 是否有真实业务 fixture 或脱敏样本计划？
19. 是否进入 release gate？
20. 是否明确不承诺专业判断或无损转换？

任一项回答“不知道”，就是边界不清；回答“以后再接”，就是链路未闭环；回答“UI 有但执行/报告/测试没有”，就是假闭环。

## 12. 不承诺边界

核心场景矩阵不承诺：

- 法律意见、合同条款有效性、医学/监管结论；
- 财务、预算、报价金额正确性；
- 专利权利要求质量或侵权判断；
- 翻译质量和术语正确性；
- OCR/PDF/完整 LaTeX 无损转换；
- AI 生成内容事实正确性；
- 外部学校、期刊、招采、监管系统的最新规则自动同步；
- 复杂学科图形、CAD/Visio/宏对象的自动语义修复。

这些能力可以进入 plugin/manual gate、confidence report、人工确认或外部集成，但不能在核心场景中静默承诺。

## 13. 结论

V25 的判断是：

```text
当前高频覆盖的静态链路已经 clean；
真正的短板是 L5 产品化深度、独立可浏览 evidence、CI 发布门和真实插件/专业边界。
```

因此后续应避免继续堆顶层入口，转向：

- 让每个高频 request-cell 可见、可筛选、可追溯；
- 让每个 pack/family 的十个槽位可验收；
- 让控件语言和模板管理保持一致；
- 让 Word/OOXML 风险进入执行前、报告和修复；
- 让专业/导入边界明确降级到 plugin/manual gate。

这才是“不遗漏高频适用场景、边界清晰、链路不互断”的完整矩阵。

## 17. 高层场景能力矩阵再深化：避免高频遗漏的判定坐标

仅按“论文/标书/公文/合同”等场景名规划，仍会遗漏大量高频需求。更完整的矩阵应该按六个坐标交叉判断：

| 坐标 | 要问的问题 | 防遗漏价值 |
| --- | --- | --- |
| 任务心智 | 用户到底要完成什么交付？ | 避免把售前方案误归技术手册，把资质包误归普通附件 |
| 输入事实源 | 事实来自 DOCX、JSON、XLSX、资料包、PDF/OCR、LaTeX、插件还是人工？ | 避免自由文本冒充结构化事实 |
| 文档形态 | 单文档、长文档、多文件、批量、套打、审阅稿、材料包？ | 避免把 batch/forms/fixed layout 混入普通排版 |
| Word 风险面 | 是否触碰编号、分节、页眉页脚、表格行高、域、批注修订、内容控件、OLE、宏、隐藏文本？ | 避免“格式统一”破坏真实 Word 对象 |
| 交付意图 | final、review、compare、signing、archive、student/teacher、cover letter、submission package？ | 避免用散落开关替代业务版本 |
| 证据成熟度 | 是否有 request-cell、fixture、report、repair、test、release gate？ | 避免 UI 有、执行/报告/测试没有的假闭环 |

因此，后续新增或升级任何场景时，不先问“要不要加一个顶层入口”，而先填这个坐标。只要坐标能落入既有 pack/family/profile/preset/plugin gate，就不新增顶层场景；只有当用户心智、输入事实源、交付意图和风险面同时长期稳定不同，才考虑新入口。

## 18. 高频适用场景的完整覆盖视角

为避免遗漏，场景矩阵应覆盖四类高频维度，而不是只覆盖行业名称：

| 维度 | 必须覆盖的高频形态 | 当前主要承接 | 易漏边界 |
| --- | --- | --- | --- |
| 格式修复型 | 套模板、目录页码、编号、段落表格、图片题注 | `quick_formatting`、template | 不应承诺专业规则 |
| 规则合规型 | 学校、期刊、招采、公文、申报、附件清单、字数口径 | `chinese_academic`、`english_journal`、`bidding_materials`、`official_policy`、`application_reports` | 规则来源、更新时间、人工确认 |
| 资料驱动型 | 合同字段、投标主体、签章 Logo、HR 批量、产品资产、报价表 | material schema + family | 字段一致性与专业真实性分开 |
| 多版本交付型 | 审阅稿、签署稿、正副本、归档、学生/教师/答案、投稿包、对比稿 | `DeliveryPreset` | 不用场景开关代替 preset |
| 固定版位型 | 套打表单、证书、答题卡、固定行高表格 | `batch_forms` / fixed-layout profile | `w:trHeight` 只在这里正式承诺 |
| 专业/导入边界型 | 法务、财务、医疗、专利、双语质量、OCR/PDF、完整 LaTeX、AI 内容 | `professional_disclosure`、`import_ai_boundary`、plugin/manual gate | 必须有 confidence/report/handoff，不静默承诺 |

这个视角下，公式、输出、水印、行高、对象预检都不应再被看作“先不管的参数”。它们分别属于：

- 公式：专业符号与导入边界，核心只承诺低风险片段和 fallback；
- 输出：交付 preset，是场景矩阵的一等能力；
- 水印：状态/版本归 scene/delivery，外观归 template/control contract；
- 行高：只在 fixed-layout/表单/答题卡/套打场景正式产品化；
- 对象预检：所有可能破坏 Word 对象的场景都必须消费。

## 19. 边界清晰的硬规则

后续执行中使用以下硬规则防止边界滑移：

1. 只改变外观基线：归 Template。
2. 改变任务策略、范围、失败/降级行为：归 Scene/Profile。
3. 改变字段、图片、签章、附件、主体事实：归 Material Schema。
4. 改变规则口径、字数、清单、规则来源：归 Compliance/Profile。
5. 改变产物版本和文件包：归 DeliveryPreset。
6. 高风险、依赖外部服务、专业判断：归 Plugin/Manual Gate。
7. 只对本次运行有效：归 Session。

如果一个能力同时命中多项，必须在 UI/报告中展示 owner surface。不能用一个“高级开关”同时承载模板样式、业务策略、输出版本和专业判断。

## 20. 仍保留的高层缺口

V25 + N2.152d/N2.153 后，矩阵可见性、证据可达性和发布门禁更强，但仍保留明确缺口：

- 全局 request-cell registry 浏览器尚未实现，当前仍是 per-scene 视角；
- report artifact drilldown 尚未从 request-cell 列表直接打开；
- GitHub workflow 已配置，但远端状态徽章、分支保护和发布分支策略未闭合；
- 真实业务模板 fixture/脱敏样本深度不足，多数 pack 仍不能升到 Green/L5；
- plugin/manual gate 还缺真实插件生态和人工确认记录；
- 场景配置的控件一致性需要继续用 control contract 测试锁住，尤其是输出、水印、公式、fixed-layout profile 等下一批 UI。

下一步优先级仍然不是新增顶层场景，而是把 P0/P1 高频链路补成可看、可跑、可报告、可修复、可发布的 L5 闭环。
