# 工作台导航与修复路由一致性审计记录

日期：2026-06-28

## 本轮目标

上一轮已经新增了 `workbench_issue_navigation.py`，把 Workbench 问题 target type 到 panel/card 的跳转规则集中起来。

但项目里原本还有另一张表：

- `src/config/scene_repair_routing.py`

它负责说明“某类问题属于哪个修复归属面”。如果这两张表不做一致性审计，就可能出现：

- 修复归属表里登记了 target type，但工作台没有显式导航。
- 工作台导航表里登记了 target type，但没有修复归属说明。
- 某些 target 静默落到 `content_fill` fallback，用户点击后不知道为什么去了资料页。

本轮目标是让这两张表建立自动审计关系。

已新增工作台导航一致性审计：

- `WorkbenchIssueNavigationAuditResult`

现在 `scene_repair_routing` 中登记的 `repair_target_types` 都有显式工作台导航，不再依赖 unknown fallback。

## 新增审计规则

审计结果包含三类问题：

| 字段 | 含义 |
| --- | --- |
| `missing_route_target_types` | 修复归属表里有，但导航 registry 没登记 |
| `fallback_route_target_types` | 修复归属表里有，但实际会落到 `content_fill` fallback |
| `unexpected_navigation_target_types` | 导航 registry 有，但修复归属表没有，且不在允许额外 target 列表 |

`is_clean` 只有在三类问题都为空时才为 `True`。

## 显式额外 target

有些导航 target 不是 `scene_repair_routing` 的修复归属 target，而是工作台动作派生出来的 target，因此需要显式允许：

- `parameter_path`
- `profile_question_figure_repair_candidate`
- `profile_question_figure_repair_conflict_selection`
- `question_figure_batch_apply_transaction_task_summary`

这些不是遗漏，而是更靠近工作台执行动作的 target。

## 为什么这一步重要

前面已经把链路拆成了：

- adapter projection：说人话。
- shared UI：摆控件。
- navigation registry：决定去哪。
- panel：执行动作。

但如果 navigation registry 没有被审计，它仍然可能变成另一张“不知道有没有漏”的表。

本轮把导航表和修复归属表连起来，形成了更完整的产品约束：

- 产品规划里说某个 target 应该能修。
- 工作台必须知道它应该去哪。
- 如果不知道，测试会失败。

这比单纯添加 UI 分支更接近优秀设计：规则有归属、可枚举、可审计。

## 当前仍然不足

### 1. 审计还没有检查 panel/card 是否真实存在

现在能证明 target type 有导航 projection，但还没有自动验证：

- `template / tpl_overview` 是否存在于模板面板。
- `scene / scn_output` 是否存在于场景面板。
- `quick_execute` 是否存在于工作台动态卡片。

后续可以把 panel registry 和 detail card registry 也纳入审计。

### 2. 审计还没有检查 bridge 副作用

Material/profile 类型不只是跳到 assets，还需要 bridge 调用：

- `request_material_repair_target`
- `request_material_profile_repair_target`
- `request_material_profile_repair_candidate`

当前这些仍由 `panel_v2.py` 执行，测试主要靠既有 panel/quick detail 覆盖。后续可以抽 command 层进一步审计。

### 3. plugin/manual gate 仍只是进入 quick_execute

`plugin_manual_gate` 现在显式路由到 `quick_execute`，比 fallback 清晰，但它还缺少专门的人工确认/插件交接详情面。

这个属于产品设计问题，不是 registry 能单独解决。

## 推荐下一步

下一轮建议做“目标面存在性审计”：

1. 列举 navigation registry 里的 `panel_id/card_id/feature_card_id`。
2. 对照 `PANEL_SPECS`、ScenePanel card 常量、TemplatePanel card 常量、Workbench feature card 定义。
3. 如果 card 不存在，测试失败。
4. 用 MD 记录哪些 target 只是 fallback 或等待产品面。

这样能继续保证功能分布、边界、可读性不靠记忆维护。
