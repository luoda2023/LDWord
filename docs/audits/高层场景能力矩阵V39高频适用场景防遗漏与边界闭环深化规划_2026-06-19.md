# 高层场景能力矩阵 V39 高频适用场景防遗漏与边界闭环深化规划

日期：2026-06-19

## 1. 文档定位

本文继续回应“更高层的场景能力矩阵目前功能点过于不完善，不能出现高频适用场景遗漏或者边界不清晰”的要求。

V38 已经把完整场景能力拆成 28 个产品能力槽位，并明确当前风险不是顶层 pack 数量不够，而是 pack 下面的真实产品能力、用户旅程、修复入口、交付执行和边界交互不够深。V39 在此基础上继续向上收敛，专门回答三个问题：

1. 哪些高频适用场景必须被覆盖，不能靠“以后再说”或“算在某个大类里”带过。
2. 一个新需求到底应该归 pack、family、profile、schema、preset、fixed-layout、plugin/manual gate 还是 negative/handoff。
3. 怎么判断某个场景能力已经“完善”，而不是只有规划名、审计项或半截 UI。

V39 的核心结论：

```text
顶层 12 个 coverage pack 仍然够用；
真正要补的是每个高频任务域的承载层、能力槽位、失败/降级/人工门旅程、前台发现入口和报告/修复闭环。
```

因此，后续不建议为了“看起来完整”继续新增顶层入口。完善路径应当是：

```text
高频任务域
-> 用户话术和歧义裁决
-> 承载层
-> 输入事实源
-> 模板/控件/范围
-> 资料/规则/对象/固定版式
-> 交付/批量/报告/修复
-> fixture/release gate
-> 明确边界
```

这意味着当前矩阵已经能挡住明显断链，但不能代表高频用户任务都可以稳定推荐给普通用户使用。

## 3. V39 的完善定义

“完善”不能被定义为“有这个场景名”。一个场景能力至少要同时回答九个问题。

| 序号 | 完善问题 | 不完善时的典型表现 |
| ---: | --- | --- |
| 1 | 用户会怎么说这件事，是否有 request-cell 或明确 negative/handoff | 高频说法找不到入口 |
| 2 | 它属于哪个承载层：pack、family、profile、schema、preset、plugin/manual gate | 顶层入口膨胀，或错误归入通用排版 |
| 3 | 输入事实源是什么：DOCX、JSON、Markdown、XLSX、PDF/OCR、LaTeX、AI、人工资料 | 执行靠猜，报告无法复盘 |
| 4 | 是否复用模板管理的控件、命名、单位、禁用语义和执行字段 | UI 能配但 pipeline 不认 |
| 5 | 触碰哪些 Word/OpenXML 风险面，动作是 preserve、warn、block、skip、repair 还是 manual | 文档对象被静默破坏 |
| 6 | 输出哪些 artifact：DOCX、PDF、ZIP、report、manifest、compare、intermediate | 用户不知道交付是否完整 |
| 7 | 缺资料、歧义、对象风险和执行失败能否进入 issue queue 与 repair route | 只有 warning，没有下一步 |
| 8 | 是否覆盖成功、降级、失败/人工门三类 journey fixture | 静态闭合冒充真实可用 |
| 9 | 边界是否前台可见：专业判断、AI/OCR/LaTeX、复杂图形、非 Word 输出不被过度承诺 | 核心能力越界，后续无法验收 |

Green/L5 的最低准入不是“没有阻塞 issue”，而是：

```text
P1/P1_CANDIDATE 场景具备可发现、可配置、可执行、可报告、可修复、可回放、可解释边界的完整旅程；
manual/plugin/negative 场景具备前台可见的限制、替代路径和报告记录；
所有共享模板控件都通过场景运行时一致性验证；
所有 Word/OOXML 风险面都有动作和证据，而不是只写在规划文档里。
```

## 5. 边界裁决树

新增需求先按下面顺序裁决，不先问“要不要加一个场景入口”。

1. 是否需要 Word 原生交付。不是 Word 核心交付时，进入 negative 或 external plugin。
2. 是否只是外观模板、段落、页眉页脚、目录、题注、表格样式。是则归 TemplateConfig 和模板管理控件。
3. 是否是场景页复用模板控件。是则必须继承同名、同单位、同禁用语义、同运行时字段。
4. 是否是资料事实、图片、签章、附件、人员、项目。是则归 MaterialSchema / AssetsPanel。
5. 是否是字数、词数、图表、公式、参考文献、规则来源。是则归 CountProfile / RuleSourceGovernance。
6. 是否是输出版本、命名、目录、PDF/ZIP/report/manifest/intermediate。是则归 DeliveryPreset / OutputConfig。
7. 是否是多记录、多人员、多公司、多项目、多模板。是则归 BatchPreset。
8. 是否是固定版位、证书、答题卡、套打、固定行高。是则归 fixed-layout profile 和 Word risk。
9. 是否触达字段、批注、修订、内容控件、文本框、OLE、rels、宏。是则先走 ObjectPreflight。
10. 是否涉及法律、财务、审计、专利、医学、翻译质量、AI 内容质量、OCR/LaTeX 无损转换。是则进入 PluginManualGate。
11. 是否能从导入边界 handoff 到目标 pack/family。能则必须有 handoff 报告、置信度和回退策略。

新增顶层 pack 只有在同时满足以下条件时才成立：

| 条件 | 判断标准 |
| --- | --- |
| 稳定心智 | 用户长期用这个大类表达，而不是一次性行业别名 |
| 独立事实源 | 输入事实源、资料 schema 或规则 profile 明显不同 |
| 独立交付 | 输出版本、目录、artifact 或失败策略明显不同 |
| 独立 Word 风险 | 触碰的 OOXML 风险组合不能由现有 pack 承载 |
| 独立证据链 | 有 request-cell、fixture、report、repair、release gate 计划 |

不满足时，优先归 family/profile/schema/preset/plugin/manual gate。

## 6. 高频易混边界

这些边界最容易让用户觉得“功能点不完善”或“场景不清楚”，必须在 UI、报告和规划中明确。

| 易混项 | 裁决 |
| --- | --- |
| 产品手册 vs 技术手册 vs 售前方案 | 技术事实/长文结构走 `technical_long_docs`；客户方案和营销资产走 `product_sales_documents`；报价金额走 `finance_quote_documents` 或专业边界 |
| 证书/奖状 vs 资质证照归档 | 生成和套打走 `form_batch_documents` fixed-layout；证照附件清单和缺件走 `qualification_archive_packages` |
| 通知/函/申请表 | 公文格式和文号走 `official_policy`；固定表单填充走 `batch_forms`；项目资料走 `project_application` |
| 合同 vs 法律文书 | 合同字段一致、审阅/签署包走 `contract_delivery`；法律意见、诉讼、仲裁等进入 professional manual/plugin |
| 答题卡 vs 固定表单 | 内容版本和题源走 `exam_teaching`；固定版位、`w:trHeight`、文本框和内容控件走 fixed-layout profile |
| 中文论文 vs 英文投稿 | 学校论文、学位规则走 `thesis_cn`；journal display items、cover letter、BibTeX/CSL 走 `journal_en` |
| 项目申报 vs 标书 | 申报限字、成果、预算和提交包走 `project_application`；资质证照、正副本、投标附件走 `bidding_materials` |
| Excel 到 Word vs 资料包 | Excel 是 InputFactSource；字段映射归 MaterialSchema，多记录归 BatchPreset，最终落到目标 pack |
| PDF/OCR/AI 导入 vs 目标场景 | 导入只负责置信度和 handoff；格式化/交付仍由目标 pack 执行 |
| 双语排版 vs 翻译质量 | 对照版式和术语一致性可做；翻译准确性走 plugin/manual gate |

## 7. 场景控件一致性要求

场景配置可以按场景组合、隐藏或禁用控件，但不能改写模板管理已经定义的同名参数语义。控件一致性不是视觉偏好，而是执行链安全。

| 控件族 | 场景侧允许 | 场景侧禁止 |
| --- | --- | --- |
| 左缩进/右缩进 | 可同一行或同组展示，单位和 stepper 与模板管理一致 | 改名、改单位、写入不同字段 |
| 段前/段后 | 可同一行或同组展示，保持“段前/段后”命名 | 改成前距/后距且执行链无法对应 |
| 特殊缩进 | 必须可切换无/首行/悬挂；无时禁用数值并归零 | 只显示文本或无法交互切换 |
| 行距类型/行距值 | 类型和值绑定；单位随固定/多倍/最小值清晰变化 | UI 可选但执行模块不消费 |
| 普通表格参数 | 归 TableConfig，处理边框、宽度、对齐等通用表格外观 | 混入 `w:trHeight` 固定版位语义 |
| 固定行高 | 只在 fixed-layout profile 出现，对应 Word `w:trHeight` | 回流到普通模板表格参数 |
| 公式/输出/水印 | 归场景能力板块，复用模板控件语言和边界报告 | 当成模板杂项或一次性开关 |
| 资料/素材控件 | 归 MaterialSchema/AssetsPanel，缺项进入 repair target | 只显示 warning，不给修复入口 |

任何场景控件进入产品前，都必须通过：

```text
Template control contract
-> ScenePanel runtime control
-> resolver/pipeline consumer
-> report field
-> issue/repair target
-> fixture/test/release gate
```

## 8. Word/OpenXML 反推缺口

高频场景不能只从“业务名称”出发，还要从 Word 本身反推。

| Word/OpenXML 面 | 高频触发场景 | 必须有的能力 |
| --- | --- | --- |
| `word/document.xml` paragraph/run | 所有格式化、论文、合同、技术文档 | 范围定位、样式清理、报告差异 |
| `word/styles.xml` | 模板基线、标题、正文、表格样式 | TemplateBaseline、ControlContract |
| `word/numbering.xml` | 论文、技术文档、公文、合同条款 | 编号保留/重建策略、report evidence |
| `w:tbl` / `w:trHeight` | 表单、证书、答题卡、套打 | fixed-layout profile，不回普通 TableConfig |
| `w:sectPr` / headers / footers | 论文、公文、合同、长文档 | WordStoryScope、页眉页脚/页码策略 |
| footnotes/endnotes | 学术、投稿、技术文档 | ReferenceCitation、CountProfile |
| comments/revisions | 合同、投稿修回、审阅稿、披露 | ObjectPreflight、manual confirmation |
| `w:txbxContent` / shapes | 证书、套打、复杂版式 | fixed-layout profile、preflight、residue check |
| `w:sdt` content controls | 表单、合同、资料填充 | MaterialSchema、fixed-layout text runtime |
| fields / TOC / PAGE / REF | 目录、页码、交叉引用、题注 | preflight、update/report/repair |
| relationships/media/embeddings | 图片、附件、嵌入对象 | AssetInventory、ObjectPreflight |
| macros/ActiveX | 安全风险 | block/manual/report |

V39 对 `TableConfig.row_height_pt` 的裁决保持 V38 结论：它不再是完全未实现残留参数，但也不能回到通用表格样式。后续只作为 fixed-layout profile 的产品化能力推进。

## 9. 成熟度分层

为避免“审计通过”冒充“产品完整”，V39 建议继续使用静态闭合和产品成熟度双轨。

| 等级 | 定义 | 可对用户承诺 |
| --- | --- | --- |
| L1 Gray | 只有文档规划或概念 | 不承诺可用 |
| L2 Blue Boundary | 边界、人工门、负例或插件门清晰 | 可以解释为什么不能自动完成 |
| L3 Yellow | 有 route、profile、schema、preset 或 first-slice 执行证据 | 可试用，但必须提示限制 |
| L4 Orange | UI/执行/报告/fixture/release gate 基本闭合 | 可作为主流程能力，但保留缺口 |
| L5 Green | 高频成功、降级、失败/人工门路径均产品化，真实业务 fixture 足够 | 可稳定推荐给普通用户 |

当前 27 个 readiness subject 没有 Green/L5。V39 不把这视为失败，而是把它当成后续路线排序依据。

## 12. V39 判定

V39 对当前高层场景能力矩阵的总体判断：

- 大类覆盖已经基本完整，短期不应通过新增顶层入口解决“不完善感”；
- 不完善感主要来自子场景内部链路：前台发现、真实资料录入、固定版式、交付 artifact、规则来源、失败/降级旅程、歧义澄清和专业边界；
- 高频场景不能只从业务名扫描，必须同时从用户话术、输入事实源、工作流、Word/OpenXML 风险、交付产物、失败模式和边界承诺七个方向扫描；
- 场景配置控件必须继续继承模板管理控件契约，尤其是缩进、段前段后、特殊缩进、行距、固定行高、公式、输出、水印和资料控件；
- fixed-layout、report artifact drilldown、真实业务 fixture 和规则来源生命周期是下一阶段最能降低“遗漏/边界不清”风险的四条主线。

一句话收束：

```text
高层场景能力矩阵的完善，不是让菜单变长，
而是让任何高频任务都能被准确归属、稳定执行、失败可解释、缺口可修复、边界可见。
```
