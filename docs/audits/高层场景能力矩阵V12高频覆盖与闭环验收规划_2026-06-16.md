## 2. V12 总判断

当前矩阵最大风险不再是“没有想到某个场景名”，而是：

```text
场景名已经覆盖不少，但能力成熟度、承载层边界和闭环证据还没有同样完整。
```

要避免高频遗漏和边界不清，不能继续按“多加几个场景入口”推进。正确方向是建立一张四维矩阵：

```text
高频任务族
  用户自然会怎么描述这件事。

横切工作流
  它本质是规范化、资料填充、多版本、批量、计数、对象保护、提交包还是插件导入。

模型承载层
  顶层场景、planning family、profile、MaterialSchema、CountProfile、DeliveryPreset、BatchPreset、模板、会话或插件。

闭环证据
  UI 能配置，resolver 能合并，runtime 能预检，pipeline 能执行，report 能解释，tests 能锁定。
```

V12 的核心验收语句：

```text
高频任务没有唯一优先承载层，算遗漏；
承载层没有明确不负责项，算边界不清；
配置没有进入执行和报告，算链路断裂；
只有 UI 没有测试，算展示原型；
涉及专业判断却没有插件或人工确认边界，算越界承诺。
```

## 3. 顶层入口不再膨胀

Workbench 当前 6 个 P0 可执行入口仍应保持稳定：

| 顶层入口 | 推荐长期语义 | 不能继续吞掉什么 |
| --- | --- | --- |
| `custom` 自定义 | 一次性组合、调试、未知文档 | 不能暗含专业规则 |
| `thesis` 论文排版 | 近期继续服务中文学术，长期收窄为 `thesis_cn` | 不能继续吞英文投稿、试卷、项目申报 |
| `bidding` 标书排版 | 商务投标、政府采购、资质材料包 | 不能承诺商务策略、法律判断、证照真伪 |
| `official` 公文排版 | 行政文书、正式/内部稿、文号类文书 | 不能变成所有制度/会议/HR 表单的大入口 |
| `technical` 技术文档 | SOP、规范、接口、手册、对象保护强的工程文档 | 不能验证技术内容真实性 |
| `report` 通用报告 | 总结、计划、调研、可研、轻量商业报告 | 不能吞合同、披露、投稿、项目申报等强 profile 任务 |

新增高频需求优先落为 planning family、profile、preset 或插件，不直接升为顶层入口。只有同时满足以下条件，才允许从 family/profile 升为顶层入口：

1. 用户心智高频且低歧义；
2. 不是现有 P0 入口的自然子 profile；
3. 有模板基线、输入契约、资料 schema、合规 profile、交付 preset 和报告闭环；
4. 至少一个 first slice 达到 L3；
5. 专业边界能在 UI 和报告中明确说明；
6. 有跨 UI、执行、报告、失败路径的测试。

文档类型只是第一维。很多高频需求本质上是同一类工作流。

| 工作流 | 高频场景 | 当前代码事实 | 主要缺口 | L3 闭环标准 |
| --- | --- | --- | --- | --- |
| 快速规范化 | report/custom/technical/official | P0 场景和模块开关已可执行 | 风险解释仍偏执行后 | 运行前展示范围、模块、对象风险和输出路径 |

| 资料填充 | bidding/official/contract/HR/project | MaterialSchema registry、ScenePanel、runtime 预检已推进 | 多 schema 与 AssetsPanel 全链路仍不足 | 缺字段/缺资产/unknown schema 运行前、报告、测试可见 |
| 签章/图片/附件 inventory | bidding/contract/project/qualification | material package 和 manifest 已有执行基础 | 附件角色、PDF/xlsx 资产、缺项原因未统一 | asset roles、manifest、zip、缺项报告闭环 |

## 7. Word/OOXML 视角补强

从 Word 本身看，场景不是只处理 `document.xml` 正文。V12 要求每个 L2 以上 family 都声明它使用哪些 Word story 和 package 风险。

| Word 视角 | 典型 XML/package 面 | 高频场景 | 必须说明 |
| --- | --- | --- | --- |
| 正文段落/run | `word/document.xml` 的 `w:p/w:r` | 所有场景 | 不破坏 run 级格式和字段结果 |
| 编号 | `numbering.xml`、段落编号属性 | official/meeting/thesis/long doc | 保留还是重建，不能静默覆盖 |
| 表格 | `w:tbl/w:tr/w:tc` | bidding/exam/form/finance/disclosure | 样式、内容、行高、合并单元格策略 |
| 表格行高 | `w:trHeight` | form/套打/报价/证书 | 只作为版位保护，不作为通用模板噪音参数 |
| 图片/绘图 | drawing、relationship、media part | technical/bidding/product/qualification | 图片角色、缺图、复制、关系完整性 |
| 页眉页脚 | `header*.xml`、`footer*.xml` | official/thesis/contract/disclosure | 外观归模板，状态/字段/水印归场景或 preset |
| 脚注/尾注 | `footnotes.xml`、`endnotes.xml` | thesis/journal/long doc/legal docs | CountProfile 是否计入必须明确 |
| 批注 | `comments.xml` | contract/technical/journal/bilingual/disclosure | 默认保护，不静默删除 |
| 修订 | `w:ins/w:del/w:moveFrom/w:moveTo` | contract/official/technical/disclosure | 运行前确认，必要时跳过高风险模块 |
| 文本框/shape | `w:txbxContent`、VML/WPS shape | form/bilingual/official | 预检、版位保护、避免粗暴重排 |
| 内容控件 | `w:sdt` | form/contract/official/HR | 字段映射、残留检查、保护策略 |
| 域代码/域结果 | `w:fldSimple`、`w:instrText`、`fldChar` | toc/caption/page/contract/disclosure | 更新/保留/跳过策略和报告证据 |
| 隐藏文字 | `w:vanish` | review/disclosure/legal | 预检和 CountProfile 是否计入 |
| 嵌入 Excel | `word/embeddings/*.xlsx` | finance/technical/disclosure | 默认保护或阻断，不能当普通表格改写 |
| OLE/Visio/嵌入包 | `embeddings`、relationships | technical/bidding/legacy templates | 预检、跳过、报告 |
| 宏 | `vbaProject.bin`、macro content type | 外来模板/合同/表单 | 默认阻断或人工确认 |
| package relationship | `.rels`、media、external links | 图片/附件/嵌入对象 | inventory、缺项、资料包复制和报告 |

CountEngine 目前已能读取 body、tables、headers、footers、footnotes、endnotes、comments、textboxes、hidden_text、tracked_changes、field_codes、field_results 等范围。V12 要求 CountProfile 不只声明指标，还要声明这些范围是否纳入，以及为什么纳入或排除。

## 8. 重点 family 的 first slice 规划

### 8.1 `contract_delivery`：优先从 L2 推到 L3

当前事实：

- `scene_family_application.py` 只支持 `contract_delivery` 的默认应用；
- 已能追加 `contract_parties_v1`、`signature_assets_v1`；
- 已能设置 `contract_fields` CountProfile；
- 已能生成 review/signing/field report preset；
- 对象预检策略已有合同专属 skip mapping。

L3 最小闭环：

1. ScenePanel 一键应用合同 profile 后，资料 schema、必填字段、签章角色、对象预检、交付 preset 全可见；
2. Workbench 运行前能提示 unknown/missing schema、缺签章、修订/批注/域风险；
3. 执行能输出审阅稿、签署稿、字段一致性报告；
4. 报告中明确“不提供法律意见，不判断条款有效性”；
5. 测试覆盖 registry、UI、runtime、报告和失败路径。

未闭合：

- 运行前 readiness/quick status 对 unknown MaterialSchema 的即时可见性已补第一版；
- 签章素材的真实性边界要在 UI/报告中更显式；
- 字段一致性还应从“计数/字段覆盖”向“重复字段值冲突”深化。

### 8.2 `form_batch_documents`：从行高问题切入

这是表格行高 `TableConfig.row_height_pt` 的真正落点。它不应回到通用模板里成为默认噪音，但必须进入固定版式和套打场景。

L3 first slice：

1. 支持 docx 固定模板 + xlsx/json 记录；
2. 字段映射支持段落占位符、表格单元格、内容控件，文本框先做预检提示；
3. 表格行高对应 `w:trHeight`，作为版位保护策略暴露；
4. 一记录一输出，失败隔离；
5. 残留占位符、空字段、行高被改写风险进入报告；
6. 不承诺替代表单系统，不承诺数据真实性。

控件要求：

- 行高使用与模板表格控件一致的数值 + 单位交互；
- 但标签必须说明“版位保护/场景覆盖”，避免用户误以为是普通表格美化；
- 特殊缩进、段距、左右缩进等同名段落参数必须复用模板管理控件。

### 8.3 `exam_teaching`：建立结构化事实源范式

外部试卷记录的关键原则应正式吸收：

```text
JSON 是事实源，Markdown 是人工预览，Word 是正式输出。
```

L3 first slice：

1. `Paper -> sections -> questions` 结构化 schema；
2. answer、analysis、knowledge_points 永远存在于事实源；
3. 学生版、教师版、答案版、解析版只通过 DeliveryPreset + visibility rules 控制显隐；
4. CountProfile 至少区分题型、题量、分值、公式、图片；
5. 报告说明“AI 内容质量不由核心承诺”；
6. 复杂几何图、电路图、结构式进入图片资产或插件。

### 8.4 `hr_batch_documents`：批量生成闭环

L3 first slice：

1. 人员 xlsx/json 作为多实体资料源；
2. 一条记录对应一份输出；
3. 每条记录的缺字段/缺头像/缺签名独立失败；
4. 成功产物和失败报告分开；
5. 最近结果和 artifact browser 按人员/profile 分组；
6. 不验证人员资格和背景真实性。

### 8.5 `project_application`：申报包与附件清单

L3 first slice：

1. 项目、团队、预算、成果和附件 schema；
2. 章节字数/字符数 profile；
3. 附件 inventory 与缺项报告；
4. 申报书、附件包、合规报告同源输出；
5. 不替代申报系统，不判断评审分数。

### 8.6 `bidding`：P0 入口的资料包深度化

当前 `bidding` 已是 P0 可执行入口，但成熟度仍受资料包和附件链路影响。

L4 方向：

1. `bid_materials_v1` 与 `qualification_archive_assets_v1` 可组合；
2. 正本/副本/资料归档包/缺项报告统一走 DeliveryPreset；
3. 资质 PDF/图片附件进入 material manifest；
4. 多公司/多项目批量时失败隔离；
5. 不判断投标策略、资质真实性和法律有效性。

### 8.7 `journal_en`：不要被 thesis 吞掉

L3 first slice：

1. journal profile registry；
2. BibTeX/CSL 解析和 citation 检查；
3. title/abstract/main text/references/display items 计数；
4. submission manuscript、review copy、cover letter、declaration package；
5. 不承诺出版社终版，不自动抓取未审核投稿规则。

### 8.8 `long_document_publishing` 与 `regulated_disclosure_documents`

这两类容易被 report、finance 或 technical 吞掉。V12 建议先不升顶层，但必须明确落点。

long doc first slice：

- chapter inventory；
- 目录/交叉引用/域保护；
- proof/review/final/archive preset；
- 不承诺出版社排版系统替代。

regulated disclosure first slice：

- 章节、表格、附件、批注 inventory；
- board review、public release、archive package；
- audit/legal/finance 专业判断全部外置。

## 9. 控件一致性硬规则

场景配置不是第二套模板管理。凡是同名参数，必须保持模板管理中的控件语言。

| 参数 | 场景配置要求 | 边界说明 |
| --- | --- | --- |
| 左缩进 / 右缩进 | 同行排布，名称、单位、步进与模板一致 | 只在“场景覆盖”区出现，不作为业务 profile 核心 |
| 段前 / 段后 | 同行排布，单位一致 | 不允许一个页面叫段前、另一个叫上间距 |
| 特殊缩进 | 必须可切换无/首行/悬挂，并联动数值启用状态 | 不能只是下拉展开后不可交互 |
| 行距类型 / 行距值 | 类型和值同组，固定值/倍数/最小值语义清楚 | Word 行距是组合语义 |
| 表格行高 | 普通模板默认隐藏或弱化；表单/套打场景作为版位保护 | 对应 `w:trHeight`，不是通用美化项 |
| 表格列宽/边框 | 与模板表格控件一致 | 场景覆盖必须说明业务理由 |
| 公式字体/字号/编号 | 外观控件复用模板；转换策略、低置信度归场景 | 不能只做字体项 |
| 水印字体/颜色/角度 | 外观复用模板控件 | 启用状态、正式/内部/审阅版本归场景和 preset |
| 输出目录/命名/产物 | 不归模板控件；归 DeliveryPreset/Workbench | 输出不是文档外观 |
| 风险策略 | 使用 summary、badge、确认区、报告解释 | 不伪装成普通 checkbox |
| 资料字段 | schema 驱动，支持字段/资产/附件角色 | 不用自由文本长期承载核心资料 |

验收公式：

```text
同名参数 = 同命名 + 同控件 + 同单位 + 同交互；
不同归属 = 明确显示“模板默认”或“场景覆盖”；
高风险项 = 必须进入预检或确认；
交付项 = 必须进入 DeliveryPreset，不进入模板。
```

## 10. 成熟度与准入门槛

| 等级 | 定义 | UI 可见 | 可执行 | 可对用户承诺 |
| --- | --- | --- | --- | --- |
| L0 | 只有需求想法 | 否 | 否 | 否 |
| L1 | registry 有 planning contract | 可在规划摘要中可见 | 否 | 否 |
| L2 | schema/profile/preset 至少一层落地 | 可作为推荐或受限预览 | 部分 | 只承诺规划方向 |
| L3 | first slice 有 UI、执行、报告、测试 | 是 | 是 | 可承诺受限能力 |
| L4 | 多工作流闭合，失败与边界可解释 | 是 | 是 | 可作为稳定能力 |
| L5 | profile 治理、批量、归档、插件边界长期稳定 | 是 | 是 | 可产品化推广 |

准入规则：

- L1 不得出现在顶层可执行导航；
- L2 可以在 ScenePanel 显示“推荐/规划族”，但不能冒充完整能力；
- L3 必须有 UI、runtime、pipeline/report、tests 四类证据；
- L4 必须有失败路径、跳过路径、边界声明；
- L5 必须有 profile 来源、版本、审核和跨版本回归。

## 11. 防遗漏检查表

任何新场景、profile、参数或功能进入设计前，必须逐项回答：

```text
1. 用户会自然怎么叫这件事？
2. 它是文档类型、工作流、资料 schema、交付 preset、模板参数、会话状态还是插件？
3. 它是否已经能被 P0/P1/P2 family 承载？
4. 如果不能承载，是新增 family、profile，还是插件边界？
5. 输入格式是什么，是否需要结构化事实源？
6. 需要哪些字段、图片、签章、附件、多实体资料？
7. 涉及哪些 Word story、OOXML 节点或 package part？
8. 需要哪些 CountProfile 指标和包含/排除范围？
9. 缺字段、缺资产、低置信度、高风险对象时如何处理？
10. 输出哪些版本、报告、对比稿、资料包或归档包？
11. UI、执行、报告、测试是否消费同一份配置？
12. 同名参数是否和模板管理保持同控件、同单位、同交互？
13. 是否涉及法律、财务、IP、审计、OCR、完整 LaTeX、AI 内容质量等外置边界？
```

任何一项无法回答，不能进入“完整场景能力”描述。

## 14. V12 最终结论

完善的高层场景能力矩阵不应追求“入口越多越完整”。它应该做到：

```text
少量稳定入口承接高频操作；
planning family 承接高频但未闭环的任务；
profile 表达同族差异；
MaterialSchema 管事实和资产；
CountProfile 管统计口径；
DeliveryPreset 管输出版本；
ObjectPreflight 管 Word 风险；
插件管高风险、窄领域、专业判断和外部导入。
```

当前高频大类已经基本有归属。真正要继续推进的是：

```text
把最常见的 P1/P1 candidate 从“有规划名”推进到“有 L3 first slice”；
把跨 family 的资料、计数、对象保护、显隐、多版本、批量和报告做成统一底座；
用控件一致性和测试证据防止模板、场景、资料、输出再次分裂。
```

V12 之后，判断一个场景是否完整，不再看它有没有名字，而看它是否有：

```text
唯一归属 + 明确边界 + 模型契约 + Word 风险面 + UI 控件一致性 + 执行报告 + 失败路径 + 测试证据。
```

## 15. Phase N2.53 Workbench unknown MaterialSchema 运行前可见性补记（2026-06-16）

## 16. Phase N2.54 Workbench 缺字段/缺资产 readiness 补记（2026-06-16）

本轮继续推进 N2.53 后的直接缺口：unknown schema 已经能在执行前显示，但资料包场景中更高频的失败其实是“schema 已注册，但本次资料没有填必填字段或没有提供必需资产角色”。此前这些问题主要由执行侧 material preflight 暴露，QuickExecution 状态仍缺少同一视角。

已落地内容：

- 新增共享 helper `material_readiness_reasons(scene, material_context)`；
- helper 复用 `evaluate_material_requirements()`，同时消费：
  - `InputSourceProfile.material_schema_id/material_schema_ids`
  - `required_material_fields`
  - `required_image_roles`
  - `MaterialExecutionContext.entity_data`
  - `MaterialExecutionContext.asset_items`
  - `MaterialExecutionContext.image_rules` 的必需资产角色；
- `material_schema_readiness_reasons(scene)` 保持为只检查 schema 注册的兼容 helper；
- legacy Workbench readiness 切到完整 `material_readiness_reasons()`；
- `QuickExecutionDetail` 新增 `set_material_context()`，状态区会随当前资料上下文刷新；
- `WorkbenchPanelV2` 在 bootstrap、bridge material context 变化、资料详情编辑写回时同步 QuickExecutionDetail；
- 新增测试锁定：
  - bidding 场景缺 `company_name/project_name/legal_person` 和 `logo/seal` 时展示 warning；
  - 填齐字段和资产后恢复就绪；

| 财务披露/IP/双语 | 报价、预算、年报、ESG、专利、双语审校 | P2 family 或插件 | 不做审计、法律、专利、翻译质量判断 |
| 导入和 AI | PDF/OCR、完整 LaTeX、AI 内容生成、复杂专业图 | 插件或输入助手 | 核心不承诺无损导入和内容质量 |

防遗漏裁决：

```text
一个用户高频说法找不到唯一场景包 = 覆盖遗漏；
能找到场景包但没有承载层 = 模型缺口；
有承载层但没有 UI/执行/报告/测试 = 不是完整能力；
涉及专业判断但没有插件或人工确认边界 = 越界承诺。
```

### 22.3 横切能力必须成网

高频场景不是单点功能，而是工作流组合。每个 L3 family 至少要声明以下能力轴中哪些是主轴、哪些是次轴、哪些明确不做：

| 能力轴 | 必须回答 | 典型场景 |
| --- | --- | --- |
| 输入事实源 | docx、json、xlsx、markdown、bibtex、latex 哪个是机器事实源 | exam、HR、project、journal |
| 模板基线 | 哪些外观归模板，哪些允许场景覆盖 | 所有场景 |
| 资料 schema | 字段、图片、签章、附件、多实体如何建模 | bidding、contract、HR、project |
| 结构定位 | 正文、摘要、参考文献、附录、文本框、页眉页脚如何纳入或排除 | thesis、journal、long doc |
| 内容显隐 | 同一事实源如何输出不同版本 | exam、contract、official、product |
| CountProfile | Word-like 与规则口径如何并列展示 | thesis、journal、project、exam |
| ObjectPreflight | 哪些 Word 对象触发阻断、跳过或人工确认 | technical、contract、finance、disclosure |
| DeliveryPreset | 输出哪些 docx、compare、report、manifest、zip | bidding、journal、project、contract |
| BatchPreset | 一记录一输出、失败隔离、产物分组 | HR、form、bidding |
| 插件边界 | OCR/AI/LaTeX/专业图/法律/财务/IP/翻译质量如何外置 | P2 与导入类 |

任何 family 如果只回答“文档类型”，没有回答这些能力轴，就仍是场景名，不是可验收能力。

### 22.4 两份参考文档的吸收规则

`count_engine_tech_record.md` 应吸收为 CountProfile 治理规则：

- 不能设计成单一“字数统计器”；
- 必须同时支持 Word-like、中文字符、汉字、英文词、含/不含空格字符、折算字数、参考文献、图、表、公式、段落、章节等多指标；
- 中文学位论文、英文期刊、学校系统、投稿系统必须用 profile 表达口径差异；
- UI 和报告必须显示计入口径、排除范围、profile 来源和“与官方系统可能不同”的边界；
- CountProfile 必须显式声明 Word story 范围，例如 body、tables、headers、footers、footnotes、endnotes、comments、textboxes、hidden text、tracked changes、field codes、field results。

`exam_generator_tech_stack_record.md` 应吸收为结构化事实源与同源多版本规则：

- AI 不直接生成 Word，AI 只能生成结构化 JSON，Markdown 只是预览和人工检查层；
- `Paper -> sections -> questions` 是试卷事实源，answer/analysis/knowledge_points 永远保留在结构化数据中；
- 学生版、教师版、答案版、解析版不能分别生成，必须由同一事实源通过 `DeliveryPreset + ContentVisibilityRule` 控制显隐；
- Word 母版渲染和 python-docx 后处理属于模板/执行层，不属于 AI 内容承诺；
- 通用图片、题图绑定、图片替换、公式处理是高频能力；复杂几何图、电路图、结构式和 AI 生图进入插件或图片资产边界。

### 22.5 边界裁决硬规则

以下边界后续不能再模糊：

| 易混边界 | 裁决 |
| --- | --- |
| 顶层入口 vs planning family | 只有 L3+ 且高频低歧义才允许升入口；L1/L2 不进可执行导航 |
| 文档类型 vs 工作流 | “合同/试卷/标书”是场景族，“多版本/批量/计数/导入”是工作流 |
| 模板 vs 场景 | 外观基线归模板；启用状态、风险策略、交付版本、资料契约归场景 |
| 资料 schema vs 当前资料 | schema 描述字段/资产角色；实际值归 MaterialExecutionContext |
| CountProfile vs 统计结果 | profile 描述口径；结果必须带 profile 来源、范围和差异说明 |
| DeliveryPreset vs OutputConfig | preset 描述业务版本；OutputConfig 是具体 artifact 开关 |
| Markdown 预览 vs 结构化事实源 | Markdown 只给人看，不能作为核心机器事实源 |
| ObjectPreflight vs 专业判断 | 对象预检只判断 Word 风险，不判断内容真实性、法律或财务结论 |
| 插件导入 vs 核心排版 | PDF/OCR/完整 LaTeX/AI 内容/复杂图形必须有低置信度和人工确认边界 |
| 控件复用 vs 新控件 | 同名参数必须复用模板管理控件语言；不同归属必须显示“模板默认/场景覆盖” |
