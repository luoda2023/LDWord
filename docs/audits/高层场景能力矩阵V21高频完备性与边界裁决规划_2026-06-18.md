# 高层场景能力矩阵 V21 高频完备性与边界裁决规划（2026-06-18）

## 1. 本轮目标

用户继续要求：高层场景能力矩阵不能停留在“已有功能点 + 若干缺口”的层面。真正要解决的是：

```text
高频适用场景不能漏；
相似场景边界不能含糊；
规划、UI、执行、报告和测试不能各说一套；
公式、输出、水印等先前暂缓项也必须进入场景板块的边界定义。
```

V21 在 V20 的基础上继续深化。V20 已经把 12 个 coverage pack、20 个能力槽位、Word/OOXML 风险面、控件契约和当前 P2 缺口梳理出来；V21 进一步回答：

```text
什么才算“完善的场景能力矩阵”？
每个高频自然请求落到哪里？
哪些 planned family 目前只有规划没有执行默认？
哪些 count profile 在 registry 声明和真实注册之间断链？
哪些场景应进入核心，哪些只能进入 profile、delivery preset、资料包或插件人工门？
下一轮实现如何避免继续遗漏？
```

## 3. 总判断

### 3.1 顶层 pack 不宜继续膨胀

当前 12 个 coverage pack 仍然是合理上限：

```text
quick_formatting
chinese_academic
english_journal
exam_education
bidding_materials
official_policy
technical_long_docs
application_reports
contract_delivery
batch_forms
professional_disclosure
import_ai_boundary
```

它们覆盖了用户的主任务心智。继续新增顶层入口会让导航膨胀，并重新制造“模板、场景、资料包、输出、插件”混在一起的问题。

V21 的方向不是加更多顶层场景，而是：

```text
顶层 pack 稳定；
pack 内子场景完整；
profile / material schema / count profile / delivery preset 足够细；
自然语言别名能路由；
边界冲突有裁决规则；
执行闭环能被测试证明。
```

### 3.2 当前最真实的断链不是“有没有名字”，而是“有没有全链路”

本轮静态比对发现两类高层断链：

| 断链类型 | 当前事实 | 风险 |
| --- | --- | --- |
| planned family 声明了 count profile，但 `count_profiles/builtin.json` 缺注册 | N2.127 已注册 `batch_item_inventory`、`chapter_inventory`、`finance_attachment_inventory`、`patent_section_inventory`，并新增静态 parity test | 当前已闭合；后续新增 family 时由测试防止回归 |
| planned family 已入 coverage pack，但 `scene_family_application.py` 尚无默认应用函数 | N2.128 已补 `hr_batch_documents`、`form_batch_documents`、`finance_quote_documents`、`bilingual_translation_documents` 默认应用；`ip_patent_documents` 明确为 plugin/manual-only | 当前已闭合为“可执行 defaults 或明确边界”二选一，由 parity test 防止回归 |

这说明“功能点不完善”的关键，不只是某个按钮没做，而是规划层、registry 层、默认应用层、运行层之间还没有形成统一准入标准。

## 4. 完整场景的定义

一个场景能力不能只满足“有一个开关”或“有一个模板”。V21 定义一个完整场景必须具备 12 项契约：

| 契约 | 必须回答的问题 | 典型落点 |
| --- | --- | --- |
| 高频别名 | 用户自然会怎么说？ | coverage pack `natural_requests`、后续 router |
| 归属裁决 | 落到哪个 pack/family/profile？ | `scene_coverage_manifest.py`、`scene_family_registry.py` |
| 事实源 | 机器可信数据来自哪里？ | docx、JSON、XLSX、MaterialSchema、BibTeX/CSL |
| 模板基线 | 外观由哪个模板决定？ | `TemplateConfig`、compatible template |
| 场景策略 | 哪些模块启用、跳过、阻断？ | `SceneWorkspace`、module switches |
| 资料包 | 哪些字段、图片、附件必需？ | `material_schema_registry.py` |
| 计数/清单口径 | 字数、附件、章节、对象如何统计？ | `CountProfile` 或专用 inventory evidence |
| Word 风险面 | 会碰哪些 OOXML surface？ | object preflight、risk surface registry |
| UI 投影 | 用户能否看懂当前会做什么？ | ScenePanel summary/detail |
| 交付 preset | 输出哪些版本和包？ | `DeliveryPreset`、`OutputConfig` |
| 报告/问题中心 | 风险、缺项、边界是否可追踪？ | JSON/Markdown report、issue queue |
| 测试证据 | registry/UI/runtime/report 是否有断言？ | pytest |

缺任一项，都只能算“规划切片”或“能力组合草稿”，不能算完整场景。

## 6. Pack 内子场景完备矩阵

### 6.1 `quick_formatting`

必须覆盖：

- 普通文档套模板；
- 格式清洗；
- TOC/PAGE/REF 字段修复；
- 审阅前对象风险检查；
- final/report/compare 基础交付。

边界：

- 不判断专业合规；
- 不替代论文、标书、公文等 profile；
- 不静默处理 OLE/VBA/修订/批注。

当前状态：

- 主链已闭合；
- 后续重点是自然语言 router 和更多 OOXML 风险 repair，不是新增入口。

### 6.2 `chinese_academic`

必须覆盖：

- 本科/硕士/博士论文；
- 课程论文、开题、综述；
- 学校字数、摘要、图表公式、参考文献数量；
- 参考文献引用置信度；
- 公式转换置信度；
- final/review/compliance report。

边界：

- 不吸收英文期刊投稿包；
- 不承诺所有学校规则天然内置；
- 不把完整 LaTeX 工程转换作为核心能力。

当前高层缺口：

- 学校规则来源治理还应继续做；
- 公式/引用的深度执行能力仍是后续 L4/L5；
- 需要自然语言 router 区分“课程论文”与“期刊投稿”。

### 6.3 `english_journal`

必须覆盖：

- manuscript；
- cover letter；
- declaration；
- highlights；
- supporting information；
- response/revision；
- BibTeX/CSL；
- display items；
- Journal profile rule source governance。

边界：

- 不承诺出版社最终出版版式；
- 不自动执行未审阅期刊规则；
- 不替代 EndNote/Zotero；
- 完整 LaTeX 工程进入导入/插件边界。

当前状态：

- 规则来源治理、投稿包、BibTeX/CSL first slice 已闭合；
- 后续完善应放在 profile 更新流程、真实期刊规则包和更细 display item 检查。

### 6.4 `exam_education`

必须覆盖：

- 结构化题源；
- 题型、分值、答案、解析 schema validation；
- 学生版、教师版、答案版、解析版；
- 答题卡；
- 题图、公式、通用图表；
- 同一事实源多版本输出。

边界：

- AI 生成题目质量不属于核心；
- 复杂几何图和学科专用图形进入插件；
- 不允许学生版和教师版来自两次独立生成。

当前高层缺口：

- 学科图形插件边界已登记，但真实插件能力未实现；
- 答题卡的固定版位与 `w:trHeight` 应复用 fixed-layout 契约，不回流普通 TableConfig。

### 6.5 `bidding_materials`

- Logo/签章/附件资料包；

当前状态：

## 7. 跨场景边界裁决表

| 冲突 | 裁决 |
| --- | --- |
| 产品手册 vs 技术手册 | 面向客户方案/销售包归 `application_reports/product_sales_documents`；面向操作、接口、SOP 归 `technical_long_docs` |
| 白皮书 vs 项目申报 | 面向客户/市场/产品归 product/pre-sales；面向评审系统、分节限字、附件包归 project application |
| 报价单 vs 售前方案 | 报价金额、预算附件归 `professional_disclosure/finance_quote_documents`；方案正文和产品资产归 product/pre-sales |
| 会议纪要 vs 普通报告 | 行政会议、文号、归档、水印归 `official_policy`；普通会议总结可归 `quick_formatting` 或 `application_reports` |
| 证书/奖状 vs 资质证照 | 套打生成证书归 `batch_forms`；投标资质证照归 `bidding_materials/qualification_archive_packages` |
| 课程论文 vs 英文期刊 | 学校/课程要求归 `chinese_academic`；出版社/期刊投稿包归 `english_journal` |
| 讲义 vs 试卷 | 有题源、答案、解析、多版本归 `exam_education`；普通教学资料整理可归 `quick_formatting` 或 `technical_long_docs` |
| 合同审阅 vs 法律审查 | 字段、修订、交付包归 `contract_delivery`；法律结论进入专业插件/人工确认 |
| ESG 年报 vs 长文档 | 长章节和审阅定稿能力可复用 `technical_long_docs`；披露边界和归档包归 `professional_disclosure` |
| PDF 转 Word 后排版 | 先 `import_ai_boundary` 形成置信度和人工确认，再进入目标 pack |
| LaTeX 公式 vs LaTeX 工程 | 公式片段可进入目标场景；完整工程进入导入插件边界 |
| 水印视觉 vs 状态水印 | 字体/角度/颜色是控件契约和视觉基线；“内部传阅/征求意见/归档版”是场景/交付状态 |

## 8. 公式、输出、水印的场景归属

此前用户暂时说公式/输出/水印先不管，但进入场景定义后，这三类必须纳入高层矩阵。

### 8.1 公式

归属拆分：

| 内容 | 归属 |
| --- | --- |
| 是否处理 LaTeX 片段、低置信度如何处理 | Scene |
| 公式字体、字号、行距等视觉基线 | Template 或模板控件契约 |
| 数学、物理、化学、复杂图形生成 | Plugin / Manual Gate |
| 公式转换结果和失败样例 | Report / issue queue |

验收要求：

- 场景摘要显示公式策略；
- 执行报告显示低置信度、跳过、fallback；
- 完整 LaTeX 工程不应被描述为核心能力。

### 8.2 输出

归属拆分：

| 内容 | 归属 |
| --- | --- |
| final/review/compare/archive/student/teacher/customer/internal | DeliveryPreset |
| 具体文件名、目录、是否生成资料包 | OutputConfig / DeliveryPreset |
| 本次输出目录 | Session |
| 输出产物可打开、可定位 | Workbench artifact browser |

验收要求：

- 输出不是一个全局开关，而是场景语义 preset；
- 多版本必须来自同一事实源；
- manifest/package/report 彼此引用一致。

### 8.3 水印

归属拆分：

| 内容 | 归属 |
| --- | --- |
| 征求意见稿、内部传阅、归档版等状态 | Scene / DeliveryPreset |
| 水印颜色、字号、角度、透明度 | 控件契约或模板视觉基线 |
| 是否对每个 preset 生成不同水印 | DeliveryPreset |
| 水印与页眉页脚、section 的 OOXML 风险 | ObjectPreflight / report |

验收要求：

- 场景页必须把水印当状态策略展示；
- 不把水印塞进页眉页脚外观配置里混淆；
- 报告说明是否写入、写入哪些 preset。

## 13. 最终结论

“完善的高层场景能力矩阵”不是把所有高频词都变成顶层按钮，而是让每个高频词都有稳定落点、每个落点都有事实源、规则口径、输出语义、Word 风险策略和报告证据。

V21 后续执行的核心顺序应为：

```text
1. 扩展公式、输出、水印、插件门的控件契约；
2. 把 issue queue repair routing 接到模板、资料包、输出、对象预检和插件门；
3. 让 Workbench/ScenePanel 消费 natural request route payload；
4. 用静态审计和 runtime/report 测试防止新增断链。
```

只要继续用这套标准推进，就不会因为场景名看似很多而实际缺链，也不会把高频但高风险的需求误包装成核心承诺。
