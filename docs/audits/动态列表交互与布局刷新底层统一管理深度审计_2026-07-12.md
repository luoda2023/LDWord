# 动态列表交互与布局刷新底层统一管理深度审计

> 实施状态（2026-07-12）：本审计提出的 P0、P1、P2 迁移及后续全项目复扫缺口均已完成。第 3～8 节保留的是改造前证据与决策过程，最终实现和验收结果见第 11 节。

- 日期：2026-07-12
- 范围：`src/ui`、`src/shared/ui`
- 起因：公文资料字段新增/删除后，滚动页面仍出现瞬时跳动
- 审计目标：判断该问题是否为单点缺陷，并评估是否需要从项目层统一动态列表、布局事务和刷新调度

## 1. 执行结论

结论分为三层：

1. 公文资料字段的跳动是结构性缺陷，不是动画、显卡或单个滚动值问题。
2. 相同的“清空控件 → 全量重建 → 延迟布局 → 再修正几何”模式在项目内多处存在，公文资料区只是第一个被明显感知的场景。
3. 有必要重构一部分底层能力，但不建议把所有界面强制迁移到一个巨型列表框架。应统一三项基础设施：
   - 稳定键驱动的增量控件列表；
   - 带视口锚点的同步布局事务；
   - 按“结构、数值、摘要、外部持久化”分级的刷新调度。

优先级建议：

- P0：公文资料字段、共享 `SummaryGrid`、视口布局事务；
- P1：页码编号分组的复制/移动、工作台自由字段、资料包份数列表；
- P2：主题卡片、素材槽位、证据行等低频动态集合；
- 暂不统一：分页按钮、抽屉内容替换、主面板切换、普通 `QTableWidget` 数据刷新。

## 2. 本次方法

本次审计没有只做关键词判断，而是采用三步法：

1. 静态扫描动态 UI 模式；
2. 对高风险交互追踪调用链和布局链；
3. 对公文字段新增/删除做事件循环级运行诊断，记录滚动值、锚点坐标、滚动范围和外层内容高度。

扫描命中概况如下。这里的“命中”包含定义、导入和调用，目的是反映模式扩散范围，不等同于缺陷数量。

| 模式 | 涉及文件 | 扫描命中 |
|---|---:|---:|
| `while layout.count()` 清空布局 | 10 | 13 |
| `setParent(None)` 脱离控件树 | 12 | 20 |
| `deleteLater()` 延迟销毁 | 20 | 30 |
| `refresh_layout_chain_later` | 15 | 44 |
| `updates_suspended` | 12 | 32 |
| `QTimer.singleShot(0, ...)` | 12 | 14 |
| `setRowCount(...)` | 8 | 8 |

这些 API 本身都不是错误。风险来自以下组合：

```text
用户在当前滚动页执行 CRUD
  + 清空并重建整个控件集合
  + 重新创建正在触发信号的发送者
  + 同步和延迟布局并存
  + 外层滚动容器另有一套延迟几何同步
  + 最后用 QTimer 修正滚动位置
```

## 3. 公文资料字段：已确认的根因

### 3.1 当前调用链

新增同类字段：

```text
点击某行“＋”
→ _add_official_series_field
→ 修改 profile.field_scopes
→ _refresh_official_fields_preserving_view
→ _refresh_summary
→ _refresh_field_statuses
→ _refresh_official_field_editor
→ 清空固定字段布局
→ 清空自由字段布局
→ 重建全部字段行
→ 同步刷新布局链
→ 延迟刷新布局链
→ 延迟恢复滚动值
→ 外层 ScrollableDetailGeometrySync 再次同步高度
```

关键位置：

- `src/ui/panels/assets/field_status_presenter.py:445`
- `src/ui/panels/assets/field_status_presenter.py:930`
- `src/ui/panels/assets/section_summary_presenter.py:70`
- `src/shared/ui/detail_geometry.py:11`

删除字段没有进入 `_refresh_official_fields_preserving_view`，而是直接调用 `_refresh_summary()`：

- `src/ui/panels/assets/field_status_presenter.py:1010`

因此删除路径没有完整的锚点保护。

### 3.2 事件级实测

诊断环境：离屏 Qt，窗口 `1280 × 700`，滚动值主动设置为 `180`，在自由字段区为“主送机关”新增同类字段。

| 时刻 | 滚动值 | 滚动最大值 | 锚点在视口中的 Y | 外层内容高度 |
|---|---:|---:|---:|---:|
| 新增前 | 180 | 218 | 317 | 918 |
| 同步重建结束 | 180 | 218 | 79 | 918 |
| 下一事件循环 | 0 | 218 | 476 | 918 |
| 外层几何同步后 | 0 | 275 | 497 | 975 |

一次新增实际出现了三个中间状态：

```text
原位置
→ 全量重建后的临时位置
→ 错误滚动补偿归零
→ 外层高度最终稳定
```

这证明当前“保护视图”逻辑不是保护，而是在不稳定布局上计算了错误补偿。

### 3.3 为什么会把 180 恢复成 0

当前代码在内容容器坐标系中记录锚点，并在字段行刚刚重建后立刻再次读取锚点位置。

此时新行布局还没有完成外层高度同步，锚点临时上移约 238 px。算法得到：

```text
目标滚动值 = 180 + 临时坐标差(-238) = -58
```

随后被限制到滚动条最小值 `0`。

等下一事件循环真正恢复了内容高度，代码已经不再做第二次正确补偿，因此最终留在顶部。

### 3.4 发送者在自己的点击回调中被拆掉

新增同类字段时，当前实现会清空两个分区。用户正在点击的“＋”按钮所属行也会立即 `setParent(None)`，再 `deleteLater()`。

因此点击信号还未完全退出，发送者已经：

- 离开控件树；
- 失去焦点；
- 触发布局收缩；
- 等待延迟销毁。

新增一行不应销毁源行。这是控件身份没有被稳定管理的直接证据。

### 3.5 旧测试为何没有暴露问题

现有测试使用 `ensureWidgetVisible()`，但目标字段原本已经位于视口内，滚动值通常保持为 `0`。测试还会先处理完全部异步事件，再检查最终坐标。

它没有覆盖：

- 非零滚动值；
- 中间帧；
- 滚动值错误归零；
- 外层内容高度的第二轮变化；
- 删除路径；
- 已存在控件的对象身份。

## 4. 项目级风险分级

### 4.1 P0：需要作为底层重构入口

#### A. 公文资料字段列表

文件：

- `src/ui/panels/assets/field_status_presenter.py`

问题：

- 任意结构变化重建固定和自由两个分区；
- 新增时销毁源行；
- 删除没有锚点事务；
- 结构变化通过全量 `_refresh_summary()` 扩散到整个资料面板；
- 布局稳定、滚动恢复和绘制恢复不在同一事务内。

结论：必须增量化，不能继续增加定时器补丁。

#### B. 共享 SummaryGrid / TemplateSummaryCard

文件：

- `src/shared/ui/summary_grid.py:440`
- `src/shared/ui/summary_grid.py:466`
- `src/shared/ui/template_summary_card.py:88`

问题：

- 每次 `set_items()` 都删除全部 tile 并重建；
- 即使 item key、列数和控件结构完全没有变化，也不更新原控件；
- 每次重建都会刷新父布局链；
- `TemplateSummaryCard` 还会再排队一次高度同步；
- 资料面板 `_refresh_summary()` 会更新全部分区的摘要卡片，包括隐藏分区。

影响：

- 它不是唯一跳动源，但会放大任何局部刷新；
- 同类模式被场景面板、模板详情、样式管理和资料面板共同使用；
- 这是最有项目级收益的共享改造点。

建议：改为按 `SummaryGridItem.key` 增量更新 tile；只有列跨度或顺序发生变化时才移动布局项。

#### C. 视口布局事务缺失

文件：

- `src/shared/ui/layout_sync.py`
- `src/shared/ui/detail_geometry.py`

现状：

- `updates_suspended` 只负责关闭和恢复绘制；
- `refresh_layout_chain_later` 只负责延迟执行多轮布局；
- `ScrollableDetailGeometrySync` 只负责外层内容高度；
- 三者不知道滚动锚点，也没有统一提交时机。

结果：业务代码只能自行组合这些低层工具，容易出现：

```text
恢复绘制早于布局稳定
滚动补偿早于外层高度同步
同步布局和延迟布局重复执行
```

结论：需要新增真正的“视口布局事务”，而不是继续扩充业务层滚动补丁。

### 4.2 P1：高价值迁移对象

#### A. 页码编号分组的复制和移动

文件：

- `src/ui/panels/template_elements_page_plan.py:719`
- `src/ui/panels/template_elements_page_plan.py:975`
- `src/ui/panels/template_elements_page_plan.py:991`

现状：

- 普通“添加”和“移除”已经部分采用增量逻辑；
- “复制”和“上移/下移”却重新序列化所有配置，再清空重建全部分组；
- 重建后执行同步布局和延迟布局；
- 每个分组都是较高的可折叠表单，重建成本和视觉位移都较大。

这是一个很有代表性的“同一组件内 CRUD 策略不一致”问题。

建议：

- 复制：创建一个新 row，插入目标 row 后；
- 移动：移动现有 widget 和 controls 对象，不重新创建；
- 只更新序号、按钮可用状态和标题；
- 使用统一视口事务保持当前分组位置。

#### B. 工作台自由字段

文件：

- `src/ui/panels/workbench/quick_execution_detail.py:512`

现状：每次外部 `MaterialExecutionContext` 更新都会清空并重建全部自由字段。

本地输入通过同步保护避免了立刻反向重建自己，因此风险低于公文资料区。但当资料区、文种或外部上下文改变时，如果工作台正在显示，仍可能出现整卡跳动和焦点丢失。

建议：复用同一个稳定键列表控制器，key 使用字段内部 key。

#### C. 资料包份数列表

文件：

- `src/ui/panels/assets/profile_presenter.py:67`

现状：新增、复制、删除一份资料都会清空 `QListWidget` 并重新添加全部 item，然后重新选择和刷新整个资料摘要。

这里不需要 QWidget 列表控制器，应直接使用 `QListWidget.insertItem()`、`takeItem()` 或迁移到模型 API。

#### D. 普通资料字段建议区

文件：

- `src/ui/panels/assets/field_status_presenter.py:235` 附近

现状：新增、删除或扫描字段变化时清空并重建全部建议行。它与公文资料字段位于相同滚动外壳，也使用绘制暂停和延迟布局。

建议：与公文字段共用稳定键列表能力，但保留不同 row builder。

### 4.3 P2：适合后续迁移

#### A. 自定义主题卡片

文件：

- `src/ui/panels/theme_panel.py:710`

新增或删除一个主题时，全部自定义主题卡片都会销毁和重建。该区域是 FlowLayout，卡片数量通常较少，风险不如滚动长表单高，但增量插入/删除实现成本也很低。

#### B. 素材槽位和附件槽位

文件：

- `src/ui/panels/assets/scene_spec_presenter.py:216`
- `src/ui/panels/assets/scene_spec_presenter.py:245`

目前在场景或 schema 变化时整组重建。因为这里通常代表上下文整体切换，全量重建在语义上可以接受；但若未来允许用户在当前页直接新增/删除素材位，应提前迁移到稳定键 reconcile。

#### C. EvidenceLineList

文件：

- `src/shared/ui/evidence_widgets.py:137`
- `src/shared/ui/evidence_widgets.py:154`

每次 `set_items()` 都重建全部证据行，且场景面板多处频繁调用。证据行通常较短，不是当前首要视觉风险，但可在 SummaryGrid 改造后采用相同的 keyed reconciliation 思路。

#### D. 最近运行产物列表

文件：

- `src/ui/panels/workbench/recent_run_panel.py`

选择不同运行记录时，产物列表整体内容本来就变化，重建是合理的。只有未来支持在当前记录内流式追加产物时，才需要改为增量追加。

### 4.4 暂不纳入统一重构

以下场景虽然使用 `clear()`、`deleteLater()` 或 `setRowCount()`，但语义与滚动 CRUD 不同：

- 主窗口替换整个面板；
- 抽屉替换整块内容；
- 分页按钮重建；
- 下拉框选项重载；
- 切换运行记录后替换完整详情；
- `QTableWidget` 设置新数据集；
- 对话框关闭后的控件销毁。

这些操作本身就是“替换上下文”，不需要为了形式统一而强行增量化。

## 5. 项目里已经存在的正确方向

统一重构不需要从零设计。项目中已有可参考实现。

### 5.1 ConfigListWidget

文件：

- `src/shared/ui/config_list_widget.py:103`
- `src/shared/ui/config_list_widget.py:115`

它使用稳定 `config_id` 保存 card：

```text
新增 → 只创建一张 card
删除 → 只 remove 对应 card
过滤 → 只切换可见性
```

这是公文字段列表应采用的核心模式。

### 5.2 页码分组的普通添加/移除

同一个 `template_elements_page_plan.py` 中，普通添加和移除已经会操作单个 row，说明该组件具备增量改造基础。问题只在复制和移动又退回全量重建。

### 5.3 DynamicNavigationRail 等稳定集合

项目中已有按 ID 维护导航卡片、按需插入和移除的组件。这证明团队代码风格可以接受稳定对象身份，不必依赖全量 rebuild。

## 6. 建议新增的三项底层能力

### 6.1 KeyedWidgetListController

职责：管理“有稳定 key 的 QWidget 行集合”。

建议接口概念：

```python
controller = KeyedWidgetListController(
    layout=layout,
    create_widget=create_row,
    update_widget=update_row,
    dispose_widget=dispose_row,
)

controller.reconcile(items, key=lambda item: item.key)
controller.insert(index, item)
controller.remove(key)
controller.move(key, target_index)
```

必须保证：

- 相同 key 的 widget 身份不变；
- 只创建新增 key；
- 只销毁被移除 key；
- 顺序变化时移动已有 layout item；
- 支持更新后续序号，但不重建行；
- 能返回新增、删除、移动和保留 key 集合，便于测试和日志。

适用：

- 公文固定/自由字段；
- 普通资料字段建议；
- 工作台自由字段；
- 页码编号分组；
- EvidenceLineList；
- 主题卡片。

不适用：

- `QListWidget`、`QTableView` 的模型数据；
- 完整详情页替换；
- 无稳定 key 的瞬时装饰控件。

### 6.2 ViewportMutationTransaction

职责：将一次滚动区结构变化变成同步、不可见中间态的提交。

建议流程：

```text
选择稳定锚点
→ 记录锚点相对 viewport 的坐标
→ 关闭 viewport 和内容绘制
→ 执行增量结构变化
→ 激活局部布局
→ 同步执行外层 geometry sync
→ 计算锚点的新 viewport 坐标
→ 在恢复绘制前同步修正滚动值
→ 恢复绘制并只 update 一次
```

建议 API 概念：

```python
with viewport_mutation(
    scroll=detail_scroll,
    content=detail_page,
    anchor=surviving_widget,
    layouts=(field_layout,),
    geometry_sync=detail_geometry,
):
    controller.insert(index, item)
```

关键约束：

- 不允许使用 `QTimer` 完成正确性补偿；
- `QTimer` 只能用于非关键摘要合并；
- 锚点坐标必须相对 `scroll.viewport()`；
- 删除当前行时必须提前选下一行、上一行或分区标题作为 surviving anchor；
- 外层高度同步必须发生在恢复绘制之前。

### 6.3 分级刷新调度

当前 `_refresh_summary()` 同时承担模型投影、字段结构、预览、素材、导航和摘要更新。建议把刷新原因显式化：

```python
RefreshScope.STRUCTURE
RefreshScope.VALUES
RefreshScope.SUMMARY
RefreshScope.PREVIEW
RefreshScope.ASSETS
RefreshScope.PERSISTENCE
```

示例：

```text
新增字段
→ STRUCTURE（同步）
→ SUMMARY | PREVIEW（合并一次）
→ PERSISTENCE（一次）

编辑字段值
→ VALUES（同步更新当前行）
→ SUMMARY | PREVIEW（250ms 合并）
→ PERSISTENCE（防抖）
```

结构正确性不能依赖防抖；摘要和持久化可以防抖。

## 7. 不建议的方案

### 7.1 继续增加 QTimer

问题：事件顺序依赖 Qt 当前队列，外层 geometry sync、layout request 和滚动恢复可能互换顺序。

### 7.2 只冻结绘制更久

问题：冻结绘制不会阻止内容高度和滚动范围在后台经历错误状态，也不会修复错误锚点计算。

### 7.3 所有动态 UI 强制改成 QAbstractItemModel

问题：复杂表单行包含输入框、公式、菜单和可展开内容，不适合为追求统一而全部表格化。

### 7.4 做一个全局“万能刷新管理器”

问题：模型更新、布局事务、滚动锚点和持久化节流是不同职责。全部塞进一个全局单例会产生隐式依赖和更难追踪的刷新顺序。

建议统一协议和小型基础组件，不统一所有业务状态。

## 8. 分阶段落地建议

### 阶段 0：建立可证明的测试基线

先补测试，不先改行为：

- 非零滚动值新增字段不能归零；
- 新增后源 row 和源 button 对象身份不变；
- 删除后 surviving anchor 的视口 Y 不变；
- 固定区变化时自由区标题保持位置；
- 一次 CRUD 不出现中间 `valueChanged(0)`；
- 一次 CRUD 外层内容高度只提交一次稳定结果；
- 无关分区不能重建。

### 阶段 1：视口事务 + 公文字段增量化

- 新增 `ViewportMutationTransaction`；
- 为公文字段建立 row/index/button 字典；
- 新增、删除、撤销、同类复制全部走增量路径；
- 删除 `QTimer.singleShot(0)` 滚动补偿；
- 结构变化不再直接调用全量 `_refresh_summary()`。

### 阶段 2：SummaryGrid keyed reconciliation

- 相同 key 直接更新 tile 文本和样式；
- key 顺序变化时移动 tile；
- 列数或 span 变化时只重新布局，不重新创建 tile；
- 隐藏摘要卡片不执行高度同步；
- 汇总调用链中只更新发生变化的分区。

这是项目级收益最大的一步。

### 阶段 3：迁移高风险动态表单

- 页码编号分组复制/移动；
- 工作台自由字段；
- 普通资料字段建议区；
- 资料包份数列表使用 QListWidget 增量 API。

### 阶段 4：迁移低频集合

- 自定义主题卡片；
- EvidenceLineList；
- 在当前上下文内允许动态变化的素材槽位。

## 9. 验收标准

### 9.1 用户体验

- 新增后当前字段、鼠标位置和滚动位置不跳；
- 删除后相邻字段留在原位置；
- 输入焦点不丢失；
- 不出现先收缩再展开的一帧；
- 不出现滚动条先变短再变长；
- Toast 不参与页面布局。

### 9.2 控件身份

- 未变化 key 的 widget 对象地址保持不变；
- 新增一个 item 只创建一个 row；
- 删除一个 item 只销毁一个 row；
- 移动 item 不销毁 widget。

### 9.3 事件与性能

- 一次结构操作只提交一次外层稳定高度；
- 不出现错误的中间滚动值；
- 不调用隐藏分区的大型 rebuild；
- 不在发送者点击回调中销毁发送者，除非操作本身就是删除该发送者；
- `QTimer.singleShot(0)` 不用于滚动正确性。

### 9.4 兼容性

- 内部字段 key、别名、公式、固定/自由 scope 不变化；
- 资料包序列化格式不因 UI 控件管理重构而改变；
- 旧资料包和旧模板继续可用；
- 批量生成和单次生成只消费模型，不依赖 widget 实例。

## 10. 最终判断

需要重构，但重构对象应是“动态交互基础设施”，而不是整个项目 UI。

当前项目已经出现两种并存风格：

```text
稳定 key + 单项增删
```

以及：

```text
状态变化 + 清空全部控件 + 全量 rebuild + 延迟修正
```

前者适合持续交互，后者只适合真正的上下文整体替换。当前若干界面把后者用于新增、删除、复制和移动，所以发生跳动、失焦和布局重复计算。

推荐的项目级方向不是“禁止 rebuild”，而是建立明确规则：

> 同一视口内、用户可感知的 CRUD 必须增量；上下文整体切换可以重建；任何会改变滚动内容高度的 CRUD 必须在一个同步视口事务中提交。

按照该边界推进，可以先彻底解决公文资料区，再把已经确认的高风险交互逐步迁移，不需要进行高风险的大爆炸式重写。

### 11.3 删除抖动的最终根因与结果

新增路径稳定后，严格删除测试又发现两层延迟因素：

1. QWidget 移除会排队 `QEvent.LayoutRequest`，事务如果在该事件派发前测量，会看到旧几何；
2. 外层详情容器把上一次内容高度写入 `minimumHeight`，收缩时会用旧高度反向影响新的 `sizeHint()`。

最终处理是：事务提交前只同步派发 LayoutRequest，再由几何同步器清除旧最小高度并重新测量，随后在恢复绘制前修正滚动值。

页码 6 行删除实测：

| 时刻 | 滚动值 | 最大值 | surviving anchor Y |
|---|---:|---:|---:|
| 删除前 | 2107 | 2897 | 335 |
| 同步删除提交后 | 1756 | 2546 | 335 |
| 后续 8 个事件循环 | 1756 | 2546 | 335 |

公文字段和普通资料字段也均覆盖：非零滚动、删除前后未变行对象身份、锚点漂移不超过 1 px、`valueChanged` 不出现 0。

### 11.4 分级刷新已落地

资料面板的刷新调度现区分：

- `fields`：字段状态、预览、导航摘要；
- `full`：再包含素材表、历史表、批量投影等完整刷新。

高频字段输入只触发合并后的 field-only projection；如果同一窗口内出现 full 请求，full 会覆盖 pending fields 请求。结构正确性仍同步完成，摘要投影可以合并。
