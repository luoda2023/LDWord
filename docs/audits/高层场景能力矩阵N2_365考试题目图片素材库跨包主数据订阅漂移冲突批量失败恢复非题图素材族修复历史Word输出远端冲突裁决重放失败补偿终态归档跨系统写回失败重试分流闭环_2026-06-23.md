# 高层场景能力矩阵 N2.365 考试题目图片素材库跨包主数据订阅漂移冲突批量失败恢复非题图素材族修复历史 Word 输出远端冲突裁决重放失败补偿终态归档跨系统写回失败重试分流闭环

日期：2026-06-23

## 背景

N2.364 已把 cross system writeback receipt 后的 external status proof 首片打通：manual dead-letter、authorization refresh、remote snapshot review 都可以被登记为外部状态证明，并留下 failure retry split required、final external confirmation required、manifest 与 metadata。

N2.365 闭合的是 terminal archive cross system writeback failure retry split 首片。它不声明失败重试已经真实执行、不声明 no-retry archive 已经最终归档，也不声明外部系统最终确认已经完成；本轮只承诺 proof items 可以被前台显式登记为失败重试分流事实，并把每个 item 拆成 retry required、manual retry required、authorization retry required 或 no-retry archive required。

## 本轮闭合内容

1. `AssetsPanel` 新增 cross system writeback failure retry split 输出目录、record finder、split item 派生、artifact/record 构造和 metadata 回写。
2. cross system writeback external status proof 后表格动作从只保留 `Manifest` 推进为 `Split` + `Manifest`；执行 `Split` 后状态推进为 `split`，动作收敛为 `Manifest`。
3. `locate_manifest` 优先打开 failure retry split manifest，再回退到 proof、receipt、writeback、post release dashboard、release confirmation、release handoff、closure report 和更早阶段 manifest。
4. manual dead-letter proof item 被分流为 `manual_dead_letter_failure_retry_split_recorded`，并留下 `manual_retry_required`、`failure_retry_execution_required` 与 `manual_dead_letter_failure_retry_execution`。
5. authorization refresh proof item 被分流为 `authorization_refresh_failure_retry_split_recorded`，并留下 `retry_required`、`authorization_refresh_retry_execution_required` 与 `authorization_refresh_failure_retry_execution`。
6. remote snapshot proof item 被分流为 `remote_snapshot_failure_retry_split_recorded`，并留下 `retry_not_required`、`remote_snapshot_no_retry_archive_ready` 与 `no_retry_archive_required`。
7. maturity/readiness 将 cross system writeback failure retry split UI bridge 移入 evidence，并把剩余 L5 blocker 推进为 terminal archive cross system writeback failure retry execution UI。

## 链路变化

N2.365 后链路变为：

`terminal archive` -> `durable scheduler` -> `execution monitor` -> `result finalization` -> `final closure audit` -> `closure report` -> `release handoff` -> `release confirmation` -> `post release dashboard` -> `cross system writeback` -> `cross system writeback receipt` -> `cross system writeback external status proof` -> `cross system writeback failure retry split`

状态投影变为：

`archived` -> `scheduled` -> `monitored` -> `finalized` -> `closed` -> `reported` -> `handoff` -> `confirmed` -> `dashboard` -> `writeback` -> `receipt` -> `proof` -> `split`

## 边界

这个链路把“外部状态证明已记录”推进为“失败重试分流已记录”。它仍然保留明确边界：本轮不执行重试、不触发真实外部连接器、不把 no-retry archive 视为已经归档、不把 final external confirmation ready 等同于外部系统最终完成态。下一轮应处理 failure retry execution，把 retry-required items 接入执行入口，并把 no-retry archive 与 final external confirmation 拆成可审计的后续节点。

## 矩阵迁移

本轮将以下 evidence 纳入 `exam_education` pack 与 `exam_teaching` family：

- `question asset per-question asset library cross-package master subscription drift conflict batch failure recovery non-question asset family repaired historical Word output remote conflict decision retry replay failure compensation terminal archive cross system writeback failure retry split UI bridge`

剩余 gap 从 cross system writeback failure retry split 推进为：

- pack：`advanced question asset library cross-package asset master data subscription drift conflict batch failure recovery non-question asset family repaired historical Word output remote conflict decision retry replay failure compensation terminal archive cross system writeback failure retry execution UI`
- family：`advanced asset library cross-package asset master data subscription drift conflict batch failure recovery non-question asset family repaired historical Word output remote conflict decision retry replay failure compensation terminal archive cross system writeback failure retry execution UI`

这意味着 cross system writeback failure retry split UI 已从 L5 blocker 中移出。后续不应再把“缺少分流入口”作为开放缺口；真正未完成的是失败重试执行、无需重试归档落地、最终外部确认和真实外部运营系统完成态回流。

## 控件一致性

cross system writeback failure retry split 继续沿用场景矩阵与模板管理一致的控件规则：表格行内动作使用短动作词 `Split`，状态列只显示 `split`，`Manifest` 作为只读 drilldown，重复登记由 handler 拒绝。它与 `Proof`、`Receipt`、`Writeback`、`Dashboard`、`Confirm`、`Handoff`、`Report`、`Close`、`Finalize`、`Monitor` 保持同一交互模型，避免在场景配置里出现另一套控件语义。
