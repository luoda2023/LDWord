# 高层场景能力矩阵 V19 高频场景完备性与边界治理规划（2026-06-18）

## 1. 本轮定位

V18 已经把场景能力从“场景名称列表”推进到 12 个 coverage pack、15 个能力原子、Word/OOXML 风险面、closure task 和控件契约。但用户继续指出一个更高层的问题：当前功能点仍然过于不完善，不能只按已有模块往下补；必须先确认高频适用场景没有遗漏，且边界不会在后续实现中反复漂移。

V19 的目标是建立一套更高层的场景能力矩阵治理模型：

```text
自然请求
-> 高频任务族
-> coverage pack
-> planned scene family / executable scene / profile / plugin boundary
-> 能力原子
-> Word/OOXML 风险面
-> UI 控件契约
-> resolver / pipeline / report / issue queue / artifact
-> 测试和闭环证据
```

只有这条链路能被说清楚，某个功能才可以进入“场景能力矩阵”。否则它只是一个孤立功能点、一个模板参数、一个资料字段，或者一个需要插件/人工确认的边界能力。

## 3. V19 的总判断

当前不应优先扩展很多顶层导航入口。更正确的方向是：

```text
保持 12 个 coverage pack 稳定；
扩充每个 pack 的高频请求别名、子场景、事实源、工作流槽位和边界；
把 P1 高频缺口推进到 UI / resolver / pipeline / report / issue queue / artifact / test 的可验收闭环。
```

顶层入口只适合承载已经 L4 产品化的稳定任务。大量高频任务应先落在 planned family、profile、material schema、delivery preset 或 plugin/manual gate 中。

如果一个请求只是“用户经常会说”，但没有明确事实源、Word 风险、执行链和报告面，它不能直接升级为场景能力。

## 4. 完善场景能力的 10 个门槛

V17 已定义 9 个准入门槛。V19 额外强调“高频请求覆盖门槛”，因此完整门槛调整为 10 个：

| 门槛 | 必须回答的问题 | 未回答时的风险 |
| --- | --- | --- |
| 高频请求别名 | 用户会怎样自然提出这个任务，是否已被覆盖 | 高频场景遗漏 |
| 归属层级 | 属于 scene、template、material、output、session 还是 plugin | 参数边界混乱 |
| 事实源 | 哪个输入是机器可信事实源 | AI/Markdown/人工文本漂移 |
| 工作流槽位 | 需要哪些复用工作流才能成立 | 只有场景名，没有流程 |
| Word 风险面 | 会触碰哪些 Word/OOXML 面 | 执行时破坏文档结构 |
| UI 控件契约 | 与模板管理同名参数是否同控件、同单位、同禁用规则 | 用户交互和写出语义不一致 |
| 执行链 | 是否经过 resolver、scheduler、pipeline、runner | 配置无法真正生效 |
| 报告/问题/产物 | 失败、风险、缺口和产物是否可解释 | 只能看日志，无法修复 |
| 测试证据 | 是否有 registry/UI/runtime/report 的测试证据 | 文档规划无法防回归 |
| 边界承诺 | 明确不做什么，是否需要插件或人工确认 | 过度承诺专业判断或内容质量 |

V19 的硬规则：

```text
缺高频请求别名 -> 可能遗漏；
缺归属层级 -> 必然混乱；
缺事实源 -> 不能进入执行；
缺 Word 风险面 -> 不能宣称 Word 场景能力；
缺报告/问题/产物 -> 不能算闭环；
缺边界承诺 -> 不能对用户开放为稳定能力。
```

## 5. 高层承载层

### 5.1 Template 层

负责稳定外观基线：

```text
页面、字体、字号、段落、标题编号、目录、题注、页眉页脚、参考文献样式、普通表格样式。
```

模板不决定：

```text
是否执行某项能力、处理哪些业务范围、失败如何处理、本次生成哪些版本、是否需要人工确认。
```

### 5.2 Scene 层

负责任务策略：

```text
场景类型、处理范围、模块开关、编号重建/保留、公式/引用/清理策略、对象风险策略、业务版本策略。
```

场景可以有样式覆盖，但必须满足：

```text
有业务理由；
复用模板管理同源控件；
写入 resolver provenance；
报告中能解释该覆盖来自场景而非模板默认值。
```

### 5.3 Material 层

负责事实和素材：

```text
字段、JSON/XLSX、图片、签章、Logo、附件、资质证照、合同主体、题目结构。
```

Material 不负责决定业务策略。它告诉系统“有什么”，场景告诉系统“怎样用”。

### 5.4 Output 层

负责交付语义和产物：

```text
final、review、compare、student、teacher、answer、signing、archive、manifest、report、zip。
```

Output 不应只是几个复选框。它需要被 DeliveryPreset 管理，并和内容显隐、目标模板、文件命名、目录结构、报告级别打通。

### 5.5 Plugin / Manual Gate 层

负责高风险能力：

```text
AI 内容生成、OCR、PDF 转 Word、完整 LaTeX 导入、复杂几何图、专业审计/法律/财务/IP/翻译判断。
```

这些能力可以高频，但不能直接伪装为核心场景能力。核心只接收经过校验、人工确认或结构化后的结果。

### 5.6 Session 层

负责本次运行：

```text
当前输入文件、输出目录、本次临时覆盖、用户选择的资料包、本次执行状态。
```

会话信息不能污染可复用场景定义。

## 7. 12 个 coverage pack 的产品化定义

### 7.1 `quick_formatting`

高频任务：

```text
快速规范化 Word、清洗格式、套模板、生成最终稿和报告。
```

完整能力必须包括：

- 模板基线选择；
- 处理范围解释；
- object preflight；
- 输出 final/report；
- Workbench 问题中心修复入口；
- 不做专业合规判断的边界说明。

当前判断：L4-。P0 链路已基本闭合，后续主要增强控制契约、更多对象风险和可视化修复。

### 7.2 `chinese_academic`

高频任务：

```text
中文论文、课程论文、综述、开题、学校计数、引用和公式置信度报告。
```

完整能力必须包括：

- `thesis_cn` profile split；
- 学校/学院 CountProfile；
- 正文、摘要、参考文献、附录等范围定位；
- 引用/参考文献和公式置信度报告；
- final/review/compliance report；
- 不吸收英文期刊和试卷的边界。

当前判断：L3。`thesis_cn` 和引用/公式报告 first slice 已闭合；学校规则来源治理、BibTeX/CSL 深引用和更多公式 fallback 仍是增强项。

### 7.3 `english_journal`

高频任务：

```text
英文期刊投稿、cover letter、revision、submission package、section word count、display items。
```

完整能力必须包括：

- journal profile；
- BibTeX/CSL parser 和引用检查；
- title/abstract/main/methods/references/display item 等多口径计数；
- submission package runtime；
- review copy / cover letter / declaration package；

### 7.4 `exam_education`

## 8. 高频矩阵的四条主线

### 8.1 格式规范线

覆盖：

```text
quick_formatting、chinese_academic、official_policy、technical_long_docs。
```

核心能力：

```text
模板基线、范围定位、编号策略、对象保护、报告证据。
```

最容易混淆的边界：

```text
模板外观 vs 场景执行策略；
标题编号样式 vs 编号重建/保留；
页眉页脚外观 vs 水印/版本状态。
```

### 8.2 结构化事实源线

覆盖：

```text
exam_education、contract_delivery、batch_forms、application_reports、bidding_materials。
```

核心能力：

```text
JSON/XLSX/material schema、字段一致性、素材角色、批量失败隔离、delivery preset。
```

最容易混淆的边界：

```text
资料字段 vs 场景策略；
同一事实源多版本 vs 多次生成多个漂移版本；
资料真实性 vs 字段完整性。
```

### 8.3 合规计数线

覆盖：

```text
chinese_academic、english_journal、application_reports、professional_disclosure、exam_education。
```

核心能力：

```text
Profile-driven Multi-metric CountEngine；
section classification；
Word-like 与规则口径并存；
报告解释使用了哪个指标、范围和排除项。
```

吸收 `count_engine_tech_record.md` 的结论：

```text
不能做单一字数统计器；
中文、英文、投稿、申报、试卷和披露的计数口径必须由 profile 驱动；
报告要输出多指标和不确定项，而不是只有一个数字。
```

### 8.4 交付归档线

覆盖：

```text
english_journal、exam_education、bidding_materials、technical_long_docs、application_reports、contract_delivery、professional_disclosure。
```

核心能力：

```text
DeliveryPreset、ContentVisibilityRule、artifact manifest、zip/package、review/final/archive/report。
```

最容易混淆的边界：

```text
输出开关 vs 业务交付版本；
水印装饰 vs 文档状态；
归档 manifest vs 专业合规证明。
```

## 9. 对外部技术记录的吸收裁决

### 9.1 CountEngine 记录

需要吸收：

- CountEngine 必须 profile-driven；
- 同时提供 Word-like 统计和规则统计；
- 中文论文、英文期刊、申报、试卷和披露不能共享单一口径；
- section / element classification 是计数可信度的前提；
- 报告必须解释范围、指标、排除项和不确定项。

不直接吸收：

- 未经项目验证的具体模块目录；
- 任何特定学校、期刊或系统的硬编码规则；
- 对 Word 自身统计结果的完全一致承诺。

### 9.2 试卷生成记录

需要吸收：

- JSON 是正式机器事实源；
- Markdown 只做预览和人工检查；
- Word 是正式输出；
- 学生版、教师版、答案版来自同一结构化题源；
- 答案、解析、分值、知识点必须保留在结构化数据中，由 visibility/delivery 决定是否显示；
- 通用图片能力优先于复杂几何图；
- 复杂几何图和 AI 内容质量属于插件/人工确认边界。

不直接吸收：

- 立刻引入 docxtpl/Pydantic 作为唯一方案的硬要求；
- 复杂学科图形的核心实现承诺；
- AI 直接生成 Word 的路径。

## 10. 场景配置与模板管理控件一致性

用户已明确要求：场景配置中的控件样式控制必须与模板管理中规定的样式保持一致。V19 将其提升为场景能力准入门槛，而不是 UI 美化事项。

### 10.1 总原则

```text
同名样式参数必须同控件、同单位、同启停规则、同校验范围、同写入语义。
```

如果场景页需要改样式，它不是“新控件”，而是“模板基线的业务覆盖”。因此必须复用模板管理的控件体系。

### 10.2 已确认的一致性落点

当前代码中已有以下正向证据：

- `FontCombo`；
- `SizeCombo`；
- `SpecialIndentInput`；
- `IndentInput`；
- `SpacingInput`；
- `LINE_SPACING_OPTIONS`；
- `control_contract_registry.py` 的同源控件约束；
- `scene_parameter_ownership.py` 对 `section_styles`、`table`、`toc`、`caption`、`reference_style` 等归属的声明。

### 10.3 必须锁定的交互规则

| 参数 | 场景配置要求 | 原因 |
| --- | --- | --- |
| 中文字体 / 英文字体 / 字号 | 与模板管理同控件，同下拉行为 | 避免样式写出语义不一致 |
| 左缩进 / 右缩进 | 可放同一行，单位和步进与模板一致 | 高频参数，应减少垂直冗余 |
| 段前 / 段后 | 可放同一行，使用 `SpacingInput` | 与模板页的段落密度一致 |
| 特殊缩进 | 必须可交互切换无/首行/悬挂 | 当前用户截图指出的关键交互缺口 |
| 行距类型 / 行距值 | 类型决定值是否启用，规则一致 | 避免固定值、多倍行距写出错误 |
| 普通表格行高 | 不出现在通用 TableConfig | 防止 `w:trHeight` 回流成普通表格参数 |
| 固定版位行高 | 只在 fixed-layout profile 暴露 | 与 `batch_forms` 边界一致 |
| 水印 | 版本状态归场景/输出，视觉细节可由模板基线提供 | 防止业务状态被当成装饰 |
| 公式 | 外观基线和转换策略分离 | 防止模板样式和场景执行策略混淆 |

### 10.4 新增验收要求

任何新增场景样式控件必须通过 6 个问题：

```text
1. 模板管理是否已有同类控件？
2. 是否复用了同一个 shared UI 组件？
3. 单位、步进、最小值、最大值、禁用规则是否一致？
4. 是否写入同一个 config/resolver 语义？
5. 是否进入 provenance/report 或至少能被测试追踪？
6. 如果没有复用，是否能证明它是场景专属业务策略而非样式参数？
```

答不清时不能新增控件。

## 14. 新功能进入矩阵的裁决流程

任何新需求先走下面的判断：

```text
1. 用户会怎样自然提出？
2. 是否属于已有 12 个 coverage pack？
3. 是否只是模板外观参数？
4. 是否只是资料字段或素材角色？
5. 是否只是本次输出/会话设置？
6. 是否需要插件或人工确认？
7. 如果确实是新场景族，是否有明确 fact source、workflow、Word risk、delivery、report、test？
```

裁决结果：

| 情况 | 处理方式 |
| --- | --- |
| 已有 pack 能承接 | 补 profile/workflow/closure，不新增顶层入口 |
| 是外观基线 | 回模板管理 |
| 是字段/图片/附件 | 回 MaterialSchema/资料包 |
| 是版本/产物 | 回 DeliveryPreset/OutputConfig |
| 是 AI/OCR/PDF/专业判断 | 回 plugin/manual gate |
| 真正新高频任务族 | 先 planned family + boundary + closure task，不直接上导航 |

## 15. V19 结论

当前功能点确实不完善，但更大的风险不是“少几个按钮”，而是：

```text
高频任务没有稳定落点；
模板、场景、资料、输出、插件的边界不清；
Word/OOXML 风险没有提前进入矩阵；
报告和问题中心没有成为闭环证据；
控件样式与模板管理不一致导致用户以为配置生效但链路断开。
```

因此，V19 的产品判断是：

```text
12 个 coverage pack 继续保持稳定；
不盲目新增顶层入口；
把高频自然请求词典、能力原子、Word 风险面、控件契约、执行证据和边界承诺统一成准入门槛；
优先推进 exam_education 的多版本交付，因为结构化题源 runtime first slice 已闭合，多版本 preset 是该场景下一条最高频未闭合链路。
```

下一步工程闭环建议：

```text
N2.112：exam_education student/teacher/answer delivery presets。
N2.113：english_journal BibTeX/CSL parser and citation checks。
N2.114：english_journal submission package runtime and report evidence。
```

这条顺序能同时满足两件事：先补最高频缺口，又不让 AI、复杂图形、专业判断等边界不清的能力提前污染核心链路。
