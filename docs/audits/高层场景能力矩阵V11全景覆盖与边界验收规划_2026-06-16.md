# 高层场景能力矩阵 V11 全景覆盖与边界验收规划（2026-06-16）

## 1. 文档定位

本文继续深化“高层场景能力矩阵怎样才算完善”。V10 已经建立了高频覆盖与边界治理规则，但用户进一步指出：当前功能点仍然过于不完整，不能出现高频适用场景遗漏，也不能让边界含糊。V11 因此不再只是列举 family，而是把场景能力拆成一张可验收地图：

```text
用户高频任务
-> 场景族或 profile 归属
-> 横切工作流
-> 模型承载层
-> Word/OOXML 风险面
-> UI 控件一致性
-> 执行与报告证据
-> 测试闭环
-> 不承诺边界
```

只要一条高频任务不能完整走完这条链，就不能算“场景能力完善”。

## 2. V11 核心结论

当前最大问题不是完全没有场景覆盖，而是：

```text
已有很多名字，但多数名字还没有成为可执行、可解释、可测试、可交付的场景能力。
```

完善的高层矩阵必须同时满足六个条件：

1. 高频任务没有大类遗漏；
2. 每个任务有唯一优先归属，不在“顶层场景、profile、preset、模板、资料包、插件”之间摇摆；
3. 横切工作流有稳定承载，不把“多版本输出、批量、附件清单、计数、对象保护”误做成碎片化入口；
4. Word/OOXML 风险进入每个 family 的验收条件，而不是运行失败后再补救；
5. 场景配置控件继承模板管理的控件体系，同名参数同控件、同单位、同交互；
6. 每个可承诺能力都有 UI、执行、报告和测试证据。

V11 的判断标准：

```text
一个高频任务没有承载层，算遗漏；
一个承载层没有边界，算混乱；
一个场景没有执行和报告证据，算规划；
一个输出不能被用户验收，算未交付；
一个专业判断没有插件或人工确认边界，算越界承诺。
```

## 3. 当前事实基线

### 3.1 可执行 P0 入口

当前 Workbench 顶层可执行入口仍是 6 个：

| 入口 | 当前价值 | V11 收口要求 |
| --- | --- | --- |
| `custom` | 临时组合与兜底 | 只承诺手动组合，不吸收专业规则 |
| `thesis` | 中文学术论文排版主入口 | 应逐步收窄为 `thesis_cn`，不要吞英文投稿和通用报告 |
| `bidding` | 标书与投标资料主入口 | 补强签章、附件 inventory、正副本、资料包、对象安全 |
| `official` | 公文与行政文书主入口 | 补强文号字段、编号保留、正式/内部稿、水印状态 |
| `technical` | 技术/工程文档主入口 | 补强 OLE、Visio、嵌入 Excel、域、题注、变更报告 |
| `report` | 通用报告轻量入口 | 保持通用，不吞合同、申报、披露、售前等 profile |

这些入口应保持稳定，不建议把每个细分行业都升成顶层入口。

### 3.3 当前可用承载层

| 承载层 | 当前已有能力 | 主要断点 |
| --- | --- | --- |
| `TemplateConfig` | 页面、样式、表格、页眉页脚、水印外观等版式基线 | 容易被场景误当作业务策略 |
| `SceneWorkspace` | 任务策略、模块开关、范围、场景覆盖 | family 推荐只落地 `contract_delivery` |
| `InputSourceProfile` | 输入格式、结构化格式、Markdown/LaTeX 策略、资料包要求 | 只能主指向一个 `material_schema_id`，多 schema family 表达不足 |
| `MaterialSchema` | 字段、图片、签章、附件、多实体资料契约 | 资料 schema 与场景 UI/批量/输出还不够全链路 |
| `ComplianceProfile` | 合规 profile、count profile、检查范围、失败策略 | profile 来源、版本、适用边界不够产品化 |
| CountProfile | 多指标统计口径 | 多数 profile 仍是 first-pass，不足以支撑真实学校/期刊/申报指南 |
| `ObjectPreflightPolicy` | OLE、宏、修订、批注、文本框、域等风险策略 | family 差异化策略和可编辑跳过矩阵还不完整 |
| `DeliveryPreset` | 多版本输出、目标模板、命名、产物开关、显隐规则 | 结构化源映射、完整块级 UI、真实产物预览仍未完备 |
| `ContentVisibilityRule` | marker block 显隐规则 | 与结构化题源、合同状态、正式/内部版的业务语义未系统化 |
| `BatchPreset` | 批量预设概念 | HR、表单、陪标、证明等批量执行闭环不足 |
| Workbench Session | 当前文件、输出目录、运行状态、产物路径 | 对场景族 maturity 和边界说明还不够显式 |
| Plugin boundary | OCR、AI、完整 LaTeX、法律、财务、IP 等边界 | 需要在 UI/报告中让用户看见“核心不承诺” |

## 4. 顶层场景、Profile、Preset、模板、插件的硬边界

| 需求特征 | 应归属 | 不应归属 |
| --- | --- | --- |
| 用户反复用业务名描述，如“合同签署稿”“项目申报书” | scene family / profile | 单个模板开关 |
| 同一事实源输出多个版本，如学生版/教师版、正式稿/内部稿 | `DeliveryPreset` | 新建顶层场景 |
| 字段、签章、附件、人员、产品、项目、预算等事实 | `MaterialSchema` / Assets | 模板样式 |
| 字数、词数、图表数、附件数、显示项数 | CountProfile / `ComplianceProfile` | 普通 validation 开关 |
| 外观版式，如字体、缩进、段距、页边距、表格边框、页眉页脚外观 | `TemplateConfig` | 业务 profile |
| 某次运行的文件、目录、确认、日志、产物浏览 | Workbench Session | 持久场景配置 |
| 修订、批注、域、文本框、内容控件、OLE、宏、嵌入 Excel | `ObjectPreflightPolicy` | 普通清理模块 |
| OCR、完整 LaTeX 工程、AI 内容生成、法律、财务、IP、审计判断 | Plugin / 人工确认 | 核心排版承诺 |

特别规则：

- 公式不是只属于模板。模板管公式字体、间距、编号样式基线；场景管公式来源、转换策略、低置信度策略、学科适用范围和报告。
- 输出不属于模板。输出版本、目标模板、命名、显隐、资料包和报告属于 `DeliveryPreset`。
- 水印外观可由模板提供基线；水印状态、版本差异、审阅/内部/机密交付策略属于场景和 `DeliveryPreset`。
- 表格行高不是一般样式残留。普通文档可不暴露行高；表单套打、证书、报价单、固定版式场景中，行高对应版位保护能力，应作为 `form_batch_documents` 的重点。
- 模板管理和场景配置出现同名控件时，必须同控件、同命名、同单位、同交互；区别只在标签中说明“模板默认”或“场景覆盖”。

## 7. Word/OOXML 风险必须进入场景验收

每个 L2 以上 family 必须声明 `ooxml_touchpoints`，并映射到 `ObjectPreflightPolicy.scan_targets` 或明确“不触碰”。否则只是业务标签，不是 Word 能力。

| OOXML/Package 风险面 | 高频场景 | 验收要求 |
| --- | --- | --- |
| `paragraph` / `run` | 所有排版、合同字段、双语审阅 | 不破坏 run 内格式，字段填充和显隐规则可解释 |
| `numbering` | 公文、会议制度、长文档、论文、标书 | 保留/重建策略明确，不能静默覆盖 |
| `table` | 标书、试卷、表单、财务、披露 | 表格样式、单元格内容、固定版位、行高策略明确 |
| `drawing` / 图片 | 技术、标书、论文、产品、资质 | 图片角色、缺图、关系引用、复制到资料包 |
| `field` | 目录、页码、交叉引用、合同编号、披露字段 | 更新/保留/跳过策略和报告证据 |
| `comment` | 合同、公文内审、投稿修回、双语审校 | 默认保护，不能静默删除 |
| `revision` | 合同、技术审阅、公文内审、披露 | 运行前确认，必要时跳过高风险模块 |
| `textbox` / `shape` | 表单套打、固定版式、双语材料 | 预检、版位保护、避免粗暴重排 |
| `content_control` | 表单、合同、公文、HR | 字段映射、残留检查、保护策略 |
| `embedded_workbook` | 财务报价、披露、技术表格 | 预检和阻断/降级策略 |
| `ole_objects` / Visio | 技术、标书、工程图、历史模板 | 高风险预检，跳过可能破坏对象的模块 |
| `macros` | 外来模板、合同、复杂表单 | 默认阻断或人工确认 |
| `relationship` / package part | 图片、附件、外部链接、嵌入对象 | inventory、缺项、资料包复制和报告 |
| `headers_footers` | 公文、论文、合同、披露 | 页眉页脚外观归模板，状态/字段归场景 |
| `footnotes` / `endnotes` | 论文、书稿、法律/合同附注 | CountProfile 和引用策略明确 |
| `hidden_text` | 审阅稿、合同、披露 | 预检和报告，不能默认当普通正文 |

## 8. 场景配置控件一致性规则

场景配置不是第二套 UI。凡是与模板管理复用同一语义参数，必须复用模板管理的控件语言。

| 参数 | 场景配置要求 | 原因 |
| --- | --- | --- |
| 左缩进 / 右缩进 | 同行排布，命名与模板一致，单位一致 | 用户看到的是同一 Word 段落语义 |
| 段前 / 段后 | 同行排布，使用同一数值 + 单位控件 | 防止模板页和场景页语义漂移 |
| 特殊缩进 | 必须可交互切换：无、首行、悬挂 | 不能只显示一个不可切换状态 |
| 行距类型 / 行距值 | 类型和值同组，固定值/倍数/最小值可切换 | Word 行距是组合语义 |
| 表格边框/宽度/行高 | 普通模板作为默认样式，表单套打作为版位保护策略 | 同一参数在不同场景的风险不同 |
| 公式参数 | 复用模板控件外观，但场景需要额外显示转换/置信度/适用范围 | 公式是专业对象域 |
| 水印参数 | 外观控件复用模板，状态和版本绑定 DeliveryPreset | 水印既有样式又有交付语义 |
| 输出参数 | 不用模板样式控件承载，应归 Output/DeliveryPreset 区 | 输出不是版式 |
| 风险策略 | 使用 combo、badge、summary、确认区 | 不能伪装成普通开关 |
| 资料字段 | 使用 schema 驱动表单/表格，不靠自由文本堆叠 | 资料需要执行和报告同源 |

验收规则：

```text
同名参数：同控件、同单位、同交互；
不同归属：用标题和摘要说明“模板默认”还是“场景覆盖”；
高风险参数：必须有说明、预检或确认；
业务输出：必须进入 DeliveryPreset，不进入模板管理。
```

## 9. CountEngine 吸纳后的矩阵要求

`count_engine_tech_record.md` 的核心结论是“不要做单一字数统计器，而要做 profile-driven multi-metric CountEngine”。V11 将它上升为场景验收条件。

| 场景族 | 必须支持的计数视角 | 不能只做什么 |
| --- | --- | --- |
| `thesis_cn` | 中文字符、汉字、总字符、不含空格、参考文献、图、表、公式、正文范围 | 不能只显示 Word `Words` |
| `journal_en` | title、abstract、main text、methods、references、display items、figure legends、table captions | 不能只做全文 words |
| `project_application` | 章节字数、附件清单、预算表/团队表 inventory | 不能只跑正文字符数 |
| `bidding` | 附件、表格、图片、签章、资质材料 inventory | 不能把标书当普通报告 |
| `contract_delivery` | 主体/金额/日期字段覆盖、批注/修订/域 inventory | 不能声称法律审查 |
| `exam_teaching` | 题型、题量、分值、公式/图片、答案/解析 visibility | 不能用段落数代替题目数 |
| `regulated_disclosure_documents` | 章节、表格、图片、附件、批注、披露归档清单 | 不能声称审计结论 |

CountProfile 必须逐步增加：

- 来源；
- 版本；
- 适用范围；
- 包含/排除范围；
- 与 Word 内置统计的差异；
- 与外部系统最终口径不一致的声明；
- UI 摘要、Markdown/JSON 报告和测试证据。

## 10. 试卷/教学技术记录吸纳后的矩阵要求

`exam_generator_tech_stack_record.md` 的关键结论是：

```text
JSON 是机器事实源，Markdown 是人工预览层，Word 是正式输出。
```

这条规则不只适用于试卷，还适用于所有结构化生成场景。

| 场景 | 结构化事实源要求 | 多版本要求 |
| --- | --- | --- |
| 试卷教学 | `Paper -> sections -> questions -> answer/analysis/score` | 学生版、教师版、答案版从同一 JSON 输出 |
| HR 批量 | 一条人员记录对应一份输出 | 成功/失败分离，失败不污染成功 |
| 表单套打 | 字段 schema 映射内容控件/表格/文本框 | 每条记录独立产物和残留报告 |
| 合同交付 | 甲乙方、金额、日期、合同号、签章资产 | 审阅稿/签署稿/字段报告同源 |
| 项目申报 | 项目、团队、预算、附件 | 申报书/附件包/合规报告同源 |
| 产品售前 | 产品、案例、图片、参数表 | 客户版/内部版同源显隐 |

硬边界：

- AI 可以作为输入助手或插件，但核心不承诺内容质量；
- 不允许为学生版和教师版分别生成两份不同事实源；
- Markdown 可以用于预览和人工编辑，但不能成为最终排版事实源；
- 复杂几何图、电路图、化学结构式等走图片资产或专用插件。

## 11. 当前最容易遗漏或边界不清的区域

| 区域 | 问题 | V11 处理 |
| --- | --- | --- |
| 培训课程 | 容易被试卷场景吞掉 | 作为 `exam_teaching` 教育 profile，不单独顶层 |
| 表单套打 | 容易被“批量填充”泛化掉 | 独立 P1 candidate，强调行高、内容控件、文本框、版位保护 |
| 资质证照包 | 容易散落在标书/申报/附件里 | 作为横切 family，提供 inventory 和 archive manifest |
| 双语审校 | 容易误承诺翻译质量 | 只做版式、术语、一致性和对照审阅 |
| 年报/ESG/披露 | 容易被通用报告或财务吞掉 | P2 family，边界是归档与证据，不做审计结论 |
| PDF/OCR | 高频但不是场景本体 | 插件入口，核心只接收确认后的结构化/Word 结果 |
| AI 内容生成 | 高频但风险高 | 输入助手插件，核心要求 JSON 校验和人工确认 |
| 水印 | 容易被当作模板小项 | 外观归模板，状态/版本归场景和 DeliveryPreset |
| 输出 | 容易被当作模板配置 | 归 DeliveryPreset 和 Workbench |
| 公式 | 容易只看字体 | 场景还要管来源、转换、低置信度、学科范围 |
| 表格行高 | 已从模板退场，但在表单场景仍有价值 | 不回到通用模板；进入 `form_batch_documents` 版位保护 |

## 12. 成熟度门槛

| 等级 | 含义 | 可对用户承诺吗 |
| --- | --- | --- |
| L0 | 只有需求或文档想法 | 否 |
| L1 | registry 有 planning contract | 否，只能展示规划 |
| L2 | schema/profile/preset 至少一层落地 | 只能作为受限预览 |
| L3 | first slice 有 UI、执行、报告、测试 | 可以作为受限能力 |
| L4 | 多工作流闭合，失败、跳过、边界可解释 | 可以作为稳定能力 |
| L5 | profile 治理、批量、归档、插件边界长期稳定 | 可以产品化推广 |

准入规则：

- L1 family 不能出现在顶层可执行导航；
- L2 family 可以被 ScenePanel 作为“规划族推荐”提示，但不能承诺完整能力；
- L3 以上必须有最小闭环测试；
- L4 以上必须有失败路径和边界说明；
- L5 必须具备 profile 版本治理和跨版本回归测试。

## 13. V11 优先级路线

优先级不按“新场景数量”排，而按“能闭合最多高频链路”排。

| 顺序 | 主题 | 目标成熟度 | 价值 |
| --- | --- | --- | --- |
| 1 | `contract_delivery` 签章资料和签署包 | L2 -> L3 | 复用字段一致性、对象保护、DeliveryPreset、资料包 |
| 2 | 场景配置控件一致性 | 横切 L3 | 防止模板/场景同名参数交互不一致 |
| 3 | `form_batch_documents` 固定版式 first slice | L1 -> L3 | 解决行高、内容控件、文本框、批量套打高频痛点 |
| 4 | `exam_teaching` 结构化题源 + 多版本 | L1 -> L3 | 建立 JSON 事实源 + DeliveryPreset 显隐范式 |
| 5 | `hr_batch_documents` 批量失败隔离 | L1 -> L3 | 高频办公批量产物闭环 |
| 6 | CountProfile 治理 | L2 -> L3 | 支撑论文、投稿、申报、披露和附件 inventory |
| 7 | ObjectPreflight family 策略矩阵 | L3 -> L4 | 支撑技术、合同、标书、披露、长文档安全底座 |
| 8 | `project_application` 申报包 | L1 -> L3 | 复用资料、计数、附件、提交包能力 |
| 9 | `bidding` 资料包深度化 | L2 -> L4 | P0 入口中最依赖资料/附件/签章 |
| 10 | Plugin boundary UI | 横切 L3 | 防止 OCR、AI、法律、财务、IP 越界承诺 |

## 14. 对当前代码层的具体改造建议

### 14.1 Registry 层

- 给 `PlannedSceneFamily` 增加成熟度证据字段，例如 `implemented_closures`、`missing_closures`、`recommended_next_slice`；
- 支持 family 引用多个 material schema，并能合并字段与 asset roles；
- 给每个 family 增加 `ui_exposure_policy`，区分 `hidden_planning`、`scene_panel_recommendation`、`profile_selector`、`top_level_candidate`；
- 给 `workflow_archetypes` 建立枚举或 registry，避免拼写和语义漂移。

### 14.2 MaterialSchema 层

- 将 `required_material_fields`、`required_image_roles` 与 schema 合并逻辑前移成统一 resolver；
- 支持 file/pdf/xlsx/image 等附件角色的统一 inventory；
- 支持 batch mode 与 `BatchPreset` 直接关联；
- 在 manifest 中记录 schema 来源、family、必填/推荐、缺失原因和边界声明。

### 14.3 CountProfile 层

- 给每个 profile 增加 `source_name`、`source_version`、`last_reviewed`、`scope_explanation`；
- UI 和报告同时显示 Word-like 统计与规则统计；
- 对 school/journal/application 等 profile 加“不是外部系统最终口径”的声明；
- 增加 profile 覆盖测试，防止 registry family 引用不存在的 CountProfile。

### 14.4 ScenePanel 层

- 继续沿用 `TemplateFormStack`、`template_form_row`、`StyledComboBox`、`ToggleSwitch`、`SummaryGrid` 等共享控件；
- 输入/资料、合规、输出三块需要支持 family 推荐摘要和一键应用，但要标明成熟度；
- 特殊缩进、行距类型、数值单位等必须与模板管理控件完全一致；
- 风险策略区应使用摘要、badge、确认区，而不是普通 checkbox 堆叠；
- 输出区继续以 `DeliveryPreset` 为中心，不把输出参数塞回模板。

### 14.5 Workbench/执行层

- payload 必须持续携带 material diagnostics、object preflight、count report、delivery preset、artifact paths；
- 运行前确认要能按 family 展示“为什么阻断/为什么跳过/为什么继续”；
- 最近结果和 artifact browser 要按 preset 分组显示产物；
- 批量执行必须支持失败隔离和汇总报告。

### 14.6 测试层

每个 family 至少要有四类测试：

1. registry 合法性：schema/profile/preset/count 引用存在；
2. UI 投影：ScenePanel 能显示 family 摘要、推荐、边界；
3. 执行消费：runtime 能写出产物或报告；
4. 失败路径：缺字段、缺资产、高风险对象、非法输出路径可见。

## 15. V11 防遗漏审阅清单

后续任何需求进入实现前，必须回答：

```text
1. 用户自然会把它叫成什么任务？
2. 它是顶层场景、profile、DeliveryPreset、MaterialSchema、CountProfile、模板参数、Workbench 状态还是插件？
3. 已有 P0/P1/P2 family 能否承载？
4. 它涉及哪些横切工作流？
5. 它需要哪些输入格式和结构化事实源？
6. 它需要哪些字段、签章、图片、附件、多实体资料？
7. 它涉及哪些 Word/OOXML 风险对象？
8. 它的缺失、低置信度、失败、跳过如何处理？
9. 用户在哪里看到结果、风险、边界和产物？
10. 哪些 pytest 锁住 registry、UI、执行、报告和产物？
11. 它是否涉及法律、财务、IP、审计、OCR、AI 内容或完整 LaTeX 等不承诺边界？
12. 它和模板管理中同名参数的控件是否一致？
```

任何一项回答不清，都不能宣布能力完整。

## 16. V11 最终判断

当前高层矩阵应从“场景名清单”升级成“任务覆盖网 + 工作流承载图 + OOXML 风险图 + 交付验收表”。

近期不应优先新增顶层入口。更正确的推进方式是：

```text
先把 P0/P1 高频链路做成 L3；
再把多 family 共用的 CountProfile、ObjectPreflight、DeliveryPreset、MaterialSchema 做成 L4；
最后才考虑将成熟 family 升为独立入口或插件。
```

本轮 V11 的结论是：

```text
高频场景大类基本已有归属；
遗漏风险主要来自横切工作流未闭合；
边界混乱主要来自模板、场景、资料、输出和插件职责不清；
下一阶段必须用成熟度、承载层和测试证据治理所有场景能力。
```
