## 1. 文档说明

这是一份从现有实现反向整理出的 PRD，不等同于最初需求。它解决两个问题：

1. 把散落在代码、配置、测试和审计记录中的产品行为，收敛成可讨论、可排期、可验收的产品定义。
2. 明确区分“当前已经存在的事实”“根据实现推导出的产品意图”和“为了让 PRD 完整而提出的建议”。

### 1.1 证据标记

| 标记 | 含义 | 使用方式 |
| --- | --- | --- |
| `F`（Fact） | 可由当前代码、配置或测试直接确认 | 可作为 V1.0 现状基线 |
| `I`（Inference） | 根据多个实现事实推导出的产品意图 | 需产品负责人确认措辞与优先级 |
| `P`（Proposal） | 为补齐目标、指标、非功能要求等提出的建议 | 评审通过后才成为承诺 |

反向工程只能说明“产品现在如何工作”，不能替代用户访谈、商业目标、竞品研究和真实运行数据。因此，文中所有目标数值均标为建议值，发布前应通过基线测试校准。

### 1.2 一份优秀 PRD 应覆盖什么

一份优秀 PRD 的核心不是篇幅，而是让团队对以下问题得到同一个答案：

## 2. 产品摘要

### 2.1 一句话定义

Alavette Form 是一款 Windows 本地优先的文档生产工作台：用户将原始文档、处理方案、格式模板和资料包组合起来，经过风险预检与可控执行，生成规范化 DOCX 及可追溯的报告、对比稿和交付包。

### 2.2 核心价值

- 把反复、易错的 Word 格式整理从人工操作变为可复用流程。
- 把“处理哪些内容”“套用什么格式”“填入什么资料”“交付哪些版本”拆成独立、可管理的产品对象。
- 在执行前识别宏、嵌入对象、修订、批注、隐藏文本等高风险对象，降低破坏原稿的概率。
- 支持论文、试卷、标书、公文、技术文档和报告等不同业务入口，而不是仅提供一组通用格式按钮。
- 生成变更报告和产物清单，使用户能够知道做了什么、跳过了什么、还需要人工确认什么。

### 2.3 当前定位冲突

以下事实必须在 V1.0 对外发布前统一：

| 冲突 | 当前事实 | 建议决策 |
| --- | --- | --- |
| 产品名称 | 仓库与包名使用 `Lark Formatter`，应用元数据使用 `Alavette Form V1.0` | 选定唯一对外品牌；旧名称只作为迁移别名 |
| 产品范围 | README 仍描述为“毕业论文 / 学位论文格式修订工具”，代码已包含 7 个顶层工作模式 | 将对外定位更新为“场景化文档生产与规范化工作台”，论文作为重点场景之一 |
| 输入能力 | GUI 方案配置声明 DOCX、Markdown、XLSX 等模式化输入；CLI 当前只接收 DOCX | 在发布说明中明确差异，或在发布前补齐统一能力矩阵 |
| 标准承诺 | 模板名称包含 GB/T 7713、GB/T 9704 等标准名称 | 对外说明规则版本、适用范围和人工复核边界，避免承诺“自动合规” |

## 3. 背景与用户问题

### 3.1 背景

专业文档的生产通常不是单纯“改字体”。用户需要同时处理页面、分节、标题编号、目录、页眉页脚、题注、表格、图片、公式、参考文献、占位符和多个交付版本。不同业务又有不同规则：试卷需要学生卷与答案版，标书需要正副本和资料附件，公文需要文种与版式匹配，论文需要学校规则与引用边界。

这些工作如果完全依赖人工，会出现耗时长、标准难复用、批量错误扩散、无法说明改动内容等问题。

### 3.2 核心用户问题

| 编号 | 用户问题 | 影响 |
| --- | --- | --- |
| P-01 | 格式规则分散在样例、通知、个人经验和旧文档中 | 同类文档结果不一致，换人后难延续 |
| P-02 | 原始内容、格式模板和业务资料相互混杂 | 修改一处容易误伤内容或丢失资料 |
| P-03 | Word 文档含复杂对象，批量处理前难判断风险 | 可能破坏域、批注、修订、嵌入对象或宏 |
| P-04 | 同一内容需要多个交付版本 | 重复复制、删除与改名，容易串版 |
| P-05 | 批量文档中单条失败会拖累整批任务 | 返工成本高，失败项难定位 |
| P-06 | 处理结束后缺少可读的变更说明和产物清单 | 用户不敢直接交付，支持人员难排障 |
| P-07 | 高专业度判断被误认为可以完全自动化 | 产生合规、法律、财务或内容真实性风险 |

## 4. 产品愿景与原则

### 4.1 产品愿景

让没有 Word 自动化经验的用户，也能把一套复杂文档规范保存成可复用工作流，并在不牺牲原稿安全与可解释性的前提下稳定重复执行。

### 4.2 产品原则

1. **本地优先**：文档默认只在本机处理，不自动上传。
2. **原稿不可变**：不得直接覆盖输入文件；所有结果写入独立输出路径。
3. **职责分离**：方案决定“做什么”，模板决定“长什么样”，资料包决定“填什么”，母版决定“装到哪里”。
4. **高风险保守处理**：无法安全自动化时阻断、跳过或要求确认，不静默修改。
5. **结果可解释**：用户能看到执行状态、问题、跳过项、变更报告和产物路径。
6. **由浅入深**：高频任务可快速执行，复杂配置通过方案、模板和资料包逐层展开。
7. **场景边界明确**：工具负责文档结构、版式和资料装配，不对业务内容真实性与专业结论背书。

## 5. 产品目标、非目标与成功指标

### 5.1 V1.0 产品目标

| 目标 | 描述 | 优先级 | 证据 |
| --- | --- | --- | --- |
| G-01 高效完成 | 用户可通过选择工作模式、方案、模板和文件完成一次文档生成 | P0 | F/I |
| G-02 结果一致 | 同一输入与同一配置快照应得到可重复的结构和格式结果 | P0 | I |
| G-03 原稿安全 | 输入文件不被覆盖，高风险对象在执行前被识别并按策略处置 | P0 | F |
| G-04 配置复用 | 用户可复用、复制和维护方案、模板、母版与资料包 | P0 | F |
| G-05 多版本交付 | 一次任务可按交付预设生成一个或多个版本及辅助产物 | P0 | F |
| G-06 批量可控 | 批量生成时各条记录隔离，失败项可定位并单独重试 | P1 | F |
| G-07 可审计排障 | 执行结果包含状态、诊断、产物和脱敏问题报告 | P0 | F |

### 5.2 建议成功指标

产品坚持本地优先，因此 V1.0 不应默认上报云端遥测。以下指标建议通过本地结构化执行记录计算，由用户主动导出或在测试环境汇总。

| 指标 | 定义 | V1.0 建议目标 | 标记 |
| --- | --- | --- | --- |
| 首次任务完成率 | 首次进入后成功生成至少一个主 DOCX 的用户占比 | ≥ 70% | P |
| 有效任务成功率 | 通过预检并开始执行的单任务中，状态为成功或部分成功的占比 | ≥ 95% | P |
| 原稿破坏事故 | 输入文件被覆盖或不可恢复修改的次数 | 0 | P |
| 关键问题可解释率 | 失败任务中包含明确错误类型、建议动作和定位入口的占比 | ≥ 95% | P |
| 缺失资料修复闭环率 | 从预检问题进入资料包并修复后成功重试的占比 | ≥ 80% | P |
| 批量失败隔离率 | 单条失败未导致其他有效条目失败的批次占比 | 100% | P |
| 结果可定位率 | 成功或部分成功任务中，主产物和报告路径可打开的占比 | 100% | P |

### 5.3 非目标

V1.0 不承诺：

- 替代 Microsoft Word 的完整编辑能力。
- 判断文档内容是否真实、合法、准确或具有专业有效性。
- 自动给出法律、财务、专利、审计、投标策略或行政决策意见。
- 覆盖所有学校、期刊、地区或机构的最新规则；未审核规则必须人工确认。
- 在核心产品内完成高质量 OCR、完整 PDF 还原、完整 LaTeX 工程转换或专业翻译。
- 提供云端协作、在线账号、团队审批、远程资产库和跨设备同步。
- 保证所有第三方 Word 插件、宏和嵌入对象在重排后仍保持原行为。

## 6. 目标用户与核心任务

### 6.1 用户角色

| 角色 | 特征 | 核心任务 | 最关注 |
| --- | --- | --- | --- |
| 文档经办人 | 熟悉业务内容，不一定熟悉 Word 高级功能 | 选择现成方案并快速生成规范文档 | 简单、安全、结果可交付 |
| 规则/模板维护者 | 熟悉单位格式规范或 Word 样式 | 维护模板、编号、页眉页脚、目录和交付规则 | 配置完整、预览准确、可复用 |
| 资料包维护者 | 管理企业、项目、人员、图片和附件资料 | 维护字段映射、图片、附件与多份资料 | 缺失检查、版本一致、批量效率 |
| 批量任务操作员 | 需要一次生成多份相似文档 | 导入记录、预检、批量生成、重试失败项 | 隔离、进度、汇总报告 |
| 支持/测试人员 | 负责排障和发布验证 | 查看日志、导出脱敏问题报告、复现实例 | 可诊断、可追溯、不泄露内容 |

### 6.2 关键用户故事

- 作为文档经办人，我希望拖入一个 DOCX、选择方案和模板后直接生成结果，而不需要理解所有底层格式参数。
- 作为论文作者，我希望统一页面、标题、目录、题注、公式和参考文献格式，同时保留需要人工确认的学校规则边界。
- 作为教师，我希望用同一份题目内容生成学生卷与答案版，避免手工删除答案导致串版。
- 作为标书制作人员，我希望复用企业资料、签章图片和附件包，批量生成正本、副本与资料报告。
- 作为公文经办人，我希望先选择文种，再使用匹配母版和字段生成正式版与内部审阅版。
- 作为模板维护者，我希望复制内置模板后修改页面、样式、标题、表格、页眉页脚、目录和题注，并即时预览。
- 作为批量任务操作员，我希望单条资料错误只影响该条，并能在修复后重试失败项。

## 7. 产品对象与术语

| 对象 | 定义 | 主要负责 | 不负责 |
| --- | --- | --- | --- |
| 工作模式（Mode） | 顶层业务入口，如试卷版、公文版 | 筛选可见方案、模板、母版和资料架构 | 具体格式参数 |
| 方案（Plan/Scene） | 一次处理的规则集合 | 处理范围、模块开关、风险策略、交付预设 | 字体页边距等完整格式细节 |
| 模板（Template） | 可执行的格式配置 | 页面、正文/标题、编号、表格、页眉页脚、目录、题注 | 具体业务资料值 |
| 母版（Master） | 带固定结构或占位符的 DOCX 骨架 | 承载固定版式、文种结构和内容装配位置 | 通用处理规则 |
| 资料包（Material Package） | 字段、内容文件、时间计划、图片和附件的集合 | 提供占位符数据和外部资料 | 格式规则 |
| 交付预设（Delivery Preset） | 一组输出版本规则 | 文件名、输出目录、内容显隐、产物类型 | 输入内容编辑 |
| 执行会话（Execution Session） | 一次冻结后的执行上下文 | 记录有效身份、依赖版本、进度和结果 | 长期替代用户配置 |
| 产物（Artifact） | 执行产生的文件 | 主 DOCX、对比稿、报告、清单、交付包等 | 未经声明的外部发布 |

关键约束：方案、模板、母版、资料包必须属于兼容的工作模式；执行时应冻结其有效版本，避免用户在运行中修改配置导致结果漂移。


### 8.4 能力族与顶层模式的边界

代码中还存在中文学术、英文期刊、申请报告、合同交付、批量表单、专业披露和导入/AI 边界等高频能力族。V1.0 应将它们视为路由、资料架构、报告或插件边界能力，不应在没有完整入口与用户验证前全部宣传为独立顶层产品模式。

## 9. V1.0 功能需求

优先级定义：`P0` 为 V1.0 发布阻断项，`P1` 为应随 V1.0 交付但可受控降级项，`P2` 为增强项。

### 9.1 应用壳与工作模式

| ID | 需求 | 优先级 | 证据 |
| --- | --- | --- | --- |
| FR-001 | 应用应在 Windows 上提供单实例桌面运行；重复启动时提示用户使用现有窗口 | P0 | F |
| FR-002 | 用户应可在顶栏切换 7 个工作模式，切换后方案、模板、母版、资料架构与默认入口同步变化 | P0 | F |
| FR-003 | 当当前模式存在未保存修改时，模式切换或退出必须提供保存、放弃、取消三种选择 | P0 | F |

## 10. 核心业务规则

### 10.1 资源规则

1. 内置资源是规范基线，用户不得直接覆盖；定制通过复制生成用户资源。
2. 方案、模板、母版和资料包必须带稳定 ID、所属模式、来源类型和版本/修订信息。
3. 用户资源引用的依赖不存在、模式不兼容或版本无法解析时，应拒绝执行，不得静默替换。
4. 执行使用冻结快照；运行开始后，界面中的后续编辑只影响下一次任务。
5. 保存方案、模板和资料包必须原子化；检测到版本冲突时要求用户刷新、另存或明确覆盖。

### 10.2 输入与输出规则

1. 输入文件必须存在、可读，且满足当前方案的格式策略。
2. 输出路径不得与输入文件相同，也不得通过路径解析绕过该检查。
3. 默认输出目录为原始文档同级的 `output`；用户可选择其他本地目录。
4. 文件名模板变量必须在执行前解析；未解析变量、非法字符和重复路径应阻断该预设。
5. 已存在文件的覆盖策略必须显式：建议 V1.0 默认生成唯一名称，不静默覆盖。

### 10.3 风险处置规则

| 风险 | 默认建议 | 用户动作 |
| --- | --- | --- |
| 宏 | 阻断 | 使用无宏副本或明确进入受控流程 |
| OLE/嵌入工作簿/Visio | 警告并跳过高风险分节模块，部分模式阻断 | 查看对象清单并确认 |
| 修订、批注、隐藏文本 | 警告并写入报告 | 确认保留策略后继续 |
| 文本框、内容控件、域 | 警告，优先保留 | 检查结果与对比稿 |
| 必填资料缺失 | 阻断相关交付版本 | 跳转资料包补齐 |
| 专业判断边界 | 不自动给出结论 | 转人工或插件处理 |

### 10.4 状态规则

| 状态 | 含义 | 是否可作为已交付 |
| --- | --- | --- |
| 等待 | 未开始或输入不完整 | 否 |
| 预检中 | 正在检查依赖、资料与对象风险 | 否 |
| 待确认/被阻断 | 存在需修复或确认的问题 | 否 |
| 运行中 | 已冻结快照并执行 | 否 |
| 成功 | 所有必需产物成功发布 | 是 |
| 部分成功 | 主产物或部分版本成功，但存在辅助产物/批次失败 | 需人工判断 |
| 失败 | 未获得可用主结果 | 否 |
| 已取消 | 用户取消，未完成发布 | 否 |

## 13. 验收标准

以下为 V1.0 发布前的端到端验收主场景。每条均应有自动化测试或可重复的人工验收脚本。

### AC-01 通用 DOCX 快速生成

- 给定一个可读 DOCX、通用方案和默认模板；
- 当用户使用默认输出目录生成文档；
- 则输入文件哈希不变，输出目录出现最终 DOCX 和已启用的报告；
- 且最近结果可打开主产物与所在目录。

### AC-02 高风险对象阻断

- 给定包含宏或方案声明为阻断对象的文档；
- 当用户开始生成；
- 则系统在写入阶段前停止，展示发现对象、风险等级和建议动作；
- 且目标目录中不存在伪装为成功结果的半成品。

### AC-03 缺失资料修复闭环

- 给定一个需要必填字段或图片角色的方案，当前资料包缺失该项；
- 当用户执行预检；
- 则系统列出具体缺失项并可跳转到资料包对应位置；
- 当用户补齐并返回工作台重新检查；
- 则原任务上下文保留并可继续生成。

### AC-04 试卷多版本交付

- 给定包含题目、答案与解析的有效试题内容；
- 当用户同时生成学生卷和答案版；
- 则学生卷不包含答案和解析，答案版保留相应内容；
- 且两个版本使用不同文件名，不修改原始题目内容。

### AC-05 批量失败隔离

- 给定 10 条资料档案，其中 1 条缺少必填项；
- 当用户执行批量生成；
- 则 9 条有效记录可以成功发布，问题记录被单独标记失败或阻断；
- 且汇总报告准确列出成功、部分成功与失败数量；
- 修复后可只重试失败记录。

### AC-06 内置资源保护

- 给定任一内置方案或模板；
- 当用户尝试修改；
- 则系统要求先复制为用户资源，内置文件内容与修订保持不变；
- 用户副本可保存、再次打开并用于执行。

### AC-07 输出冲突保护

- 给定输出路径等于输入路径、多个预设解析到同一路径或目标文件被占用；
- 当用户开始生成；
- 则系统在发布前阻断对应任务或预设，并明确指出冲突路径；
- 不得覆盖输入或已存在的无关文件。

### AC-08 取消与原子发布

- 给定一个正在执行的长任务；
- 当用户请求取消；
- 则系统进入已取消状态，不再启动新阶段；
- 已完成的正式产物按事务规则处理，未完成产物不得出现在正式输出清单。

### AC-09 部分成功

- 给定主 DOCX 可正常写入，但某个辅助报告无法写入；
- 当任务结束；
- 则状态为部分成功，而不是成功；
- 主产物与失败辅助产物分别列出，错误信息不掩盖主产物路径。

### AC-10 本地隐私与问题报告

- 给定包含用户姓名、本地路径和正文内容的执行环境；
- 当用户导出问题报告；
- 则报告不包含文档正文，用户名与本地路径被隐藏；
- 未经用户主动操作，不发生文档网络上传。

### AC-11 CLI 安全边界

- 给定有效 DOCX 和显式方案/模板；
- 当通过 CLI 执行；
- 则使用与 GUI 相同的生产执行服务生成结果；
- 非 DOCX、不存在文件和执行失败返回非零退出码；
- 输入文件不被覆盖。

### 14.4 兼容性

- 发布平台：Windows 10/11 64 位。
- 开发运行时：Python 3.10+；正式用户优先使用打包版本。
- 文档格式：以 OOXML DOCX 为核心；复杂对象兼容性按预检结果降级。
- 精确 Word 版式、分页和部分对象处理可依赖本机 Microsoft Office；无 Office 时必须提供明确降级说明。
- 高 DPI、常见 Windows 缩放比例和中英文混排应纳入视觉验收。

### 14.5 可用性与可访问性

- 关键操作应有清晰名称、状态和焦点顺序，不只依赖颜色或图标表达。
- 错误提示应包含“发生了什么、影响什么、用户下一步做什么”。
- 窄窗口下核心操作不得被裁切；长列表和预览应保持滚动与当前项上下文。
- 文本与背景对比度、键盘导航、控件可访问名称和屏幕缩放应纳入发布检查。

### 14.6 可维护性与许可证

- 方案、模板、资料包和执行报告采用版本化结构，并为不兼容变更提供迁移或明确拒绝。
- UI 与 CLI 复用执行引擎、资源解析和安全检查。
- 项目源码按 MIT 发布；PySide6、Qt 及其他第三方组件继续遵循各自许可证并随包披露。
- 发布包必须通过公开发布扫描、依赖许可清单和严格工程门禁。

## 15. 数据、观测与支持

### 15.1 本地数据

应用需要持久化以下数据：

- 用户方案、模板、母版和资料包；
- 当前工作模式、最近选择和主题；
- 执行会话摘要、最近结果与产物路径；
- 日志、问题报告和必要的本地缓存；
- 内置资源的版本身份和用户副本的来源关系。

数据目录应与安装目录分离，卸载和升级时不得误删用户资源。需要为用户提供可理解的备份、导入和迁移路径。

### 15.2 观测事件建议

在不上传正文与敏感资料的前提下，本地记录以下结构化事件：

- 应用启动完成、启动失败；
- 模式切换、任务创建、预检完成；
- 问题类型与处置结果；
- 执行开始、取消、成功、部分成功、失败；
- 产物类型与发布状态；
- 批量总数、成功数、失败数与重试数；
- 预览引擎与降级原因；
- 配置迁移、冲突与恢复结果。

事件不得包含正文、字段值、完整文件名、用户名、密钥或可反推业务内容的附件信息。

## 17. 依赖与约束

### 17.1 关键技术依赖

- PySide6 / Qt：Windows 桌面界面与本地交互。
- python-docx、lxml：DOCX/OOXML 读写。
- Pillow：图片处理。
- markdown-it-py：Markdown 解析。
- openpyxl：XLSX 资料导入。
- pypdfium2：PDF 页面渲染或预览能力。
- pywin32 / Microsoft Office：Windows 上的部分精确布局探测与 Office 能力。
- PyInstaller：桌面发布包构建。

### 17.2 产品约束

- Word 的分页、域、目录、文本框、嵌入对象和第三方插件行为具有环境差异，无法只靠 OOXML 静态处理完全保证。
- 标准和机构规则可能更新；规则来源、版本和审核状态必须显式保存。
- 本地优先限制了统一云端指标与远程支持能力，需要通过脱敏报告和标准样本补足。
- 当前代码能力面很宽，V1.0 必须以用户可理解的顶层模式收敛，不应把内部覆盖矩阵直接当作市场功能清单。

## 18. 主要风险与待确认问题

### 18.1 主要风险

| 风险 | 影响 | 缓解建议 |
| --- | --- | --- |
| 产品定位与实现不一致 | 用户预期错误，测试范围失焦 | 发布前统一名称、定位、模式清单与 README |
| 场景数量膨胀 | 界面复杂、维护成本高、每个场景都不够深 | 顶层模式收敛，其他能力作为子场景/插件/边界能力 |

| GUI、CLI 和配置声明不一致 | 同一任务结果或支持格式不同 | 建立公开能力矩阵与共享执行契约测试 |
| Office 环境差异 | 预览和最终分页不一致 | 能力探测、降级说明、真实 Word 样本验收 |
| 用户资源版本迁移失败 | 升级后模板或资料包不可用 | 版本化结构、备份、迁移报告与失败回滚 |
| 批量任务误覆盖或串资料 | 大规模错误交付 | 每条快照隔离、路径唯一性检查、批量事务清单 |
| 缺少真实用户与运行指标 | 功能多但主流程不够易用 | 发布前完成角色访谈、5～8 人可用性测试和基线计时 |
