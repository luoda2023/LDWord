# Alavette Form V1.0 用户文档体系与教程制作蓝图

> 状态：建议执行基线
> 适用版本：Alavette Form V1.0
> 目标：把“功能说明书”重构为能帮助首次用户完成真实任务、遇到问题能够自救、后续可以持续维护的用户文档体系
> 本文不替代最终用户手册；它定义最终手册该写什么、怎么写、如何验收和如何随版本发布

## 1. 结论先行

V1.0 不应该继续制作一本从界面菜单开始、逐项解释所有控件的“大而全说明书”。更合理的做法是建立一套以用户任务为中心、由四类内容组成的文档体系：

1. **快速开始**：帮助完全不了解产品的用户在 10 分钟内生成第一份文档。
2. **任务教程与操作指南**：按“我想完成什么”组织，而不是按代码模块或界面面板组织。
3. **概念与参考**：解释工作模式、方案、模板、资料包、母版、交付预设之间的关系，并提供格式、状态和产物查询。
4. **排障与边界说明**：让用户能识别阻断、警告、部分成功、输出冲突及 Word 环境差异，并知道下一步该做什么。

最终用户看到的首要交付物建议为：

- 发布包根目录中的《快速开始》PDF；
- 可搜索的《完整用户手册》PDF；
- GitHub 仓库中的 Markdown 文档源；
- 后续版本再增加应用内上下文帮助或离线 HTML。

Markdown 应作为唯一内容源，PDF/DOCX/HTML 均由同一内容源生成，避免维护多份互相漂移的正文。

## 2. 本轮证据范围

本蓝图基于以下当前产品证据：

| 证据 | 用途 |

| `src/config/work_mode.py` | 当前可见工作模式和隐藏模式 |
| `src/ui/panel_specs.py` | 当前一级导航 |
| `src/ui/panels/workbench/` | 快速执行、预检、输出和结果反馈 |
| `src/ui/panels/scene_panel.py` | 方案配置及交付逻辑 |
| `src/ui/panels/template_panel.py` | 模板管理结构 |
| `src/ui/panels/assets_panel.py` | 资料包、记录、字段和生成检查 |
| `src/assistant/ui/` | AI 文档助手入口、模型选择、材料与确认流程 |

| `dist/Alavette-Form_V1.0/` | 当前发布包实际结构 |

用户提供的临时目录 `<LOCAL_PATH>` 已不存在，因此本文不能对旧说明书逐页点评。下面的诊断来自当前仓库、发布包和现有视觉素材，不虚构旧说明书内容。

## 3. 当前文档状态诊断

### 3.1 产品已经具备发布证据，但尚未形成用户文档产品

仓库中有大量 PRD、审计、架构和回归记录，却没有清晰、稳定的 `docs/user/` 用户文档入口。内部证据能证明产品做了什么，但不能直接回答首次用户最关心的五个问题：

1. 我该下载或打开哪个文件？
2. 第一次应该选择哪个模式？
3. 需要提前准备什么？
4. 怎样判断已经成功？
5. 如果被阻断，下一步去哪里修复？

这说明当前缺失的不是更多功能描述，而是从用户目标到产品操作的教学转换层。

### 3.2 当前发布包没有附带用户说明

`dist/Alavette-Form_V1.0/` 顶层目前包含可执行文件、许可证、第三方通知和运行依赖，但没有快速开始或用户手册。即使仓库里随后补写说明书，只要打包脚本不复制并校验文档，最终用户仍然无法看到。

### 3.3 开发者 README 不能充当最终用户手册

当前 README 主要包含源码安装、Python 环境、启动脚本、打包和许可证口径，适合开发者或源码使用者，不适合拿到 ZIP 发布包的普通用户。

同时，当前 `README.md` 中大量中文已呈现乱码，相关测试甚至仍以乱码文本作为断言。这是公开发布页面的质量问题，不能把 README 中现有中文直接复用到用户手册。

### 3.4 产品口径必须以当前运行时为准

当前运行时有四个 active 工作模式：

- 通用版；
- 试卷版；
- 论文版；
- 公文版。

标书版、技术文档版和报告版在注册表中为 hidden。V1.0 用户手册不应把它们写成用户可以直接选择的正式入口，也不应沿用旧 PRD 中“七个顶层模式全部可用”的描述。

### 3.5 现有流程图适合建立全局认知，不适合直接充当逐步教程

`docs/product/visuals/` 中的单文档、资料驱动、试卷、批量和 AI 流程图有较完整的业务分支，可用于：

- 章节开头的整体流程概览；
- 支持人员理解失败、修复和重试路径；
- 附录中的全流程参考。

但其中部分图片高度达到 1800～5400 像素，分支和回路较多，不适合放在一个具体操作步骤旁。逐步教程应将其拆成 3～6 节点的局部图，并配合真实界面局部截图。

### 3.6 现有 UI 截图不能直接用于正式手册

当前多张 UI 验证图中的中文显示为方框，说明截图环境没有正确加载中文字体。它们可以保留为内部布局证据，但不能进入正式用户手册。

正式截图必须在最终打包版本、正常中文字体环境和统一 DPI 下重新采集，并检查：

- 所有中文可读；
- 文本没有截断；
- UI 与最终版本一致；
- 不包含真实用户名、文件路径、API Key 或业务资料；
- 目标控件在裁剪后仍能从上下文中找到。

### 3.7 现有材料按“功能域”组织，用户实际按“任务”寻找答案

用户不会先思考“我要进入方案模块还是模板模块”，而会思考：

- 怎样快速整理一份已有 Word？
- 怎样生成学生卷和答案版？
- 怎样按单位资料生成公文？
- 为什么生成按钮不可用？
- 为什么提示缺少字段或高风险对象？
- 生成的文件在哪里？

文档必须先用任务语言回答这些问题，再在需要时解释方案、模板和资料包。

## 4. 什么才算“真正优秀”的教程

优秀教程不是文字多、截图多或视觉漂亮，而是读者能独立完成任务，并且完成后知道如何判断结果是否正确。

### 4.1 教学目标

每篇教程必须让读者完成一个可观察的结果。例如：

- 生成一份不覆盖原稿的新 DOCX；
- 同时生成学生卷和答案版；
- 补齐资料后从阻断状态恢复执行；
- 创建一个内置模板的用户副本并完成修改；
- 找到执行报告并理解“部分成功”。

禁止使用“了解工作台”“熟悉资料包”这类无法验收的目标作为教程标题。

### 4.2 最小完整闭环

一篇可执行教程至少包含：

1. **结果**：完成后会得到什么。
2. **准备**：需要的系统、文件、权限、资料和预期耗时。
3. **入口**：从应用中的哪个明确位置开始。
4. **步骤**：按实际操作顺序书写。
5. **即时反馈**：每个关键步骤后界面应出现什么。
6. **完成判断**：怎样确认成功。
7. **异常出口**：最可能遇到的阻断和跳转位置。
8. **下一步**：完成基础任务后适合继续学习什么。

### 4.3 内容类型必须分开

文档采用四分法：

| 类型 | 回答的问题 | 写法 |
| --- | --- | --- |
| 教程 Tutorial | 我第一次怎样完整做成一件事？ | 有明确起点、样例和终点，带领用户成功 |
| 操作指南 How-to | 我已经知道产品，怎样完成某个具体目标？ | 直接给最短可靠步骤 |
| 参考 Reference | 某个模式、状态、格式或产物具体是什么？ | 完整、准确、可查询 |
| 解释 Explanation | 为什么要区分方案、模板、资料包和母版？ | 解释关系、原则和边界 |

不要在“10 分钟快速开始”中插入完整字段表，不要在参考表里夹入长篇教程，也不要在排障页重新复制整套主流程。

### 4.4 量化验收

建议用 5～8 名接近目标用户的人完成发布前测试，并记录：

| 指标 | V1.0 建议门槛 |
| --- | ---: |
| 无人协助完成“生成第一份文档” | ≥ 80% |
| 从解压发布包到看到成功回执的中位时间 | ≤ 10 分钟 |
| 能找到输出文件 | 100% |
| 能确认原稿未被覆盖 | 100% |
| 遇到缺资料阻断后能找到修复入口 | ≥ 80% |
| 能正确区分方案、模板和资料包 | ≥ 80% |
| 教程中的 UI 名称与最终版本一致 | 100% |
| 失效链接、缺图、乱码和泄露信息 | 0 |

首次测试先记录基线，不为了达成目标而隐藏失败。若多数用户在同一步失败，应优先修正 UI 或教程结构，而不是继续增加解释段落。

## 5. 文档受众与优先级

### 5.1 第一优先：文档经办人

特征：

- 熟悉业务内容；
- 不一定理解 Word 样式、域、分节或编号；
- 希望快速、安全地得到可交付文件。

他们的主路径必须出现在文档最前面。

### 5.2 第二优先：模板与规则维护者

需要学习：

- 方案决定做什么；
- 模板决定长什么样；
- 资料包决定填什么；
- 母版决定内容装到哪里；
- 内置资源为什么要先创建用户副本。

这部分应放在完成首次任务之后，避免首次用户被大量配置淹没。

### 5.3 第三优先：批量操作员与支持人员

需要学习：

- 批量资料选择、单项隔离和失败项重试；
- 执行报告、日志和脱敏问题报告；
- 环境差异、输出占用和高风险对象；
- 如何收集可复现信息而不泄露文档内容。

### 5.4 开发者不进入同一本用户手册主线

源码安装、Python 环境、CLI、打包、测试和许可证生成仍放在仓库 README 或开发者指南中。用户手册可以提供一个“高级：命令行”附录，但不能让普通用户先安装 Python。

## 6. 推荐的信息架构

### 第 0 部分：开始之前

1. Alavette Form 能做什么
2. V1.0 当前支持的四个工作模式
3. 不会做什么：不替代 Word、不保证专业内容正确、不承诺绝对合规
4. 本地处理、原稿保护和联网边界
5. 系统要求和发布包结构

控制在 2～3 页。所有免责声明只写最必要内容，其余放到对应任务和边界章节。

### 第 1 部分：10 分钟快速开始

唯一目标：使用通用版对一个示例 DOCX 完成一次安全生成。

1. 解压完整发布包；
2. 启动 `Alavette-Form_V1.0.exe`；
3. 确认工作模式为“通用版”；
4. 在“工作台 > 快速执行”中添加 DOCX；
5. 选择处理方案和模板；
6. 选择输出目录；
7. 点击“生成文档”，按需确认风险；
8. 在成功回执中打开文档或输出目录；
9. 检查新文档存在且原稿未改变。

这部分应能独立打印或作为单独 PDF 放到发布包根目录。

### 第 2 部分：按场景完成第一次任务

每个当前 active 模式一篇独立教程：

1. **通用版：整理一份已有 Word 文档**
2. **试卷版：生成学生卷和答案速查**
3. **论文版：按论文模板整理标题、目录和正文**
4. **公文版：选择文种并用资料生成正式文档**

每篇使用专用样例，不要求读者先创建复杂模板或资料包。教程目标是体验模式的默认可靠路径。

### 第 3 部分：AI 文档助手

AI 文档助手应作为独立、可选的任务入口，不与确定性排版教程混写。

建议章节：

1. 配置模型连接；
2. 描述文档目标；
3. 添加当前支持的 DOCX 材料；
4. 阅读任务识别、内容计划和权限确认；
5. 确认后进入本地文档生产；
6. 查看产物和结果说明；
7. 理解模型数据、API 提供方、材料发送和专业边界。

必须明确区分：

- 模型生成或理解内容；
- Alavette Form 在本地执行确定性的文档生产；
- 用户确认；
- 第三方模型服务的数据处理边界。

不要用“智能完成一切”作为宣传口径。

### 第 4 部分：常用操作指南

按任务命名，建议至少包括：

- 更换当前工作模式；
- 选择或更换处理方案；
- 选择模板；
- 选择输出目录；
- 查看最近一次结果；
- 取消正在执行的任务；
- 创建内置方案的用户副本；
- 创建内置模板的用户副本；
- 修改页面、正文、标题编号、表格和页眉页脚；
- 新建资料包和资料记录；
- 填写字段、图片、附件和时间计划；
- 执行资料生成检查；
- 修复缺少的资料并返回执行；
- 批量生成并重试失败项；
- 导出脱敏问题报告；
- 切换主题和设置模型；
- 使用 CLI 处理单个 DOCX（高级）。

### 第 5 部分：理解核心对象

用一张简单关系图和一个贯穿示例解释：

```text
工作模式
  └─ 决定当前业务入口和可见资源
      ├─ 方案：处理什么、采用什么风险策略、交付哪些版本
      ├─ 模板：页面和样式长什么样
      ├─ 母版：固定结构和占位符装在哪里
      └─ 资料包：字段、图片、附件和多份记录填什么
             ↓
        执行会话冻结配置
             ↓
        生成 DOCX、报告和其他交付物
```

这一章的目标不是讲实现细节，而是消除“方案和模板有什么区别”“资料包为什么不是模板”的认知障碍。

### 第 6 部分：结果、风险与排障

按用户看到的状态组织：

| 用户看到的状态 | 需要回答 |
| --- | --- |
| 待执行 | 还缺少什么 |
| 正在执行 | 当前阶段、能否取消 |
| 成功 | 产物在哪里、怎样复核 |
| 部分成功 | 哪个辅助产物失败、主文档是否保留 |
| 已取消 | 哪些正式产物已保留 |
| 失败 | 原因、修复入口、是否需要重试 |
| 阻断问题 | 为什么不能继续、怎样修复 |
| 风险警告 | 继续意味着什么、何时应返回 |

重点排障条目：

- 文件不存在或无权限；
- 不支持的文件类型；
- 方案、模板、母版不兼容；
- 必填资料缺失；
- 宏、修订、批注、隐藏文本、文本框或嵌入对象；
- 输出文件正在被 Word/WPS 占用；
- 输出目录无权限或空间不足；
- Word 精确预览不可用；
- 中文字体或分页与目标电脑不同；
- AI 模型没有配置、连接失败或材料已失效；
- 批量任务部分失败。

### 第 7 部分：参考

适合快速查询的内容：

- 四个 active 模式能力矩阵；
- 支持的输入格式与用途；
- 产物类型；
- 文件命名和输出位置；
- 资料类型与必填状态；
- 执行状态定义；
- 日志和本地数据目录；
- 隐私、许可证和第三方组件；
- 已知限制；
- 版本变更记录。

## 7. “10 分钟快速开始”的页面设计

### 7.1 开篇

标题：**生成你的第一份规范化文档**

导语只保留三句话：

- 本教程会使用通用版处理一份 DOCX。
- 结果写入新目录，不会覆盖原稿。
- 预计需要 5～10 分钟。

### 7.2 准备清单

- Windows 10/11 64 位；
- 已完整解压的发布包；
- 一份不含敏感信息的测试 DOCX；
- 一个可写入的输出文件夹；
- 建议关闭正在占用该测试文件的 Word 或 WPS。

### 7.3 步骤模板示例

#### 步骤 1：添加要处理的文档

在 **工作台** 的 **快速执行** 中，将 DOCX 拖到文件区域，或点击 **浏览选择**。

**你会看到：** 文件名和所在目录出现在文件区域中。

**如果没有出现：** 确认文件扩展名为 `.docx`，并确认文件仍然存在。

此处只配一张局部截图，标出文件区域和“浏览选择”，不放整张应用窗口。

#### 步骤 2：确认方案和模板

在 **处理方案** 和 **模板** 中保留默认项，第一次不修改高级设置。

**你会看到：** 页面摘要中显示当前方案和模板。

#### 步骤 3：选择输出位置

在 **输出位置** 中选择一个空文件夹。

**你会看到：** 输出路径预览更新。

#### 步骤 4：生成文档

点击 **生成文档**。如果出现风险确认，先阅读对象类型和处置说明，再决定继续或返回修改。

**你会看到：** 读取文件、检查风险、套用模板、生成报告和输出文件的进度。

#### 步骤 5：检查结果

任务完成后，点击 **打开文档** 或打开输出目录。

完成标准：

- 输出目录中有新的 DOCX；
- 可以用 Word 或 WPS 打开；
- 原始 DOCX 仍位于原位置且未被覆盖；
- 成功回执或报告中可以看到产物路径。

### 7.4 结束页

只提供三个下一步：

- 想调整版式：进入“修改模板”；
- 想填入字段和图片：进入“使用资料包”；
- 遇到阻断：进入“根据执行问题修复并返回”。

不要在快速开始结尾罗列所有功能。

## 8. 每篇操作文档的统一模板

```markdown
# 用动词描述结果

一句话说明完成后会得到什么。

## 开始之前

- 权限、输入、资料、版本、预计耗时

## 操作步骤

1. 在哪个明确位置执行什么动作。
   - 预期结果：
   - 如果不一致：
2. ...

## 完成检查

- [ ] 可以观察到的结果
- [ ] 原稿或用户资料没有被误改

## 常见问题

- 只列与本任务直接相关的 2～4 个问题

## 下一步

- 最多 3 个相关入口
```

编写规则：

- 一篇只解决一个用户目标；
- 优先 3～7 个步骤，超过 9 个步骤时拆成子任务；
- 一个编号步骤只承载一个主要决策；
- 先写动作发生的位置，再写动作；
- 先写目标，再写实现目标的操作；
- 关键步骤写出预期界面反馈；
- 可选步骤以“可选：”开头；
- UI 文本使用粗体，文件名和扩展名使用等宽格式；
- 不使用“点击左边那个按钮”“见下图红框”等依赖方向或颜色的表达；
- 不重复已有完整操作，通过链接复用。

## 9. 截图与图示策略

### 9.1 截图不是装饰

只有满足至少一个条件时才使用截图：

- 入口难找；
- 多个名称相似的资源容易选错；
- 用户需要核对某个状态；
- 风险确认或修复路由需要建立信心；
- 文字描述明显比局部图更费力。

纯粹展示应用“长什么样”的大图只放在产品概览，不要在每个步骤重复。

### 9.2 正式截图规范

- 使用最终打包 EXE，而不是开发环境窗口；
- 固定 Windows 缩放比例和应用窗口尺寸；
- 推荐以 1920×1080、100% 或 125% 缩放采集，再裁剪；
- 一个截图只突出一个主要目标；
- 保留足够上下文，让用户知道目标在哪个页面；
- 使用编号标记或单色描边，不同时使用大量箭头、阴影和高饱和色；
- 标记不能覆盖 UI 文本；
- 不仅用红/绿区分状态；
- 所有路径、用户名、文档名和业务资料使用专用演示数据；
- 截图文件名稳定，例如 `QS-04-generate-document.png`；
- 每张图记录产品版本、提交、模式、页面、缩放和采集日期；
- 版本发布前逐图检查中文字体、裁剪、清晰度和 UI 漂移。

- 图中信息必须在正文中有文字等价说明；
- 图标题说明它帮助读者判断什么，而不是只写“流程图”。

## 10. 语言、术语和提示规范

### 10.1 统一术语

| 使用 | 避免 |
| --- | --- |
| 工作模式 | 版本、场景版、工作区混用 |
| 处理方案 | 规则模板、场景模板 |
| 模板 | 格式方案 |
| 母版 | 模板文件、底稿随意混用 |
| 资料包 | 数据包、资产包、素材包混用 |
| 资料记录 | 档案、条目、实体随意混用 |
| 输出目录 | 保存路径、发布路径无区分 |
| 生成文档 | 开始、运行、发布在同一步混用 |
| 阻断 | 报错、失败、风险警告混用 |
| 部分成功 | 成功但有点问题 |

术语表应由产品代码中的可见名称反向生成或定期核对。

### 10.2 语气

- 使用直接、平静、负责的表达；
- 告诉用户下一步能做什么；
- 不责怪用户；
- 不用“显然”“只需”“非常简单”；
- 不把风险提示写成恐吓；
- 不承诺“完全自动合规”“任何文档都能处理”；
- 不把内部类名、schema、payload 或测试编号暴露给普通用户。

### 10.3 提示等级

| 等级 | 用途 | 示例 |
| --- | --- | --- |
| 提示 | 提高效率，不影响正确性 | 第一次可以保留默认模板 |
| 注意 | 容易忽略，但可以恢复 | 切换模式会改变可见资源 |
| 重要 | 可能导致任务失败或结果不符合预期 | 请先关闭正在占用输出文件的 Word |
| 警告 | 可能造成数据、隐私或专业风险 | 确认材料是否会发送给第三方模型服务 |

同一页避免连续堆叠多个提示框。

## 12. 发布包接入

V1.0 打包流程需要增加明确的文档门禁：

1. 构建用户文档；
2. 检查两个 PDF 存在且非空；
3. 检查文档版本为 V1.0；
4. 将其复制到 `dist/Alavette-Form_V1.0/`；
5. 在压缩前验证发布包根目录包含：
   - `Alavette-Form_V1.0.exe`
   - `快速开始.pdf`
   - `用户手册.pdf`
   - `LICENSE`
   - `THIRD_PARTY_NOTICES.md`
6. 若文档缺失则打包失败，不允许只警告后继续。

建议再增加一个很短的 `请先阅读.txt`，内容只包括：

- 请先完整解压；
- 双击哪个 EXE；
- 快速开始和完整手册在哪里；
- 文档默认本地处理；
- 支持或问题报告入口。

## 13. 制作执行计划

### 阶段 A：冻结产品事实

完成条件：

- 确认产品名为 Alavette Form V1.0；
- 确认四个 active 模式；
- 确认最终导航和按钮文案；
- 确认 AI 文档助手对外状态；
- 确认发布包为便携 ZIP、安装包或两者；
- 确认系统要求和 Word/WPS 依赖口径；
- 选定一个用于截图和文档验收的候选构建。

在此阶段完成前，不批量截图。

### 阶段 B：建立样例与主路径

产物：

- 一份无敏感信息的通用 DOCX；
- 一份结构化试题样例；
- 一份论文样例；
- 一份公文样例和演示资料包；
- 一个固定演示输出目录；
- 每个样例的预期产物清单。

样例必须与手册一起版本化。没有可复现样例的教程不可发布。

### 阶段 C：先写快速开始

先用纯文字和占位图完成快速开始，再由一名未参与开发的人执行。

只有当文字路径能跑通时才采集正式截图。避免先拍大量图片，再强行围绕图片写步骤。

### 阶段 D：完成四个模式教程和 AI 教程

顺序建议：

1. 通用版；
2. 试卷版；
3. 公文版；
4. 论文版；
5. AI 文档助手。

顺序可根据正式首要用户调整，但不能同时开写所有章节而没有统一模板。

### 阶段 E：补齐操作指南、概念和排障

来源：

- 真实可用性测试卡点；
- P0 AC-01～AC-11；
- UI 中真实阻断和修复路由；
- 支持人员最需要用户提供的信息；
- 当前已知限制。

不要根据功能列表机械生成 100 篇短页面。

### 阶段 F：视觉制作和多格式输出

- 在最终候选构建采集截图；
- 完成局部标注和脱敏；
- 生成 PDF/DOCX；
- 逐页渲染检查；
- 检查书签、目录、页码、交叉引用和图片清晰度；
- 检查黑白打印和高缩放可读性；
- 为复杂图提供文字说明。

### 阶段 G：可用性测试与发布门禁

让 5～8 名目标用户完成：

1. 找到并启动应用；
2. 完成第一份通用文档；
3. 找到输出；
4. 解释原稿是否被修改；
5. 处理一次缺资料或输出占用；
6. 找到相应排障页。

记录每个停顿点、误选、返回和求助，不只记录最终成功或失败。

## 14. 文档质量门禁

### 14.1 内容正确性

- [ ] 所有正式模式来自当前运行时；
- [ ] 所有 UI 名称与候选构建一致；
- [ ] 输入和产物能力没有超出实现；
- [ ] 隐藏模式没有被宣传为正式入口；
- [ ] 原稿保护、风险处置和 AI 数据边界准确；
- [ ] 示例结果可以复现。

### 14.2 教学可用性

- [ ] 每篇教程只有一个可验收目标；
- [ ] 开始条件完整；
- [ ] 每个关键动作有预期结果；
- [ ] 至少覆盖最常见失败出口；
- [ ] 完成检查可观察；
- [ ] 快速开始不依赖读者先理解高级概念。

### 14.3 视觉与可访问性

- [ ] 无乱码、方框字、裁剪和模糊；
- [ ] 不用颜色作为唯一信息；
- [ ] 截图中的敏感信息已清理；
- [ ] 复杂流程图有文字等价说明；
- [ ] 标题层级和阅读顺序正确；
- [ ] PDF 目录、书签和链接可用；
- [ ] 图片在 100% 显示和打印时可读。

### 14.4 发布一致性

- [ ] 文档版本和应用版本一致；
- [ ] 截图清单记录候选构建；
- [ ] 发布包包含快速开始和完整手册；
- [ ] README 链接到用户文档；
- [ ] 已知限制与发行说明一致；
- [ ] 打包脚本在文档缺失时失败；
- [ ] 文档变更已进入版本控制。

## 15. 维护机制

### 15.1 文档所有权

每篇文档需要元数据：

- owner；
- last_verified_version；
- last_verified_commit；
- related_ui；
- related_tests；
- screenshot_ids。

产品文案或导航变化时，相关文档必须进入评审清单。

### 15.2 更新触发器

出现以下变化时必须评估文档更新：

- 工作模式状态变化；
- 一级导航、页面名、按钮名变化；
- 快速执行步骤变化；
- 方案、模板、资料包关系变化；
- 输入格式或产物变化；
- 风险确认、失败状态或修复路由变化；
- AI Provider、材料发送和确认流程变化；
- 发布包结构和启动方式变化。

### 15.3 发布后反馈

建议在脱敏问题报告之外增加“文档反馈”模板，至少收集：

- 用户想完成什么；
- 使用的手册章节；
- 卡在哪一步；
- 实际界面或结果；
- 期望看到什么；
- 应用版本；
- 是否允许附带脱敏截图。

## 16. 仍需产品负责人确认的五个问题

这些问题会实质改变最终手册，不应由文档作者静默猜测：

1. V1.0 对外发布的是便携 ZIP、安装包，还是同时提供两种？
2. 第一目标用户是通用文档经办人、论文用户、教师，还是单位公文经办人？
3. AI 文档助手在 V1.0 中属于正式功能、测试功能，还是需要显式标注为可选功能？
4. Microsoft Word 是必需、推荐还是只用于增强预览？WPS 的正式支持口径是什么？
5. 用户支持渠道是什么：GitHub Issues、邮箱、内置问题报告，还是其他渠道？

在没有结论前，可以先完成“通用版快速开始”和通用排障，但不要发布带有猜测的安装、AI 隐私或支持承诺。

## 17. 推荐的下一步

最合理的实际执行顺序是：

1. 修复 README 中文编码和公开口径；
2. 确认上述五个产品问题；
3. 建立 `docs/user/` 和演示样例；
4. 只写《10 分钟快速开始》第一版；
5. 用最终候选构建让 3 名非开发人员试跑；
6. 根据卡点改写后，再扩展四个模式教程；
7. 最后补齐完整参考、排障和 PDF 视觉设计；
8. 将用户文档纳入打包失败门禁。

如果资源有限，宁可先交付一份经过真实用户验证的 8～12 页快速开始，也不要先做一本 80 页但无人能顺利完成第一项任务的功能百科。
