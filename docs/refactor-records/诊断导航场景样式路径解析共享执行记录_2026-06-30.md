# 诊断导航场景样式路径解析共享执行记录

日期：2026-06-30

## 1. 本轮目标

上一轮已经把模板详情和场景详情里的普通场景样式路径解析收口到：

```python
scene_style_navigation_target_from_field_id(...)
scene_style_policy_key_from_field_id(...)
```

但执行问题队列使用的诊断导航层仍然保留了一套独立解析：

```text
scene.section_styles.<variant>.<field>
section_styles.<variant>.<field>
<variant>.<field>
<variant>
```

这意味着用户从模板、场景、执行问题队列进入同一项时，表面链路已经打通，底层路径语义仍有漂移风险。

本轮目标是把诊断导航层的“普通分区样式路径”也迁移到共享 helper，同时保留诊断层自己的错误原因判断。

## 2. 修改前的问题

`src/ui/adapters/workbench_issue_navigation.py` 原本直接依赖：

```python
STYLE_VARIANTS
```

并在 `_workbench_scene_style_focus_projection(...)` 内部自行判断：

```text
是否是 scene.section_styles 前缀
是否是 section_styles 前缀
variant 是否存在
是否是 <variant>.<field>
是否是纯 <variant>
```

这和模板详情、场景详情已经抽走的解析逻辑重复。

## 3. 本轮实现

### 3.1 诊断层接入共享 helper

`workbench_issue_navigation.py` 现在引入：

```python
scene_style_navigation_target_from_field_id
```

普通路径统一交给配置层解析：

```text
scene.section_styles.references_body.font_cn
section_styles.references_body.line_spacing_value
references_body.special_indent_mode
references_body
scene.section_styles.references_body
```

诊断层拿到 `(variant_key, editor_field)` 后，再决定：

```text
editor_field 为空 -> style_variant_toggle
editor_field 不为空 -> style_variant
field 不合法 -> unknown_style_field
```

### 3.2 删除诊断层对 STYLE_VARIANTS 的直接依赖

本轮移除：

```text
from src.config.style_variant_semantics import STYLE_VARIANTS
_scene_style_variant_ids(...)
```

这样场景样式 variant 的身份判断不再散落到诊断导航层。

### 3.3 抽出 toggle 投影 helper

新增：

```python
_workbench_scene_style_toggle_projection(...)
```

它只负责把一个已解析出的 `variant_key` 表达成诊断导航投影：

```text
normalized_key = scene.section_styles.<variant>
focus_kind = style_variant_toggle
display_label = 对应分区名称
```

这让当前职责更清楚：

| 层 | 职责 |
| --- | --- |
| `style_field_descriptors.py` | 解析普通路径里的 variant 与 editor field |
| `workbench_issue_navigation.py` | 判断诊断投影、错误原因、规范化 target key |

## 4. 行为统一

本轮后，以下入口对普通路径的理解一致：

| 入口 | 结果 |
| --- | --- |
| 模板正文样式详情 | 定位只读 policy 行 |
| 场景分区样式详情 | 切换分区并高亮字段 |
| 执行问题队列诊断导航 | 生成 scene field focus projection |

示例：

```text
scene.section_styles.references_body
```

现在在诊断层也被识别为：

```text
focus_kind = style_variant_toggle
normalized_key = scene.section_styles.references_body
```

这和模板详情、场景详情对同一路径的理解一致。

## 5. 保留在诊断层的边界

### 5.1 通配符仍由诊断层单独判断

```text
scene.section_styles.*.line_spacing_value
```

`*` 不是真实 variant key。共享 helper 不处理它，诊断层继续将它表达为：

```text
focus_kind = style_wildcard
normalized_key = scene.section_styles.*.line_spacing_pt
```

### 5.2 错误原因仍由诊断层负责

诊断层继续保留：

```text
unknown_style_variant
unknown_style_field
missing_style_field
not_scene_style_field
```

这些不是纯路径语义，而是面向审计和问题队列的解释结果，不应该下沉到配置层。

## 6. 代码落点

| 文件 | 变更 |

| `tests/test_workbench_issue_navigation.py` | 新增带前缀 policy toggle、短路径 alias、结构复用守门 |

## 7. 当前效果

现在场景样式路径语义已经贯穿三层：

```text
style_field_descriptors
  -> template_style_detail
  -> scene_panel
  -> workbench_issue_navigation
```

这使“模板管理、场景规划、执行问题队列”不再各自维护一套分区样式路径解释。

路径解析统一只是链路底座。用户看到的页面还需要继续收敛为：

```text

editor

```

## 9. 本轮结论

本轮把“执行问题队列如何理解场景分区样式路径”接入了与模板、场景相同的共享语义入口。

这不是视觉层改动，但它直接影响后续交互能否稳定：用户从任何入口点到同一分区、同一字段，都应该得到同一个 normalized key、同一个 policy key 和同一类高亮反馈。
