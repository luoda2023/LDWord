# 请求样本筛选控件共享契约执行记录

日期：2026-06-29

## 1. 本轮结论

上一轮已经把样本和请求样本的显示名、tooltip、证据编号下沉到共享投影层。但继续审计后发现，还有一个会导致界面慢慢分叉的点：请求样本筛选控件。

场景面板和 Workbench 里各自复制了一份筛选项：

```text
all / direct_family_fixture / manual_boundary_fixture / ambiguous_fixture_set / negative_control / pack_fixture_proxy
```

它们当前看起来一致，但这种一致靠复制维持，不靠契约维持。后续只要新增一个覆盖方式，或者把“全部”改成更明确的“全部说法”，就可能出现：

- 场景页能筛，Workbench 不能筛；
- Workbench 文案更新，场景页仍旧；
- 测试只覆盖其中一个入口，另一个入口悄悄漂移。

本轮把筛选项和筛选匹配逻辑都收进 `scene_summary_projection.py`，让它们和请求样本覆盖方式显示名同源。

## 2. 与模板管理一致性的关系

模板管理的成熟点不是“每个页面长得一样”，而是相同概念只有一个投影来源：

- 样式来源只有一个投影；
- 样式差异只有一个摘要 slot；
- 执行回执只消费统一 projection；
- 控件只负责渲染，不私自解释业务枚举。

请求样本筛选也应该遵守同一规则：

| 层 | 职责 |
| --- | --- |
| 投影层 | 定义筛选项、显示名、匹配规则 |
| 场景面板 | 渲染下拉框和列表 |
| Workbench | 渲染下拉框和列表 |
| 测试层 | 验证两个入口消费同一契约 |

这样“筛选控件一致性”不再是视觉巧合，而是代码结构保证。

## 3. 已落地调整

### 3.1 新增共享筛选契约

文件：`src/ui/panels/scene_summary_projection.py`

新增：

- `REQUEST_CELL_FILTER_ALL_ID`
- `REQUEST_CELL_FILTER_OPTIONS`
- `scene_request_cell_filter_options()`
- `scene_request_cell_matches_filter(...)`

当前选项：

| filter id | 显示名 |
| --- | --- |
| `all` | 全部说法 |
| `direct_family_fixture` | 直接证据 |
| `manual_boundary_fixture` | 人工确认 |

## 5. 当前边界

已归一：

- 请求样本显示名。
- 请求样本 tooltip。
- 请求样本筛选项。
- 请求样本筛选匹配逻辑。
- 场景页与 Workbench 的请求样本浏览主路径。

仍需继续：

1. 抽 `SampleEvidenceBlock`，把样本详情、生成样本库、打开证据、请求筛选和列表组织为共享组合块。
2. 把 tooltip 中较长的证据编号、manual gate、路径信息升级为可展开证据面板。
3. 将请求样本计数文案也投影化，例如 `5/5` 是否应改为“5 条说法 / 共 5 条”，避免 Workbench 和场景页继续使用不同计数表达。
4. 给空态补共享投影，例如“当前筛选没有请求说法”，不要让每个面板自己写空态。

## 6. 设计判断

这轮改动很小，但边界意义很大：它把“筛选控件”也纳入共享契约，避免只统一列表项文案、却让下拉选项继续散落在页面里。

从优秀设计的角度看，控件复用不应该止于 UI 类复用，还要包括：

- 枚举来源复用；
- 显示名复用；
- 筛选语义复用；
- 空态和计数语义复用；
- 证据层入口复用。

本轮完成的是其中第三步。下一步应该继续把“请求样本浏览”从零散控件推进成共享 block。
