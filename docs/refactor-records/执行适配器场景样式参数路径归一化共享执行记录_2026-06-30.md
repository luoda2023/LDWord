# 执行适配器场景样式参数路径归一化共享执行记录

日期：2026-06-30

## 1. 本轮目标

上一轮已经把执行问题队列的诊断导航接入共享场景样式路径 helper。但执行适配器在生成问题项时，仍有一段私有归一化：

```python
_normalize_scene_style_field_path(...)
```

它只做前缀拼接：

```text
section_styles.references_body.font_cn
-> scene.section_styles.references_body.font_cn
```

没有复用 `style_field_descriptors.py` 中已经建立的普通路径语义。

本轮目标是让执行问题证据生成侧也复用同一个 helper。

## 2. 本轮实现

`src/ui/adapters/workbench_execution_adapter.py` 现在引入：

```python
scene_style_navigation_target_from_field_id
canonical_paragraph_style_field_id
```

普通有效路径会先走共享 helper：

```text
section_styles.references_body.line_spacing_value
-> references_body + line_spacing_value
-> scene.section_styles.references_body.line_spacing_pt
```

如果 helper 无法识别，则继续走原来的前缀兜底：

```text
scene.section_styles.*.line_spacing_pt
scene.section_styles.not_a_variant.font_cn
```

这样通配符和未知路径不会被提前丢弃，仍可进入诊断导航层，由那里给出更准确的错误原因或通配符定位。

## 3. 边界判断

执行适配器只负责把参数证据变成可路由 target，不负责判断控件是否真实存在。

| 情况 | 当前处理 |
| --- | --- |
| 已知 variant + 字段 alias | 规范化为 canonical 字段 |
| 已知 variant + 未知字段 | 保留未知字段，交给诊断层报错 |
| 通配符 `*` | 保留原路径，交给诊断层处理 |
| 未知 variant | 保留原路径，交给诊断层报错 |

这保持了职责边界：

```text
execution_adapter：从证据推断 target
workbench_issue_navigation：验证 target 并说明原因
style_field_descriptors：提供普通路径解析与字段 alias
```

## 4. 代码落点

| 文件 | 变更 |
| --- | --- |
| `src/ui/adapters/workbench_execution_adapter.py` | `_normalize_scene_style_field_path(...)` 复用共享 helper，并规范化字段 alias |
| `tests/test_workbench_execution_center.py` | 增加短路径 alias 进入执行问题项后的 canonical target 断言；增加源码守门 |

## 5. 当前效果

现在同一条参数路径能贯穿：

```text
执行诊断 payload
-> WorkbenchIssueItem.repair_target_key
-> workbench_issue_navigation focus projection
-> ScenePanel / TemplatePanel 实际高亮
```

并且普通路径语义来自同一处：

```text
src/config/style_field_descriptors.py
```

## 6. 后续重点

路径语义已经基本收口。下一步更应该回到用户可见层：

```text
场景概览首屏减少内部 key 与契约词
样式板块按 source / policy / editor / preview / receipt 重排
模板、场景、执行复核对同一 policy key 使用同一当前态和同一人话摘要
```

## 7. 本轮结论

本轮把执行问题证据生成侧也接到了共享路径语义上。

这让“执行发现问题 -> 生成 repair target -> 打开场景样式控件 -> 高亮同一字段”的链路更稳定，也减少了未来字段 alias 或分区路径新增时需要同步修改的地方。
