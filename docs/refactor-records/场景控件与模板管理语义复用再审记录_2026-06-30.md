# 场景控件与模板管理语义复用再审记录

日期：2026-06-30

## 1. 本轮结论

这轮继续审视“场景规划为什么仍不像模板管理一样好懂”。结论不是控件样式完全没有复用，而是复用停在了外观层和一部分样式对象层：

- 已复用：`template_form_row`、统一按钮 variant、统一输入框尺寸、`StyleManagementBlock`、`StylePolicyControlDeck`、样式预览 surface、诊断跳转和执行前复核的样式路径解析。
- 未完全复用：场景规划里非样式能力，尤其是“输入资料 / 资料规则 / 交付输出”的用户语言、控件分组、主次层级和修复动作语义。

换句话说，当前不是“控件不好看”的问题，而是“控件背后的对象语言还不稳定”。模板管理讲的是页面、排版、标题、表格、页眉页脚；场景规划有些地方还在讲 schema、DOCX、unknown、preset、module list。这会让用户感觉像在操作内部配置，而不是在规划一个业务场景。

## 2. 与模板管理的对比

| 维度 | 模板管理当前模式 | 场景规划当前状态 | 问题判断 |
| --- | --- | --- | --- |
| 对象命名 | 页面、排版、标题、表格、页眉与页脚 | 已有“输入、交付、资料规则”，但仍混入 schema / DOCX | 业务对象和技术对象混排 |
| 控件结构 | 一行一个参数，左侧标签稳定，右侧控件直接表达操作 | 多数详情页已用同一套 FormRow | 结构复用基本到位 |
| 操作语言 | 执行、跳过、编辑、导入导出 | 仍有替换未知、清理未知、每行一个 schema | 动作词不够像用户语言 |
| 状态摘要 | 当前值、来源、预览结果清楚 | 已逐步改成“已启用 / 已跳过 / N 项设置” | 导航层明显改善 |
| 预览关系 | 参数变化能在样式预览里验证 | 样式链路较完整，资料与输出链路仍偏表单 | 非样式能力缺少同等预览模型 |
| 诊断跳转 | 问题能回到对应控件 | 样式路径已打通，资料规则也能定位 | 跳转链路有，但入口文案仍生硬 |

## 3. 链路打通度

### 3.1 样式链路

样式链路已经接近模板管理的成熟形态：

```text
模板样式参数
-> 场景分区覆盖
-> 样式策略控件
-> 样式预览
-> 执行前复核
-> 诊断问题回跳
```

当前已具备的关键条件：

- 样式字段路径解析已共享，场景、模板、执行适配器和诊断导航不再各自解析。
- 场景样式控件已经通过 block 暴露语义 API，不再要求页面层直接了解字段编辑器内部结构。
- 执行前复核已经能复用只读策略控件和预览 surface。

剩余问题主要是内容组织，而不是底层链路：

- 样式控件仍需要更稳定的“模板继承 / 场景独立 / 与模板一致 / 与模板不同”四态表达。
- 详情页里高级证据和可编辑控件需要进一步分层，避免用户把审计字段当成必须配置项。

### 3.2 输入资料链路

输入资料链路功能上已经可用：

```text
场景选择资料规则
-> 输入资料要求写入 scene.input_source_profile
-> schema registry 校验
-> 缺失规则提示
-> 可替换或移除未识别规则
-> 执行侧读取资料字段与图片角色
```

但体验上仍落后一截，原因是它把工程词放进了用户第一接触层：

```text
每行一个 schema，例如 signature_assets_v1
替换未知
清理未知
```

这些表达的问题：

- `schema` 是实现名，用户真正理解的是“资料规则”。
- `未知` 没有说明“系统未识别这个规则”，像是用户做错了。
- `清理` 听起来可能会删除真实资料，动作边界不清楚。

本轮已把这些入口改成：

```text
从上方选择资料规则，或输入规则 ID
每行一个资料规则；建议用上方“加入列表”
替换未识别
移除未识别
```

这里保留“规则 ID”是刻意的：高级用户仍可能需要手填配置 ID，但不再用 `contract_parties_v1` / `signature_assets_v1` 作为教程式示例。

### 3.3 交付输出链路

交付输出链路上一轮已经从 “最终 DOCX / 对比 DOCX” 改成 “最终 Word / 对比 Word”。这个方向正确，因为用户配置的是交付版本，不是文件扩展名。

当前仍要继续注意：

- 主控件使用 Word、报告、资料清单、资料包。
- 文件路径、产物名、执行日志可以保留 `.docx` 和内部变量。
- 变量插入和显隐规则属于高级配置，不应该和最终交付开关混成同一密度。

### 4.2 改动细节

| 原文案 | 新文案 | 设计理由 |
| --- | --- | --- |
| 替换未知 | 替换未识别 | 表达系统状态，不暗示用户犯错 |
| 清理未知 | 移除未识别 | 明确只是从规则列表移除，不像清理文件 |
| 例如 contract_parties_v1 | 从上方选择资料规则，或输入规则 ID | 先给用户路径，再给高级输入出口 |
| 每行一个 schema，例如 signature_assets_v1 | 每行一个资料规则；建议用上方“加入列表” | 避免把实现名当成说明文字 |

## 5. 边界规则

后续场景规划与模板管理保持一致时，可以按这个边界判断：

| 层级 | 应使用的表达 | 可保留的内部表达 |
| --- | --- | --- |
| 导航卡 | 已启用、已跳过、N 项设置、需确认 | 不显示 module list |
| 主控件标签 | 页面、排版、资料规则、最终 Word、资料包 | 不显示 schema / docx / preset id |
| 输入占位 | 操作提示、选择路径、业务名称 | 仅高级输入可出现“规则 ID” |
| 修复按钮 | 替换未识别、移除未识别、应用推荐 | 不使用 unknown / 清理未知 |
| tooltip / 诊断 / 审计 | 可展示真实 id、字段路径、schema id、docx | 用于定位和排查，不作为主说明 |
| 执行产物 | 保留真实扩展名和变量名 | 不反向污染主控件文案 |

关键原则：

- 主界面讲用户要完成的事。
- 高级证据讲系统实际做了什么。
- 存储字段保持稳定，不为了文案好看而改配置结构。
- 同一类操作在模板管理和场景规划里要使用同一组动作词。

## 6. 仍然不够好的地方

### 6.1 资料规则选择还不是一个真正的复用控件

当前资料规则由 combo、设为主规则、加入列表、替换未识别、移除未识别、主规则输入、多规则输入拼成。它已经能工作，但还不是一个像样的共享控件。

更好的形态应该是抽成一个 `MaterialRuleSelectorBlock`：

```text
选择资料规则
主规则
附加规则
未识别规则修复
规则预览
```

页面层只负责传入当前 profile 和 registry，block 负责：

- 规则列表展示；
- 主规则设置；
- 附加规则增删；
- 未识别规则替换 / 移除；
- 当前规则覆盖了哪些字段、图片角色和附件角色；
- 导航高亮入口。

这样才算和模板管理的样式 block 达到同等复用层级。

### 6.2 场景规划缺少统一的文案契约

现在文案清理是逐点推进，风险是下一个新增控件又写出 `schema`、`preset`、`module` 这样的内部词。

建议后续新增一个轻量规则文件或 projection helper：

```text
technical term -> user term
schema -> 资料规则
docx -> Word
preset -> 版本 / 方案
unknown -> 未识别
module -> 功能
```

这不一定要做成复杂 i18n，但需要有集中出口，至少让导航卡、详情摘要、按钮和占位文案不要各写各的。

### 6.3 主控件和高级证据还需要继续分层

模板管理的优秀之处在于主控件、来源、预览之间关系比较清楚。场景规划里仍有一些详情页把“能编辑的主设置”和“用于审计的证据字段”放得太近。

后续建议每个详情页固定成三层：

```text
1. 当前状态：这组功能是否启用，影响哪些输出
2. 主要设置：用户最可能会改的 3 到 6 个控件
3. 高级与证据：字段路径、变量、诊断、审计说明
```

这样可以减少冗余文本，也能避免用户把边界说明当成必填项。

## 7. 后续优先级

### P0：抽出资料规则选择 block

目标是让输入资料详情不再直接管理一堆 schema 控件，而是像样式详情一样复用一个明确的业务控件。

验收标准：

- 页面层不直接拼接“主规则 / 附加规则 / 未识别修复”的按钮状态。
- block 对外提供 `set_profile(...)`、`apply_to_profile(...)`、`navigation_widget_for_field(...)`。
- 测试不再依赖内部按钮树，而是验证 block 语义。

### P1：建立场景文案契约

目标是防止 raw 技术词重新出现在主界面。

验收标准：

- 主导航、主控件、按钮、占位文案不出现 `schema`、`DOCX`、`unknown`、`module` 这类词。
- tooltip、诊断和审计可以保留真实 ID，但必须不污染主文案。
- `tests/test_scene_panel_architecture.py` 增加源码级或控件级守门。

### P2：非样式能力也建立预览模型

目标是让资料与输出像模板样式一样可以被预览和解释。

可先做两个小预览：

- 资料规则预览：当前规则会要求哪些字段、图片角色、附件角色。
- 交付版本预览：最终会生成哪些文件、命名模板是什么、哪些内容会隐藏。

### P3：详情页统一三层布局

目标是减少重复说明，统一用户扫读路径。

验收标准：

- 每个详情页都有“当前状态 / 主要设置 / 高级与证据”。
- 不再在主控件附近堆长解释。
- 高级证据默认密度更低，必要时折叠或放到底部。

## 8. 本轮验收口径

本轮不宣称已经完成整体优秀设计，只推进一个明确断点：

```text
输入资料详情不再把 schema 示例和 unknown 文案暴露给用户。
```

本轮应通过的检查：

- 资料规则按钮显示“替换未识别 / 移除未识别”。
- 主资料规则占位不出现 `contract_parties_v1`。
- 资料规则列表占位不出现 `signature_assets_v1`。
- 主占位和列表占位不再出现 `schema`。
- 现有资料规则写回、未知规则替换、未知规则移除链路保持不变。

## 9. 设计判断

要让场景规划真正接近模板管理的完成度，后续不要继续只做局部文案替换。更合适的路线是：

```text
先统一对象语言
再抽共享业务控件
再统一详情页三层布局
最后补齐资料与交付预览
```

本轮的小改动只是把最刺眼的工程词从输入资料详情入口移除。真正的下一步，是把资料规则从一组散落表单控件提升为和样式管理同等级的复用 block。
