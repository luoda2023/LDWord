# 请求说法列表行投影归一执行记录

日期：2026-06-29

## 1. 本轮结论

前几轮已经把请求说法的筛选、数量、空态和证据动作状态统一到共享投影层。继续审计后，列表行本身仍有一个分叉点：

- 场景页自己创建 `QListWidgetItem`，自己补 tooltip。
- Workbench 也自己创建 `QListWidgetItem`，tooltip 只显示基础证据。
- 场景页额外补了“候选路由 / 候选资料包”，Workbench 没有。
- “候选路由”本身偏工程化，且显示 route id 的风险较高。

这意味着同一条“容易误解”的请求说法，在场景页和 Workbench 的解释不一致。用户在场景规划里看到需要澄清，到了执行工作台可能看不到同样的候选资料包说明。

本轮新增请求说法列表行 projection，让列表行文本、tooltip、消歧说明从同一个函数产出。

## 2. 已落地调整

### 2.1 新增列表行 projection

文件：`src/ui/panels/scene_summary_projection.py`

新增：

- `SceneRequestCellListItemProjection`
- `scene_request_cell_list_item_projection(...)`

投影字段：

| 字段 | 用途 |
| --- | --- |
| `sample_id` | 内部选择/追踪，不做主文案 |
| `text` | 列表可见文本 |
| `tooltip` | 请求、覆盖层级、资料包、场景族、证据编号、边界与澄清说明 |

### 2.2 消歧说明进入共享投影

旧逻辑在 `scene_panel.py` 中私有拼接：

```text
候选路由：...
候选资料包：...
```

新逻辑在 projection 内生成：

```text
需要先澄清
澄清：...
候选资料包：合同交付 / 专业披露/审阅
```

移除“候选路由”是有意的：route id 对普通用户没有帮助，候选资料包才是用户能理解的决策方向。

### 2.3 场景页接入

文件：`src/ui/panels/scene_panel.py`

调整：

- 请求说法列表使用 `scene_request_cell_list_item_projection(...)`。
- `QListWidgetItem.text` 来自 projection。
- `QListWidgetItem.tooltip` 来自 projection。
- 删除场景页本地 route 消歧拼接逻辑。

### 2.4 Workbench 接入

文件：`src/ui/panels/workbench/quick_execution_detail.py`

调整：

- Workbench 请求说法列表同样使用 `scene_request_cell_list_item_projection(...)`。
- Workbench 的 `_format_request_cell_tooltip(...)` 也转为 projection wrapper。
- 现在 Workbench 和场景页看到的“容易误解”请求说法 tooltip 一致。

## 4. 当前边界

已归一：

- 请求说法列表行文本。
- 请求说法 tooltip。
- 请求说法消歧提示。
- 请求筛选项、匹配逻辑、数量/空态。
- 请求证据动作状态。

仍需继续：

1. 抽 `SampleEvidenceBlock`，把样本库动作、请求说法浏览、证据打开状态组织成共享 UI 组合。
2. 把路径、证据编号、manual gate 等 tooltip 内容升级为可展开证据面板。
3. 将场景页样本文件列表也抽成行 projection，避免样本文件行和请求说法行成熟度不一致。
4. 对 Workbench 与场景页做视觉层审计：同一个 projection 在两个入口下是否有同样的密度、空态和动作节奏。

## 5. 设计判断

这轮继续推进“控件复用不只是 UI 复用，而是投影复用”：

```text
同一条请求说法 -> 同一个列表行 projection -> 场景页与 Workbench 同样解释
```

用户不再看到“候选路由”这种工程词，而是看到“候选资料包”。这让请求说法浏览更接近模板管理的成熟模式：主路径说人话，技术证据留在可追踪层。
