# 工作台问题导航注册表执行记录

日期：2026-06-28

## 本轮目标

前几轮已经完成：

- 证据区共享控件抽象。
- 证据 projection 下沉到 adapter。
- 工作台详情区只消费 projection 和共享控件。

剩下最明显的耦合点是“点击后去哪”。

之前这些规则散在两个地方：

- `QuickExecutionDetail`：证据参数路径如何转成修复 target。
- `panel_v2.py`：target type 如何跳到模板、场景、资料、输出或工作台卡片。

这会造成两个问题：

- 同一个 target type 的含义只能靠阅读 UI 分支判断。
- 模板管理/场景管理如果要复用工作台问题动作，容易再次复制路由规则。

本轮目标是新增一个纯数据导航注册表，让 UI 执行动作，但不再私有维护 target type -> panel/card 的映射。

## 执行结论

已新增工作台问题导航 registry：

- `src/ui/adapters/workbench_issue_navigation.py`

新增 projection：

- `WorkbenchIssueNavigationProjection`

新增函数：

- `workbench_issue_navigation_for_target(target_type, target_key)`
- `workbench_issue_parameter_navigation_target(issue, parameter_path)`

调整后：

- `QuickExecutionDetail` 不再私有维护参数路径到修复 target 的规则。
- `panel_v2.py` 不再私有维护 template/scene/material target type 集合和 card map。
- `panel_v2.py` 只保留必要副作用：
  - profile repair 解码。
  - bridge repair request。
  - 题图事务报告文件打开。
  - 实际 panel/card 或 feature card 导航。

## 新边界

### `workbench_issue_navigation.py` 负责

- target type -> action kind。
- target type -> panel id。
- target type -> card id。
- target type -> feature card id。
- parameter evidence path -> repair target。

### `QuickExecutionDetail` 负责

- 当前选中问题。
- 点击证据动作。
- 调用 `workbench_issue_parameter_navigation_target(...)` 得到修复 target。
- emit `issue_repair_requested(target_type, target_key)`。

### `panel_v2.py` 负责

- 收到 `issue_repair_requested`。
- 查询 `workbench_issue_navigation_for_target(...)`。
- 对 profile/material 类动作调用 bridge。
- 对事务报告打开文件。
- 执行 panel/card 或 feature card 导航。

## 参数证据路由

`workbench_issue_parameter_navigation_target(...)` 现在集中处理：

| parameter path | repair target |
| --- | --- |
| `scene.section_styles.*` | `scene_style_field` |
| `section_styles.*` | `scene_style_field`，自动补 `scene.` |
| `scene.format_scope.*` | `scene_scope_field`，去掉 `scene.` 前缀 |
| `format_scope.*` | `scene_scope_field` |
| 其他路径 + 当前 issue 有修复目标 | 当前 issue 的 `workbench_issue_action_target(...)` |
| 其他路径 + 无 issue | `parameter_path` fallback |

这样“证据里点参数”不再由 `QuickExecutionDetail` 私有判断。

## 对已有审计的调整

项目里已有 `src/config/scene_repair_routing.py`，它负责审计“问题类型属于哪个修复归属面”。

本轮没有替代它，而是补上更靠近 UI 的一层：

- `scene_repair_routing`：归属/审计层，说明问题应该由哪个产品面负责。
- `workbench_issue_navigation`：UI 导航层，说明点击后进入哪个 panel/card。

同时更新了 `scene_repair_routing` 的 evidence marker：

- 原先指向 `panel_v2.py` 里的硬编码分支。
- 现在指向 `workbench_issue_navigation.py` 里的 registry map。

这让审计证据跟当前架构保持一致。

## 为什么这一步重要

用户前面反复强调：

- 功能分布应该更合理。
- 边界应该更清晰。
- 要删除冗余文本描述。
- 要和模板管理保持一致性与复用。

这类目标不能只靠改文案达成。真正需要的是：

- projection 层说人话。
- shared UI 层摆控件。
- navigation registry 负责跳转规则。
- panel 只执行动作。

本轮把“跳转规则”从 panel 私有 if/else 里拿出来，形成了可以测试、可以审计、可以复用的 registry。

## 仍然未完成

### 1. registry 仍在 `src/ui/adapters`

这是合理过渡层，但如果后续模板管理、场景管理都要复用，可能需要更通用的位置：

- `src/shared/navigation`
- 或 `src/ui/navigation_registry`

当前先放 adapter，是因为它仍然以 Workbench issue target type 为输入。

### 2. bridge 副作用仍在 `panel_v2.py`

profile/material 修复需要 bridge 调用，这属于实际 UI 执行层，暂时保留在 panel。

后续可以继续抽成 command：

- `WorkbenchIssueNavigationCommand`
- `execute_material_profile_target(...)`
- `execute_transaction_artifact(...)`

但现在贸然抽 command 会扩大改动面。

### 3. `scene_repair_routing` 和 `workbench_issue_navigation` 还没有自动一致性校验

目前两者分别有测试。后续可以新增 audit：

- 每个 `repair_target_type` 都应该有 navigation projection。
- 每个 navigation projection 都应该能回到某个 repair route 或明确标记为 feature-only。

### 4. plugin/manual gate 的最终产品面仍需设计

本轮把 `plugin_manual_gate` 显式路由到 `quick_execute`，比旧 fallback `content_fill` 更符合“工作台确认问题”的定位。

但更优秀的设计可能需要专门的“人工确认/插件交接”详情区。

## 推荐下一步

## 当前状态

工作台问题链路现在更像模板管理的结构：

- adapter projection 负责用户理解。
