本轮目标：继续推进“运行时诊断 -> Workbench 问题队列 -> ScenePanel 具体控件”的闭环。上一轮已经让 Workbench 能接收 `scene_scope_field` / `scene_style_field` 并路由到 `ScenePanel.scn_scope`，但执行诊断层还没有稳定生成这类 repair target。本轮补上字段路径到场景 repair target 的推断。

## 1. 本轮发现的问题

上一轮后的链路是：

```text
Workbench repair target
  -> scene_scope_field / scene_style_field
  -> ScenePanel scn_scope
  -> 处理范围复选框 / 样式覆盖开关或控件
```

但源头仍依赖手动构造：

```text
repair_target_type = scene_style_field
repair_target_key = scene.section_styles.references_body.font_cn
```

如果真实执行诊断只给：

```text
parameter_path = scene.section_styles.references_body.font_cn
```

Workbench issue queue 之前不会自动知道这是一个场景样式字段问题。

## 2. 本轮执行

### 2.1 Adapter 从参数路径推断场景字段 repair target

修改：
- `src/ui/adapters/workbench_execution_adapter.py`

新增逻辑：

```text
batch_execution_issue_items()
  -> _batch_issue_parameter_paths(payload)
  -> _infer_scene_field_repair_target(parameter_paths)
```

推断规则保持收敛：

```text
scene.format_scope.sections.references
format_scope.sections.references
sections.references
  -> repair_target_type = scene_scope_field
  -> repair_target_key = format_scope.sections.references

scene.section_styles.references_body.font_cn
section_styles.references_body.font_cn
scene.section_styles.*.line_spacing_pt
  -> repair_target_type = scene_style_field
  -> repair_target_key = scene.section_styles....
```

没有这些明确前缀时，不推断，避免影响原有 material/batch issue。

### 2.2 Batch issue detail 保留参数路径

同一文件中，`_batch_issue_detail_lines()` 新增参数路径说明：

```text
参数路径：scene.section_styles.references_body.font_cn
```

这样用户在问题明细里能看到系统为什么跳到场景样式覆盖，而不是只看到一个抽象目标类型。

### 2.3 Runtime batch diagnostics 透传 parameter_path(s)

修改：
- `src/ui/panels/workbench/execution_runtime.py`

`_batch_issue_items_for_result()` 现在会从 `material_diagnostics` 读取：

```text
parameter_path
field_id
parameter_paths
```

并写入 batch issue payload：

```text
parameter_paths: [...]
```

这样真实批量执行结果里的诊断字段路径不会在 runtime -> adapter 中间丢失。

### 2.4 修复路由 evidence 补源头

修改：
- `src/config/scene_repair_routing.py`

`scene_field_repair` 的 evidence 增加：

```text
src/ui/adapters/workbench_execution_adapter.py
  _infer_scene_field_repair_target
  scene_scope_field
  scene_style_field
```

这让审计能证明场景字段修复不只是 UI 路由，也有 issue item 生成入口。

## 3. 链路状态

本轮后，代表性链路为：

```text
material_diagnostics:
  parameter_path = scene.format_scope.sections.references

_batch_issue_items_for_result()
  -> parameter_paths = [scene.format_scope.sections.references]

batch_execution_issue_items()
  -> repair_target_type = scene_scope_field
  -> repair_target_key = format_scope.sections.references

WorkbenchPanel._open_issue_repair_target()
  -> ScenePanel scn_scope

_ScopeDetail.focus_navigation_field()
  -> references 处理范围复选框高亮
```

样式覆盖链路：

```text
parameter_path = scene.section_styles.references_body.font_cn
  -> scene_style_field
  -> scene.section_styles.references_body.font_cn
  -> references_body 独立样式开关或字体控件
```

## 5. 仍未完成的缺口

### 5.1 普通非批量 diagnostics 还只是摘要

当前 `WorkbenchExecutionAdapter.build_result_state()` 接收的是：

```text
diagnostics_count
diagnostics_summary
batch_issue_items
```

普通非批量 diagnostics item 没有作为结构化 issue item 进入队列。本轮没有扩这个公共接口，避免波及过大。后续如果要让单文档执行里的 `scene.section_styles.*` 也自动变成 issue，需要新增结构化 diagnostics issue item 输入。

### 5.2 通配 section_styles 的具体分区策略仍未定

`scene.section_styles.*.line_spacing_pt` 现在能被识别为 `scene_style_field`，但 ScenePanel 当前会按当前编辑分区定位。后续仍要决定通配字段应该：

```text
默认落到第一个已覆盖分区
或落到样式覆盖摘要
或要求诊断生成层给出具体 variant
```

### 5.3 视觉截图仍未覆盖

本轮测试验证了 issue item、repair target、intent 和 widget property，但没有做截图级视觉验证。高亮边框是否足够明显，还需要后续运行界面检查。

## 6. 下一步建议

下一轮优先处理通配 `scene.section_styles.*.*` 的具体落点策略，或者继续把普通非批量 diagnostics item 结构化进入 Workbench issue queue。前者更贴近场景样式覆盖交互，后者会扩大执行结果接口。
