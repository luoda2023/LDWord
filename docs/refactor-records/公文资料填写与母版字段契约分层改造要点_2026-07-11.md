# 公文资料填写与母版字段契约分层改造要点

日期：2026-07-11  
状态：深度分析已完成，修改方案待实施  
范围：公文资料填写、文种字段契约、母版占位符扫描、资料上下文同步、资料预览

关联记录：

- `docs/audits/公文国标合规双轨整改规划_2026-07-10.md`
- `docs/audits/公文文档深度审阅与规划_2026-07-09.md`
- `docs/audits/工作模式与母版管理配置分层规划_2026-07-09.md`

## 1. 结论先行

前序分析的主方向正确，但需要补充两项关键修正。

正确部分：

1. 公文母版 DOCX 应继续负责版式、结构块和占位符承载。
2. 当前文种需要填写什么，应由文种装配契约决定，不应由运行时扫描结果决定。
3. 母版扫描应降级为母版完整性校验和开发诊断，不应成为填写表单的字段注册器。
4. 公文填写页不应把当前文种的所有可选字段等权平铺。
5. 内置只读母版不需要在每次输入时重新扫描。

需要修正和补充的部分：

1. 项目中已经存在一套公文专用资料填写表单，不是所有公文字段都由通用资料包页扫描生成。
2. 当前项目同时存在“公文专用表单”和“通用资料包表单”两条编辑链路，两者共同写入 `MaterialExecutionContext`，容易产生重复刷新和状态漂移。
3. 当前性能风险的主要来源不是约 11 ms 的首次母版扫描，而是每次按键发布完整资料上下文后，引起其他面板重载资料档案和多次刷新。
4. 当前 15 个公文 profile 实际只有两种字段合同：公共合同和纪要扩展合同，尚未真正表达各文种差异。
5. 当前字段语义仍有冲突，例如 `issuer`、`organization`、`signer` 的职责没有完全分清。

最终目标模型：

```text
文种 profile
  -> 文种字段契约
  -> 表单投影（必填 / 常用 / 条件 / 高级）
  -> 当前任务资料
  -> 公文装配 runtime
  -> 母版 DOCX

母版扫描
  -> 只做契约一致性、母版完整性和开发诊断
```

## 2. 当前实现的真实结构

### 2.1 当前存在两套资料填写界面

第一套是通用资料包页：

```text
src/ui/panels/assets_panel.py
src/ui/panels/assets/profile_editor_presenter.py
src/ui/panels/assets/field_status_presenter.py
src/ui/panels/assets/preview_table_presenter.py
```

它面向通用 `{{字段}}`，目前会：

1. 从当前执行目标取得 DOCX 或母版路径。
2. 扫描精确 `{{字段}}`。
3. 生成动态字段输入行和预览映射。
4. 将填写结果写入资料档案和 `MaterialExecutionContext`。

第二套是方案页中的公文专用表单：

```text
src/ui/panels/scene_panel.py::_ContentDetail
```

它已经具备：

1. 公文文种选择器。
2. 公文标题、正文、发文机关、发文字号等专用字段。
3. 正文多行编辑器。
4. 公文资料包导入、导出、批量导入和未版本化资料转换。
5. 当前文种必填检查。
6. 字段到母版占位符的映射说明。

两套界面通过同一个 `PanelBridge.material_context_changed` 相互同步。当前没有明确的“唯一编辑拥有者”。

### 2.2 公文专用表单当前是近似全量平铺

`src/ui/panels/scene_panel.py` 当前固定创建以下 11 个公共字段：

```text
title             标题
body              正文
organization      发文机关
document_no       发文字号
issue_date        成文日期
recipient         主送机关
issuer            签发机关
attachment_note   附件说明
copy_scope        抄送范围
printing_org      印发机关
printing_date     印发日期
```

另外固定创建两个纪要字段：

```text
meeting_date      会议时间
participants      参会人员
```

界面初始化时实际创建 13 个编辑器，只在非纪要文种下隐藏最后两个会议字段。其余 11 个公共字段对所有公文文种都显示。

因此当前并不是“15 个文种所有字段合并全量展示”，但确实是“11 个公共字段对所有文种近似全量平铺”。

### 2.3 当前文种契约只有两种有效形态

字段契约位于：

```text
src/config/official_document_profiles.py
```

当前 15 个公文 profile 中：

- 除纪要外，全部使用 `_COMMON_FIELD_BINDINGS`，共 11 项。
- 纪要使用公共 11 项，加 `meeting_date` 和 `participants`，共 13 项。

公共必填字段当前为：

```text
title
body
organization
document_no
issue_date
```

公共选填字段当前为：

```text
recipient
attachment_note
issuer
copy_scope
printing_org
printing_date
```

这还不能表达通知、报告、请示、批复、函、命令和纪要之间真实存在的字段适用性差异。

### 2.4 当前表单字段和 schema 还没有完全对齐

`official_document_v1` schema 中还存在：

```text
document_type
security_level
urgency
signer
archive_status
archive_no
retention_period
```

但公文专用表单没有展示这些字段，装配合同也没有全部绑定。

同时存在以下语义风险：

```text
organization  发文机关
issuer        当前 UI 标注为“签发机关”
signer        schema 中存在，但没有进入当前装配绑定
```

现有公文国标整改规划已经指出，上行文需要真正的签发人字段和版头策略。后续不能继续用 `issuer` 模糊兼容 `signer`。

纪要 schema 中存在 `meeting_title`，当前装配合同仍复用通用 `title`。是否继续这样映射，需要在首版正式字段契约中显式确定，不能依赖字段名相似推断。

## 3. 母版扫描现状和性能证据

### 3.1 当前扫描链路

通用资料包页的公文扫描链路为：

```text
PanelBridge.current_execution_target()
  -> official 模式选择 default_master("official")
  -> 得到 official_gbt_standard.docx
  -> scan_docx_placeholders()
  -> scan_document_exact_placeholders()
  -> 扫描正文、表格、页眉页脚、文本框和内容控件
```

扫描后还会按当前文种的 `placeholder_bindings` 过滤，因此通用资料包页的可见字段集合实际上是：

```text
母版扫描结果
∩ 当前文种允许的 placeholder id
```

### 3.2 本轮实测

内置公文母版：

```text
文件：config_library/masters/official/builtin/official_gbt_standard.docx
大小：37954 bytes
版本：official-master-gbt-shell-2026-07-09
```

实测耗时：

```text
首次完整扫描：约 9–12 ms
同一面板缓存命中：约 0.01–0.05 ms
```

当前缓存键：

```text
placeholder_source_path + 文件 mtime
```

因此输入过程中不会每次重新打开 Word。正常输入刷新只会执行一次文件状态检查并复用缓存。

### 3.3 当前扫描结果与契约不一致

完整扫描通常稳定返回 8 个字段键：

```text
official_organization
official_document_no
official_title
official_recipient
official_body
official_attachment_note
official_issuer
official_issue_date
```

母版 manifest 声明 13 个槽位，公文合同声明公共 11 项、纪要 13 项。以下字段并未稳定进入通用扫描结果：

```text
official_copy_scope
official_printing_org
official_printing_date
official_meeting_time
official_meeting_attendees
```

其中会议字段还可能由公文装配 runtime 根据文种和数据动态插入，进一步说明填写表单不能依赖静态母版扫描来决定字段集合。

### 3.4 “出现次数”当前不可靠

本轮对同一母版连续完整扫描，字段键集合大体稳定，但重复字段的 `occurrence_count` 在 8–10 之间波动，个别轮次还会从说明页表面读到额外字段。

原始 `word/document.xml` 中共有 24 个 `{{official_*}}` 文本实例，其中包含正式装配区域和母版占位符说明页的重复说明。

因此当前计数至少混有三种口径：

1. 正式输出中实际可替换的出现次数。
2. 母版参考说明页中的示例次数。
3. 文本框、内容控件和普通段落之间的重复扫描次数。

在完成稳定表面去重和说明页排除之前，产品不应展示“出现几处”作为可靠业务数据。

## 4. 性能问题的真实主因

### 4.1 扫描不是主要负担

首次 11 ms、缓存命中约 0.01 ms，不足以解释明显输入卡顿。

### 4.2 每次按键会发布完整资料上下文

公文专用表单当前连接方式：

```text
QLineEdit.textChanged / TextArea.text_changed
  -> _on_official_material_edited()
  -> _write_official_material_context()
  -> PanelBridge.set_current_material_context()
  -> material_context_changed.emit(full_context.clone())
```

`PanelBridge.set_current_material_context()` 当前没有相等性短路，每次都会克隆并广播整个上下文。

### 4.3 通用资料包页收到广播后做重操作

`AssetsPanel._on_material_context_changed()` 当前会：

1. 覆盖当前 profile。
2. 重建 profile 列表。
3. 重新设置编辑器值。
4. 重新同步批量选择。
5. 多次刷新资料摘要和预览。

本轮对一次 `set_current_material_context()` 的同步调用实测：

```text
profile list reload：1 次
set editor values：2 次
full summary refresh：3 次
batch selection sync：1 次
```

完整摘要刷新还会读取当前素材集合、生成预览行、更新图片状态、题图表格、资料导航卡和摘要卡。

因此明显卡顿更可能来自“每个字符触发跨面板完整状态广播和三次全量投影”，而不是母版扫描。

## 5. 正确的数据权威边界

### 5.1 文种 profile

负责：

- 当前是什么文种。
- 行文方向和布局族。
- 哪些字段适用。
- 哪些字段必填、选填、条件必填或禁止。
- 哪些字段属于本次公文、组织默认值或系统生成值。

不负责：

- 直接解析 Word。
- 保存本次用户输入值。
- 操作 OOXML。

### 5.2 文种字段契约

字段契约应成为填写表单和运行时装配的唯一字段来源。

建议每个字段至少包含：

```text
field_key
label
placeholder_id
editor_kind
group
requirement
source_scope
show_when
order
help_text
```

推荐枚举：

```text
editor_kind
  single_line
  multiline
  date
  select
  multi_value
  attachment_list

group
  core
  routing
  closing
  imprint
  meeting
  archive

requirement
  required
  optional
  conditional
  forbidden

source_scope
  task
  organization_default
  generated
  archive_metadata
```

### 5.3 母版 DOCX

负责：

- 页面版式和结构族。
- 占位符锚点。
- 条件结构块。
- 版头、主体、末尾、版记和页脚。

不负责：

- 决定用户表单展示哪些字段。
- 推导字段是否必填。
- 保存资料值。

### 5.4 母版占位符索引

负责：

- 验证契约声明的占位符是否存在。
- 验证母版是否出现未声明占位符。
- 记录母版版本、哈希和扫描证据。
- 为开发诊断提供稳定表面位置。

不负责：

- 自动向资料包添加字段。
- 控制业务表单显示。
- 推断中文或英文别名。

## 6. 公文填写页目标交互

### 6.1 不再全量平铺

公文填写页建议按以下顺序呈现：

```text
文种

当前必填
  标题
  正文
  发文机关
  发文字号
  成文日期

当前文种常用
  只显示本文种高频适用字段

条件内容
  有附件
  需要抄送
  有签发人
  会议资料

高级与版记
  默认折叠

归档字段
  默认折叠或独立步骤
```

### 6.2 字段必须按控件类型展示

示例：

```text
title             单行文本
body              多行正文编辑器
issue_date        日期控件或规范日期输入
recipient         可重复列表或多值输入
attachment_note   附件清单，不应只是单行文本
participants      多值输入或名单编辑器
document_type     文种选择器，不应重复显示成普通字段
```

### 6.3 普通用户不需要看到原始占位符映射

当前专用表单底部会全量显示：

```text
标题 -> official_title
正文 -> official_body
...
```

该信息应移动到“高级 / 映射诊断”折叠区。主填写流程只显示中文业务标签、必填状态和条件状态。

### 6.4 隐藏不等于删除

切换文种时：

- 不适用字段从当前表单隐藏。
- 已填写值保留在任务草稿中，除非用户明确清除。
- 生成时只消费当前文种契约允许的字段。
- 禁止字段如果仍有值，应提示但不得静默写入。

## 7. 文种差异的建模方式

不建议为 15 个文种复制 15 份完整字段列表。建议采用公共基线加 profile 覆盖：

```text
COMMON_CORE_FIELDS
COMMON_OPTIONAL_FIELDS

PROFILE_FIELD_POLICIES
  notice
    recipient = applicable
    attachment_note = conditional

  report / request
    signer = required_or_policy_driven
    recipient = profile_rule

  letter
    recipient = profile_rule
    letter-specific routing fields = applicable

  minutes
    meeting_date = applicable
    participants = applicable
    meeting-specific fields = applicable
```

上表只表达建模方式，不代表已经完成公文业务规则审定。每个文种的 required / optional / forbidden 必须结合现有国标整改规划、真实样张和业务确认后冻结。

母版也不需要因为文种多就拆成 15 份。继续沿用既有规划中的“最少结构族”原则：普通行文、上行文、信函、命令、纪要等布局族由版式差异决定是否拆母版；字段差异由文种契约负责。

## 8. 母版扫描目标策略

### 8.1 内置母版

建议在构建、发布或母版登记时扫描一次，并保存索引：

```text
master_id
master_version
master_sha256
placeholder_ids
placeholder_surfaces
replaceable_occurrence_count
scan_version
scanned_at
```

运行时读取索引，不在每次打开填写页时重新解析 DOCX。

### 8.2 用户自定义母版

在以下情况扫描：

1. 首次导入。
2. 文件哈希或版本发生变化。
3. 用户主动执行“重新校验母版”。

扫描结果持久化到用户母版 manifest 或独立索引，不跟随每次键盘输入刷新。

### 8.3 缓存失效条件

```text
master_id changed
master_version changed
sha256 changed
scanner_version changed
explicit_rescan requested
```

不应使用“资料字段值发生变化”作为母版扫描缓存失效条件。

### 8.4 稳定计数口径

如果未来需要展示出现次数，必须先定义：

```text
只统计正式输出区域
排除母版说明页
同一 XML 文本节点只能归属一个扫描表面
运行时动态插入字段单独标记为 generated_surface
表格、页眉页脚、文本框和内容控件保留明确 surface id
```

验收前，产品只展示“字段存在 / 缺失”，不展示“出现 N 处”。

## 9. 两套编辑器的收敛方案

### 9.1 推荐方案

建立共享的公文资料表单投影层，例如：

```text
OfficialMaterialFormProjection
  profile_id
  visible_groups
  field_specs
  values
  issues
  mapping_diagnostics
```

公文专用方案页和资料包页如果都需要展示公文资料，必须读取同一投影，不得分别维护字段常量和显示规则。

### 9.2 编辑拥有权

建议同一时刻只有一个主编辑面：

- 公文模式优先使用公文专用表单。
- 通用资料包页展示资料包管理、导入导出和映射预览。
- 通用资料包页不再根据公文母版扫描结果自动创建公文字段。
- 如果两个页面都允许编辑，必须共享同一字段组件和增量状态模型，不能通过完整上下文互相覆盖。

### 9.3 资料上下文同步

建议增加：

1. 250–400 ms 输入合并提交。
2. 上下文相等时不广播。
3. 字段增量事件，例如 `material_field_changed(profile_id, key, value)`。
4. 完整上下文只用于导入、切换资料包、恢复草稿和执行前快照。
5. AssetsPanel 收到单字段变化时只更新对应输入行和预览值，不重建 profile 列表。
6. 批量选择只在 profile 集合或勾选状态变化时同步，不随单字符变化同步。

性能验收目标：

```text
一次字符输入
  -> 0 次 DOCX 重扫
  -> 0 次 profile list rebuild
  -> 0 次 batch selection rebuild
  -> 最多 1 次合并后的轻量字段投影刷新
```

## 10. 分阶段修改要点

### P0：冻结行为和证据

- 为 15 个 profile 输出当前字段合同快照。
- 为当前母版生成稳定占位符索引测试。
- 锁定首次扫描和缓存命中基线。
- 增加“单字段输入不得重建 profile 列表”的性能测试。
- 记录当前两套编辑器的同步入口。

### P1：建立公文字段投影模型

修改重点：

```text
src/config/official_document_profiles.py
src/config/material_schema_registry.py
```

- 给字段增加控件类型、分组、来源范围和条件规则。
- 从公共绑定加纪要特例，升级为公共基线加 profile 覆盖。
- 明确 `issuer`、`signer`、`organization` 的语义。
- 明确当前文种禁止字段的处理方式。
- 正式发布前统一运行时字段键；未版本化测试资料通过显式转换器写成首版 v1。

### P2：收敛公文专用表单

修改重点：

```text
src/ui/panels/scene_panel.py
```

- 删除固定 `OFFICIAL_COMMON_MATERIAL_FIELDS` 全量循环对显示规则的所有权。
- 从共享投影生成字段组。
- 必填项默认展开。
- 条件项按开关显示。
- 高级、版记和归档字段折叠。
- 原始 placeholder 映射移入诊断区。
- 保留正文多行编辑能力。

### P3：收敛通用资料包页

修改重点：

```text
src/ui/panels/assets/field_status_presenter.py
src/ui/panels/assets/preview_table_presenter.py
src/ui/panels/assets/material_context_application_presenter.py
```

- official 模式不再用母版扫描结果自动注册资料字段。

## 12. 不应采取的方案

1. 不为 15 个文种机械复制 15 份 DOCX。
2. 不把母版扫描结果直接持久化成用户资料字段。
3. 不在每次按键时扫描母版。
4. 不把所有可选、版记和归档字段平铺在主表单。
5. 不继续让 `issuer` 同时代表签发机关、签发人或落款机关。
6. 不用中文标签相似度或英文别名猜测公文正式字段。
7. 不通过隐藏输入框解决字段不适用问题；必须由契约表达适用性。
8. 不让两套编辑器通过完整上下文广播互相重建。

## 13. 尚需业务确认的决策

以下项目不能仅凭代码推断，需要结合真实样张、现有国标整改规划和业务确认：

1. 15 个文种各自的 required / optional / conditional / forbidden 字段矩阵。
2. 发文字号是用户输入、编号服务生成，还是两者均支持。
3. 成文日期、印发日期的默认生成和人工覆盖策略。
4. `issuer`、`signer`、`organization` 的最终中文语义和迁移规则。
5. 主送机关、抄送范围和参与人员采用单值、多值还是结构化列表。
6. 附件说明是否升级为附件清单及其编号策略。
7. 组织级默认资料存放位置和跨任务复用边界。
8. 哪些归档字段属于生成阶段，哪些属于人工归档阶段。

## 14. 最终判断

“公文使用内置母版 DOCX”是合理的；不合理的是让母版扫描结果承担业务字段定义。

公文模式的正确主链应当是：

```text
当前文种契约决定字段
字段投影决定填写交互
资料上下文保存本次值
装配 runtime 按合同写入母版
母版索引只验证合同和 DOCX 是否一致
```

当前扫描性能本身可接受，但扫描口径不稳定；当前填写体验和卡顿的更大根因是字段合同过粗、公共字段平铺、两套编辑器并存，以及每个字符触发完整上下文广播和多次全量刷新。

实施顺序应优先为：

```text
共享字段投影
  -> 公文专用表单分层
  -> 通用资料包页 official 分支收敛
  -> 增量同步和性能收敛
  -> 母版索引与稳定预检
  -> 文种规则矩阵全面冻结
```

### 15.3 当前文种策略的边界

本轮冻结的是“契约表达方式、运行时消费方式和保守兼容基线”，不是未经样张和业务确认的完整公文业务规则。

