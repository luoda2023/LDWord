# 场景导航卡副标题人话化执行记录

日期：2026-06-30

## 1. 本轮目标

上一轮已经把场景概览第一屏文案压成更短的人话状态，但左侧导航卡仍有内部术语：

```text
docx · 2 字段 / 1 schema
basic_format · 基础规则
4/9 个分区
启用 5/8 类能力
```

这些文字虽然不是详情正文，但它们出现在用户第一眼扫视的位置，会破坏“模板管理式”的清晰感。

本轮目标是把导航卡副标题也改成短中文状态：

```text
Word 文档、Excel 表格 · 资料字段 2 个 · 资料规则 1 项
合同交付规则 · 合同字段计数
已选 4 个区域 · 自动范围
已启用 5 类功能
```

## 2. 本轮实现

### 2.1 新增导航摘要 helper

新增轻量 helper：

```python
_nav_display_id(...)
_nav_join(...)
_nav_scope_subtitle(...)
_nav_capability_subtitle(...)
_nav_format_summary(...)
_nav_rule_label(...)
_nav_count_label(...)
```

这些 helper 只服务导航卡，不承载详情证据。

### 2.2 资料卡副标题改写

修改前：

```text
docx/xlsx · 2 字段 / 1 schema
```

修改后：

```text
Word 文档、Excel 表格 · 资料字段 2 个 · 资料规则 1 项
```

### 2.3 核对依据卡副标题改写

修改前：

```text
contract_delivery · contract_fields
```

修改后：

```text
合同交付规则 · 合同字段计数
```

### 2.4 范围与功能卡副标题改写

修改前：

```text
4/9 个分区 · 自动范围
启用 5/8 类能力
```

修改后：

```text
已选 4 个区域 · 自动范围
已启用 5 类功能
```

数字比例仍保留在 badge 中，但改为 `4 项`、`5 项`，避免副标题像仪表盘计数。

## 3. 边界判断

导航卡的职责不是证明配置完整性，而是帮助用户扫视：

| 区域 | 应显示 | 不应显示 |
| --- | --- | --- |
| 核对依据 | 规则口径、计数口径的人话标签 | raw rule id、count profile id |
| 处理范围 | 当前启用区域状态 | `N/M` 比例串 |
| 启用模块 | 当前启用数量 | `N/M` 比例串 |
| 输入与资料 | 输入格式、资料字段数、资料规则数 | `schema`、下划线 id、斜杠拼接 |
| 输出设置 | 默认交付版本、产物数量 | raw preset id |

内部 id、schema id、样本 id 仍可留在详情页 tooltip 或高级证据区域，不进入导航副标题。

## 5. 当前效果

左侧导航现在更像模板管理侧的摘要导航：

- 先说当前状态。
- 数量只作为辅助。
- 内部 key 不直接露出。
- 资料、规则、输出都使用中文业务标签。

## 6. 后续继续推进

### P0：动态功能卡描述仍有详情化倾向

动态能力卡仍直接使用 `group.description`。它们目前多为中文，但仍可能偏“功能说明”，后续应继续统一成短状态：

```text
表格与图表：已启用 / 已跳过
页面元素：已启用 / 已跳过
```

### P1：输出详情控件仍有 `DOCX` 文案

输出设置详情里仍有“最终 DOCX”“对比 DOCX”。这是详情层控件标签，不是导航卡，但后续可以统一成“最终 Word”“对比 Word”。

## 7. 本轮结论

场景规划现在在第一屏正文和左侧导航卡两个层面都开始减少内部语法。

这一步对体验很关键：用户不需要先理解 `schema`、`count_profile`、`N/M`、`docx/xlsx` 才知道该去哪一页。导航卡只负责告诉他“这里有什么、现在是什么状态、要不要点进去”。这更接近模板管理的清晰边界。
