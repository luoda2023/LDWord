# 分区样式批量恢复撤销与模板管理一致性执行记录（2026-06-29）

## 1. 本轮问题判断

前一轮已经把“分区样式”从工程化的“样式覆盖”改成用户能理解的“独立样式 / 跟随模板”，并接入了模板管理同源的 `StyleManagementBlock`、owner 状态、样式预览和差异对照。

但批量恢复动作仍有一个设计缺口：`全部跟随模板` 一次关闭多个分区独立样式后，用户没有安全退路。对用户来说，这类动作的影响范围大于“当前分区恢复模板”，如果误点后只能逐个重新开启并重填样式，会破坏信任感。

本轮补齐的是批量恢复后的“一步撤销”，并重新校准控件层级，使它继续遵守模板管理的复用边界。

## 2. 与模板管理的对齐原则

### 2.1 单对象动作留在 owner 工具条

模板管理里，样式编辑面板的主要对象是“当前样式项”；场景分区样式里，主要对象是“当前分区”。

因此当前分区的恢复动作继续留在共享 owner 工具条：

```text
恢复模板
```

含义只限当前正在编辑的分区，不扩展到其他分区。

### 2.2 批量动作放在分区样式卡片头部

`全部跟随模板` 不是某一个分区的属性，而是整组分区样式的批量动作，所以放在 `SceneStyleOverrideSection` 的卡片头部动作区。

这和模板管理的结构保持一致：

| 层级 | 模板管理 | 分区样式 |
| --- | --- | --- |
| 当前对象 | 当前模板样式项 | 当前分区 |
| 当前对象动作 | 编辑当前样式 | 恢复当前分区到模板 |
| 整组动作 | 模板级导入导出/应用 | 全部跟随模板 / 撤销恢复 |

### 2.3 撤销也属于批量动作层

`撤销恢复` 只撤销最近一次 `全部跟随模板`，它不是当前分区动作，也不是样式字段编辑动作。因此它和 `全部跟随模板` 同层，放在同一个卡片头部动作区。

这样用户看到两个按钮时能形成直接关系：

```text
全部跟随模板    撤销恢复
```

主界面不再新增长段解释，影响范围通过禁用状态和 tooltip 告知。

## 3. 功能边界重新划分

### 3.1 服务层只处理数据动作

文件：`src/ui/panels/scene_style_override_service.py`

新增：

```python
restore_all_scene_section_styles_to_template(scene, variants=STYLE_VARIANTS)
```

职责：

- 只遍历 `STYLE_VARIANTS` 注册的已知分区。
- 只删除已经开启的独立样式。
- 返回实际恢复的分区 key。
- 不承担 UI 文案、按钮状态、撤销快照。

这个边界很重要：服务层保持纯动作，UI 才能自由决定如何呈现“全部恢复”和“撤销”。

### 3.2 Section 层只暴露控件和信号

文件：`src/ui/panels/scene_style_override_sections.py`

新增：

- `restore_all_requested`
- `undo_restore_all_requested`
- `restore_all_button`
- `undo_restore_all_button`
- `set_restore_all_enabled(enabled, labels=())`
- `set_undo_restore_all_enabled(enabled, labels=())`

职责：

- 统一按钮位置、主题样式和 tooltip。
- 不读写 `scene.section_styles`。
- 不保存撤销快照。

这样 `SceneStyleOverrideSection` 继续是模板管理共享控件的组合壳，而不是业务状态容器。

### 3.3 ScenePanel 层负责编排和撤销快照

文件：`src/ui/panels/scene_panel.py`

新增状态：

```python
self._restore_all_style_snapshot: dict[str, object] = {}
```

职责：

- 批量恢复前深拷贝被删除的分区样式。
- 批量恢复后同步关闭对应分区开关。
- 点击 `撤销恢复` 时把快照写回 `scene.section_styles`。
- 手动编辑、单项恢复、分区开关变更、处理范围变更时丢弃快照。
- 同一场景的保存回灌和模板同步刷新不丢失快照。

撤销快照放在 `ScenePanel`，因为它需要同时知道当前 scene、当前模板、分区开关、样式编辑器和父级保存刷新链路。

## 4. 本轮发现的链路问题

最初测试失败点是：点击 `全部跟随模板` 后，分区样式确实被清空，但 `撤销恢复` 按钮仍然禁用。

追踪后发现链路如下：

```text
全部跟随模板
-> ScenePanel 删除 scene.section_styles
-> 保存撤销快照
-> emit style_rules_changed
-> 父级 ScenePanel._on_scene_edited()
-> bridge.set_current_scene()
-> on_scene_changed()
-> _apply_scene()
-> _style_rules.set_scene()
-> 快照被误清空
```

这说明问题不在按钮，也不在服务函数，而在父子保存刷新链路把“同一场景的保存回灌”误判成“切换场景”。

修正方式：

- `StyleRulesDetail.set_scene()` 只在传入新 scene 对象时清空撤销快照。
- 同一 scene 的保存回灌、模板重新同步、预览刷新保留撤销快照。
- 处理范围变更仍主动丢弃快照，因为分区存在性可能已经变化。

## 5. 当前交互结果

### 5.1 没有独立样式

```text
全部跟随模板：禁用，tooltip = 当前没有独立样式
撤销恢复：禁用，tooltip = 暂无可撤销的恢复
```

### 5.2 存在多个独立样式

```text
全部跟随模板：启用，tooltip = 将关闭独立样式：参考文献、附录
撤销恢复：禁用
```

### 5.3 点击全部跟随模板后

```text
全部跟随模板：禁用
撤销恢复：启用，tooltip = 恢复独立样式：参考文献、附录
状态摘要：全部跟随模板
来源状态：来自模板
```

### 5.4 点击撤销恢复后

```text
参考文献、附录独立样式恢复
对应分区开关重新选中
状态摘要：2 个分区独立样式
撤销恢复重新禁用
```

## 6. 文案和冗余文本处理

本轮没有新增主界面说明段落，也没有引入确认弹窗。原因是当前设计目标是让控件自己表达边界：

- 当前分区动作：`恢复模板`
- 批量动作：`全部跟随模板`
- 批量安全动作：`撤销恢复`
- 状态摘要：`全部跟随模板` / `N 个分区独立样式`
- tooltip：只在用户悬停时说明影响范围

这比继续堆“手动控制所有功能开关与处理范围”之类描述更清楚，也更接近模板管理已有的短标签、状态条、动作按钮模式。

## 8. 当前限制

1. 撤销是一步撤销，只针对最近一次 `全部跟随模板`。
2. 撤销快照只保存在当前面板内存，不跨场景、不跨应用重启。
3. 如果用户在恢复后继续手动编辑独立样式，撤销快照会被丢弃。
4. 当前没有做弹窗确认，仍以按钮状态和 tooltip 表达影响范围。
5. Qt offscreen 截图环境中文字体仍可能显示为方框，视觉验收需要真实桌面环境补一轮。

## 9. 后续建议

1. 如果后续出现更多批量样式动作，可以把“一步撤销快照”抽成通用 helper。
2. 可以增加轻量 toast，例如“已全部跟随模板，可撤销”，但不要在主界面增加常驻说明。
3. 模板管理和分区样式后续可共享更多动作区规范：单项动作在 owner toolbar，批量动作在卡片头部。
4. 继续做真实桌面视觉验收，重点看两个头部按钮在窄宽度下是否需要折行或菜单化。

## 10. 当前结论

本轮之后，分区样式和模板管理的复用关系更清楚：

- 控件层复用：共享 `StyleManagementBlock`、owner 状态、预览、样式编辑表面。
- 业务层分离：服务层做数据动作，Section 层发信号，ScenePanel 层编排撤销。
- 文案层收敛：不再讲工程术语，只讲“跟随模板 / 独立样式 / 恢复”。
- 安全层补齐：批量恢复后有一步撤销，不再让用户承担不可逆误操作。

这一步不是简单加按钮，而是把“分区样式”真正整理成和模板管理同构但边界清晰的二级样式管理面。
