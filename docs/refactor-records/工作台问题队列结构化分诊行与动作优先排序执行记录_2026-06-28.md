# 工作台问题队列结构化分诊行与动作优先排序执行记录

日期：2026-06-28

## 1. 本轮继续判断

上一轮已经加入动作筛选，并把列表行文本改成：

```text
先处理 · 资料字段缺失... · 待处理
```

这比纯技术分类更好，但继续看仍然不够优秀。因为“先处理”只是文本前缀，视觉层级和普通摘要混在一起，用户扫列表时仍然需要读整行。

真正的分诊列表应该做到：

- 动作先被看到。
- 阻断项自然排在前面。
- 摘要、状态、动作三类信息分开。
- 原有资料、模板、场景、插件跳转逻辑不变。

所以本轮继续把问题列表从“带前缀的字符串列表”推进成“结构化分诊行”。

## 2. 本轮实现

### 2.1 动作统计固定优先级

文件：`src/ui/adapters/workbench_execution_adapter.py`

新增 `_count_issue_action_values(...)`，让动作统计按固定顺序输出：

```text
先处理 -> 建议确认 -> 仅查看
```

这样动作筛选下拉不会受源数据顺序影响。即使插件确认项先进入队列，筛选控件仍然先显示“先处理”。

### 2.2 列表按动作优先级排序

文件：`src/ui/panels/workbench/quick_execution_detail.py`

新增：

- `_sort_issue_items_by_action(...)`
- `_issue_action_group_rank(...)`

排序规则：

| 动作 | 优先级 |
| --- | --- |
| 先处理 | 最高 |
| 建议确认 | 中 |
| 仅查看 | 最低 |

同一动作组内保留原始队列顺序，避免隐藏业务生成顺序。

`current_filtered_issue_items()`、列表渲染、当前可处理目标都使用同一排序结果，保证用户看到的顺序和“处理”按钮选择的顺序一致。

### 2.3 列表行改为结构化 widget

文件：`src/ui/panels/workbench/quick_execution_detail.py`

新增 `_build_issue_list_row_widget(...)`，每一行包含：

- 动作 badge：`先处理` / `建议确认` / `仅查看`
- 问题摘要
- 状态文本

同时保留 `QListWidgetItem.text()`：

```text
先处理 · 资料字段缺失... · 待处理
```

这样既有测试、键盘选择和 fallback 文本仍然有效，视觉层也能变成真正的分诊行。

### 2.4 badge 样式

新增 `_issue_action_badge_stylesheet(...)`：

- `先处理` 使用错误色系，强调必须先看。
- `建议确认` 使用信息/主色系，表示可继续但建议确认。
- `仅查看` 使用中性色系，表示信息保留。

badge 不是新业务状态，只是 `workbench_issue_action_group(...)` 的视觉投影。

## 3. 与模板/场景一致性的关系

这轮看似只改工作台问题队列，但它解决的是同一个大问题：信息层级必须一致。

模板管理里，用户看到的是：

```text
样式对象 -> 控件 -> 预览 -> 保存
```

场景页里，用户看到的是：

```text
业务范围 -> 分区覆盖 -> 跟随/覆盖状态 -> 轻量预览
```

工作台现在也更接近同一思路：

```text
运行问题 -> 动作分诊 -> 结构化行 -> 真实修复入口
```

也就是说，工作台不再像“日志输出”，而更像“进入资料、模板、场景控件之前的任务入口”。

## 4. 链路复查

本轮完成后，关键链路仍然成立：

1. 运行前或运行后问题进入 `WorkbenchIssueItem`。
2. `workbench_issue_action_group(...)` 生成用户动作分组。
3. 摘要层统计动作分组，并按固定优先级输出。
4. UI 层按动作优先级排序可见问题。
5. 列表行显示结构化 badge、摘要、状态。
6. “处理”按钮仍然通过 `workbench_issue_action_target(...)` 跳到资料、模板、场景或插件确认入口。

这轮没有改修复目标模型，因此不会改变诊断到控件的路由边界。

## 5. 仍然不足

继续看还有明显缺口：

- 列表行虽然结构化了，但选中态还主要依赖 `QListWidget` 背景；自定义行 widget 没有单独做选中态联动。
- badge 还没有图标辅助，低视力或快速扫视场景下仍主要依赖文字。
- 问题详情仍然是说明型文案，下一步应压缩为“动作、影响、证据”三块。
- 问题队列仍在 `QuickExecutionDetail` 内部实现，长期应抽出共享 `IssueQueuePanel`。
- 动作排序目前是 UI 层排序，摘要层只负责统计；如果后续多个界面复用，排序规则也应上移为共享投影。
