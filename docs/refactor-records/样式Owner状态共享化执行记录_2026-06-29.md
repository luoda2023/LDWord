# 样式 Owner 状态共享化执行记录（2026-06-29）

后续进展：本文第 8 节提到的“模板基线与分区有效样式对照”已在 `docs/refactor-records/模板基线与分区样式对照执行记录_2026-06-29.md` 中推进为状态对照条。当前分区样式页已经能展示 `模板基线 / 当前分区 / 差异`。

## 1. 本轮目标

上一轮已经把场景规划中的“样式覆盖”改成了更清楚的“分区样式 / 独立样式”，并补上了从概览页进入 `scn_style_rules` 的链路。但模板管理和分区样式之间还有一个更深的差异：用户看到的“当前样式由谁控制、会影响哪里、为什么能不能编辑”仍然不是同一套表达。

本轮继续推进的是 `docs/audits/分区样式与模板管理一致性深度分析_2026-06-29.md` 中第 7.1 条：同源 owner 状态组件。

## 2. 发现的问题

### 2.1 模板页绕开了共享状态外壳

模板正文排版页已经使用 `StyleManagementBlock`，但原先同步样式时直接调用：

```python
self._style_surface.apply_state(template_body_style_owner_state(style).surface_state)
```

这意味着模板页只复用了底层字段表单，没有完整复用 `StyleManagementBlock -> StyleEditingSection -> owner state` 这条链路。

### 2.2 场景页有状态提示，但模板页没有同级表达

分区样式页通过 owner toolbar 的 hint 显示：

- 跟随模板
- 开启独立样式后可编辑
- 正在编辑某个分区

模板页则主要依赖摘要卡和按钮。用户能编辑，但缺少同等位置的“来源 / 影响 / 编辑状态”说明。

### 2.3 不能用长文案解决

用户之前明确指出界面“不说人话”，并要求删除冗余文本描述。因此这轮不能再加大段说明，而应该把状态压缩成稳定、短、可扫读的结构。

## 3. 本轮方案

新增共享控件 `StyleOwnerStatusStrip`，只显示三段短状态：

| 槽位 | 模板管理示例 | 分区样式示例 |
| --- | --- | --- |
| 来源 | 模板默认样式 | 跟随模板 / 已开启独立样式 / 已调整 N 项 |
| 影响 | 模板全局 | 来自模板 / 仅当前场景 / 处理范围未启用 |
| 编辑 | 可编辑 | 可编辑 / 开启独立样式后可编辑 / 不可编辑 |

它不替代摘要卡，也不替代预览。它只回答三个高频认知问题：

1. 当前样式从哪里来？
2. 改它会影响哪里？
3. 现在能不能编辑？

## 5. 为什么这个方案更接近优秀设计

### 5.1 一致性来自同一状态模型

之前的复用偏底层：字段控件、预览、表单布局是共享的；但“解释当前状态”的语言仍然散在模板摘要、场景 hint、场景 summary 里。

现在模板和场景都依赖 `StyleOwnerViewState`。这比单纯复制文案更稳，因为后续新增样式 owner 时，只要给出同一组状态字段，就能获得一致表达。

### 5.2 可读性不是靠更多说明

状态条只保留三段短文本：

```text
来源：...
影响：...
编辑：...
```

它避免了大段帮助说明，也避免了工程词。用户扫一眼就知道当前控件为什么能改、改了会影响哪里。

### 5.3 功能边界更清晰

- 模板管理：`影响：模板全局`
- 场景跟随模板：`影响：来自模板`
- 场景独立样式：`影响：仅当前场景`
- 分区未启用：`影响：处理范围未启用`

这比“覆盖/不覆盖”的二元状态更贴近用户任务。

## 9. 当前判断

本轮之后，样式功能的一致性从“控件复用”推进到了“状态解释复用”：

- 同一套 `StyleOwnerViewState` 描述模板和场景样式 owner。
- 同一套 `StyleOwnerStatusStrip` 展示来源、影响、编辑状态。
- 模板页不再绕过共享外壳。
- 场景分区样式不再只靠 hint 解释状态。

这一步没有解决所有高级交互，但已经把“模板管理与分区样式为什么一致、哪里不同、用户该怎么理解”放进了同一条可维护链路。
