# 资料规则选择 Block 首片抽象执行记录

日期：2026-06-30

## 1. 本轮目标

上一份《场景控件与模板管理语义复用再审记录》把输入资料详情的问题定位为：

```text
控件样式已复用，但资料规则仍是散落表单控件，不像模板管理里的样式 block。
```

本轮不继续只改文案，而是推进 P0 的第一片：把“资料规则选择、主规则、附加规则、未识别修复”收进一个语义对象，让 `_ContentDetail` 不再直接管理这一组控件的创建、写回和修复状态。

## 2. 改动前的问题

`_ContentDetail` 原先同时负责：

- 创建资料规则下拉框；
- 创建“设为主规则 / 加入列表 / 替换未识别 / 移除未识别”按钮；
- 创建主资料规则输入框；
- 创建资料规则列表输入框；
- 解析主规则和附加规则；
- 判断未识别规则；
- 推荐替换规则；
- 修改输入框文本；
- 回写 `scene.input_source_profile`；
- 处理诊断导航定位。

这和模板管理的成熟模式不一致。模板管理已经把样式编辑、来源状态、策略控制和预览逐步下沉到 block / projection / slot，而输入资料详情仍像一个“大页面脚本”。

## 3. 本轮实现

### 3.1 新增 `_MaterialRuleSelectorBlock`

新增内部语义块：

```text
_MaterialRuleSelectorBlock
```

当前职责：

- 持有资料规则选择工具条；
- 持有主资料规则输入；
- 持有资料规则列表输入；
- 统一应用模板管理同源的按钮和输入框样式；
- 提供 `set_scene(scene)`；
- 提供 `apply_to_profile(profile)`；
- 提供 `schema_ids_from_inputs()`；
- 提供 `navigation_widget_for_field(field_id)`；
- 负责未识别规则的替换和移除；
- 发出 `edited` 信号给 `_ContentDetail`。

### 3.2 `_ContentDetail` 改成语义调用

`_ContentDetail` 现在不再直接拼接资料规则列表，也不再直接计算替换按钮状态。

保留的页面职责：

- Markdown / LaTeX / 资料包必需；
- 必填字段；
- 资产角色；
- 失败策略；
- 水印；
- 摘要刷新；
- 将 block 的编辑信号接回 `scene_edited`。

资料规则职责下沉到 block：

```text
set_scene
apply_to_profile
sync_actions
navigation_widget_for_field
```

这让输入资料详情开始接近模板管理里 `StyleManagementBlock` / `SceneStyleRulesBlock` 的边界。

### 3.3 保留旧属性别名

为了不打断现有测试和外部定位，本轮保留旧属性名：

```text
_schema_registry_tools
_schema_registry_combo
_set_primary_schema_btn
_append_schema_btn
_replace_unknown_schema_btn
_remove_unknown_schema_btn
_material_schema_id
_material_schema_ids
```

这些属性现在都指向 `_material_rule_selector` 内部控件。

这是过渡策略，不是最终形态。后续测试和调用方应逐步从“拿按钮树”改为“调用 block 语义 API”。

## 4. 为什么暂时放在 `scene_panel.py`

本轮没有直接把 block 移到 `src/shared/ui`，原因是：

- 它仍依赖场景侧的资料规则 registry、推荐替换策略、`SceneWorkspace` family hints；
- 它还需要兼容 `_ContentDetail` 的旧属性和导航行为；
- 当前首要目标是收窄页面边界，而不是提前承诺跨页面公共组件。

更合理的演进路线是：

```text
同文件内部 block
-> 稳定语义 API
-> 测试从内部控件改为 block 语义
-> 移到独立 material_rule_selector_block.py
-> 供执行前复核或资料面板复用
```

## 5. 本轮用户可见变化

主界面基本不改变布局，只继续保持上一轮的人话文案：

```text
替换未识别
移除未识别
从上方选择资料规则，或输入规则 ID
每行一个资料规则；建议用上方“加入列表”
```

tooltip 也进一步避免把 `Schema` 当成主解释：

```text
当前资料规则均已识别
选择一个已登记的资料规则后可替换
将未识别规则 ... 替换为 ...
移除未识别规则 ...
```

真实规则 ID 仍会出现在 tooltip 和输入框值里，因为它们用于高级配置、诊断和审计。

## 8. 当前仍未完成的部分

本轮只是首片抽象，不宣称资料规则控件已经达到优秀状态。

仍要继续做：

### 8.1 测试脱离内部按钮树

现在很多测试仍直接点：

```text
panel._content._set_primary_schema_btn
panel._content._append_schema_btn
panel._content._replace_unknown_schema_btn
panel._content._remove_unknown_schema_btn
```

后续应逐步改成：

```text
selector.set_selected_schema_as_primary()
selector.append_selected_schema()
selector.replace_unrecognized_schemas()
selector.remove_unrecognized_schemas()
```

这样才算真正把页面层和按钮树解耦。

### 8.2 抽独立文件

当 block API 稳定后，应移动到：

```text
src/ui/panels/material_rule_selector_block.py
```

或者如果确定跨面板复用，再进入更通用的位置。

### 8.3 做规则预览

当前 block 只负责选择和修复，还没有像模板样式预览那样展示：

- 当前资料规则覆盖哪些字段；
- 哪些是必填字段；
- 哪些图片/附件角色会被要求；
- 当前场景族是否匹配。

这应该是下一轮最有价值的 UX 改善，因为它能把“资料规则”从 ID 输入变成可理解的业务预览。

### 8.4 进一步删除冗余说明

当资料规则预览出现后，很多摘要里的长说明可以继续减少。主界面只保留：

```text
当前用了哪些规则
是否识别通过
还缺什么
可执行什么修复
```

详细字段、英文说明和 raw ID 放到 tooltip / 证据 / 高级区域。

## 9. 下一步建议

下一轮建议继续做：

```text
资料规则预览摘要进入 block
```

具体可以先实现 block 内部一个轻量 summary/projection：

```text
规则：合同方字段资料、签章资料
字段：5 个必填
图片：2 个必填 / 3 个全部
状态：全部已识别
```

这样输入资料详情会更接近模板管理的“参数 + 预览 + 来源/状态”模型，而不是只是一组配置输入框。
