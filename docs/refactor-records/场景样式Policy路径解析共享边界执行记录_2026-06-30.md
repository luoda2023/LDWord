# 场景样式 Policy 路径解析共享边界执行记录

日期：2026-06-30

## 1. 本轮目标

上一轮已经打通模板正文样式与场景分区样式之间的双向定位：

```text
模板正文样式 policy 行
-> 场景分区样式
-> 返回模板正文样式
-> 同一 policy 行高亮
```

但实现里仍有一个不够优秀的点：模板详情和场景详情分别自己解析 `scene.section_styles.<variant>` 路径。

这会让两个页面虽然看起来打通了，底层却还是各说各话。后续只要新增一种路径写法，就可能出现模板能识别、场景不能识别，或场景能识别、模板不能识别的问题。

本轮目标是把“场景分区样式路径代表哪个 policy、后面跟哪个编辑字段”收成共享配置层 helper。

## 2. 修改前的问题

### 2.1 模板详情本地解析 policy key

`StyleDetail.focus_navigation_field(...)` 内部通过本地方法识别：

```text
scene.section_styles.references_body
section_styles.references_body
references_body
```

命中后再高亮模板正文样式中的只读 policy 行。

问题是这个解析不属于模板详情自身能力。模板详情只应该关心“我要高亮哪个 policy 行”，不应该重复知道场景路径的语法。

### 2.2 场景详情本地解析 variant 与字段

`ScenePanel._StyleRulesDetail._style_navigation_target(...)` 同样自己解析：

```text
scene.section_styles.references_body.font_cn
section_styles.references_body.font_cn
references_body.font_cn
```

命中后再切换到对应分区，并高亮具体字段控件。

问题是模板详情与场景详情都在维护同一套 variant key 识别逻辑，后续很容易漂移。

## 3. 本轮实现

### 3.1 新增共享 helper

新增位置：

```text
src/config/style_field_descriptors.py
```

新增能力：

```python
scene_style_navigation_target_from_field_id(field_id) -> tuple[str, str]
scene_style_policy_key_from_field_id(field_id) -> str
```

共享 helper 现在统一识别：

| 输入 | 输出 |
| --- | --- |
| `scene.section_styles.references_body.font_cn` | `("references_body", "font_cn")` |
| `section_styles.references_body.line_spacing_value` | `("references_body", "line_spacing_value")` |
| `references_body.special_indent_mode` | `("references_body", "special_indent_mode")` |
| `scene.section_styles.references_body` | `("references_body", "")` |
| `section_styles.acknowledgment_body` | policy key `acknowledgment_body` |

### 3.2 模板详情只消费 policy key

`src/ui/panels/template_style_detail.py` 不再保留：

```text
_style_variant_key(...)
_policy_key_from_navigation_field(...)
```

现在直接调用：

```python
policy_key = scene_style_policy_key_from_field_id(target)
```

模板详情因此只处理模板页该处理的事情：

```text
路径 -> policy key
policy key -> 只读 policy 行高亮
```

### 3.3 场景详情消费 variant 与 editor field

`src/ui/panels/scene_panel.py` 现在先调用：

```python
variant_key, editor_field = scene_style_navigation_target_from_field_id(target)
```

命中后再完成场景页自己的 UI 状态：

```text
切换当前分区
同步 policy 当前行
高亮字段控件或 policy toggle
```

## 4. 为什么没有全部抽走

这次只抽“稳定路径语义”，没有把所有场景样式定位逻辑都搬到配置层。

### 4.1 `scene.section_styles.*.font_cn` 仍留在场景页

`*` 不是一个真实分区 key。它需要根据当前场景状态选择一个可落地的分区：

```text
优先选已启用且已独立样式的分区
其次选已启用分区
再选已有独立样式分区
最后回到当前下拉分区
```

这依赖 `SceneWorkspace` 当前状态，不是纯路径解析。放进 `style_field_descriptors` 会让配置层反向知道页面状态，边界会变差。

### 4.2 `section_style.font_cn` 仍留在场景页

`section_style.font_cn` 表示“当前正在编辑的分区里的中文字体”。它没有携带 variant key，必须依赖场景页当前选择。

这也不是纯路径语义，而是页面上下文语义，所以仍由场景页处理。

## 5. 与模板管理一致性的收益

本轮收口后，模板管理和场景规划对同一条路径的理解变成一致入口：

```text
scene.section_styles.references_body.font_cn
          |
          v
style_field_descriptors.scene_style_navigation_target_from_field_id(...)
          |
          +-> 模板详情：高亮 references_body policy 行
          |
          +-> 场景详情：切到 references_body 并高亮 font_cn
```

这解决的是“高复用”里更深一层的问题：不是控件长得像，而是同一对象、同一路径、同一 policy key 在不同页面里的解释一致。

## 7. 当前仍需继续优化

### P0：诊断导航层也应迁移到共享 helper

`src/ui/adapters/workbench_issue_navigation.py` 仍有一套场景样式路径判断。它处理的是诊断投影和错误原因，逻辑更复杂，本轮暂未一起改。

下一步可以把其中普通路径识别迁移到同一 helper，只保留诊断层自己的错误原因判断：

```text
unknown_style_variant
unknown_style_field
missing_style_field
style_wildcard
```

### P0：页面板块仍需要继续按同一蓝图重排

路径解释一致只是底层语义一致。用户真正感知到的优秀设计，还需要继续统一板块：

```text
source：来自哪里
policy：哪些对象独立处理
editor：当前能改什么
preview：改完什么样
receipt：与基线差在哪里
```

模板详情已经越来越接近这个结构，场景概览和执行复核仍需要减少内部术语，把证据、契约、schema、英文规则下沉到诊断层。

### P1：只读 policy 与可编辑 policy 的行为协议继续收紧

模板详情中的场景覆盖是只读 policy，场景详情中的分区样式是可编辑 policy。两者应继续共享：

```text
current_policy_key
policy_selected
navigation_field_highlight
style_policy_row_current
```

差异只应来自 mode/projection，不应来自页面各自拼逻辑。

## 9. 本轮结论

这轮推进的是“看不见但决定一致性”的底层边界。

模板管理和场景规划现在不只是共用样式控件，也开始共用同一套场景样式路径语义。用户从模板只读覆盖项进入场景分区，再返回模板同一行时，背后用的是同一个 policy key 解释入口。

后续继续优化时，应优先把剩余诊断导航路径和页面板块蓝图纳入同一套协议，让功能分布更清楚，文案更少，状态更稳定。
